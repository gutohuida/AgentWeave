## Lessons

- A spec that adds API fields should name them and their response shapes. Otherwise the drive author invents them and every later task must follow the drive's docstring. (cites: ckpt-b68a6bf8d325)
- Place each requirement in the task whose acceptance criteria depend on it. read-ci's criteria needed the CI send-back and ready gate, so those were built a task early. (cites: ckpt-03a69573d447, ev-533368499124)
- Check that each acceptance precondition is reachable under the spec's own rules. The 'ready PR fails CI' start cannot happen when every fresh push is a draft. (cites: ev-c221875c411d)
- A real-GitHub acceptance drive needs a named owner and a step after the last behaviour task. Otherwise each reviewer defers it and the requirements stay at partial coverage. (cites: evr-ee6ed70afe12, evr-f4aa013df2e1)
- Say what happens after CI concludes. A re-run that fails on the same head is otherwise never noticed. (cites: ckpt-332c68d0748e)
- UI tasks that change hub/ui must rebuild the committed bundle against current master just before review. Otherwise the generated assets conflict. (cites: ttr-5f16fae8c8f0)
- When a spec builds on states from an earlier slice, such as the 'pushed' landing, list how the UI should show each of them. (cites: task-78e03a575910)
