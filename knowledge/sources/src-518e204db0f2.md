# Build retrospective of A check run finishes when master moves

## Lessons

- After this change, a check run on an older master tip that ends `error` or `interrupted` is retried only at the next refresh or approval. Only a `failed` run with no own failure is re-requested when it ends. (cites: ev-dc2bfa0b773a, evr-ccebe9f93a80)
- A move of master no longer ends a check run in flight. Only new work on the task branch, through _stop_run_on_older_work, supersedes a run, so a hung check now holds the task until it ends. (cites: ev-7be20c7bb115, ev-eb8b9d18d23a, ckpt-c8df1853cff0)
- The eight check and landing test files take more than 10 minutes serially on this machine. Run them with pytest -n 4, which takes about 2.5 minutes. (cites: run-549631454a69)
- Tests in test_checks_refresh_when_main_moves.py hold checks open with file-released gates in a sibling control directory. A new test that leaves a gate unreleased will hang. (cites: ckpt-c8df1853cff0)
- The full hub-tests gate can take well over an hour when its first xdist attempt crashes. Plan for the check gate, not the building, to dominate wall time. (cites: chk-b163130f844c)

## What to improve

- [specs] Say explicitly what should happen to a check run that ends `error` or `interrupted` on an older master tip, and to a check that hangs now that a master move no longer supersedes it. (cites: ckpt-c8df1853cff0, spreq-71274c1f58b4)
- [code_and_checks] Investigate the xdist worker crashes in hub-tests: "node down" followed by a KeyError in loadscope._assign_work_unit. Each crash costs a near-full rerun of the suite. (cites: chk-b163130f844c)
- [tooling] Make the stall detector treat an active check gate as progress, and make the mender able to resolve a build's task from the loop id. Both menders spent their runs on a slow check gate, and one wrongly reported a missing cron. (cites: stall-72ea858deaa3, stall-115d9ecc89b5, run-48fd37843c00)
- [tooling] Give builder checkouts git metadata and working dependency links (symbolic links on Windows), so agents can inspect their diff and run tests without workarounds. (cites: ckpt-c8df1853cff0, run-2db5b728048a)


## Superseded (note added 2026-11-04 by DeveloperOpus, task CKTPG-3)

The first lesson above, that an `error` or `interrupted` run on an older master tip is retried only at the next refresh or approval, is superseded by spec/changes/checks-know-their-phase-and-give-way-to-the-user/spec.json (spdoc-807a4baaa68f, FR-7 to FR-10) once CKTPG-3's work lands on main. From then on, what ended a run decides what happens next. A merge conflict sends the task back to its builder as merge-needed, and no run starts on the same work until its branch has a new commit (FR-7). A run interrupted by a Hub stop is requested again as soon as the Hub starts (FR-8). Any other error, or a check that runs out of time without naming a failing test, is retried once on the current tip right away. If that retry also fails to judge the work, it goes on the operator's Needs-you list as a `checks_unjudged` stall and the task stays where it is (FR-9, FR-10). Until that work lands on main, the lesson still describes the running Hub.
