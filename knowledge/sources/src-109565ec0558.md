# Agent visibility and per-spec stats — what slice 2 of the red thread showed (2026-10-24)

Operator request, 2026-10-24: keep this so we can explore it later and give the agents' work better
visibility. Nothing here is decided or specified yet; it is the starting material for a later
exploration.

## What the operator asked for

1. **Which spec a task came from is hard to see.** The operator could not find where the app says
   which specification document a task belongs to, and said it isn't intuitive.
2. **More information on the runs of each spec.** Stats for each spec, possibly on the spec itself:
   cost, how many runs, and similar.
3. **Evidence verdicts per runner.** How many pieces of evidence from each runner were accepted and
   rejected.
4. **How long each task took to complete.** So different models doing the development can be
   compared.

## What the app does today (checked 2026-10-24)

- Every task records its document (`tasks.spec_document_id`, `spec_task_key`), but the app hardly
  shows it. Only the Dependencies view (`hub/ui/src/components/tasks/DependencyListView.tsx`) groups
  tasks by document. Board cards (`TaskCardCompact.tsx`) and the task drawer (`TaskDetailDrawer.tsx`)
  don't name it.
- Tasks filed in the middle of a flow (follow-ups, defects QA found) often belong to no document. Of
  the 5 open follow-ups from slice 2, only `task-6ac1bb3d4d39` is linked to the slice's document.
- Everything the stats need is already recorded, so this is a missing summary and display, not
  missing history:
  - `runs` (agent, task_id, started_at, ended_at, status)
  - `turn_usage` (runner, model, tokens, `api_equivalent_usd_micros` per run)
  - `task_transitions` (every status change, with actor and time)
  - `requirement_evidence` with `evidence_reviews` (who produced each piece of evidence and who
    decided it)
- The manager settings page already shows a cost per firing for manager jobs, with no total
  (`ManagerSettings.tsx`).

## A caveat for comparing models by evidence verdicts

A rejected piece of evidence does not mean that evidence was wrong. When the reviewer sends a task
back, it rejects every piece of evidence from that commit, including the ones that held up. QA said
this explicitly in its slice-1 rejection of `task-9ade8679f06a`: FR-4, FR-7, FR-8 and FR-12 "held in
what I ran, but they are rejected with this verdict because they come from the same commit". A raw
accepted/rejected ratio therefore mostly counts rounds back to the developer multiplied by the number
of requirements per task.

Measures that compare models more fairly:

- Rounds back to the developer per task (`revision_needed` transitions)
- Time from first `in_progress` to `approved` per task, and active run minutes as opposed to wall
  clock
- Cost per approved task, split between building and reviewing runs
- Failed runs per agent and model

## Open questions for the later exploration (not answered yet)

1. **Where do per-spec stats live?** The suggestion was to show them on the document's page,
   computed live from what the Hub records, rather than writing them into `spec.json`. Writing them
   into the file would create a git change on every run and go out of date between runs. The
   operator originally said "on the spec file", so check what they meant.
2. **How wide is the model comparison?** Within one spec only, or across specs (a project-wide
   leaderboard of runners and models)? Does the cost of the reviewer's runs count against the model
   that did the building?
3. **Where does a task name its document?** On the board card, in the drawer, or both? Should a task
   with no document say so? Should follow-up tasks filed mid-flow be linked to the document that
   produced them?
4. Should the Thread (red-thread roadmap) carry these stats on its knots, or is that a separate
   surface?
