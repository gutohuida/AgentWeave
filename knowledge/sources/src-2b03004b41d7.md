Decisions taken while building (Architect's defaults; the operator may change them):
- A fourth kind, `reply`, **on by default**, with its own switch in Sound and notifications.
- It plays the brand's **'ready'** pair (the bright one); there is no new sound.
- It is **silent while the window is in front and showing that conversation**. Elsewhere, or with
  the window behind, it behaves like the other kinds (toast, quiet or normal sound, title count,
  taskbar flash).
- In a burst, ask and fail outrank it, so a reply that ends with a question sounds once, as ask.
- The toast's Open goes to the conversation, not to the project overview.
- Hub: `_broadcast_run_lifecycle` now puts the run's `initiator` on every run lifecycle event.

# Original request (as recorded before it was built)

Recorded 2026-10-23 by Architect at the operator's request. The operator asked whether the
notifications fire "when an agent responded to the user ... like in this conversation". They do
not. Not yet specified.

## Today

The notifier (`hub/ui/src/lib/notify/classify.ts:25-48`, change
agentweave-calls-you-with-its-own-sound) sounds only for these events:

- **ask:** question_asked, permission_requested
- **fail:** stall_recorded, run_failed, queue_chain_suspended, loop_stopped
- **done:** loop_stopped with reason 'loop queue is empty'

A finished agent turn (`run_completed`) is ignored on purpose. The spec's acceptance criterion
says "nothing for run_completed". The likely reason is that `run_completed` fires for every run
in every project, flows and loops included, which would be constant noise.

## What the operator wants

A sound (and a toast or title count) when **an agent finishes replying in a conversation the
operator is chatting in**: the operator sends a message, the agent works for minutes, and the
operator is looking elsewhere or the window is behind.

## What it rests on (from the code on master 5f5616c)

- `run_completed` is broadcast by `_broadcast_run_lifecycle` (`hub/hub/api/v1/agent_trigger.py:2770`).
  Its payload carries `agent`, `run_id`, `conversation_id`, `session_id` and `exit_code`
  (`agent_trigger.py:3735-3744`), stamped with `project_id`.
- It does **not** say what started the run: an operator message, or a flow, loop, job or another
  agent's message. That is what separates "replied to you" from "an automatic run ended". The run
  knows it (this run's environment carries AW_TURN_DEPTH=0, "Operator (hop 0)"), but the event does
  not expose it. So this needs a small Hub change, adding the trigger or origin to the payload,
  plus a new kind in the UI notifier.

## Open decisions (operator's)

1. A fourth kind, "reply", with its own switch in Sound and notifications. On by default?
2. Should it sound when the operator is already looking at that same conversation, or only when
   they are elsewhere or the window is behind?
3. Which sound? The brand set has ask, done and fail (`brand/sound/agentweave-sound.js`). Reuse
   done, or add a reply phrase to the brand kit?
4. A reply that ends by asking a question already produces an ask (`question_asked`). It should
   not sound twice.
5. Does a turn that failed or was stopped in the operator's conversation already count as fail
   (run_failed), and should a stopped one be silent?

Next step: a small Tier 1 change spec. It needs one Hub field and one UI kind, with an acceptance
drive: send a message in a conversation, switch away, and the reply sounds and toasts naming the
agent.
