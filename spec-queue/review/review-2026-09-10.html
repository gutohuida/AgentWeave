The argument

F309 and F310 read as two defects on one screen. They are one failure: two mechanisms act on one keystroke, and the one further from the operator wins. In F310 a nested control answers Escape and a hook bound on document answers it again; in F309 a menu's focus-restore — scheduled after React has mounted the very input the menu's own selection asked for — wins over that input's autoFocus. Neither is a broken control: the mouse path works perfectly in both cases. So the fix is not new behaviour but arbitration, in both halves: the hook stands down on an Escape that has already been defaultPrevented, and a menu item that opens a control expecting input tells the menu not to take focus back. The signal is event.defaultPrevented and nothing else, and there is no setTimeout anywhere in the design — the ordering was read in the dependency's own source rather than remembered.

What each round changed — and none of the three came back empty

Lead with this one, because it is the clearest evidence the round discipline earns its keep. R1 found a third instance of F310 that nobody has ever driven: the directory browser inside the project modal (DirectoryPicker.tsx, mounted in ProjectManagerModal.tsx whose useDialogFocus is active). R1 concluded it was repaired for free by the hook change, because the picker already calls preventDefault(). R2 re-read the same file and agreed. The task list said, in as many words, "Change nothing in DirectoryPicker.tsx."

R3 found that the handler cannot run at all. It is a React onKeyDown bound to the picker's own root div, and nothing in the file ever focuses that root — opening the browser leaves focus on the Browse… button, a sibling of the picker. React dispatches a synthetic event along the React tree from the target, so the keystroke never travels through the picker's subtree, preventDefault() never runs, and the arbitration condition is false. The modal closes and takes the browser with it. The cost is identical to F310; the mechanism is not — which is exactly why two rounds reading for outcomes agreed on the wrong one. The change's own design had already argued this point in the opposite direction, three sections earlier, and could not have been right both times.

R3's second finding: a scenario falsified by correct behaviour

One scenario in the deltas — "typing an answer does not operate the menu" — had no task producing its evidence in any round, and its second clause read "no part of the surface becomes unresponsive to the pointer while they type." That is false of the correctly fixed product: the drawer renders a position: fixed; inset: 0 scrim that deliberately makes the board behind it unresponsive, and the drawer's own click-outside listener depends on it. Archiving that sentence would have recorded a shipped, intentional behaviour as a defect. Narrowed to "does not stop answering the pointer because a menu re-opened over it", and given evidence by a new task that extends a probe already reading both facts.

The general form, worth reusing — this is what a third round is actually for. A proposal can be right about the code and still write a delta that claims more than the change delivers (R2's finding, and R3's picker) or that a shipped behaviour contradicts (R3's scrim). Neither over-claim rides in on a statement about the source, so a round that only re-checks line citations cannot see either — R2 re-derived every one of R1's citations and they all held. The test that catches both is two questions: name the task that produces this scenario's evidence, and ask whether it can; then, if it can, ask what already-shipped behaviour would make the scenario false.

A corollary the loop should keep: a round that re-reads what the previous round already re-read is the low-yield round. R3 was told what to attack rather than told to be thorough, and it found the change's largest defect inside a file R2 had also opened.

DAY-1 — should this change swallow F307?

It deliberately does not, and this is a scoping decision you may want to reverse. F307 is the Tab branch of the same hook — focus never moves into the panel on activation, so the first Tab escapes to whatever follows in DOM order, measured landing in the instructions textarea behind the scrim and driven all the way to a wrong write today (§3). The three reasons for leaving it out:

  1. It is a different question. F307 asks where focus starts; this change asks who answers a keystroke. Neither answer constrains the other.
  2. Its fix needs a decision no window should make alone. Moving focus into the panel means focusing the panel's first focusable — which in a destructive confirmation is Cancel — or its last, which is the destructive button itself. F307 says so in its own words and declines to guess. That is a decision for this page, not for a proposal.
  3. It reaches five dialogs this drive never opened. This change touches the sixth. Widening it would put a keyboard repair on a mandatory path behind a design question about five screens that are not broken in this way.

What holds either way: if F307 is later fixed by binding Escape on the panel instead of on document, this change's arbitration rule still holds — it is about who answers, not about where focus is. And one carve-out already exists: the change does place initial focus in the directory picker, because without it R3's finding cannot be demonstrated on any surface. That is one component chosen for a named reason, and the tasks say so to the implementer.

Answer only if you want to change it. No answer means the split above stands and F307 stays open for a change of its own.
