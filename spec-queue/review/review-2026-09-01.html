Row 16 — Logs, Events and SSE — was driven last, and it is the row where what the Hub says and what any screen can hear turn out to be two different vocabularies. t_sweep_row16_logs_events_sse.py, 44 passed / 15 failed, run twice on the state the first run left with an identical failure set, on one real claude-haiku-4-5 turn per run. Nine of the seventeen have UI code written to handle them, which is what turns an unused vocabulary into a defect. useCheckpoints subscribes to checkpoint_ready and conversation_cut_over, and its own docstring says what happens without that subscription: "the checkpoint was generated, probed and stored, and the operator saw nothing until they happened to reload." That is the behaviour today — the subscription exists and is never called. eventSummary.ts carries a written operator-facing sentence for six more (task_blocked, task_unblocked, run_diverged, run_divergence_resolved, queue_agent_paused, review_unstaffed). And this has happened before: useSSE.ts:530 records six loop events that "were absent from SSE_EVENT_TYPES above and silently dropped" until someone noticed, and the test suite has two tests of exactly that shape, one per batch someone noticed. No test compares the array against the Hub's broadcast vocabulary, so the next name added on the server is dropped by default.

The Logs screen renders the oldest 500 events a project ever recorded. useLogs asks for limit=500 with no offset and list_logs orders timestamp.asc(), so the window is events 1–500 of the whole history and nothing after the five-hundredth is reachable from that page — which passes no since, no offset and no limit. Live mode makes it worse: it invalidates on every SSE event and refetches the same oldest 500. This is not a synthetic condition. On proj-18e5d4e0, a real project on this instance that the drive only read, the screen's own request ends at 2026-08-24 11:26 while the project's newest event is 2026-08-27 04:15 — three days it cannot reach, growing by every event since. The same table through /events/history returns the newest correctly, so the two read routes over event_logs disagree about which end of a log an operator wants, and the one wired to the Logs page picked the wrong end.

A subscriber that falls behind loses events silently. One instance-stream client that stops reading, then 3,000 events pushed through: 1,574 of 3,000 arrived, the same count on both runs. SSEManager.broadcast drops on QueueFull at 256 deep and says nothing to anyone — the wire carries no id: field, no sequence and no gap marker, and the connection is never closed, so the client's one catch-up mechanism (onSseReconnect → invalidateQueries, which fires on reconnect) never runs. A client that lost half the stream looks exactly like a client watching an idle project. The drop itself is a defensible choice; the silence is the finding. For scale, 3,000 events in 15 seconds is not an operator typing — it is one verbose turn, which broadcasts per streamed chunk, reaching a backgrounded tab.

The problem

openspec/specs/runner-registry/spec.md:72-73 is a shipped requirement, not a proposal: "Runner management SHALL offer the catalog's models for the chosen provider rather than accepting free-typed text." The screen does not — RunnersPage.tsx:228-238 is a free-text <Input> — and when the backend refuses what the screen let the operator type, the screen says nothing at all. useCreateRunner/useUpdateRunner declare onSuccess and no onError; main.tsx configures no MutationCache handler and no toast. The argument

Replace the free-text field with a select built from GET /model-catalog, and give RunnerForm the error surface it has never had, reusing the app's existing readableApiError idiom rather than inventing one. The scope call is deliberate and written into design.md: the change stays inside runner management. 1 · Name and test the context-elevation boundary S

"When Context Gets Root" (arXiv 2608.27299) achieved 13 of 13 attack objectives on all six coding harnesses tested, including all three that offer automatic permission review, by getting the harness to promote low-privilege text into the system prompt. For AgentWeave: four defences already hold — the context file is re-rendered from Hub state every turn, request_agent takes a template rather than text, agent jobs are off by default, and spec bodies stay behind a tool call. But one agent-authored string does reach another agent's system prompt (a task title, 256 characters, unescaped, into the reviewer's context), and nothing tests the property — it rests on statement ordering, so a refactor removes it with a green board. Sell it as an undefended property, not a vulnerability; the exploit alone will not survive contact with the code.

2 · Record the runner CLI version on every run S/M

Claude Code v2.1.251 (2026-08-28) fixed four permission-boundary defects in one release, including a post-check symlink swap that read and wrote outside the approved location. For AgentWeave: the Hub answers permission prompts, but the CLI's own engine opens the file — and every one of those four defects lived in that engine. The Hub records no CLI version anywhere, so two runs a week apart under identical settings can have materially different containment and nothing in the record distinguishes them. Take the cheap half only (capture it, store it on the run, show it in diagnostics); a minimum-version gate is a support burden that should wait for a second machine to exist.

The drift surface (run 1's candidate 2) is stronger than when it was filed: grep -rn 'spec/drift' hub/ui/src/ still returns nothing, while the night filed F178, F206 and F211 and today filed F215 and F225 — that is now a pattern with a name, routes shipped without an operator surface, rather than one orphaned feature. F225 is the same shape on a router that is otherwise fully on the operator's screen, which is the version that is hardest to notice: the jobs UI is complete, so the two missing loop actions look like a gap in a feature rather than a feature with no surface.

Row 11 supplies the counter-example that keeps the pattern honest, and it is worth reading before treating "route with no surface" as a universal diagnosis. Decline is in the served bundle, so F229 is only a D. What it is missing is not a call site but a place: the one screen named after the feature cannot reach it. That variant is worse than an orphaned route in one respect — the operator is not stuck, they are quietly split across two screens that disagree, which is how F228 turns into F227 and costs a real turn. A repair aimed only at "is there a call site anywhere" would score this router green.

Row 12 supplies a third variant, and it is the subtlest of the three. The permissions router is fully surfaced — every route in the served bundle, a card component, a dismiss button, the whole thing wired. What is missing is a query: the app issues one URL and the route understands two, so the decided history the route keeps on purpose is unreachable from any screen (F231). Grepping for orphaned routes finds nothing here; grepping for orphaned parameters would. If the operator wants one repair out of this, the cheapest by a wide margin is a screen that answers "what have I allowed?" — the read side already exists and already works over HTTP.
