The problem

A run that has ended is supposed to release what was waiting behind it — the agent's own input, queued while the run was busy, and any other agent parked behind the task checkout the run held. Both are released by exactly one call, redrain_queued_agents(project_id), and nothing in the Hub runs on a timer to do it later; the code says so of itself at agent_trigger.py:1908: “Nothing does on a timer.” _execute_run places that call last, at :2281. The run's terminal status is committed far earlier, at :2175. Between those two lines the function does real work that can raise — five calls, each because it does uncaught database work. The handler at :2282 catches all of it and computes one flag, already_terminal, then uses it to answer two different questions. The first use is right: do not relabel a cleanly-ended run as failed because later bookkeeping raised. The second is the redrain at :2358, which sits inside if not already_terminal: — even though its own comment claims to be “[u]nconditional”. So the redrain is skipped in exactly the window where the normal path's redrain was also skipped. The run is correctly terminal, correctly labelled and correctly broadcast, and the input behind it is queued with nobody coming for it — reconcile_interrupted_runs does not recover it either, because it selects only Run.status == "running" (run_reconciliation.py:60). The entry then waits for an unrelated operator action — opening the project, saving settings, relocating the workspace — and is delivered by coincidence. The operator-visible shape is a message that simply never runs. This is observed, not derived: it is one of the three CI failures above, delivered_in_run_id is None for an entry queued behind a stopped run.

What R1 found on its own account

R1 corrected the finding, and the correction is worse than the finding. F286 said the Codex app-server path “reaches the same handler.” It does not: _execute_run delegates and returns above its own try blocks, and the app-server function's outer construct is try:/finally: with no except clause at all. An exception there escapes into a task whose only done-callback is a set discard. After that path's terminal commit it is F286 with no redrain attempt and no logger.exception; before it, the Run row stays running with error=None and the agent is wedged until a Hub restart — app-server runs never set Run.pid, so nothing can reap it.

What R2 changed — it did not change nothing

  • The change is a restoration, not a pure gap — and this is the one that changes what the proposal argues. R1 said the shipped requirement “Repeated delivery failure does not wedge an agent” (spec.md:1228) does not reach F286, because the entry is never returned.   • R1's delivery-attempt accounting was a false dichotomy. Nothing charges on delivery; the charge sites are a failed run returning an entry and a non-transient refusal.
