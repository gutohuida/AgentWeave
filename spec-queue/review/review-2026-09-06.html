The defect, in one line

When the GET that loads a project's instructions fails, the Instructions page renders exactly what it renders for a project that has never had any: an empty textarea with an enabled Save button. One click, with nothing typed, replaces the project's instructions with the empty string. Nothing on screen says a load failed, before, during or after. 

stored before Save: 'ALPHA PROJECT RULES\n\n- Never force-push.\n- Every PR needs a test.\n'
stored after  Save: ''

Why severity A rather than B. Project instructions are prepended to every agent's canonical turn context and to every charter the Hub serves, and both consumers gate on the content being non-empty — agents.py:1529-1533 emits ## Project Instructions only if project_instructions:, and get_charter_context prepends only if instructions_row and instructions_row.content (:2119-2121). So blanking the row does not degrade the context, it removes the section entirely, and every charter silently reverts to its unprepended text. No history, no undo, no confirmation.

The gate is data present, not isError — and that is a decision, not a detail

R1 built a four-state table from the installed query-core (isLoading = isPending && isFetching, queryObserver.js:310; @tanstack/react-query 5.90.21 bundled, ^5.62.16 being the declared floor) and found two states fall through to the editor today, not one: error, and a disabled query. Gating on "not errored" would fix one of them.

Ordering is load-bearing and is its own scenario. data is checked before isError, so a background refetch failure cannot take a loaded editor away from an operator mid-edit. query-core ships R1's ordering as two named flags — isLoadingError = isError && !hasData and isRefetchError — which is corroboration, not the source.

InstructionsPage never reads saveMutation.isError or .error: :20-26 binds isSuccess alone. A rejected PUT re-enables the button, renders nothing, and leaves the operator believing the save landed.

Folded into this change as tasks 1.6 and 2.8 rather than filed separately, on three recorded grounds: it is measured on one page, it is the same defect class in the same component — the page saying something untrue about its own state — and it needs no delta, since the requirement already binds. A page that starts announcing read failures while still swallowing save failures is less coherent than one that announced neither.

The other direction is clean. A configuration section states what it governs survives the new failure state, because SettingsSection renders title and description in the heading (:45-57), outside the {children} the branch replaces — but only if the implementation replaces the branch rather than the whole section. That is an easy and invisible way to breach it, so it is now task 1.5.

DAY-3 — should a save that blanks non-empty instructions confirm first?

This change deliberately leaves that alone. The empty string is a value the route accepts on purpose — InstructionsUpdate's docstring records that the field was named precisely so no mis-shaped body could blank the row — and "clear my instructions" is a legitimate ask. Whether the product should nonetheless confirm before a destructive overwrite is yours, not the loop's.

Recorded in design.md as an explicitly rejected alternative, with the note that it would not be sufficient on its own: it does nothing about the misleading empty editor, and a client that cannot tell "not loaded" from "empty" would still be lying to you with the confirmation dialog on screen.
