DAY-3 — posture on a harness that blocks MCP carried from last night, enlarged

The question. On a harness that blocks MCP by policy, what permission posture should an unstated claude run get? Today it gets manual plus an approver flag naming an MCP tool that will never answer, and F299 measures the consequence: every mutating tool call is denied and the model tells the operator their machine is misconfigured.

Why it is yours. Every remedy moves containment, and agent-capability-plane says in as many words that the containment a run gets is the operator's to decide, separately from what the run is told. Resolving to cli on an inference hands every unstated claude run acceptEdits, which has no path check at all (runner_commands.py:66-67). Keeping manual and dropping the approver denies everything anyway, with nobody headless to ask. Leaving it as it is leaves F299. There is no non-widening, non-breaking option, so it is not the implementing window's to guess.

What shipped meanwhile, and how it grew. The description is now honest — such a run is told the HTTP form, and the plane works for it — and the posture is untouched, so nothing widened. The one-line workaround is hub_client: "cli", already documented in src/agentweave/config.py:714 as "uncomment if MCP is blocked by company policy". What it silently buys is acceptEdits, and nothing in the UI says so. Enlarged 2026-09-09 by F300 and F301: there is no posture on this machine on which a claude run can use the HTTP form of the plane under its own power — the default workspace posture's own approver denies the URL as a path outside the workspace (mcp_server.py:936), and the cli path's acceptEdits has no approver to overrule a harness that statically refuses an interpolated credential. So hub_client: "cli" restores writes, not access, and the choice in front of you now includes a third question the original did not: whether the workspace approver should recognise a URL at all.
