The problem

A conversation renders turns; each turn shows how its run ended. The outcomes come from a different query than the turns do — the timeline route, which returns a run-facts map built over the last fifty merged events for the whole agent. So work the agent does in other conversations pushes this conversation's runs out of the window, and turns that are finished, on screen, and unchanged silently lose their outcome. The two windows have never agreed and nothing made them: one is scoped to the agent and capped at fifty events, the other is scoped to the conversation and — measured, not assumed — capped at nothing. get_chat_history applies no .limit() on any of its three queries. That kills the obvious cheaper fix outright: no widening of the event window can be large enough by construction.

The fix is that the map travels with the turns. Both chat-history responses gain runs: Dict[str, RunFacts], built by primary-key lookup over the run ids their own returned entries name — the same coverage-by-construction the timeline route already uses, applied to the query the client actually renders. AgentTimeline takes its runs prop from the chat response instead of the timeline query.

What R1 found on its own account, and it corrects the ledger

F274 said the route was not in breach and that no requirement covered the case. The second half is false. A run's terminal outcome is visible (agent-stream-events/spec.md:299) is quantified over the conversation, requires an outcome for every run that ended, and permits none only for "a run whose row genuinely cannot be found" — F274's runs have rows. The corpus already forbade this. What hid it is that requirement's own next sentence, which cross-references a rule quantified over the runs a returned event names — so it cannot forbid omitting a run that no returned event names, which is the whole of F274. The corpus forbids the behaviour and simultaneously points at the wrong rule. The delta carries a MODIFIED requirement that repoints the cross-reference and says what went wrong with it, and F274's ledger entry now carries the correction.

2 — The review's independence check tests a name S/M

review_dispatch_refusal refuses completing_agent == reviewer, but two agents may share one runner_id, and a runner is a (cli, model) pair. arXiv 2609.01873 (2026-09-01) measures what that costs when reports multiply from one evidence root: naive posterior coverage 0.940 → 0.263. What it would mean here: the 403 that reads as an independence guarantee is, in the ordinary configuration, a guarantee about naming — and AgentWeave currently cannot say how independent any review was, so an operator reading three green reviews cannot tell three evidence roots from one. This page is itself an instance: today's three "independent" rounds ran on one runner. The change records the reviewer's resolved (cli, model) at dispatch and a same-runner flag; it must not become a fourth refusal status, which would lock a single-CLI operator out of reviewing anything.

3 — The context number has no composition S/M

Measured on a real rendered context: 6,831 of 7,817 bytes (87%) is the ## Your tools blurb. agent-context-usage has 18 requirements and every one measures the total; none names a contributor. What it would mean here: AgentWeave writes that file with named sections and therefore knows its composition by construction, but reports only a percentage — an operator at 60% cannot learn that most of what the Hub put there describes tools rather than the job. It is arithmetic on a string the product already holds. The research argues against its own candidate honestly: 7.8 KB is under 1% of a 1M window, so if the real problem is a 600 KB file the agent read, this is precise and useless — and the correct outcome may be a line in the spec saying so and no feature.
