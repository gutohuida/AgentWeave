4.1 a-spent-allowance-holds-the-queue — F355 B built · driven · archived

The problem. A provider refused a turn at its session limit. The Hub counted that as a delivery failure and re-delivered twice, about 10 s apart, into the same exhausted allowance. Then it gave the input up: "delivery failed 3 times; the Hub stopped retrying". On LoopEngine, 25 entries were withdrawn this way, a review among them, and the */5 job kept re-queuing into the wall.

The argument. A refusal is recognisable from what the Hub already records. Read mode=ro, 69 of 69 session-limit runs carry turn_usage.allowance status rejected with an epoch resetsAt, and 0 of 205 completed runs do. So the change works like this:

  • A refused turn is not counted, its session is kept, and its input is never withdrawn.
  • The agent is held. The hold is derived from its newest informative usage row, with a 60 s floor.
  • New operator input probes the allowance once.
  • A date job wakes the agent at the reset.
  • The loop's busy guard answers held, and plain jobs coalesce.

What each round changed.

  • R2 found that flows did not inherit the hold: decide_firing re-briefed a held assignee every tick. It armed the wake at every refusal's run end, not only failed ones, and it filed F368.
  • R3 found that R2's repair made a held assignee's task read as in flight on its assignment alone. That breaches a shipped agent-loops requirement. It also added D11: pressing Run on a held loop answered "already being worked … nothing is wrong" or a 500. That is F127, now retired.
  • The review said proceed. It restored a shipped agent-loops sentence that R3 had made false for every flow. It gave the board the guard's reason instead of "stalled: no claimable task" for the length of a hold. It closed a race in D11: F369, filed and retired.

4.3 a-late-answer-is-delivered — F356 B specced through review · not built

The problem. An answer to ask_user can arrive after the tool's wait has ended but while the asking run still lives. No later prompt carries it, and nothing calls get_answer for it, so it reaches nobody. The ledger was corrected on the way, by a mode=ro read: only 1 of F356's three batches was lost (09-13 14:38). The 23:26 and 16:50 batches were delivered by the shipped run-has-ended path.

The argument. Still waiting becomes: blocking, wait_ended_at IS NULL, and the run live. That is the tool's own report, not wait_expires_at, because the tool polls about 2 s past the Hub's deadline. The expiry report delivers an answer that landed after the tool's last poll, once per batch. Both writers decide after commit, so the worst case is a duplicate, never a loss. There is no receipt stamp (D5), so a residual is named and left to you.

What each round changed.

  • R2 found that the report could still lose an answer that committed between its load and its write. Both writers declined, so the report now takes its keys from the rows it stamped, re-read after commit (task 2.9). It found a pre-existing race that put wait_ended_at on a declined row, closed with a guarded UPDATE … AND declined IS FALSE (task 2.8). It corrected D5's cost.
  • R3 measured R2's fix on aiosqlite with the real Question model. The guard gives rowcount 0 on a mid-report decline. But the default synchronize_session still stamps the loaded object, so synchronize_session=False is required, and only populate_existing makes the re-read fresh. It collapsed the report to one decision point, because two of R2's mutations could not fire. The run-end sweep is a second writer with the same race, so both writers now go through one helper (task 2.10). D5 was kept, with a three-route table.
  • The review (Opus) did not stop the change. It found:
    • a fourth loss that R1–R3 missed: when a sibling is declined mid-report, _completed_batch judges on stale identity-map rows, and both writers decline (task 2.11);
    • a trap in the sweep rewrite that would park a declined question's task (2.10);
    • that the comment "a declined question never carries wait_ended_at" is false in shipped code (task 1.6, comments only; the guard stays).
