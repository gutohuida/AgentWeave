4 · What was specced

A — an-at-mention-an-agent-wrote-reads-no-file (F409, severity A)

The problem. Every Hub turn's whole prompt goes on the claude CLI's command line. Before the model runs, the CLI itself expands any @path token in that text into an attached file read — no tool call, so no posture and no disallowed-tools list ever sees it. The prompt is mostly text the operator did not write: another agent's send_message, a job or loop briefing an agent can author, a checkpoint delivery, a delegation. So one agent's text can make another agent's turn read any file the Hub's own user account can read, silently. Measured live on claude 2.1.280: a marker file outside the workspace, every file tool disallowed, returned with 0 tool calls — the CLI's own session transcript shows the attachment.

The argument, in brief. Escape every @ in non-operator text to \@ before it reaches a runner (measured: the CLI never expands one preceded by \, whatever precedes that backslash) — unconditionally, because the CLI's whitespace set (JavaScript's) diverges from a narrower rule's (U+FEFF expands a mention and is not whitespace to Python's \s). format_turn_prompt neutralises every non-operator block; the question echo and the board's Start work text are escaped where they are composed, since they mix operator and agent authorship. The turn's preamble names the substitution once, when it fired. A new probe, scripts/drive/d2_0923_at_mention_tokeniser.py, pins the CLI's own tokeniser behaviour and fails on a CLI upgrade that changes it.

What R2 changed. Widened scope: the Hub's two one-shot workers — the checkpoint worker and the conversation titler — also put agent-authored text on their own claude -p calls with no posture at all, and were measured to expand an outside @path; the checkpoint worker's reply carried the file's contents, which would reach a stored checkpoint and the successor agent. New design D7 neutralises both workers' whole prompt. The D6 "here's why" trigger moved to "the blocks contain \@", because R1's rule missed the escaped question echo. Closed: the Hub's notices, the divergence path (already covered by D3), the --append-system-prompt-file context file (measured not to expand), and the trust boundary on /agent/trigger. Filed F410 (C, out of scope): checkpoint and divergence blocks reach the agent labelled Agent "None".

What R3 changed. Found a second mixed-author vector R1 and R2 both missed: the board's Start work button posts Work on task <id>: <title> as an operator message, and an agent can author the title (new design D8) — this pulls the UI and its bundle into the change's impact. R3 also replaced D7's "stored worker output carries no \@" prompt-rule (which R2 itself had already found one Windows-separator residual in) with an exact code-side inverse, restore_file_mentions, checked exhaustively over 5,460 short strings with 0 failures; made the probe's grading symmetric; and offered dropping the Start-work title entirely as Q3 instead of escaping it.

B — pressing-run-names-the-reason-that-held (F400 + F373, severity B)

The problem. agent-loops requires that a 409 from pressing Run names the real reason a firing declined. Two of its answers are false. F400: since a-loop-staffs-the-agent-it-names (archived 09-22), a documentless loop's work goes only to the agent its job names, so when that agent is busy the refusal is never about the roster — yet the route still answers "no other agent is free to take this loop's work". Measured with a sibling agent free: the sentence is false, and the code's own comment says restaffing "changes nothing". F373: an in-flight decline writes no row, so the route's fallback to latest_run answers from an unrelated, possibly hour-old, earlier firing's stall. Measured: a flow whose only task was being actively worked was answered "loop queue is stalled: 1 still awaiting a prerequisite's approval".

The argument, in brief.
