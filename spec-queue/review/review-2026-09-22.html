6 · Research, briefly

One ranked candidate today (S cost). AgentWeave's agent-plane writes (send_message, create_task) have no retry-safe identifier: a Hub timeout on the client side (measured live — a slow response surfaces as a bare TimeoutError, caught by neither of _hub_request's two exception branches) can hit an agent after the server has already committed the write and started scheduling the recipient. A retry then writes it twice. create_task is one field away from safe — the Hub already accepts and dedupes a client-supplied task id (since 2026-06-17), but the MCP tool stopped sending one. send_message has no id field at all. The motivating evidence is that openai/codex merged the same primitive (an agent message board with caller-supplied, deduplicated request IDs) as eight PRs on 2026-09-21. Measured on the live instance (read-only, mode=ro): 274 agent-sent messages and 23 agent-created tasks over five days, zero duplicates — so this is latent, not observed. What it would mean for AgentWeave: a client-minted, Hub-deduplicated id on both writes, so a timed-out retry becomes a no-op instead of a second recipient turn or a second task — closing the same class of bug the ledger already has open once from the UI side (F315).
