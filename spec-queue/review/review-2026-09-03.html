4What was specced — a-blocked-agent-workspace-holds-its-input

For F188 (A). Three rounds ran. openspec validate --strict passes. Nothing under hub/hub/, hub/ui/ or src/ is committed from today.

The problem

Two refusals stop an agent from running. One holds the operator's message until they perform the repair; the other destroys it on the third schedule. They are eleven lines apart in the same function and the difference is a keyword argument. agent_trigger.py:879-883 raises the worktree refusal with no agent_wide=True; the three sibling refusals at :573, :594 and :624 all pass it, and turn_scheduler.py:204 reads that flag to decide whether a delivery attempt is counted. Both conditions are ones only the operator can clear; both stop the agent starting; one of them eats the message. Worse, the control the conversation view offers for exactly this situation — the Continue button — is itself a schedule, so the operator's attempts to find out why nothing is happening are what consume the allowance. F114 reproduced verbatim at a site the F114 fix did not reach.

The argument

The obvious repair — flag the site — breaches a requirement that shipped on 2026-08-28, in order to fix a finding from the same sweep. One except covers two workspaces: resolve_turn_workspace dispatches on takes_task_workspace, so a task-bound writing turn fails on .agentweave/tasks/<id> — where other queued input really could have run, and counting the attempt is right — while everything else fails on .agentweave/worktrees/<agent>, which blocks the agent's whole ordinary population. TriggerAgentError's docstring justifies leaving the site unflagged on the strength of the task arm alone. So the repair is not to flag the site: it is to make the site say which of the two workspaces it could not prepare, and let the rule that already exists apply to each — the scheduler then answers the starvation question, because it is the only party holding the rest of the queue. The refusal also gains the sentence saying what would clear it, which today it never states. Read this way the change completes a decision the 2026-08-28 change deferred (its task 1.2a examined this exact raise and left it counting because "no static per-site flag can express it") rather than reversing one — splitting the except is what dissolves that objection.

What round 2 changed about round 1's version

R2 changed the proposal; it did not confirm it. R1's design D3 rested on takes_task_workspace reducing to "the entry names a task". agent_trigger never passes an entry's task_id — it passes turn_workspace.task_id, and naming a task is not taking a task's checkout: resolve_turn_workspace_inputs returns unbound for a grandfathered task (Task.workspace_scheme == 'agent', written only by migration 0095) and for an id validate_task_id refuses; resolve_bound_task drops the binding for a deleted or decided task (F79). Measured under py -3.11 at HEAD: grandfathered and bad-id both return TurnWorkspace(task_id=None). R1's helper would have counted the attempt and destroyed the head having released nothing — F188 surviving its own fix on every project old enough to have grandfathered tasks.

Four smaller corrections: R1 applied no eligibility filter (a hop-budget-exhausted or closed-conversation entry would have counted); the two errors are not symmetric — a false yes destroys, a false no only holds — and that is now a SHALL; R1's reason for excluding entries already inside selected was an enumeration of two routes out of four; and D2 gained terminal_failure. New design D3a put the predicate in task_workspace.takes_own_checkout so the resolver and the scheduler cannot drift. Tasks 24 → 28.
