# ghcp slice 1 `each-runner-cli-is-one-adapter`: Opus adversarial review, 2026-09-28

This is task 0.3, the operator's standing step before an APPROVED row. It ran on master `450de52`, which has
no `hub/` change since `ef55e6f`. It read code only and wrote nothing except this file. No Hub was started.
It read the trial database `mode=ro` once, for runner flags.

The question: can anything about a Claude or Codex run differ after this change, and would some golden case

## Findings

### 1. BLOCKING: the RPC golden never runs the code that moves

**What task 1.4 does.**
- The capture half drives today's `_execute_codex_appserver_run` and records the kwargs.
- The test half calls `CodexAppServerTransport.run_turn(RpcTurnRequest(...), RpcCallbacks(...))` directly, with a
  request the test builds itself.

**What goes untested.** After the change, `_execute_rpc_run` builds the `RpcTurnRequest` and `RpcCallbacks` from
its own parameters (D9). That mapping is the refactor's largest behavioural move on the one path that no drive
covers, because Codex is undrivable. The golden cannot see it. Mistakes it would miss include:
- `yolo`, `mcp_command` or `model` dropped;
- `cwd` and `workspace` swapped;
- `known_session_id` put in the wrong field.

**The existing suite does not close the gap.** The 17 `codex_run_turn` patch sites assert only a few kwargs:
- `cli` (`test_agent_trigger.py:2551`);
- `resume_thread_id` (`:2658-2659`);
- `config_overrides` (`test_agent_trigger_overrides.py:404`);
- `should_interrupt` (`test_agent_trigger.py:2768`).

`grep` over those files finds no assertion on the app-server call's `posture`, `yolo`, `mcp_command`, `model`,
`workspace`, `cwd`, `env` or `prompt`. The `mcp_command` assertions at `:747` and `:1020` capture `build_command`,
which is the Claude path.

**Callables recorded by name.** The golden records each callable only by its parameter name. So it cannot see a
change in what the callable does. Two examples:
- `request_approval`'s `timeout_seconds=_codex_decision_timeout(env)` (`agent_trigger.py:3220-3228`). That function
  is renamed and moved in D9.
- the `tool_name` label that `_on_refusal` writes (`:3202`, `:3213`). It moves to `refusal_label` in D9.

**The capture varies too little.** It varies only `permission_mode` × `mcp_command`. `yolo`, `resume` and
`config_overrides` all reach `_thread_policy` or the thread config, and none of them is varied.

**Fix.**
- Task 1.4's test half drives the new `_execute_rpc_run` (or `POST /agent/trigger`) with `hub.codex_appserver.run_turn`
  patched by the same recorder, and compares against the golden. The direct transport call can stay as a second
  assertion.
- Widen the capture:
  - `yolo` ∈ {False, True};
  - `known_session_id` ∈ {None, "thread-x"};
  - `config_overrides` ∈ {{}, {"model_reasoning_effort": "high"}};
  - `model` ∈ {None, "gpt-5.5"}.
- Record the callables' behaviour, not just their names:
  1. Invoke the recorded `request_approval("item/fileChange/requestApproval", {...})` with `_await_operator_permission`
     patched, and record its kwargs: `timeout_seconds` under an `env` carrying `AW_DECISION_TIMEOUT`, `method` and
     `subject`.
  2. Invoke `on_refusal` and record the persisted `tool_name`.
  3. Invoke `should_interrupt` before and after adding the run id to `_stop_requested`.

### 2. SHOULD-FIX: `build_command` has no way to reach Codex's `exec` transport

**What the design says.** D6 says `build_command` takes "its **stream** transport for these flags (Codex: exec)".
The only member that selects a transport is `transport(flags)`. For Codex that returns the app-server (RPC)
transport unless the flags contain `--no-app-server` (D3, `codex_appserver.py:79-89`).

**Why that cannot work.**
- The trigger passes flags with the sentinels already stripped (`agent_trigger.py:1211`, `:1223`).
- Tests call `build_command(runner="codex", cli="codex", prompt=...)` with no flags and expect `exec` argv:
  - `test_runner_parsing.py:177`, `:185`, `:190`, `:195`, `:200`;
  - `test_agent_tool_surface_phase7.py:81`;
  - `test_codex_posture_ordering.py:167`;
  - `test_runner_command_env.py`, `test_runner_command_overrides.py`.

So `transport(extra_flags)` returns an RPC transport, and that has no `build_launch`.

**Task 1.2 cannot be written as stated.** It says: *"`get_adapter(runner).transport(flags)` builds it (stream
transport; Codex `exec` via `--no-app-server`)"*. For a golden captured with `extra_flags=[]`, adding
`--no-app-server` to select the transport also puts it in the argv, unless the test strips it again. A working
implementation therefore needs a member D3 does not define.

**Fix.**
- Add `RunnerAdapter.stream_transport() -> Optional[StreamTransport]` to D3, D16 and task 2.2/2.3. Claude returns
  `ClaudeStreamTransport`; Codex returns `CodexExecTransport`.
- D6's `build_command` uses `stream_transport()`, never `transport(flags)`.
- Task 1.2 reads: *"`adapter.stream_transport().build_launch(LaunchRequest(extra_flags=<the golden's flags>, …))`
  equals the golden"*.
- Task 3.3's executor choice stays `adapter.transport(raw_flags).kind`.

### 3. SHOULD-FIX: `flags` is nullable, and NULL is the usual case

**The contract assumes a list.** `transport`, `collaboration` and `resolve_access_axes` are all typed
`flags: Sequence[str]`. Two call sites pass `Runner.flags` raw:
- `get_agents_launchability` (`agents.py:253`, `runner_row.flags`);
- D3's rebase text for the permissions-pill list route, which passes `flags=bound_runner.flags`.

**But `Runner.flags` can be NULL.**
- The column is `Mapped[Optional[Any]]`, `nullable=True` (`db/models.py:331`).
- `RunnerCreate.flags` defaults to `None` (`schemas/runners.py:17`).
- `uses_app_server` guards with `(flags or [])` (`codex_appserver.py:89`).
- The trigger guards with `list(runner_row.flags or [])` (`agent_trigger.py:1209`).

**Measured.** The trial database, read `mode=ro`, returns `[('claude', None, 5), ('claude', 'null', 1),
('codex', None, 4)]` for `select cli, flags, count(*) from runners group by …`. Every runner has no flags.

**What breaks.** An adapter written to the contract as stated (`APP_SERVER_OPT_OUT_FLAG in flags`) raises
`TypeError` for every default Codex agent. That turns `GET /agents/launchability` into a 500, which is exactly the
failure D15 forbids.
- `test_launchability.py:314` (`test_default_codex_agent_is_collaboration_ready`, bound with no flags) would catch
  it on that route.
- Nothing pins the agents-list caller that the permissions-pill change adds.
- Tasks 1.5(k) and 1.6 call these members with `[]` and sentinel lists only, never `None`.

**Fix.**
- Type `flags` as `Optional[Sequence[str]]` in D3, D4 and D16, and state that `None` means no flags.
- Add `None` to 1.5(k) (`collaboration(None, yolo=False)` equals `(True, None)` for Codex) and to 1.6
  (`resolve_access_axes(codex, hub_client=None, flags=None)` gives the app-server row).

### 4. SHOULD-FIX: moving the binary check leaves the test patch seam to a lint rule

**The seam.** D6 relies on 222 test sites, in 46 files, that patch `hub.launchability.shutil.which` (counted
again: `grep -rn "hub.launchability.shutil" hub/tests --include=*.py | wc -l` gives 222). D6 argues the patch
"keeps working from `runner_adapters/base.py`", because it lands on the `shutil` module object. That is only true
while `hub.launchability` still has a `shutil` attribute.

**What removes it.** `shutil` is used exactly once in `launchability.py` (`:98`). D14 moves that line into
`base.probe_binary`. The import is then unused, and CI's `ruff check hub/` (rules `F`, `pyproject.toml:101`)
fails on F401. The natural fix, deleting the import, makes all 222 patches raise.

**Checked with `unittest.mock`.** Patching `'<mod>.shutil.which'` on a module that has no `shutil` raises
`AttributeError: module '<mod>' has no attribute 'shutil'`. The failure is loud, not silent. But the design does
not say which way to go.

**Fix.** Choose one in D6 and D14, and in task 3.2:
- keep `import shutil  # noqa: F401 -- test patch seam, see runner_adapters.base.probe_binary` in `launchability.py`; or
- move the 222 targets to `hub.runner_adapters.base.shutil.which` as a stated task, with the file count.

### 5. SHOULD-FIX: `GET /agents` is in the "no API response changes" promise, but nothing captures it

**The gap.** The spec delta says moving runners onto adapters SHALL NOT change *"anything an API returns about
it"*. Two parts of the agents list move, and no golden or drive baseline covers them:
- D5 moves `_display_model` (`agents.py:557-565`, the list's `display_model`) onto `adapter.display_name`.
- After the permissions-pill change lands, the list also gains `permission_mode_at_rest` and
  `permission_mode_built_in`, which this change re-routes through `posture_at_rest(axes)`.

Task 1.7 and task 5.4 capture only the two launchability routes.

**The trap.** Today's expression is `agent_meta.get("model", "Claude")`. It returns a stored `None` or `""` as it
is, and falls back only when the key is absent. The obvious rewrite, `agent_meta.get("model") or
adapter.display_name`, differs from it.

**Fix.**
- Task 1.7 and task 5.4 also capture `GET …/agents` (per agent: `runner`, `display_model`, and the two posture
  fields once they exist) for:
  - a Claude-bound agent;
  - a Codex-bound agent with NULL flags;
  - one with `hub_client: "cli"`.
- D5 states that the fallback keeps `.get("model", adapter.display_name)` semantics.

### 6. NOTE: D15's claim about catching `FileNotFoundError` is not true of today's code

### 8. NOTE: the argv golden should cover three more cases

1. **An empty `mcp_command`.** D6's compatibility `build_command` "derives axes from `mcp_command`". Today every
   check is by truthiness (`if mcp_command`, `runner_commands.py:240`, `:250`, `:317`). If the derivation were
   `is not None`, `mcp_command=[]` would give `approvals=mcp_permission_tool` and default `workspace`. The run would
   get `--permission-mode manual` with no approver and refuse everything. Fix: state truthiness in D6, and add a
   golden case with `mcp_command=[]`.
2. **`effort` together with `permission_mode`.** This fixes the order in which `control_args` are spliced. Today
   `effort` is only a one-axis variation.
3. **The one-shot matrix is ill-defined for titles.** Task 1.3 says "each CLI × {model, None} × {schema path, None}"
   for titles too, but `build_title_command` takes no schema. Fix: capture titles × {model, None} only.

### 9. NOTE: `RpcTransport.inject_mcp` has no caller in slice 1

D3 defines `inject_mcp(mcp_command) -> dict` on the RPC transport. But `codex_appserver.run_turn` builds the entry
itself (`:969-983`) and is left unchanged, so nothing calls the member. That contradicts D16's rule that no member
exists without a caller.

**Fix.** Either pass the entry into `run_turn`, or drop the member until slice 2 needs it.

### 10. NOTE: several call sites use the CLI name as the catalog provider

Several sites index the catalog by CLI name rather than by `catalog_provider`:

### 11. NOTE: the "no branch on a runner name" requirement is stated wider than the code keeps it

The `runner-registry` delta says *"Code outside the adapters SHALL NOT branch on a runner CLI's name"*. D5
deliberately keeps these branches in `probe_agent` and `_display_model`:
- `runner == "manual"`;
- `runner == "claude_proxy"`;
- `runner == "copilot"`;
- the legacy rows.

**Fix.** Narrow the requirement to *"a supported runner CLI's name (one with an adapter)"*, so the synced spec
does not contradict the code on the day it lands.

## The change's own findings: both are real, derived from code

**Codex app-server keeps its write tools on a specification turn** (task 6.2(b)). Real.
- `_execute_codex_appserver_run` takes no `restrict_spec_writes` and no `extra_flags` (`agent_trigger.py:3040-3058`).
- `codex_appserver.run_turn` takes neither (`:904-926`).
- `_thread_policy` reads only `yolo` and `posture` (`:235-241`), so a default thread is `workspace-write`/`on-request`.
- `codex_appserver.py` has no `spec` reference at all.
- The runner's flags are dropped on this transport too.

**The Codex MCP allow-list omits `AW_QUESTION_TIMEOUT`** (task 6.2(c)). Real.
- `mcp_server.QUESTION_ANSWER_TIMEOUT = _configured_wait("AW_QUESTION_TIMEOUT", 240)` is read in the MCP child
  (`mcp_server.py:1005`).
- Both allow-lists carry five names (`runner_commands.py:322-328`, `codex_appserver.py:973-979`).
- The trigger sets the variable (`agent_trigger.py:1261-1262`), and the Hub records the deadline from the same
  setting (`:600-628`).

The consequence is sharper than the design says, and the finding should say so:
- **Configured above 240 s.** The tool stops waiting at 240 s. Its `POST /questions/wait-ended` report is then
  refused, because the Hub's own deadline has not passed (`agent_actions.py:682-710`, *"unanswered, with a
  `wait_expires_at` that has not passed"*). The task stays waiting until the run-end sweep.
- **Configured below 240 s.** The tool waits past the Hub's deadline.

The other three missing names do not matter on Codex. `AW_DECISION_TIMEOUT` is read Hub-side for app-server. The
workspace and posture variables are read only by Claude's approver.

**F301's addendum** (task 6.2(a)). Holds. `get_agents_launchability` reaches `collaboration_ready = True` for any
non-Codex bound runner (`agents.py:264-265`), whatever its `hub_client`.
