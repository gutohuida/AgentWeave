## 3. `a-retried-firing-records-how-its-work-ended`: REVISE

**HIGH: MODIFIED deltas are missing.** Two existing requirements become false, and neither is
modified. Only the stranded-firing requirement is MODIFIED today.
- `openspec/specs/agent-loops/spec.md:466-481`, *A firing in progress is distinguishable…*: its text
  reads "WHEN a firing's run has ended … AND whether it completed or failed is reported". After this
  change, a failed attempt that hands its input back leaves the record `in_progress`.
- `loop-firing-accountability/spec.md:30-33`, scenario *A firing that does start is unaffected*: it
  says "its record reaches its terminal state when the agent's run ends". This is the same
  contradiction.

**Medium: the Core `UPDATE` bypasses the `@validates` fitter.**
- **The problem:** task 2.1 says to "`UPDATE` every `in_progress` row". Design D1 relies on the
  `error_summary` fitter (`db/models.py:1413-1419`), which only fires on ORM attribute assignment.
- **The consequence:** the give-up reason embeds an unbounded `exc.detail` (`turn_scheduler.py:610-613`),
  and an unfitted write makes `GET /jobs/{id}/history` answer with a response-validation 500.
- **Fix:** load the rows and assign them through the ORM, or call `fit_error_summary` explicitly. Add a
  test with a reason longer than 500 characters.

**Medium: D3's "route still answers 200" is not what production does.**
- **Why the test passes:** test 1.7 patches `conclude_dispatches_for_conversation` to raise before any
  DB work, so the session stays healthy.
- **What production does:** a real failure at flush or commit leaves the route's session needing a
  rollback. The `persist_event(session…)` that follows at `api/v1/inbound_queue.py:269` then raises,
  and the route answers 500. The give-up path's `persist_event(db…)` loop (`turn_scheduler.py:639+`)
  has the same problem.
- **Fix:** call `await session.rollback()` in the `except`, or run the conclusion in its own session.
  Inject the fault at flush or commit, not by replacing the function.

**Medium: D6 ordering is unspecified.**
- **The problem:** the loops refetch is keyed on `queue_entry_withdrawn` and `queue_entry_abandoned`.
  The withdraw route broadcasts inside itself (`inbound_queue.py:269-270`), and the give-up
  broadcasts right after its commit (`turn_scheduler.py:639-655`). Tasks 2.3 and 2.7 do not say where
  the conclusion goes. If it lands after the broadcast, the refetch reads `in_progress`.
- **Fix:** specify that the conclusion commits before the persist and broadcast. Have 1.12 or 1.6
  assert that ordering.

**Medium: a gap between this change and change 5.**
- **The problem:** change 5's D1 says that "the dispatch conclusion added by change 3 belongs inside
  `reconcile_run`". But change 3 adds no conclusion to the run-reconciliation loop; the startup reaper
  does that job. After a Stop, no reaper follows. If `return_run_entries` abandons the entry at the
  limit, the dispatch stays `in_progress` until the next restart. That contradicts change 3's own
  clause about the Hub giving the input up.
- **Fix:** `reconcile_run` calls `conclude_dispatches_for_conversation(…, "failed", reason=<abandoned
  reason>)` after returning the entries. Under the D1 rule this is a no-op when the entry was
  requeued. State this in both changes.

**Low:**
- **A resume job under a withdrawal.** The correlation is per conversation. So when the operator
  withdraws a resume job's second dispatch while its first is still running, both rows end with the
  running run's status, not `stopped`. Name this under Risks.
- **The startup reaper's reason.** An entry abandoned at startup by `reconcile_interrupted_runs` gets
  the reaper's generic "no live run" reason rather than the abandonment reason.

**Verified:**
- Autoflush ordering at all five sites.
- Delivery claims entries and creates the `Run` atomically (`inbound_queue.py:170-185`).
- `firing_active` needs a running `Run`.
- `stopped` is a valid `JobRun` status.

## 5. `stop-clears-a-run-an-earlier-hub-left-running`: REVISE

**HIGH: the "cannot end the process → 409" path cannot fire on Windows.**
- **The problem:** `terminate_process_tree` never raises on Windows. It runs `taskkill` with
  `check=False` and ignores the exit code (`pty_runner.py:199-205`). So an access-denied or failed
  kill falls straight through to reconcile, while the process keeps writing to the checkout. That is
  the case D2 exists to prevent.
- **Why the test passes:** test 1.4 patches the function to raise, which production never does.
- **Fix:** after terminating, poll `pid_alive(pid)` for about 2 seconds. If it is still alive, answer
  409 with D4's sentence. Add a test with `terminate` patched to do nothing and `pid_alive` returning
  True.

**HIGH: the POSIX `killpg` can hit the wrong process group.**
- **The problem:** `terminate_process_tree` does `os.killpg(os.getpgid(pid))` (`:210-211`).
  - If the pid has been reused by a process in the Hub's own group (any non-`setsid` child, such as a
    `git` subprocess), this SIGKILLs the Hub itself.
  - If it is some other unrelated process, it kills that process's whole group.
- **What the original child looks like:** the original PTY child is a session leader, so `pgid ==
  pid`.
- **Fix:** on this path, call `killpg` only when `getpgid(pid) == pid` and it differs from
  `os.getpgrp()`. Otherwise answer 409, because the process cannot be identified as the run's.

**Medium: pid reuse on Windows.**
- **The problem:** the design's "pid reuse takes many spawns" is a POSIX argument. Windows recycles
  pids quickly, and the gap between startup and Stop can be hours.
- **Fix:** a cheap stdlib identity check. Compare the process creation time (Windows
  `GetProcessTimes`, Linux `/proc/<pid>/stat` starttime) with `run.started_at`. The process spawns
  seconds after its row commits, so a creation time before `started_at`, or long after it, means the
  pid was reused. Answer 409.

**Verified:**
- `started_at` is a `UTCDateTime` that re-attaches UTC to naive values (`db/models.py:47-48`).
- `StopAgentResponse.status` is a plain `str`.
- Startup already reconciles runs with `pid=None`, so D2 only fires in production when there is a
  live pid.
- D1/D4 are sound.
- Also fold in change 3's conclusion (see change 3 above).
