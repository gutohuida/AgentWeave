## 1. `a-document-moves-forward-only-through-its-checks`: APPROVE WITH FIXES

**MEDIUM: the check sits at the routes, not at `transition()`.**
- The problem: D3 puts `phase_blockers` in `set_phase` and `propose`. But the existing SHALL
  (`spec-document-authority/spec.md:159-180`) says a phase rule SHALL be enforced "at the point the
  Hub actually changes a document's phase … a rule checked in one place only survives until a second
  caller of that place is added". F207 is exactly that failure.
- Today's callers: R3's two-caller claim is true today (`spec.py:1607`, `spec_service.py:781`, with
  one `.phase =` writer at `spec_lifecycle.py:339`), but nothing pins it.
- **Fix (operator: inside `transition()`):** give `transition()` a `workspace` argument and call
  `phase_blockers` inside it.

No working automated path breaks:
- No loop, flow or MCP tool moves a document's phase.
- Adoption requires a payload (`spec_adoption.py:190-207`).
- `create_document` writes a stub payload (`spec.py:1453`), so test 1.1 answers 409, not 422.

## 2. `evidence-is-decided-after-the-run-that-recorded-it`: APPROVE WITH FIXES

**HIGH: in F358's own scenario, the refused agent is never told the row is ready.**
- In F358, the reviewer was woken by the author's message while the author's run was still live
  (`scripts/drive/FINDINGS.md:29419-29424`).
- Nothing stops a turn from being delivered while another run is live: `run_is_live` has no caller in
  `scheduler.py` or `turn_scheduler.py`.
- After D1, the tester gets `recording_run_live` and its turn ends. Nothing notifies it again when the
  recording run ends.
- **Fix (operator: re-queue):** when a run finalizes, queue a short entry to each agent that was refused
  `recording_run_live` on that run's rows.

**LOW:**
- A hung run blocks decisions until it is stopped. There is no maximum turn duration, and an `ask_user`
  wait stays in the liveness registry. The refusal should name stopping the run as a remedy.
- A revised row keeps its old `produced_at`, while `commit_for_task_review` ("most recent evidence
  wins", `requirement_evidence.py:785-800`) and change 3's *latest* label both order by `produced_at`.
  Decide whether a revision bumps it.

**Verified:**
- A crashed run left `running` cannot block decisions, because the registry fails open.
- D6 is sound: the wrapper's `except Exception` catches `TimeoutExpired`.
- D5 uses `requirement_evidence._git`, which catches `OSError` and `SubprocessError` (`:475-490`).
- The MCP client treats both 200 and 201 as success.

## 3. `the-coverage-bar-takes-the-evidence-decision-it-asks-for`: APPROVE WITH FIXES

broadcast all hold.

## 4. `a-footprint-names-the-line-of-work-its-commit-is-on`: APPROVE WITH FIXES

**The migration is a no-op on real data.** Read-only counts on `:8000` (head `0105`): zero rows with
`'HEAD'`, zero with `''`, 9 NULL and 89 named. The trial DB has 2 rows, both task branches. The
idempotent `UPDATE` is safe to re-run.

**MEDIUM: the `""` bucket is reduced as if it were a real branch.**

  observation wins" for commits where neither contains the other.
- But `""` means *no known line of work*, so unrelated commits get dropped from the merge.
- **Fix:** under `""`, drop only proper ancestors, and keep every commit where neither contains the
  other.

**LOW: the MODIFIED text still contradicts itself.** It keeps the absolute rule "where no checkout for
the agent exists … SHALL fall back to the project's own directory" next to the new task-branch-tip rule.
State the order ("otherwise").

**Verified:**

- After a fast-forward, a commit at the tip of both main and the task branch resolves to the task
  branch.
- Rebased commits fall to `""`.
- Every git call goes through `_git`, which returns `None` on failure.
- The proper-ancestor test is correct.
- The cost is small.

## 6. `the-approval-preview-asks-the-gates-merge-question`: APPROVE WITH FIXES

**MEDIUM: the fallback can still answer a bare 500.**
- After the wrap catches an error, D1 falls back to "today's computation".
- For an ungoverned task, that computation is `merge_targets`. It reaches `task_branch_tip` →
  `task_integration._git`, which is unwrapped (`tasks.py:1127-1135`).
- A `TimeoutExpired` there repeats (another 60 s) and becomes a bare 500. Test 1.5a patches
  `branch_exists` on what is likely a governed fixture, so it does not reach this path.
- **Fix:** wrap the fallback too, degrading to `targets = []` and the hedged sentence. Add a test on
  the ungoverned path.

**MEDIUM: the reason can claim a merge that won't happen.**
- D1 step 3 picks the sentence from `conflicts` alone. With a merge situation but
  `will_merge == []`, `conflicts == []` reads "approval will merge one commit … cleanly".
- **Fix:** keep today's order (no main branch → no targets → conflicts), and use the real count instead
  of the hard-coded "one commit".

**LOW: "SHALL NOT change the repository" is false.** `merge-tree --write-tree` writes objects. Reword
it to "no branch, working tree or index".

The preconditions are the gate's own (`requirement_gate.py:393-418`), so the preview agrees with the
refusal.
