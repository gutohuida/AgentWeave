## Change 1: `a-flow-is-configured-from-its-own-tab`

**Verdict: APPROVE WITH FIXES.** Nothing here stops the change from working. But three rounds missed
one contradiction with a shipped requirement, one collision with an approved change, and one
duplicate-event path.

1. **Fix before build. The loop summary still reports the old agent's refusal after D2a.**
   - `_batch_loop_summaries` calls `decide_firing(..., default_agent=job_agent)`, then
     `_loop_flow_busy_reason(session, loop, job_agent)`, using the live `job.agent`
     (`api/v1/jobs.py:377-386`).
   - Under D2a, the next firing asks about `pending_agent` whenever no firing is active.
   - So when A is held and B is staged, the tab says "A is held". The next tick then proceeds under B.
   - This breaks the shipped `agent-loops` rule "A firing is refused while its loop's agent is already
     running": *"Where the loop's summary reports why the loop is not proceeding, and this refusal
     would refuse the loop's next firing, the summary SHALL report this refusal's reason."* It also
     breaks the `stall_reason` promise quoted at `jobs.py:381-385`.
   - The per-task "next: A" attribution goes stale in the same way.
   - **Fix:** in `_batch_loop_summaries`, use `next_agent = loop.pending_agent if
     (loop.pending_edit_at and loop.pending_agent and job_id not in firing_active_jobs) else
     job_agent` for both calls.
   - **Test:** A held, B staged, no firing active. `GET /loops` must not report A's hold. The test
     fails on today's summary.

2. **Fix before build. It collides with the approved `input-the-hub-accepted-is-answered-as-accepted`
   (F349), and the design does not name it.**
   - F349's D6 rewrites the same `except`. Before the accepting commit, it rolls the session back
     first and then records `failed`. It also routes `_emit_loop_edit_applied` through
     `persist_accepted_event`.
   - Once F349 is in, an edit applied early by D2a is discarded by that rollback. Change 1's handler
     would then announce a `loop_edit_applied` that did not happen.
   - Test 1.3c ("the applied edit is committed … emitted once") inverts.
   - Change 1 also adds two new `_emit_loop_edit_applied` call sites, on the busy and skip paths,
     which F349 does not know about.
   - **Fix:** name F349 in Risks. State the rule for whichever lands second: after F349, a raise
     before the accepting commit leaves the edit staged and emits nothing, and 1.3c asserts whichever
     behaviour is in the tree. The handler emits only when its own commit included the edit.

3. **Fix before build. The `except` handler can emit `loop_edit_applied` twice.**
   - D2a/2.3a says the handler emits "when a payload was made". But every normal path has already
     emitted after its own commit:
     - the stop path emits at `:3190`, and then the `persist_event(job_run_skipped)` at `:3192` can
       raise;
     - the proceed path emits at `:3491`, and then `queue_entry_queued`, `schedule_agent` or
       `job_fired` can raise.
   - Either raise reaches the handler, which emits a second time.
   - **Fix:** set `pending_edit_payload = None` immediately after each emit. Add a 1.3c variant where
     `schedule_agent` raises after the late emit, asserting exactly one event.

4. **Note. The first defect in R1-bugs-inside cannot occur on either Hub today.**
   - Nothing writes `AIJob.last_session_id`. The readers are `jobs.py:82`, `jobs.py:881` and
     `scheduler.py:3056`. Neither `JobCreate` nor `JobUpdate` has the field. The only writer is the
     CLI's local `src/agentweave/jobs.py:349`, and no Hub route accepts what it writes.
   - Measured (read-only): `:8000` has 0 resume-mode jobs and 0 non-null `last_session_id`. `:8010`
     has the same.
   - So tests 1.2a and 1.5, and the ADDED "does not resume the old agent's session" requirement,
     guard a state that production cannot create.
   - The operator's decision works as written and does no harm. **Smallest fix:** say in D2 that the
     column has no writer, so no one later reads 1.2a as evidence of a live hazard. Optionally drop
     the scheduler-side conversation and `run.session_id` drop, and keep only the one-line clear.

5. **Fix before build (needs an operator decision). A shipped requirement is contradicted with no
   MODIFIED delta: the creator stops being the creator.**
   - `agent-loops` "Only a loop's creator, or the operator, may add to its queue directly" defines the
     creator as *"the agent that created it"*, distinct from the executor (the job's agent). "A loop
     has a controller…" delegates control to *"the loop's creator agent"*.
   - The code already collapses creator into `job.agent` (`tasks.py`,
     `_authorize_loop_task_creation` docstring, D8).
   - Making the agent editable turns that latent drift into visible behaviour. With
     `control="creator"`, switching A to B hands queue authority to B, although the spec says it
     belongs to A.
   - D2 accepts this ("follows the new agent") but carries no delta.
   - **Fix:** either write MODIFIED deltas on both requirements (the creator is the agent the job
     names, and follows an agent change), or reset `control` to the operator when an agent change is
     applied. See the decisions section.

6. **Fix before build. Some stop-condition edits in the Settings panel silently do nothing, or leave a
   flow with no stop.**
   - `update_job` applies and stages `stop_at` only `if body.stop_at is not None`
     (`jobs.py:1040-1044`, `:1063`). A panel that lets the operator clear the stop time sends null,
     gets a 200, and nothing changes.
   - The panel can also stage `stop_when_queue_empties: false` on a flow with no `stop_at`. That
     leaves a flow with no stop condition, which D5's dialog and `create_flow`
     (`mcp_server.py:821`) both refuse.
   - **Fix:** in D1, say that the stop time can be replaced but not cleared, and refuse to save a flow
     with neither stop condition. Alternatively, make explicit null clear the field via
     `model_fields_set`. Add a vitest for each case.

7. **Note. Agent validation is weaker than the scenario claims.**
   - The PATCH uses `_check_agent_exists`, which change 2's R2 showed to be leaky: an empty roster
     accepts any name, and a legacy `ProjectSession` name is accepted even when its `Agent` row is
     archived (`jobs.py:208-226`). So "An unknown or archived agent is refused" holds only for
     projects that already have a roster.
   - Separately, if a staged B is archived before the firing, B is still applied.
     `_stage_pending_loop_edit` rechecks nothing, and `agent_archivable` never looks at jobs
     (`agents.py:2774ff`).
   - **Fix:** when change 2 lands, use `delivery_agent_state` for this check too. At application,
     drop a `pending_agent` that is no longer open, and say so in `loop_edit_applied`.

8. **Note (pre-existing race, now a little wider).**
   - A firing that loaded the loop before a PATCH staged `pending_agent` still clears
     `pending_edit_at` when it commits. SQLAlchemy writes only changed columns.
   - B then sits in `pending_agent` behind a NULL sentinel: never applied, never shown, and then
     applied by some unrelated later edit.
   - `pending_edit_actor` is last-writer-wins. An agent staging `purpose` after the operator staged

   - D2a moves application earlier, but the race is the same one purpose and stop already have.

   - So switching away from a held A frees only new, unassigned work, and the loop still waits on A
     for that task. Test 1.3a deliberately uses an unassigned task.
   - **Fix:** say this in the panel's help text and in the test guide's human step 2.

10. **Note.** Test 1.6 ("nothing moves with the agent") names no mutation, and it passes with no fix
    at all. **Fix:** name one, for example `_stage_pending_loop_edit` reassigning pending tasks.

## Change 2: `a-document-says-how-it-will-be-built-and-approval-starts-it`

**Verdict: APPROVE WITH FIXES.** One item fails an existing test as designed, and its fix is small.
All four operator decisions work as specified.

1. **Blocker (small fix). `set_phase` as designed fails a shipped guard test.**
   - D6 step 3a adds `persist_event(..., "job_created", ..., commit=False)` to `set_phase`.
     `set_phase` already calls `sse_manager.broadcast`, and D6 adds a `job_created` broadcast.
   - `hub/tests/test_an_event_is_announced_after_commit.py::test_no_staged_event_is_broadcast_before_commit`
     (rule 1, shipped 2026-09-25) scans every hub function. It fails on any function that both stages
     with `commit=False` and calls something whose name contains "broadcast". So task 4.1 cannot go
     green.
   - The obvious swap is also wrong: `defer_broadcast` does not know about savepoints.
     `_publish_deferred` skips nested commits, and `_drop_deferred` clears the list only when the root
     transaction ends (`sse.py:138-150`). A defer placed inside the flow's savepoint would still
     publish `job_created` after that savepoint rolled back.
   - **Fix:** make every broadcast in `set_phase` a `defer_broadcast` placed before
     `session.commit()`, in today's frame order (`spec_updated`, `task_updated`, then
     `job_created`). Place the `job_created` defer after the `async with begin_nested()` block exits
     cleanly. Tests 1.4 and 1.6a/b spy on `SSEManager.publish`: one `job_created` frame in 1.4, none
     in 1.6.

2. **Fix before build (operator decision). A flow created over an empty queue fires a real turn on
   every tick.**
   - This happens when the board failed (`outcome.failed`), or when every declared entry was
     `already_served` and adoption finds nothing.
   - The new flow's queue is then "never filled". `_loop_stall_reason`'s rule is "never filled →
     fire; the agent's job is to fill it" (`scheduler.py:2153`), and `_loop_stop_reason` never ends
     it, because `ever_count` is 0 (`scheduler.py:438-442`).
   - The result is one agent turn every 5 minutes, indefinitely, started by an approval the operator
     made while the report said the board had failed. That is costly now the weekly window is
     metered.
   - **Fix:** inside the flow savepoint, after adoption, if the new loop owns no open task, roll the
     savepoint back. Report: *"No flow was started: the approval gave it no tasks. Start a flow… once
     there is work."* Add a test for each of the two causes.

3. **Fix before build. "Newest `approval_report` by `created_at`" can tie on this machine.**
   - Measured with `py -3.11`: `time.get_clock_info('time')` is `GetSystemTimeAsFileTime`,
     resolution 0.015625 s. 200,000 calls to `datetime.now()` gave 61 distinct values.
   - Test 1.8's two approvals in one test can share a `created_at`, so which one is "newest" is not
     deterministic.
   - **Fix:** order by `created_at DESC`, then `rowid DESC`, as B11 already decided for F177. Add a
     test with a frozen clock and two approvals.

4. **Note. On re-approval that finds an existing flow, `delivery_agent` is silently ignored.**
   - The stale strip is computed from the file, so it still appears and still offers a choice. D6
     then finds the existing flow and uses nothing.
   - **Fix:** the report states that the choice was not applied because flow F already declares the
     document. It also says when F's agent differs from the delivery's.

5. **Note.** The interview line promises that a flow "has finished work reviewed by another agent".
   In the single-agent project that the ADDED scenario is written for, that review goes unstaffed.
   **Fix:** add "…when there is another agent".

6. **Note.** Whenever no flow exists, **Start a flow…** appears twice on the same page: in the phase
   bar (change 1, D4) and in the report (D7). **Fix:** keep one, or accept the duplicate knowingly.

7. **Note.** `submit_spec_document` replaces the whole document (`mcp_server.py:1856-1883`), so a
   later submission without `delivery` drops it and propose is refused again. **Fix:** the docstring
   and interview line say to include `delivery` in every later submission.

**The end-to-end path holds once findings 1 and 2 are fixed.** Explore asks, propose requires the
answer, the proposed page shows the delivery and the stale flag, and approval creates the flow on a
savepoint. The flow first fires on the next cron tick. The report is stored and read back, and the
flow is editable from its tab.

Re-derived and confirmed:

  the materialise path commits;
- `_metadata_bundle` diffs both sides through `payload_to_dict`, so a present `delivery` does not
  churn proposals;
- the partial unique index exists on both databases;
- the ended-then-archived remedy depends on B11's adoption of an archived loop's tasks, and B11's D1
  provides it;
- the `:8000` skew guards: the report renders nothing without `approval_outcome`, and
  `delivery_agent` is sent only from the strip.

## Decisions for the operator

1. **Creator after an agent change** (change 1, finding 5). Choose one:
   - **(a)** The loop's "creator" becomes whichever agent the job names, and it follows an agent
     change. This matches today's code, and the two `agent-loops` requirements get MODIFIED deltas.
   - **(b)** An applied agent change resets `control` to the operator. The new agent does not inherit
     queue authority the operator gave to the old one.

   I recommend (b): a delegation to A is not a delegation to B.
2. **An approval that would give the new flow no tasks** (change 2, finding 2): create no flow and
   report it (recommended), or create the flow anyway.
3. **Still open, from R2:** a `stop_at` already past at approval creates no flow. I recommend
   accepting it: such a flow would end at its first firing.
4. **Still open, from R3:** the Spec-page link opens the loop agent's view with no document attached,
   and Back returns to the document. I recommend accepting it: it is the only way to put the loop tab
   in front.
