## 1. `drift-watches-the-files-its-evidence-is-about`: REVISE

**HIGH: the three rules are a union, so the locator never narrows agent evidence.**
- Design D1 takes the union of the rules. Before merge, an agent commit is never reachable, so rule 3
  (the branch's diff) always applies. Every agent evidence row therefore watches its task's whole
  diff, whatever its locator names.
- Measured on `:8000`: `src/engine.js` is in the watch set of **22 of 46** accepted rows. Once those
  tasks merge, one commit to engine.js on main raises about 22 candidates. The whole-tree flood raised
  46, so this halves the flood rather than ending it.
- The claim "one unrelated commit raises nothing" is true only for operator evidence (test 1.1).
- The flip also raises a candidate for every such row whenever a sibling task merged into the same
  file first, which is common here. Risks' "at most once per such merge" understates this.
- **Fix (operator: yes):** apply the rules in order, and match locator tokens by exact tree
  membership. This is not the guess `_COMMIT_ISH` refuses, because only paths actually in the tree
  count.

**HIGH: the main production path has no test.**
- Agents record mid-turn. The footprint is corrected at run end by `restamp_run_footprints`
  (`requirement_evidence.py:905-997`, `taken` at `:962-972`).
- Task 2.3 changes restamp, but no test in group 1 goes through it. Test 1.3 commits before recording.
- If 2.3 is left out or reverted, `Footprint.watched_from` defaults to `None` and is written as NULL.
  Every agent row then lands in `recorded_before_watching` forever, and every test stays green.
- **Fix:**
  - Add a test: an agent records with its work uncommitted, the run ends, restamp runs, and the row
    ends with `watched_from == ["branch"]` and narrowed `entries`.
  - Make `Footprint.watched_from` a required field, so no constructor (such as the `paths` return at
    `:549-551`) can silently write NULL, which means "legacy".

**HIGH: an existing SHALL is contradicted with no MODIFIED delta.**
- `requirement-traceability/spec.md:291-292` says: *"A later change to a linked footprint … SHALL
  raise a drift candidate."* The new ADDED requirement says legacy footprints *"SHALL NOT be scanned"*.
- The scenario at `:326-331` says the footprint names *"that commit, its tree"*.
- **Fix:** add a MODIFIED delta for "A changed implementation raises a candidate, never an edit" that
  makes legacy and unwatched footprints an exception and rewords "its tree". With the backfill, fewer
  footprints stay legacy.

**MEDIUM: the recording response misleads the agent.**
- Mid-turn, the recorded commit is the one the turn started from, often main's tip, so it is
  reachable. Rule 3 is then skipped, and the response says `watched_count: 0` until restamp runs.
- **Fix:** mark the value provisional in `footprint_view` for agent rows that have not been
  restamped yet.

**LOW:**
- Test 1.13 covers only the operator route. Nothing fails if the agent route
  (`agent_actions.py:1207`) never passes `main_branch`.
- No test pins the order of `unwatched`. This is the F190 rule, and change 2 reads that list.
- A squash or rebase merge done by hand in a terminal never becomes reachable, so F217 persists for
  that evidence. State this in Risks.

**Verified:**
- `--diff-merges=first-parent` is needed. Plain `diff-tree` prints nothing for a `--no-ff` merge
  (re-measured on git 2.49).
- `detect_drift` is the only reader of `entries`.
- Every new git call goes through `_git`, which answers `None` on failure.
- The flip's safety argument holds.
- The change closes F427 and F432.

## 2. `drift-is-scanned-and-answered-on-the-document`: APPROVE WITH FIXES

**MEDIUM: it puts one-click buttons over F436.**
- The 409 on answering twice does not make the silencing worse, since the fingerprint was the same
  either way. But it removes the only way to correct a mislabelled answer, and nothing reopens a
  candidate.
- **Fix (operator: carry it):** one line in `resolve_drift`. `implementation_corrected` stores no

  is drift again. Drive 3.1 then no longer has to revert the file before pressing *Code corrected*.

**LOW: order ties.**
- `list_drift` orders by `created_at` only (`spec.py:990`), so candidates from one scan can tie.
- **Fix:** use `order_by(created_at, id)`, and add a backend test that the order is ascending. Today
  only the UI fixture pins it; reversing the route's order would fail no test.

The change closes F430 and F436.

## 3. `the-corpus-is-indexed-arranged-and-adopted-from-the-app`: APPROVE WITH FIXES

**HIGH: F434 is left in place.**
- D6 accepts that `write_index` or `rerender_corpus` can raise an `OSError`. The route then answers a
  bare 500 after files were written, with the database rolled back (`spec.py:1255-1265`).
- That already breaks an existing SHALL: *"When the document index cannot be written, the requirement
  index SHALL still be rebuilt, and the reason … reported"* (`spec-document-authority/spec.md:1579-1584`).
- D6's claim that "the strip shows the 500 body" is empty, because an unhandled 500 body is plain
  `Internal Server Error`.
- **Fix (operator: carry it):**
  - Catch `OSError` around `write_index`. Answer `written: null` with an `index_write_failed`
    diagnostic, and still commit the requirement index.
  - In `rerender_corpus`, catch it per document into `skipped`.
  - Do the same for arrange (`:1375-1379`).
  - Add a test that patches `write_text` to raise.

## 5. `a-pending-proposal-can-be-withdrawn`: APPROVE WITH FIXES

**HIGH: an existing SHALL is contradicted with no MODIFIED delta.**
- `spec-document-authority/spec.md:1051-1053` says the Hub *"SHALL record one pending, individually
  addressable proposal per changed unit."* D1 records nothing for a repeated changed unit.
- **Fix:** MODIFY that requirement to add *"…unless an identical proposal from the same proposer is
  already pending against the same digest"*.

**MEDIUM: a retraction leaves the retracted proposal pending.**
- When the proposer's newest submission leaves a unit equal to what is stored, the unit goes to
  `unchanged` (`spec_service.py:354-356`, and `:376-378` for metadata), and nothing is superseded.
- Example: v1 omitted FR-3, which created a `remove` proposal. v2 restores FR-3, but the `remove`
  stays pending, and accepting it deletes a requirement the proposer brought back.
- **Fix:** units the newest submission leaves unchanged also supersede that proposer's pending
  proposals for them. Add a test.

**MEDIUM: an update can be lost between supersede and accept.**
- Status is written as a plain attribute. A submission that supersedes v1 and commits after an accept
  of v1 turns an applied proposal into `superseded`. Withdraw and accept race the same way.
- **Fix:** use `update(SpecEditProposal).where(id=…, status=='pending')` and check the row count.

**LOW: the twin marker can point at the wrong row.**
- It compares without `expected_digest`.
- **Fix:** send `expected_digest` in `_proposal_view`, and mark the row with the older digest.

The change closes F428 and F431.
