## Findings

### 1. BLOCKING: a junction on `.agentweave/calls` turns case 3 into "write any `.json` file without asking"

D8 case 3 says that each path is resolved with `realpath` and *"compared with `os.path.normcase` as `_where`
does"*. `_where` compares against a **realpath'd** root (`_decide`: `root = os.path.realpath(workspace)`,
`mcp_server.py:1567`). The natural implementation, `_where(p, os.path.realpath(<ws>/.agentweave/calls))`, accepts
everything under wherever `calls` points. D14's per-turn creation (`mkdir`, exist-ok) leaves an existing junction in
place. Measured:

```
New-Item -ItemType Junction -Path ws2\.agentweave\calls -Target ws2\.claude   # then New-Item -Force the dir, as the Hub would
realpath(file)= ...\ws2\.claude\settings.json
realpath(calls)= ...\ws2\.claude
inside realpath(calls)? True
inside unresolved calls? False
```

Under "Workspace only", `_decide` allows the junction's creation:
`New-Item -ItemType Junction -Path .agentweave\calls -Target .claude` → `{'allow': True, 'reason': 'inside your
workspace'}`. The junction then **persists across postures, runs, agents and runners** in that workspace. Later,
under "Ask me", a write of `.agentweave/calls/settings.json` is allowed without a card and lands in
`.claude/settings.json`. Hooks there run code at the next Claude start. Other targets work the same way: a junction to
the workspace root reaches `.mcp.json` and `package.json` scripts, and one to `.vscode` reaches `tasks.json` with
`runOn: folderOpen`. Under "Ask me", a direct write to any of those opens a card. The spec scenario *"resolves, after
links are followed, outside the run's calls directory"* does not decide this case, because after links are followed
the calls directory **is** `.claude`. Test 1.6's link row (tasks `:113`) covers only a file-level link pointing out.

**Fix.**
- The comparison root is `os.path.join(os.path.realpath(workspace), ".agentweave", "calls")`, **not** resolved
  further. The predicate is `None` unless `normcase(realpath(root)) == normcase(root)`, so neither `.agentweave` nor
  `calls` may be a link or junction, and unless the file's realpath is inside `root`.
- Apply the same rule in case 2.
- D14: the per-turn creation replaces a `calls` (or `.agentweave`) that is a reparse point, or refuses the turn.
- Add a scenario (*"a calls directory that is itself a link is not the calls directory"*) and a test-1.6 row with a
  directory junction. `New-Item -ItemType Junction` needs no privilege, so the row is not skipped on Windows.

### 2. SHOULD-FIX: the persistent-session residual is wider than D8 states, and the spec sentence about it is false

The sandboxing requirement says: *"The call command itself runs its interpreter isolated from interpreter settings in
the environment, so that a setting made earlier in the same shell cannot change what the allowed invocation runs."*
`-I` isolates only `PYTHON*` and the user site. Measured on PowerShell 5.1:

- **`ComSpec`.** PowerShell runs a `.cmd` as `%ComSpec% /c ""<path>\aw-tool.cmd" <args>"`. With
  `$env:ComSpec = "<ws>\argv.exe"`, a bare `aw-tool list_tasks .agentweave/calls/1.json` printed
  `ARGV-EXE cmdline=...\ws\argv.exe /c ""...\bin\aw-tool.cmd" list_tasks .agentweave/calls/1.json"`. So the
  workspace program ran in place of the launcher. A relative `ComSpec` is not honoured ("cannot find the file").
  `_decide` allows `$env:ComSpec = "<ws>\argv.exe"` under "Workspace only".
- **cmd `AutoRun`.** The same captured command line has no `/d`, so `HKCU`/`HKLM` `Command Processor\AutoRun` runs
  before every call (see note 9).
- **POSIX.** `LD_PRELOAD`, `LD_LIBRARY_PATH` and `DYLD_*` are untouched by `-I`.
- **Site-packages `.pth`.** These still execute under `-I`. This machine has five, including `pywin32.pth` and three
  `__editable__` finders (`py -3.11 -I` still runs `site`; `-I -S` measured 85 ms against 92 ms).
- **The realistic triggers are ordinary commands, not odd ones.** An `Import-Module .\helpers.psm1` that defines
  `aw-tool` gave `WORKSPACE-FUNCTION list_tasks …`. A venv-style `PATH` prepend
  (`.venv\Scripts\Activate.ps1` does exactly this) with an `aw-tool.cmd` in `Scripts` gave `VENV-SCRIPTS list_tasks
  …`. Under "Ask me", the operator approves "activate the venv" or "import the project's helper module" once. After
  that, every later `aw-tool` call in that persistent Copilot session runs workspace code with no card.
- **It is Copilot-specific.** Claude's Bash tool does not persist aliases, functions or environment variables between
  calls.

**How bad, and is it closable?** The predicate cannot close it, as R2 said. The harm is standing, unasked execution
for the rest of a Copilot session, bought with one ordinary-looking approval. Most of it can be closed outside the
predicate:
- an `.exe` launcher removes `cmd.exe` from the chain, and with it `ComSpec`, `AutoRun` and `%*` re-parsing. pip's own
  console-script launcher (`pip/_vendor/distlib/t64.exe`, which is how `aw.exe` itself exists) is one ready-made
  form;
- `-I -S` removes `.pth` execution at no cost, because call mode is stdlib-only;
- detect and degrade: an auto-approved shell call whose `toolCallId` produces no call-mode request at the Hub
  withdraws case 2's standing for the rest of that run, which returns it to cards.

**Fix.** Rewrite the spec sentence to claim only interpreter variables. List `ComSpec`, `AutoRun`, `.pth`,
module/profile functions and `PATH` in D8's residual, with the venv trigger named. Put the `.exe` launcher, `-I -S`
and detect-and-degrade to the operator together with open question 7.

### 3. SHOULD-FIX: D3's encoding claim is wrong for `Set-Content`, so spec text with an em dash fails

D3 says the file is read as UTF-8 or UTF-16-with-BOM *"because `Out-File`/`Set-Content` in 5.1 write those"*.
`Set-Content` in 5.1 writes the ANSI code page with no BOM (CLAUDE.md says so too). Measured: an em dash was written
as `97`, then `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x97`. This project's text is full of em dashes,
and finding 4 makes the shell the only way to write the args file on spec turns.

**Fix.** If strict UTF-8 fails and there is no BOM, decode with the system ANSI code page. Otherwise return a `usage`
error that names `-Encoding utf8`. The notice says to write the file with the file tool, or with
`Set-Content -Encoding utf8`. Test 1.x gains a cp1252 row.

### 4. SHOULD-FIX: spec turns remove the tools that write the args file, and neither slice says what happens then

A spec turn takes away every write tool that case 3 approves:
- Claude: `--disallowedTools Edit,MultiEdit,Write,NotebookEdit` (`runner_commands.py:229`);
- Copilot: `--excluded-tools=apply_patch,create,edit,…` plus Plan mode (slice 2 D9).

A spec turn described `shim` (every Copilot spec turn on the work PC) must therefore write
`.agentweave/calls/*.json` from the shell to call `submit_spec_document`, and that write:
- is neither case 2 nor case 3;
- is denied on Claude's `cli` path, which has no approver;
- may be blocked outright by Plan mode (unmeasured);
- hits finding 3.

The design never mentions spec turns, and no drive task makes one.

**Fix.** State the gap in D8 or D13 and add a drive row: *a Copilot spec turn told `shim` submits a document*. Put
the options to the operator:
- keep the edit tools on spec turns for a run told `shim`;
- accept one card per args file on spec turns;
- treat the spec flow as MCP-only on locked-down machines.

### 5. SHOULD-FIX: `mcp_announce.wait` checks and then registers, a race placed where the announce is expected

D9: *"`wait` first checks `Run.mcp_adapter_online_at` … because the announce can precede the wait"*, and the route
notifies only after its commit. An announce that commits between the check and the registration notifies no one,
and the run is recorded `absent`/`shim` while it holds MCP. By D9's own timings, `session/new` returns at +1.85 s
and the announce is expected at about +2–2.5 s, so the window is the expected arrival time.

**Fix.** Register the Event first and check the database second, or re-check the stamp on every poll step (the poll
already exists for `should_interrupt`).

### 6. SHOULD-FIX: Codex after the group 6 cut — the diagnostics requirement and the notice over-claim

- **Every first Codex run is now told `shim`.** No grounds → `shim` (D10), where before it was told the HTTP form. If
  its app-server then reports `failed`, D12 makes Codex's own `map_mcp_server_failure` *"the one statement"*. That
  text says *"this turn had no AgentWeave tools -- no messages, evidence, task updates or questions"*, which is
  false for a run told `aw-tool`. This is the exact defect D9 fixed for Copilot. It also breaks
  `runtime-diagnostics`' *"naming the surface the run was actually told to use"*. Fix: for a Codex run told `shim`,
  emit D12's event and suppress or reword Codex's, as for Copilot. Otherwise scope the requirement.
- **The Codex caveat was dropped.** R2's *"say in the notice's Codex story that an untested Codex run points at a
  command that may not connect"* (open question 4) reached no task and no spec text. The capability-plane scenario
  still asserts *"reachable through the call command"* for Codex, whose sandbox network is unverified. Fix: carry
  the sentence into the notice and into task 5.2, or scope the scenario.

### 7. SHOULD-FIX: the operator's `hub_client: "mcp"` against a run that tests itself

`described_access_path` returns `"mcp"` on `override == "mcp"` (`launchability.py:311-314`), and the spec keeps
*"The operator's own statement is honoured"*. The new scenario *"A run that tests itself is described from its own
result … whatever earlier runs reported"* does not say which of the two wins for a Copilot run whose wait times out.
D12's *"Its next turn is told `aw-tool`"* is false under a declared `mcp`, because the next Claude turn is still told
MCP. `hub_client` is rare (0 agents in the backup and profile databases, read with `mode=ro`), but the two scenarios
still conflict. **Fix:** state the order (my recommendation: this run's own negative test beats the declaration),
and make D12's "next turn" wording conditional on there being no declaration.

### 8. SHOULD-FIX: group 7's allow rule is wider than D8, and the shim reads any path

`Bash(aw-tool:*)` matches `aw-tool <tool> <any path>`. D3 lets the shim read *"any path its process can read, because
the restriction belongs to the approver"*. On Claude's `cli` path the approver is that prefix rule, and it restricts
no path. Separately, the predicate resolves the path against the workspace, while the shell resolves it against its
current directory. Both persistent shells, and Claude's Bash tool, keep a `cd`.

**Fix.** The shim enforces finding 1's rule itself: the args file's realpath is under
`<realpath(AW_WORKSPACE_DIR)>/.agentweave/calls`, otherwise `usage`. Then both approvers mean the same thing, and a
drifted working directory fails closed with a readable error.

### 9. NOTE: `AutoRun` output breaks *"nothing else is ever printed to stdout"*

Because the call runs through `cmd /c` without `/d`, a machine whose `Command Processor\AutoRun` prints anything puts
that text ahead of the JSON envelope on every call. `chcp 65001` is a common one, and it prints `Active code page:
65001`. Corporate images set `AutoRun`, and the work PC is one. The `.exe` launcher in finding 2 removes this too.
Add it to human-only step 3's list of likely causes.

### 10. NOTE: gaps in the precedence against how runners end

- **Claude.** An `init` that reports `pending` for the Hub's server is ignored, so the announce decides `connected`.
  If the server then fails, nothing later corrects it, and F340's latch is back for Claude versions that report
  `pending` for a slow fastmcp start. Have drives 9.2 and 9.7 record the literal `init` status string.
- **Codex.** `cancelled` is likewise ignored.
- **Copilot, late announce.** An announce that arrives after the 15 s wait flips the record `absent`→`connected`.
  The D12 event has already said *"did not start"*, and the `/mcp list` quote may say `(connected)`. This is benign
  but self-contradictory; say so in D12. A cold first start under corporate antivirus is the likely cause.

### 11. NOTE: the pinned file is now re-executed per call from a directory shared across the machine

Before this change, the pin was verified at trigger and loaded once per harness. Now every `aw-tool` call re-reads
the pinned file from `~/.agentweave/hub/tool-server/<digest>/`. A change to that file mid-run (which needs a write
outside the workspace) reaches every in-flight run's later unasked calls, not only the next spawn. That is low risk,
but it should be stated in D5.

### 12. NOTE: the callable set in the Hub process

The predicate runs synchronously (`approve_tool_call`, slice 2's handler) in fastmcp mode, where enumerating
registered tools is async or private. **Fix:** specify a module-level name set, filled by a thin wrapper around
`.tool()` in both modes, which also keeps D3's *"cannot drift"*.

### 13. NOTE (open question 7): the auto-approved write's content is never shown to anyone

Python runs any file as a script, whatever its extension. So a later card for `py .agentweave/calls/x.json` asks the
operator to approve code they never saw. The card could flag a command whose words name a file under
`.agentweave/calls/`. This is not a reason to refuse case 3.

## Answers to 0.3

- **D2, not a CLI subcommand: sound.** All four reasons hold. `Get-Command aw*` on this machine lists only
  `Python311\Scripts\aw.exe`, and no `aw-tool` exists anywhere today. The CLI stays at five `cmd_*`, and
  `src/agentweave/` is untouched.
- **D8 / open question 7, the args-file write under "Ask me": acceptable once finding 1 is fixed.** Without that fix
  it is not: case 3 is then a standing licence to write any `.json` file a junction reaches, and the junction survives
  posture changes. With the fix, the file is inert data in a Hub-owned, git-excluded directory, which is the same
  standing `mcp__agentweave__*` already has. Note 13 is the only residue. The persistent-session residual is **not**
  closable by the predicate, and it is wider and easier to trigger than D8 says (finding 2). An `.exe` launcher, `-I
  -S` and detect-and-degrade close most of it. The operator should decide Q7 with finding 2's triggers in front of
  them.
- **D11, runs no longer told the HTTP form: sound.** Keeping `_http_lines` keyed on `"http"` as the route-parity check
  is right. The only regression is Codex, where the dropped caveat now makes a false claim (finding 6).

## Contract conflicts

**(1) Slice 2's `"Shell"` key: keep case 2 limited to `Bash`/`PowerShell`, and fix slice 2's text, not the
predicate.** An unnamed shell is exactly the one whose name lookup nobody knows, and `cmd` looks in the current
directory first. Measured: with the launcher first on `PATH` and an `aw-tool.bat` in the workspace, `cmd /d /c
"aw-tool list_tasks …"` printed `WORKSPACE-BAT list_tasks …` (once `NoDefaultCurrentDirectoryInExePath` was
unset; Claude Code sets it in its own shells, runs do not). Reading the text "both ways" checks characters, not
resolution, so admitting `"Shell"` would let a bare `aw-tool` run agent-written code unasked. Also:
- `write_powershell` is `execute`-kind, but its input is `{shellId, input, delay}` (`app.js` `uFe`): text for
  a running process, not a command. It must never reach case 2 either.
- So slice 2's § *Provided to slices 3–5* item 4 (*"which slice 3 already requires to satisfy both readings"*)
  is wrong and should say that `"Shell"` gets no standing (a card under "Ask me").
- This slice's D8 caller text (*"no caller loses a real case"*) should say the same.
- Slice 2's task 1.1 capture should measure how often a genuine `powershell` request arrives with no known
  name. If that is common, the fix belongs in slice 2's `calls` map.

**(2) Other cross-slice dependencies.**
- Slice 2 D9 against this slice: spec turns (finding 4). Neither slice owns it today.
- Slice 2 D10/D18 against D12: consistent after reconciliation.
- Slice 1: `tests_mcp_before_first_prompt` on the transports, `RpcCallbacks.render_surface`, `plane` staying
  `"mcp"|"cli"`, and axis 1 staying `hub_client`-only all agree. No issue found.
- Slice 5: consistent. It needs no hook mode, owns the GitHub server's failures, and does not rely on stdin.

## Checked and found sound

- R3's table, spot-re-run: `aw-tool --list` passes intact (`LAUNCHER --list`), and `.cmd` beats the extensionless file.
- `PSModulePath` auto-loading does **not** beat a `PATH` application: a module exporting `aw-tool` placed on
  `PSModulePath` left `LAUNCHER …` running. Only an explicitly imported module does, which is finding 2.
- Case 3's exotic Windows path forms all fall through (return `None`), because the predicate is total:
  - `\\?\…\calls\..\..\x`, `\\.\…`, `\\?\GLOBALROOT\??\…` and `calls \x.json` → different-drive `ValueError`;
  - `x:y.json` → realpath returns the bare `x:y.json`;
  - `x.json::$DATA` and a trailing space on `.json` → fail the suffix rule.
- `CONIN$.json` resolves inside, and is harmless.
- `-I` keeps `os.environ`, so the token still reaches the shim.
- Call mode never announces. The source precedence (harness report > announce > wait) is order-independent, as D1
  claims.
- The Copilot sequence (wait inside `session/new` → `render_surface` → prompt) and the bare `/mcp list` block match
  slice 2's fixed `run_turn` order.
