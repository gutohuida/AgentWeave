# Adversarial review: `a-copilot-run-shows-its-credits` (ghcp slice 4), task 0.3

Reviewer: Opus, 2026-09-28, against master `450de52`. This review is read-only: no product code was
edited, no Hub was called, and the two databases were read only through `file:...?mode=ro` URIs.

**Verdict: APPROVE WITH FIXES.** Nothing here blocks building, because slices 1–3 must land first
anyway. Five should-fix items need to be settled before IMPL starts: two are spec text that would be
false once archived, one is a missing negative test on the exact 0.3 question, one is a
double-count path that R3's proof does not cover, and one is an overstated claim about task 7.3.

## Answers to the three 0.3 questions

### Q-a. Does any path add a Copilot credit to a token total or to the budget?

**No.** I traced every reader and writer of the new fields.

- **Budget readers are tokens-only, and there are exactly two.**
  - `project_budget_state` (`usage_accounting.py:213-224`) sums `TurnUsage.total_tokens` for
    `status == "measured"`. Its callers are `turn_scheduler.py:363` and `api/v1/inbound_queue.py:211`.
  - `budget_state(project.token_budget, total)` (`:103-110`, `:189`) takes
    `project_summary["total_tokens"]`, and `PATCH /budget` (`accounting.py:79`) does the same.
  - A grep for `token_budget|used_tokens|total_tokens` across `hub/hub` finds no other reader.
  - The UI reads `budget.used_tokens` (`AccountingPanel.tsx`, `OverviewBudgetSummary.tsx`).
- **The ledger's token fields cannot pick up a credit.**
  - `_accounting_from_dimensions` (`runner_parsing.py:72-126`) matches only named token keys.
  - `totalNanoAiu` matches none of `total_tokens`/`totalTokens`/`total`.
  - `session.usage_checkpoint` carries no token field.
  - `cost` (the multiplier) goes nowhere: `cost_usd` is passed explicitly, and D1 keeps it None.
- **The new columns are separate.**
  - They are summed separately in `_aggregate_columns`, and `ck_turn_usage_availability`
    (`db/models.py:1286-1292`) does not touch them.
- **The UI keeps them apart.**
  - `usageByRunId` returns `{tokens, nanoAiu}` as separate fields.

The only way a credit reaches a budget is an implementation mistake. Test 1.10 guards the API's
`budget.used_tokens`, but nothing guards the hot path (finding 11).

### Q-b. Is a Claude/Codex-only project byte-identical when no Copilot row exists?

**Screens: yes, by design.** Every new UI element is gated on a non-null field or on
`compaction_percent < 95`, and tests 1.16–1.18 pin the Claude strings. No UI test uses snapshots
(`grep toMatchSnapshot|toMatchInlineSnapshot` over `hub/ui/src` finds nothing).

**API responses: no, and the design only half says so.** A Claude-only project gains all of the
following:

- `ai_nano_aiu: null` and `premium_requests: null` in:
  - `project`;
  - every `agents[]` entry;
  - `GET /accounting/conversations/{id}`;
  - every `recent_turns[]` row.
- `runner` inside `preferred_display` of kind `allowance`. This is the common case: 345 of the 348
  Claude rows on `:8000` carry a reading.
- `checkpoint_compaction_percent: 95` on **every** Claude agent in `GET /agents`. It is not null
  there: D10 says null only when there is no runner.
- `threshold_source` on every `checkpoint_due` broadcast.

Key order is preserved only if the new keys are appended after the existing ones.

Existing exact-equality tests will fail and must be updated. See finding 9.

### Q-c. Can D8 hold a queue on anything but the structured quota code?

**Not as designed, but one guard is missing from the tests (finding 2).**

- Every hold is derived by `allowance_refusal` (`provider_allowance.py:60-80`): a dict reading with
  `status == "rejected"` and a numeric `resetsAt`.
- The only writer of a Copilot `rejected` status is `quota_reading(refused=True)`, and `refused` is
  set only by `errorType == "quota"` together with `errorCode == "quota_exceeded"`, from a
  `session.error` or from a prompt error's `data`.
- The settle only *fills* `resetsAt` into a reading that is already rejected.
- `session_quota_exceeded`, `billing_not_configured`, `rate_limit` and message text are all
  excluded, and test 1.9 asserts each of them.

Two nuances:

1. **The hold is status-blind.** Because the hold is derived, a *stopped* run whose ledger saw the
   quota error also holds (`agent_trigger.py:2708-2712` arms for any status). That is still the
   structured code, and it matches the existing requirement (*"a hold that began with a turn which
   ended in some way other than failing"*).
2. **`quota_reading(snapshots, *, refused, prior_reading)` has an unguarded path.** If an
   implementer made it return the prior reading whenever this run has no snapshot, a *non-refused*
   run could re-write an earlier `rejected` reading and re-establish a hold on an ordinary failure.
   No test forbids that (finding 2).

## Findings

### 1. should-fix: the spec says a refusal with no known reset is returned uncounted, but the code counts it, clears the Copilot session at attempt 2 and abandons the input at attempt 3

**Evidence: the spec delta contradicts itself.**

- `specs/agent-conversation-workspace/spec.md` says: *"A refused turn SHALL end as a failed turn …
  In every case the input it was given returns to the queue without being counted as a delivery
  attempt."*
- The same requirement says that with no known reset the refusal *"SHALL NOT hold the queue"*.

**What the code does in that case.** In `_execute_run`'s branch (`agent_trigger.py:2681-2689`),
which task 5.3 copies:

- `refusal` is set only when `allowance_refusal` returns non-None, and that needs a numeric
  `resetsAt`.
- Without one, `return_run_entries(db, run_id)` runs with no refusal.
- `inbound_queue.py:286`, `:294`: `RESUME_RETRY_LIMIT = 2` clears the conversation's provider
  session, which throws away the Copilot context, and `DELIVERY_ATTEMPT_LIMIT = 3` abandons the
  input.

**This is not a corner case.**

- Once the plan is spent, a refusal lands on a run's *first* call. That run has no `assistant.usage`
  and so no `quotaSnapshots`, which leaves the prior reading as the only source of a reset (D8).
- The prior-reading lookup is per agent, `runner == "copilot"`. So each of these gets no reset:
  - a newly bound Copilot agent;
  - an agent whose last reading dates from last month (its `resetsAt` is past);
  - any agent on a plan that gives no `resetDate` (Q4).
- Each of those turns hits F355's defect, which the proposal's *Why* item 3 says it fixes. The
  Copilot quota is per GitHub account, not per agent, so another agent in the same project may well
  hold a valid reading.

**Fix:**

- **(a) Required.** Reword the requirement so the uncounted return applies only "when the refusal
  holds the queue". State the no-reset consequence: counted, the session cleared at the second
  attempt, the input withdrawn at the third.
- **(b) Recommended.** Widen D8's prior-reading lookup from the agent to the **project's** newest
  `runner == "copilot"` reading whose `resetsAt` is ahead. The quota belongs to the account, so any
  Copilot agent's reading states the same reset. Add a 1.9 case: agent `b` refused on its first
  call, with agent `a`'s reading ahead, is held.

### 2. should-fix: no test forbids the prior reading from turning a non-refused run into a hold

**Evidence.**

- Test 1.9 says *"A refused run with no snapshot and a `prior_reading` whose `resetsAt` is ahead
  uses it"*. The word "uses" invites copying the whole reading.
- D7 says *"A run with no qualifying snapshot writes no reading"*, but nothing tests that rule
  against a `rejected` prior reading.

**The failure it allows.**

1. Run R1 is refused and held until Oct 1.
2. On Sep 20 the operator's probe run R2 fails for another reason, for example a `rate_limit` error
   on its first call, with no snapshot.
3. If R2 re-emits R1's rejected reading, the hold is renewed on a non-quota error.

That is exactly the 0.3 question.

**Fix.** Add two cases to 1.9:

- `refused=False` with no snapshot and a `rejected` prior reading ⇒ **no reading written**.
- `refused=True` with a prior reading ⇒ only `resetsAt` is copied. `status`, `quota` and
  `remainingPercentage` come from this run, or are absent.

In D8, say that `prior_reading` is consulted only when `refused` is True, and only for `resetsAt`.

### 3. should-fix: the baseline "newest by `observed_at`" double-charges credits if the Hub clock steps backwards between runs of one session

**Evidence.**

- D4 orders baseline candidates by `observed_at, id`.
- `observed_at` is wall-clock time at flush (`db/models.py:1280`, default `_now`).
- `id` is a random `short_id` and carries no order.

**Simulation** (`py -3.11`, a scratch script, the D4 rule exactly as written). Four runs of one
session spend 275856000, 124144000, 100000000 and 50000000. The clock steps back 10 units before
run 3.

| | Run 1 | Run 2 | Run 3 | Run 4 | Sum |
|---|---|---|---|---|---|
| Charged | 275856000 | 124144000 | 100000000 | **150000000** | 650000000 |
| Real | 275856000 | 124144000 | 100000000 | 50000000 | 550000000 |

Run 4's baseline is still run 2's row, the newest by the clock. So run 3's 100000000 is charged
twice.

R3's invariant proof assumes the baseline is the previous run's stored total. That holds only while
`observed_at` is monotone.

**Fix.** Either option works:

- **(a)** Chain explicitly. Record which row each run differenced against (one nullable column),
  and take the baseline from the chain's tip: the row no other row names.
- **(b)** Keep the ordering, and state in D4 that "never twice" assumes a monotone Hub clock.

Taking `MAX(session_nano_aiu_total)` is **not** a fix. After a `/clear` reset it double-charges
once the new counter passes the old maximum.

### 4. should-fix: "D4 is right under either answer to 7.3" is overstated; under restart-per-process semantics a lost call event under-charges

**Evidence (computed).** Take restart semantics, where a loaded process's checkpoint counts only its
own spend:

| Quantity | Value |
|---|---|
| Baseline `S` | 100000000 |
| This run's real spend = its checkpoint `K'` | 250000000 |
| One call event dropped, so the per-call sum `P` seen | 140000000 |
| `diff = K' − S` | 150000000 |

- Because `diff >= P`, D4 charges 150000000. The truth is `K'` = 250000000.
- It also takes premium requests from `K'_prem − S_prem`, which under restart semantics is
  meaningless: here 0.

Under restart semantics the right figure is `max(K', P)`, and the premium count is `K'_prem`.

**Fix.** Keep 7.3 as a gate for D4 as well as for Q10. If 7.3 observes restart semantics, a loaded
session charges `max(K', P)` and takes premium from `K'` alone. Correct the D4 text, the test guide
item 5 and task 7.3's *"D4 needs no revision either way"*.

The larger-of rule does stay *never twice, never negative* under both semantics. R3's claim fails
only for *never lost*.

### 5. should-fix: "the lowering SHALL be stated wherever the threshold is reported" is not what D10 builds

**Evidence.**

- The only statement D10 adds is the `AgentSettingsControls` line, and only for
  `compaction_percent < 95`.
- **Claude's own lowering is stated nowhere.** A configured 93–99% becomes 92
  (`threshold_source: "runner_ceiling"`), and that source travels only on the `checkpoint_due`
  payload, which R3 found no UI reads.
- **The project panel is silent.** `ProjectSettingsPanel.tsx` reports a project threshold of 80 with
  nothing saying it is 77 for the project's Copilot agents.

**Fix.** Either option works:

- **(a)** Narrow the requirement to "stated in the agent's checkpoint settings". Make the line
  appear whenever the effective threshold is below the configured one, for any runner, Claude 95 →
  92 included.
- **(b)** Also add a one-line note in `ProjectSettingsPanel` when any agent's runner lowers the
  project threshold.

Extend test 1.18 to cover the case you choose.

### 6. note: Q7 is a real behaviour change for existing users, but none exists on this machine

**Re-verified with `mode=ro` reads.**

| Database | Projects | Agents | Runners |
|---|---|---|---|
| `:8000`, revision `0109` | all 3: `checkpoint_threshold_mode`, `_value` and `_notes_value` NULL | all 8: the same | `claude` ×8, `codex` ×3 |
| Trial, revision `0110` | all 4: the same | all 3: the same | — |

`turn_usage` holds only `claude` rows.

So on this machine the Claude behaviour is unchanged: built-in 80/70/92, with C=95 for Claude,
Codex and no runner.

For PyPI users, three Claude bands change:

- a percent threshold of 93–99, and with it a notes value of 92 or more, which becomes 82;
- a token threshold above 92% of the window. In `automatic` mode this now **bills a generation** at

- a token notes value above 82% of the window.

**The token-mode ceiling also trusts `percent`.** Token mode exists for windows the Hub cannot
trust (`checkpoint_policy.py:8-11`, `:163-168`). If a reading's denominator is wrong, for example a
catalog limit of 200k on a 1M session, a user's token threshold of 600k is overridden at 184k.

Acceptable, and stated. Add one line to Q7 about the denominator risk.

### 7. note: the Copilot key names do not match the shared normaliser

**Evidence.** `_accounting_from_dimensions` (`runner_parsing.py:83-95`) recognises:

- for cache reads: `cache_read_input_tokens`, `cacheReadInputTokens`, `cached_input_tokens` and
  `cache_read_tokens`;
- for cache writes: the `cache_creation…` and `cache_write…` spellings.

Copilot sends:

- **per call:** `cacheReadTokens` and `cacheWriteTokens`;
- **in the prompt result:** `cachedReadTokens`, `cachedWriteTokens` and `thoughtTokens`.

None of these match. Totals are unaffected (`cache_is_separate_input=False`), but the breakdown
comes out None.

Test 1.1 catches this on the per-call path. It is **not** caught when the prompt result wins, because
test 1.3 asserts only the total and the source.

**Fix.**

- Test 1.3 also asserts `cache_read_tokens == 21888` when the source is `copilot_prompt_result`.
- D3 names the Copilot keys explicitly.

### 8. note: "the operator can end the hold … by rebinding the agent" (D8) is imprecise

**Evidence.**

- The hold is keyed on the agent name (`provider_allowance.py:122-143`), and rebinding writes no
  `turn_usage` row.
- Rebinding alone leaves the month-long hold in place. Loops and jobs stay blocked too
  (`scheduler.py:1182`, `:1740`).
- Only operator input after the refusal, served by the new runner, ends it. The main spec already
  says exactly that (`agent-conversation-workspace/spec.md:2489-2492`).

**Fix.** Change D8's wording to "rebinding the agent and then messaging it". Put this in front of
the operator with Q6.

### 9. note: existing exact-equality assertions will break, and the tasks do not list them

- `:98` (`agents ==`);

- `:368` (the conversation `==`).

### 10. note: the label "excludes N turns with no reported cost" is false for a Copilot turn

A Copilot turn *did* report a cost, in credits. D12 counts it as unpriced, which is right for the
count. But the UI string (`accountingDisplay.ts:44-47`) says "no reported cost".

**Fix.** Word it "no reported API-equivalent cost", or leave it to the human-only item 2 with this
named. The same goes for `usage-accounting`'s *"Allowance and currency presentation cannot imply
billing"*. Credits are a billing unit (1 credit = $0.01), so the ADDED requirement should say
explicitly that credits are provider-reported consumption, not a monetary figure, and so outside
that requirement.

### 11. note: no test pins that credits stay out of the scheduling hot path

Test 1.10 asserts `budget.used_tokens` on `GET /accounting`. Nothing asserts `project_budget_state`,
which is what `turn_scheduler.py:363` actually gates on.

**Fix.** Add to 1.10: with `token_budget = 1801` and the same rows, `project_budget_state(...)
["exhausted"] is False`.

### 12. note: nothing refuses a negative credit at the database

`total_tokens` has `ck_turn_usage_total_nonnegative`. The four new columns get no CHECK constraint,
because D5 avoids a table rebuild. D4 guarantees non-negative values in code.

Either accept this and state it in D5, or have the ledger drop negative `totalNanoAiu` values as
`_token_int` does. Test 1.8 would then include one negative per-call value.

### 13. note: a reset date the server applies late is counted, not held

A refusal can land just after `resetDate`, before Copilot's server has actually reset: for example
a first-call refusal at 00:00:30 on the 1st, with a prior `resetsAt` of 00:00.

1. The prior reading's `resetsAt` is past, so it is not filled.
2. The refusal is counted, and a 60 s floor hold starts (`provider_allowance.py:100`).
3. The session is cleared at the second attempt.

This is the same as Claude's existing behaviour for a past reset. Mention it under D8's clock
handling. No change is needed beyond finding 1(a)'s wording.

## What I checked and found sound

- **The acp4 arithmetic** (recomputed):
  - per-call nano-AIU: 10988×20000 + 21×120000 = 222280000; 148×20000 + 10880×2000 + 38×120000 =
    29280000; 84×20000 + 11008×2000 + 5×120000 = 24296000;
  - their sum, 275856000, is the checkpoint total;
  - calls 1 and 3 alone give 22106 tokens, 33.36% short of 33172;
  - `datetime(2026,10,1,tzinfo=utc).timestamp()` = 1790812800.
- **R3's run sequences, "never twice, never negative" under a continuing counter.** S1–S6 and S9
  hold. I added these:
  - **A run killed mid-turn with no checkpoint.** It charges `P` and stores `S+P`. If the durable
    counter missed a call in `P`, the next run's `diff < P` falls back to that run's own calls.
    Nothing is doubled.
  - **A checkpoint arriving after the prompt result**, which the ledger drops. The next run's
    difference carries it once.
  - **A `session/load` that replays a checkpoint.** The ledger is not armed yet, so it is ignored.
  - **A loaded run with no baseline, then another.** No older row can exist, so no double count is
    possible.
  - **A settle retried on an existing row.** `record_turn_usage` returns the existing row, so the
    retry has no effect.
  - **Two agents, or two sessions.** The baseline is keyed by project, agent and session, so they
    stay disjoint.
  - **The `-32002` fallback.** Its baseline is 0, and `Run.session_id` is rebound before its row is
    written.

  The only exceptions are finding 3 (clock) and finding 4 (restart semantics with lost events).
- **Keying the settle on `credit_session_new`, and carrying it through `merged`.** This is the
  correct fix for S10.
- **D8's route into the hold.** It holds only through the structured code. `session_quota_exceeded`,
  `billing_not_configured`, `rate_limit` and message text are excluded, and 1.9 tests each one.
- **Task 5.3's branch is inert for Codex.** No Codex sample carries an allowance: only
  `_claude_usage_sample` at `runner_parsing.py:365` reads one.
- **D10's formulas.**
  - C=95 gives 80/70/92, and C=80 gives 65/55/77.
  - Test 1.13 at 66%: `should_request_notes` is False (66 ≥ 65) and `should_checkpoint` is True.
  - The token notes ceiling is 67 for C=80 and 82 for C=95.
  - The module constants stay, so the pin at `test_checkpoint_policy.py:249` still holds.
  - The `resolve_policy` callers match D10's list (`jobs.py:536`, `checkpoint_handover.py:244`,
    `checkpoint_trigger.py:182`).
  - A run requires `Agent.runner_id` (`agent_trigger.py:729`), so `consider`'s runner lookup finds
    the runner that actually ran.
- **D11's route-raises.**
  - The accounting routes 404 before they aggregate.
  - `PATCH /budget` commits and then aggregates (`accounting.py:62-66`).
  - `GET /agents` reads `runners_by_id` (`agents.py:405-407`, `:548`) and adds no query.
- **The cross-slice contract** is as stated:
  - slice 2 D12 R3: `.data` is present, and every failure after the prompt returns `failed`;
  - `COPILOT_RAW_EVENTS` is named;
  - slice 1 D16 strikes `spend_from` and `quota_hold_from`, and keeps `compaction_percent` for this
