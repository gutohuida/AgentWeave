### 1. `an-agents-tool-server-is-the-one-its-hub-loaded` (F354): APPROVE WITH FIXES

These claims hold:
- `mcp_server.py` imports only the standard library and `fastmcp`, so a byte copy runs identically.
- There is one spawn site (`agent_trigger.py:1141-1144`).
- A 409 re-queues the input with its reason (`turn_scheduler.py:424`).
- Installed and source Hubs both work, because the pin reads its own `__file__`.
- There is no double start.

Findings:
- **MEDIUM (security): the pin location is in the shared temp directory.** Today it is
  `tempfile.gettempdir()/agentweave-tool-server/<digest>/`, which is `/tmp` on native Linux. Another
  local user could pre-create that directory and swap the file between the check and the spawn (a
  TOCTOU race). The same pre-created directory would also make every MCP turn of a second user's Hub
  answer 409. **Fix (operator):** put it under `~/.agentweave/hub/tool-server/<digest>/`.
- **LOW:** add a task that rewrites `.claude/rules/mcp-server.md`'s line *"The operator's `:8000` Hub
  spawns this file fresh on every agent turn…"*, and that checks the `DEAD-ENDS.md` entries mentioning
  `mcp_server.py`.
- **LOW:** old pinned copies are never cleaned up. Prune other digest directories at startup, or say
  that they stay.

### 4. `input-the-hub-accepted-is-answered-as-accepted` (F349): APPROVE WITH FIXES

These claims hold:
- The trigger plus six sites (`messages.py:318`, `agents.py:2257`, `agents.py:2693`, `questions.py:212`,
  `inbound_queue.py:253`, `accounting.py:78`).
- A per-agent lock and an atomic Run+delivery commit rule out double starts.
- A drain that raises is lost today (`run_reconciliation.py:184-187`, `:205`).

Findings:
- **HIGH: the loop/flow/job firing path has the same defect.**
  - `scheduler.py:3444` commits the entry, `:3467` persists an event on the job's session, and `:3471`
    calls `schedule_agent` without a guard.
  - If that call raises, `_do_fire_job`'s `except` (`:3514`) marks the JobRun `failed` while the entry
    stays queued and later runs.
  - If the event write failed, the reused session raises `PendingRollbackError`.
  - `scheduler.py:3605` catches the error and moves on.
  - **Fix (operator: fold it in):** route both sites through `schedule_accepted` and
    `persist_accepted_event`. A non-terminal `waiting_reason` leaves the JobRun in progress, not
    `failed`. Add a test for each.
- **MEDIUM: "bounded retry" is not bounded.** It retries any `Exception`, so a permanent error retries
  forever and nothing surfaces it. **Fix (operator: transient only):** retry only `OperationalError` or
  a locked database. Anything else is logged once and the entry stays queued.
- **LOW:** pending retries do not survive a restart, because they live in memory. Say so in D2.
- **LOW:** the requirement's *"whatever fails after the input was queued"* contradicts the accepted
  exception, where a failed withdrawal after a refusal still answers 500. Add that exception to the
  text.

### 5. `a-loop-that-is-gone-lets-go-of-its-document` (F53, F157): REVISE (spec deltas only). Fixed per the operator.

- **HIGH: three existing SHALLs are contradicted, with no MODIFIED delta.**
  - `agent-loops/spec.md:43-52` says *"No other code path SHALL set or change a task's `loop_id` once
    created"*. Name claim-time adoption as a third mechanism.
  - `spec.md:146-153` says a second loop claiming a document *"SHALL be refused"* (already stale since
    `2239f38`), and that the declaring loop's id is written on every materialised task. Change these to
    "no other **live** loop" and "the live declaring loop".
  - `spec.md:497-501` says an archived loop's queue history stays *"still retrievable"*. After
    adoption, `GET /tasks?loop_id=<gone>` no longer lists the moved tasks. **Fix:** persist a
    `loop_tasks_adopted` event `{from_loop, to_loop, task_ids}` in the same transaction, against both
    loop ids (`GET /loops/{id}` reads `EventLog.loop_id`). The delta should say this is how the history
    survives.
- **MEDIUM:** an adopted in_progress task can have an archived assignee (`scheduler.py:1839-1843`).
  Keeping the assignee is the operator's decision. Add a design note and a test for what the successor
  reports: a stall reason that names the archived assignee.
- **LOW:** the claimed races hold (partial unique index, rollback at `jobs.py:765-770`). A loop that
  has ended but is not archived still blocks a successor; say so. There is no collision with B10.
