### 1. F354 — live agents run MCP from the working tree (open)

**Re-verified.** `agent_trigger.py:1141-1144` still names `Path(__file__).resolve().parents[2] /
"mcp_server.py"` on every spawn; it reaches Claude as `--mcp-config` (`runner_commands.py:250-259`)
and Codex as `config.mcp_servers` (`codex_appserver.py:969-972`). `mcp_server.py` imports only the
stdlib and `fastmcp` and never reads its own location (`grep`), so a copy is the same program.
It is the only repository file spawned per turn (`grep -rn sys.executable hub/hub`).

**Options.** (a) pin the bytes at Hub start and spawn a content-addressed copy outside the repo;
(b) a rule never to edit `mcp_server.py` in the checkout `:8000` runs (the status quo, which has
blocked F363 since 2026-09-14); (c) run `:8000` from elsewhere (contradicts CLAUDE.md's
"by intent"); (d) `python -m hub.mcp_server` (still reads the working tree).

**Recommended: (a).** It is the only option under which the Hub's routes and its tool server
change on the same event, a restart. Written as `an-agents-tool-server-is-the-one-its-hub-loaded`.
A pin that cannot be written refuses the turn through the context file's existing
`TriggerAgentError` 409 path (`agent_trigger.py:1110-1118`); it never falls back.

**For B12 (F363), explicitly:** B11 recommends pinning. Once that change is built **and `:8000` has
been restarted onto it**, an edit to `mcp_server.py` in the checkout reaches `:8000`'s agents only at
`:8000`'s next restart, together with the routes it calls, like every other Hub file. So F363 needs
no version-skew analysis for the pinned case. Recommended order: this change's IMPL → the operator's
`:8000` restart → F363's `mcp_server.py` half. B12's own D5 shows F363 degrades gracefully if it
ships first, so this is a preference, not a gate. Until the restart, `:8000` still spawns the
working tree's file, so an uncommitted edit there still reaches live agents.

### 6. F133 — queue status recomputes the reason (open, no-spec)

**Re-verified.** The status route's token-budget branch asks `all(entry.origin_type != "operator")`
over every queued entry (`inbound_queue.py:140-144`). The scheduler asks whether any operator entry
is in the **selected turn**: the controlling entry's conversation, within the hop budget, of a
compatible kind (`turn_scheduler.py:340-376`). An operator entry in another conversation, behind an

**Options.** Mirror the selection in the route (narrow; keeps two copies), or factor the pure part of
the selection out of `_attempt_turn` (`controlling`, `selected`, `initiator` from entries, budget and
cap; the conversation-lifecycle check stays in the scheduler) and have both call it. **Recommended:
the shared function**, as a Round-3-style fix with no spec. **Sequencing:** B1's
`why-queued-input-waits-is-told-truthfully` rewrites `get_queue_status` (its D3, D4); land F133 as a
task inside that change's IMPL or strictly before it, never in parallel. Tests (in the route's own
order, `sequence` ascending): an autonomous entry in conversation A, then an operator entry in B,
budget exhausted → `waiting_reason == "token budget exhausted"` (fails today: `null`); reversed (the
operator's entry first) → the reason is **not** the budget one, because the scheduler would start it.
The reversed case is what fails if the test's order were the one the route never returns.

### 18. F21 — retire? (open; the premise is challenged)

The proposed answer was "retire: not fixable inside AgentWeave", on the ground that whether Claude
Code defers MCP tool schemas behind a search step is the harness's behaviour. **Two things R1 found
weaken that:**

- **The harness has a setting for it.** The installed `claude` (2.1.280) reads an
  `ENABLE_TOOL_SEARCH` environment variable (strings in the binary: an unset or `auto` value means a
  10%-of-context threshold, a number sets the percentage, and a `standard` mode logs
  `result=false`). The Hub already sets its own variables in the run's environment
  (`agent_trigger.py:1184-1187`). Semantics **unverified by a run**.
- **The Hub does not isolate the run's MCP configuration.** `build_command` passes `--mcp-config`
  without `--strict-mcp-config` (`runner_commands.py:250-259`; `grep strict-mcp hub/hub` finds
  nothing), so a run may also load servers from the operator's own configuration, which count toward
  the threshold that triggers deferral. Whether any such servers reach a headless run on this machine
  is **unverified** (the user-level `mcpServers` in `~/.claude.json` is empty; account-level
  connectors were not checked).

And `agent-tool-surface` *"An invocable tool surface is the default, not an opt-in"* already requires
that a newly created agent's runs have a tool surface *"the agent can actually call"*. So F21 may be
a breach of a shipped requirement with a fix in `runner_commands.py`.

**Recommended: do not retire yet.** Run one probe (Haiku, per the cheap-model rule) with three arms:
the default argv; `--strict-mcp-config`; `ENABLE_TOOL_SEARCH` set to disable deferral. For each,
read the `system/init` line's tool list for `mcp__agentweave__record_evidence` and whether a search
tool is offered. If an arm makes the Hub's tools directly callable at an acceptable context cost, F21
becomes a small spec change on `agent-tool-surface`. If none does, retire it as proposed. Also worth
a separate finding whatever the probe shows: a Hub run may inherit the operator's own MCP servers.
