Final -- what the bundle reached, and why

The Hub's live event stream (SSE) has three defects that each make the app show something other than the truth: it announces a write that is then rolled back (F335), it silently drops events for a slow tab (F253), and the app throws away 18 of the 63 kinds the Hub sends (F251). Three small changes fix them. IMPL is not started; the bundle is parked awaiting approval.

The design questions, with options and recommendations

F335: how to stop announcing a write that can roll back. The options were:

  • (A) Defer the announcement to the commit of the session that staged it. Publish on the root

transaction's after_commit, and drop it on the root's after_transaction_end.

  • (B) Make every caller of apply_transition broadcast after committing.
  • (C) Stop broadcasting the kind live.
  • (D) create_task the async broadcast from the listener.

Recommended: A. B spreads the rule across callers, and the next commit=False announcement repeats the defect. C drops a true live signal. D reorders frames and makes tests depend on timing.

R1 measured the SQLAlchemy event order on 2.0.50 with aiosqlite, rather than assume it:

  • A close without commit fires no after_rollback.
  • A savepoint release fires after_commit with in_nested_transaction() == True.

So the listener must skip nested commits, and clearing must hang off after_transaction_end. The listener runs on the loop thread.

Two traps are named in the design:

  • The existing 1.8a spy is on broadcast, which the deferred path bypasses. The new tests spy on a

single sync SSEManager.publish funnel, and a control proves the spy sees a true resolution.

  • An exception in after_commit propagates out of a commit that has already landed. That would

be a 500 for a write that happened (JSONServerSentEvent serialises in its constructor). So each publish is caught and logged.

The operator's PATCH route keeps the wire order run_divergence_resolved before task_updated (tasks.py:1470 commit, :1472 broadcast). A test pins that order from the real route.

F253: how to tell the client. The options were:

  • (A) A stream_gap frame.
  • (B) Close the slow subscriber so the client reconnects.
  • (C) Event IDs and replay.
  • (D) Block, or grow the queue.

Recommended: A, with one change from the finding's sketch: the stream writes the gap, not the next put. A gap queued by the next broadcast is never delivered after a burst followed by silence, and it competes for a full queue. B loops a throttled tab through reconnects and puts nothing on screen. C is out of proportion. D stalls the broadcasters.

The gap carries no project_id. It is stream metadata, like connected, because the operator queue mixes projects. The client answers it instance-wide: invalidateQueries() plus the existing reconnect listeners. The Activity feed shows one line whatever project is selected. The two route generators are folded into one stream_frames, so the gap is written once and can be unit-tested without a stalled socket.

F251: what the app does with a kind (B9-Q1, for the operator). The options were:

  • (A) A runtime allowlist generated from a server registry.
  • (B) No runtime filter, with the generated vocabulary kept as a TypeScript union type.
  • (C) No filter and no generation.

Recommended: B.

  • A reintroduces F251 whenever the committed bundle lags the Hub. It does lag: /health's

ui_stale exists for exactly that.

  • C lets a handler for a kind that is never sent (job_deleted) compile.
  • B blocks both failure directions. Nothing is dropped by omission, and tsc (run by

npm run build) rejects a case or === against a kind that does not exist.

The server side is the same under every option: hub/hub/sse_events.py, plus an AST test that each broadcast kind is registered and each registered kind is broadcast. At runtime an unregistered kind is warned about, never raised on, for the same after-commit reason as F335.

F253 does not depend on the other two, because its client branch runs before the allowlist test. If F335 has landed, F253's counter sits in F335's publish funnel. If F253 has landed, F251's registry lists stream_gap as a stream frame. Order to build: F335 → F253 → F251. Stopping after any one leaves complete work.
