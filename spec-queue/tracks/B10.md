### D6 — build the mount point, or delete the code? One answer per surface

**The rule R1 applied.** A surface is built when it carries something the operator needs and cannot
get elsewhere, and a small mount exists. It is deleted when the spec already removed it on purpose,
or when everything it carried is shown somewhere else. That follows `DIRECTION.md`'s two standing
lines: "barriers are the enemy" argues against deleting a warning or a control, and "cleanest
solution wins" argues against keeping unmounted code that a unit test certifies.

**1. Launchability card (F178): build the collaboration line in `RunnerPicker`, and delete
`AgentCard`.**
- *Build* releases the one sentence that predicts a silent failure (*"AgentWeave tool calls … will
  be silently denied"*). It goes in the component that already fetches the verdict and already
  handles a failed read, so no query call site is added or removed. Spec: one ADDED
  `runtime-diagnostics` requirement.
- *Delete* would remove `collaboration_*` from the payload and REMOVE `runtime-diagnostics`' *"Collaboration
  readiness is checkable before it is needed"*. The silent failure would stay, with no warning left.
- `AgentCard` goes either way. Its other content is on the rail and in the header, and an
  unmounted card certified by a test is how F178 went unnoticed for 24 days.
- Change: `a-runner-that-cannot-collaborate-says-so-where-it-is-bound`.

**2. Loop controls (F225): build Stop, Archive and delegation in `LoopTab`.**
- *Build* costs three mutation hooks and one tab section, and uses existing routes only. The Stop
  control uses `update_job`'s existing operator stop, not a new `/loops/{id}/stop`. It makes
  `LoopTab.tsx:242`'s *"runs until stopped by the operator"* and `LoopsIndexTab`'s *Show archived*
  true. The clientless ceiling goes from 35 to 33.
- *Delete* would REMOVE delegation (`agent-loops:344-350`, *"SHALL be able to delegate … and to take
  it back"*) and loop archival. That is a governance capability the spec wrote on purpose, and the
  code that enforces it (`tasks.py:701-703`) would stay behind without its switch.
- The change also fixes the missing operator `loop_stopped` event, written in the same transaction
  as the stop. Otherwise a failed event write would answer 500 for a stop that landed.
- Change: `a-loop-is-stopped-archived-and-delegated-from-its-own-tab`.

**The interaction with `ROUNDS.md` item 3.** The `archive_job` refusal was withdrawn *because* no
stop control existed, to be *"revisited only if a stop control ships"* (`jobs.py:1238-1242`). This
bundle ships one, so it re-answers the question, and the answer is **still no refusal**:
- Since F224, archiving the job ends the loop in the same transaction, with a recorded reason
  (`jobs.py:1279-1285`). An archived job can never fire again (F222). So the refusal's purpose,
  D17's *"archiving can never conceal work that is still firing"*, is already met.
- The main spec says it outright: *"Archiving a job retires its loop … the operator is not required
  to stop it first"* (`agent-loops:534-540`).
- The refusal would turn one action into two and add no information.

The only code consequence is `archive_job`'s docstring. The two answers are consistent. *Build* is
what makes the refusal *possible* to bring back, and D1 of the change is why it still should not
come back.

**3. Messages screen (F260, F263): delete.**
- The *Messages* destination was removed by an accepted spec, which also requires the messages API
  to stay (`agent-conversation-workspace:162-179`). Peer mail is read in each conversation's
  timeline. What would be lost is a project-wide who-wrote-to-whom view. The spec judged that
  redundant, and nothing since has asked for it back.
- *Build* would mean reversing a specified decision, and the screen's three query sites are all
  MISREPORT rows (`n11` rows 165-167).
- **The deletion changes no main spec, so it gets no change directory.** It is a no-spec round.
  Delete `components/messages/` (3 files), `api/messages.ts`, and the `@/api/messages` mock in
  `conversationShell.test.tsx:49`. Remove `n11`'s three `DEAD` rows (165-167) and lower
  `UNHANDLED_SITE_CEILING` by the measured drop.
- **The route ceiling does not move.** `GET /messages` and `PATCH /messages/{id}/read` stay
  "reached" through the CLI transport (`n10` measured today: both rows have `cli: True`). Deleting
  the UI hooks therefore adds no clientless route.
- Leave the CLI transport's `get_pending_messages`/`archive_message` alone in that round. Deleting
  them would make both routes clientless, which the R-1 ratchet forbids unless the routes go too,
  and the spec requires them to stay.
- F263 needs nothing: it was already fixed.

**4. The message-read flag (F259): stop deciding anything from it. Derive "outstanding" and
"pending" from the delivery the inbound queue already records.**
- Every agent- or operator-sent message has exactly one entry with `message_id`
  (`messages.py:265-276`, `agents.py:2228-2236`). Its `state` moves queued → delivered, and back to
  queued or to withdrawn (`inbound_queue.py:175-195`, `:225-295`). The timeline already derives
  `delivery_state` from it (`agent_chat.py:210`).
- Options, laid out in the change's design D1:
  - **(a) Mark read on delivery.** A second stored copy, four transitions to keep in step, and a
    backfill migration against `:8000`. Withdrawn mail would stay outstanding forever.
  - **(b) Derive (recommended).** Two query changes, no migration, no API change.
  - **(c) Delete the column and the PATCH route.** The cleanest end state, but it modifies
    `agent-conversation-workspace`'s *"messages API MUST remain unchanged"* and rebuilds a table on
    `:8000`. It stays available later as a separate cleanup.
- Spec: MODIFIED `agent-loops` *"An empty queue with a request still in flight…"*. Its scenario said
  *"unread message"*, which named the dead flag.
- Change: `a-loops-outstanding-mail-is-mail-not-yet-delivered`.
- **How it fits with answer 3:** with (b), deleting `useMarkRead` changes nothing the product
  decides, so the two can ship in either order.

nothing mounts, routes that have no button, and a flag that nothing sets. For each one it decided
whether to **build the missing mount or delete the dead code** (D6). One finding was already fixed.
Three are addressed by specified changes, and one by a no-spec deletion. **IMPL has not started. The
bundle is parked, awaiting the operator's approval.**

### Decisions

| # | Question | Recommended answer | Why |
|---|---|---|---|
| D6.1 | Launchability card (F178): build or delete? | **Build** the collaboration line under the runner picker, and **delete** the unmounted `AgentCard` | The line predicts a silent failure: a Codex agent's AgentWeave tool calls are denied with no one present to approve them (`agents.py:256-262`). The picker already fetches the verdict and handles a failed read, so this is a few lines. `AgentCard`'s only importer is its own test. The runnable half already reaches the picker (F179, `12db377`). |
| D6.2 | Loop controls (F225): build or delete? | **Build** Stop, Archive and delegation in the loop's own tab | The spec wrote delegation and loop archival on purpose (`agent-loops:344-350`, `:483-506`), and the enforcement code exists (`tasks.py:701-703`). Only the buttons are missing. The tab already promises *"runs until stopped by the operator"* (`LoopTab.tsx:242`) and offers no way to do it. The work is three hooks on existing routes, and the clientless-route ceiling drops 35 → 33. |
| D6.2a | Once Stop exists, should archiving a running loop's job be refused (ROUNDS item 3)? | **No, still no refusal** | Archiving the job already ends the loop in the same transaction, with a reason (`jobs.py:1279-1285`), and an archived job can never fire again (F222). The main spec says *"the operator is not required to stop it first"* (`agent-loops:534-540`). A refusal would add a step and no information. |
| D6.2b | Should an operator stop whose reason reads "loop queue is empty" record `completed`? | **No: an operator stop always records `stopped`** | The main spec forbids deriving the ending from prose (`agent-loops:552`). `end_loop` does exactly that (`loop_ending.py:57-58`). The fix is a required `completed=` keyword on `end_loop`. |
| D6.2c | Should the stop, archive and control events be written in the same transaction as the change? | **Yes, all event rows of the four functions** | Today each is written after the commit, so a failed write answers 500 for a change that landed with no history row. In the same transaction, B9's now-final guard (rules 1 and 2) is also satisfied mechanically, whichever change lands first. The frame order is fixed in design D3. |
| D6.3 | Messages screen (F260): build or delete? | **Delete** | An accepted spec removed the Messages destination and kept only the API (`agent-conversation-workspace:162-179`). Peer mail is read in each conversation's timeline. |
| D6.4 | Message read flag (F259): mark read on delivery, derive, or drop the column? | **(b) Derive "outstanding" from the inbound queue's delivery state** | There is no migration, no API change and no second stored copy. Withdrawn mail stops counting as outstanding. Mail delivered into a creator turn that is still running counts as in flight. (c), dropping the column, remains a possible later cleanup. |
