### F363 (B) — still open; change `a-specification-is-read-in-results-that-fit`

Re-verified. The route has no size bound (`hub/hub/api/v1/agent_actions.py:1374-1481`). `include` is
still only `requirements|full` (`:1377`), and a `spdoc-` id still reaches `validate_spec_path`
(`:1401-1404` → `spec_manifest.py:72`), which answers *"path must begin with 'spec/'"*. Measured
on this repository's own corpus: the default view of
`spec/capabilities/agent-conversation-workspace/spec.html` is over 72,000 characters before its
envelope, with 47 requirements (30.7 KB of statements and 41.9 KB of criteria).

**One claim in the finding changed shape.** *"`list_evidence` accepts that id"* is not quite right.
`list_evidence_for_agent` (`agent_actions.py:1248-1275`) reads `document` **only** when
`identifier` is given, and then resolves it by path (`_resolve_requirement`, `:1154-1164`, which
would 404 on an id). Without `identifier`, `document` is ignored silently, so the call "accepts" the
id by not looking at it. The ids agents actually hold come from tasks (`spec_document_id`,
`mcp_server.py:754`, `:859`). `run_task_binding.spec_document_for_task` (`:464-477`) exists
because a builder tried the id and was refused. **Candidate new finding (not filed, since R1 does
not edit FINDINGS.md):** `list_evidence`'s `document` is silently ignored when `identifier` is
empty.

**The F354 dependency.** `spec-queue/tracks/B11.md` did not exist when R1 ran. **Assumption
stated:** R1 assumes nothing about F354's answer. The change is designed so that either version skew
between `mcp_server.py` (spawned from the working tree) and the running Hub degrades to today's
behaviour, never to a refusal (design D5). The skew table:

- **New tool, old Hub:** the extra `identifiers` query parameter is ignored. An `include=outline`
  gets a 422, which is why the tool's default must stay `requirements` (task 1.11).
- **Old tool, new Hub:** everything works.

So F354 decides only *when* IMPL's commit may land on the branch `:8000` runs, not the design. If B11
recommends pinning the server the Hub loaded, D5 becomes belt and braces.

**D-B12-3 — how the read is bounded.**

- (a) **A budget enforced by the Hub, with continuation by requirement identifier.** Recommended.
  An agent cannot see the harness ceiling, so a bound it chooses is chosen wrong. Identifier-keyed
  continuation matches how agents already reason (`FR-n`) and also serves a builder that only
  needs its task's requirements.
- (b) A `max_chars` or page parameter chosen by the agent. It fails invisibly, because the agent
  sees a spill notice and not a size.
- (c) Only add `outline`. The default read shrinks, but criteria reads still spill.

Recommended: (a), at 40,000 serialised characters. R2 must confirm Claude Code's MCP ceiling. R1
believes it is 25 k tokens by default (`MAX_MCP_OUTPUT_TOKENS`), but did not verify.

**Route under raise (design D6).** `read_document` raising `OSError` or `UnicodeDecodeError` is an
unhandled 500 today (`spec_documents.py:136-142`). R1 left the choice of owning it to R2; the
recommendation is a 409 naming the reason.

`turn_scheduler.py:596-608`, where `gives_up = attempts >= DELIVERY_ATTEMPT_LIMIT` and the entry is

**"Queued as Q4-SPEC": no such change exists.** `openspec/changes/` has no Q4-SPEC directory and

**What closed the defect: every path that could queue a review with no commit to check out now
refuses before queueing.**

2. **The operator's `POST /agent/trigger`** refuses 409 before anything is queued

3. **The divergence restaff of a failed review** (`run_divergence.py:483`) follows a review turn

So the entry F65 describes can arise today only as a leftover from before 2026-08-28. Such a

**Needs:** a ledger close on F65, not a spec. The close should cite `3e07726`, the route refusal,

### F330 (C) — still open; change `a-refused-first-send-leaves-no-exploration-behind`

Re-verified at `hub/ui/src/components/agents/NewConversationSurface.tsx:83-117`: the create happens
first, the trigger second, and a refusal throws with no cleanup. `POST /project/documents` writes
the file before its commit (`spec.py:1461` → `spec_service.py:238`). A file under `spec/` without a
row is not inert, because discovery and adoption find it. `RequestModel` refuses unknown fields
(`schemas/common.py:21`, F116). That makes the shipping order a hard constraint: a new bundle
against the old Hub would refuse every explore send (design D5). So the change ships as two
commits, with the UI only after the operator restarts `:8000`.

**D-B12-1 — what happens to a document created for a refused send.**

- (a) **The request that created it discards it** (file, events, index rows and the row), gated on
  the document still being `exploring`, having no later event, and being named by no task or loop.
  The function is reachable from no route. Recommended.
- (b) The composer archives it through the phase machine
  (`spec-document-authority` `:1891`). This keeps "no deletion", but the row and the file remain,
  so F330's *"in the repository and in the spec list"* is only half fixed. It also does nothing
  when the tab closes or the network drops.
- (c) Create it at dispatch. It needs a queue-entry column (a migration), gives no path to a
  queued first send, and still has to compensate for a file written before a rolled-back dispatch.

The argument for (a) against `:1891`'s *"rather than a separate deletion path"*: that requirement
governs a document someone has seen. This one is the refused request undoing its own write. R2 is
asked to challenge it.

**D-B12-2 — the document cannot be created (naming exhausted, write error).**

- (a) **Refuse the send and say why.** Recommended. The composer restores the text on any throw
  (`Composer.tsx:216-217`), so nothing is lost. Sending without the document is exactly the
  symptom the explore control was built to stop (`NewConversationSurface.tsx:72-76`).
- (b) Today's behaviour: send anyway, silently without a document. It is pinned by the vitest case
  *"still starts the conversation when the document cannot be created"*, which (a) replaces.

**Route under raise:** design D2 tabulates every raise (mint, create, file write, commit, dispatch
refusal) and what each leaves behind. A failed file removal answers with the original error and
leaves a file with no row, which is no worse than today.

**Out of scope, stated in the spec:** input answered `200 queued` and later given up after three
delivery failures. The operator was told it was accepted, and the document is retired through its
phase.

### D-B12-1 reversed

R2 recommends **(d): nothing committed is ever deleted.** Route-level refusals are all before the
creation point, and a failed commit rolls the rows back while the route removes its own file. That
covers F330's recorded case (F329's 500 at the commit) and its reproduction (an archived agent).
Only a dispatch refusal after the commit remains, such as an agent with no row
(`agent_trigger.py:676-687`, not checked by the route) or a runner with no adapter (`:731-738`).
There the route **archives** the document through `spec_lifecycle.transition` as the operator's act
(`exploring → archived` is permitted for a document with no requirements or tasks,
`spec_lifecycle.py:320-341`). Archived documents are left out of the spec tree's current view
(`specNavigation.ts:53`, `:103-104`) and listed under *Archived* in the browser
(`SpecDocumentBrowser.tsx:136-149`). So the file stays in `spec/changes/` for that rare case only.

- (a) R1's delete remains available, but it needs MODIFIED deltas to two main-spec requirements
  (append-only events, and `:1891`'s "rather than a separate deletion path"). R2's answer to the
  question R1 left open: the "deletion path" argument alone might hold, but the append-only rule does
  not bend to it.
- (b) The composer archives, and (c) create at dispatch: rejected for R1's reasons, which still hold.
