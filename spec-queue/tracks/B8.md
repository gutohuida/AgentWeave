## R1 — explore and propose (2026-09-24)

### What the code showed (HEAD `404c7d5`)

`cut_over` (`hub/hub/checkpoint_cutover.py:63-200`) has one guard against a second handover. It
refuses when `predecessor.lifecycle == "archived"` (`:97-103`), and its refusal ends *"unarchive it
first"*. The guard reads the lifecycle at `:97` and writes it at `:144` (`archive`), then commits
at `:145`. Between the two it awaits `archivable` (`:105`). Nothing records that a checkpoint was
handed over. `Checkpoint` (`hub/hub/db/models.py:1668-1804`) has no such column, and
`InboundQueueEntry` has no checkpoint id. `unarchive` (`hub/hub/conversations.py:479-482`; route
`hub/hub/api/v1/agent_chat.py:623-635`) is never refused and resets `lifecycle` to `open`. Two
callers exist: the route (`api/v1/checkpoints.py:370-404`, refusal → 409 at `:391-394`) and the
automatic trigger (`checkpoint_trigger.py:319-336`, refusal → `cutover_refused` on
`checkpoint_ready`). `take_checkpoint` holds an in-process claim (`_checkpoint_claims`,
`checkpoints.py:27-28, 167-186`), and nothing guards the cutover.

### Each finding re-verified

- **F293 — still open.** A throwaway test used the suite's own fixtures on its file-backed SQLite:
  `cut_over`, then `unarchive` + commit, then `cut_over` again with the same checkpoint. It produced
  **two** `handoff` successors (`conv-2997cf6e3357`, `conv-2ecad0277068`). The shape is unchanged
  since filing. The only line drift: the guard is still at `:97`.
- **F294 — still open.** Two sessions loaded the conversation and checkpoint, then waited on an
  `asyncio.Barrier(2)`, then ran `cut_over` concurrently. Both returned successors
  (`conv-9433b9e6954f`, `conv-e632a122f613`). Without the barrier the second read came after the
  first commit and was refused. So the barrier is the deterministic test, and task 1.2 keeps it.
- **A shape R1 adds to F293, not a new finding.** The app's own Handoff (`writeCheckpoint`,
  `hub/ui/src/store/checkpointOperationStore.ts:37-75`) always takes a **new** checkpoint and then
  cuts it over. An operator who unarchives and presses Handoff therefore forks the line with a
  *different* checkpoint. A per-checkpoint column alone would not close that. This drives D2.
- `git log -S "cut_over_to_conversation_id"` finds nothing, so the column has never existed.
  Operator's `:8000` database, read with `mode=ro`: head `0105`, 16 checkpoints, **0** cutover
  deliveries, **0** `handoff` conversations. The trial database has 0 checkpoints.

### Design choices, with the recommendation

| # | Question | Options | Recommended | Why |
|---|---|---|---|---|
| D1 | Where does the handover identity live? | (a) `Checkpoint.cut_over_to_conversation_id`; (b) `Conversation.handed_over_by_checkpoint_id` | **(a)**, `String(64)`, nullable, no FK | The checkpoint listing can then answer "where did it go". The successor side is already answerable via `lineage_id`. An FK would need a batch rebuild of `checkpoints` (constraint names pinned by `0088`), and SQLite does not enforce FKs here |
| D2 | "At most once" per checkpoint, or per conversation? | (a) per checkpoint; (b) partial unique index `checkpoints(conversation_id) WHERE cut_over_to_conversation_id IS NOT NULL` | **(b)** | (a) leaves the UI's own Handoff after an unarchive able to fork the line, and leaves the trigger-vs-banner race (`checkpoint_trigger.py:327-333` offers C1 while the trigger cuts over C2). | D3 | How are concurrent presses serialised? | (a) in-process claim like `_checkpoint_claims` (F294's own rec.); (b) compare-and-set `UPDATE … WHERE cut_over_to_conversation_id IS NULL` + D2's index | **(b)** | The migration exists anyway. | D4 | Keep refusing a conversation archived by hand? | (a) keep; (b) allow now that the column exists | **(a)**, reordered | `archivable` returns None for an archived conversation (`conversations.py:395-396`), so allowing it skips the run/queue checks. | D5 | Backfill legacy rows? | (a) yes, from delivered entries; (b) no | **(a)** | Exact, not heuristic: the delivered content is `_DELIVERY_PREAMBLE` + `# Checkpoint {id}` (`checkpoint_generation.py:285`). ### What each route returns when what it calls raises

The compare-and-set miss and the `IntegrityError` are converted to `CutoverRefusedError` **inside**
`cut_over`, after a rollback. So the route still answers **409**, and the trigger still reports
`cutover_refused`. The rollback is safe because neither caller has anything pending (route
`:378-384` only reads; trigger `generate_checkpoint` commits at `checkpoint_generation.py:664`).
Task 1.8 pins that the trigger's checkpoint survives the rollback. A lock-timeout
`OperationalError` stays a 500, as today; R1 does not widen it.

### The locking argument, measured (the point left open by R1)

Each scenario ran 5 times per mode:

| Race | WAL / 30 s (suite) | rollback journal / 5 s (production) |
|---|---|---|
| Same checkpoint (1.2) | 5/5: one success and one compare-and-set miss; 1 successor, 1 entry | 5/5, same |
| Two checkpoints of one conversation (1.4) | 5/5: one success and one `IntegrityError` → refusal; 1 successor, 1 entry | 5/5, same |
| `OperationalError` / `database is locked` | 0 | 0 |

The loser waited 15–46 ms, which is the busy handler working. In legacy transaction mode the
pre-write `SELECT`s open no transaction, so the loser holds no shared lock that could deadlock the
winner's commit. **R1's argument stands, and it is now measured.** Reproductions on today's code:
F293 gave 2 successors, and F294 (barrier) gave 2 successors and 2 entries.

### Decisions

| # | Question | Recommended answer | Why |
|---|---|---|---|
| D1 | Where is "this checkpoint was handed over to X" recorded? | On the checkpoint: a new nullable column `Checkpoint.cut_over_to_conversation_id`, with no foreign key | The checkpoint listing can then say where each checkpoint went. The other direction is already answerable through `lineage_id`. A foreign key would force a table rebuild of `checkpoints` (constraint names pinned by `0088`), and SQLite does not enforce it here |
| D2 | Is "at most once" per checkpoint, or per conversation? | **Per conversation**: a partial unique index on `checkpoints(conversation_id)` where the column is set | The app's own Handoff always takes a **new** checkpoint (`checkpointOperationStore.ts:37-75`). A per-checkpoint rule alone would still let one click after an unarchive fork the line. The lineage requirement says a line is linear. Chains are unaffected |
| D3 | How are two simultaneous presses serialised? | In the database: a compare-and-set `UPDATE … WHERE cut_over_to_conversation_id IS NULL` plus D2's index, with the ids captured before any write and an explicit flush first | This works across processes. R2 measured it: 20 of 20 races were clean, in both WAL (the suite) and rollback journal (production). The rollback expires instances, hence the captured ids |
| D4 | Keep refusing a conversation that was archived by hand? | Yes. The spent-checkpoint and handed-over checks now come first, so *"unarchive it first"* is said only where it is true | `archivable` returns None for an archived conversation, so allowing it would skip the run and queue checks |
| D5 | Backfill the column for past cutovers? | Yes, exactly, from delivered entries (`# Checkpoint <id>`). The first handover per predecessor wins | Legacy handovers stay protected, and a database that already holds a fork still gets its index. It writes 0 rows on both local databases |
| D6 | Should the automatic trigger keep checkpointing a reopened conversation that was already handed over? | **No.** Decline in `consider` before the notes, warning and generation branches | Otherwise D2 turns each turn past the threshold into a billed generation followed by a refusal (R3) |

### Open for the operator

1. **Approve D2, per conversation** (recommended). A reopened, handed-over conversation cannot be
   handed over again by a new checkpoint. You keep working in it or in its successor. *If "per
   checkpoint only":* F293 and F294 close, but Handoff after an unarchive, or the trigger racing
   your press, can still fork a line. The index, tasks 1.3, 1.4 and 1.12's index half, and D6 are

2. **Approve D6, the trigger declines** (recommended). *If "generate anyway":* each turn past the
   threshold in such a conversation bills a checkpoint and a probe, then sends a `cutover_refused`
   event. *If "decline only automatic generation":* the warnings return, and their Handoff bills a
   checkpoint and then gets a 409.
3. **Migration number (ordering note, not renumbered):** four unarchived changes name `0106`. They

   `worker-spend-counts-against-the-budget`, and `a-footprint-names-the-line-of-work-its-commit-is-on`.
