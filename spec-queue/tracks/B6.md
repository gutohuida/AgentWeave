### What R1 found beyond the ledger

These are not in `FINDINGS.md` (R1 may not write it). The orchestrator should decide whether to file
them.

1. **A footprint watches the whole tree** (the defect `read_footprint`'s docstring defers,
   `requirement_evidence.py:519-522`; F215's entry measured 44 candidates from one commit). Measured
   in R1: operator evidence with `locator: "ledger.py"`, then a commit changing only `other.py` →
   one candidate with `observed: {"other.py": …}`. **Carried** in the first drift change, because
   making drift reachable without it delivers a flood.
2. **Rejecting a proposal in the app leaves it on screen.** `reject_proposal_route` broadcasts
   nothing (`spec.py:669-694`), `useSpecMutation` does not invalidate `specProposals`
   (`api/spec.ts:244-256`), and `refetchOnWindowFocus` is off (`main.tsx:8-15`); the comment at
   `api/spec.ts:164-166` claims reject broadcasts. Read, not driven. **Carried** in the proposal change.
3. **The app records every rigor change with an empty reason.** The Enforcement select posts on
   change with no reason (`SpecPhaseBar.tsx:62-70`, `:184`), while the spec requires the reason to be
   recorded (`spec-document-authority/spec.md:959-962`). **Carried** in the audit change.
4. **A drift candidate can be answered twice**; the second answer overwrites the first and its
   fingerprint (`resolve_drift`, `requirement_evidence.py:1190-1222`, no state check). **Carried** in
   the second drift change.
5. **Only one unit of a multi-unit proposal can be accepted without a resubmission.** Accepting one
   changes the digest, and every sibling is refused as stale on its accept
   (`test_accepting_a_second_proposal_against_the_same_digest_is_refused_as_stale`). The spec calls
   proposals *"individually acceptable"* (`spec-document-authority/spec.md:1080-1086`). The proposal
   change's supersession makes the agent's resubmission replace the stale siblings, but does not
   change the compare-and-swap. **Not carried** — a design question for the operator.
6. **Reindex and arrange write files before the database commit** (`spec.py:1255-1265`,
   `:1375-1379`): an `OSError` mid-rerender leaves files written and digests rolled back. **Not
   carried**; flagged for R2 in the corpus change's D6.
7. **A drift candidate is never superseded when its requirement is reworded**, though the model
   comment says it is (`models.py:2643-2644`). **Not carried**; noted in the first drift change.
8. **A capability document has no authoring path in the product**: an agent's write is refused
   (`spec_service.py:159-162`) and the operator's `PUT …/content` (`spec.py:470-532`) has no client.
   This is why merge is a decision, below.

### Decisions

**F217 — the drift branch basis** (moved here from D13). Options, with what the code says about each:

| | Option | What it breaks | What it releases |
|---|---|---|---|
| A | Keep the branch basis; state the asymmetry on the drift surface and in the spec | nothing | honesty only; agent evidence is never watched after merge, and the whole-tree flood stays |
| B | Switch to `main` once `reachable_from_main`, whole tree | floods — an agent commit's whole tree differs from `main` in every file anyone else merged | agent evidence watched, drowned |
| **C** | **Narrow the footprint to the files the evidence is about, then switch to `main` once reached** | evidence that names no file and changed nothing off `main` watches nothing (today it watches everything); tests relying on the whole tree are rewritten; one migration | agent evidence watched where the product is; one unrelated commit raises nothing |

**Recommended: C.** The docstring's objection to switching (*"drift would flip bases underneath an
open candidate"*) does not survive narrowing: `reachable_from_main` only moves to `True`
(`refresh_reachability`'s filter, `:1028`), an open candidate is skipped before any comparison
(`:1131`), and a resolution's fingerprint is `{path: {was, now}}` (`:1221`), which a clean merge
reproduces exactly on `main`.

**Sub-question raised in R1 — what does evidence that names no file watch?** Recommended: nothing,
listed as unwatched with the reason and the remedy (name a file or commit in the locator). The
alternative (the whole tree, as today) keeps the flood for exactly that evidence. No operator loses a
signal: nothing reaches drift today.

**Legacy footprints** (recorded before the change, whole tree): recommended not scanned, listed as
`recorded_before_watching`. Same reasoning.

**F129's scan cadence**: recommended manual (F129's own argument, and `spec.py:963-964`).

**F206's merge route — who authors a capability document?** Options: M1 leave merge API-only for now
(recommended); M2 a payload editor dialog (rejected: the operator hand-editing JSON inverts the
product's premise); M3 agents draft capability content that always lands as proposals, the merge
recorded as the operator's on accept (the likely eventual answer; changes *"capability documents are
written by the operator"* to *accepted by*, so it wants its own exploration).

**Smaller product calls, one per change:** a demotion in the app requires a reason (recommended
yes); proposal clean-up is W3 — de-duplicate and supersede at submission, plus an operator
withdraw (recommended over either alone).

The decisions interact in one place: F217's answer and the unwatched sub-question decide what the
second drift change's strip shows. Under A the strip also says agent evidence is watched only on its
branch; under C it does not need to.
