R1 -- explore and propose (2026-09-24)

What the code showed (HEAD 404c7d5)

cut_over (hub/hub/checkpoint_cutover.py:63-200) has one guard against a second handover. It refuses when predecessor.lifecycle == "archived" (:97-103), and its refusal ends "unarchive it first". The guard reads the lifecycle at :97 and writes it at :144 (archive), then commits at :145. Between the two it awaits archivable (:105). Nothing records that a checkpoint was handed over. Checkpoint (hub/hub/db/models.py:1668-1804) has no such column, and InboundQueueEntry has no checkpoint id. unarchive (hub/hub/conversations.py:479-482; route hub/hub/api/v1/agent_chat.py:623-635) is never refused and resets lifecycle to open. Two callers exist: the route (api/v1/checkpoints.py:370-404, refusal → 409 at :391-394) and the automatic trigger (checkpoint_trigger.py:319-336, refusal → cutover_refused on checkpoint_ready). take_checkpoint holds an in-process claim (_checkpoint_claims, checkpoints.py:27-28, 167-186), and nothing guards the cutover.

Each finding re-verified
  • F293 — still open. A throwaway test used the suite's own fixtures on its file-backed SQLite:

cut_over, then unarchive + commit, then cut_over again with the same checkpoint. It produced two handoff successors (conv-2997cf6e3357, conv-2ecad0277068). The shape is unchanged since filing. The only line drift: the guard is still at :97.

  • F294 — still open. Two sessions loaded the conversation and checkpoint, then waited on an

asyncio.Barrier(2), then ran cut_over concurrently. Both returned successors (conv-9433b9e6954f, conv-e632a122f613). Without the barrier the second read came after the first commit and was refused. So the barrier is the deterministic test, and task 1.2 keeps it.

  • A shape R1 adds to F293, not a new finding. The app's own Handoff (writeCheckpoint,

hub/ui/src/store/checkpointOperationStore.ts:37-75) always takes a new checkpoint and then cuts it over. An operator who unarchives and presses Handoff therefore forks the line with a different checkpoint. A per-checkpoint column alone would not close that. This drives D2.

  • git log -S "cut_over_to_conversation_id" finds nothing, so the column has never existed.

Operator's :8000 database, read with mode=ro: head 0105, 16 checkpoints, 0 cutover deliveries, 0 handoff conversations. The trial database has 0 checkpoints.

What each route returns when what it calls raises

The compare-and-set miss and the IntegrityError are converted to CutoverRefusedError inside cut_over, after a rollback. So the route still answers 409, and the trigger still reports cutover_refused. The rollback is safe because neither caller has anything pending (route :378-384 only reads; trigger generate_checkpoint commits at checkpoint_generation.py:664). Task 1.8 pins that the trigger's checkpoint survives the rollback. A lock-timeout OperationalError stays a 500, as today; R1 does not widen it.
