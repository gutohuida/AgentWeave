The one answer both decisions rest on

D1 and D11 are the same question asked of two tables. R1's recommended answer, used by every change below:

ThingRowMeaningConcludes when
Firingnone of its own: the JobRun rows sharing (job_id, fired_at)the moment a job fired—
Dispatchone JobRunone agent's share of one firing, correlated to its run through its own conversationits input has concluded: no job input still queued on the conversation and no run on it running
Attemptone Runone process execution of one turnthe process ends; its row is the record of how that attempt ended

Why dispatch for JobRun, and not firing or attempt, from the code:

  • Not a firing. Six readers correlate a JobRun to exactly one conversation:

scheduler.py:2282 (finalize), run_reconciliation.py:236-268, api/v1/jobs.py:454-466 (firing_active), checkpoints.py:150, checkpoint_handover.py:113, api/v1/agent_chat.py:373. A wide flow firing has one conversation per agent (_stage_selection, scheduler.py:3712-3716, and its docstring at :3645-3651, which argues exactly this). A firing row would need a child table.

  • Not an attempt. Run already is the attempt. One JobRun per Run duplicates it and inflates

every counter that reads rows (F123's shape 2 names this cost; it is F121).

  • A dispatch is what the rows already are for every firing that dispatched. A skipped firing

writes one row that dispatched nothing; that is consistent (a firing with zero dispatches records itself once).

How D1 shapes D11. The table at the top is one statement: the attempt's row says how the attempt ended (F273, F291: read it from the run facts, never only from the output stream); the dispatch's row says how the work ended (F123, F147); the firing is counted once (F121); run_id names only an attempt (F149); a running attempt row that no process owns is a dead attempt, and Stop concludes it the way startup would (F168). F42 is about the attempt's binding and needs no change. F235 is the one item unrelated to D1 and is carried here only because D11 grouped it.
