### Decisions

**D3 — what an unbound self-registered agent is told, and whether `contact_mode="watchdog-spawn"` goes.**
Options: (1) delete self-registration; (2) keep it and key a third launchability sentence on
`contact_mode`; (3) drop only the `self_registered` guard. The operator already chose (1) on
2026-08-29, but the verdict lives only inside FINDINGS F111 — `DECISIONS.md` has no entry (`grep`
finds the route only in a route inventory at `:326`). The measurements settle it: no client calls the
route, no real row is self-registered, and none of the three `contact_mode` values is true of an agent
the Hub spawns (F3's own gate). **Recommended: (1) — delete the route and drop `contact_mode`,
`self_registered`, `mcp_endpoint`, `spawn_cmd`.** There is then no third sentence to write: every agent
with no runner is told *no runner is bound*. F3 asked the design question first — *how does a test make
an agent when no runner CLI is on PATH?* — and the answer is a shared `add_agent` fixture that inserts
the row directly, a pattern two test files already use locally. The fixture cost is 31 call sites in
19 files, besides `test_agents_self_registered.py` (24 sites), which is deleted with the route (F3's
own count on 2026-09-06 was 42 sites in 16 files; the suite has moved since).

**S9 / F378 — where `request_agent` templates come from.** Options: (1) a template is an existing open
agent of the project; (2) a template registry with its own table and screen; (3) delete the tool.
**Recommended: (1).** The operator approves a kind of agent by creating one; the new agent takes its
runner, charter and runner config, and **not** its grants (`can_accept_evidence`,
`can_read_checkpoints`, `can_recall`) — an agent must not mint a second holder of authority the
operator gives one agent at a time. It serves the one observed use (the Architect asking for a second
developer, 2026-09-17), and the agent it creates can actually run. `default_permission_mode` is left
un-copied (least authority); R2 is asked to argue it.

**D8 — who the actor is when a loop or flow moves a task.** Options: (1) keep the actor `operator`
(the authority the gate needs) and record a new **cause**, `origin="job"`, with a `job_id`; (2) a third
actor kind; (3) relabel in the UI. `task-lifecycle-governance` settles most of it: *"There SHALL NOT be
a third actor kind for the system"* forbids (2), and *"The recorded cause SHALL distinguish a
transition an actor asked for from one the system made on that actor's behalf"* is **violated today**
by the flow's staging — so (1) is not a new rule but the shipped one, met. (3) is impossible: the row
carries nothing to tell the two apart. **Recommended: (1).** No guard moves (`is_allowed` reads the
kind; the separation guards read `actor.agent`, `None` either way); the 38 existing operator rows are
not rewritten, because history is append-only.
