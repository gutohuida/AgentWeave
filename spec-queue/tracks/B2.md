### The one answer both decisions rest on

D1 and D11 are the same question asked of two tables. R1's recommended answer, used by every change
below:

| Thing | Row | Meaning | Concludes when |
|---|---|---|---|
| **Firing** | none of its own: the `JobRun` rows sharing `(job_id, fired_at)` | the moment a job fired | — |
| **Dispatch** | one `JobRun` | one agent's share of one firing, correlated to its run through **its own conversation** | its input has concluded: no job input still queued on the conversation and no run on it running |
| **Attempt** | one `Run` | one process execution of one turn | the process ends; its row is the record of how that attempt ended |

Why *dispatch* for `JobRun`, and not *firing* or *attempt*, from the code:

- **Not a firing.** Six readers correlate a `JobRun` to exactly one conversation:
  `scheduler.py:2282` (finalize), `run_reconciliation.py:236-268`, `api/v1/jobs.py:454-466`
  (`firing_active`), `checkpoints.py:150`, `checkpoint_handover.py:113`, `api/v1/agent_chat.py:373`.
  A wide flow firing has one conversation per agent (`_stage_selection`, `scheduler.py:3712-3716`,
  and its docstring at `:3645-3651`, which argues exactly this). A firing row would need a child table.
- **Not an attempt.** `Run` already is the attempt. One `JobRun` per `Run` duplicates it and inflates
  every counter that reads rows (F123's shape 2 names this cost; it is F121).
- **A dispatch is what the rows already are** for every firing that dispatched. A skipped firing
  writes one row that dispatched nothing; that is consistent (a firing with zero dispatches records
  itself once).

### D1 — What is a `JobRun` row? Is `run_id` in job events renamed?

| Option | What it would break | What it would release |
|---|---|---|
| **a. A firing** | the six conversation correlations above; needs a child table per agent | F121 trivially |
| **b. A dispatch** *(recommended)* | nothing read today; `run_count` stops moving per extra agent | F121 (a counter fix), F123 + F147 (a conclusion rule), F149 (a rename with a meaning) |
| **c. An attempt** | every counter and the last-ten view (one row per retry); duplicates `Run` | F123 as "history shows each try" |

**Rename:** rename to `job_run_id`, outright, no dual emission, stored events not rewritten
*(recommended)*. Alternatives: emit both for a period (protects readers that do not exist); keep and
document (leaves the timeline reader wrong); a `jobrun-` id prefix (complementary, changes nothing a
reader keys on). No reader of the key exists (`useSSE.ts:524-535` reads `id`; `eventSummary.ts:57-65`
reads names and reasons; no Hub test pins it).
