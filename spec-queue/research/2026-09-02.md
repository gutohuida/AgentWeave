## The evidence

### 1. Make the model catalog follow its providers

**What exists elsewhere, dated.** Claude Code **v2.1.257** (published 2026-09-01T17:53:52Z,
`gh api repos/anthropics/claude-code/releases/tags/v2.1.257`) opens its changelog with:

> Added Claude Fable 5.1 (`claude-fable-5-1`), now the default Fable model — 1M context, $10/$50
> per Mtok with $0.25/Mtok cache reads

Anthropic's announcement the same day
(<https://www.anthropic.com/claude-fable-and-mythos-5-1>, read 2026-09-02) adds that Fable 5.1 and
Mythos 5.1 are the same model under different safeguards, that Fable 5.1 is generally available,
and that it costs "an estimated 25% less than Fable 5 for typical workloads… For highly agentic
work, the savings will often be much larger — up to approximately 45%," through reduced cache-read
pricing. An operator running long unattended loops is exactly the "highly agentic" case.

**What AgentWeave does today.** `hub/hub/model_catalog.py` is a hardcoded `CATALOG` dict. The
Claude provider declares four models — `claude-opus-5`, `claude-sonnet-5` (default),
`claude-haiku-4-5-20251001`, `claude-fable-5` (`model_catalog.py:152-172`) — with windows the
docstring says were "live-verified… on 2026-08-09." The Codex provider declares six
(`gpt-5.6-sol` with `default=True`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`,
`gpt-5.4-mini`).

**The gap, measured this morning rather than asserted.** I read the file the catalog's own
docstring cites as its Codex source — `~/.codex/models_cache.json`, `fetched_at`
2026-08-29T10:33:58Z, `client_version` 0.146.0. It holds six entries, four with
`"visibility": "list"`:

| in the CLI's own catalog (`visibility: list`) | in AgentWeave's `CATALOG` |
|---|---|
| `gpt-5.6-terra` | ✓ |
| `gpt-5.6-luna` | ✓ |
| `gpt-5.5` | ✓ |
| `gpt-5.4-mini` | ✓ |
| — | **`gpt-5.6-sol`, declared `default=True`** |
| — | `gpt-5.4` |
| (`gpt-reserve`, `codex-auto-review` — both `hide`) | correctly absent |

**AgentWeave's default Codex model is not in Codex's catalog.** The effort control is fine — I
recomputed the intersection over the listed models and it is still `low, medium, high, xhigh`,
exactly what `model_catalog.py` declares, so the docstring's *reasoning* survives; only its
snapshot has moved. (One detail in that docstring is now stale: it says `ultra` is declared by
"three of six," and today it is one of four listed.)

On the Claude side the same staleness has a harder consequence, because of what shipped last
night. `_reject_undeclared_model` (`hub/hub/api/v1/runners.py:24-45`) refuses any undeclared model
**on create**, and on update refuses any move to a *different* undeclared model; it returns early
only when the submitted model equals the one already stored. Its docstring names the very case:

> an already-stored, unrecognised model (from before this catalog existed, **or a future CLI
> release**) is left alone

That is an exit, not an entrance. The code anticipated a future CLI release and built the path that
lets an existing runner keep a model the catalog has never heard of — F220's retirement note
confirms it works, amber `Unrecognised` chip and all — while leaving no path to *set* one. Before
last night an operator at least had a free-text field to be refused by; after
`runner-model-is-chosen-from-the-catalog` the screen is a `<Select>` fed by `GET /model-catalog`,
so `claude-fable-5-1` is not offered and, if it were typed through the API, would be a 400. The
only way in is writing the row directly, which is what F220's own reproduction had to do because
"no API path can produce one."

There is a second, cheaper route the codebase already half-holds. `claude --help` on the installed
2.1.238 documents `--model` as taking "an alias for **the latest model** (e.g. 'fable', 'opus', or
'sonnet') or a model's full name (e.g. 'claude-fable-5')." The catalog *declares* those aliases
(`aliases=("fable",)`) and `GET /model-catalog` serves them — but `ProviderDescriptor.model()`
matches `m.id` only (`model_catalog.py:113-117`), which is F221. F221 was filed severity D and
deliberately left open, with the reasoning that the picker "submits ids, after which this is
unreachable from the screen and API-only." Today inverts that reasoning: submitting ids is
precisely what stops the Hub from ever following a model release, and the alias — the thing
dismissed as unreachable — is the one spelling that would have made `fable` mean 5.1 the moment the
CLI updated. That is a genuine reversal, not a restatement, and it is worth putting in front of
whoever closes F221.

**What a change would touch.** Three separable pieces, and the first is worth doing alone:

1. **Codex: read, don't copy.** The docstring already says these entries were "read directly from"
   `~/.codex/models_cache.json`. Reading it at Hub start (or on catalog request, cached against its
   `etag`) rather than at authoring time closes the Codex half completely and deletes a maintenance
   obligation instead of adding one. `model_catalog.py` plus a fallback for a machine with no Codex
   installed.
2. **Claude: add the two descriptors and decide the alias question.** `claude-fable-5-1` at
   1,000,000 — a window the vendor's own release note states, which satisfies the catalog's
   "never authored from memory" rule with a citation. Then either resolve aliases in `model()`
   (closing F221 and letting `fable` track the latest) or state in the spec that AgentWeave pins
   dated ids on purpose.
3. **A way in for an unknown model.** Whatever else is decided, `_reject_undeclared_model` should
   have an entrance to match its exit — an operator who names a model their CLI accepts should be
   able to save it and carry the `Unrecognised` chip, rather than being told it does not exist.

**What would make it a bad idea.** Piece 1 makes the Hub's catalog depend on a file another CLI
owns, whose path and shape are undocumented and could move; a wrong read is worse than a stale
copy, because a stale copy at least fails loudly at spawn. Piece 3 partly re-opens what the
`runner-registry` spec deliberately closed — "runner management offers catalog models, not
free-typed text" — and someone should say plainly whether the catalog is a *safety* mechanism
(refuse what will fail) or a *convenience* one (offer what works). If it is safety, then refusing
`claude-fable-5-1` is correct behaviour on a Hub whose bundled knowledge ends on 2026-08-09, and
the real item is only piece 2 plus a recurring bump. I think it is convenience — the amber
`Unrecognised` chip is the product already saying so — but that is the decision the item turns on,
and it should be made before any code moves.

### 2. Let a read-only verifier produce evidence

**What exists elsewhere.** Two independent sources landed on the same structure within two days.

**Google Antigravity `/teamwork-preview`** (<https://antigravity.google/docs/teamwork/>, read
2026-09-02; Antigravity 2.0 v2.11.0, CLI v1.1.22, SDK v0.1.15) — yesterday's largest named gap, now
read. It runs a named role tier: **Sentinel** (coordinator), **Project Orchestrator** (breaks the
brief into milestones, delegates, and "hands off to a fresh successor between milestones to prevent
context degradation"), **Explorers** ("read-only research agents… without modifying any source
files"), and **Workers**. Then four verification roles, of which one matters here:

> **Auditor**: Validates work against the selected integrity mode and **checks test evidence
> against real command output, ensuring tests genuinely passed rather than being mocked or
> skipped.**

alongside **Critic** (independent code review), **Challenger** (adversarial tests, edge cases,
failure-path probes) and **Success Auditor** (final end-to-end pass before the result is shown to
the human). It also carries **integrity modes** — `development` / `demo` / `benchmark`, chosen
during the scoping interview and *recorded in the prompt artifact* — which dial how much the
Auditor will tolerate, and **Exclusive File Ownership**, where the orchestrator assigns files to
Workers so two never edit one file.

**Harness-of-Harness** (arXiv 2609.01481, submitted 2026-09-01,
<https://arxiv.org/abs/2609.01481>; repo <https://github.com/Flesymeb/HarnessOfHarness>, README
read 2026-09-02) is AgentWeave's own loop described by strangers: a framework that "operates on
existing coding-agent harnesses" and organises them into iterative planning–coding–testing loops,
with three stable roles across iterations —

> **Project Planner** — reads the public requirements and evidence from the previous iteration,
> then writes a prioritized development document. It does not modify the artifact.
> **Developer** — implements the current development document… while preserving functionality that
> has already been verified.
> **QA Tester** — executes and inspects the updated artifact against the requirements, **recording
> evidence for verified behavior and unresolved gaps. It remains read-only.**

The paper's numbers: average relative gain of 52.25% and maximum 82.86% over three iterations
against three harness–model pairs on GameCraft-Bench, FrontierSWE and ProgramBench, plus a
multi-day deployment of 70+ iterations. Their code ("HoH-lite") is announced but not yet released,
so the numbers are unreproducible today — treat them as a direction, not a benchmark.

**What AgentWeave does today, and it is closer than it looks.** AgentWeave has the harder half
right, and the module docstring says why better than I could: *"An agent's assertion is not
evidence. But that rule was originally aimed at the wrong half: a stored test artifact is a fact,
and it is the claim about what it proves that needs judging. So producing evidence is open to
anyone, and accepting it is the controlled act"* (`hub/hub/requirement_evidence.py:1-27`). Agent
evidence enters `awaiting` (`requirement_evidence.py:169`); an agent may not accept evidence it
produced, on *agent* identity rather than run identity; evidence is pinned to the requirement's
digest, which is the entire staleness mechanism; and duplicates are refused with a real
explanation.

The reviewer is placed correctly too. `review_turn.py` gives it a **detached checkout of the commit
the evidence names**, with its own working checkout outside that boundary, and the briefing at
`hub/hub/api/v1/agents.py:1155-1163` already says the right thing:

> Read it, search it, and **run its test suite**. Verifying the evidence yourself is the reason you
> were given a checkout rather than a diff.
> Do not fix what you find. Report it… a reviewer that edits the work has reviewed its own work.

So AgentWeave is not missing the Auditor's *instruction*. It has it, and `read_only` agents already
exist as a config concept (`worktrees.py:217`).

**The gap.** Evidence in AgentWeave can only ever *originate* from the party doing the work. The
review turn is selected by the evidence — `commit_for_task_review` picks the commit the evidence
names — so a task whose implementer recorded nothing cannot be reviewed at all. That is not a
theoretical concern; it is three findings already in the queue, filed as symptoms without a common
cause named:

- **F56 (A)** — one review target with no evidence permanently wedges an agent's entire inbound
  queue, silently
- **F65 (C)** — a review briefing refused for having no evidence stays queued, and blocks archiving
  its agent
- **F161 (D)** — a loop that declares its work needs no evidence still stalls asking for evidence

Both outside sources remove that whole class structurally rather than repairing it: if the
read-only verifier is the one who *executes and records*, then "the implementer recorded nothing"
stops being a terminal state. Second, and separately: nothing in an `EvidenceReview` distinguishes
a reviewer that ran the suite from one that read the diff. The instruction is prose; the record has
a `reason` field and no observation. Antigravity's Auditor is backed by mechanism, AgentWeave's is
backed by a sentence — which is the same shape as yesterday's candidate 1 and should not be sold
twice.

**What a change would touch.** The narrow version, and the one I would argue for: allow a review
turn to be staffed for a task with **no** evidence, with the reviewer instructed to produce it —
its execution becomes a `kind="test_result"` record, which then awaits the *implementer's* or the
operator's acceptance under the existing distinctness rule, which already works in that direction.
That is `review_turn.commit_for_task_review` (choose a commit when no evidence names one — the task
branch head), the review briefing, and the three findings above closing together. It does not touch
the acceptance model, the digest pin, or the footprint machinery, all of which are already right.

**What would make it a bad idea.** Two real objections. First, a reviewer that produces evidence
and an implementer that accepts it inverts the trust direction — the careless-implementer failure
the current design is built against reappears on the other side, and the distinctness rule alone
may not carry it. Second, choosing a commit when no evidence names one is exactly the guess
`task_integration.py:16` warns about (*"a wrong guess in a read-only report costs an `unknown`. A
wrong guess here writes commits"*); the reviewer would be verifying a commit nobody asserted, and
saying which commit that is, is the whole difficulty F71 already bled over. This is an M/L item
that should be explored before it is specified, not proposed straight into the queue. The
integrity-mode idea — a verification-depth dial recorded on the change and enforced at acceptance —
is genuinely novel here and has no AgentWeave analogue, but it is a product decision for the
operator, not a defect.

### 3. Record the runner CLI version — the number yesterday was missing

Yesterday ranked this second and argued for the cheap half only (record it and show it in
diagnostics; do not gate on it). Nothing about the argument has changed. One thing has: it now has
a measurement, and the measurement is worse than the argument assumed.

- Installed on this machine, read today: `claude --version` → **2.1.238 (Claude Code)**.
- Latest release: **v2.1.258**, published 2026-09-01T22:33:20Z.

The installed CLI therefore predates **v2.1.251** (2026-08-28T18:19:32Z), which fixed four
permission-boundary defects — including file tools "following a symlink swapped inside the working
directory **after the permission check**, which could read or write outside the approved location."
Yesterday's item said the Hub "records no version anywhere" and left the risk hypothetical. It is
not hypothetical on this machine: the CLI that actually enforces file access here is thirteen
releases before that fix, and no run record, no accepted evidence and no diagnostic anywhere in
AgentWeave says so.

Two smaller things from v2.1.257 (2026-09-01) sharpen the same point and are new since yesterday.
It added a **Containment Escape** rule to auto mode "so cloud metadata-credential fetches, egress
evasion, and cross-tenant reach are no longer auto-approved unless your environment marks them
expected" — a *semantic* class of denial, where AgentWeave's `_decide` (`mcp_server.py:901-948`) is
purely path containment, soundly implemented but categorical only about *where*. And it added
`permissions.blockReadsOutsideWorkingDirectories` with a one-time prompt before the first outside
read. Both are the runner CLI growing containment AgentWeave neither knows about nor can require.

**What a change would touch.** Unchanged from yesterday: capture `<cli> --version` once per run or
per Hub start, store it on the run record, surface it in diagnostics. `runner_commands.py`, the run
model, one migration, the diagnostics surface. Composes with F115's recording work rather than
competing with it.

**What would make it a bad idea.** Also unchanged, and worth repeating because the new number makes
it tempting to over-reach: a *minimum* version check is a support burden on a single-operator
product where `claude` is whatever resolves on the PATH, and it would today fail the operator's own
machine. Record it. Show it. Do not gate on it.
