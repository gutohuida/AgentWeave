## The evidence

### 1 — the default evidence kind is the one the agent can always make pass

**What exists elsewhere, dated.** Dan Luu, **2026-09-08**,
<https://danluu.com/agentic-testing/>. Method, in his words: implementations *"in Rust"*, *"26 prompt
conditions tested"* plus four skills, *"average of 80 runs from each condition and effort"*, codex
with GPT‑5.6 Sol at medium and xhigh, scored on *"the fraction of runs that passed 100% of the
(hidden) tests"*. The conditions range across formal methods (Verus, Lean 4, TLA+, Kani, Alloy,
Creusot, ACL2, Spin, SMT), property-based testing (QuickCheck, proptest, Hegel), TDD, fuzzing,
mutation testing, differential testing, audit, and a control that gives no instructions at all.

Four results matter here, and they are not the headline.

> across all conditions, agents were able to get the tests they wrote to pass on xhigh and max (not
> shown, but max had slightly better correctness than xhigh at substantially better cost). Getting
> their own tests to pass more iteratively tended to get agents to write more incorrect tests that
> would enforce incorrect behavior.

That is the first sentence to read against AgentWeave. A passing self-written suite is not weak
evidence; on the effort tiers AgentWeave's runners actually use it is **near-certain**, and the
iteration that produces it is *anticorrelated* with correctness.

Second, test count is not coverage:

> Explicitly asking agents to use the built-in test framework resulted in more tests (double normal
> on medium, 25% more on xhigh), but this didn't result in better correctness. When agents got
> things wrong, it was often because they didn't test significant behavior or implemented incorrect
> test behavior. Adding more tests didn't materially increase coverage of risky behaviors or reduce
> the fraction of runs with tests that encoded incorrect behavior.

Third, the failure has a shape and the shape is self-consistency. In the four-Huffman-stream case,
agents *"were more likely to write tests that don't cover hard cases (e.g., making all four streams
identical and then also making them trivial)"*, and in the reversal case a run *"identified this as
risky, did independent derivations and an audit, but still failed. It had a relevant test, but the
input was palindromic, so reversing the order gave the same re[sult]."* A palindromic test passes
under the bug it was written to catch. Nothing about the artifact says so.

Fourth, and this is the part that makes it actionable rather than merely depressing: the author's own
winning instruction asked for *"independently re-derive the result without context on production code
and compare (fresh context, do not re-use helper functions)"* — and he reports **"It didn't really do
the fresh context thing almost ever."** Independence that is asked for in prose does not happen.

**What AgentWeave does today.** The spec is better than most and stops one step short.
`requirement-traceability/spec.md:140`:

> **An agent's assertion SHALL NOT by itself constitute evidence.** A run reporting that it verified
> something produces a record awaiting review, not a verified requirement… What distinguishes them is
> that the artifact is a fact and the claim about what it proves is not — so producing evidence is
> open, and **accepting** it is the controlled act.

And `:155`: *"**An agent SHALL NOT accept evidence it produced.** Distinctness is on agent identity,
not run identity."* Both correct. Both about the **claim** and the **acceptance**. Neither is about
the artifact's own provenance.

The artifact is, by default, a test run. `record_evidence`'s signature is
`kind: str = "test_result"` (`hub/hub/mcp_server.py:1290-1296`), and `EVIDENCE_KINDS` puts
`"test_result"` first (`hub/hub/db/models.py:2338-2345`). Its docstring already tells the agent to
read what comes back:

> Returns the evidence `id`, its `identifier`, its `review_state` and the `footprint` captured for it
> — the branch and commit your evidence has been attached to. Read it. If its
> `outside_workspace_writes` is a non-empty list, your turn wrote into a directory that footprint
> does not describe…

So there is already a precedent in this exact return value for *"here is an independent fact about
your evidence that changes how much it is worth"* — `outside_workspace_writes`, added because a
footprint that silently omits part of the run's work is a lie by omission. Self-authored tests are
the same category of fact, about the other half of the artifact.

**The gap.** Nothing in the Hub compares the tests an evidence run executed against the paths that
run changed. Nothing has to be inferred to close it: `EvidenceFootprint.entries` is documented as
*"{path: blob id or content hash}. The fingerprint a later change is compared against."*
(`hub/hub/db/models.py:2483-2484`). The test files are in there whenever the producing run wrote
them. The question *"does this footprint contain the tests this evidence names?"* is a set
intersection over data already on the row.

**What a change would touch.** One computed field on the evidence read model, surfaced in
`list_evidence` and on the operator's evidence view, and one sentence in
`requirement-traceability`. It should follow the precedent the same spec already sets at `:227`:

> Integration SHALL NOT be a coverage state. The precedence ranks how good the evidence is;
> integration is an independent fact about the same evidence, and ranking them together would force a
> single order on two things that vary independently.

Self-authorship is the third such fact and belongs beside `reachable_from_main`, not inside the
six-state precedence at `:210`. That keeps the change small and keeps it from re-opening coverage.

**What would make it a bad idea.** Three things, and the first is serious.

- **In a repository where the author writes the tests, this fact is constant.** If every evidence row
  reports "self-authored", the field is noise and the operator learns to ignore it — the exact
  failure mode yesterday's §3 candidate ran into from the other direction. The honest version of this
  item is therefore *report it*, not *refuse it*, and the thing worth showing is the **exception**: a
  `test_result` whose tests are **not** in its own footprint is the rare, high-value row.
- **A footprint's `entries` may be empty or `kind="paths"`** (`models.py:2480-2482`), so the fact is
  three-valued — self-authored, independently authored, unknown — and a two-valued rendering would
  fabricate the third.
- **It measures provenance, not quality.** A palindromic test written by a second agent is still a
  palindromic test. Dan Luu's own data says so: only *"42 used an independent agent, but these runs
  actually scored worse"* on the Audit condition. This item makes a fact visible; it does not claim
  the fact predicts correctness, and the spec text must not claim it either.

### 2 — the run inherits the operator's environment minus five names

**What exists elsewhere, dated.** `trailofbits/coop` — *"Isolated VM environments for running Claude
Code and Codex"*, Rust, Apache‑2.0, 153 stars, 317 commits
(<https://github.com/trailofbits/coop>), on Hacker News **2026-09-07** at 58 points. Its
`docs/trust-model.md` (21,959 bytes, read 2026-09-08) is the artifact, not the tool. It opens by
declaring itself *"the engineering-facing trust model… the authoritative list of trust boundaries,
taint sources, and the invariants that hold the isolation together"*, and names its zones in a table:
host + `config.toml` **trusted**, the coop process **trusted**, **the guest VM untrusted** —
*"Agent-controlled. Anything it emits… is a taint source once it crosses back to the host."*

Its secrets section is the comparable part:

> **Never on argv.** Secrets ride SSH `SendEnv` (env channel) or process env… or are piped via
> **stdin**… Never build a command line with the secret as an argument — it is visible in
> `ps`/`/proc`.

> **`GITHUB_TOKEN` defaults to Off.** It is only forwarded with an explicit `github = auto|env|pat`
> opt-in… A change that forwards it by default, or makes it persistent where it wasn't, **is a
> finding**.

> **Proxy mode keeps the model API keys out of the guest entirely** (issue #411, opt-in `[proxy]`).
> When enabled in remote model mode, `ANTHROPIC_API_KEY` (Claude) and/or `OPENAI_API_KEY` (Codex)
> are **not** forwarded…; the host-side `coop-proxy` holds the real credential and the guest gets
> only a per-instance capability token… In proxy mode Codex's `~/.codex/auth.json` is also **not**
> staged onto the guest disk.

**What AgentWeave does today, and it is closer than it looks.** `agent_trigger.py:1067-1071` mints
the run credential and sets the identity variables; the comment at `:1116` is already the right
principle stated out loud: *"A parent service environment may contain operator credentials. Never
pass them through to a spawned run: AW_RUN_TOKEN is the run's complete authority."* What follows is a
**denylist of five**:

```python
env = dict(env) if env is not None else dict(os.environ)   # agent_trigger.py:1067
...
env.pop("HUB_API_KEY", None)          # :1117
env.pop("HUB_PROJECT_ID", None)       # :1118
env.pop("DATABASE_URL", None)         # :1127
env.pop("AW_BOOTSTRAP_API_KEY", None) # :1128
env.pop("AW_TICKET_SECRET", None)     # :1129
```

Each has a reasoned comment, and the `DATABASE_URL` one is a genuinely good catch — *"`pytest
hub/tests/`, the command this repository's own instructions tell an agent to run, has fixtures that
drop every table in whatever DATABASE_URL names."* That is a denylist written by someone who found
each entry the hard way, which is exactly the property that makes a denylist untrustworthy: it lists
what has already gone wrong.

Then `launchability.py:152-158` resolves the provider key **into** the spawned environment:

```python
proc_env = dict(os.environ)
proc_env.update(env_vars)
api_key_var = env_vars.get("ANTHROPIC_API_KEY_VAR")
if api_key_var:
    resolved = os.environ.get(api_key_var, "")
    if resolved:
        proc_env["ANTHROPIC_API_KEY"] = resolved
```

For a `claude_proxy` agent that is required and intended — `runtime-diagnostics/spec.md:37-46`
refuses to launch without it. For every other agent the key is not *added*, but it is not *removed*
either: the base is `dict(os.environ)`, so whatever the operator exported into the shell that started
the Hub — `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, an `AWS_SECRET_ACCESS_KEY`, an
`op` session — is in the process environment of every agent AgentWeave spawns.

**The gap, stated precisely, because the loose version is wrong.** The loose version is "an agent can
read the operator's secrets", and against a `yolo` run that is uninteresting: a run with
`--dangerously-bypass-approvals-and-sandbox` (`runner_commands.py:325`) can read
`~/.claude/.credentials.json` and the key is reachable whatever the environment says. The sharp
version is about the posture that promises otherwise. `agent-run-sandboxing/spec.md` has **fifteen**
requirements; `:42` is *"The default posture lets an agent work inside its own workspace"*, `:100` is
*"A posture exists in which the workspace boundary is enforced per tool call"*, `:361` is *"A file
tool writing outside the run's workspace is recorded, in every posture"*, and `:491` is *"The product
states which postures confine a run and which do not."* Every one of those confinements is
**filesystem-shaped**. A run confined to its workspace per tool call still has the operator's
provider credential in `os.environ` and an unbounded network, and the product's statement of what a
posture confines does not mention either.

That is the measurement worth writing down: **across all 43 shipped spec files, `egress`, `network
access`, `outbound network` and `firewall` appear zero times.** The only occurrences of `proxy` are
`runtime-diagnostics`' LLM-provider proxy credential checks (`:37-55`) and one readiness-check
mention (`:19`). AgentWeave has a carefully specified filesystem boundary and no specified network
boundary at all.

**What a change would touch.** Two separable pieces, and only the first is small:

- **Invert the list.** Replace the five `env.pop` calls with a pass-through allowlist plus the
  agent's own declared `env_vars`, so a variable reaches a run because someone named it, not because
  nobody thought to remove it. `AW_RUN_TOKEN` is already the run's complete authority by the
  comment's own words; this makes the code say what the comment says. Touches
  `agent_trigger.py:1116-1129` and `launchability.py:137-190`, and needs a test that starts the Hub
  with a junk `OPENAI_API_KEY` in its environment and asserts a non-proxy run cannot see it.
- **Say what a posture does not confine.** One requirement under `agent-run-sandboxing` stating that
  the postures bound filesystem writes and neither the process environment nor network egress, so an
  operator reading `:491` is not misled by omission. This is documentation of a limit, not a new
  control, and it is the honest half of the change.

**What would make it a bad idea.** An allowlist that is too tight breaks every runner that needs an
inherited variable nobody enumerated — `PATH`, `HOME`, `SystemRoot`, `NODE_OPTIONS`, a corporate
`HTTPS_PROXY`, whatever `claude` reads for its OAuth state — and the failure mode is *every agent
stops launching*, discovered at 23:05 in an unattended window. `launchability.py:145-147` already
records that `None` means *"inherit the Hub's own environment unchanged"*, which several call paths
depend on. This change is small in diff and large in blast radius, and it should not be built without
a launch test per runner. The second piece — writing down what a posture does not confine — carries
none of that risk and is worth doing on its own.

### 3 — the bearer credential follows a redirect off-origin

**What exists elsewhere, dated.** `modelcontextprotocol/python-sdk` **v2.2.0**, 2026-09-07T15:53:57Z
(<https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.2.0>), first item under
*Behaviour changes*:

> **HTTP client redirects are only followed within the endpoint's origin** (#3397)
> - `Client("https://...")`, `streamable_http_client` and `sse_client` follow a redirect only if it
>   stays on the same scheme, host and port (or upgrades `http` to `https` on the same host).
> - A redirect anywhere else is not followed: the call fails with `MCPError`…
> - The `follow_redirects` setting on an `httpx2.AsyncClient` you pass in is no longer used for MCP
>   requests… The OAuth providers apply the same rule to their own requests.

And **v1.30.0**, 2026-09-07T14:03:59Z, the maintenance line, ninety minutes earlier, with the same
text and its own PR (#3448 against #3397). The releases also add
`AuthSettings.validate_token_resource` — *"only accept tokens your `TokenVerifier` reports as issued
for this server"* — and reject authorization-server metadata whose `issuer` is not the server's own
origin. Three changes, one theme: **a credential is scoped to an origin and the transport must
enforce it.** A project that backports a behaviour change into a maintenance line the same afternoon
is telling you what it thinks the change is.

**What AgentWeave does today.** Two HTTP clients, both `urllib`, both with a bearer header, neither
constraining redirects.

```python
# hub/hub/mcp_server.py:158-171
base_url = os.environ.get("HUB_URL", "http://127.0.0.1:8000").rstrip("/")
token = _bound_token()
url = f"{base_url}/api/v1/agent-actions{path}"
...
request.add_header("Authorization", f"Bearer {token}")
with urllib.request.urlopen(request, timeout=10) as response:
```

```python
# src/agentweave/transport/http.py:186-191
req = urllib.request.Request(url, data=payload, method=method)
req.add_header("Authorization", f"Bearer {run_token or self.api_key}")
...
with urllib.request.urlopen(req, timeout=10) as resp:
```

**Measured on this machine, 2026-09-08, Python 3.11.9**, with a local 302 hop between two loopback
ports:

```
final url        : http://127.0.0.1:8899/stolen
hdr at first hop : Bearer aw_run_SECRET
hdr at OTHER host: Bearer aw_run_SECRET
```

`urllib.request.HTTPRedirectHandler` reconstructs the follow-up request from `req.headers`, and
`add_header` writes there, so the credential travels. This is not a guess about the standard library;
it is the observed behaviour of the two lines above.

**Where it actually matters, and where it does not.** Be exact, because two of the four call sites
are uninteresting.

- **`mcp_server.py` — low.** `agent_trigger.py:1105-1114` sets `HUB_URL` to
  `http://127.0.0.1:{observed_port}` with the comment *"The host is always loopback"*, unless the
  Hub's own environment carries an explicit `HUB_URL` (`:1090-1092`). For the default local
  deployment the only thing that can redirect the run credential is the Hub itself. For the
  containerised deployment where `HUB_URL` is set explicitly, it is whatever answers there.
- **`cli.py:287` and `:327` — low.** Operator token to `_hub_projects_url(port)`, loopback.
- **`transport/http.py` — this is the real one.** In operator mode `run_token` is empty and the
  header carries `self.api_key`, read from `.agentweave/transport.json` alongside a `url` documented
  in `transport/config.py:66` as `{"type": "http", "url": "https://...", "api_key": "iaf_live_xxx",
  "project_id": "proj-abc"}`. A **project API key** — a strictly higher privilege than a run
  credential, and `agent-capability-plane/spec.md:31-33` makes that separation a requirement
  (*"Credentials cannot cross privilege planes"*) — pointed at an arbitrary remote host, over a
  client that will hand it to whatever that host's 302 names. It also retries: the loop at
  `http.py:188-196` re-sends the same `req` on 5xx/429/`URLError`.
- **`cli.py:430`, the SHA256 sidecar** — no credential, but `urlretrieve`/`urlopen` with no origin
  constraint on a supply-chain fetch whose failure path is *"proceeding without verification"*
  (`cli.py:435-437`). Different bug, same file, worth one line in the finding.

**The gap.** `agent-capability-plane/spec.md:13-17` requires *"an unguessable credential for each
Hub-owned run"* whose digest only is stored and which *"MUST NOT be exposed in output"*. The
credential's confidentiality is a shipped requirement. Its transport does not enforce the one
constraint that gives confidentiality a boundary.

**What a change would touch.** A shared `_urlopen_same_origin` helper — a
`urllib.request.OpenerDirector` with a `HTTPRedirectHandler` subclass that raises unless
`(scheme, host, port)` match, allowing the `http`→`https` same-host upgrade the MCP SDK allows and
the trailing-slash relative redirect it kept working (#3450) — used at `mcp_server.py:171`,
`transport/http.py:191` and the CLI's token-bearing calls. Roughly thirty lines and one test that
stands up a redirector, as the measurement above did. Note that `mcp_server.py`'s imports are
*deliberately* stdlib-plus-`fastmcp` only (`:27-32`: *"this module is spawned as a standalone script
from an arbitrary working directory"*), so the helper must be duplicated there rather than imported
from the Hub package — the same restatement discipline that file already applies to its `Literal`
enums, and it should be commented as such or the next reader will "fix" it.

**What would make it a bad idea.** A deployment that *relies* on a redirect breaks — a reverse proxy
that 302s `http://hub.internal` to `https://hub.internal` keeps working under the same-host upgrade
rule, but one that redirects to a different hostname does not, and it would fail with a new error
class in an unattended window. The MCP SDK's own mitigation is the right one and should be copied
verbatim into the refusal message: *"If that other URL is the server you meant, use it as the
endpoint URL."* Second: this is a hardening item with no observed incident behind it, and DIRECTION's
arithmetic says the queue does not need another change. It should be **filed as a finding with the
measurement attached**, not specced — the measurement is the durable part, and it took ten minutes
to produce.

## Also seen, not proposed

- **Yesterday's §3 took a real hit, from today's source, and the correction matters more than the
  candidate did.** That item proposed counting what a reviewer has actually changed, on the argument
  that a reviewer who changes nothing is indistinguishable from one who changes everything. Dan Luu's
  Audit condition measures the base rate: *"152/160 agents actually did this and **151 agents claimed
  find an issue and then made a change as a result of the audit**"* — and *"On average, Audit did
  about as well as Default."* A rejection-and-change rate of 151/152 carries no information. The
  count yesterday's §3 wanted to add would have been ~99% for every reviewer in the roster. The
  discriminating measurement is not whether a reviewer changed something but whether the **outcome**
  differed, and AgentWeave has no held-out signal to compare against. §3 should be re-derived or
  dropped, not re-proposed; recording that here is the whole point of writing down what was rejected.
- **The rest of the Dan Luu dataset, and the one part that is about charters.** The Hegel skill —
  *"34k characters for the skill, which also loads a 45k Rust-specific reference, which ends up being
  more than 20k tokens"* — cost *"26% higher on medium and 41% on xhigh"* in tokens and 16–18% in
  dollars, *"loaded at the start of the run and… re-read on many subsequent actions"*, for **worse**
