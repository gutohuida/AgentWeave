## The evidence

### 1 — the review verdict does not say which tree it was produced against

**What exists elsewhere, dated.** GitHub Blog, **2026-09-04**, *"Project HydraFusion: Frontier quality
via multi-model orchestration"*,
<https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/>
(76 points on HN). A research preview, available on all Copilot plans through `/experimental` in
Copilot CLI. It runs one of three execution patterns per request, and the third is the one that
matters here:

> **Critique.** One model drafts a result, an independent read-only critic **from a different model
> family** reviews it (following the same review pattern as Rubber Duck), and the drafting model
> revises once.

and, among five stated operating principles:

> **Isolated review.** Run review steps in isolated, tool-less contexts, while solver steps use the
> shared workspace and normal permission-aware agent loop. This allows models to assess the work
> independently without modifying the repository.

The reported numbers, for calibration: on TerminalBench 2.1, +4.9 points of verified task quality at
67% lower estimated cost against Claude Opus 5; on CheckpointBench (their internal benchmark from
real Copilot sessions), −0.1 points at 65% lower cost; on DeepSWE, −1.5 points at 36% lower cost.
These are their own offline evaluations at a fixed medium reasoning level and should be read as
such — the load-bearing part for AgentWeave is the *architecture*, not the benchmark.

**What AgentWeave does today, and it is a considered design rather than an oversight.** Two places
in the source have already had this exact argument, and both landed on containment plus prose:

- `hub/hub/review_turn.py:9-18` — *"**Where.** The reviewer's workspace for the turn is a detached
  checkout of the commit the evidence names… This is **enforced**. **What.** The turn context states
  that this *is* a review, of which task, at which commit. This is **stated**."* Then, verbatim:

  > Design D4 is explicit that the first without the second fails: *"a reviewer that is not told it
  > is reviewing will helpfully fix the bug itself and report the work as verified."* The boundary
  > can only enforce where the agent may act, never what it thinks it is doing.

- `hub/hub/worktrees.py:580-595`, `ensure_review_checkout`, design D2: *"A branch invites a commit,
  and a reviewer is not an author… Detached also means git itself states the role: `git status` in
  here says 'HEAD detached at &lt;sha&gt;', so the environment tells the agent what it is doing rather
  than depending on the prompt to. An accidental commit is then orphaned and harmless."*

**The gap, and it is narrower and sharper than "the reviewer can write".** D2 makes a reviewer's edit
*harmless to the repository*. It does not make it harmless to the verdict. The reviewer gets a real
checkout precisely so it can run the suite — D6's stated justification is *"without this the reviewer
cannot run the suite, which is the entire justification for giving it a checkout rather than a
diff"* (`worktrees.py:614-616`). So the reachable sequence is: reviewer reads the commit, sees the
bug, fixes it in its own checkout, runs the suite, watches it go green, records a verdict against the
*commit*. The next review's `checkout --force` erases the edit. Nothing anywhere distinguishes *"the
suite passes at this commit"* from *"the suite passes at this commit plus my fix"*, and the evidence
row that carries the verdict (`RequirementEvidence.run_id`, `.task_id`, `.review_state`,
`models.py:2387-2393`) records who, when and what state, never against-what-tree.

That is not speculative. **F143 (B) is open** (`FINDINGS.md:10855`): a flow's review firing composes
the reviewer's briefing through `_compose_loop_briefing`, which has no review branch, so the reviewer
receives the *implementation* briefing verbatim — *"**Finish the task below and stop.** … Work the
task you have been given. Keep the edit minimal."* — while the turn context on the other channel says
the opposite. The agent's own transcript is quoted in the finding: *"**This is confusing.**"* It
resolved it correctly on Haiku, and F143 says plainly what that means: *"Nothing in the product
decided that — the same contradiction with a different model, or the same model on a longer briefing,
resolves the other way, and the other way is a reviewer that re-implements the work it was supposed
to check and then approves its own edit."*

Corroborating, on the model's side: arXiv **2609.04061**, *"When Models Edit Too Much: On the Fidelity
of Minimal Code Edits"*, 2026-09-03, <https://arxiv.org/abs/2609.04061>. Over-editing — rewriting
beyond what is required — is *"widespread even among strong models"*, and a **preservation
instruction** cut average excess Levenshtein distance from 0.195 to 0.131 and added cognitive
complexity by 26.6%. The instruction helps; the paper's whole point is that it does not eliminate the
behaviour, and *"these gains do not simply follow from a larger reasoning budget or larger models"*.
Telling a reviewer not to edit is a real intervention with a measured, partial effect. That is
exactly the size of guarantee AgentWeave currently has.

**What a change would touch.** The cheap version is one fact, not a refusal, and it is in the
product's own idiom — AgentWeave's answer to F87, to divergence, to `outside_workspace_writes` is
consistently *record and surface*, not *forbid*:

- `review_turn.py` returns the checkout path it provisioned; at verdict time, ask git whether that
  path is dirty against the commit under review.
- `RequirementEvidence` gains one nullable column for the answer, or the run does. `Run` already
  carries `workspace_dir` and `outside_workspace_writes` (`models.py:1074-1115`), so a
  writes-inside-the-review-checkout record is the same species as one that already exists.
- A spec delta on `requirement-traceability`'s *"Evidence names what produced it and what it was
  produced against"* (`spec.md:117`) — a requirement whose title already promises this and whose body
  currently means the author's footprint, not the reviewer's.
- The blunt version — passing `--disallowedTools Edit,Write,NotebookEdit` on a review dispatch, the
  way `restrict_spec_writes` does for a spec-authoring turn — is one argument at
  `agent_trigger.py:1052`, where the flag is gated on `bool(spec_document)` and so is **never** set
  for a review.

**What would make it a bad idea.** Four things, and the first is why the blunt version is listed
second:

- **F277 (C) already demolished the disallow-list approach from inside** (`FINDINGS.md:19409`):
  `restrict_spec_writes` omits `MultiEdit`, and more importantly *"`Bash` is not in the disallow list
  either, so a run under this flag can already write through `echo … > file`"*. F277's closing
  question is the one this candidate must answer, not dodge: *"whether a nudge that `Bash` walks
  straight through should be enumerating tools at all"*. Proposing the flag for reviews would import
  that hole rather than close it. The dirty-check does not care which tool made the write.
- D2 and D4 were argued and decided. A change that reverses them without engaging them is a
  regression dressed as a feature. The honest framing is *"D2 was right that the edit must not
  survive; it did not say the verdict should be silent about it"*.
- A reviewer running a build legitimately dirties the tree — `__pycache__`, `node_modules`,
  `.pytest_cache`. A naive `git status --porcelain` reports a false positive on every review that
  runs the suite, which is every review D6 was written for. This needs tracked-files-only, and
  `seed_repo_excludes` (`review_turn.py:207-213`) is already the place that thinks about this.
- HydraFusion's critic is *tool-less* because it reviews a **diff**, not a repository. AgentWeave
  deliberately gives the reviewer a checkout so it can execute. Those are different products making
  different trades, and the trade AgentWeave made is the better one for repository-level work. This
  candidate does not adopt theirs; it closes the one thing theirs gets for free and AgentWeave
  currently does not have at all.

### 2 — a token budget that cannot bound the turn that exceeds it

**What exists elsewhere.** The second of HydraFusion's five principles, same post, same date:

> **Bounded execution.** Give each leg explicit timeout and cancellation behavior to keep execution
> and cost within defined limits.

Corroborated from the opposite end of the market on 2026-09-05: Moadim (<https://moadim.io/>, §3
below) lists *"a watchdog on every run"* in its one-sentence description and *"kills hung runs, and
reaps the session when it's done"* as feature 01. Two products a day apart, one enterprise and one a
Show HN, both treating a per-run ceiling as table stakes rather than a refinement.

**What AgentWeave does today, measured in the code.** The budget is real, specified and shipped —
`usage-accounting/spec.md:83`, *"A project token budget pauses autonomy but not the operator"* — and
it is a **gate, evaluated once, before a turn starts**:

```python
budget = await project_budget_state(db, project_id)
if initiator == "autonomous" and budget["exhausted"]:
    return ScheduleResult(waiting_reason="token budget exhausted")
```
*(`hub/hub/turn_scheduler.py:310-312`)*

`project_budget_state` reads persisted rows, and usage is persisted **once, when the run ends**:
`record_turn_usage` writes exactly one `TurnUsage` per `run_id` and is called only from the
run-completion paths in `agent_trigger.py` (five sites, 1828–2837) and from `run_reconciliation.py:79`
after a crash. Its docstring: *"The caller owns the transaction so run completion and accounting can
commit together."*

**The fact that makes this cheap rather than architectural: the live number already exists.** The
Hub accumulates the turn's running total in memory as stream events arrive —

```python
if parsed.accounting is not None:
    accounting_sample = (
        parsed.accounting
        if accounting_sample is None
        else accounting_sample.merged(parsed.accounting)
    )
```
*(`hub/hub/api/v1/agent_trigger.py:2124-2129`; `AccountingSample.merged` at `runner_events.py:302`,
whose docstring is "Overlay newer reported fields while retaining independent earlier telemetry")*

That value is compared to nothing. A budget with 1,000 tokens remaining admits a turn that then
spends 900,000, and the exhaustion is discovered at the *next* scheduling decision, after the money
is gone. On a watched run an operator sees it and stops it. **AgentWeave's own night window is not a
watched run** — that is the same argument that put the unattended-`ask_user` item first on
2026-09-04, and it is the argument this product keeps rediscovering: controls designed for a watched
session are the ones that fail in the loop the product runs on itself.

**This is not F240, and the distinction is the point.** F240 (B) (`FINDINGS.md:16929`) drove exactly
this surface and found spend that reaches *no* total: `worker_invocations` joined to no aggregate, and
the conversation titler recording nothing at all — *"about $0.042 over 732 tokens"* with the budget
exhausted and *"spending is paused"* on screen. F240 also went out of its way to record the opposite
result for the path this candidate is about: *"the per-turn accounting itself is sound and was driven
end to end. One measured row per turn with the runner, the model and a real token total; the project
total is exactly the sum of the measured rows."* Correct, and orthogonal. F240 is *spend the budget
never sees*; this is *spend the budget sees, one turn too late*. Closing F240 does not close this,
and the two touch different files.

**What a change would touch.** `agent_trigger.py`'s stream loop already merges the sample; comparing
it against the project's remaining allowance on each merge is arithmetic on values in scope. The
run-termination path exists (stop is a shipped surface). A spec delta on `usage-accounting` —
probably a sibling to `spec.md:83` rather than an edit to it, because *"pauses autonomy"* and *"ends
a turn in flight"* are different promises and the existing scenarios are all about queueing.
`turn-outcome-visibility` needs a value for how such a run ended, since a turn killed on budget is
not a failure and must not read as one.

**What would make it a bad idea.** Three, and the first is a real design fork:

- **Killing a turn mid-flight destroys work.** An agent 90% through a change that is stopped at the
  token line leaves a dirty worktree and no evidence — arguably worse than overspending by 2×. The
  defensible version may be *refuse to start the next tool call* rather than *terminate*, or simply
  *record and alert* with no enforcement at all. Which of those is right is a decision, and it is the
  operator's, exactly as F240 concluded about its own half.
- **The telemetry is not continuous for every runner.** `AccountingSample` is runner-neutral by
  construction, but whether Codex's app-server transport emits usage per message or only at the end
  is unverified here and is load-bearing: on a runner that reports once, a mid-run check has nothing
  to check and the feature silently does nothing on half the roster. Measure this in one driven run
  before specifying, not after.
- A per-run ceiling that fires often becomes a second thing operators tune, and the product already
  has `token_budget`, hop budgets (F5), `MAX_WAITING_SECONDS`, and question timeouts. If the honest
  answer is that the project budget plus a visible live number is enough, the right outcome is a line
  in the spec saying the budget is a gate and not a ceiling — which is at least *stated*, which it
  currently is not.

### 3 — the local-first bet has no answer to a reboot

**What exists elsewhere.** **Moadim** (<https://moadim.io/>, Show HN 2026-09-05, 33 points,
MIT-licensed, `cargo install --locked moadim`). Read as a competitor it is uncomfortably close to
AgentWeave's `agent-loops` capability extracted into a standalone daemon:

> Moadim is a loop engine for AI agents. Define a loop — a prompt, a schedule, an agent — and it runs
> Claude, Codex, Hermes, or Pi against your repo on every tick… in an isolated workbench with a
> watchdog on every run.

> **Runs locally, survives reboot.** Loops fire from Moadim's portable in-process scheduler — no
> hidden queue, no cloud. Run `moadim install` to register a launchd / systemd service so the daemon
> keeps running across logins and reboots.

> **UI · REST · MCP.** Every loop is an MCP tool and a documented HTTP endpoint — Swagger UI, an iCal
> feed, and a web UI baked into the daemon.

It is macOS/Linux and needs `tmux`, so it is not a substitute on AgentWeave's own platform, and it
has none of the spec flow, review, evidence or operator-in-the-loop surface. It is a single-feature
neighbour. But it is a neighbour that has shipped the one thing on this list.

Pushing from the other direction the same week: **Cursor**, 2026-09-02,
<https://cursor.com/changelog> — *"Cursor supports self-hosted machines, which let you keep tool
execution entirely in your own network. Your codebase, build outputs, and secrets all stay on
internal machines running in your infrastructure"*, plus team pools that *"hibernate idle machines,
then restore within a reconnect window"*. A cloud vendor building toward AgentWeave's deployment bet
while a Show HN builds toward its loops. The middle is getting crowded from both ends.

**What AgentWeave does today.** `openspec/specs/app-lifecycle/spec.md` has six requirements. *"Bare
invocation is the only entry point"* (line 10), *"Environment readiness is diagnosable without
starting the app"* (61), *"Status, stop, and reset act on the local instance"* (77) — which specifies
`agentweave status`, `agentweave stop`, `agentweave reset` and nothing else — *"No CLI command
manipulates collaboration state"* (101), the native webview (112), named profiles (185). Grepped
across all 43 capabilities for `systemd`, `launchd`, `autostart`, `Scheduled Task` and *"survives a
reboot"*: **no matches in any spec file.**

**The gap, and the reason it is not a hypothetical.** AgentWeave's own development loop runs
unattended overnight on this machine, and it already needs exactly this. The only two files in the
entire repository that know how to keep something alive across a session ending are
`.agents/skills/autonomous-prep/SKILL.md` and `.agents/skills/autonomous-session/SKILL.md` — the
project's *harness*, which launches fresh headless processes from a Windows Scheduled Task. The
product the harness is developing cannot do for an operator what the harness does for itself. A Hub
stopped by a 3am Windows update takes every loop, every scheduled job and every queued turn with it,
and the operator discovers it in the morning by the absence of work.

**What a change would touch.** A seventh `app-lifecycle` requirement and a fourth CLI verb, plus a
platform shim per OS: `Register-ScheduledTask` on Windows, launchd on macOS, systemd user units on
Linux. The install must be reversible and must not become a fifth thing `agentweave reset` has to
reason about. It is the largest of the three items here and the only one that is genuinely new
surface rather than a fact the Hub already holds.

**What would make it a bad idea, and it changes the ordering.**

- **A Hub that starts itself starts its loops.** Autostart plus the gap in §2 is a machine that
  reboots at 3am, resumes an autonomous loop with nobody watching, and has no per-run ceiling on what
  that loop spends. **§3 should not ship before §2**, and if only one of the two is built it should
  be §2.
- *"Bare invocation is the only entry point"* (`app-lifecycle/spec.md:10`) is a deliberate, stated
  simplicity bet, and a service registration is the first real exception to it. That deserves the
  round discipline, not a drive-by — the requirement should be amended explicitly rather than
  quietly acquiring a neighbour that contradicts it.
- The operator may not want it. A local-first product whose value is that nothing runs without you is
  entitled to decide that a reboot *should* stop everything. That is a legitimate answer, and if it
  is the answer, the correct deliverable is a line in `app-lifecycle` saying so — which costs almost
  nothing and closes the question, instead of leaving it to be rediscovered every time a competitor
  ships `install`.
