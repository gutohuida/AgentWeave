## The evidence

### 1. Name and test the context-elevation boundary

**What exists elsewhere.** "When Context Gets Root: Privilege Escalation in LLM Harnesses"
(arXiv 2608.27299, submitted 2026-08-27, <https://arxiv.org/abs/2608.27299>) names a failure mode
that is about harnesses rather than models. Instruction hierarchy is a model-side defence that
ranks instructions by where they came from. But the harness assembles the context for each model
invocation, and *that assembly step* can lift low-privilege content into a high-privilege slot.
The paper's measurements: 13 attack objectives spanning confidentiality, integrity, availability
and RCE, across six coding-agent harnesses. With unrestricted action execution, **all 13 objectives
on all six harnesses**. Under automatic permission review, **all 13 objectives on all three
harnesses that offer that mode** — which is the number that matters, because "the approval layer
catches it" is the assumption it falsifies. The authors further reproduce the vulnerability "using
harness-provided persistent goals and scheduled tasks."

AgentWeave is a harness that assembles context, has persistent goals (charters), and has scheduled
tasks (loops, flows, jobs). The paper is describing this shape of system.

**What AgentWeave does today — and most of it is right.** The elevation channel is explicit:
`hub/hub/runner_commands.py:230` passes `--append-system-prompt-file <context_file>` to Claude, and
`:312` passes `-c model_instructions_file=<context_file>` to Codex. Whatever is in that file is
system-prompt-level instruction. It is written at `hub/hub/api/v1/agent_trigger.py:936-939`, into
`<work_dir>/.agentweave/context/<agent>.md` — inside the workspace the agent itself can write to.

Four things already defend it, and they should be said out loud because they are better than what
the paper broke:

- **The file is re-rendered from Hub-owned state on every turn**, immediately before command
  construction (`agent_trigger.py:893-895`: "Build context from current Hub-owned state for every
  turn... an edited charter is therefore visible on the next run"). An agent that writes to its own
  context file has its edit overwritten before the next turn reads it. The persistence half of the
  paper's attack does not land.
- **`request_agent` takes a template, not text** — `mcp_server.py:571-575`, "a new agent from a
  pre-approved template under the project agent budget." An agent cannot author a charter, which is
  the highest-value thing to write into.
- **Scheduled work is gated server-side.** `_require_agent_job_allowance`
  (`hub/hub/api/v1/jobs.py:31`, refusal at `:46-49`) guards create, toggle, run and archive, and
  the project default is `allow_agent_jobs: bool = False` (`hub/hub/api/v1/inbound_queue.py:52`).
  The paper's "scheduled tasks" reproduction vector is off by default here.
- **Spec documents are deliberately not inlined.** `agents.py:1250` tells the agent to
  `read_spec_document(...)` because the document "is not in your working copy" — document bodies
  stay behind a tool call instead of being pasted into the system prompt. That is precisely the
  right instinct, arrived at for a different reason (accuracy, not security).

**The gap.** One agent-authored string does reach another agent's system prompt.
`hub/hub/api/v1/agents.py:1139` renders, into the reviewer's context file:

```
- Under review: task `{review.task_id}` — {review.task_title}, at commit `{review.commit_sha}`
```

`review.task_title` is `task.title` (`hub/hub/review_turn.py:52` and `:224`). Task titles are
free text created by agents through the `create_task` tool, constrained only by
`title: str = Field(max_length=256)` (`hub/hub/schemas/tasks.py:46`) — a length cap, with no
newline restriction and no escaping at the interpolation site. So an implementing agent can put 256
characters of its own choosing, including line breaks that open a new markdown block, into the
system prompt of the agent assigned to review its work. The reviewer is the one actor in
AgentWeave's design whose independence is the whole point.

Second, and more important than the specific string: **nothing tests the property.** The security
here rests on statement ordering inside `agent_trigger.py` — the render happens before the spawn.
No test says "the context file is Hub-rendered and never agent-supplied," so a future refactor that
reuses a cached file, or skips the re-render on a resumed session, silently removes the defence
with a green board. This is exactly the hole last night closed for FastMCP, in the same shape: an
undefended assumption that happened to hold.

**What a change would touch.** A test file naming the property — the context file is regenerated
every turn from Hub state; agent-writable content that reaches it is enumerated and escaped. Plus
one interpolation fix at `agents.py:1139` (strip newlines, or render the title in a fenced/quoted
block rather than inline). Nothing architectural moves.

**What would make it a bad idea.** The concrete exploit here is weak on its own: 256 characters, a
reviewer that also receives strong explicit review instructions in the same file, and a threat
model in which the attacker is already an agent you chose to run. If the item is sold as "we have a
vulnerability" it will not survive contact with the code. It should be sold as what it is — the
property is currently true and undefended, the paper is evidence that harnesses lose this property
without noticing, and naming it costs a test file. There is also a real argument that the escaping
fix alone is enough and the test is over-engineering; I do not think so, given how much of
AgentWeave's design depends on the reviewer being uninfluenced, but it is arguable.

### 2. Record the runner CLI version on every run

**What exists elsewhere.** Claude Code v2.1.251, published 2026-08-28T18:19:32Z
(`gh api repos/anthropics/claude-code/releases/tags/v2.1.251`), fixed four boundary defects in one
release:

- "file tools (Read, Write, Edit) following a symlink swapped inside the working directory **after
  the permission check**, which could read or write outside the approved location" — a
  time-of-check/time-of-use race in the permission layer;
- "Grep and Glob not applying `Read(...)` deny rules to files reached through a symlinked search path";
- plugin commands in a marketplace entry able to point outside the plugin directory (path traversal);
- the Workflow tool reading a `scriptPath` outside what the session may read, before the permission
  check ran.

v2.1.252 (2026-08-31T19:46:55Z) then fixed "'always allow' not saving in a project that has no
`.claude/settings.local.json` yet" — a permission decision silently not persisting.

**What AgentWeave does today, and where it is genuinely ahead.** `_decide`
(`hub/hub/mcp_server.py:901-948`) is the Hub's own answer to a permission request, and it is
soundly written: it `realpath`s both the workspace root (`:920`) and the candidate (`:940`) before
comparing with `os.path.commonpath`, with a comment explaining why component comparison beats a
string prefix. Symlinks and `..` are collapsed on both sides. AgentWeave does not have the bug that
was fixed above, and `openspec/specs/agent-run-sandboxing/spec.md` imposes the permission mode from
the Hub rather than from the machine's config file — structurally stronger than a posture the run
negotiates for itself.

**The gap.** `_decide`'s own comment is the honest statement: "This does not make shell escape
impossible... and is a boundary, not a sandbox." The Hub answers *permission prompts*; the CLI's
own engine is what actually opens the file. Every one of the four v2.1.251 defects lived in that
engine. So a non-yolo AgentWeave run's real containment is a function of the runner CLI's version —
and the Hub records no version anywhere. A grep for `--version`, `cli_version`, `runner_version` or
`version_output` across `hub/hub/*.py` and `hub/hub/api/v1/*.py` returns exactly one hit, and it is
a comment in `launchability.py:338` about a diagnostic phrasing.

Three consequences, in order of how much they cost:

1. **Evidence is unanchored.** A run record and its accepted evidence say what an agent did, but not
   what the process was permitted to do while doing it. Two runs a week apart under identical Hub
   settings can have materially different containment, and nothing in the record distinguishes them.
2. **`runner_commands.py` is verified against an unnamed version.** Its opening line says "Every flag
   below was verified against the supported runner CLIs" — against no stated version. A renamed or
   removed flag ships as a failing run rather than a caught mismatch. This is the same class of
   problem as the unbounded `fastmcp>=2.0`, on a dependency that is not even declared in a
   `pyproject.toml`, and so has no ceiling available to it at all.
3. **`agent-run-sandboxing`'s claim weakens with time.** The spec's guarantee is about what the Hub
   passes. It says nothing about whether the receiving CLI honoured it, and there is no upper bound
   on how stale the installed CLI may be.

**What a change would touch.** Capture `<cli> --version` once per run (or per Hub start, cached) and
store it on the run record; surface it in the run's Workspace/diagnostics section; assert a minimum
in `runtime-diagnostics`. `hub/hub/runner_commands.py`, the run model and one migration, plus the
diagnostics surface. It composes with F115's recording work rather than competing with it — F115
records *what a run wrote*, this records *what the run was permitted to write with*.

**What would make it a bad idea.** A version string nobody reads is dead weight, and a *minimum*
version check is a support burden the operator has not asked for — this is currently a
single-operator product on one machine where the CLI is whatever `claude` resolves to. The cheap
half (record it, show it in diagnostics) is defensible on its own; the expensive half (gate on it)
should wait for a second machine to exist. Take the cheap half only.

### 3. Ratify or widen the fastmcp ceiling, with a number attached

**What exists elsewhere.** "Update from Hell: Can Coding Agents Survive Hidden Breakage in
Dependency Upgrades?" (arXiv 2608.30300, submitted 2026-08-31,
<https://arxiv.org/abs/2608.30300>) introduces DEPBENCH: 203 real-world dependency-upgrade tasks
across five package ecosystems and five language communities, each containing hidden code-level
changes that require source adaptation. Evaluating mainstream coding agents, **the best completed
configuration solves 104/203 — 51.2%**, with wide variation across harnesses, models and
ecosystems.

**Why this is the evidence the open decision needs.** Last night's commit filed the item explicitly:
"The upper bound on fastmcp is defensive and was taken unattended on 2026-09-01 — ratify or
widen" (`pyproject.toml:39`, with the pins at `:47` and `:71` and `hub/pyproject.toml:24`). The
counter-argument to ceilings is the one spec-kit 1.0.0's own release notes make — that a major
version number no longer means much because agents make migration cheap. DEPBENCH is the first
number I have seen put on that claim, and it is a coin flip. On a dependency where a break means
*every agent turn fails to start* rather than a red test, a coin flip is not a migration strategy.

The bound plus `hub/tests/test_fastmcp_api_contract.py` is therefore the right posture, and the
decision in front of the operator is narrow: keep `<4` and raise it deliberately when the contract
test passes against 4.x, or widen now and accept the resolve. The same paper is an argument
*against* extending the pattern reflexively to `fastapi>=0.110`, which is a separate open decision:
a FastAPI break is a failing test, which is the case agents handle best.

**What a change would touch.** Nothing in code. One line in `decisions_for_user` gains a citation.
This is on the list because a decision with a measurement behind it gets made, and one without it
gets deferred a fourth time.

**What would make it a bad idea.** It is not a build item, and if the 09:00 window treats it as one
it will re-litigate a change that landed eight hours ago. It belongs in the review page as a
decision, not in the spec queue.

  `r/LocalLLaMA` immediately before it returned 25 entries). Cause unknown; treat the subreddit as
  unsampled today rather than quiet.
- **Python on this machine defaults to cp1252 on stdout**, so any extraction script printing
  fetched text dies with `UnicodeEncodeError` on the first non-ASCII character — which looks like a
  parse failure and is not. `export PYTHONIOENCODING=utf-8`, or encode to ASCII with `replace`,
  before printing anything fetched from the web.
- **MSYS-style paths (`/c/Users/...`) do not work as arguments to Windows Python**, though `curl`
  accepts them. The first HN fetch appeared to fail with `FileNotFoundError` when the file had in
  fact been written correctly. Use `C:/Users/...` in every path handed to Python.
