## The evidence

### 1. Bound the `fastmcp` dependency and give the tool surface a resolution test

**What exists elsewhere.** FastMCP 4.0.0 was published 2026-08-31T18:19:53Z and uploaded to PyPI
at 2026-08-31T18:20:31Z (`gh api repos/jlowin/fastmcp/releases/tags/v4.0.0`;
`https://pypi.org/pypi/fastmcp/json`). It is a rewrite onto MCP Python SDK v2 and the
`2026-07-28` protocol revision. Its own release notes list the breaking changes: server-initiated
sampling and roots removed, `ctx.elicit()` restricted to old-protocol connections, FastMCP 3's
deprecated APIs deleted, MCP model fields moved to snake_case, background tasks moved out to a
separate `fastmcp-tasks` package
(<https://github.com/jlowin/fastmcp/releases/tag/v4.0.0>, 2026-08-31). The upgrade guide adds that
v4 requires `pydantic>=2.12` and `FastAPI>=0.133.0`, and replaces `httpx` with `httpx2`
(<https://gofastmcp.com/getting-started/upgrading/from-fastmcp-3>, read 2026-09-01).

**What AgentWeave does today.** The agent tool surface is a FastMCP server —
`hub/hub/mcp_server.py`, 1410 lines, 27 `@mcp.tool()` declarations, started over stdio at
`mcp_server.py:1397`. The dependency is declared unbounded in two places: `pyproject.toml:39`
(`mcp = ["fastmcp>=2.0", "pyyaml>=6.0"]`, and again at `:60` for `all`) and
`hub/pyproject.toml:19`. CI resolves fresh every run with no lockfile and no constraints file —
`.github/workflows/ci.yml:35-36` is `pip install -e ./hub` then `pip install -e ".[dev]"`.

**The gap, measured rather than asserted.** The two CI runs after the PyPI upload —
`33437238887` at 2026-08-31T20:39:38Z and `33444923666` at 2026-08-31T22:10:04Z — both passed.
So the tool surface every agent turn depends on moved from the 3.x line to 4.0.0 inside a
six-hour window, on a green board, with no signal. I installed 4.0.0 into a throwaway venv and
probed the four things `mcp_server.py` actually uses:

- `FastMCP(name=..., instructions=...)` — works.
- `@mcp.tool()` on a plain function — works.
- `inspect.signature(mcp.run)` returns `['transport', 'show_banner', 'transport_kwargs']`, so
  `mcp.run(transport="stdio", show_banner=False)` still binds.
- `await mcp.list_tools()` returns objects carrying `.name` and `.parameters`, and a
  `Literal[...]` default still renders as
  `{"default": "message", "enum": ["message", "delegation", "review"], "type": "string"}` — which
  is what `test_mcp_tool_schemas.py:38`, `test_tool_surface_matches_server.py:22,41`,
  `test_mcp_server_stdio_surface.py:101`, `test_agent_tool_surface_phase7.py:15`,
  `test_requirement_gate.py:550` and `test_spec_index_writer.py:40` all assert against.

So this is a near miss, not an outage. But `FastMCP.get_tools()` *is* gone in 4.0.0 (it raises
`AttributeError: 'FastMCP' object has no attribute 'get_tools'. Did you mean: 'get_tool'?`), which
shows the removal pass reached exactly the introspection layer those seven test files sit on. And
the operator's own machine still reports `fastmcp 3.4.5` — local and CI now disagree about the
version of the process that starts every agent turn.

**Why this is the top candidate.** The roadmap already carries this decision, scoped one library
too narrowly: Phase 0's "Pin the FastAPI/Starlette resolution (or add a CI job on the floor
versions)" and decision #7, motivated by "the unbounded `fastapi>=0.110` has produced two CI-only
failures through Starlette major bumps"
(`openspec/explorations/2026-08-30-release-roadmap.md`). FastMCP is the worse instance of the same
class, because a FastAPI break is a failing test and a FastMCP break is every agent failing to
start — and the Phase 5 "stranger's hour" (`pip install agentweave-ai` on a clean machine) resolves
whatever is newest that morning. Note also that FastMCP 4 requires `FastAPI>=0.133.0`, so the two
unbounded pins are now coupled.

**What a change would touch.** `pyproject.toml:39,60`; `hub/pyproject.toml:19`; one CI job in
`.github/workflows/ci.yml`. Nothing in `mcp_server.py` needs to move today.

**What would make it a bad idea.** A ceiling that is never raised is how projects end up two
majors behind — the pin has to come with the job that tests the ceiling, or it is just a slower
version of the same problem. And there is a real argument for the opposite reading: the surface
AgentWeave uses is deliberately narrow (stdlib plus `fastmcp`, by the comment at
`mcp_server.py:28-32`), it survived a two-major jump untouched, and a floor/ceiling matrix costs
CI minutes on a suite the operator has already called too long (F109).

### 2. Ship the requirement-drift surface (F129 + F132)

(<https://github.com/github/spec-kit/releases>). The release is less interesting than what it
released *into*: `extensions/catalog.community.json` (fetched 2026-09-01, `updated_at`
`2026-08-31T00:00:00Z`) lists **162 community extensions**. 56 of them match on
governance / review / autonomy / orchestration / evidence terms. The ones that sit on AgentWeave's
map:

- **Spec Sync v0.1.0** — "Detect and resolve drift between specs and implementation. AI-assisted
  resolution with human approval."
- **Architecture Guard v2.3.6** — "detecting drift, enforcing architectural rules, and generating
  actionable refactor tasks."
- **Keel Discovery v0.2.0** — "round-trip drift auditing after implementation."
- **Retrospective Extension v1.0.0** — "spec adherence scoring, drift analysis, and human-gated

- **Fleet Orchestrator v1.1.0** — "Orchestrate a full feature lifecycle with human-in-the-loop
  gates across all SpecKit phases."
- **Loop Engineering v1.0.0** — "safe autonomous agent loops... a maker/checker split,
  externalized loop state."
- **MAQA v0.1.6** — "Coordinator → feature → QA agent workflow with parallel worktree-based
  implementation."
- **Charter v0.5.1** — "Compose modular project constitutions from shared fragment registries."

**What AgentWeave does today.** The drift machinery is real and complete on the API:
`POST /spec/drift/detect` at `hub/hub/api/v1/spec.py:930`, `GET /spec/drift` at `:951`,
`POST /spec/drift/{drift_id}/resolve` at `:983`. I checked both consumers as of `67f863d`:
`grep -rn 'spec/drift' hub/ui/src/` returns **nothing** — the UI's spec client
(`hub/ui/src/api/spec.ts`) contains one `'drifting'` string literal at `:98` and no call to any of
the three routes. And the agent tool surface has no entrance either: the only two occurrences of
"drift" in `hub/hub/mcp_server.py` (`:34`, `:1073`) are comments about schema drift in CI. F129
and F132 both still hold, unchanged.

**The gap.** AgentWeave built the thing and cannot reach it from either side; the nearest
competitor's ecosystem ships four separate takes on it, and the most direct one ships it *with*
the human approval step — which is AgentWeave's stated differentiator, not spec-kit's. F132's own
note is the sharpest version: "the gate's remedy names an action no surface offers." The roadmap
puts this in Phase 3 with the constraint that Resolve ships with or before Detect. The argument for
moving it up is that Phase 1 closed yesterday, this is the differentiator that is already *built*,
and the exit criterion the roadmap wrote for Phase 3 — "a screen-recording of one spec-driven
change, requirement to merged work to drift detection when the code later moves" — is now the
demo that distinguishes AgentWeave from an assembled spec-kit stack.

**What a change would touch.** `hub/ui/src/api/spec.ts` plus a Detect/Resolve surface under
`hub/ui/src/components/spec/`; one or two tools in `hub/hub/mcp_server.py` for the agent-side
entrance (F132); nothing in the API layer. The Phase 0 proposal for this already exists at R1 per
decision D4, so this is partly a resume, not a start.

**What would make it a bad idea.** Decision #5 (review the F129+F132 drift-UI proposal) is
unmade, and this is UI work — the roadmap explicitly sequences UI *after* Phase 2's legibility
cluster, on the reasoning that surfacing a differentiator on top of wrong actor attribution
(F47/F120) shows the operator a screen that lies about who did what. Building the drift surface
before the attribution fix risks shipping a demo that has to be rebuilt.

**One caveat on the competitive read.** A catalog entry is not adoption. spec-kit's own community
page states maintainers "do not review, audit, endorse, or support the extension code itself"
(<https://github.github.com/spec-kit/community/overview.html>). 162 independently versioned
extensions with no shared execution model is also the strongest available evidence *for*
AgentWeave's "integrated, not assembled" bet — I did not measure install counts for any of them,
and the honest statement is that the ideas are converging, not that the products are.

### 3. Decide whether `ask_user` and permission approval adopt MCP's guard pattern (MRTR)

**What exists elsewhere.** The MCP `2026-07-28` revision introduced Multi Round-Trip Requests
(SEP-2322): a server returns an `InputRequiredResult` (`resultType: "input_required"`) whose
`inputRequests` field carries what it needs; the client gathers it and **retries the original
request** with `inputResponses`. This replaces server-initiated `roots/list`,
`sampling/createMessage` and `elicitation/create` outright. The same revision removes protocol
sessions and the `initialize` handshake, removes SSE resumability, and deprecates Roots, Sampling
and Logging under a new twelve-month deprecation policy
(<https://modelcontextprotocol.io/specification/2026-07-28/changelog>, read 2026-09-01). FastMCP 4
ships this as "guard-mode multi-round-trip tools (SEP-2322)" (PR #4544): a tool returns
`InputRequiredResult(description=..., requested_schema=...)` and is re-run with the answer
available, and the upgrade guide notes the pattern "works across all protocol eras and replaces
the old `ctx.elicit()` pushing model."

**What AgentWeave does today.** `ask_user` is a tool on the Hub's own surface —
`hub/hub/mcp_server.py:307`, `questions: List[Dict[str, Any]], blocking: bool = True` — whose
docstring instructs the agent to batch 1–4 questions so "your turn waits once instead of once per
question." The waiting, the resumption and the operator surface are all Hub-side machinery.

**The gap, and why it is a decision rather than a build.** The shape MCP just standardised is the
same shape AgentWeave arrived at independently, and AgentWeave's open findings are precisely the
seams of a hand-rolled version: **F146** — "the operator's own question route accepts `blocking`,
tells the panel an agent is waiting, and throws the answer away"; **F133** — "the operator's own
message erases the reason their agent is stalled"; and the `approval-waits-for-the-turn-to-end`
change, still in `openspec/changes/`. A protocol-level retry-with-answers model puts resumption in
the transport instead of in the Hub's turn bookkeeping. It is *not* obviously the right move for
AgentWeave: the guard pattern's resumption is a re-call, and AgentWeave's whole operator surface
assumes a turn that is still alive and attributable. But leaving it undecided means AgentWeave's
most distinctive surface drifts away from where the ecosystem's is going, and the decision is
cheaper now than after Phase 2 builds more on the current shape.

**What a change would touch.** A decision and a spike, not a change: read
`hub/hub/api/v1/questions.py` and the `blocking` path against SEP-2322's contract and write down
whether AgentWeave's `ask_user` should stay Hub-side. Candidate 1's pin decision partly gates this
— the guard API only exists on FastMCP 4.

**What would make it a bad idea.** Adopting a two-month-old protocol pattern into the surface the
operator experience rests on, when the current one is shipped and driven, is a large risk for an
alignment benefit. The defensible outcome of this candidate may well be a written "no, and here is
why" — which is worth having, because F146's fix will otherwise be designed without it.

### 4. Build F115's recording half — a write outside the workspace is recorded

**What exists elsewhere.** "Breaking Claude Code Opus 5 Auto Mode" (embracethered.com,
2026-08-31, 335 points on Hacker News that day —
<https://embracethered.com/blog/posts/2026/breaking-claude-code-opus-5-and-automode/>) reports a
five-stage chain that reached remote code execution at a claimed 60–80% success rate against a
mode whose published evaluation showed 0.00%. The mechanism that matters here is stage 4: the
approval classifier passed a benign-looking Python decoder without inspecting what it would import,
and running it inside the attacker-controlled directory let a malicious `struct.py` shadow the
standard library. The author's conclusion is the quotable one: "Auto Mode approval is not evidence
that a command is safe" — sandboxing, not classifier confidence, is the boundary. Treated as
content: the page contained no instructions aimed at a reading agent.

**What AgentWeave does today, and where it is already ahead.**
`openspec/specs/agent-run-sandboxing/spec.md` requires that "The Hub SHALL pass an explicit,
non-bypass permission mode to every non-yolo Claude run it spawns" and that "A non-yolo Claude
run's actual permission behavior MUST NOT depend on the config file of the machine the Hub process
happens to run on." That is a structurally stronger claim than the one that broke — the posture is
imposed by the orchestrator, not negotiated by the run. It is worth saying out loud in the docs
rewrite (Phase 5), because it is a differentiator nobody currently states.

**The gap.** Two things. `yolo` runs pass `--dangerously-skip-permissions` (same spec;
`hub/hub/runner_commands.py:22` documents the non-yolo default), and nothing records what such a
run wrote. And F115 — "the agent worktree is a working directory, not a boundary" — is
spec-complete after three rounds and **0 of 54 tasks implemented**
(`openspec/changes/a-write-outside-the-workspace-is-recorded/tasks.md`). Reading its task 1.4
corrects the finding's headline in a way worth carrying forward: the change pins that
`mcp_server._decide` **already refuses** an absolute outside path under the default posture. So
AgentWeave's containment is not the hole; the hole is that a write outside the workspace leaves no
record — the path survives only as a stringified blob inside `payload["input"]`, and nothing says
it was outside anything.

**What a change would touch.** A new `hub/hub/workspace_writes.py`, the `parse_claude_line` and
Codex `apply_patch` parse points, the run record and the activity timeline. All of it is already
written down across 54 tasks.

**What would make it a bad idea.** It is the largest item on this list by a wide margin, it is
Phase 0 queue work rather than anything new, and the security post is an argument for *containment*
while F115 delivers *observability*. If the post is taken as the motivation, the honest response is
smaller and different: state the Hub-imposed-posture property in the docs, and check what a `yolo`
run is permitted to do — not to open 54 tasks.

## Also seen, not proposed

- **MCP `2026-07-28` removes protocol sessions and the `initialize` handshake, and deprecates
  Roots, Sampling and Logging.** Dropped as a candidate because AgentWeave's server is stdio-only
  (`mcp_server.py:1397`), holds no protocol session state, and uses none of the three deprecated
  features. It is the reason candidate 1 matters, not a candidate itself.
- **spec-kit 1.0.0's release notes argue that a major version number no longer means anything**,
  because agents make migration cheap (<https://github.com/github/spec-kit/releases/tag/v1.0.0>,
  2026-08-21). Interesting as a position, and precisely the assumption candidate 1 declines to
  make about the process every agent turn starts through. Not a candidate; possibly a good line in
  a future docs page.
- **arXiv 2608.27427, "Persona-Execution Separation" (Yisen Xi, 2026-08-27)** — persona and
  execution in different trust domains joined by a governed contract bridge, so instructions can
  evolve while execution stays audited. That is close to AgentWeave's charter/runner binding and to
  the F47/F120/F142 attribution arc. Dropped: single-author, no evaluation that transfers, and the
  attribution work already has a decision filed (roadmap decision #3, the `flow` actor kind).

  cs.SE listing only; not fetched, so no claim made.

- **Langfuse v4.23–v4.26 (2026-08-28 to 2026-08-31)** — evaluator trace linking, OTel attribute
