## The evidence

### §1 — the rail that nobody talks to

**What AgentWeave does today, and it is better than yesterday's file said.**

There is a real, deliberate, cross-page "needs you" surface. `conversation_attention` computes it:

```python
async def conversation_attention(db, conversation_ids) -> Dict[str, str]:
    """Map each conversation id to "running", "waiting" or "idle".

    Waiting outranks running: a run blocked on a question is still a running process, but what
    the operator needs to see is that it stopped for them.
    """
                                                        hub/hub/conversations.py:401-408
```

It is not a half-measure. The two arms are shaped alike and both exclude the expired state, with the
reason written down:

> *"The exclusion matters most here of all the readers, because this requirement states its own
> reason and that reason expires with the wait … Once the timeout is spent and the run has gone back
> to work, the rail would say 'waiting on the operator' — outranking `running`, deliberately — about
> a run that is running and waiting for nothing. That is F14's own defect, inverted, on the
> conversation rail."* (`conversations.py:427-432`)

```python
waiting_queries = (
    select(Question.conversation_id).where(
        Question.conversation_id.in_(ids),
        Question.answered.is_(False),
        Question.wait_ended_at.is_(None),
    ),
    select(PermissionRequest.conversation_id).where(
        PermissionRequest.conversation_id.in_(ids), PermissionRequest.status == "pending"
    ),
)
                                                        hub/hub/conversations.py:433-442
```

The type is `ConversationAttention = Literal["running", "waiting", "idle"]` (`agent_chat.py:94`),
described as *"Whether this conversation needs the operator, without opening it"* (`:136`). It
reaches the sidebar tree, which renders on every page:

```tsx
// Waiting anywhere beneath a collapsed agent still has to be visible, or collapsing the
// agent hides the thing the attention state exists to surface.
const needsAttention = conversations.some((c) => c.attention === 'waiting')
                                                        hub/ui/src/components/layout/AgentTree.tsx:95-97
...
{!expanded && needsAttention && (
  <span data-testid={`rail-agent-attention-${projectId}-${agent.name}`}
        style={{ background: 'var(--amber)' }}
        title="A conversation is waiting for you"
                                                        AgentTree.tsx:170-175
```

So the design is right. **What is broken is that the rail is never told.**

**The defect, measured.** `AgentTree` reads `useProjectConversations`, whose entire refresh
condition is one line:

`Question` does the same thing eight lines above its own broadcast —
`conversation_id=await conversation_id_for_run(session, created_by_run_id)` (`questions.py:269`) —
and the model comment says why: *"Denormalized from the opening run, for the same reason as
`Question.conversation_id`"* (`models.py:1606`).

**Why nothing else covers for it.** The query client is configured `refetchOnWindowFocus: false`
(`main.tsx:8-14`), and the conversations query sets no `refetchInterval`. The only two
`refetchInterval: 3000` in the whole UI are `api/questions.ts:61` and `api/permissions.ts:52` — the
panels, which are mounted only on their own surfaces. So during a blocking `ask_user` the run is
parked: no output, no status change, no event carrying a `conversation_id`. **The dot does not
appear for the whole wait.** And symmetrically, after the operator answers, `question_answered` also
fails the guard, so a stale amber dot survives until something unrelated invalidates the query.

**The second bug the same omission causes**, already named in yesterday's file and still live at
HEAD:

line, one fix.

- **GitHub Copilot CLI v1.0.86**, released **2026-09-17T22:57:47Z**
  (<https://github.com/github/copilot-cli/releases/tag/v1.0.86>): *"The status row now says it is
  waiting for background shells, instead of 'Working', when a turn ends while an attached background

- **block/goose v1.51.0** (2026-09-17T19:15:25Z), the opt-in approval bell (#10182) — reported

**The gap.** Three vendors concluded within four days that "a human is now the critical path" needs
its own status, distinct from "running". AgentWeave concluded that first and built it — and then
starved it of the one field its refresh condition tests for.

**What a change would touch.** Eleven `sse_manager.broadcast` payloads across five files, one key
each: `questions.py:278/452/544`, `agent_actions.py:969/1013/1089`, `agent_trigger.py:2651/2846`,
`permissions.py:127/177`, `operator_direction.py:195`. Add `"question"` and `"header"` to
`question_asked` at the same time and `eventSummary.ts` starts rendering the real text with no UI
change. **No UI change is required for the rail fix at all** — which means no `make ui`, no
`scripts/refresh_ui_bundle.py`, and none of the "source and `hub/hub/static/ui` must be committed
together" constraint that DIRECTION imposes on F386. That is unusual for an operator-visible repair
and is most of why this ranks first.

There is also somewhere for a later, larger version to land: `agentStatusConfig.ts:18` already
defines `waiting: { dotColor: 'var(--amber)', label: 'Waiting' }` as an **agent** status, and
`effective_heartbeat_status` only ever produces `idle` / `running` / `stalled` plus whatever a
self-registering agent posts (`agent_status.py:28-38`). The display vocabulary is ahead of the
producer. Not proposed today; noted so the next reader does not think it needs inventing.

**What would make it a bad idea.** Three things, and the third changes how yesterday's §3 should be
sequenced.

(a) It widens what the durable event log holds. `persist_event` is called with the same dict at
`questions.py:283-289`, so adding `question` text duplicates into the log something the `questions`
row already stores. That is a duplication question rather than a disclosure one, but it should be
decided out loud. `conversation_id` alone carries no such concern and could ship first.

(b) Broadcasting more keys means more tests pinning payload shapes. `eventSummary.test.ts:8` already
asserts a `question_asked` branch with a payload the product cannot produce — the F100/F101 class
(`FINDINGS.md:7035`, *"A test can pin a branch the product cannot reach"*). Fixing the payload makes
that test honest, which is a benefit, but it means the change touches tests that currently pass.

(c) **Yesterday's §3 is confounded until this lands.** That candidate proposed measuring
`answered_at - created_at` and the pending-permission expiry rate against the 240 s / 120 s fuses
(`mcp_server.py:927`, `:935`). Every one of those historical rows was produced under a rail that
never updated. A high expiry rate would not measure operator attention; it would measure this bug.
§3 is still worth doing and its tables are unchanged — but it should be read as a **baseline** now
and re-read after §1, not treated as a verdict on the operator. That is an argument for doing both,
in that order, not for dropping either.

### §2 — the third runner, and the question the exploration left open

**What AgentWeave does today.** Two runner kinds are creatable: `RUNNER_CLIS = ("claude", "codex")`
(`hub/hub/db/models.py:311`), enforced at `hub/hub/schemas/runners.py:22-23`. Both are in
`MCP_INJECTABLE_RUNNERS = {"claude", "claude_proxy", "native", "codex"}` (`launchability.py:228`).
Copilot is refused, on purpose and in writing, in two places:

> *"Only claude/claude_proxy/native and codex are wired to an actual spawn path today —
> `runner_commands.py`'s scope. Kimi, OpenCode, and Copilot are refused with a stated 501 rather
> than silently mishandled. There is no fallback runtime for them."*
> (`hub/hub/api/v1/agent_trigger.py:14-17`)

> *"Kimi, OpenCode, and Copilot are explicitly out of scope for this task (per-runner command
> construction for them is deferred) — `build_command` raises `UnsupportedRunnerError` for anything
> else so the caller gets a clear, stated reason rather than a silently wrong command."*
> (`hub/hub/runner_commands.py:7-9`)

The **lifecycle CLI half is already written**, and it is not a stub — it names the session-resume
mechanics and the MCP registration command:

```python
"copilot": {
    "cli": "copilot",
    # Session IDs are UUIDs emitted in the `result` JSONL event's `sessionId` field.
    # Resume via --resume=<uuid> (single arg with = to disambiguate from interactive picker).
    "session_flag": "--resume",
    "output_format": "json",  # JSONL: one JSON object per line
    "session_source": "jsonl",
    "session_id_field": "sessionId",
    "session_event_type": "result",
    "model_flag": "--model",
    # CLI-based MCP registration (same pattern as claude/kimi/codex)
    "mcp_add_cmd": ["copilot", "mcp", "add", "{name}", "--", "{server_cmd}"],
},
                                                        src/agentweave/constants.py:230-242
```

There is also a standing operator skill for driving three Copilot CLI agents against a local Hub
(`.agents/skills/copilot-test-setup/SKILL.md`) and a prior exploration
(`openspec/explorations/2026-09-07-agentweave-without-mcp-and-with-copilot.md`). So the ground has
been walked; what is missing is the Hub adapter.

**The open question, and today's answer to it.** Yesterday's exploration
(`2026-09-20-the-approval-transport-is-not-the-tool-surface.md`) states the design risk precisely:
`resolve_access_path(runner, hub_client) -> "mcp" | "cli"` is *"one boolean answering three
independent questions"* — can the Hub deliver its tool surface, can it approve tool calls, and how
does the agent reach the capability plane — and concedes that for `claude` and `codex` the three
co-vary so *"the conflation costs nothing"*. The exploration does not answer whether a third runner
breaks that.

This week's Copilot CLI releases answer it, in the direction that costs least:

- **v1.0.87-0, 2026-09-18T21:29:08Z** (<https://github.com/github/copilot-cli/releases/tag/v1.0.87-0>)
  — *"A failing MCP server no longer removes other servers' tools"*; *"MCP servers that advertise
  list-change capabilities but do not implement subscriptions now connect instead of failing"*;
  *"Session resume no longer hangs while reconnecting MCP servers"*; *"`copilot mcp list` and
  `copilot mcp get` now report the built-in `github-mcp-server` when you are signed in, instead of
  showing it only in the interactive `/mcp` view"*; *"Configure per-server MCP slow-connection
  warning thresholds with `slowConnectionThresholdMs`"*; and *"Extension permission handlers approve
  subagent tool requests without leaving duplicate CLI prompts"*.
- **v1.0.86, 2026-09-17T22:57:47Z** — *"Custom agents can opt into repository instruction files
  (AGENTS.md, copilot-instructions.md, CLAUDE.md) by setting `include-custom-instructions: true` in
  their frontmatter"*, and *"/sandbox policy now reports local-network access using your configured
  setting"*.
- Eight npm publications in six days: `1.0.84` (2026-09-15T22:55Z) → `1.0.87-0` (2026-09-18T21:29Z);
  `dist-tags` today are `{latest: 1.0.86, prerelease: 1.0.87-0}`
  (<https://registry.npmjs.org/@github/copilot>).

Copilot CLI has a server-registration MCP client, a permission-handler surface that now reaches
subagents, an opt-in path for repository instruction files, and a JSONL result event carrying a
session id. That is the same shape as `claude` and `codex`: **the three questions co-vary for
`ghcp` too**, so `resolve_access_path` does not have to be split to add it. The refactor the
exploration contemplated is not on the critical path.

**The gap.** The Hub adapter. `RUNNER_CLIS` gains a third value, `MCP_INJECTABLE_RUNNERS` gains
`"copilot"`, `runner_commands.build_command` gains a branch, `RunnersPage.tsx:19`'s `CLI_OPTIONS`
gains an entry, and the `UnsupportedRunnerError` / 501 comments at `agent_trigger.py:14-17` and
`runner_commands.py:7-9` stop being true and must be edited with the code rather than after it.

**What would make it a bad idea.** Four things, and one of them is disqualifying on its own today.

(a) **This is a feature, not a defect.** No finding is open on it. It competes with §1, which repairs
something broken, and it should lose that race.

(b) **It is a stated scope boundary, twice, in prose written by someone who knew.** Crossing it is
the kind of thing that wants an `APPROVALS.md` token even though nothing formally gates it — which
makes it a poor fit for today's unsteered window and a good fit for a DIRECTION section.

(c) The two live transports are `PtySession` (claude) and `codex app-server` / `codex exec`
(`runner_commands.py:11-14`). Copilot's JSONL mode is a third parsing surface, and `runner_parsing`,
`turn-outcome-visibility` and `agent-stream-events` all assume the two that exist. The CLI-side
profile says `"output_format": "json"` and names the `result` event, but nothing in `hub/hub` has
ever read one.

(d) `v1.0.87-0` is a **prerelease**; npm `latest` is `1.0.86`. Four MCP fixes landing in one
prerelease is a sign the surface is still moving, which argues for building against `1.0.86` and
re-checking, not for chasing the tag.

## Also seen, not proposed

- **AX — `google/ax`, "Google's open agentic orchestrator", 380 points on HN 2026-09-20T22:32:43Z**
  (<https://news.ycombinator.com/item?id=49780797>, <https://agentexecutor.io>, repo created
  2026-03-30, pushed 2026-09-20, **3,808 stars**, Apache-2.0). The largest agent-infrastructure
  story of the day and **not a competitor to AgentWeave** — it is Kubernetes for agent workloads,
  four declarative primitives (`Task`, `Workspace`, `Gateway`, `Model`) on top of
  `agent-substrate/substrate`, aimed at *"billions of concurrent agent sessions per cluster"*. Three
  things from it are worth recording anyway. **(i)** Its framing — *"Agents are a new kind of
  workload. They are neither stateless microservices nor run-to-completion batch jobs … and can burn
  money in a loop if nobody is watching"* — is answered in AgentWeave already: `usage-accounting`
  ships *"A project token budget pauses autonomy but not the operator"* (`spec.md:83`), enforced
  through `budget_state` and `PATCH /budget` (`api/v1/accounting.py:43-73`). **(ii)** Its `Gateway`
  primitive — *"Lock traffic down to an explicit allowlist of hosts and ports"* — is something
  AgentWeave's spec **deliberately declines**: *"This is a rule about what a shell command's text
  names. It is not containment of network"* (`agent-run-sandboxing/spec.md:539`). Copilot CLI
  shipped *"Sandbox proxies work on Windows"* in v1.0.87-0 the same week, so that is two containment
  shipments in three days on AgentWeave's own host platform. Still not proposed: reversing a written
  non-goal is an operator decision and an L, and nothing has been bitten. **(iii)** Its
  suspend/resume claim — *"Idle agents waiting on model responses, external tool calls, or **human
  responses** are checkpointed, suspended, and brought back in under a second"* — is the structural
  alternative to AgentWeave's fuse (`OPERATOR_DECISION_TIMEOUT = 120`, `QUESTION_ANSWER_TIMEOUT =
  240`, `mcp_server.py:927/935`). AgentWeave cannot checkpoint a CLI process, so this is not
  portable; recorded because it is the first time the human wait has shown up as a *scheduling*
  state rather than a UI state. One HN commenter's framing is worth the caveat: *"it's misleading to
  label it as 'Google's' … that does not imply it has the full backing of Google."*
- **arXiv 2609.21190, *SWE-Proof* (2026-09-18, <http://arxiv.org/abs/2609.21190>)** — the strongest
  outside evidence this week on AgentWeave's central bet, and it **generated a candidate that died
  on measurement**. The paper's finding: *"models that must write their own [specification] gain
  nothing over an unaided baseline, and only 62% of their specifications pass our audit. The usual
  failure is faithfulness, a specification that constrains part of the required behavior and leaves
  the rest free."* AgentWeave writes model-authored specs, and its coverage computation measures
  *requirement → work → evidence* (`requirement-traceability/spec.md:204-227`) — never whether a
  requirement constrains the whole of its behaviour. The obvious mechanical proxy is
  SHALL-clauses-per-scenario, so it was measured across all 43 shipped capabilities: **637
  requirements, 2,588 SHALL clauses, 2,229 scenarios; median SHALL/scenario 1.0; zero requirements
  with no scenario; 49 with exactly one, of which two carry four or more SHALLs.** The corpus is
  healthy on this axis and there is nothing to propose. Recorded in full because the measurement is
