### 3. The grounds are positive-only and permanent; the harness reports both ways, every run

**What AgentWeave does today.** One signal decides F299's grounds, and from today it will decide the
approver flag too. That signal is `Run.mcp_adapter_online_at`, set when the Hub's adapter first
announces itself (`api/v1/agent_actions.py:441-442`). `harness_has_honoured_mcp`
(`launchability.py:232-259`) reads it as *"True from the moment **any** run of this agent has an
`mcp_adapter_online_at`"*: `select(Run.id) … .limit(1)`, with no recency and no count of later
failures. Its docstring states why there is no other signal:

> Positive evidence only. **There is no negative form to record: a harness that ignores the
> configuration is silent**, and silence is exactly what "no grounds" means.

**What the harness actually emits (table, rows Q4b/Q4c and I1–I3).**

- *With* the approver flag (every first run, and every run of an agent that ever had grounds), the
  harness writes `Warning: MCP server blocked by enterprise policy: agentweave` to stderr and exits
  1. The Hub shows it as text (`runner_parsing.py:238`) and does not act on it.
- *Without* the flag (1b's shape), the very first stdout line, before any model call, is the
  `system`/`init` message. Its `mcp_servers` list gives `agentweave` as `connected`, as `failed`, or
  **not at all** when policy blocks it. `mcp_server_errors` is also defined on that event, since
  **v2.1.219** (2026-07-24T17:14:23Z): *"Added `mcp_server_errors` to the headless stream-json init
  event, listing `--mcp-config` entries skipped by config validation."* It was `null` in all three
  probes. `parse_claude_line` has no `system` branch (`runner_parsing.py:244-364`), and `grep
  mcp_servers hub/hub` finds only Codex config-building code.

**The gap, in two cases the current signal gets wrong.**

1. **A policy arrives after the first success.** An operator's organisation pushes an MCP block,
   say `managedMcpServers`, which **v2.1.259** added and which *"skip[s]"* every entry *"that
   name[s] a command to run"*, as AgentWeave's stdio server does (`runner_commands.py:233-241`,
   `"type": "stdio"`). The agent's old run row keeps `harness_has_honoured_mcp` true, so 1b never
   fires for that agent. Every later run gets the approver flag and, on 2.1.269, fails at spawn,
   **permanently**, until someone deletes run history.
2. **The Hub's own server fails to start.** F329, fixed yesterday at `5bc00c9`, was a first start
   that *"builds a database no conversation can be written to"*, so failures of the Hub's own
   machinery are ordinary. On an agent with grounds, the harness says `failed` and the Hub hears
   nothing. The operator gets `Error: MCP tool … not found. Available MCP tools: none` and has to
   work out that the tool server is the Hub's.

**What a change would touch.** A `system`/`init` branch in `parse_claude_line` that reads the
`agentweave` entry. A per-run nullable column beside `mcp_adapter_online_at`, holding "harness
reported the server `failed` / absent". `harness_has_honoured_mcp` would then read the *latest*
run's report rather than *any* run's. On the approver-flag path, the one stderr line
`MCP server blocked by enterprise policy: <name>` would be recognised, so the Hub can turn it into
its own sentence naming the fix. That fix already exists: `hub_client: "cli"`, documented at
`src/agentweave/config.py:714` as *"uncomment if MCP is blocked by company policy"*.

**Why this is third, and not something to push into R1.** 1b says *"same signal, same grain, same
conservative direction"* (`DECISIONS.md:753-754`). A new signal is a new decision, and DIRECTION
says F299's R1 does the proposal, not the decision. File it as a finding today. It costs no queue
slot, and its evidence is the two tables in this file. The *"no negative form"* sentence is exactly
the kind of in-code claim the ledger exists to correct.

**What would make it a bad idea.** Parsing a harness's startup line and matching one of its stderr
sentences ties the Hub to two more vendor shapes it does not version. The `init` event has changed
before, gaining `mcp_server_errors` in 2.1.219 and `plugin_errors` later, and it is not a
documented contract. A `status` string the Hub does not recognise has to count as "no grounds",
never as "grounds". Also, "absent from `mcp_servers`" was measured with `--settings`, not a real
managed policy, which is the case that matters. That needs one run on a machine with real
managed settings before anything depends on it.
