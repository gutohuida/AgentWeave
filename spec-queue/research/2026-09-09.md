## The evidence

### 1. Put staffing behind the per-agent grant mechanism the product already built

**What exists elsewhere.** Two papers, both 2026-09-08, both arguing that authorization belongs at the
mutation boundary rather than in the model's context, and neither citing the other.

**CapScope** — *"Authority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant
Coding Agents"*, <https://arxiv.org/abs/2609.08371>, 2026-09-08T07:37:00Z. It names the failure as
**ambient authority**: *"Within the agent's sandbox, these tools often carry ambient authority: naming
a resource is sufficient to act on it."* Its mechanism is three moves — derive a task-wide authority
ceiling from **trusted input, before repository contents or tool output are read**; give each agent a
separate set of typed capabilities **stored outside the model's context**; check every tool call
against the capabilities of the agent that issued it. The evaluation is an orchestrator delegating to
sub-agents across five Python tasks, five injection surfaces, four authorization conditions, three
trials — **300 runs**. The injected effect executes in **33–47 of 75** runs under both the
ambient-authority and the **global-policy** baselines, and **3 of 75** under CapScope. Repair
completion is **68/75** against baselines of 68–72/75 — the defence is close to free.

The global-policy baseline is the one that matters here. One policy applied to every agent scores
essentially the same as no policy at all.

**Cross-substrate authority** — <https://arxiv.org/abs/2609.08472>, 2026-09-08T09:11:53Z, reaches the
same place from memory governance: *"Experiment 2 uses 96 planning calls: workspace-visible evidence
yields 12/16 unsafe publication decisions, and planning with the typed relation remains unreliable
(15/32 first actions correct)... Experiment 3 replays the same 32 fixed model-generated first-action
intents with zero additional model calls; a deterministic execution guard prevents all six unsafe
intents from becoming effects and permits all 12 valid authorized publish intents."* Telling the
planner more did not work. A guard at the mutation boundary worked completely, for free.

**What AgentWeave does today — and it is further along than either paper's baseline.** The `Agent` row
carries three capability flags, and the comments around them state CapScope's thesis in the product's
own words (`hub/hub/db/models.py`, the `Agent` class):

> *"These live on the Agent row and nowhere else. A charter is behaviour text the model reads; if it
> could widen access, then prose an agent can be persuaded to write would be an authorisation
> mechanism."*

and, on `can_accept_evidence`:

> *"deliberately not conferred by a charter... a charter says how an agent behaves, and behaviour is
> not authority."*

`can_read_checkpoints`, `can_recall` and `can_accept_evidence` are all `default=False,
server_default="0"`, enforced at `checkpoint_access.py:46,62` and `requirement_evidence.py:674`. This
is per-agent typed capability, held outside the model's context, checked at the effect. **The
mechanism exists and is correct.** The question is only what it covers.

**The gap: it covers three reads and one acceptance, and nothing that creates.** `get_agent_actor`
returns `AgentActor(project_id, agent, run_id)` (`agent_auth.py:23-27`) — identity, and no capability
set — and every one of the ~28 MCP tools and every `agent_actions.py` route is reachable by every
active run of every agent. Two instances are load-bearing:

**`request_agent` mints a peer, and the peer's posture is the template's, not the requester's.**
`agents.py:2023-2091`. The guards are real but they are all about *what* and *how many*, never *who*:
the template must exist in `ProjectSession.data["agents"]` (*"not pre-approved for this project"*),
the name must be free, and `len(existing_names) >= project_row.agent_budget` caps the roster. Then:

```python
copied_config = dict(template_config)
copied_config.pop("principal", None)
agent_row = Agent(..., config=copied_config, created_by_run_id=source_run.id)
```

The whole config is copied, one key removed. `config` is what the spawn path reads for `yolo`
(`agent_trigger.py:729`), `env_vars` (`:546`, `launchability.py:92,145`), `cli`
(`launchability.py:79`), `model` (`agent_trigger.py:685`) and `read_only` (`worktrees.py:217`). A run
under the default `workspace` posture cannot execute freely — but it can create a peer from a `yolo`
template and hand it a `task` of `min_length=1, max_length=100_000` (`agent_actions.py:165-169`),
whose first turn is queued immediately in the same call. **That is privilege escalation through the
roster, and it is exactly the sentence CapScope's per-agent split exists to make false.**

**`create_job` schedules recurring work against any peer, and only *stopping* it asks a person.**
`AgentJobCreate` (`agent_actions.py:172-188`) accepts `agent: str` — the agent to fire — and
`message: str = Field(max_length=10000)` — the prompt — plus a `cron`. `create_governed_job`
(`:743-755`) takes only `AgentActor` and consults no grant. The `create_loop` and `create_flow` MCP
tools post through this same schema (`agent_actions.py:179-182`). Meanwhile `archive_governed_job`
(`:788-810`) is the one route with an always-ask operator gate, imposed in `operator_direction.py` so
it reaches HTTP and MCP alike. **Creating unbounded recurring work is ungoverned; ending it is the
governed act.** That ordering is backwards on its own terms, before any injection is considered.

**Nothing in the ledger covers this.** `grep '^## F'` over all 306 findings returns no heading about
`request_agent`, template config, or job creation; the two raw mentions of `request_agent` in
`FINDINGS.md` (lines 544, 590) are about `contact_mode` and an unrelated conjunct. This is new ground.

**What a change would touch.** `Agent` gains grant columns in the shape of the three that exist — the
natural split is *may create agents* and *may create scheduled work*, both `default=False`; a
migration; the enforcement points at `agent_actions.py:730-755` and the `create_loop`/`create_flow`
adapters; the roster UI that already renders `GRANT_FIELDS` (`agents.py:2229-2239`); and one
`agent-capability-plane` requirement, which today says the agent API *"is a least-privilege
allowlist"* without saying the allowlist is the same for everyone. **`agent-capability-plane/spec.md`
already names both operations as *"governed agent requests, and governed scheduled-work mutations"* —
so the word is there and the mechanism behind it is the operator gate on one route, not a grant.**

**What would make it a bad idea.** Three things, and the third is the real one.

- The template list is genuinely an authority ceiling derived from trusted input — the operator writes
  `agentweave.yml` and the watchdog pushes it (`agents.py:123-133`). CapScope's first move is
  therefore already made. If every template in a project is narrow, the escalation has nowhere to go.
- `agent_budget` bounds the blast radius to a number the operator chose.
- **Closed-by-default breaks every existing roster.** The three shipped grants could default closed
  because they gate reads that agents rarely needed; staffing is how flows and loops are meant to
  work, and a migration that defaults these to `False` would silently stop working compositions.
  `agent-capability-plane` has a shipped scenario — *"New operator APIs are denied by default"* — but
  no precedent for **retracting** a capability agents already exercise. The migration has to decide
  between fail-closed and not breaking the product, and that decision is the change.

### 2. Record the build of the CLI that produced a run

**What exists elsewhere.** *"Scanning the Harness: An Empirical Study of Supply-Chain Defects in AI
Coding-Agent Configurations"*, <https://arxiv.org/abs/2609.07360>, 2026-09-07T11:27:24Z. 3,171 public
GitHub repositories; 2,660 setups assembling two or more component types; 511 published skill
collections. Every finding is validated three ways — an independent re-derivation at the pinned
commit, a model adjudicator on disagreements, a second model session re-checking every counted pair —
which is why the confirmed rate (**16.7%**) is well under the raw scanner rate (**25.5%**) and why the
numbers are worth quoting. Three security classes survive: **9.8%** install an MCP server with no
version pinned, **3.1%** pre-approve arbitrary execution behind a scoped-looking grant such as
`Bash(python:*)`, **3.8%** ship a skill that pre-approves the shell for whoever installs it. The frame
is the sentence to keep: the harness is *"a dependency layer ... with no lockfile, no install-time
check, and no vocabulary for what a component may do."*

**Two of the three classes are not AgentWeave's problem, and it is worth saying why.** Class 3 — a
component that pre-approves the shell for its installer — cannot happen through a charter, because the
product decided charters grant nothing and enforced that decision in the schema (see §1). Class 2 *is*
AgentWeave's problem, and it is §1: a template name is precisely a scoped-looking grant behind which
arbitrary execution can sit. **Class 1 is this candidate.**

**What AgentWeave does today.** A `Runner` is `id, project_id, name, cli, model, flags` with
`CheckConstraint("cli IN ('claude', 'codex')")` — *"which CLI, which model"*, and no version. The
binary is resolved at spawn from the ambient environment:

```python
resolved = shutil.which(cmd[0])          # pty_runner.py:126
```

`grep -rn "cli_version\|runner_version\|harness_version" hub/hub/ --include=*.py` returns **zero
hits**. AgentWeave does not read the CLI's `system`/`init` stream event either — `grep` for `"init"`
and `"system"` across the package finds only spec-lifecycle actor kinds and a log filter — so the
version is not arriving for free somewhere else and being discarded. It is simply never asked for.

**The gap, and why it costs this product more than most.** AgentWeave's bet is that the specification
and its evidence are the durable artefacts. `EvidenceFootprint` is built entirely around that: *"What
the implementation looked like when evidence was produced"* — the commit and the blob ids of every
changed path, with a content-hash fallback for non-repository projects, because *"a git-only first cut
would leave every non-repository project permanently unverifiable"* (`models.py:2477-2489`). That is a
careful, complete answer to **what the code was**. There is no answer at all to **what the harness
was**. A `verified` requirement names a commit, a model and an agent; three weeks later, when the
result does not reproduce, nothing on the row can distinguish *the code changed* from *the harness
changed under us*.

**Two numbers make this concrete today, both from this run.**

- Claude Code published **v2.1.263** (09-06), **v2.1.265** (09-08T20:37:31Z) and **v2.1.266**
  (09-08T23:55:14Z) in three days. v2.1.266's entire changelog is the undoing of v2.1.265: the
  `CLAUDE_CODE_USE_GATEWAY` variable *"began forcing Cloud-gateway sign-in on its own in 2.1.265, so
  configurations that set it alongside an API key, `apiKeyHelper`, or custom auth headers **failed
  every request** with 'Not signed in to the Cloud gateway'."* A Hub that ran turns inside that
  3h18m window would hold a set of uniformly failed runs and no record of why.
- **Measured on this machine, 2026-09-09**: the installed CLI is **`2.1.238`** — twenty-eight releases
  behind the current one. Every agent AgentWeave spawns here runs that build, and no row says so.

The repository's own ledger already pays this cost in the currency of retractions: `F290` is
`RETRACTED`, `F115` and `F188` are `RETIRED`, `F295` is *"half-retired"*, and `DIRECTION.md`'s D-2 for
2026-09-08 was literally *"did the F292 repair hold? re-run, do not assume."* A measurement you cannot
attribute is a measurement you have to take again.

**What a change would touch.** A nullable `cli_version` on `Run` (or on `JobRun` too); one capture at
spawn beside `resolve_executable`; a cache keyed on the resolved absolute path and its mtime, so the
subprocess runs once per binary rather than once per turn. **The cost is measured, not guessed:
`claude --version` returned in 0.216s on this machine.** Then the version travels to the two places
that need it: `EvidenceFootprint`, whose whole purpose is to say what produced this, and the run
detail the operator reads. `runner-registry/spec.md` has a shipped requirement — *"Launchability
reports the runner that would actually be spawned"* (`:187`) — which is the natural home: reporting
what *would* be spawned without its version is reporting half the answer.

**What would make it a bad idea.** `codex` and `claude` do not agree on how to be asked, and a
`--version` that hangs would hang a turn; the capture needs a timeout and must be non-fatal, which is
more care than the diff length suggests. A cached-by-mtime answer is stale exactly when an npm shim is
rewritten without a content change. And there is a real scope argument that the honest artefact is not
a version string but the whole resolved launch — flags, MCP config, posture — of which the version is
one field; a change that adds only the version may need redoing when that argument wins.

### 3. Say whether a `test_result` ran tests the same footprint wrote

**Carried from `research-2026-09-08.md` §1, which was written as a finding rather than a proposal
because the queue was frozen. The queue is not frozen, and the item now has a number.** One line of
restatement and the rest is new: the default evidence kind is a test run, and nothing anywhere asks
whether the producing run also authored the tests it ran.

**The new number.** *"ExecCritic: Learn to Test, Test to Improve for Coding Agents"*,
<https://arxiv.org/abs/2609.09133>, 2026-09-08T17:53:37Z. It isolates test provenance by holding the
repair agent fixed and swapping only where the tests came from, on SWE-bench Verified:

| Tests supplied to a fixed base Repair agent | Resolved rate |
|---|---|
| none (baseline) | **61.2%** |
| written by the base Test agent | **57.3%** |
| written by GPT-5.6-sol | **65.3%** |

**Weak-provenance tests are worse than no tests at all** — a 3.9-point loss against the baseline, and
an 8.0-point spread across provenance alone with everything else held constant. The stated mechanism
is AgentWeave's exposure in one sentence: *"Agent-generated tests can encode incomplete or incorrect
behavioral targets; when the same trajectory writes both the patch and the test, their errors can
agree and create false confidence."* ExecCritic's fix is structural, not statistical — *"The scaffold
separates test construction from source-code repair: a Test agent independently generates
repository-native tests, a **fail-closed harness qualifies and freezes them**, and a Repair agent
revises source code from their execution feedback without changing the tests."* Role-specific training
then takes the composed pair to 72.6%. Code at <https://github.com/MSR-Orchard/execcritic>.

This lands the day after Dan Luu's 80-runs-per-condition measurement
(<https://danluu.com/agentic-testing/>, 2026-09-08, 179 points on HN as of this run) which yesterday's
file read as its own §1 evidence. Two independent measurements, one controlled benchmark and one
controlled prompt study, published within sixteen hours, agreeing that an agent's own tests are the
weakest input to its own verification.

**What AgentWeave does today.** `record_evidence` defaults `kind="test_result"`
(`mcp_server.py:1341-1348`). Its docstring is already unusually honest about what the claim is worth —
*"A careful agent and a careless one report success in the same words with the same authority, so what
you record is a claim until somebody else decides on it"* — and `requirement-traceability` enforces
that at two levels: the agent's assertion is not the fact, and an agent cannot accept its own evidence
(`can_accept_evidence`, `requirement_evidence.py:674`; `task-lifecycle-governance/spec.md:219`, *"An
agent cannot approve the work it produced"*). **Neither reaches authorship.** A reviewer deciding on
an `awaiting` `test_result` is told a test passed and is not told the same run wrote the test.

**The gap is one derivation away from being closed, because the fact is already stored.**
`EvidenceFootprint.entries` (`models.py:2501`) is a JSON map of changed path → blob id for the
producing run, and `record_evidence` already returns the footprint and instructs the agent to read it.
The system therefore knows which paths that run touched. Intersecting that set with the paths the
`locator` names — or, more simply, with the test paths under the project's test roots — answers "did
this run author what it ran" without a single new write.

**What a change would touch.** A derived field on the evidence read model rather than a new column;
the reviewer surface where an `awaiting` row is decided; and one `requirement-traceability`
requirement, alongside the two that already refuse assertion and self-acceptance. Cost is S/M because
the derivation is easy and getting "which of these paths are tests" right in a language-agnostic way
is not.

**What would make it a bad idea.** The intersection is a heuristic wearing a fact's clothes: a run
that legitimately edits one test while running two hundred would be flagged, and a run that
regenerates a fixture would be flagged, and the reviewer learns to ignore the flag — which is worse
than not having it. The honest presentation is a count and a path list rather than a verdict, and if
the surface cannot carry that, the fact is better left unshown. Also worth noting against it:
`work_needs_evidence` and `evidence_governs` (`task_integration.py:376-383`) already make approval
refuse to merge on unaccepted evidence, so the reviewer is a real gate rather than a rubber stamp;
this candidate improves the reviewer's information, not the product's structure.

## What changed on earlier candidates

**2026-09-07 §1 — "fence the turn prompt" — got one vendor confirmation and one qualification, and the
qualification is more useful.** Claude Code **v2.1.265** (2026-09-08T20:37:31Z) shipped exactly that
defence for cross-authored content: *"Improved the Artifact tool's read of an artifact someone else
wrote: the summary now treats the page as **untrusted content** and flags embedded instructions rather
than relaying them."* Anthropic shipping content-marking for one agent reading another's artefact is
direct support for `format_turn_prompt` emitting unescaped peer content (`inbound_queue.py:98-122`).
**But CapScope, the same week, is an argument that this is the weaker layer**: its whole design is *"a
harness-level authorization mechanism that restricts tool use **without requiring the model to
identify malicious text**"*, and its result is that an injection may still cause an agent to *request*
an action — the request is simply blocked. Fencing reduces how often the model is fooled; capability
scoping bounds what a fooled model can do. **The two are complements and the ordering matters: §1 of
09-07 should not be built as a substitute for candidate 1 above, and if only one is built this
quarter, the capability boundary is the one that holds when the fence fails.**

**2026-09-08 §2 — "scrub the spawned run's environment by policy" — got a second vendor doing it.**
gemini-cli **v0.60.0-preview.0** (2026-09-08T21:04:17Z) shipped *"fix(extensions): prompt for consent
on environment changes and **sanitize runtime-altering environment variables**"* (PR #28863) alongside
*"fix(cli): isolate settings directory in sandbox containers"* (#29216). That release is almost
entirely a containment sweep — path boundary and symlink checks (#29170), NTFS 8.3 short-name
mitigation (#29116), RFC 9207 issuer identification in MCP OAuth (#29117), envelope metadata
provenance for untrusted tool outputs (#29215). Combined with Trail of Bits' `coop` trust model cited
yesterday, that is two independent implementations in two days treating the spawned process's
environment as an allowlist rather than a subtract-five-names list. **The candidate is unchanged; its
evidence base doubled.**

**2026-09-08 §3 — "pin the Hub credential to the endpoint's origin" — no change.** No new MCP Python
SDK release since v2.2.0/v1.30.0 on 2026-09-07.

## Also seen, not proposed

- **"The Unreliable Progress Bar"** (<https://arxiv.org/abs/2609.08589>, 2026-09-08) concludes *"agent
  frameworks should not control task flow on the strength of the model's state reports alone."*
  **Checked, and AgentWeave already satisfies it — this is a validation, not a gap, and the build
  window should not spend a day on it.** `_loop_stop_reason` ends a loop when no task on it is outside
  `TERMINAL_FOR_BINDING` (`scheduler.py:324-343`), and that set is `frozenset({"approved",
  "rejected"})` (`task_transition_service.py:628`) — not `completed`, which is where an agent's own
  report lands. Termination therefore waits on a governed transition by a different actor, under
  `task-lifecycle-governance`'s *"An agent cannot approve the work it produced"* (`:219`) and *"Some
  transitions are the operator's alone"* (`:117`). The paper's finding that the newest models *"grow
  conservative at the finish line"* is the residual risk here and it fails safe: a loop that never
  drains, not one that reports itself `completed` early.
- **Cache-token accounting** — considered as a candidate after Claude Code v2.1.265 shipped **two**
  prompt-cache-prefix fixes (resumed subagents changing their tool list; SubagentStart hook context
  moving out of the prefix), which is a vendor treating cache reuse as correctness-grade. Dropped:
  AgentWeave already stores `cache_read_tokens` and `cache_write_tokens` on both accounting rows
  (`models.py:1221-1222, 1808-1809`) and normalises them from the Codex side
  (`codex_appserver.py:321-329`). The related observation that a loop firing can never reuse a session
  (*"A loop job never resumes a conversation — task 8.1 refuses `session_mode='resume'` for one"*,
  `scheduler.py:355-358`) is a deliberate design decision with a stated reason, not a defect.
- **The shell-command workspace boundary** — `_decide` (`mcp_server.py:939-991`) reads only *absolute*
  paths out of a command, by the comment's own admission: *"Relative paths are left alone... This does
  not make shell escape impossible... and is a boundary, not a sandbox."* Not proposed: this is heavily
  driven ground already (F52, F115 retired, F230, F281, F282, F284, and F300 filed this morning), the
  concession is in the code rather than absent from it, and a new finding would duplicate F281's frame.
- **NTFS 8.3 short names** — probed after gemini-cli #29116. **Confirmed enabled on this machine's C:
  drive** (`dir /x` returns `AGENTW~1` for a directory created as `Agent Workspace`, 2026-09-09). Not
  proposed: AgentWeave resolves both sides with `os.path.realpath` and compares with `commonpath` +
  `normcase` (`workspace_writes.py:192-207`, `mcp_server.py:975-988`), and the escape direction a short
