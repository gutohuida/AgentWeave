## The evidence

### 1. Map the Codex app-server surface AgentWeave already answers

**What exists elsewhere, dated.** Codex `rust-v0.153.0` was published **2026-09-03T01:37:38Z**
(`gh api repos/openai/codex/releases/tags/rust-v0.153.0`). Under *Configuration and API Updates*:

> Structured asynchronous questions are supported through `request_user_input_async` when enabled
> by the model catalog. ([#42151](https://github.com/openai/codex/pull/42151),
> [#42178](https://github.com/openai/codex/pull/42178))

PR #42178, *"Add structured asynchronous user input requests"*, merged 2026-09-02T02:11:24Z
(<https://github.com/openai/codex/pull/42178>, read 2026-09-03):

> Replace `send_user_message_async` with `request_user_input_async`, accepting one or more
> questions with optional suggested answers **while allowing the turn to continue**.
> Attach structured question metadata to asynchronous agent messages **while retaining readable
> fallback text**, and preserve it through app-server events, thread history, and generated
> schemas.

**The shape matters more than the feature, and it is the reason this is a candidate rather than a
headline.** `request_user_input_async` does *not* add a new `ThreadItem` variant and does *not* add
a server→client request. It adds a **field to `agentMessage`**, an item AgentWeave already handles.
From the generated schema at the released tag
(<https://raw.githubusercontent.com/openai/codex/rust-v0.153.0/codex-rs/app-server-protocol/schema/typescript/v2/ThreadItem.ts>,
fetched 2026-09-03):

```ts
{ "type": "agentMessage", id: string, text: string, phase: MessagePhase | null,
  memoryCitation: MemoryCitation | null, delivery: AgentMessageDelivery | null,
  questions: Array<AsyncUserInputQuestion> | null }

export type AsyncUserInputQuestion = { title: string, options: Array<string> | null };
```

`AsyncUserInputQuestion` is **absent from 0.146.0** — the version every measurement in
`codex_appserver.py` is pinned to — and present in 0.153.0 (both `schema/typescript/v2/index.ts`
files fetched and compared: 531 exports at 0.146.0, 614 at 0.153.0).

**What AgentWeave does today.** `map_item_to_events` (`hub/hub/codex_appserver.py:390`) handles
`agentMessage` in five lines (`:406-410`):

```python
if item_type == "agentMessage":
    if is_start:
        return []
    text = str(item.get("text") or "").strip()
    return [text_event(text)] if text else []
```

`text` and nothing else. So on the next `codex` upgrade, a Codex agent that asks the operator a
structured question with suggested answers produces: the fallback sentence, as an ordinary
assistant message in the timeline; **no question record**, because AgentWeave's question route is
`ask_user` (`mcp_server.py:307`) and its `q-…` rows; **no answer affordance**, because the
Questions surface reads those rows; and **no stop**, because the tool is asynchronous by design and
the turn continues past it. The operator sees an agent musing aloud and the agent proceeds on its
own guess. Nothing errors. Nothing is refused. Nothing is logged.

**The gap is in the method, not in anyone's care.** This repository has already swept exactly this
file for exactly this class of problem and closed it correctly. **F104 (—)**
(`FINDINGS.md:6627`), *"ThreadItem's eleven unhandled variants: swept live, none of them occur"*,
is a model negative result — one live turn traced every notification, delivered five item types,
zero unhandled, and its stated lesson is worth quoting because it is right:

> a protocol you have checked back tells you what **can** arrive, never what **does**. The
> generated schema is the cheap way to build a candidate list; only driving the product ranks it.

F104's unit of sweep was the **variant**. `questions` is a **field on a handled variant**, so
F104's method cannot see it, and neither can a re-run of F104's probe on 0.146.0, where the field
does not exist. This is not a counterexample to F104's lesson — it is the second half of it: a
handled branch that reads one key out of an item is a silent truncation point, and the sweep that
enumerates types will report it as covered.

**And the re-drive trigger is already written down, by this repository, in advance.** F106 (—)
(`FINDINGS.md:6769`), which established that `ask_user` drives clean end to end on Codex, closes:

> **The mechanism that makes this stay closed:** … There is no Codex-side branch in the question
> path to be wrong. **Re-drive this only if the transport itself changes.**

The transport just changed, and it changed *by growing a second question path* — one that does not
go through `ask_user`, and therefore is not covered by the sentence that made F106 safe to close.
That is as clean a trigger as this corpus gets.

**The second half: what else is on that surface.** While checking whether `questions` was new, I

present in **both** — `GuardianWarningNotification`,
`ItemGuardianApprovalReviewStartedNotification`, `ItemGuardianApprovalReviewCompletedNotification`,

**The third half, which is why this is one item and not three: the Hub cannot say which protocol

> `codex app-server` is `[experimental]`… **Method names, `_meta` keys, and approval shapes can
> change without a major version.**

On this transport the CLI version *is* the protocol version. The runner-CLI-version item has now
been proposed three days running on a security argument (a stale `claude` predating permission

or beside any accepted evidence.

**What a change would touch.** Three separable pieces, smallest first:

1. **Read `questions` off `agentMessage`.** Either render it as a distinct timeline event, or —
   better, and the reason to think about it before it arrives — route it into the existing question
   record so the operator answers it on the page built for that. Note the shapes are not
   equivalent: `AsyncUserInputQuestion` is `{title, options: string[]}`, while `ask_user`'s
   question carries `header`, `question`, `options: [{label, description}]` and `multi_select`.
   AgentWeave's is strictly richer, so the mapping is lossless in the direction that matters.
   `map_item_to_events`, plus wherever the question row is created.
2. **Record the runner CLI version on the run.** `runner_commands.py`, the run model, one
   migration, the diagnostics surface. Composes with F115's recording work.
3. **Probe Guardian.** A drive-window task, not a spec: run a Codex turn under `workspace` posture
   with a command Guardian would score, and trace every notification the way F104's probe did.
   Outcome is a finding either way, including a negative one.

**What would make it a bad idea.** Piece 1 builds against a feature that is **gated** — the release
note says "when enabled by the model catalog" — on a CLI this machine does not have, for a
transport its own module calls `[experimental]`. Every one of yesterday's arguments about writing
code against an unread snapshot applies here in reverse, and F104's lesson cuts directly against
building a branch for something never observed to arrive. The honest scoping is: piece 1 is worth
doing only if the drive in piece 3 upgrades `codex` and *sees* a `questions` field, and the
proposal should say that. Piece 2 stands regardless and is the part that survives being wrong about
everything else — it is what makes the next version-shift a lookup instead of an investigation.

### 2. Read relative paths at the workspace boundary

**What exists elsewhere, dated.** Claude Code **v2.1.259**, published **2026-09-02T22:33:51Z**
(`gh api repos/anthropics/claude-code/releases/tags/v2.1.259`):

> Fixed Bash `Read()` deny rules not covering files given as option values
> (`--ignore-revs-file=.env`, `-f.env`, `@file`), `git diff`/`git grep` file operands, or
> **`cd DIR && cat FILE` compounds**; `grep -r`/`cp -r` over a directory holding a denied file now
> asks

That is a mature harness team, on a matcher that has shipped for a year, finding four distinct ways
a path reaches a shell command without being seen by the checker in front of it. Three of the four
are about *where in the command string* the path appears. The fourth — the `cd` compound — is about
the command changing the ground the check stands on.

**What AgentWeave does today, and it is a good design with one wrong sentence in it.** The Hub is
the approver under the `workspace` posture, so `_decide` (`hub/hub/mcp_server.py:901`) is the
boundary for Bash. It collects candidate paths two ways: declared keys (`file_path`, `path`,
`notebook_path`, `:895`) and, for a shell command, a regex over the command text
(`_ABSOLUTE_PATH_RE`, `:898`, applied at `:935`). Every candidate is then `realpath`'d and compared
by `os.path.commonpath` against the resolved workspace root — a genuinely correct containment
check, immune to the `/work-other` string-prefix trap, with `..` and symlinks collapsed first. The
comparison is not the problem. What reaches it is.

The regex matches absolute paths only. The comment says why (`:930-933`):

> Relative paths are left alone: **they resolve against the run's cwd, which is the workspace.**
> This does not make shell escape impossible -- a command can still build a path at runtime -- and
> is a boundary, not a sandbox.

The second sentence is an honest, correctly-scoped limitation and it stands. The first sentence is
the justification, and a `cd` in the same command falsifies it: after `cd ../../..` the run's cwd
is no longer the workspace, and every relative path in the rest of the command resolves somewhere
else. `cd ../../.. && cat some-file` contains no absolute path, so `candidates` from the command is
empty and `_decide` returns `{"allow": True, "reason": "inside your workspace"}` — the reason
string asserting the exact thing the command just stopped being true. This is not "a command
building a path at runtime"; it is the plainest form of the problem, it is one of the four cases
Claude Code fixed yesterday, and it is a shell idiom that a routine on this very machine has a
standing rule against for the same mechanical reason.

**The gap, and where it belongs.** This is not a new finding so much as a second mechanism for one
already open: **F115 (B?)** (`FINDINGS.md:7646`), *"the agent worktree is a working directory, not
a boundary: an absolute path writes straight into the operator's checkout"* — status *"open,
severity is the operator's call."* F115's reproduction used an absolute path. The relative-plus-`cd`
route reaches the same place with the check nominally engaged, which is worse for the operator's
severity judgement than the absolute case: there, the boundary refuses and the agent knows;
here, the boundary approves and records the approval as containment. Since the severity call is
explicitly waiting on the operator, this is the input that should reach them.

**What a change would touch.** Small and self-contained. `_decide` is pure and total and already
has a table-driven test surface. Two options, and the first is what I would argue for:

1. **Detect the cwd-changing prefix and deny.** If the command contains a `cd` (or `pushd`) whose
   target is not inside the workspace — or simply any `cd` at all, since a run already starts in
   its workspace and has no legitimate need to leave it — deny with a reason that names it.
   Refusing an idiom is cheaper and far more legible than modelling shell semantics.
2. **Resolve relative candidates too**, which means parsing enough of the command to know which
   tokens are paths — the road Claude Code went down, and the one that took four separate fixes.

Either way, update the comment: the current justification is load-bearing prose that is not true,
and a future reader will trust it.

**What would make it a bad idea.** Option 1 will refuse legitimate commands — `cd hub && pytest`
is inside the workspace and entirely reasonable, so a blanket `cd` denial is wrong and the check
must resolve the target. Option 2 is an arms race the release note above is direct evidence of:
four fixes on one matcher in one release, and the next command shape is always cheaper to invent
than to parse. The strongest counter-argument is the module's own: this is a boundary, not a
sandbox, and the durable answer is the sandbox (worktrees plus F115's recording), not a better
regex. That is fair, and it argues for scope — fix the `cd` case, name the limit, do not attempt
the general one — rather than for doing nothing.

### 3. `--permission-prompts none` for the run with no approver

**What exists elsewhere, dated.** Also Claude Code **v2.1.259** (2026-09-02T22:33:51Z):

> Added `--permission-prompts none` for unattended headless hosts: anything that would prompt is
> denied automatically while the active permission mode (including auto mode) keeps deciding

**What AgentWeave does today.** `runner_commands.py` has two default postures. With the Hub's MCP
server configured, the run gets `--permission-mode manual` plus
`--permission-prompt-tool mcp__agentweave__approve_tool_call` — the Hub answers, and this is the
good path. Without it, the fallback is `acceptEdits` (`:73`), justified thus:

> `workspace` *is* `manual` plus an answerer… without it, defaulting to `workspace` would name an
> approver that is not there and refuse everything… **A run that cannot be answered gets the
> posture that needs no answering.**

The same module's header docstring records that this is not quite so (`:22-28`):

> It was `acceptEdits` until 2026-08-13, which fixed writing and left executing broken for the same
> reason: **`acceptEdits` still prompts for `Bash`**, so an agent could write code and never run it.

Both statements are in one file. The fallback path is the state the product deliberately moved
*away from* on 2026-08-13, retained as the lesser evil because there was no third option. As of
yesterday there is one: `--permission-prompts none` makes "needs no answering" literally true —
`acceptEdits` keeps accepting edits, and the `Bash` prompt that has nothing to answer it becomes an
immediate deny with a decision behind it rather than an unanswerable prompt.

**The gap, honestly bounded.** I did not measure what happens on that path today — no run was
started, and the claim above rests on reading `runner_commands.py` and its own recorded history,
not on observation. What is certain is that the flag exists as of 2026-09-02, that it addresses
precisely the situation the fallback comment describes, and that the installed CLI here (2.1.238)
does not have it.

**What a change would touch.** One conditional in `_build_claude_command` and its test:
emit `--permission-prompts none` when `mcp_command` is absent and yolo is not set. Also worth
saying out loud in the same breath, since it is the operator's decision and not a defect: with the
approver present, this flag is redundant, and adding it there would be a second mechanism competing
with `_decide` for the same job.

**What would make it a bad idea.** It is a flag that does not exist on the CLI this machine runs,
so shipping it unconditionally breaks every 2.1.238 spawn with an unknown-argument error — which
makes this item *depend on* candidate 1's piece 2, and is the cleanest available argument for why
recording the runner version is not bookkeeping. Second, it is small enough to be busywork: nothing
in the corpus reports the no-approver fallback biting anyone, because the Hub's server is
configured on every path the product actually drives. Rank it third and treat it as a
one-line change to make when the CLI is next bumped, not as a slot of its own.

## Also seen, not proposed

- **arXiv 2609.01992, ClaimReceipt** (2026-09-02, <https://arxiv.org/abs/2609.01992>). Splits agent
  evidence into two questions AgentWeave's model conflates nowhere: **sufficiency** (is a claim
  recomputable from what was retained?) and **coverage** (do the retained records span the
  committed experiment set?), with a three-valued verdict — `PASS` / `INVALID` /
  `INCONCLUSIVE_COVERAGE` — so that an omission is visible rather than absent. On 1,392 historical
  records the verifier reproduced all five manual audit verdicts and returned the expected result
  on 11/11 semantic faults with 0/8 false positives; instrumentation cost 0.021% of inference time
  and 9.9 KB per transaction. **Not proposed, and the reason is a compliment to the repo:**
  `openspec/specs/requirement-traceability/spec.md:204-254` already mandates a single coverage
  definition used by every surface, already ranks evidence by precedence, already refuses to let
  integration be a coverage state, and already has a state for "the evidence no longer applies".
  The one idea with no analogue is the *committed universe* — a manifest fixed before the work,
  against which a missing record is itself a finding — and that is a research direction for the
  spec flow, not a change. Worth re-reading whoever writes the next evidence exploration.
- **arXiv 2609.02246, "LLM-as-a-Judge Is Not an Oracle"** (2026-09-02,
  <https://arxiv.org/abs/2609.02246>). A production report, months of autonomous prompt-optimisation
  loops, eleven catalogued ways the evaluation signal failed. Two numbers transfer: agents scored
