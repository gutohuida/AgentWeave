### 1. Give the Codex adapter a version floor it checks, not a version it remembers in a comment

**What happened elsewhere, yesterday.** `openai/codex` published **`rust-v0.154.0`**,
<https://github.com/openai/codex/releases/tag/rust-v0.154.0>, 2026-09-09T22:35:38Z. It is the first
non-alpha tag in that line — this routine has reported `alpha.6` through `alpha.11` across four days,
every one of them with a release body that was the bare string `"Release 0.154.0-alpha.N"`. The GA
body is 19,881 bytes and has sections. Three of its entries land on AgentWeave's seam:

- **`## Chores` — *"The deprecated `codex mcp-server` entry point is no longer available."*** (#42993).
  This is the load-bearing one, and not because AgentWeave uses it: `grep -rn 'mcp-server'` across
  `hub/hub/` finds exactly one hit and it is a prose comment (`agent_trigger.py:2545`). It matters
  because it establishes that **OpenAI now removes surfaces at a GA cut**, which is the class of
  change a version-blind adapter cannot survive.
- *"Experimental worktree support lets you create isolated checkouts for new or forked sessions using
  `--worktree` or `/worktree`, then browse and resume them."* (#42652, #43069, #43120, #43286). The
  runner now has its own worktree manager, in a product that has one (`hub/hub/worktrees.py`,
  `openspec/explorations/2026-08-27-per-task-worktrees.md`). A `Runner`'s `flags` are free-form.
- *"Automatic approval reviews better preserve authorization context through compaction and **reject
  approvals invalidated by new user instructions or answers**."* (#42844, #42852, #43442).

**What AgentWeave does today.** `hub/hub/codex_appserver.py` is unusually honest about where its
knowledge comes from, and that honesty is what makes the gap visible. Line 14:

> *"Every shape below was measured against a live `codex app-server` (CLI 0.146.0, Windows), not
> [assumed]"*

Line 24 records the caveat the module was written under — *"`codex app-server` is `[experimental]`;
keep exec alive until this is proven equivalent"* — and line 58 records that the caveat has since been
overtaken: *"app-server is now the DEFAULT for codex, not an opt-in"*, with `--no-app-server` as the
opt-out (`:73`). Five further sites pin specific structures to that same build: the JSON schema was
taken from `codex app-server generate-json-schema` at 0.146.0 (`:91`), `FileChangeRequestApprovalParams`
has *"exactly `itemId`, `startedAtMs`, `threadId`"* (`:131`), an error shape was *"Measured live
2026-08-28 against CLI 0.146.0 (F100)"* (`:1128`), the `ServerNotification` schema *"of CLI 0.146.0 …
has exactly `turn/started`"* (`:1144`), and the item taxonomy at `:1185`. `hub/hub/worker.py:18` says
the same of the `exec` fallback: assumptions verified against *"`codex-cli` 0.146.0 rather than
assumed, and each one is load-bearing."*

**The gap is that every one of those is a comment.** The binary is resolved from the ambient
environment at spawn (`pty_runner.py:126`, `shutil.which`), `AppServerProcess.spawn`
(`codex_appserver.py:703-716`) execs whatever that returned, and nothing compares it to 0.146.0. There
is no `MIN_CODEX_VERSION`, no floor, no warning: `grep -rn "0\.14\|MIN_.*VERSION"` across `hub/hub/`
returns only the prose above. `src/agentweave/diagnostics.py:166` has `check_python_version` and no
counterpart for the runner the product's whole value depends on.

**Two measurements from this machine, today.**

| binary | installed | current | gap |
|---|---|---|---|
| `codex` | **`codex-cli 0.146.0`**, 0.249s | `0.154.0` (GA, 2026-09-09) | 8 minor versions |
| `claude` | **`2.1.238`**, 0.209s | `2.1.267` (2026-09-09T19:58:14Z) | 29 releases |

The codex row is the whole argument in one line: **the installed build is exactly the one the protocol
was measured against, and the only reason is that nobody upgraded.** The next installer refresh on any
operator's machine moves it eight versions across a GA boundary that removed an entry point, and the
Hub's behaviour on that day is undefined and unannounced. `claude`'s row says the same thing about the
other runner with a larger number.

**This subsumes yesterday's candidate 2 and sharpens it.** That item asked for a nullable
`cli_version` on `Run`, for evidence attribution. This one asks for the same capture plus a comparison
— the recorded string is worth having, but the actionable half is a *floor* the diagnostics surface can
report against. Yesterday's own objection against itself, *"the honest artefact is not a version string
but the whole resolved launch"*, is partly answered: the launch's other axes are already captured.
`models.py:432` stores per-turn controls — *"Control id -> value (e.g. `{"model": "claude-opus-5",
"effort": "high"}`)"* — validated against the model catalog (`agent_trigger.py:187`), and
`model_catalog.py:12` documents where `--model` and `--effort`'s accepted values come from. **Model and
effort are recorded; only the build that interpreted them is not.**

**A vendor shipped exactly this, in the same release.** Codex 0.154.0's changelog line #42270 is
*"Report the exec-server release version in environment info."* A harness reporting its own component's
build into the record it hands downstream is the move this candidate asks for, published by one of the
two runners AgentWeave supports, on the day the ask was already open.

**What a change would touch.** A `MIN_CODEX_VERSION` / `MIN_CLAUDE_VERSION` constant beside the shapes
they justify; one capture at `resolve_executable`, cached on resolved path + mtime; a diagnostic in
`runtime-diagnostics` and in `agentweave doctor`; and a nullable `cli_version` on `Run` so the
attribution half lands too. `runner-registry/spec.md:187` — *"Launchability reports the runner that
would actually be spawned"* — remains the natural home.

**What would make it a bad idea.** A floor that refuses is worse than one that warns: an operator on a
newer, fine build must not be locked out, so the only safe first version is advisory, which is also the
version easiest to ignore. `codex --version` and `claude --version` do not agree on output shape and a
hang would hang a turn, so the capture needs a timeout and must be non-fatal — more care than the diff
suggests. Version strings are a weak proxy for protocol compatibility: the module itself names the
better instrument, `codex app-server generate-json-schema`, and a floor on the version number is the
cheap approximation of running that. And there is a real argument that AgentWeave should track the
`app-server` schema rather than the version, in which case this change is a stepping stone that gets
replaced.

### 2. Move the loop stop-condition refusal out of the tool and into the contract

**What AgentWeave promises the model.** `create_loop`'s docstring, `hub/hub/mcp_server.py:657`:

> *"Refused outright with no stop condition: a loop that cannot stop is not created"*

and the refusal that backs it, `:683-689`, raised **before any HTTP request is made**:

```python
if stop_at is None and not stop_when_queue_empties:
    raise HubAPIError(400, "a loop needs a stop condition: supply stop_at or "
                      "stop_when_queue_empties=True", "POST", "/jobs")
```

`create_flow` holds the identical check at `:772`.

**What the contract underneath accepts.** `POST /agent/jobs` takes `AgentJobCreate`
(`agent_actions.py:171-187`), whose comment states the design intent plainly — *"Mirrors `JobCreate`'s
loop-opt-in fields … so a field present there but not here silently drops on the agent path — this is
what `create_loop` (MCP-only, `mcp_server.py`) posts through."* It carries `purpose`, `stop_at`,
`stop_when_queue_empties`, `work_needs_evidence`, `spec_document_id`, `initial_tasks`.
`create_governed_job` (`:744-757`) does one thing: `JobCreate(**body.model_dump(), source="hub")`, then
`create_job`. There is no stop-condition check anywhere below it. `jobs.py:104-106`:

```python
def _loop_opts_in(purpose, stop_at, stop_when_queue_empties) -> bool:
    return purpose is not None or stop_at is not None or stop_when_queue_empties is True
```

and at `:668-680` a `Loop` row is constructed with `stop_at=body.stop_at,
stop_when_queue_empties=body.stop_when_queue_empties` — both permitted to be the falsy default.
**`{"name": ..., "agent": ..., "message": ..., "cron": ..., "purpose": "x"}` creates a loop with
neither stop condition**, and `agent-loops/spec.md:142-145` states what that loop then does, as a
shipped scenario: *"A loop with no stop condition never stops itself … its firings are never skipped
for a stop-condition reason."*

**This is a named violation, not an inference.** `agent-capability-plane/spec.md:109`, under
*"HTTP and MCP access have equal capability"*:

> *"Direct HTTP SHALL be the application contract. MCP SHALL be a thin adapter over that contract with
> the same operations, validation, governance, attribution, and typed failure meaning. An adapter
> MUST NOT duplicate queue, budget, identity, or lifecycle business rules, **MUST NOT hold a governance
> or waiting rule that the contract does not itself impose on every caller**, and MUST NOT silently
> convert failures into empty or successful results."*

A stop condition is a lifecycle business rule. The adapter holds it; the contract does not impose it.
The same requirement's reasoning at `:111-113` names the reason two adapters exist — *"some environments
forbid MCP servers while still allowing ordinary local API calls"* — which is the precise case where the
weaker surface is the one in use. And AgentWeave has just shipped the capability that makes that case
ordinary: `agent-capability-plane` gained the `cli` access path this week (`F301`, `3a1e6bc`,
`45ebf58`), whose entire purpose is a run reaching these routes without MCP.

**Why now, from outside.** *"If It's Not Buggy, Don't Fix It: On the Dynamics of Iterative Bug-fixing
with LLMs"*, <https://arxiv.org/abs/2609.10123>, 2026-09-09T13:00:47Z. Across multiple models and
repair environments it finds that LLMs *"consistently claim to detect bugs in entirely bug-free
programs while the rate of repair of buggy programs is less than that of the damage to correct
programs"*, and — the sentence for this candidate — that iterating *"frequently reaches a
pseudo-bug-fixing cycle where the same changes are added and removed again ad infinitum."* Mechanistic
probing finds *"a steering vector which controls the editing propensity"*, which the authors read as an
internal representation of "buggy code" being falsely activated. The paper's own framing of what it is
for is *"stopping conditions under ambiguous goals."* A recurring job whose message is a standing
instruction and whose stop condition is absent is that setting exactly.

**Give the product its due on the adjacent risk, because it closed it.** My first reading was that a
loop's own agent could defer `stop_when_queue_empties` forever by adding one task per firing. It cannot:
`agent-loops/spec.md:313` is a shipped requirement — *"A self-created loop's queue accepts additions
from its creator only until its first fire"* — enforced in `_authorize_loop_task_creation`
(`tasks.py:601-660`), whose D10 note explains that control defaults to the operator so *"a self-created
loop whose control was never delegated still needs the operator once it has fired."* After an explicit
`POST /loops/{id}/control` delegation the creator decides for itself again, which is the operator
knowingly handing over the brake. **The queue-emptiness condition is agent-proof by default.** The hole
is not in the conditions; it is that a loop can be created with none of them through the route the
product designates as its contract.

**What a change would touch.** Move the check from `mcp_server.py:683-689` and `:772` into `create_job`
in `jobs.py`, beside `_loop_opts_in` — where the same 400 reaches HTTP, MCP and the `cli` access path
alike; leave a thin client-side pre-check only if the tool's error text is worth keeping. One decision
has to be made deliberately: **does the operator's own `POST /jobs` get the same refusal?**
`agent-loops/spec.md:142-145` currently guarantees the stop-condition-less loop exists, so tightening
the contract means editing a shipped scenario, and the honest options are (a) refuse for every caller and
retire that scenario, or (b) refuse only on the agent plane and say so in `agent-capability-plane`, which
is a documented asymmetry rather than a silent one.

**What would make it a bad idea.** Option (a) is a behaviour change to a shipped, specified guarantee,
and `DECISIONS.md`'s `D-7` — quoted in `APPROVALS.md` as still OPEN and grouping response-shape changes
as ones *"no window took unattended"* — is the kind of gate this would want. A purpose-only loop is also
a legitimate shape: a monitoring job that should run until an operator stops it is not a defect, and the
`cron` plus `AIJob.enabled` already bound it. And the realistic harm here is bounded by things that
already work — `agent_budget`, the operator-only archive gate (`agent_actions.py:794-810`), and the
`ending_state` refusal that closes a stopped loop's queue to every caller including the operator
(`tasks.py:645-660`). This is a promise-versus-contract defect first and a runaway-loop defect second,
and it should be argued as the former.

### 3. Let a reviewer re-run the thing the evidence names

**What exists elsewhere.** *"Introducing Consort: A Spec-First Agent Framework for Enforced,
Test-Driven Development on Live Database Branches"*, <https://arxiv.org/abs/2609.09671>,
2026-09-09T03:38:38Z. Read it for its taxonomy, not its results — see the caveat below. It opens with a
sentence that is AgentWeave's premise in someone else's words — *"When an agent writes code, the
development framework becomes the control system for a non-deterministic worker"* — then names the
field: *"the installable ones, GitHub Spec Kit, obra/superpowers, BMAD, and GSD, and our own, all
capture intent through a specification or durable planning artifacts. Since they agree on capturing
intent up front, what separates them is how each enforces the engineering discipline."* Three modes:

1. **by persuasion** — *"prompt discipline the model may ignore"*
2. **by front-loaded structure** — *"strong specs, then a trusted build"*
3. **through controls the agent cannot edit** — *"a deterministic orchestrator, human-approved gates,
   immutable tests, and a green result that must pass against a live, branched database"*

**AgentWeave is in mode 3 on authority, and it is not close.** Worth stating because the frame invites
the question and the answer is a good one. `submit_spec_document` at `contract` or `gate` rigor does not
write: *"your submission is diffed against what is stored and recorded as one pending proposal per
changed requirement plus one for everything else, for an operator to accept or reject"*
(`mcp_server.py:1213-1218`). The Hub mints requirement identifiers and *"An agent-supplied identifier is
not honoured"* (`spec-document-authority/spec.md:122`). *"Approval is the operator's decision and no
agent can express it"* (`:159`). Consort's "immutable tests" has a direct analogue already shipped:
*"Evidence against an older wording is not verification"* (`requirement-traceability/spec.md:236`),
backed by a stored per-requirement text digest (`spec-document-authority/spec.md:248`). Charters confer
nothing; capability lives on the `Agent` row.

**The one place AgentWeave is in mode 1 is the green itself.** `record_evidence` says so in its own
voice (`mcp_server.py:1358-1360`): *"Evidence enters `awaiting`, never `accepted`. A careful agent and a
careless one report success in the same words with the same authority, so what you record is a claim
until somebody else decides on it."* Every value in `EVIDENCE_KINDS` (`models.py:2355-2362`) — the list's
own comment is *"Open at the edges on purpose"* — names a thing an agent asserts: `test_result`,
`screenshot`, `artifact_diff`, `review_record`, `manual_observation`, `external_reference`. And
`locator` is documented as *"Where the artifact lives, if it has one — a path, **a command**, a run id"*
(`mcp_server.py:1367`).

**Measured, not assumed: the Hub never runs it.** `grep -rn "subprocess\.\|create_subprocess\|Popen"`
across `hub/hub/` returns four callers and no fifth: the runner itself (`pty_runner.py:351`,
`codex_appserver.py:710`), `git` (`requirement_evidence.py:477`, `:602` — `_git`, with a 15s timeout, for
the footprint), the conversation titler (`conversation_titles.py:97`), and the native approval dialog
(`native_dialog.py:145`). The Hub will shell out to compute *which commit* an evidence row describes and
will not shell out to find out whether the command that row names still exits zero.

**The gap, stated as the reviewer's problem.** An operator deciding an `awaiting` `test_result` is shown
a summary an agent wrote, a `locator` that may be a runnable command, and a footprint. To check it, they
leave the product. This is the same exposure yesterday's §3 named from the authorship side — ExecCritic
(<https://arxiv.org/abs/2609.09133>, 2026-09-08) prices self-authored tests at **57.3% against a 61.2%
no-test baseline** on SWE-bench Verified, and its scaffold's answer is *"a **fail-closed harness**
qualifies and freezes them"* — a harness AgentWeave has no place to put, because it runs nothing.

**What a change would touch.** The smallest honest version is operator-initiated and records rather than
decides: a re-run action on the evidence review surface that executes the `locator` in the run's recorded
workspace, with a timeout, and writes exit code + head/tail of output as a **Hub-authored** row. That row
would be the first evidence in the system whose actor is not an agent or an operator, which is the point
— and it is also the reason this is M and not S: `EVIDENCE_KINDS`, the `actor` field, and
`requirement-traceability`'s *"Evidence names what produced it and what it was produced against"*
(`:117`) all currently assume one of those two produced it.

**What would make it a bad idea, and one of these is close to disqualifying.**

- **Consort has no results.** Its own abstract ends *"claims we frame as a pre-registered, testable
  hypothesis."* It supplies a taxonomy and a competitor census, not a measurement, and this file's
  standing rule is that a candidate rests on evidence rather than agreement. The measured half of the
  argument is ExecCritic's, and ExecCritic is yesterday's item.
- **Executing an agent-supplied string from a review surface is a new and serious surface.** The command
  was written by the run under review. `_decide`'s own comment already concedes what the shell boundary
  is worth — *"This does not make shell escape impossible… and is a boundary, not a sandbox"*
  (`mcp_server.py:939-991`) — and this would put a click behind it.
- **It moves the Hub across a line it has held on purpose.** The Hub owns execution *of agents*, not of
  projects; it has no notion of a project's toolchain, and "run the tests" is language-, framework- and
  environment-specific in a way `EvidenceFootprint`'s content-hash fallback was written precisely to
  avoid needing.
- A re-run that fails for environmental reasons and is shown next to an agent's green is a worse
  reviewer surface than no re-run, for the same reason yesterday's §3 gave: the reviewer learns to ignore
  it.
