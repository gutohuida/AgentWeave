## The evidence

### 1. An unattended run has no operator to time out against

**What exists elsewhere, dated.** Claude Code **v2.1.260** was published **2026-09-03T23:48:12Z**
(`gh api repos/anthropics/claude-code/releases/tags/v2.1.260`, read 2026-09-04). Under *Changed*:

> Changed self-hosted runner `--kill-session-after-min` to release a session that is only waiting on
> its user (paused, resumable on the next message) instead of killing it and reporting a failure.

One line, and it is a position: **a session waiting on a human is not a stuck session.** The wall
clock that governs a working session does not govern a waiting one, and the correct terminal state
for a wait nobody answered is *paused and resumable*, not *ended with a verdict*.

**What AgentWeave does today, and it is not an accident.** The opposite, deliberately, and recently:

- `hub/hub/mcp_server.py:891` — `QUESTION_ANSWER_TIMEOUT = _configured_wait("AW_QUESTION_TIMEOUT", 240)`.
- `hub/hub/api/v1/agents.py:1784-1786` — `MIN_WAITING_SECONDS = 10`, `MAX_WAITING_SECONDS = 600`. Ten
  minutes is the ceiling an operator can configure, and 4 minutes is the default.
- `hub/hub/mcp_server.py:363-366`, the rationale in the code:

  > *Waiting is the point: an agent that asks and carries on regardless has guessed… The wait is
  > bounded for the same reason the permission approver's is — a turn suspended forever is worse
  > than one told nobody replied.*

- `hub/hub/mcp_server.py:463-468`, what the agent is told at expiry:

  > *"N of M question(s) went unanswered within 240s."* … *"Continue as best you can and say plainly
  > which decisions you made without an answer."*

- `hub/hub/api/v1/agent_actions.py:664-666` — on expiry, `question.wait_ended_at = now` and
  `release_block_for_expired_wait(...)`: the task that was parked on the question is **unparked** and
  goes back to `in_progress`.

This is not an oversight and the file should say so plainly. **F14 and F60 are both FIXED
(2026-08-30, `a-task-waits-while-its-run-waits`, three spec rounds and eleven implementation
groups)** — `FINDINGS.md:528` and `:3301`. That change is precisely the engineering of the current
behaviour: the task parks *as the question is asked*, the wait's deadline is stamped Hub-side so an
expiry is a report of a fact rather than a lever, the report releases the park, the run's end sweeps
what the report missed, and the task then carries `proceeded_without_answer_reason` **permanently**,
so that an operator answering five minutes late cannot erase the record that a decision was taken
without them. The operator-side string was built too: `FINDINGS.md:10727-10731` records
`QuestionsPanel.tsx:22-26,52-64,150-151` dropping the row out of the red *"Blocking — agents are
waiting for your answer"* banner and stamping it *"The run that asked this has ended. Answering now
would reach it as a new message, not as the answer it was waiting for."*

**The gap is not that AgentWeave forgot. It is that the decision was made for a watched run.** Every
sentence of the rationale above assumes an operator who is present and might be slow. Under that
assumption "a turn suspended forever is worse than one told nobody replied" is obviously right.

AgentWeave's own product runs overnight loops. This repository's night window fired twenty-four times
last night. In that setting the 240-second wait is not a wait: it is a fixed delay in front of a
guess, against an operator who is asleep and who could not have answered under any timeout this
product permits, because the ceiling is ten minutes. The bet — *the operator stays in the loop at the
decisions that matter* — holds for four minutes by default and cannot be configured to hold for
eleven.

And the two mechanisms already in the spec are in tension. `agent-capability-plane/spec.md:248-256`
requires that where the asking run *"is no longer waiting — it expired, ended…"*, the operator's
answers reach the agent later as **one delivery for the batch**. So the shipped design is: tell the
agent to commit, then hand it the real answer afterwards. For a watched run that is a good recovery
path. For an unattended one it is the normal path, and it means the answer arrives after the code
that needed it has shipped.

**The change, at its smallest.** Not a reversal of `a-task-waits-while-its-run-waits` — a **third
outcome** beside *answered* and *proceeded without answer*: **suspended**. For a run the Hub knows is
unattended (a loop or flow firing rather than an operator-driven conversation), an expired blocking
wait ends the turn with the task **left parked** and its `blocked_reason` still naming the question,
instead of releasing it and instructing the agent to continue. When the operator answers in the
morning, the existing batch-delivery path (`agent-capability-plane/spec.md:248`) becomes a trigger
rather than a postscript.

**Every mechanism this needs is already shipped**, which is why the cost is M and not L:

- The run already ends cleanly rather than hanging — measured, `FINDINGS.md:10722-10726`: agent back
  to `idle` after 70s against a 60s window, `idle` and not `error`.
- Sessions already resume: `Run.session_id` / `provider_session_id`, `runner_commands.py:264-265`
  (`--resume <id>` for claude) and `:333-334` (`resume <id>` for codex), driven from
  `agent_trigger.py:728-729`.
- The park already exists and already survives: `block_task_for_question`, `blocked_reason`,
  `question.blocked_task_id`.
- A loop that waits on a human is a known, accepted shape rather than a new one: F12's residual
  (`FINDINGS.md:451`) is exactly this, and `5237ec5` made a continuing stall count in place, so a
  task parked overnight occupies one JobRun row and evicts nothing.

**What it touches.** `mcp_server.py` (the expiry note and what `ask_user` returns),
`agent_actions.py:615-684` (`report_wait_ended` must stop releasing the park for this case),
`run_divergence.evaluate_run_end`'s sweep, the `unattended` discriminator (does the Hub have one that
reaches the run? `jobs.py`/`scheduler.py` know a firing is a firing — the MCP server, spawned
standalone, may not, and this is the first thing to check), and the surfaces F60's round 3 had to
correct — the conversation rail, a loop's open-question count, the checkpoint's `open_questions`,
`scheduler._pending_loop_request`.

**What would make it a bad idea.**

- **It re-opens a change archived five days ago**, and F60's own write-up names six readers that
  derive "somebody is waiting" from question state. A third outcome is a third thing all six must
  read. If the day window is not willing to re-drive `t_f14_f60_wait_parks_the_task.py`, do not start.
- **A suspended run holds a worktree.** Per-task worktrees are in
  `openspec/explorations/2026-08-27-per-task-worktrees.md`; a parked task that holds its checkout
  until morning is a resource decision, not just a state one.
- **The discriminator may not be clean.** An operator can drive a conversation at 03:00 and a loop
  can fire at 11:00. If "unattended" ends up meaning "the operator has not touched this Hub in N
  minutes", that is a heuristic, and this product's own findings are full of heuristics that
  disagreed with the thing they proxied.
- **The honest alternative is cheaper and may be enough**: leave the behaviour alone and raise
  `MAX_WAITING_SECONDS`. It does not work — the comment at `agents.py:1779-1783` says the ceiling is
  "well past anything measured" and that the *measured* limits were 150s for the permission tool and
  240s for an ordinary MCP tool call. A wait long enough for a sleeping operator is a tool call held
  open for eight hours, which is the failure the bound exists to prevent. That is the argument for
  suspend-and-resume rather than a bigger number, and it should be in the change if it is written.

### 2. Withdrawing yesterday's candidate 2

**Yesterday's item.** *"Read relative paths, not just absolute ones, out of a shell command at the
workspace boundary"*, ranked 2, justified entirely by Claude Code **v2.1.259**
(2026-09-02T22:33:51Z):

> Fixed Bash `Read()` deny rules not covering files given as option values
> (`--ignore-revs-file=.env`, `-f.env`, `@file`), `git diff`/`git grep` file operands, or
> `cd DIR && cat FILE` compounds; `grep -r`/`cp -r` over a directory holding a denied file now asks

**v2.1.260, published 2026-09-03T23:48:12Z — 25 hours and 15 minutes later:**

> Reverted the 2.1.259 change applying `Read()` deny rules to Bash arguments; it denied
> `npm run build` under a `Read(./**/build/**)` rule in every mode and made `cd … && grep` prompt
> even in auto mode

Both read 2026-09-04 from `gh api repos/anthropics/claude-code/releases/tags/{v2.1.259,v2.1.260}`.

That is the vendor with the most production exposure to this exact matcher shipping the fix, measuring
it, and taking it out. The failure is not an implementation slip: **path-shaped strings in a shell
command are not paths.** `npm run build` contains the token `build`; a matcher that treats argument
text as filesystem intent denies a build script. The same generalisation that catches `cd /etc && cat
passwd` catches `cd src && grep foo`.

**And AgentWeave's position is better than yesterday's item implied.** Read against the code:

- `hub/hub/mcp_server.py:929-934`, the comment yesterday quoted:

  > *A shell command carries no declared path argument, so absolute paths are read out of the command
  > text. Relative paths are left alone: they resolve against the run's cwd, which is the workspace.
  > **This does not make shell escape impossible — a command can still build a path at runtime — and
  > is a boundary, not a sandbox.***

  Yesterday's file quoted the second sentence and stopped. The third sentence is the disclaimer, and
  it is already there.

- `openspec/specs/agent-run-sandboxing/spec.md:491-505`, a shipped requirement titled *"The product
  states which postures confine a run and which do not"*, which requires the documentation to say
  *"that a workspace is a working directory rather than a wall, that the operator is the boundary
  where no posture is checking, and that a write that leaves the workspace is recorded rather than
  prevented"*, and has a scenario *"Containment is not claimed for a mode"*.

So the premise yesterday leaned on — *"a comment asserting a containment property that the code does
not establish"* — is wrong at the level that matters. AgentWeave already refuses to claim containment,
in a spec, with a scenario asserting the refusal.

**What is actually left, and it is one sentence.** The middle clause — *"Relative paths are left
alone: they resolve against the run's cwd, which is the workspace"* — is false for a command
containing its own `cd`, and it reads as a justification rather than as a limitation. Rewrite it to
say what is true: *relative paths are not checked, because a command can change its own directory and
because argument text is not path intent — see the revert in Claude Code 2.1.260 for what checking it
costs.* That is a comment change and, if the day window wants it durable, one sentence in
`agent-run-sandboxing`'s posture-honesty requirement.

**What would make even that a bad idea.** Nothing much, at this size — but the temptation it creates
is real. A change that touches `_decide` invites someone to "just also handle `cd`", which is the
thing being withdrawn. If the item is picked up, it should be scoped as *the comment and the spec
sentence, and explicitly not the matcher*, with the revert quoted in the change so the next reader
does not rediscover the idea.

**One thing from 2.1.260 that is genuinely new on this surface and still does not apply:**

> Fixed `Edit`/`Write`/`Read` permission rules whose path contains parentheses being dropped as
> invalid or ignored by the Bash sandbox, which left "read-only" folders writable

On a Windows host — `C:\Program Files (x86)\…` — that would be a live hazard for any product that
generates path-based permission rules. **AgentWeave does not generate any.** `runner_commands.py:73-83`
uses `--permission-mode workspace` plus `--permission-prompt-tool
mcp__agentweave__approve_tool_call` and routes every decision to the Hub's own `_decide`; there is no
`Edit(...)`/`Read(...)` rule anywhere in the spawned command. Checked and dropped, recorded so it is
not re-checked.

and `rust-v0.153.2`, **2026-09-03T23:53:12Z**, corrects a *"GPT-6-Astra **Fast tier**"* description
from 1.5x to *"2x speed, increased usage"*.

**What AgentWeave does today.** `hub/hub/model_catalog.py:215-219` offers Codex exactly three models —
`gpt-5.6-sol` (declared `default=True`), `gpt-5.6-terra`, `gpt-5.6-luna`. The file was last touched
**2026-08-28** (`git -C <REPO> log -1 -- hub/hub/model_catalog.py`). Its docstring states the rule:

> Codex: read directly from `~/.codex/models_cache.json`, the CLI's own server-synced catalog… **Only
> entries with `"visibility": "list"` are included** (`codex-auto-review`, visibility `"hide"`, is an

**Measured on this machine, 2026-09-04**, reading `~/.codex/models_cache.json` with explicit
`encoding='utf-8'` (`fetched_at` = `2026-08-29T10:33:58.629066600Z`):

| id | visibility | context_window |
|---|---|---|
| `gpt-5.6-terra` | list | 272000 |
| `gpt-5.6-luna` | list | 272000 |
| **`gpt-reserve`** | **hide** | 272000 |
| `gpt-5.5` | list | 272000 |
| `gpt-5.4-mini` | list | 272000 |
| `codex-auto-review` | hide | 272000 |

Two facts, and the second is the candidate.

**The first is F174 and should be closed as F174, not re-specified.** `gpt-5.6-sol` is not in the
cache at all, while the catalog declares it the Codex default. `FINDINGS.md:13074` already carries
that comparison and `t_sweep_row2_runners.py` re-measures it every sweep. Yesterday's file made the
mistake of presenting it as new; this file is not repeating it. What is new is only its **size**: the
gap is no longer one variant, it is a generation.

**The second is not covered anywhere.** The rule *"only `visibility: list`"* was derived from a single
example — `codex-auto-review`, an internal review model — and the docstring's parenthesis is the whole
justification. The `hide` bucket is not "internal models". It already holds `gpt-reserve` on this
machine, and Codex has now shipped a *user-facing frontier model* into exactly this shape: settable
by configuration, absent from the picker. **A catalog refresh will not fix this**, because the rule
that produces the catalog is the thing excluding the model. An operator who wants Astra will be told
by AgentWeave that Codex offers GPT-5.6.

**A second structural fact from the same two releases.** `ModelDescriptor`
(`model_catalog.py:60-66`) is `id`, `label`, `aliases`, `context_window`, `default`. Codex now
describes Astra as having a **Fast tier** with different speed and usage. Whether that is a distinct
model id or a per-model setting is **not established from anything fetched today** — `0.153.2`'s note
is about display text only, and the machine's cache predates Astra. It is named here as the thing to
check first, not as a claim. Note also that the catalog's own docstring already flags the adjacent
limitation: *"Precise per-model control values would be the more accurate fix but requires extending
the schema to scope a control's values by model, not just by provider — flagged as a follow-up"*.

**What a change would touch.** `model_catalog.py`'s Codex reader and its docstring rule; whatever
surfaces the picker (`hub/ui/src/…` model selection); `t_sweep_row2_runners.py`, which encodes the
current comparison; and the `openspec/specs/model-catalog` capability.

**What would make it a bad idea.**

- **This machine still runs Codex 0.146.0** and its cache is from 2026-08-29. Every claim above about
  what Astra looks like *inside* `models_cache.json` is inference from a release note. A change
  written before a cache that actually contains Astra is a change written against a guess — and F174
  exists because this catalog was authored from memory once already. **Upgrade Codex first, re-read
  the cache, then write.**
- **Widening past `visibility: list` is not free.** It would surface `codex-auto-review`, which the
  original parenthesis was right about. The rule needs replacing with something sharper — an
  allowlist of hidden ids the operator may opt into, or a "hidden" flag the UI renders differently —
  not deleting.
- **Astra is "rolling out today to a limited set of organizations."** A catalog that offers a model
  this operator cannot reach produces the `claude-haiku-4-5-20251001[1m]` failure the docstring
  already warns about at length: an error message that reads like an entitlement gate in front of a
  real model. Whatever ships should have the "you may not have access to this" case in it from the
  start.
