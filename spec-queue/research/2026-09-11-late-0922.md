## The evidence

### 1. Give a reviewer one fact the author did not produce

**What was published yesterday.** *"Engineering Reliable Commit Gates for Agentic AI: Cost-Aware
Verification Portfolios under Common-Mode Data Failures"*, <https://arxiv.org/abs/2609.10969>,
2026-09-10T01:42:40Z. It is a runtime-assurance design plus a deterministic benchmark — 48 task
templates, 2,880 scenarios, six fault regimes — built around one question that nobody in this
routine's reading has separated before: **when a verifier approves something it should not have, was
the problem that the verifier was the same model, or that it was looking at the same evidence?**

The experiment holds the proposal fixed and varies the two independently in a fixed-call 2×2:

> On frozen proposals from two local actor families, **a cross-model vote over shared evidence
> approves 62.9% of unsafe proposals, versus 22.9% with an independent source. The source effect is
> 40.9 percentage points, compared with 11.3 for model diversity.**

Three further results matter here and one qualifies the claim:

- *"After-check races defeat verifier-only gates; transactional partial guards prevent only covered
  failures, while **a full atomic guard records no unsafe effects across 216 episodes**."*
- *"**Idempotent request identifiers prevent duplicate effects after lost responses**."* That is
  `F315`, filed into this repository yesterday — *"the button that blocks a ticket says nothing for
  the two seconds it takes, and a second press writes the move again"* — arrived at independently,
  with the remedy named.
- The honest limit, in the paper's own words: *"Transfer remains conditional: unseen fault families
  yield 16–26% risk, and **a FinQA check fails to reproduce the source effect** with the tested
  small verifiers."* So the 40.9-point figure is a property of that benchmark's fault regimes, not a
  law. What survives the caveat is the *ordering* — source beat model in the population where both
  were measured — and that ordering is enough to rank two pieces of work.

**What AgentWeave does today.** It is unusually well-built on the axis the paper says is worth 11.3
points, and empty on the one worth 40.9.

On identity, the product is rigorous and the rigour is stated in specs, not only in code:

- `requirement-traceability/spec.md:155` — *"**An agent SHALL NOT accept evidence it produced.**
  Distinctness is on agent identity, not run identity — the same rule, for the same reason, that
  already governs task approval."*
- `:140` — *"**An agent's assertion SHALL NOT by itself constitute evidence.** … producing evidence
  is open, and **accepting** it is the controlled act."*
- `task_transition_service.agents_that_may_have_authored` (`:253-283`) unions three records that
  associate an agent with a task, and `F306` — today's spec loop — adds the fourth.
- `scheduler.py:1566-1577` computes the reviewer's `exclude` set and its comment is explicit that
  `exclude=set()` *"is a self-approval route"*.
- `review_turn.py` goes further than most: the reviewer gets *"a detached checkout of the commit the
  evidence names, and its own working checkout is outside that boundary. **This is enforced.**"*
  plus a turn context stating that this is a review — because, per design D4, *"a reviewer that is
  not told it is reviewing will helpfully fix the bug itself and report the work as verified."*

On source, every input to that judgement traces back to the author's run:

- `EVIDENCE_KINDS` (`db/models.py:2355-2362`) is `test_result`, `screenshot`, `artifact_diff`,
  `review_record`, `manual_observation`, `external_reference`. Six things an agent produces and
  hands over. The list is deliberately open at the edges — the comment above it says so — but
  openness is about vocabulary, not provenance.
- **The commit under review is chosen by the author.** `commit_for_task_review`
  (`requirement_evidence.py:785-825`) selects the newest evidence row naming a commit, ordering by
  `produced_at` — *"The most recent evidence wins. A task can carry several evidence rows naming
  different commits — observed live, `ev-42cad5d2` and `ev-5d0273ad` on the same task."* The
  reviewer is put where the author's last evidence row points.
- **The Hub executes nothing of the project's.** `grep -rn "subprocess\|create_subprocess"` across
  `hub/hub/` returns the agent CLIs (`agent_trigger.py`, `codex_appserver.py`), the conversation
  titler (`conversation_titles.py:97`, capped at `MAX_CONCURRENT_TITLE_RUNS = 2`), and git. Nothing
  runs a test.

The reviewer *can* read the code, and that is a genuine second look — but it is a second look by a
model at the same artefact, which is precisely the 62.9% arm. Nothing in the loop produces a fact
about the work that did not pass through the author.

**The gap, stated so R1 can act on it today.** `F306` closes a hole in the *exclusion* — an agent
that recorded evidence for a task can currently be staffed to review and approve it, measured live
(`FINDINGS.md`, F306: `proj-f741298c9c6b` on `:8011`, agent `r7af142d`, sequence 19
`under_review → approved`, `actor_kind='run'`). That fix is correct and should ship as decided; the
verdict is binding and nothing here reopens it. What VP-CONTROL adds is a ceiling on what it buys:
**after `F306`, the reviewer is a different agent voting over the author's evidence, which is the
arm that approved 62.9% of unsafe proposals.** If R1 writes one sentence into the design
acknowledging that — that identity-distinctness is the weaker half and the evidence source is
untouched — the next change on this ground starts from the right place instead of from "review is
solved".

**What a change on the 40.9 axis would touch.** The smallest honest version is the one this routine
proposed on 2026-09-10 §3 and could not price: **let the review turn produce one fact of its own.**
A project declares a verification command; the Hub runs it in the reviewer's existing detached
checkout (`review_turn.prepare_review_turn` already provisions that worktree via
`worktrees.ensure_review_checkout`) and records the result as an evidence row whose `actor_kind` is
the Hub rather than an agent. `RequirementEvidence` already carries `actor` and `actor_kind`, so the
row shape exists. `requirement_gate.evaluate` would then have something to read that no run wrote.

**What would make it a bad idea, and this is not small.** Running a project-declared command from
the Hub process means the Hub executes code the project controls — the one thing its subprocess
inventory shows it has never done, and the reason `agent-run-sandboxing` exists at all is that
project code runs inside an agent's confinement, not inside the Hub's. Doing this without deciding
where that command runs would hand every project a Hub-privileged execution path. The 40.9-point
prize does not pay for that on its own; the design question *"whose process runs the referee"* has
to be answered first, and SaltBench (below) is a reminder that the referee's own isolation is
something you test rather than assume. A cheaper first move that carries no new execution: make the
reviewer's briefing **name which of the facts in front of it were authored by the agent under
review**, so a reviewer cannot mistake the author's `test_result` for an independent one. That is
text, not subprocesses, and it is the version to reach for if the execution question stays open.

### 2. Decide how long one turn may run, and make both runners give the same answer

**What exists elsewhere.** Two independent events in four days, both the same shape: a vendor
discovering that an unbounded wait is a defect and giving it a number.

Claude Code **v2.1.268**, 2026-09-10T20:30:54Z,
<https://github.com/anthropics/claude-code/releases/tag/v2.1.268>:

> Fixed **WebFetch hanging indefinitely** on a server that keeps the response open without
> finishing; a fetch now fails after **300 seconds**. Set `CLAUDE_CODE_WEBFETCH_DEADLINE_MS` to
> override the deadline (0 turns it off).

Note the shape: a default, an override, and an explicit off switch. The same release also fixed
`CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` *"not extending SessionEnd hooks that have no per-hook
`timeout` (they were still cancelled after 1.5 seconds)"* — a hard-coded bound that an operator
control was supposed to reach and did not. That is the failure mode this candidate is about, in
someone else's product, fixed the same week.

And the measurement, from the other direction. Armin Ronacher, **2026-09-07**, *"Astra for Coding:
Why Are We Doing This Again?"*, <https://lucumr.pocoo.org/2026/9/7/astra-why/>, 251 points on HN as
of this morning. He built what he calls a software factory — *"intentionally set up to let the model
decide the how of the workflow entirely. It was free to manage its own context and could maintain
its own records in an agent-notes folder. Then it spun off subagents to work on stuff."* — and ran
it on one prompt:

> the slop machine was running for **35 hours** until I turned it off. In that time it produced a
> net addition of **75k lines of code** and **it did not stop**. In the 35 hours it burned around
> **1B tokens** for a total of around **1200 USD** in raw API costs. It managed to produce **79
> commits**, and that comes to a cost of around **15.5 USD per commit**, and the agents exchanged
> around **1400 messages**.

> 35 hours later, the factory has delivered **absolutely nothing of value** and also not taught me
> anything about how to operate a better one.

And the generalisation, which is the part that is about AgentWeave rather than about one model:

> when left unattended, it **will** keep going, and earlier models did not do that. Even Fable
> wasn't as crazy as that. **When you accidentally give it slightly too big of a task, it will
> continue until it succeeds, even if it burns through an entire subscription.**

This is an anecdote with a bill attached, not a controlled study, and it is cited for the bill.

**What AgentWeave does today, and the asymmetry is the finding.**

*Codex turns are capped at ten minutes and nothing can change it.* `codex_appserver.py:588-590`:

> `# No protocol-level turn timeout exists (implications.md §2) — the Hub enforces its own so a`
> `# stuck app-server cannot wedge an agent forever (task 2.7).`
> `DEFAULT_TURN_TIMEOUT_SECONDS = 600.0`

`run_turn` takes `turn_timeout: float = DEFAULT_TURN_TIMEOUT_SECONDS` (`:921`) and builds its
deadline from it (`:1005`). **`grep -rn "turn_timeout" hub/hub/` returns exactly three lines, all
three inside `codex_appserver.py`.** No caller passes the parameter. So every Codex turn the product
runs — including a night-window build turn — dies at 600 seconds, there is no operator control for
it, and the value appears in no spec. The reasoning that produced it is sound and narrow: it was
written to stop a *stuck* app-server, and it also bounds a *working* one.

*Claude turns have no bound.* `pty_runner.py:232-233` sets `self._proc.fileobj.settimeout(0.1)` with
the comment *"A timeout lets read() poll liveness without discarding buffered data"* — a poll
interval, not a deadline. `grep` for `run_timeout|max_run_seconds|max_turn_seconds|MAX_RUN_DURATION`
across `hub/hub/` and `src/agentweave/` returns nothing. Every other timeout in `agent_trigger.py`
is about waiting for a *human*: `AW_DECISION_TIMEOUT` and `AW_QUESTION_TIMEOUT` (`:1112-1115`),
`_codex_decision_timeout` (`:2512`), `CODEX_OPERATOR_DECISION_TIMEOUT` (`:2576-2579`).

*The budget is a gate at the door, not a brake in the room.* `turn_scheduler.py:310-312`:

```
budget = await project_budget_state(db, project_id)
if initiator == "autonomous" and budget["exhausted"]:
    return ScheduleResult(waiting_reason="token budget exhausted")
```

That is `usage-accounting/spec.md:83-88` working exactly as specified — *"A project token budget
pauses autonomy but not the operator … When measured project usage is greater than or equal to the
configured budget, autonomous turns"* pause — and it has been driven and confirmed
(`FINDINGS.md:6308-6311`, `:10116-10178`). Both halves of that design are deliberate and right. But
both halves are about *admission*: the check runs once, before `trigger_agent_directly`, and the
turn it admits may then run for as long as the model keeps going. A turn admitted at 99.9% of budget
is not interrupted at 100%.

**The gap.** The product has three different answers to "how long may one turn run" — ten minutes,
forever, and "until the next admission check" — and none of them is stated anywhere an operator
reads. The Codex answer exists because the app-server protocol forced somebody to ask; the Claude
answer does not exist because nothing forced the question. That is the definition of an accidental
invariant, and `F45` already recorded what it costs when it fails: *"The flow's stop conditions
cannot end it … The only bound is the project's token budget, which is `null` here … A flow in this
state spends indefinitely on a conclusion it already reached, and **every tick looks healthy** — a
turn ran, an agent was named, no notice was raised"* (`FINDINGS.md:2386-2400`). `F45` was fixed at
`fec52d1` for the between-turns case. The in-turn case is untouched and is not the same bug.

**What a change would touch.** A per-runner turn ceiling on the `Runner` record beside `cli`, `model`
and `flags`; `codex_appserver.run_turn`'s caller in `agent_trigger.py` (the wrapper documented at
`:2618`) passing it instead of taking the default; the pty read loop in `pty_runner.py` gaining one;
and `runner-registry/spec.md` saying what the ceiling means. The honest default for Claude is **not**
600 seconds — this repository's own night windows run turns far longer than that on purpose, and a
ten-minute cap would break the product's flagship use. The decision to write down is that the ceiling
is **stated, per-runner and operator-settable**, with "none" a legal value; the defect is that today
it is neither stated nor settable and differs by runner for no reason anybody chose.

**What would make it a bad idea.** A wall-clock ceiling is the wrong instrument for what Ronacher
measured. His run was not slow, it was expensive — 1B tokens is the number that hurt, and a turn
that costs $1,200 in 35 hours costs the same in 35 minutes on a faster model. If only one thing gets
built, the better one is a **mid-turn spend check**, not a clock: the accounting rows already exist
per turn, and `budget_state` (`usage_accounting.py:99-106`) already computes `exhausted`. But
mid-turn interruption means killing a live agent process, which is exactly the window
`run_liveness`'s docstring warns about — *"`_execute_run` pops its registry entry in a `finally` that
runs **after** the finalize block has taken the turn's snapshot commit and restamped the evidence
footprints"* — so a brake applied inside that window can destroy the commit the work lives in. The
cheap, safe first move is therefore the *stated* ceiling and the Codex asymmetry, filed as a finding;
the mid-turn brake is a design question that needs its own rounds.

### 3. Write down whether a runner has to be a local process

**What exists elsewhere, from yesterday.** OpenAI published the **Agents API**,
<https://developers.openai.com/api/docs/guides/agents-api/overview>, on 2026-09-10; the HN thread
(243 points, 2026-09-10T19:43Z) is what surfaced it. The overview's first sentence is the whole
strategic fact: *"The Agents API gives your application access to **the Codex harness** through an
OpenAI-managed API. OpenAI manages sessions, orchestration, context compaction, and recovery while
your application provides tools and chooses its execution environment."*

The architecture page (<https://developers.openai.com/api/docs/guides/agents-api/architecture>) names
three pieces, and the split between the first two is the one that matters here:

> **Harness:** The OpenAI-hosted Codex instance that runs the model and tool loop and maintains the
> agent's session.
> **Environment:** Where the agent runs commands, executes code, and works with files. An
> environment can be a remote sandbox, **your laptop**, a Docker container, or an AWS Lambda
> function.
> **Application server:** Your code that connects the agent to your product.

`environment.type` takes `none`, `openai_hosted` or **`self_hosted`**: *"Use `environment.type:
"self_hosted"` when the agent needs your infrastructure, private network, or custom software. Your
code starts the environment and connects an executor to the session."* Its object model is `Agent`
(model, instructions, tools, MCP servers) / `Environment` / `Session` / `Events and items` — which is
AgentWeave's own vocabulary with the harness moved to the other side of a network boundary.

Two smaller things in the same docs are worth recording because AgentWeave has the same problems.
`multi_agent: { enabled: true, max_concurrent_subagents: N }` is set **by the application, not by the
model** — *"The harness supplies tools to create, message, wait for, and interrupt subagents. **You
do not declare these tools yourself.**"* — so the delegation tool surface only exists when the
application turns it on. That is the exact control shape this routine proposed on 2026-09-09 §1 for
`request_agent` (still unbuilt), now shipped by a vendor rather than argued from a paper. And the
showcase list includes *"Incident response agent: investigate alerts and **request approval for
recovery actions**"* — the human-in-the-loop surface, as a reference application, on day one.

**What AgentWeave does today.** `SUPPORTED_RUNNERS = ("claude", "claude_proxy", "native", "codex")`
(`runner_commands.py:52`). The registry already models *how* a CLI is reached — the comment at
`:94-99` says *"claude_proxy and native both invoke the claude CLI (see `_build_claude_command`)
under a different auth/proxy setup — their catalog identity for control-override rendering is still
`claude`"* — so there is already a notion of runner variants that differ in transport rather than in
binary. What there is no notion of is a runner whose **model loop does not run on this machine**.
Every path ends in `resolve_executable` / `shutil.which` and a spawned process.

`runner-registry/spec.md` is where the assumption lives, unmarked:

> The Hub SHALL persist runner definitions as project-scoped database rows, each identifying **a
> supported CLI (`claude` or `codex`)**, optional launch flags, and an optional default model.

> **WHEN** the Hub triggers an agent that has a bound runner — **THEN** it **spawns the CLI**, flags,
> and model that runner record specifies.

> **WHEN** an operator attempts to create a runner naming a CLI other than `claude` or `codex` —
> **THEN** the Hub rejects the request.

Three requirements, and "local process" is load-bearing in all three without being the subject of any
of them.

**The gap.** AgentWeave's deployment bet is stated as *local and self-hosted, not a cloud service*.
As of yesterday that phrase has two independent axes, and the product's positioning, its specs and
its diagnostics all collapse them into one. OpenAI now sells "your files, our loop". AgentWeave is
"your files, your loop". Those are different products with the same adjective, and the operator has
no way to see which one they are running — `agentweave diagnose`'s runner check
(`src/agentweave/diagnostics.py:208`) asks whether the CLI is on `PATH`, which is a question that
only makes sense for one of the two answers.

**What a change would touch.** The smallest version is a decision record plus one sentence: an
exploration in `openspec/explorations/` stating whether a runner may be remote and why, and — if the
answer is "not yet, deliberately" — a line in `runner-registry/spec.md` saying so, so the next person
to add a runner knows it is a decision rather than an oversight. The nearby precedent is that this
repository already writes those down: `agent-run-sandboxing/spec.md:491` is a whole requirement whose
content is *"The product states which postures confine a run and which do not"*.

**What would make it a bad idea.** "AgentWeave should support hosted runners" is an L-cost bet against
the product's own positioning, and nothing published yesterday says it is time — OpenAI shipping a
managed harness is a reason to know your answer, not a reason to change it. The failure mode here is
treating candidate 3 as permission to start building an HTTP runner adapter. It is not; it is an hour
of writing. If the day has no room even for that, the correct outcome is that this sits in the
research archive until it does, and that is why it is ranked third.
