## The evidence

### §1 — a write an agent cannot safely retry

**What exists elsewhere.** On 2026-09-21 Codex merged the first full multi-agent collaboration
primitive in a coding harness that is shaped like AgentWeave's messaging. It came as eight PRs in
fourteen hours, all behind the default-off `agent_message_board` flag:

- **#46959** (07:52:53Z), interfaces: *"`AgentMessageBoard` covers channel creation, posting, thread
  listing, post search, bounded reads, and subscriptions, **with documented membership and retry
  semantics**."*
- **#46966** (08:24:12Z), storage: *"Serialize mutations across independent handles with immediate
  transactions. **Deduplicate retries by caller and request ID, reject changed requests that reuse an
  ID, and return existing post metadata without repeating notifications.** Deliver deduplicated
  notifications after commit; notification failures leave committed posts successful and readable."*
  The PR's tests cover *"concurrent retries across independent handles"* and *"notification
  failures"*.
- **#46985** (09:28:38Z), tools: *"Derive post request IDs from turn and invocation metadata for
  direct and Code Mode calls"*. Its tests cover *"duplicate post calls"* and *"mutation rejection
  without writes under insufficient budgets"*.
- **#47017** (12:35:50Z) wires the board into persistent multi-agent runtimes, and **#47075**
  (17:29:27Z) adds an attributed 150-character preview to notifications.

Links: <https://github.com/openai/codex/pull/46966>, <https://github.com/openai/codex/pull/46985>.

Two of those sentences are the design AgentWeave lacks. First, **the caller's retry is a first-class
case with its own identifier**. Second, **a failure after the commit does not turn a committed post
into a reported failure**.

**What AgentWeave does today, read line by line.**

1. **The client.** Every agent-plane MCP tool goes through `_hub_request` (`mcp_server.py:164-200`).
   It calls `urllib.request.urlopen(request, timeout=10)` (`:184`) and handles two exception types.
   `HTTPError` becomes `HubAPIError` (`:187-198`). `URLError` becomes `HubUnreachableError` (`:199-200`),
   whose message tells the agent *"Check this run's HUB_URL — it may point at the wrong instance"*
   (`:118-121`).
2. **What a slow answer looks like to the agent. Measured today, not inferred.** I ran a scratch
   server that reads the body, sleeps 3 s and answers 201, against a client timeout of 1 s, on this
   machine's Python 3.11.9. It raised `TimeoutError` (MRO `TimeoutError → OSError → Exception`) with
   the text `timed out`. That is **not** a `URLError`, so neither branch catches it. The agent gets a
   bare `timed out` for a request that may have been applied in full. A connect-phase timeout would
   instead arrive wrapped in `URLError` and read as "wrong HUB_URL", which is also misleading.
3. **The server commits first and does more work afterwards.** In `create_message_for_actor`, both
   the message and the recipient's `InboundQueueEntry` are committed at `messages.py:270-271`. After
   that come `persist_event("message_created")` (`:274`), `persist_event("queue_entry_queued")`
   (`:284`), a conditional `persist_event("queue_chain_suspended")` (`:295`) and
   `schedule_agent(...)` (`:307`). `persist_event` commits by default (`utils.py:40-41`), so each is
   its own write transaction on SQLite. The repo has already measured what one of those does under
   contention: F89 recorded *"every other connection's write waits out the 5s busy timeout and then
   raises `database is locked`"* (FINDINGS.md:6152). An exception at `:274` or later answers 500 for
   a message that is **already queued, and that will start a recipient turn**. The sender sees
   `HubAPIError(500)` and has every reason to send again.
4. **Tasks are one step from safe, and have been since June.** `a9c7762` (2026-06-17) *"honor[ed]
   client-supplied task id in POST /api/v1/tasks"*. At the time the MCP tool generated the id locally.
   The Hub half is still in place: `AgentTaskCreate.id` (`agent_actions.py:95`),
   `task_id = body.id or f"task-{short_id()}"` (`tasks.py:759`), and a duplicate returns 409
   `"Task id '…' already exists"` (`:780-787`). The schema comment still says it exists to *"let the
   MCP `create_task` tool return the same id that the Hub stored"* (`schemas/tasks.py:67-71`). **The
   MCP tool's body no longer carries an `id`** (`mcp_server.py:283-294`). So a retried
   `create_task` creates a second task, and the comment describes a caller that no longer exists.
5. **Messages have no key at all.** `AgentMessageCreate` is copied field by field into
   `MessageCreate` (`agent_actions.py:205-215`), and `Message.id` is always minted server-side
   (`messages.py:45`, `f"msg-{short_id()}"`).

**Measured on the live instance, read-only.** `~/.agentweave/hub/data/agentweave.db`, opened with
`mode=ro`:

- **274** messages with a `created_by_run_id` (2026-09-13 16:35 → 2026-09-17 22:09). **Zero** pairs
  share sender, recipient and content within 300 s.
- **23** agent-created tasks. **Zero** pairs share a title and a `created_by_run_id`.

**So this is latent, and I am calling it latent.** Nobody has been bitten on this machine. The case
for doing it now does not rest on frequency. It rests on four things:

- the cost of a duplicate: a message queues a whole recipient **turn**, and those are the tokens the
  flow exploration is trying to save;
- the fix being mostly built already;
- the repo's own ledger naming the same class twice from the UI side: **F315** (open, C), *"a second
  press writes the move again"*, and 2026-09-11's citation that *"Idempotent request identifiers
  prevent duplicate effects after lost responses"*;
- a direct competitor having just shipped the same surface with the retry case designed in from the
  first PR.

**The gap, in one line.** AgentWeave's agent-plane writes have no idea of "the same request again".
The one place that did was left without a caller.

**What a change would touch.**

- `mcp_server.py`: `create_task` mints `task-<short id>` once per tool call and sends it.
  `send_message` does the same with a new `id` field. `_hub_request` catches `TimeoutError`, retries
  once with the same body, and returns a sentence that says the write *may* have landed and that
  retrying with the same id is safe.
- `agent_actions.py` / `schemas/messages.py`: an optional `id` on `AgentMessageCreate` and
  `MessageCreate`, validated with the same regex as the task id (`^[A-Za-z][A-Za-z0-9_-]{0,63}$`).
- `messages.py:32-308` and `tasks.py:759-787`: when the id already exists and sender and content
  match, return the stored row with 200 and **do not re-queue**. When the id exists but the content
  differs, return 409. This is Codex's *"reject changed requests that reuse an ID"*.
- `messages.py:273-307`: an exception after the commit at `:271` is logged and does not become the
  response. The accounting path already has this contract: *"accounting must not take the work down
  with it"* (quoted in F89).
- `agent-capability-plane` requires *"HTTP and MCP access have equal capability"* (`spec.md:107`),
  so the operator route `POST /messages` (`messages.py:311-331`) gets the same field. No migration
  is needed, because the key *is* the primary key.

**What would make it a bad idea.** (a) **Frequency is measured at zero.** If the operator ranks by
observed harm, this sits below every open A and B in the ledger. That is a fair call, and it is why
the cost is S and not more. (b) A client-minted id makes the id a thing the agent could forge. That
is already accepted for tasks and bounded by the regex. Scoping duplicates to the caller's
`project_id` and sender, which Codex does *"by caller"*, stops one agent from colliding with
another's id. (c) Returning the stored row on a retry hides the case where the first request's
post-commit work, `schedule_agent`, never ran. So the retry path should call `schedule_agent` again,
which is idempotent by design since it only wakes the scheduler, rather than returning early.
