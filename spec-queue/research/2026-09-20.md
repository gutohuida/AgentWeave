## The evidence

### §1 — the loop waits, and nobody is told

**What AgentWeave does today, measured.**

Two blocking primitives, two hard deadlines, both reasoned about in place:

```
OPERATOR_DECISION_TIMEOUT = _configured_wait("AW_DECISION_TIMEOUT", 120)   mcp_server.py:927
QUESTION_ANSWER_TIMEOUT   = _configured_wait("AW_QUESTION_TIMEOUT", 240)   mcp_server.py:935
```

The comments above each are careful, and both reason about the same two things — what the provider
tolerates, and how long a human needs to *act*:

> *"Claude was measured holding a permission tool call open for at least 150s, so the default fits
> inside what the provider tolerates while leaving an operator time to read and click."*
> (`mcp_server.py:925-926`)

> *"A question deserves a longer wait than a permission prompt: the operator has to read it and
> compose an answer, not click one of two buttons."* (`mcp_server.py:930-934`)

Neither reasons about the operator **arriving**. The clock starts when the agent asks, not when the
human finds out, and `ask_user`'s own docstring names the outcome: *"answered=False, declined=False
— nobody responded before the wait ran out. Unlike a decline, this does not mean the operator saw
it."* (`mcp_server.py:357-360`).

**What reaches the operator.** The Hub does broadcast. `ask_question_for_actor` — the single
creator, shared by the agent route (`agent_actions.py:574`, `:614`) and the operator route
(`questions.py:303`) — emits `question_asked` on SSE and persists it (`questions.py:277-290`). In
the browser that event is handled by exactly this:

```ts
case 'question_asked':
case 'question_answered':
  queryClient.invalidateQueries({ queryKey: ['project', pid, 'questions'] })
  queryClient.invalidateQueries({ queryKey: ['project', pid, 'status'] })
  break
                                                          hub/ui/src/hooks/useSSE.ts:455-458
```

Two cache invalidations. Whether anything becomes visible depends entirely on which component is
mounted, and there are two: `QuestionsPanel` on the `questions` route (`App.tsx:382`) and
`QuestionInterruptCard` on Overview (`OverviewPage.tsx:133`). On Spec, Agents, Tasks, Loops or any
conversation, an arriving question is invisible for its whole 240 seconds.

The permission surface is worse, because its subscription lives *inside* its hook:
`usePendingPermissionRequests` invalidates on `permission_requested` in its own `useSSE` callback
(`api/permissions.ts:35-43`), and the hook is called from **one** place —
`AgentOutputPanel.tsx:218`, rendering `PermissionRequestCard` at `:1026`. An operator not looking at
*that agent's* output panel does not fetch the request, does not render the card, and has 120
seconds.

`grep -rni "Notification|document.title|favicon|new Audio|navigator.vibrate" hub/ui/src` returns
nothing usable — two `Notification` hits, one a comment in `LoopFiringGroup.tsx:54` and one a
fixture path in `specNavigation.test.ts:226`. There is no out-of-band signal of any kind.

**The defect underneath it.** `summaryForEvent`'s `question_asked` branch:

```ts
case 'question_asked': {
  const source = data.from_agent ? `from ${data.from_agent}${data.blocking ? ' (blocking)' : ''}: ` : ''
  return `${source}${String(data.question ?? 'waiting for an operator answer').slice(0, 80)}`
}
                                                          hub/ui/src/lib/eventSummary.ts:15-18
```

`data.question` is never sent. Both `sse_manager.broadcast` and `persist_event` are given
`{"id": q_id, "from_agent": from_agent, "blocking": body.blocking}` (`questions.py:278-290`), while
the row itself stores `question=body.question` a few lines earlier. So every activity-log row for a
question renders the fallback string, and `eventSummary.test.ts:8` asserts the branch with a payload
the product cannot produce. That is the class `FINDINGS.md:7035` already named — *"A test can pin a
branch the product cannot reach"* (F100/F101) — recurring in the UI rather than in `run_turn`.

**What exists elsewhere, with dates.**

- **openai/codex #46574**, *"Notify users when asynchronous questions arrive in the TUI"*, merged
  **2026-09-19T02:09:39Z** (<https://github.com/openai/codex/pull/46574>): *"Send an `async-question`
  notification when new unanswered questions arrive, honoring existing notification settings and
  taking priority over turn completion. Show a shortened question title for a single question or a
  count for a batch. Empty batches, duplicate deliveries, and replayed history do not trigger
  notifications."* Note the third sentence — it is the design AgentWeave would need for a batched
  `ask_user`, where up to four questions share one `batch_id` (`models.py`, `batch_index` /
  `batch_size`) and must produce one signal, not four.
- **block/goose v1.51.0**, released **2026-09-17T19:15:25Z**
  (<https://github.com/block/goose/releases/tag/v1.51.0>): *"Opt-in terminal bell when a turn
  finishes or approval is needed"* (#10182). Two things AgentWeave should copy: it covers **both**
  surfaces with one mechanism, and it is **opt-in**.

**The gap.** Both vendors treat "a human is now the critical path" as an event worth interrupting
for. AgentWeave treats it as a cache invalidation. This is not a peripheral surface — *the operator
stays in the loop at the decisions that matter* is one of the product's four stated bets, and it is
currently implemented as a hope that the operator is on one of two pages.

**What a change would touch.** `hub/hub/api/v1/questions.py:278-290` — add `question` and `header`
to both payloads; one line each, and it makes the activity-log row readable whether or not anything
else lands. Then one UI change: a handler on the existing `question_asked` / `permission_requested`
events that raises a signal. Cheapest credible shape, in order of cost: a `document.title` prefix
and the already-built `SidebarItem` badge — no new component, no permission grant, works in a
background tab — then, opt-in, the browser `Notification` API, which needs a grant and a settings
row. `hub/ui/src` means `make ui` / `scripts/refresh_ui_bundle.py`, and the source and
`hub/hub/static/ui` must be committed together, the same constraint DIRECTION states for F386.

**What would make it a bad idea.** Three things. (a) If §3 returns an expiry rate near zero, the
signal is solving nothing and only the payload line is worth doing — which is why §3 is cheap and
should run first if both fit. (b) An unconditional notification is a regression for an operator
running an unattended night window: goose made it opt-in and Codex honours existing notification
settings, and a default-on browser permission prompt on first load would be worse than the gap.
(c) Sending question text into `persist_event` widens what the durable event log contains; the row
already holds the same text, so this is a duplication question rather than a disclosure one, but it
should be said out loud rather than discovered.

### §2 — which charter was this run actually given?

**What AgentWeave does today.** The charter is read live and rendered per turn:

```python
# Build context from current Hub-owned state for every turn. Runners consume a file,
# so materialize the canonical response inside the effective workspace immediately
# before command construction; an edited charter is therefore visible on the next run.
                                             hub/hub/api/v1/agent_trigger.py:1015-1017
...
context_file = Path(effective_work_dir) / ".agentweave" / "context" / f"{agent}.md"
context_file.write_text(rendered_context["context"], encoding="utf-8")
                                             hub/hub/api/v1/agent_trigger.py:1060-1064
```

That is a deliberate and defensible dispatch rule. What follows from it is not deliberate:

- `Charter` is `id, project_id, name, content, created_at, updated_at` (`models.py:344-351`). An
  edit through the UI overwrites `content` in place. There is no revision table and no history.
- `Run` records `snapshot_commit_sha`, `work_dir`, `outside_workspace_writes`,
  `capability_token_hash`, `divergence_source_run_id`, `turn_depth` — and nothing about the
  behaviour contract it executed under (`models.py:1105-1234`).
- The one materialised artefact, `<work_dir>/.agentweave/context/<agent>.md`, is keyed by agent
  name inside a shared worktree and rewritten on the next turn.

So: an operator edits a charter at 14:00. A run from 13:40 is reviewed at 15:00. Nothing in the Hub
can state whether the author was told the same thing the reviewer is measuring against — and
`review_turn.py` is emphatic that the *other* half of this, *"the reviewer's workspace for the turn
is a detached checkout of the commit the evidence names"* (`:12-13`), matters precisely because the
two halves *"must not drift apart"* (`:9`).

**What exists elsewhere, with dates.** Three shipments in one week, all the same rule:

- **openai/codex #46580**, *"Keep Guardian reviews on the applied instruction snapshot"*, merged
  **2026-09-19T02:31:53Z** (<https://github.com/openai/codex/pull/46580>). Its *Why*, verbatim:
  *"Shared thread instructions can change after an action is generated but before Guardian reviews
  it. Polling the live provider during review can give the reviewer different instructions from
  those applied to the action."* The fix initialises reviewers *"with the user and thread
  instructions captured in the review session reuse key"*. That is AgentWeave's reviewer, one vendor
  over, with the failure stated in one sentence.
- **openai/codex #46577**, *"Allow thread instruction providers to share updates with subagents"*,
  merged **2026-09-19T02:15:33Z** (<https://github.com/openai/codex/pull/46577>): *"Subagents
  inherit applied instruction snapshots, so later provider updates do not reach running
  descendants."* The new sharing is **opt-in** (`share_with_subagents()` *"defaulting to `false`"*)
  and Guardian sessions keep *"snapshot-only instructions"* regardless — i.e. even where they added
  live propagation, they excluded review from it.
- **block/goose v1.51.0** (2026-09-17): *"Build recipes from one validated snapshot"* (#11612) and
  *"Guard recipe-before-inference ordering on scheduled runs"* (#11502). The same rule applied to a
  scheduled run's configuration rather than to review.

**The gap.** Everyone is arriving at the same place: the instruction set an action ran under is a
fact about that action and must be captured with it, not re-derived. AgentWeave already believes
this about *code* — the detached checkout is exactly that argument — and has not applied it to the
artefact its own product description calls the behaviour contract.

**What a change would touch.** Two sizes, and the small one carries most of the value. **S:** a
`charter_id` and a `charter_sha256` on `Run`, written at spawn from the content actually rendered;
one migration; and one read that lets any surface say *"the charter changed between this run and its
review"*. **M:** persist the whole rendered briefing per run and show it on the trace — which is
also what would make 2026-09-19 §1 (label the model-authored checkpoint) auditable after the fact
rather than only at compose time.

**What would make it a bad idea.** The M version stores a large blob per run, and this project has
hundreds of runs on one machine — the same reasoning that made F389 record *"a row per allowed tool
call would bury the refusals"*. The S version has a migration behind it, and DIRECTION explicitly
rejected a sentinel for F388 because it *"needs a migration installed against the very database
being protected"*; that caution applies today and is a reason to sequence this after F388 lands,
not a reason to drop it. And it should be said plainly: nobody has been bitten by this yet. It is
argued from three vendors' regression tests and AgentWeave's own review design, not from a finding.

### §3 — does the operator ever actually arrive?

**What is already stored.** Everything the reading needs, in two tables:

| table | columns | `models.py` |
|---|---|---|
| `questions` | `created_at`, `answered`, `answered_at`, `blocking`, `batch_id`, `from_agent` | `:927-961` |
| `permission_requests` | `status` (default `pending`, **indexed**), `dismissed`, `agent`, `run_id`, `tool_name` | `:1581-1610` |

Two questions, two `GROUP BY`s. **(a)** Of every question ever asked, what fraction was answered,
declined, or neither — and for the answered ones, what is the distribution of
`answered_at - created_at` against the 240 s fuse? **(b)** How many `permission_requests` rows are
still `pending` with an ended run, against the 120 s fuse?

Nothing in the product reads this. The only open-question count that renders anywhere is per-loop —
`loop.open_questions` at `JobCard.tsx:345`, `LoopsIndexTab.tsx:52` and `LoopTab.tsx:286` — so a
question asked by an ordinary agent run is counted nowhere at all, and the aggregate across the
project has never been computed.

**Why now.** **crewAI 1.15.22** (2026-09-16T22:09:58Z,
<https://github.com/crewAIInc/crewAI/releases/tag/1.15.22>) lists *"Collect human feedback and pause
events in tracing"* among its features. The human pause is becoming a first-class traced interval in
the frameworks AgentWeave competes with, while AgentWeave's `trace-timeline` spec requires a
*"chronological timeline of spans and related activity"* (`trace-timeline/spec.md:66-76`) with no
requirement that a wait on a human is one of them. **Langfuse v4.38.0** (2026-09-17T15:26:11Z) is
the same direction from the observability side: *"feat(ai-gateway): correlate coding agent
requests"* (#17573) and a *"persistent trace summary strip"* (#17536).

**How to run it safely, which is not optional today.** The rows live in the operator's real database
at `~/.agentweave/hub/data/agentweave.db`, which on 2026-09-19 a window attached a throwaway Hub to
(F388, A) and whose recovery *"took the operator's own app down for about three hours"*
(`DIRECTION.md`, `## 2026-09-20`, item 2). The day window's own result asks the operator to *"confirm
`:8000` still starts cleanly and its data looks right before the next loop window runs."* **Copy the
file and query the copy.** Do not open the live path, read-only or otherwise, until that
confirmation exists.

**What would make it a bad idea.** It answers nothing about the counterfactual: a low expiry rate
could mean the operator always arrives, or it could mean agents learned not to ask. A count of
`ask_user` calls per run over time is the control, and it comes from the same `tool_use` rows
yesterday's §3 wanted for `recall` — one read, two questions, which is an argument for doing them
together rather than for doing neither.
