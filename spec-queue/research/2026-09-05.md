## The evidence

### 1 — the charter stops at the first subagent

**What exists elsewhere.** Claude Code `v2.1.261`, 2026-09-04T19:58:10Z
(<https://github.com/anthropics/claude-code/releases/tag/v2.1.261>):

> Added `--append-subagent-system-prompt-file` to read the subagent system prompt from a file, for
> prompts too large to pass on the command line

The wording matters twice over. It says *"the subagent system prompt"* — definite article, a distinct
thing from the session's. And it adds only the `-file` spelling, which means the non-file spelling
already existed.

**Measured on this machine, 2026-09-05.** The installed CLI is `2.1.238`. Probing the argument parser
directly (a known flag reports a missing argument; an unknown one reports an unknown option):

```
$ claude --append-subagent-system-prompt
error: option '--append-subagent-system-prompt <prompt>' argument missing
$ claude --append-subagent-system-prompt-file
error: unknown option '--append-subagent-system-prompt-file'
$ claude --append-bogus-flag-xyz                      # control
error: unknown option '--append-bogus-flag-xyz'
```

So the channel is open on the CLI AgentWeave is running **today**, 23 releases before the one that
prompted this. Only its file-backed spelling is new.

**What AgentWeave does today.** `agent_trigger.py:994-997` renders the agent's context and writes it
to `<work_dir>/.agentweave/context/<agent>.md`; `runner_commands.py:230` passes it as
`--append-system-prompt-file`. That file is the charter's only delivery mechanism — the
`agent-charter` capability's eight requirements are all about authoring, binding, seeding and the UI
(`openspec/specs/agent-charter/spec.md:10-197`); the contract is prose, appended to a system prompt,
and that is the whole of its enforcement.

`grep -c subagent openspec/specs/*/spec.md` matches **nothing, in all 43 capabilities**. AgentWeave
has no stated position on what happens inside a subagent.

**The gap.** An agent bound to a charter that says *"you review, you do not implement"* spawns a
`Task` subagent that has never seen that sentence. The subagent inherits the workspace, the MCP
surface and the permission posture, and none of the accountability. It is reachable in the ordinary
default: the no-approver fallback is `acceptEdits` (`runner_commands.py:73`), which does not put a
`Task` call to anyone. The charter capability's own framing — *"A charter names an accountability,
not an activity"* (`agent-charter/spec.md:167`) — is precisely the thing that does not propagate.

**What a change would touch.** `runner_commands.py:230` — one extra pair of argv entries. The
rendered context measured on disk is **7,817 bytes**, comfortably inside a Windows 32,767-character
command line, so `--append-subagent-system-prompt <text>` works on 2.1.238 now and the `-file`
spelling becomes a one-word swap when the CLI is upgraded. A spec delta on `agent-charter` saying
what a subagent inherits. Tests in `hub/tests/test_worker.py` and the runner-command tests.

**What would make it a bad idea.** Three things, and the first is the reason this is S and not free:

- The full 7.8 KB context is the wrong payload for a subagent. Most of it is `## Your tools` — the
  Hub's MCP surface, which a `Task` subagent has no business calling and may not even be able to
  reach. Passing the whole file would spend ~1,700 tokens per subagent on tools it cannot use. The
  right payload is probably the `## Charter` section alone, which means the renderer has to be able
  to emit a subset — a real design decision, not a flag.
- **Unverified and load-bearing:** whether `--disallowedTools Edit,Write,NotebookEdit`
  (`runner_commands.py:203-210`, the `restrict_spec_writes` guard) reaches subagents. If permission
  rules are session-wide, the *containment* half is already fine and only the *behaviour* half leaks.
  If they are not, F277's missing `MultiEdit` is the smaller of two holes. This is measurable in one
  driven run and should be measured before the change is specified, not argued.
- A charter written for an agent may read as nonsense to a subagent ("your teammates are…"), so this
  is not a copy — it is a decision about which clauses are role-scoped.

### 2 — the review's independence check tests a name

**What exists elsewhere.** arXiv **2609.01873**, *"Epistemic Sybil Resistance: Multiplying AI Agents
Without Multiplying Evidence"*, 2026-09-01, <https://arxiv.org/abs/2609.01873>. From the abstract:

> another agent is not another observation: apparently independent reports may descend from the same
> evidence […] Holding one evidence root fixed while report multiplicity rises from 1 to 32 collapses
> naive posterior coverage from 0.940 to 0.263 […] correlated extraction errors, **which a shared base
> model can induce among independent agents**, lower that ceiling further […] The agent's replicate
> extraction errors are correlated (gamma_cal = 0.719) […] Collective inference should therefore track
> evidential ancestry and dependence, not agent or report multiplicity or similarity.

Over 20,000 controlled LLM-agent report and extraction calls. The paper's conclusion is not "reviews
are useless" — it is that a *report-only aggregator cannot tell replication from corroboration*, and
that the fix is to record ancestry.

Adjacent, same week: **2609.01870 ArcticSwarm** (2026-09-01, <https://arxiv.org/abs/2609.01870>)
reaches 82.6% on BrowseComp-Plus with gated isolation versus 78.8% without — *"parallel agents
repeatedly explore the same evidence, while access to peers' partial findings cause search to
converge on an early candidate before alternatives are tested."*

**What AgentWeave does today, and does well.** `review_dispatch_refusal`
(`hub/hub/api/v1/agent_trigger.py:450-490`) is a real, enforced separation of duties, and the error
text is the product at its best:

> Cannot review task {id} as {reviewer}: that is the agent recorded as completing it, so the review
> would claim its own author is reviewing it. *(`agent_trigger.py:484-490`, HTTP 403)*

**The gap.** That check compares two strings from the roster. An `Agent` carries `runner_id`
(`hub/hub/db/models.py:216`) pointing at a `Runner`, which is *"Reusable execution capability an agent
is bound to: which CLI, which model"* with columns `cli` and `model` (`models.py:303-320`). Nothing
stops two agents pointing at the same runner — that is the intended shape of the three-way
Runner/Agent/Charter split. So `reviewer != author` is satisfiable by two names running the identical
`claude --model <same>` binary, and the 403 that reads as an independence guarantee is, in that
configuration, a guarantee about naming.

This is not hypothetical for the product's own loop: the 2026-09-04 day window ran *"spec R1 / spec R2
re-derive independently / spec R3 re-derive again"*, three rounds on one runner. It found real
defects — `spec-queue/APPROVALS.md` records round 2 finding the code in breach of a shipped
requirement and round 3 overturning design decision D3 by measurement. That is the point: the answer
is not to refuse same-runner reviews, it is that **AgentWeave currently cannot say how independent any
review was**, so an operator reading three green reviews cannot tell 3 evidence roots from 1.

**What a change would touch.** `review_dispatch_refusal` gains a non-refusing observation alongside
the 403; the review record gains the reviewer's resolved (cli, model) and a flag for "same runner as
the author"; `requirement-traceability` / evidence surfaces render it. A spec delta on the review half
of `task-lifecycle-governance`. No migration beyond two columns. **It must not become a fourth refusal
status** — a single-CLI operator would be locked out of reviewing anything.

**What would make it a bad idea.** The paper's mechanism is *correlated extraction errors from a
shared base model*, and AgentWeave's reviews are not extractions from documents — they are code
reads with a filesystem as ground truth, where a shared model's error correlation may be far lower
than γ=0.719. Recording ancestry is cheap and honest; *acting* on it (weighting, requiring a second
runner) is not warranted by this paper on this task and should not be specified from it. Also: the
displayed value must be the runner *as resolved at dispatch*, since a runner's `model` column is
mutable and a review read six weeks later would otherwise report the wrong ancestry — the same class
of defect as the catalog drift in the lead.

### 3 — the context number has no composition

**What exists elsewhere, all inside 24 hours.**

- Claude Code `v2.1.261` (2026-09-04): *"Added `/skill-doctor` to show which loaded skills go unused
  and what they cost in context, so you can prune them."* Attribution plus a prune recommendation, per
  contributor. The same release also adds `bashOutputMaxChars`/`taskOutputMaxChars` — an operator
  control over how much inline output the model receives.
- r/mcp, read 2026-09-05 via `.rss`: *"I compile MCP servers into CLIs so the tool schemas stop
  sitting in context. 4.1x smaller on nine real servers."*
- Spotify Engineering, 2026-09-04,
  <https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90>
  (83 points on HN). Routes bulk reads and boilerplate generation to a cheap model. The load-bearing
  sentence is about *mechanism*, not cost: *"The first version of this was a block of routing rules in
  CLAUDE.md. It sort of worked […] But the rules were advisory, not enforced. Claude could ignore
  them."* They moved to `PreToolUse` hooks that block a `Read` over 350 lines.

**What AgentWeave does today.** `openspec/specs/agent-context-usage/spec.md` is a serious capability —
18 requirements covering measured/estimated/unsupported/unavailable status, provider cache semantics,
Claude and Codex mappings, per-turn reporting when a conversation's model changes, and *"Unknown
context usage is reported as unknown"* (`spec.md:253`). It is careful about the honesty of the number.
Every requirement is about the total. None attributes it.

**Measured today**, `.agentweave/worktrees/alice/.agentweave/context/alice.md`, the file AgentWeave
itself writes and passes to the CLI (7,817 bytes, 53 lines, mtime 2026-08-22):

| Section | Bytes | Share |
|---|---|---|
| `## Project Operating Profile` (incl. workspace, Team) | 615 | 8% |
| `## Communication Mode` | 172 | 2% |
| **`## Your tools`** | **6,831** | **87%** |
| `## Charter` | 50 | 0.6% |

**Two honest caveats on that table.** Alice has no charter bound — those 50 bytes are the literal
string *"No charter is assigned to this agent."*, so 87% is the charter-less ceiling, not the typical
case. And the file is two weeks old, from a worktree, so the tool list may since have grown. It is a
measured floor, not a headline. It is also *before* the MCP tool schemas the CLI loads from
`--mcp-config`, which are a second copy of the same surface in a different notation.

**The gap.** AgentWeave writes that file, with named `##` sections, and therefore knows its
composition by construction — but the Hub reports only `context_tokens` / `percent`. An operator who
sees an agent at 60% cannot learn that most of what the Hub put there describes tools rather than the
job. This is the same shape as the `/cost` change noted on 2026-09-04 (naming the *likely cause* of a
prompt-cache miss rather than only the number) and the *"Organization policy"* line added to `/status`
in v2.1.261 (saying *why* the policy could not be loaded). Three Claude Code changes in two days
moving diagnostics from *what* to *what of*.

**What a change would touch.** The renderer at `agents.py:1073` returns the section sizes it already
computes; `agent_trigger.py:994-997` records them on the run; the context surface renders an injected
breakdown beside the measured total. No model call, no estimation, no new dependency — this is
arithmetic on a string AgentWeave already holds.

**What would make it a bad idea.** The injected context is a small and *shrinking* fraction of a
1M-token window — 7.8 KB is roughly 2,000 tokens, well under 1%. If the operator's real problem is a
600 KB file the agent read, a breakdown of the 2,000 tokens the Hub contributed is precise and
useless, and worse, it invites pruning the one part of the context AgentWeave controls for a rounding
error. The honest version of this candidate reports injected bytes as *one line* against the measured
total and resists growing into a dashboard. If the number turns out to be under 1% for every real
agent, the correct outcome is a line in the spec saying so and no feature.
