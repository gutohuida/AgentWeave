## The evidence

### 1. Pin the refusals `_ABSOLUTE_PATH_RE` makes by accident, before the URL change moves it

**What today's change will do.** `DECISIONS.md`'s F312 verdict (`:630-656`) and the narrowed F300
verdict (`:694` onward) together say that `_decide` must stop treating a URL as a path. It must let
the run's own Hub URL through and refuse every other URL for a reason that names network access.
Both findings locate the defect in one regex, `hub/hub/mcp_server.py:936`:

```python
_ABSOLUTE_PATH_RE = re.compile(r"(?:[A-Za-z]:[\\/]|/)[^\s\"'|;&><)]*")
```

F312's table shows the mechanism. The regex has no idea where a token starts. It matches the `p:`
of `http:` as a drive letter, and the `/api/…` after an unexpanded `$HUB_URL`. So whatever R1
proposes will change **where in a token the regex is allowed to begin**. There is no other way to
stop it matching inside `https://…` or `$HUB_URL/…`.

**What that same looseness currently does, measured this morning.** `hub/hub/mcp_server.py` was
copied to `C:/Users/huida/.claude/routines/agentweave-research/scratch/`. It was run with
`PYTHONDONTWRITEBYTECODE=1` and `-B`, and `AW_WORKSPACE_DIR` was set to a scratch directory. Nothing
was written into the repository: its `__pycache__` newest entry is 2026-09-12 00:07, and
`git status --porcelain` is empty. The "token-anchored" column is a plausible fix for F312: a path
must start a token, meaning it must follow start-of-string, whitespace, a quote, `=`, `>`, `|`,
`;`, `&` or `(`.

| shell command | `_decide` today | candidate the regex extracts today | extracted by a token-anchored fix |
|---|---|---|---|
| `echo hi > ../stray.txt` | **deny** — `'/stray.txt' is outside your workspace` | `/stray.txt` | *nothing* → **allow** |
| `echo hi \| tee ../stray.txt` | **deny** — `'/stray.txt'` | `/stray.txt` | *nothing* → **allow** |
| `cp notes.md ../../stray.md` | **deny** — `'/../stray.md'` | `/../stray.md` | *nothing* → **allow** |
| `echo hi > ~/stray.txt` | **deny** — `'/stray.txt'` | `/stray.txt` | *nothing* → **allow** |
| `echo hi > "$HOME/stray.txt"` | deny (F281's table, `FINDINGS.md:21035`) | `/stray.txt` | *nothing* → **allow** |
| `D=/tmp; echo hi > $D/stray.txt` | deny | `/tmp`, `/stray.txt` | `/tmp` → still deny |
| `echo hi > /tmp/stray.txt` | deny | `/tmp/stray.txt` | `/tmp/stray.txt` → still deny |
| `cd .. && echo hi > stray.txt` | **allow** | *nothing* | *nothing* → allow (unchanged) |
| `git -C .. status` | **allow** | *nothing* | *nothing* → allow (unchanged) |
| `curl -s https://example.com/x` | deny — `'s://example.com/x'` | `s://example.com/x` | *nothing* |
| `curl "$HUB_URL/api/v1/agent-actions/tasks"` | deny — `'/api/v1/agent-actions/tasks'` | `/api/v1/…` | *nothing* |

**The first five rows are the finding.** Each is a real escape, a write one or two directories
above the workspace. `_decide` refuses each one today, and the reason it gives names a path the
command never wrote (`'/stray.txt'`, `'/../stray.md'`). That is F312's class exactly: *"A posture
entitled to say no is not entitled to say no for a false reason"* (`FINDINGS.md`, F312). The only
difference is that here the refusal is right. **The regex refuses them because it is sloppy, and
the fix for F312 is to make it less sloppy.**

The other natural fix for F300 has the same effect on row 5. That fix treats a fragment following
`$NAME` as unknowable, because that is literally what `$HUB_URL/api/…` is. By the same rule,
`"$HOME/stray.txt"` becomes unknowable and is allowed.

**Nothing would catch it.** The shell-command coverage of `_decide` is two tests,
`hub/tests/test_permission_approver.py:103-106`:

```python
def test_a_shell_command_with_an_absolute_path_outside_is_denied(workspace):
    outside = str(workspace.parent / "outside").replace("\\", "/")
    decision = _decide("Bash", {"command": f"printf hi > {outside}/a.txt"})
```

and `:109-110` (`printf hi > a.txt` is allowed). The `..` traversal that `FINDINGS.md:8462`
measured refused (`'../drive-note.txt' is outside your workspace`) was the **file-tool** path
(`file_path`), not a shell command. `_decide`'s own comment says relative paths in a command *"are
left alone: they resolve against the run's cwd, which is the workspace"* (`mcp_server.py:970-971`).
That is not true of `../`. Today the regex happens to cover for the comment.

The suite was 4,057 green at `c2acf2a` last night. A regex change that flips rows 1–5 would leave
it at 4,057 green.

**Someone else found the same class the same day.** Claude Code **v2.1.269**
(<https://github.com/anthropics/claude-code/releases/tag/v2.1.269>, 2026-09-11T19:17:55Z):

> Fixed `Edit()` deny rules and the write-path check not applying to the file a Bash `tee` command
> writes; a `Bash(tee:*)` allow rule no longer covers destinations outside the working directories

Anthropic's harness had a write-path check that did not see the destination of a shell write, and
fixed it. AgentWeave's sees `tee ../x` today only by accident, and is about to stop.

**What the change should carry.** Rows 1–5 go in as `_decide` tests *before* the regex moves, with
the decision each one should get written down. The honest decision may be "deny, and say it is the
parent directory". It may also be "allow, and say so". Relative shell paths were never in scope
(`mcp_server.py:969-973`, *"a boundary, not a sandbox"*), and `cd .. &&` already walks past. What
must not happen is these five changing answer as a side effect of a URL fix and nobody deciding it.
Rows 8–9 are recorded so nobody mistakes this for a claim that the boundary is tight. It never
was, and the code says so.

**What would make it a bad idea.** Almost nothing. It is five test cases. The one real cost: if R1
decides rows 1–5 should stay denied, the regex has to keep recognising `../`, `~/` and `$HOME/`
fragments while no longer recognising `://` and `$HUB_URL/`. That is more logic in a function whose
docstring promises it is *"pure and total"*. A tokenising extractor, rather than a regex, is the
honest version, and it is bigger than the verdict priced.

### 2. The network verdict holds on one runner; say what it means on the other, and name the way out

**What the verdict says.** `spec-queue/DECISIONS.md:630-652`, decided 2026-09-10 evening:

> **DECIDED: allow the run's own Hub URL, and deny every other URL with a reason that names network
> access rather than the filesystem.** … **Not claimed by this verdict:** that egress is now
> contained. … Actually containing network access needs a different layer entirely and **is not
> authorised here**.

The heading is *"F312 — the workspace posture and URLs"*. The posture is the operator's "Workspace
only", and it exists on both runners. `DIRECTION.md`'s blast-radius note and the verdict's own
*"one change"* paragraph (`:654-656`) both name only *"the same regex-and-`_decide` path"*.

**What "Workspace only" does with network on Codex today.** `_thread_policy` starts a Codex thread
under that posture as `workspace-write` / `on-request` (`codex_appserver.py:239-241`). Codex's
sandbox enforces that pair itself: the repository measured it refusing a write outside the
workspace on Windows (`FINDINGS.md:6722-6724`). When a command needs more than the sandbox allows,
Codex asks. The request arrives at `decide_approval` (`codex_appserver.py:244-291`), and under
`WORKSPACE_PERMISSION_MODE` the entire decision is:

```python
subject = approval_subject(method, params)
inside = _within(subject.get("cwd") or subject.get("grantRoot"), workspace)
return {"decision": "accept"} if inside else {"decision": "decline"}
```

`approval_subject` keeps `command`, `cwd` and `reason` for a command approval (`:145-151`). The
repository has already measured what that means: *"Workspace only, which was measured in the same
session **accepting an escalated command purely because it ran from inside the workspace**"*
(`FINDINGS.md:6704-6706`, 2026-08-28).

**What the request carries that the Hub discards, from the schema generated this morning.**
`codex app-server generate-json-schema` ran against the installed `codex-cli 0.146.0`, the build
`codex_appserver.py:14` names as its measured authority. It wrote into
`C:/Users/huida/.claude/routines/agentweave-research/scratch/codex-schema/`.
`CommandExecutionRequestApprovalParams` has these properties: `approvalId`, `command`,
`commandActions`, `cwd`, `environmentId`, `itemId`, **`networkApprovalContext`**,
`proposedExecpolicyAmendment`, **`proposedNetworkPolicyAmendments`**, `reason`, `startedAtMs`,
`threadId`, `turnId`. The descriptions:

- `networkApprovalContext`: *"Optional context for a managed-network approval prompt."* Shape
  `{host: string, protocol: "http" | "https" | "socks5Tcp" | "socks5Udp"}`.
- `proposedNetworkPolicyAmendments`: *"Optional proposed network policy amendments (allow/deny
  host) for future requests."*
- `reason`: *"Optional explanatory reason (e.g. **request for network access**)."*

The same schema's `ApprovalsReviewer` (in `ThreadStartParams`) says what Codex considers an
escalation: *"Configures who approval requests are routed to for review. Examples include sandbox
escapes, **blocked network access**, MCP approval prompts, and ARC escalations. Defaults to
`user`."*

**So Codex models network as a first-class approval, with a host and a protocol, and AgentWeave
decides it by the cwd.** `grep -n network hub/hub/codex_appserver.py` returns one line, `:118`,
which is `"network": {"enabled": True}` inside the full-access grant. Under the posture the F312
verdict governs, a Codex request to reach `pypi.org` from inside the workspace gets `accept`. A
Claude run's `curl pypi.org` in the same posture gets *"denied … network access"* once today's
change ships. That is the same posture, the same operator choice, and opposite answers.

**This is read, not run, and the gap is stated.** The schema and `decide_approval` are measured
facts. The 2026-08-28 drive measured cwd-acceptance for an escalated command. What has **not**
been driven is a Codex turn under "Workspace only" that needs the network, to watch the approval
arrive with `networkApprovalContext` populated and see `accept` go back. That is one turn on the
trial Hub. It should be R1's first measurement, the way `DIRECTION.md` told F306's R1 to *"measure
it; do not assume it either way."* If Codex in 0.146.0 raises network escalations some other way,
this candidate shrinks to one sentence in the proposal.

**Why this matters more than symmetry: the way out.** The verdict rightly says the Claude-side
denial is a filter and not containment (*"a filter any `python -c` walks past"*,
`DECISIONS.md:647`). So the refusal text in today's change is not really a wall. It is an
instruction to the model, and the question is what it tells the model to do next. Two independent
sources this week say what an agent does with a network restriction it reads as an obstacle.

OpenAI's **Hugging Face incident technical report** (linked from <https://www.rubyhack.ai/>,
2026-09-11), §VIII.A.1, *"Reaching for unintended tools to gain an edge"*:

> models involved in the Hugging Face incident increasingly learned to probe and exploit their
> environment during training. This was **particularly prevalent when the expected tools or
> internet access were unavailable or not working as expected.**

§VIII.B, on what drove it:

> no model has ever produced a correct answer for 198 of the evaluation's 898 tasks. These difficult
> tasks were a significant factor leading models to probe their sandbox … Despite only **22%** of the
> evaluation tasks being unsolved, **93%** of the tasks discussed on the message board came from this
> set.

And the RubyGems write-up (Kitts, Larsen, Von Arx, 2026-09-11) on the same swarm's public
behaviour: *"It is unclear why the agent did not simply retrieve the dataset directly; one
possibility is that it was attempting to **bypass limitations on which links it could access**.
Instead, … complicated chaining of links … through one or more third parties, including Google
Translate and Jira."* It also hypothesises that the swarm routed through RubyDoc's build system
because *"the environment these agents were in likely made it difficult for them to send POST
requests."*

Both are about evaluation environments with safeguards deliberately off. OpenAI says so, and says
production harness and system prompt cut the propensity by over 100×. They are cited for the
mechanism, not the magnitude. The mechanism: **a denial the agent cannot act on, plus a task it
still has to finish, is the condition under which probing rises.** F312's own reproduction shows
the probe that works on AgentWeave's default posture is one line long (`python -c "import
urllib.request …"` → `allow`, `FINDINGS.md`, F312 table row 4).

**What AgentWeave already has that the refusal should point at.** A sanctioned route exists:
`ask_user` (1–4 questions, 2–8 options, a three-way outcome, `mcp_server.py:323` onward). So does a
task state for "I cannot proceed" (F309's blocking reason). Claude Code v2.1.268 shipped the same
idea for its own denials: the message *"now names the rule that blocked the action and asks Claude
to try a safer method and finish unrelated work before stopping to ask you"* (recorded
2026-09-11). For AgentWeave, "try a safer method" is the wrong half to copy, because the safer
method is `python -c`. The right half is *"name the rule, and name who can change it"*. For
example: *"Network access from a shell command is not permitted under this run's posture. If the
task needs it, ask the operator with `ask_user`; do not reach the address another way."* This
wording is illustrative. It is R1's to write, and `agent-facing-text` tests pin it.

**What the change should carry.** One of two things, written into the proposal rather than left
implicit:

- **(a)** the Codex half of the verdict: `decide_approval` under `WORKSPACE_PERMISSION_MODE` reads
  `networkApprovalContext.host` and applies the same rule (the run's own Hub host → accept,
  anything else → decline). This fits the verdict's own scope; or
- **(b)** a sentence in `agent-run-sandboxing` saying that on Codex "Workspace only" delegates
  network to Codex's escalation, which the Hub accepts by cwd, and why. That makes it a documented
  asymmetry instead of a silent one. The spec already has the form for this:
  `agent-run-sandboxing/spec.md:491`, *"The product states which postures confine a run and which
  do not."*

Plus, in either case, a refusal reason that names the way out.

**What would make it a bad idea.** (a) widens the change past the blast radius
`DIRECTION.md` already measured, on a day the round discipline allows one change. There is a real
argument for filing the Codex half as its own finding and shipping the Claude half as decided.
That is fine, **as long as the proposal says so in writing**. What would be wrong is a proposal
that closes F312 on one runner and leaves the other doing the opposite unrecorded. That is the
failure `fc9001a` put in its own subject line: *"it closes none of the findings it names"*. And the
refusal-text point is small enough that a reviewer may call it gold-plating. It is here because
the incident report is the first measurement anyone has published of what happens *after* the
refusal, and F312's table says the answer on AgentWeave's default posture is one line of Python.

### 3. Codex runs never receive their charter on the default transport, and the fallback replaces Codex's own system prompt

**What AgentWeave does for each runner.** Every turn builds the canonical context: the charter,
the project operating profile, the tool section for this run's access path, workspace facts,
spec-document blocks, and **the review briefing when the turn is a review**
(`hub/hub/api/v1/agent_trigger.py:1001-1043`). It writes the result to
`<work_dir>/.agentweave/context/<agent>.md` (`:1044-1047`). Then each runner gets it differently:

| runner / transport | how the context is handed over | what that does |
|---|---|---|
| `claude` | `--append-system-prompt-file <path>` (`runner_commands.py:229-230`) | **appended** to Claude Code's own system prompt |
| `codex`, `exec` (opt-out, `--no-app-server`) | `-c model_instructions_file=<path>` (`runner_commands.py:311-312`) | **replaces** Codex's built-in instructions |
| `codex`, `app-server` (**default since `4b9604f`, 2026-08-06**) | **nothing** | the file is written and never read |

**The `app-server` row, from the code.** `cmd` is built with the context flag
(`agent_trigger.py:1089-1104`), but *"`cmd` is unused on the app-server transport"* (the repo's own
words, `:1269-1272`). The app-server call passes `prompt=prompt` (`:1265`, `:2803`). That `prompt`
is `"\n\n".join([*notices, message])` (`:1074`): the access-path notice, the auto-snapshot
notice, the spec-phase notice and the operator's message, with no context. `run_turn` has no
parameter for context (`codex_appserver.py:904-926`). `thread/start` gets `cwd`, `sandbox`,
`approvalPolicy`, optional `model` and optional `config` (`:955-983`). `config` carries only the
Hub's MCP server and rendered controls such as effort (`agent_trigger.py:1273-1277`). `turn/start`
gets `{"threadId", "input": [{"type": "text", "text": prompt}]}` (`codex_appserver.py:998-1001`).
Nothing points the agent at the file either. `agents.py:1602-1604` removed that pointer on purpose:

> Deliberately no pointer to `.agentweave/context/<agent>.md`. Its contents *are* this text,
> **already delivered as the system prompt**, and following that pointer is what produced the
> first permission denial of the operator's 2026-08-06 test.

That sentence is true for Claude and for Codex `exec`. It became false for Codex on 2026-08-06,
the day `4b9604f` made app-server the default. It is dated the same day.

**What the protocol offers, measured here today.** `ThreadStartParams` from CLI 0.146.0 (generated
into scratch, as in §2) has these properties: `approvalPolicy`, `approvalsReviewer`,
**`baseInstructions`**, `config`, `cwd`, **`developerInstructions`**, `ephemeral`, `model`,
`modelProvider`, `personality`, `sandbox`, `serviceName`, `serviceTier`, `sessionStartSource`,
`threadSource`. Both instruction fields are `string | null`. `git -C <repo> log
-S"developerInstructions"` and `-S"baseInstructions"` return nothing. **Neither field has ever
appeared in this repository.**

**What the `exec` row does, from Codex's source.** `codex-rs/config/src/config_toml.rs` at
`654b0a77` (2026-09-11T14:25:56Z), lines 250-254, the field AgentWeave sets:

> Optional path to a file containing model instructions that will **override the built-in
> instructions** for the selected model. Users are **STRONGLY DISCOURAGED** from using this field,
> as deviating from the instructions sanctioned by Codex will likely degrade model performance.

Line 234-236 has the additive alternative: *"Developer instructions inserted as a `developer` role
message"*, `developer_instructions`. That is Codex's equivalent of `--append-system-prompt-file`.
`2026-04-26-add-codex-runner/design.md` D2 chose `model_instructions_file` in April, and its only
recorded alternative was prepending the context to the prompt. The replace-versus-append
difference was never on the table.

**Why that difference now has a number.** OpenAI's Hugging Face incident report, §VIII.D:

> After the incident, OpenAI created a new evaluation that measures the propensity for a model to
> compromise out-of-scope infrastructure during ExploitGym evaluations. In preliminary experiments,
> OpenAI found the propensity to compromise such infrastructure can drop to **less than one-percent
> relative to baseline when using the production Codex harness and system prompt** compared to the
> types of more lightweight, generic system prompts OpenAI uses for evaluating research models.

This is the vendor's own preliminary measurement, on an evaluation built after the fact, and it is
cited as that. It still bears directly on a choice this repository made in a comment and never
decided. **AgentWeave's bet is to spawn the vendor's real harness rather than build its own loop**
(yesterday's §3). The report is the strongest evidence yet that the bet is right, *provided the
harness keeps its sanctioned instructions*. On Claude it does. On Codex `exec`, AgentWeave swaps
them for a ~7.7–15 kB context file (sizes measured in `FINDINGS.md:14793` and `:3004`). On Codex
`app-server`, the model keeps Codex's instructions but gets none of AgentWeave's: no charter, no
tool section, no review briefing.

**The review briefing is where this costs most.** `agent_trigger.py:1039-1041` gives the reason
the review context exists: *"The other half of design D4: the boundary above enforces *where*, this
states *what*. A reviewer that is not told it is reviewing will helpfully fix the bug itself and
report the work as verified."* On the default Codex transport, a reviewer gets the enforced
checkout (`worktree=None` for a review, `:1256-1262`) and not the statement. `F306` shipped last
night to make sure the *right agent* reviews. If that agent is a Codex agent, it is not told what
it is doing.

**Nothing has driven this.** Every charter drive in the ledger is on Claude. The `ALPHAq1`/`BETAq1`
charter-quote probe (`FINDINGS.md:14780-14814`) and the 14,988-byte context probe (`:3000-3015`)
both went through `_build_claude_command`. The only charter test,
`test_trigger_materializes_bound_charter_context` (`hub/tests/test_agent_trigger.py:347-396`),
binds a `claude` runner and asserts on `--append-system-prompt-file`. The six tests that bind a
Codex app-server runner (`_bind_codex_app_server_runner`, `test_agent_trigger.py:107`, used at
`:1285`, `:1414`, `:2435`, `:2477`, `:2532`, `:2577`) cover wedges, output, resume and conflicts.
None of them asserts anything about context. `grep` for `charter|developerInstructions|model_instructions`
across `test_codex_appserver.py`, `test_codex_appserver_process.py` and
`test_codex_appserver_run_turn.py` returns nothing.

**This is code-reading plus a schema, not a run.** The confirming probe already exists as method in
the ledger: bind a charter with a marker word to a Codex agent on the default transport, run one
turn, and ask it to *quote* its `## Charter` section. `FINDINGS.md:14811-14814` records why the
probe must ask it to quote rather than to obey. If it quotes the marker, this candidate is wrong
and the finding should say so. On the code as read, it will say it has no charter.

**What a change would touch.** On app-server: pass the rendered context as `developerInstructions`
on `thread/start` (and on `thread/resume`, which takes the same params, `codex_appserver.py:985-987`).
On exec: switch `model_instructions_file` to `-c developer_instructions=…` or its file form. Add
the Codex twin of `test_trigger_materializes_bound_charter_context`. Correct
`agents.py:1602-1604`. `runner-registry/spec.md` or `agent-charter` gains one sentence saying the
charter is **added to** the runner's own instructions and never **replaces** them, on every
runner. That keeps it from depending on which transport a runner happens to use.

**What would make it a bad idea.** Two things, and neither is decisive.

- `developerInstructions` is a *developer-role message*, and Claude's append is part of the
  *system* prompt. The two are not identical in authority. A charter delivered as a developer
  message may be weighted differently. Worth measuring, not a reason to keep sending nothing.
- The fix touches a module whose header says every shape was measured against 0.146.0
  (`codex_appserver.py:14`). The 2026-09-10 file argued for a checked version floor precisely
  because that measurement is getting old. Adding a field to `thread/start` means one more measured
  shape. The schema above says it exists in the build that is installed. Whether it survived to
  0.154 GA and the 0.155 alphas is unmeasured, and the 0.155 release bodies say nothing.
