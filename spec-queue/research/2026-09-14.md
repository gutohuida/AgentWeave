## The evidence

### 1. F352's R1: the dedup's scope first, then the holdings as data, then the one action that frees them

**What F352 asks for, and what it does not see.** F352's last paragraph sets the repair's
constraints without proposing one. Whatever else changes, *"the unstaffed sentence has to name the
holdings — agent → task"*. That is right, and it is the whole of what the operator is shown
(`resolve_reviewer`'s docstring, `scheduler.py:1094-1098`). But the sentence does not reach the
operator directly. It goes through `_emit_review_unstaffed` (`:1944`), which first asks
`_review_unstaffed_already_stands` (`:1978`) whether the same fact was already reported.

**The dedup, read.** `scheduler.py:1913-1941`:

```python
    """Whether the newest `review_unstaffed` for this task already says exactly this.

    Narrow in the same two directions as `_stall_run_to_increment`: the **most recent** record for
    this task, so a condition that cleared and returned is news again, and the **same reason** …
    """
    ...
                select(EventLog)
                .where(EventLog.project_id == loop.project_id)
                .where(EventLog.event_type == "review_unstaffed")
                .where(EventLog.loop_id == loop.id)
                .order_by(EventLog.timestamp.desc(), EventLog.id.desc())
                .limit(1)
    ...
    return data.get("task_id") == task_id and data.get("reason") == reason
```

The docstring says the most recent record **for this task**. The query takes the most recent record
**for the loop** and only then compares the task. With one unstaffed task these are the same thing.
With two, a firing emits for A, then asks about B and finds A's event newest, so it emits again. The
next firing finds B's event newest when it asks about A, and emits again. **With two or more
unstaffed tasks, nothing is ever suppressed.** `_emit_review_unstaffed` persists *and* broadcasts
over SSE (`:1990-1995`), so every one of those events reaches the operator's screen.

**What tested it.** The dedup's tests, `hub/tests/test_a_review_nobody_is_doing.py:527-570`, each
build **one** wedged task. The first fires five times and expects one event, and the second changes
the reason and expects two. Neither can see the alternation. The dedup came in with `001a07d`
(2026-08-31, *"impl(F154): a firing stops claiming work nobody is doing"*).

**Where it has already happened, probably.** F352: *"Fourteen firings, 21:20 to 22:30 UTC, each
recorded `review_unstaffed` for the two finished tasks the rest of the flow waited on
(`task-611ae46fe0fb` …, `task-c8d4a3d70c19` …)"*. If "recorded" means `review_unstaffed` rows, the
code as read predicts **28** where the design intends **2**. **O-2 can settle it with one `mode=ro`
count** of `event_logs` where `event_type = 'review_unstaffed'` and `loop_id =
'loop-103ecb8aeb89'` in that window. That is read-only and within the day's rules.

**Why it matters more after the fix than before.** Today the reason is a constant sentence per
excluded-clause, so the defect costs one duplicate per task per firing. Once the sentence names
holdings (*"Architect holds `task-9e89…` (under review, outside this flow); dev holds …"*), its text
changes whenever any agent's holdings change. That is correct, because a changed fact is news. But
combined with the loop-scoped dedup, the activity feed gets every unstaffed task on every firing
with churning text. The dedup has to be per task **before** the sentence becomes specific, or the
fix for *"the reason it gives names nobody"* becomes a feed nobody reads.

**What exists elsewhere.** The Kubernetes scheduler has solved "why can nothing take this work" at
scale, and its shape answers two of F352's open questions. `pkg/scheduler/framework/types.go`
(<https://github.com/kubernetes/kubernetes/blob/master/pkg/scheduler/framework/types.go>, file last
changed 2026-09-09T04:14:33Z, fetched today):

- **The diagnosis is data first, and text second.** `Diagnosis.NodeToStatus` *"records the status of
  nodes … if they're rejected in PreFilter … or Filter plugins"* (`:1320-1334`). The message is
  derived from it.
- **The message is a count plus a reason for each candidate class.** `NoNodeAvailableMsg = "0/%v
  nodes are available"`, then a sorted histogram of reasons (`:1367-1406`). For example: `0/4 nodes
  are available: 1 node(s) had untolerated taint, 3 Insufficient cpu.`
- **Then what would free a slot.** The `PostFilterMsg` (`:1409-1417`) is where preemption reports
  whether evicting something would make room.

Kubernetes aggregates because it has thousands of nodes. AgentWeave rosters have four, so it can
name each agent and task outright. The structure transfers: **a per-agent status recorded in the
event's `data`**, `{agent: [{task_id, status, in_this_flow}]}`, with the sentence rendered from it.
That also gives the dedup something better to compare than prose: compare the per-task status map,
not the string.

**The third part, what frees a hold, is F353, and a stranger shipped the same move last night.**
Cline desktop **v0.0.27** (<https://github.com/cline/cline/releases/tag/desktop-v0.0.27>,
2026-09-13T22:28:16Z): *"Credential failures also carry a fix button: **Sign in to Cline** for the
Cline provider … **Open model settings** for others."* F353 records that the one action that would
have unblocked LoopEngine, **Land it**, exists in the drawer and *"neither this refusal nor the
flow's `review_unstaffed` sentence points to it."* The data shape above lets the UI put the control
beside the holding it clears, just as Cline's error carries its fix.

**What the repair must keep.** Holding counts as busy **on purpose**. D4 rejected "not running"
alone *"because an agent can hold three assigned tasks and be idle between turns, which is the
pile-up the operator named as the thing to avoid"* (`scheduler.py:981-984`). Whatever scope R1
chooses (flow, loop, or project with `pending` excluded), the proposal should show that the
operator's pile-up case still refuses. A test with an agent holding three `in_progress` tasks
**inside** the flow must still report that agent busy.

**What would make it a bad idea.** Recording holdings in the event's `data` puts task ids into an
SSE payload the UI already renders, which is no new exposure. But the event rows grow, and
`event_logs` is already 3,492 rows on LoopEngine. The per-task dedup is a one-line `where`. It is
the least contestable part of this candidate, and if R1 has room for only one thing from here, it
should be that.

### 2. F354's R1: pin the tool server by content, and make both halves of the tool surface come from the same bytes

**What F354 proposes.** *"A repair could pin the server the Hub loaded — copy `mcp_server.py` aside
at startup and spawn the copy — so an agent's tool surface changes when the Hub restarts, like the
rest of its Python."* The direction is right. Four things the sketch does not cover were checked
this morning.

**(a) The file is the approver, not only the tool surface.** `agent_trigger.py:1084-1087` spawns
`[sys.executable, <hub>/mcp_server.py]` for every turn on the MCP path. Python never caches
bytecode for a script run as `__main__`, so each spawn compiles whatever the file holds at that
moment. That file contains `_lex` (`mcp_server.py:1174`), `_read_command` (`:1272`), `_decide`
(`:1301`) and `approve_tool_call` (`:1453`). Those four are the permission approver that the
`workspace` posture names through `--permission-prompt-tool`. **A turn's approver is whatever the
working tree holds at the second the turn starts.** Codex's approvals are decided in-process by
`decide_approval` in `codex_appserver.py`, which is loaded at Hub start, so the two runners differ
here too.

**(b) The measurement that turns F354 from hypothetical to "unknown".** From the OS (read-only, the
way `day-window.md` prescribes): `:8000` is **PID 12480, `pythonw`, started
2026-09-13T19:15:07+01:00**. The last *commit* to `mcp_server.py` is `612b9c9`
(2026-09-12T23:54:19+01:00). That is before the start, so committed code has not drifted, and the
file is clean in the tree now (sha256 `a895f6e9…c5521`). But F354 saw **uncommitted** edits at 22:31
UTC. The night log places them: F332 §1 closed at `1ebff15` (22:12:57 UTC), §2 was then built *"not
committed"*, and `b1fbd5a` stopped it at 22:37:06 UTC. `DECISIONS.md` `OPEN F332-rule` says what
that §2 code did when measured: *"It **allows two writes outside the workspace that today's lexer
refuses**, on Windows only."* F352 records that *"the 22:35 firing started `dev` on
`task-49b0567ce119` and `tester` on `task-c9787d4be5e1` in parallel."*

So two of the operator's live turns started **inside the window in which the tree may have held an
approver measured to have an escape**. Whether the edit was still there at 22:35 is recorded
nowhere. The risk that was actually realised is close to nil: the escape needs a command like
`mkdir A; echo hi > $'A\Uffffffff/../../x'`. The finding is that **nobody can say which approver
judged those two turns.** O-2 can narrow it by reading the two runs' start times and whether either
made a shell call that went through `approve_tool_call`. It cannot close it.

**(c) The Hub imports the same module separately, at a different moment.** `agents.py:923-936`,
`_operations()`:

> Constrained values are taken from `mcp_server`'s own `Literal` aliases, **so this cannot drift
> from the schema clients receive.** Imported inside the function because `mcp_server` is spawned
> standalone and is not imported at this module's scope.

A function-level import runs once, at first call, and is then cached for the life of the process.
The spawned server re-reads the file every turn. After any edit, the **tool section** the Hub
writes into every agent's context (`agents.py:1449`, `for operation in _operations()`) comes from
the old bytes, while the **schema** the agent's server exposes comes from the new ones. The same
module's docstring (`:1421-1425`) records what that costs: *"this list has now fallen behind the
server twice. The second time cost a completed interview … **A silently incomplete inventory is
worse than none, because the agent believes it.**"* `test_tool_surface_matches_server.py` checks
the two at build time, from one checkout. It cannot see a live Hub whose halves were loaded at
different moments. F354's sketch pins the spawned half only. The in-process import must load the
same pinned copy, or the fix moves the drift instead of removing it.

A static import map of `hub/` (AST, module-level versus function-level imports, reachability from
`hub.main`; script and output in scratch) found that **127 of 130 modules load with the app, and
three load only at first call**: `hub.mcp_server` (from `agents.py`), `hub.turn_scheduler` (from
`agent_trigger`, `agents`, `accounting`, `checkpoints`) and `hub.checkpoint_trigger`. CLAUDE.md's
*"a Python change reaches it only when the operator restarts it"* therefore holds exactly for 127
modules. For the other three it holds only from their first use. Whether `drain_deferred_schedules`
(`main.py:471`) already loads `turn_scheduler` at startup is unmeasured, and a static map cannot
see `importlib`. This is secondary. Importing the three eagerly in the lifespan would make the
sentence true.

**(d) "Aside" has to mean verified.** SEP-2640, *Skills Extension*
(<https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640>, merged
2026-09-13T21:27:51Z, `Status: Final`, `seps/2640-skills-extension.md`) sets the rule for exactly
this: content a host verified once and later loads again from disk.

> A cached copy is only as trustworthy as the host's certainty that its bytes have not changed since
> they were verified … Hosts that cache skill content on disk MUST therefore do one of the following
> for every file served from the cache: keep the cache where **nothing but the host can write to it
> (not the model, not scripts or tools the model runs, not other users of the machine)** and never
> modify a cached file in place; or **recompute the file's SHA-256 digest from the cached bytes on
> each access** and compare it against the entry's digest … **Comparing a stored digest label, or a
> modification time, is not verification.**

and, on approvals:

> When a host persists any per-skill user approval, it MUST be bound to the entry's `resources` set
> (every `uri` and `digest`) observed at the moment of approval. If a subsequent entry … advertises
> a different set … the host MUST treat the prior approval as revoked.

For AgentWeave the first option does not exist. Every agent runs as the operator's own user, and
under the full-access postures it can write anywhere that user can. So the pinned copy has to be
**re-hashed at each spawn**. At 1,841 lines that costs next to nothing. On a mismatch, the Hub
should spawn nothing from the copy, say why, and keep the turn alive by re-copying from the bytes it
hashed at startup, which it holds in memory. **Record the digest on the `Run`**, as one nullable
column or on the run's start event. That answers "which approver judged this run" for every future
case like (b). It is the Hub-side half of the *record the build* item this routine has carried
since 2026-09-09.

**Why it is buildable today and what it unblocks.** None of this edits `mcp_server.py`. It touches
`agent_trigger.py:1086`, the lifespan in `main.py`, and `agents.py:930`. So the day's rule does not
stop it, and once it is built and `:8000` restarts, **the rule that stops every other
`mcp_server.py` fix on a build day can be retired**, F332's lexer included.

**What would make it a bad idea.** Two real costs.

- **A security fix to `_decide` stops reaching `:8000` on the next turn.** Today F332's eventual fix
  would protect the operator's agents the moment it is committed. After pinning, it waits for a
  restart. That is the same trade as every other module, and it is the right one. It means an
  `mcp_server.py` change should be listed on the review page like a migration: *"takes effect on
  `:8000` at the next restart."*
- **Developer ergonomics.** Editing the server on a running Hub no longer takes effect per turn. The
  loop's own procedure already assumes restart semantics: *"Restart it from the branch's code before
  drawing any conclusion, and confirm no `.py` under `hub/hub` or `src` is newer than the process
  start time"* (`day-window.md:362-363`). So the loop loses nothing, and interactive sessions lose
  hot pickup.

One thing it does not pin is `fastmcp`, which the spawned server imports fresh from site-packages
(`mcp_server.py:19`). A `pip install -U` in that interpreter changes the server under a running Hub.
The `fastmcp <4` bound limits that and does not pin it. The server's reported version could go in
the same `Run` field.

### 3. Production SQLite runs the lock regime the suite rejects as a flake class, and the decision was never raised

**The two regimes, side by side.**

| | production (`hub/hub/db/engine.py:36-40`) | test suite (`hub/tests/conftest.py:86-115`) |
|---|---|---|
| journal | SQLite default, rollback (`delete`; measured on the operator's DB in F351) | `journal_mode=WAL` |
| busy timeout | pysqlite default, **5 s** | **30 s** |
| synchronous | `FULL` (default) | `OFF` |
| alembic | `timeout: 30.0` (`migrations/env.py:92-98`) | `timeout: 30.0` |

The suite's own docstring gives the reason, and it is the argument for changing production:

> WAL rather than the faster `journal_mode=MEMORY`, deliberately. **Under a rollback journal a
> writer holds an exclusive lock across its commit and readers block on it, so the sessions this
> change exists to let run concurrently would contend for the file and some would surface `database
> is locked` after the busy timeout** (30s here, raised from SQLite's 5s default …). Trading F285's
> shared-connection rollback for **a fresh `SQLITE_BUSY` flake class would be no fix at all.** …
> These pragmas are per-connection and set only here, in the suite — **production keeps SQLite's
> defaults.**

`test_migrations.py:570-595` pins alembic's 30 s timeout with the message *"alembic's engine must
match the main engine's busy timeout (30s)"*. The main engine has 30 s only under the suite's
listener. In production, alembic now waits six times longer than the Hub it migrates for.

**The decision that was left and never raised.** F89 (`FINDINGS.md:6171-6175`), fixed at `7cecd71`:
*"The engine opens SQLite with neither WAL nor an explicit `busy_timeout` … WAL would make readers
stop blocking writers at all and would have made this defect a slowdown instead of a wedge. It is
also a deployment-visible change — extra `-wal`/`-shm` files, and it does not work over a network
filesystem — so it is a decision rather than a repair."* `grep -n WAL spec-queue/DECISIONS.md`
finds nothing. The decision exists in a finding's closing paragraph and in no ledger an operator
reads.

**What has happened since.** The two newest lock findings are both the production class, and both
were filed on 2026-09-13:

- **F351 (A):** a job lost because an insert waited *"6.3 s"* against *"pysqlite's default busy
  timeout [of] 5 s"*. Worse, *"the scheduler stops waking for every job"*. It was fixed by taking
  the job store off the database, which removes one writer and leaves the regime as it was.
  DEAD-ENDS (`.claude/handoffs/DEAD-ENDS.md:331-339`) generalised it: *"A synchronous SQLite call on
  the event loop deadlocks against ANY open async write … (journal mode `delete`)"*.
- **F349 (B), open:** two simultaneous `POST …/agent/trigger` requests, and *"one returned **500**
  with `database is locked`"* while the message was delivered anyway.

LoopEngine is the first production workload with parallel agents: F352 records *"started `dev` …
and `tester` … in parallel"*. Each streams output rows and context-usage snapshots, each in its own
session (`agent_trigger.py:2208-2212`). That is the concurrency the suite's docstring describes, on
the regime the docstring rejects.

**Why today's review cannot see it directly.** DEAD-ENDS `:340-343`: *"The operator's Hub (port
8000) logs to `DEVNULL` … so a `logger.error` there is unrecoverable. Evidence has to come from what
the Hub persisted."* The desktop shortcut runs `pythonw` (CLAUDE.md), and `_hub_native_start`
passes `stdout=_sp.DEVNULL, stderr=_sp.DEVNULL` (`src/agentweave/cli.py:1086-1087`). So O-2 should
look for the **shadow** DEAD-ENDS names: *"a ~5–6 s gap between two writes a request makes back to
back"* in `event_logs` timestamps. The absence of error lines proves nothing, because the errors
were never kept.

**What a decision row would put to the operator.** One question: *production adopts the suite's
regime (WAL, 30 s), or the suite adopts production's (so the product's lock class is visible in CI),
or both stay and the difference is written down.* Evidence: F89, F349, F351, and the two docstrings
above.

**What would make it a bad idea, and this is not small.** WAL has its own `database is locked`, and
this repository measured it. DEAD-ENDS `:315-322`: *"in WAL, a connection that took a read snapshot
and then asks to upgrade to a write is refused **immediately, `busy_timeout` ignored, with nothing
holding the file** … Measured side by side: **0.000 s** (snapshot, 30 s timeout ignored) vs **2.234
s** (real holder)."* SQLAlchemy sessions read and then write all the time. Switching production to
WAL trades a 5-second wait class for an instant-refusal class, unless the write paths begin with
`BEGIN IMMEDIATE`, which the suite's schema reset already does (DEAD-ENDS `:312-314`). Other costs,
per <https://sqlite.org/wal.html> (fetched today):

- *"All processes using a database must be on the same host computer; WAL does not work over a
  network filesystem."*
- The quasi-persistent `-wal`/`-shm` files, which break a backup that copies `agentweave.db` alone
  while the Hub runs.
- A `mode=ro` reader, which is how the day window reads `:8000`, now needs *"the -shm and -wal files
  [to] already exist or … can be created"*. They can in the operator's own profile directory, but
  it is a changed precondition for the loop's own instrument.

### 4. A stopped or interrupted Claude turn spends tokens no budget sees, and the harness already wrote them down

**What AgentWeave does today.** The accounting for a Claude turn comes from the `result` line only:
`usage` first (`runner_parsing.py:333`), then `modelUsage` (`:309`). The per-message `usage` on
each `assistant` event (`:273`) becomes a *context* sample for the meter, not accounting. The
shipped spec says so on purpose: `usage-accounting/spec.md:35-39`, *"Claude final result is
authoritative … partial samples are not added as additional turns"*. A turn that ends without a
`result` line gets `sample=None` or an allowance-only sample, which is **`unavailable`**
(`usage_accounting.py:36-42`). That covers an operator stop, a kill, a Hub restart
(`run_reconciliation.py:70-86`), and a harness that exits mid-turn. The budget brake sums measured
rows only (`budget_state`, `usage_accounting.py:99-106`), and the scheduler consults it at admission
(`turn_scheduler.py:378`). **Spend that ended any way but cleanly never reaches the brake.**

The reconciliation comment already knows the cost: *"This run has ended. **Its tokens were spent —
one of the three specimens that found this had been streaming for thirteen minutes** — and the
process that could have read the telemetry died with it, so `unavailable` is the true outcome."*

**Measured this morning, three ways.**

*How often, on this machine.* A `mode=ro` census of every drive and trial database under
`~/.agentweave/hub/profiles/` (13 databases; `live` skipped, `:8000`'s never opened). Script:
`scratch/usage/profiles.py`.

| run status | usage `measured` | usage `unavailable` | typical duration |
|---|---|---|---|
| `completed` | **92** | 0 | — |
| `failed` | 0 | **12** | ~0 s (spawn failures, nothing spent) |
| `interrupted` | 0 | **3** | median 20 s, max 26 s |
| `stopped` | 0 | **2** | 19 s |

The rule is exact in this sample: **a run is measured if and only if it completed.** The drive runs
are short test turns, so the tokens involved here are small. LoopEngine's are not, which is why O-2
should run the same `group by` on `:8000` (`runs` left-joined to `turn_usage`) and report the
unavailable count by status beside the project's measured total.

*What the stream carries.* One Haiku turn (`claude --model haiku --output-format stream-json
--verbose`, two Reads, 2.1.269, workspace in `%TEMP%` and deleted; `scratch/usage/`):

| source | input | output | cache read | cache write | total |
|---|---|---|---|---|---|
| `result.usage` (what the Hub records) | 26 | 308 | 68,501 | 8,061 | **76,896** |
| `assistant` events, **deduplicated by `message.id`** | 26 | **5** | 68,501 | 8,061 | 76,593 |
| `assistant` events, summed naively | — | — | — | — | **178,518** |
| the harness's transcript `.jsonl`, deduplicated by `message.id` | 26 | **308** | 68,501 | 8,061 | **76,896** |

Two traps are visible in the stream. Claude Code emits one `assistant` event **per content block**
(thinking, text, tool_use), each repeating the same message's `usage`, so a naive sum is 2.3× the
truth. And the stream's `output_tokens` is the value at message start (3, 1, 1), not the final
count.

*What the transcript carries.* Claude Code writes every session to
`~/.claude/projects/<cwd-slug>/<session_id>.jsonl` as it goes. The probe's own file held the
**final** per-message usage (output 169 + 107 + 32 = **308**), so summing it by message id
reproduces `result.usage` **exactly**, on every dimension. A stranger measured the same thing at
scale (r/ClaudeAI, 2026-09-14T05:11Z, <https://www.reddit.com/r/ClaudeAI/comments/1wfu8eh/>,
self-reported): *"Both tools write every session to a disk as JSONL containing per-response token
count … 3,171 sessions – 30.1B tokens recorded – 92.7M of those were generated output, so 0.3%."*
The LoopEngine review is already reading those transcripts (`DIRECTION.md`: *"transcripts in 25
directories matching `~/.claude/projects/C--Users-huida-Documents-projects-LoopEngine*`"*).

**The gap.** For every ending except a clean one, the Hub has two exact records within reach. It
sees the first (the stream) and discards it. It never reads the second (the transcript), which
survives even a Hub crash. It records `unavailable` instead. The spec's refusal to *invent* numbers
is right. But a transcript's usage for completed API calls is not invented. It is the harness's own
measurement, missing only the one call in flight when the process died.

**Why now, from outside.** arXiv **2609.11987**, *"Harness or Model? Isolating the Harness Effect in
Agentic Coding"* (revised 2026-09-08, in the 2026-09-14 cs.SE listing,
<https://arxiv.org/abs/2609.11987>): *"On the Anthropic account **58 runs left no usage record**,
and allocating that spend to either cell would **move the Opus ratio between 0.7 and 2.3**, so the
billed ordering is unresolved. This revision corrects an August 2026 manuscript whose cost figures
rested on **a usage-semantics defect in our own telemetry**."* The unmeasured share decided their
answer. The same paper: *"**22 of 81 runs cancelled at the wall-clock ceiling had produced a passing
patch**"*. The runs that end uncleanly are not the idle ones.

**What a change would touch.** At a non-`result` ending, while the Hub still knows the run's
`session_id` and cwd: read the transcript, keep the last usage seen per `message.id`, sum it, and
record it under a third status, say `partial`, labelled as *"completed calls only; the call in
flight is missing"*. `record_turn_usage` gains the branch. `TurnUsage`'s `CheckConstraint`
(`db/models.py:1231-1238`) gains the value, which needs a **migration**, so it goes on the review
page. `usage-accounting/spec.md` gains a scenario beside *"Missing usage is unavailable"*, and the
budget decides whether `partial` counts. It should: a lower bound is still spend.

**What would make it a bad idea.**

- **The transcript is not a documented contract.** Its path slug and line format are Claude Code's
  internals, and they change with the version like the `init` event does (F340). A parser must treat
  anything unrecognised as `unavailable`, never as zero.
- **Subagent sidechains** may be written elsewhere or marked inside the file. Unmeasured today. A
  turn that used the Task tool could be undercounted or, worse, double-counted.
- **It reads a file full of conversation content to get six integers.** Only the `usage` fields and
  `message.id` should be read. For Codex, whose own session files are a different format and whose
  runner is undrivable, it would be a separate change.
- **If the day has no room**, the cheaper half is the O-2 count above. It turns "the budget
  undercounts" from a code-read into a number on the operator's own project.
