### The error is F292, and today it finally carried a working instrument

`sqlite3.OperationalError: database is locked` on `DROP TABLE requirement_drift`, at the `app`
fixture's schema reset in `hub/tests/conftest.py:713-716`. This is F292, occurrences **#13, #14 and

The valuable part: `d1c` (2026-09-08) built a **per-stage census** into the F292 diagnostic and
noted it had **never fired** — the six runs after it were all green. It fired three times today, and
all three printed the same thing:

```
[before dispose]  0 with an OPEN sqlite3 handle
[before drop_all] 0 with an OPEN sqlite3 handle
[at failure]      1 with an OPEN sqlite3 handle -- idle, worker thread alive
```

Read with `d1c`'s own mutation-checked criterion — *a holder reads `IN TRANSACTION`, a victim reads
`idle`* — the single late handle is the **victim**, almost certainly the DROP's own connection
returned to the pool before the `except` block sampled (`Connections in pool: 1`,
`Checked out: 0` agrees). Not the holder. So **the early sampling came back empty, three times**,
which is the branch `d1c` explicitly called *"the strong result"*.

Three things follow, and two of them change where the next window should look.

1. **The dispose-before-drop mitigation works and cannot be the fix.** `conftest.py:706` was written
   for a previous test leaving a connection checked out. At `[before drop_all]` zero connections
   this process opened hold the file, in all three runs. The file is clean at that instant; the
   holder arrives after it. Tidying earlier cannot help.
2. **The child-process candidate is demoted.** `d1c` named a lingering subprocess as *"the candidate
   class to look at first"* on exactly this result. Measured: `grep -c subprocess` over both erroring
   files returns **0 and 0**, and in each run the immediate predecessor is a test in the **same
   file** — no subprocess anywhere in the failing neighbourhood. Not ruled out as a class; no longer
   first.
3. **The un-awaited background task is promoted.** All three predecessors are flow-fires-a-review
   tests (`a_flow_staffing_its_own_review_is_not_refused`,
   `an_unstaffable_review_does_not_stop_the_flow_doing_other_work`), and both erroring files are the
   scheduler-flow files. That is the shape of `agent_trigger.py:1190`'s un-awaited
   `asyncio.create_task(_execute_run(...))`: a staffed review fires a turn, the turn's task outlives
   its test, and a task torn down at loop close is cancelled — which is precisely the
   `CancelledError` in `_finalize_fairy` → `_reset` → `do_rollback` that the pool log records in all
   three runs. It still names no holder; nothing measured here attributes that `CancelledError` to a
   connection identity.

**And the limitation is the same one, for the third time.** Every sample is taken either side of the
30-second busy-timeout wait, never inside it — so a holder that acquires the lock after
`[before drop_all]` and releases before the report is invisible at all three stages, which is
exactly the profile the evidence now describes. The next instrument has to sample **concurrently**,
from a separate task while the DROP is blocked, and attribute each `sqlalchemy.pool` ERROR to a
connection identity instead of logging it unattributed. Both are `hub/tests/conftest.py`-only, so
they are inside this window's scope guard — but they are an instrument change, which is `D-6`
territory, not `D-0`'s.

Written to `scripts/drive/FINDINGS.md` as a new section under F292, plus a superseding note on the
entry's `**Status:**` paragraph pointing at it — the entry is 1,100 lines and a reader who starts at
the top gets the falsified reading first.
