### What was actually wrong, measured rather than reasoned

Two probes, both in a real browser:

1. **The timeline.** After clicking *Move to blocked*, `document.activeElement` is `BODY` at `+0ms`
   and still `BODY` at `+2000ms`, while the input is mounted the whole time. So the effect was not
   losing a race with something slower — whatever took the keyboard took it and kept it.
2. **The trap.** With the menu open, `focus()` on an element *outside* it returns
   `DIV role=menu` immediately and again at `+200ms`. Radix's focus scope pulls any outside focus
   straight back to the menu container within the same tick.

Together they name the cause: Radix flushes an item's `onSelect` **synchronously** —
`dispatchDiscreteCustomEvent` wraps it in `flushSync` — so `setBlockingReason('')` commits, the
input mounts, and §4's effect focuses it *while the menu is still open and still trapping*. The
trap yanks the keyboard back; the menu then unmounts with `onCloseAutoFocus` prevented, exactly as
§3.3 intends, and focus lands on `document.body` because the element holding it has just been
removed. **§3's "stand aside on close" is necessary and was not sufficient.** Every round read this
component and none asked *when* the selection's own action runs.

### The fix: the menu hands the keyboard over instead of the control grabbing it

`RowMenu`'s ref stops holding a boolean and holds the pending action. An item that declares
`takesFocus` no longer runs its `onSelect` at selection time; the action is held and run from
`onCloseAutoFocus`, after `preventDefault()`, by which point the scope has torn down and the
control's own focus sticks. Everything without the flag is untouched and still fires immediately
with Radix's focus return intact — which is what §7.5 exists to check.

No `setTimeout` and no `requestAnimationFrame` anywhere (§4.3 holds), no passthrough prop and no
`modal={false}` (§3.5 holds), and the drawer still has exactly one mechanism that focuses the input.
Recorded in `tasks.md` as a new **§3.2a**, ticked, rather than folded silently into §3.2 — the
proposal did not contain it and the next reader should see that the drive is what produced it.

**Mutation-checked.** Replacing `opensAControl()` with `void opensAControl` — a deferred action
that is never run — fails `taskDetailDrawer.test.tsx` **by name** at the reason-panel assertion
(`1 failed | 13 passed`). Restored byte-identically afterwards. So the one risk the deferral
