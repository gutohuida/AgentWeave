### D-2 — R1 for F295, and the finding's title names the wrong trigger

`openspec/changes/2026-09-07-a-dead-connection-is-never-handed-back-out/` —
`proposal.md`, `design.md`, `tasks.md` (19 tasks), and an `app-lifecycle` delta with two ADDED
requirements. `openspec validate --strict` passes.

**The round did not take the finding's word for the mechanism.** Two shapes were run standalone under
`py -3.11` against the installed `aiosqlite 0.22.1`:

| | coroutine cancelled | loop closed under the in-flight call | worker thread | connection reused |
|---|---|---|---|---|
| A | yes | no | **alive** | **succeeds** |
| B | yes | yes | **dead** | **hangs** |

Shape A is the shape `F295`'s title describes — *"a cancelled or superseded run's background task
can leave a permanently dead worker thread"* — and it is benign. `set_result` is
`if not fut.done(): ...` (`aiosqlite/core.py:32-34`) and a cancelled future is already done, so the
worker's report is a no-op and the thread returns to `tx.get()`. **Cancellation is how a run gets
abandoned mid-write; it is not what kills the connection.** The precondition is the *event loop
closing* while a synchronous call is in flight, which is `F295`'s second half and is exact, doubled
traceback and all.

Three further things were measured, and two of them killed the obvious repairs:

1. **A timeout does not rescue you.** `asyncio.wait_for(..., timeout=6)` around a whole
   `engine.begin()` + `execute()` on a dead-thread connection did not return; the process ran to a
   2-minute external kill. Unwinding the cancelled task needs SQLAlchemy to *close* the connection,
   which needs the thread that died. So bounding the wait is unsound here, and the proposal says so
   rather than adding one.
2. **A `checkout` guard raising `DisconnectionError` alone also hangs** — invalidation closes the
   connection it is discarding, same dead end.
3. **Neutralise-then-raise recovers.** Setting the aiosqlite `Connection`'s `_running = False` and
   `_connection = None` first makes `close()` a documented no-op (`core.py:199-201`); then:

   ```
   worker alive after kill: False
   RECOVERED, select 2 -> 2
   ```

   The thread in that run was killed by the real mechanism — a queued `(future, function)` whose
   future belongs to a closed loop — not by faking `is_alive()`.

**And a correction R1 owes the record: the production blast radius `F295` claims is not established.**
Read out of the code, the Hub's only in-process loop closure is process exit — `lifespan`'s teardown
is `terminate_all_active_runs()` + `shutdown_scheduler()` (`main.py:356-358`), neither of which
touches a connection, and then uvicorn's `asyncio_run` cancels the leftovers and closes the loop.
The one other `asyncio.run` is alembic's, and it disposes its own engine in a `finally`
(`migrations/env.py:73`), a hole already closed on 2026-09-06. Nothing in production calls
`.cancel()` on an `_execute_run` task: `grep -rn "\.cancel()" hub/hub/ --include=*.py` returns two
live sites, both Codex reader tasks. So what production gets today is an uncaught worker-thread
traceback at shutdown on a process that is leaving anyway; where the damage is *demonstrated* is the
test suite, which closes a loop per test against a process-global engine.

That is written into the proposal as an open question for R2/R3 rather than settled by R1 — the
severity is theirs to adjudicate, and `design.md` names it as the load-bearing negative that is easy
to assert and hard to earn.

The change is worth making at either severity: the fix for the small production case and the large
test case is the same pair — settle the background runs and dispose the engine while the loop still
runs, and never hand out a connection whose driver worker is gone.

**Not conflated with F292**, per DIRECTION.md. `F292` stays open, and the proposal explicitly
declines to claim it is resolved.
