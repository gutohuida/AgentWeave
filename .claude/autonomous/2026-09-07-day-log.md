**The round did not take the finding's word for the mechanism.** Two shapes were run standalone under

| | coroutine cancelled | loop closed under the in-flight call | worker thread | connection reused |
|---|---|---|---|---|
| A | yes | no | **alive** | **succeeds** |

Shape A is the shape `F295`'s title describes — *"a cancelled or superseded run's background task
can leave a permanently dead worker thread"* — and it is benign. `set_result` is
`if not fut.done(): ...` (`aiosqlite/core.py:32-34`) and a cancelled future is already done, so the
worker's report is a no-op and the thread returns to `tx.get()`. **Cancellation is how a run gets
abandoned mid-write; it is not what kills the connection.** The precondition is the *event loop
closing* while a synchronous call is in flight, which is `F295`'s second half and is exact, doubled
traceback and all.

Three further things were measured, and two of them killed the obvious repairs:

1. **A timeout does not rescue you.** `asyncio.wait_for(..., timeout=6)` around a whole
   `engine.begin()` + `execute()` on a dead-thread connection did not return; the process ran to a
   2-minute external kill. Unwinding the cancelled task needs SQLAlchemy to *close* the connection,
   which needs the thread that died. So bounding the wait is unsound here, and the proposal says so
   rather than adding one.
2. **A `checkout` guard raising `DisconnectionError` alone also hangs** — invalidation closes the
   connection it is discarding, same dead end.
3. **Neutralise-then-raise recovers.** Setting the aiosqlite `Connection`'s `_running = False` and
   `_connection = None` first makes `close()` a documented no-op (`core.py:199-201`); then:

   ```
   worker alive after kill: False
   RECOVERED, select 2 -> 2
   ```

   The thread in that run was killed by the real mechanism — a queued `(future, function)` whose
   future belongs to a closed loop — not by faking `is_alive()`.

**And a correction R1 owes the record: the production blast radius `F295` claims is not established.**
Read out of the code, the Hub's only in-process loop closure is process exit — `lifespan`'s teardown
is `terminate_all_active_runs()` + `shutdown_scheduler()` (`main.py:356-358`), neither of which
touches a connection, and then uvicorn's `asyncio_run` cancels the leftovers and closes the loop.
The one other `asyncio.run` is alembic's, and it disposes its own engine in a `finally`
(`migrations/env.py:73`), a hole already closed on 2026-09-06. Nothing in production calls
`.cancel()` on an `_execute_run` task: `grep -rn "\.cancel()" hub/hub/ --include=*.py` returns two
live sites, both Codex reader tasks. So what production gets today is an uncaught worker-thread
traceback at shutdown on a process that is leaving anyway; where the damage is *demonstrated* is the
test suite, which closes a loop per test against a process-global engine.

That is written into the proposal as an open question for R2/R3 rather than settled by R1 — the
severity is theirs to adjudicate, and `design.md` names it as the load-bearing negative that is easy
to assert and hard to earn.

The change is worth making at either severity: the fix for the small production case and the large
test case is the same pair — settle the background runs and dispose the engine while the loop still
runs, and never hand out a connection whose driver worker is gone.

### Four corrections, and one open question answered

1. **The timeout measurement was of the symptom, not the reason.** R1 wrote "did not return at 6
   seconds", which is equally consistent with a broken timer — and a broken timer would have made a
   different repair look promising. `probe_timeout_reason.py` separates them: with the statement
   `shield`ed, `TimeoutError` fires at **4.0s, on schedule**, task still pending; an explicit
   `task.cancel()` afterwards had **not completed six seconds later**; `task.get_stack()` came back
   **empty**, which is where a task parked inside SQLAlchemy's greenlet sits. What never returns is
   `wait_for`'s await of its own cancellation. The precise version rules out more than the vague one
   did — `asyncio.timeout()` and any shorter bound fail identically, and the one construction that
   *does* return (`shield` + abandon) converts an unbounded hang into an unbounded pool leak.

2. **The severity paragraph was missing the fact that would have been used against it.** A raw
   `aiosqlite` worker is a **non-daemon** thread (`core.py:90`, measured `daemon=False`) — which
   would make the Hub's never-disposed engine block `threading._shutdown` and hang the exit outright.
   It does not, because **SQLAlchemy** sets `connection._thread.daemon = True` at connect
   (`sqlalchemy/dialects/sqlite/aiosqlite.py:412`). Measured through an engine of
   `hub/hub/db/engine.py`'s exact shape: `daemon=True`, exit in 0.35s with no dispose. R1's "a
   process that is leaving anyway" is now earned rather than assumed.

3. **The test-suite half was overstated.** `hub/tests/conftest.py`'s teardown disposes the engine
   after *every* test, so a pooled connection does not normally reach a second loop there either.
   Two paths get past it, both read out of the code: `dispose()` does not close a **checked-out**
   connection, and — the sharper one — the settle's `for ... else: raise AssertionError(...)`
   (`:364-368`) sits **before** `await _REAL_ENGINE.dispose()` (`:369`), so hitting the pass cap
   skips the dispose entirely and carries the whole pool into the next test's loop. The fixture that
   exists to prevent this hazard stops preventing it exactly when something has already gone wrong.

## Iteration 5 — R3 moved the fix, and the change's own last step was the thing that could hang

### The finding that changes the change

`await engine.dispose()` — task 2.3, the **last thing the new shutdown does** — hangs forever on a
dead-worker connection sitting idle in the pool.

| probe | result |
|---|---|
| `probe_r3_dispose_hang.py bare` | dispose **never returned**; 40-second external kill |
| `probe_r3_dispose_hang.py close` | same dispose, **0.00s** |

`dispose()` never dispatches `checkout`, so a checkout-sited guard cannot see the connection it is
closing. The path is `QueuePool.dispose()` -> `_ConnectionRecord.close()` -> `__close()` ->
`Pool._close_connection()` -> the aiosqlite dialect's `close()`, which is
`self.await_(self._connection.close())`.

As R1 and R2 wrote it, this change could have turned *a traceback on a process that is leaving
anyway* into *a Hub that will not exit* — strictly worse than the defect. `hub/tests/conftest.py`'s
per-test dispose has the same exposure today.

### So the neutralisation moves off the checkout listener onto the `close` pool event

`_ConnectionRecord.invalidate()` dispatches `invalidate`, then `__close()` dispatches **`close`**
before anything is actually closed. Every close of a pooled connection passes through that one
event: checkout invalidation, `engine.dispose()`, checkin close, and the retry-exhausted abandon.

Measured (`probe_r3_close_listener.py` case A): a checkout listener that **raises only** — the
arrangement `tasks.md` 1.2 told the implementer never to write, with a comment begging them not to
reorder two adjacent lines — recovers in **0.00s** once the `close` listener exists.

```
  checkout: raising DisconnectionError (NO inline neutralise)

RESULT after 0.00s: RECOVERED, select 2 -> 2
```
