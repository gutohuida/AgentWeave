### The catch: round 1's change would ship a screen where a legacy runner cannot be saved

`_reject_undeclared_model(cli, model)` takes a provider and a model string. **It cannot see the
runner's stored model.** Its docstring (`runners.py:25-27`) claims it can — *"a model is refused only
when it is being newly set — an already-stored, unrecognised model … is left alone"* — and that
claim is true today **only by accident**: the free-text box sends `model: model || undefined`, which
`JSON.stringify` drops, so an untouched model arrives as an absent key.

A picker cannot do that. Its selected value *is* the stored model, and round 1's own task 2.3
requires the edit path to keep sending `model` explicitly. Measured:

```
GET   /runners/<r>                                   -> model_unrecognised: true
PATCH {"name": "renamed"}                            -> 200, legacy model survives
PATCH {"name": "renamed", "model": "claude-3-legacy-9"}   <- the runner's OWN model
                                                     -> 400 'claude-3-legacy-9' is not a model 'claude' declares
```

So round 1's task 4.4 (*"saving unchanged submits that same model"*) asserts the opposite of what
the code does, and shipping it would breach the **shipped** `runner-registry` scenario *"Existing
runners keep working"* that this change is otherwise strengthening — a legacy runner would become
uneditable in every respect, because `name` and `model` travel in the same PATCH. This is the
2026-08-28 shape exactly: **the argument was wrong while everything it argued about was right.**

Repaired in the proposal: new task **1.3** (`update_runner` does not refuse a model identical to the
one already recorded; a *different* undeclared model and any undeclared model on create stay
refused), new test task **1.5**, a normative clause and a new scenario in the spec delta, and task
4.4 rewritten to say the assertion is unsatisfiable without 1.3. Filed as **F220 (C)**.
