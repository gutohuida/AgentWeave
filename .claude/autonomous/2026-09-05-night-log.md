### The diagnostic F292 asked for cannot work, and that is the iteration's first finding

The entry asked for *"the pool's checked-out count immediately before the `drop_all`"*.
`AsyncEngine.dispose()` **replaces** the pool rather than emptying it — measured in five lines: the
pool object's identity changes across the dispose, and a connection checked out beforehand leaves
the fresh pool reading `Current Checked out connections: 0`. In the forced reproduction it read `0`
even *before* the fixture's own dispose, because the previous test's autouse teardown had already
disposed once. The count is zero in exactly the situation being diagnosed.

So what went in instead is a registry of our own, fed by `checkout`/`checkin`/`close` listeners on
the **engine** — measured to survive the replacement in both directions. It records, per
still-checked-out connection: the nodeid of the test that checked it out, the asyncio task and its
coroutine's qualname, up to six repository frames of the call site, and a weakref to the
`_ConnectionRecord` so `in_transaction` can be read at failure time.

Three facts that cost real time and are now in the finding rather than only here: the DBAPI
connection is **not weakref-able** (`__slots__`, no `__weakref__`) while the `_ConnectionRecord` is;
`aiosqlite.Connection.in_transaction` forwards straight to `sqlite3.Connection` with no worker-thread
hop, so it is safe to read after the creating loop is gone; and SQLAlchemy runs the sync half of
every async call **inside a greenlet**, whose frame chain ends at its own entry point — without a hop
to `greenlet.getcurrent().parent.gr_frame` the origin names only the listener. The first version had
no hop and printed exactly that, which is how the last one was found.

### The instrument is proven — on a forced reproduction, not on a hope

A throwaway two-test file (written, run, **deleted**) leaked D-6's established shape — a session that
wrote and did not commit, held across the boundary. The next test's `app` fixture failed with the
error CI reports: `OperationalError: (sqlite3.OperationalError) database is locked` on
`DROP TABLE requirement_drift`, `ERROR at setup`, 34.87s. The diagnostic named the **culprit** test,
its task (`Task-7`), the source line, and `IN TRANSACTION` — against a failure reported at the victim.

### Negative result, and it rules something out rather than merely failing to find it

- **15 consecutive runs** of `tests/test_flow_fires_a_review_turn.py` and
  `tests/test_reviewer_is_not_the_author.py` under `py -3.11`: `21 passed` every time, 13.46–14.87s.
- The same pair at **`busy_timeout=50`** — which turns any contention at all, however brief, from a
  30-second wait into an immediate failure — **passed again**.

Sub-millisecond contention within those two files is therefore *ruled out*, not just unobserved.
Whatever holds the file runs **before** them in full-suite order.

And a cheap explanation is gone with it: CI runs plain `pytest tests/ -v` with no `pytest-randomly`
installed and no `-n`, so the order is deterministic run to run. The intermittency is **timing**, not
ordering — which is what a fire-and-forget task looks like and what a different file's leak would not.
