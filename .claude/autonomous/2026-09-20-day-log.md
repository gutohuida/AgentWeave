## Iteration 4 — f185-r2: item 1's R2, an independent re-derivation

Read the code **before** re-reading R1's proposal, so this was a fresh comparison rather than a
re-check of R1's reasoning: `charters.py` whole, `agent_lifecycle.py` whole, `agents.py`

`hub/ui/src` side of both routes. `openspec validate --strict` passes.

**R1's findings all reproduce and most of its conclusions survive. Four claims did not.**

1. **C1 — D3's justification was false; its conclusion survives on a different reason.** R1 wrote
   that the charter/runner asymmetry rests on a difference in kind: *"a charter is instruction for
   turns the agent will take; a runner is the record of what this agent ran with."* The second half
   is not true of this code. `TurnUsage` (`db/models.py:1235-1248`, *"The immutable accounting
   outcome for one Hub-owned run"*) carries `runner` and `model`, is written for every run by
   `usage_accounting.record_turn_usage` (called from six sites in `agent_trigger.py` plus
   `run_reconciliation.py:80`), and archival does not touch it. `Run` itself carries **no** runner
   or model column — checked, because R1's sentence implied one. Structurally the two bindings are
   identical: adjacent same-shaped branches in `patch_agent` (`:2461-2470`, `:2472-2478`), adjacent
   fields on `AgentSummary` (`:568`, `:569`), each walling a `DELETE` with the same sentence one
   word apart. What actually separates them is a **display dependency**: `list_agents` derives the
   runner and display model from the live binding and from nothing else (`:517-524`), never from
   `TurnUsage`, so clearing `runner_id` drops an archived agent's row to the `"native"`/`"Native"`
   fall-through that `:512-515` exists to prevent. D3 rewritten to that reason. **The same false
   sentence was in the normative spec text** (`agent-configuration`'s runner paragraph) and was
   fixed there too — an argument being wrong while its conclusion is right is exactly what a round
   is for.
2. **C2 — D2(c)'s unarchive sentence had two defects, found against this document's own D8.** R1's
   sentence ended *"so bind one before this agent's next turn"*, an instruction implying a charter
   is **required** — D8 records the measured opposite (an agent with no charter is fully usable and
   says so). And it never said the release is **permanent**, which is literally the one thing the
   operator's rider (*"unarchive must then say the bindings are gone"*) asked for. Replaced with:
   *"No charter is bound. Archiving releases an agent's charter and unarchiving does not restore
   it. An agent with no charter still runs — bind one only if this agent should have one."* Every
   clause is true of an agent that never had a charter. Changed in D2, task 2.2 (with 2.3 now
   asserting the old phrase is absent), the spec's requirement and its scenarios, and the
   test-guide.
3. **C3 — the whole of group 2 reaches no operator (new D9).** `useArchiveAgent`
   (`hub/ui/src/api/agents.ts:214-241`) is the only client of **both** routes, its one non-test
   caller is `AgentSettingsPage.tsx:224`, and its `onSuccess` **takes no argument** — the response
   body is discarded, not merely under-typed. So `released_charter_id`, the archive sentence and
   the unarchive sentence are correct API facts nothing renders, and group 2's tests would pass
   while the operator saw nothing: this repo's named dominant failure mode. Group 2 is **kept** (an
   API that states the fate of a binding it silently changed is right regardless of today's
   client), but the proposal's *"the product says so rather than letting the operator find out at
   the next turn"* was struck, group 2 was retitled from *"The operator is told…"*, test-guide
   items 1/2 and A4/A10 were corrected, and task 2.5 was added recording that the operator's rider
   is **half discharged** — the API says it, the app does not show it.
