three carry the **same traceback**, two of them only in the captured log:

```
hub/output_recording.py:94: in record_agent_output

```

Locally, under `py -3.11`, all fourteen tests in `test_a_turn_says_how_it_ended.py` pass and both
named `test_agent_trigger.py` tests pass. So the assertion line was never going to separate the two
readings — the mechanism had to.

Measured, not assumed: SQLAlchemy's aiosqlite dialect picks the pool from the URL.

```
sqlite+aiosqlite:///:memory:   pool=StaticPool
sqlite+aiosqlite:///<file>     pool=AsyncAdaptedQueuePool
```

`hub/tests/conftest.py:19` pins the suite to `:memory:`. A **StaticPool hands the same DBAPI
connection to every checkout**, with no in-use tracking — so every `AsyncSession` in the suite, the
background run task's and every HTTP request's `get_session` alike, shares one connection and one
transaction. Returning a connection to a pool resets it, and reset means `ROLLBACK`. **A request
finishing is a rollback issued on the transaction a background run has open.**

Reduced to nothing else in `scripts/drive/staticpool_shared_connection.py` — one session inserts and
has not committed, a second opens and closes, the first commits and refreshes:

```
sqlite+aiosqlite:///:memory:   -> InvalidRequestError: Could not refresh instance '<Row at ...>'
sqlite+aiosqlite:///<file>     -> no error; rows in db = ['r1']
```

Then reproduced **inside the real suite on this machine, with CI's exact error**, by
`scripts/drive/churn_sessions_plugin.py` — an autouse fixture that churns short-lived sessions
during the test, making by demand the interleave CI hits by luck:

```
CHURN_DELAY=0.3 PYTHONPATH=scripts/drive py -3.11 -m pytest \
  hub/tests/test_a_turn_says_how_it_ended.py -p churn_sessions_plugin -k stopped_run_persists
-> sqlalchemy.exc.InvalidRequestError: Could not refresh instance '<AgentOutput at 0x...>'
```

Still a race, and the log says so rather than rounding it up: `0.25`, `0.35` and `0.4` land earlier
and kill the stop path's own status write first (`assert 'running' == 'stopped'`). Same rollback,
different casualty.

**Why "artefact" is the verdict and not a preference.** Production is never in-memory.
`hub/hub/config.py:16` defaults to `~/.agentweave/hub/data/agentweave.db`, native mode sets
`DATABASE_URL` to a file before `Settings` is instantiated, and `:memory:` appears anywhere in
`hub/hub/` only in the two places that exist to *detect* it. On a file-backed engine each session
holds its own connection, so reset-on-return rolls back only its own transaction — which is what the
second line of the reduction shows. "Green on Windows, red on Linux" is not a platform difference in
the product; it is a scheduling difference in when a request happens to finish.

## Iteration 4 — D-4, spec R1 on F286: the release is gated on the wrong question, and the Codex path has no gate at all

`openspec/changes/a-terminal-run-releases-the-queue-behind-it/` — `proposal.md`, `design.md`,
`tasks.md`, and an `agent-conversation-workspace` delta with two ADDED requirements.
`openspec validate --strict` clean. **Nothing implemented**; this window fills.

### The argument, re-derived from the code rather than from F286's summary

`_execute_run` writes and commits the run's terminal status at `agent_trigger.py:2175`, then does
its post-turn bookkeeping — `evaluate_run_end`, `_report_abandoned_entries`,
`_broadcast_run_lifecycle`, a `persist_event` + broadcast per returned entry, `record_agent_output`
at `:2235`, `maybe_generate_title` — and only at `:2281` calls `redrain_queued_agents`. The handler
at `:2282` computes `already_terminal` across `:2305-2313` and uses that **one** flag for **two**
unrelated questions: do not relabel a cleanly-ended run as failed (right), and do not release the
queue (`:2350`/`:2358`, wrong). So an exception between `:2175` and `:2281` leaves the run correctly
terminal and its queued input stranded.

The proposal's one-sentence form: **whether the queue behind a run gets released depends on what
happened after the run ended, when it should depend only on the run having ended.**

### What R1 found that F286 did not, and what it corrects in F286

**F286 says the Codex app-server path "reaches the same handler". It does not, and the truth is
worse.** Two code facts: `_execute_run` delegates at `:1824`, which is **above** its own `try:` at
`:1846`, and returns; and `_execute_codex_appserver_run`'s outer construct is `try: … finally:`
(`:2536`/`:2873`) with **no `except` clause at all** — its only `except` is the inner spawn/connect
one at `:2692`. So an exception there escapes into a task whose only done-callback is
`_background_runs.discard` (`:1231`), which never retrieves it. After that path's terminal commit
(`:2813`) it is F286 with not even an attempted redrain and no `logger.exception`; **before** it,
the `Run` row stays `running` with `error=None`, `schedule_agent` refuses every later turn, and the
only recovery is a Hub restart — that path never set `Run.pid` (`:1937` is the sole assignment, on
the PTY path), so `reconcile_interrupted_runs` reconciles it at the next start and only then. That
is the same unbounded outage `_execute_run`'s handler documents having been added to prevent.

**And nothing recovers an F286 entry even across a restart.** `reconcile_interrupted_runs` selects
only `Run.status == "running"` (`run_reconciliation.py:60`); an F286 run is terminal, so it is not
examined. The entry waits for project open, settings save or relocate (`projects.py:315`, `:527`,
`:588`) — the four remaining callers of `redrain_queued_agents` — which is delivery by coincidence.

Four line citations in F286 were off and are corrected in the ledger: the terminal commit is `:2175`
not `:2174`, the handler starts at `:2282` not `:2287`, `already_terminal` spans `:2305-2313`, and
the "same handler" claim is replaced by the paragraph above. The corrections are appended to F286 in
`scripts/drive/FINDINGS.md` rather than left in the change, because the ledger is the durable record.

### The design decisions, and the two alternatives rejected on evidence

- **D1** — ungate the redrain in the handler; leave the relabel gated. Smallest change matching the
  code's own comment, which already claims to be *"unconditional, where this was gated on
  `returned`"* while sitting inside a second gate.
- **Rejected: put the release in `finally`.** The block carries an explicit warning at `:2364-2368`
  that a cancelled task raises at its *first* await point, which is why its only `await` is last. A
  redrain there would be skipped under exactly the cancellation the handler was widened to catch.
- **Rejected: release immediately after the terminal commit.** Closes the window by removing it, but
