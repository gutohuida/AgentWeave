### The verdict, first

### How it was established

`gh run view 33840761719 --log-failed`. The three assertions CI prints look unrelated — `assert 0 ==
1`, `assert None is not None`, and an error propagating out of `_await_background_run()` — but all
three carry the **same traceback**, two of them only in the captured log:

```
hub/output_recording.py:94: in record_agent_output
    await db.refresh(row)
sqlalchemy.exc.InvalidRequestError: Could not refresh instance '<AgentOutput at 0x...>'
```

Locally, under `py -3.11`, all fourteen tests in `test_a_turn_says_how_it_ended.py` pass and both
named `test_agent_trigger.py` tests pass. So the assertion line was never going to separate the two
readings — the mechanism had to.

Measured, not assumed: SQLAlchemy's aiosqlite dialect picks the pool from the URL.

```
sqlite+aiosqlite:///:memory:   pool=StaticPool
sqlite+aiosqlite:///<file>     pool=AsyncAdaptedQueuePool
```

`hub/tests/conftest.py:19` pins the suite to `:memory:`. A **StaticPool hands the same DBAPI
connection to every checkout**, with no in-use tracking — so every `AsyncSession` in the suite, the
background run task's and every HTTP request's `get_session` alike, shares one connection and one
transaction. Returning a connection to a pool resets it, and reset means `ROLLBACK`. **A request
finishing is a rollback issued on the transaction a background run has open.**

Reduced to nothing else in `scripts/drive/staticpool_shared_connection.py` — one session inserts and
has not committed, a second opens and closes, the first commits and refreshes:

```
sqlite+aiosqlite:///:memory:   -> InvalidRequestError: Could not refresh instance '<Row at ...>'
sqlite+aiosqlite:///<file>     -> no error; rows in db = ['r1']
```

Then reproduced **inside the real suite on this machine, with CI's exact error**, by
`scripts/drive/churn_sessions_plugin.py` — an autouse fixture that churns short-lived sessions
during the test, making by demand the interleave CI hits by luck:

```
CHURN_DELAY=0.3 PYTHONPATH=scripts/drive py -3.11 -m pytest \
  hub/tests/test_a_turn_says_how_it_ended.py -p churn_sessions_plugin -k stopped_run_persists
-> sqlalchemy.exc.InvalidRequestError: Could not refresh instance '<AgentOutput at 0x...>'
```

Still a race, and the log says so rather than rounding it up: `0.25`, `0.35` and `0.4` land earlier
and kill the stop path's own status write first (`assert 'running' == 'stopped'`). Same rollback,
different casualty.

**Why "artefact" is the verdict and not a preference.** Production is never in-memory.
`hub/hub/config.py:16` defaults to `~/.agentweave/hub/data/agentweave.db`, native mode sets
`DATABASE_URL` to a file before `Settings` is instantiated, and `:memory:` appears anywhere in
`hub/hub/` only in the two places that exist to *detect* it. On a file-backed engine each session
holds its own connection, so reset-on-return rolls back only its own transaction — which is what the
second line of the reduction shows. "Green on Windows, red on Linux" is not a platform difference in
the product; it is a scheduling difference in when a request happens to finish.

### The two findings the triage produced that are not about the harness

**F286 (B) — a product gap, and the one thing here that outlives the CI fix.** `_execute_run` commits
the run's terminal status at `agent_trigger.py:2174` and only redrains the agent's queue at
**`:2281`**. Its exception handler computes `already_terminal` (`:2306`) and uses it for two
purposes: refusing to relabel an already-ended run as `failed`, which is right and well argued in
its own comment; and gating the redrain at **`:2358`**, which is wrong. The redrain is skipped in
exactly the case where the normal path's redrain was also skipped — an exception between `:2174`
and `:2281` — and its own comment argues it should be *"[u]nconditional"*. Nothing recovers it:
`agent_trigger.py:1908` states plainly that there is no tick. That is what `assert None is not None`
on `queued_entry.delivered_in_run_id` actually is: input queued behind a stopped run, never handed
to a successor, with no surface saying so. `_execute_codex_appserver_run` has the same layout
(`:2872`) and the same handler.

**F287 (C).** `record_agent_output` ends `db.add / await db.commit() / await db.refresh(row)`. The
refresh is dead weight: the factory is `expire_on_commit=False` (`db/engine.py:39`) and
`AgentOutput` has no server-side defaults — `timestamp` is a Python-side `default=_now`
(`models.py:1247`), already applied at flush. It costs one extra `SELECT` per output row on the
Hub's hottest write path, and it is the only reason F285 is a crash rather than an invisible no-op.
