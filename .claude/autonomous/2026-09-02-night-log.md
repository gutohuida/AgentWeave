## Iteration 8 — 2026-09-03T02:52:23+01:00 — `f272-persist`: the lost row is the harness's one shared connection, and it settles F266 too

`f272-persist` asked one question — is the terminal status row lost by the product or by the test
harness — and named one cheap experiment. The experiment was run, it was not enough on its own, and
three more were needed. **The answer is the harness**, and the same measurement closes `F266`, open
since 2026-09-01 with a 23-minute reproduction and a whole bisection session behind it.

### The named experiment ran, and by itself it would have proved nothing

Step 1 was "re-run the test against a file-backed URL and compare against the in-memory baseline of
2/20". Done, and the first thing it produced was a warning about its own method: **re-measuring the
in-memory baseline gave 0 failures in 20**, against the 2/20 measured the night before. The race is
load-dependent, so on an idle machine neither arm fails and the comparison is empty. Thirty-six
whole-file runs, alternating in-memory and file-backed, came back **18/18 green on both**.

At a true 10% rate, seeing zero in 18 has probability 0.15 — so a green file-backed arm was never
going to be evidence. **Two things fixed that**, and the order matters: the load amplification made
the statistics usable, and a deterministic probe made the statistics unnecessary.

### Load amplification: four concurrent pytest processes

Running four processes of the whole file at once takes the in-memory rate from 0/20 to something
visible. Six alternating rounds, four processes per arm, `-p no:randomly`, every run captured to its
own file with `--tb=long` (never piped to `tail` — that is how this went three iterations
unattributed):

| arm | failures |
|---|---|
| `sqlite+aiosqlite:///:memory:` — today's harness | **5 / 24** |
| `sqlite+aiosqlite:///<temp>.db` — file-backed | **0 / 24** |

All five failures are the identical traceback: `output_recording.py:94` → `db.refresh(row)` →
`InvalidRequestError: Could not refresh instance '<AgentOutput ...>'`, and the route then reads `[]`
back. At the observed rate, 0-in-24 has probability ≈ 0.004.

### The deterministic probe, which is what actually settles it

Statistics on a race are never comfortable, so the mechanism was reproduced directly: two
`AsyncSession`s on one engine, **no product code involved** — A `INSERT`s, B `close()`s (emitting
`ROLLBACK` on whatever connection B holds), A `COMMIT`s. Then a **2×2 over storage and pool**:

| cell | pool | shares one DBAPI connection | row survives commit | `refresh` |
|---|---|---|---|---|
| memory / default | `StaticPool` | yes | **no** | `InvalidRequestError` |
| memory shared-cache / default | `StaticPool` | yes | **no** | `InvalidRequestError` |
| **file / FORCED `StaticPool`** | `StaticPool` | yes | **no** | `InvalidRequestError` |
| file / default | `AsyncAdaptedQueuePool` | no | yes | ok |
| memory shared-cache / forced `AsyncAdaptedQueuePool` | `AsyncAdaptedQueuePool` | no | yes | ok |

Rows 3 and 4 are the whole argument: **same storage, opposite outcome.** The variable is the pool,
not in-memory SQLite being odd. `db/engine.py:34-38` passes no `poolclass`, so the dialect picks
`StaticPool` — one connection for the whole process — for `:memory:` and only for it. Every shipped
configuration (native file URL, Docker/Postgres) gets a connection per session and cannot produce
this.

### The correction that is worth more than the verdict

Both `F272` and `F266` say the write has **already committed** when the refresh raises. **It has
not.** The `COMMIT` executes and commits an empty transaction, because the `INSERT` was rolled back
underneath it. That inverts one of the three fixes `F266` proposed: dropping the refresh and
stamping `timestamp` client-side would **hide a lost write**, not tolerate a harmless one. The
refresh is the only thing in the process that notices, which is exactly what `f272-persist` said not
to delete — and now there is a reason rather than an instruction.

It also explains `F266`'s bisection result, which had been left as "accumulated process state or
load at full-suite scale, cause unknown": that *is* what a shared-connection interleave looks like,
and the 4-way load experiment reproduces it in 22 seconds instead of 23 minutes.

### The repair is measured, and one candidate died at suite scale

- **File-backed temp database** — works (0/24), but `assert_engine_is_disposable`

  because a real database was destroyed. Re-expressing it is safety-critical, not a one-liner.
- **In-memory shared-cache URL + explicit `AsyncAdaptedQueuePool`** — right at the mechanism level
  (row 5 above), and **refuted at suite scale: 8 / 8 failures**, every one
  `OperationalError: database table is locked: sqlite_master`, because the `app` fixture's
  `drop_all`/`create_all` now collides with the other pooled connections holding the shared cache.
  **This is why the deterministic probe alone is not sufficient either** — it fixes the interleave
  and breaks the fixture.
- **File + forced `StaticPool`** — dead end: the 14-test file took **259s** against 4s.
- **Shared-cache URL with no explicit pool** — not a change at all; SQLAlchemy still picks
