### Three things R1 found by re-deriving instead of inheriting the finding's framing

**1. F274's own framing is wrong on the requirement position, and the ledger now says so.** The
finding says *the route is not in breach and no requirement says the events must cover the turns the
client renders*. The first half holds — `agent-stream-events:334` explicitly permits the empty map
at `:363-366`, and `:368` is satisfied. The second half does not. *A run's terminal outcome is
visible* (`:299`) is quantified over **the conversation**, requires an outcome for every run that
ended, and allows none only for *"a run whose row genuinely cannot be found"*. F274's runs have rows.
**That requirement is breached.**

What hid it is the requirement's own next sentence, which cross-references *The run facts cover every
run the events name* — a rule quantified over the runs a returned **event** names, so it cannot
forbid omitting a run **no returned event names**, which is the whole of F274. The corpus forbids the
behaviour and simultaneously points at the wrong rule, and that mis-direction is a plausible reason
three rounds could read `:299` and ship this anyway. The delta therefore carries a **MODIFIED**
requirement that repoints the cross-reference and says what went wrong with it. F274's entry in
`FINDINGS.md` now carries the correction too — the ledger claimed a thing about the corpus that is
false.

**2. The single-conversation half kills the obvious cheaper fix.** `get_chat_history`
(`agent_chat.py:567-642`) applies **no limit at all** — measured, not assumed: no `.limit()` on any
of its three queries. So the turns on screen are unbounded while the facts are bounded at fifty
merged events. No widening of the event window can be large enough by construction, which is why
"raise the cap" is rejected in design D1 rather than left as an alternative.

**3. The map cannot move without the invalidation moving with it, and that is not cosmetic.**
`useAgentChatHistory`/`useAgentRecentChat` invalidate on `message_created`, `agent_output` and the
queue events (`agentChat.ts:284-291`) — **not** on the run lifecycle events, which is exactly what
`useAgentTimeline` invalidates on (`agents.ts:389-407`). Move the facts and leave the predicate and
a terminal label starts arriving on unrelated traffic. The case that never arrives at all is the one
the corpus already carves out at `:393-400`: a run reconciled `interrupted` at Hub restart writes
**no** terminal status line, so there is no `agent_output` event to piggyback on and an operator
with the conversation open watches that turn stay silent indefinitely. Hence a second ADDED
requirement — *A run ending refreshes the conversation that renders it* — and D4, which takes the
four terminal events and deliberately **not** `run_started` (an extra refetch of an unbounded
response for a signal `agent_output` already carries).

### Decisions R1 made that R2 and R3 should attack

- **D2 — lookup by id, not by `Run.conversation_id`.** The column exists and is indexed
  (`models.py:1180`, `ix_runs_conversation_started`), so the cheaper query is available. Refused
  because it depends on `Run.conversation_id` and `AgentOutput.conversation_id` agreeing rather than
  on the ids the response literally returns, and because the recent-chat route is cross-conversation
  and needs the id-set form anyway.
- **D5 — `AgentTimeline.runs` stays**, even though after this change nothing in the UI reads it
  (`AgentActivityTab.tsx:24-26` unwraps `events` only and says so). Removing it would delete two
  requirements that shipped two days ago and a public response field for no behaviour. The guard
  against a future author re-wiring the panel back to it is the prop comment — which today reads
  *"straight from the timeline route"* and must be corrected — plus task 4.7's test. **This is the
  weakest decision in the proposal** and the one most worth a fresh pair of eyes: two identically
  constructed maps from different windows, one unread, is exactly the arrangement that produced
  F274.
- **D6 — no chunking of the unbounded `IN`.** SQLite's parameter ceiling is 32766 since 3.32 and
  this machine's Python 3.11 links **3.45.1** (measured). A conversation needs 32,766 distinct runs
  to reach it.
