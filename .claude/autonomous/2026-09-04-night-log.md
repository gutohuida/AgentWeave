### The mechanism, traced rather than argued

A pytest plugin that wrapped `_background_runs` in a set printing a stack on every `add`:

```
_execute_run:1914 → _execute_codex_appserver_run:2932 → _record_run_failure_tail:1864
   → turn_scheduler.redrain_queued_agents:538 → schedule_agent:322 → trigger_agent_directly:1230
```

— which registers a **new** task in `_background_runs`. And the ordering, printed:
`ADD Task-43`, `CLEAR`, `ADD Task-48`.

So cancelling a run stopped being terminal. The fixture cancels the leftovers, `gather`s them, and
then `clear()`s the set — but the gather is what *causes* the successor, and a later link in the
chain lands after the `clear()`. That successor sat pending on an event loop that closed moments
later, and every subsequent test in the process then died in the same fixture cancelling a task
belonging to a closed loop. The failing test is never the leaking one: `..._probes_the_bound_runner...`
leaks it, `..._does_not_report_a_missing_repository...` reports it.

### Why the product is not what gets changed

Three measurements, and I would rather state them than the conclusion:

1. **The respawn is the specified behaviour.** It is requirement 2 — a run whose tail raises hands
   its input back and the release redelivers it. Test 3.5 asserts exactly that, deliberately.
2. **It is bounded, not a runaway.** `return_run_entries` charges `delivery_attempts` and withdraws
   the entry at `DELIVERY_ATTEMPT_LIMIT` (3). The observed chain was three tasks — 32, 43, 48.
3. **Nothing in the product cancels a run task.** The comment block at `agent_trigger.py:2386`
   says so and says how it was established: `_stop_requested` is a cooperative flag the read loop
   checks, not a cancellation. Loop teardown is the only caller — which is to say, the fixture.

So the gap is the fixture's contract, which assumed cancellation settles a task. Fixed there:
`hub/tests/conftest.py` now settles to a **fixed point**, looping cancel-and-gather up to
`_MAX_BACKGROUND_SETTLE_PASSES` (10) and removing only what each pass actually settled
(`difference_update(leftover)`) instead of `clear()`. It fails loudly with the still-registered
tasks named if it ever does not settle — a leak deserves an error on the test that leaked, not a
confusing one on the next.

Mutation-checked, because the loop and the `difference_update` are separable and only one of them
is the fix: putting `clear()` back **inside** the new loop returns the error immediately
(`test_inbound_queue.py` alone, 11 passed 1 error). The loop alone would not have helped.

`hub/tests/conftest.py` is the only file this phase touched. No production code changed — `git
status` shows `conftest.py` and `tasks.md`.
