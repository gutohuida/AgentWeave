## Iteration 4 - trace-hub-wide-2-impl (2026-10-20 night)

CI at tip 34a022b: **in_progress**; newest finished run f304e58: **success**. Branch and tip match STATE (autonomous/2026-10-18-daily, 34a022b).

**Built slice 2** of `everything-the-hub-does-is-in-a-trace` (Tier 2, `spdoc-19e17276aeac`), the D5 events:
- `persist_event` now calls `traces.record_event`, guarded so that a defect in it never stops the event. `record_event` handles three cases:
  - **A request's span is current and still in memory:** the event is appended to that `PendingSpan` (name = event type; `aw.event.id`, severity, agent, loop, and the redacted data JSON bounded at 8 KiB), and the span gets `keep=True`. A routine read that emitted an event is therefore recorded, and a request that nothing authenticated takes the event's project, so the event is not lost with a discarded span.
  - **A run's executor is current:** this is a `RunTrace(project_id, run_id)`, set by `traces.within_run`, which wraps `_execute_run` at its one `create_task` in `agent_trigger.py`. The event is appended to the run's root row in the event's own session (`_add_event`, which now returns whether the root existed).
  - **Neither:** a short, already-ended `aw.event` span is staged in the event's session, so it commits, or rolls back, with the event.
- The D5 design gap noted at compose ("PendingSpan has no form for an already-written root") is closed by `RunTrace`. Without it, the executor task would inherit the trigger request's span through the copied context.
- `traces.enqueue` marks the span `enqueued`. An event that arrives after its request was handed to the writer (work the request spawned) gets a span of its own instead of being appended where it would never be written.
