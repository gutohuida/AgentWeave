### The finding: the registry cannot falsify the thing the ledger says it has falsified

The F292 entry currently states, as its leading conclusion, that *"the standing (main-engine
registry) mechanism is **falsified for all four occurrences that carried the instrument**, n=4"* —
now n=5 — and reads that as ruling out a connection of the product engine as the holder. **That
inference does not hold, and the reason is in SQLAlchemy's own source (2.0.50 installed here).**

The registry listens on `checkout` / `checkin` / `close`. In `_ConnectionRecord.__close()`:

```python
def __close(self, *, terminate: bool = False) -> None:
    self.finalize_callback.clear()
    if self.__pool.dispatch.close:
        self.__pool.dispatch.close(self.dbapi_connection, self)   # <- listener fires HERE
    assert self.dbapi_connection is not None
    self.__pool._close_connection(self.dbapi_connection, terminate=terminate)
    self.dbapi_connection = None
```
(`sqlalchemy/pool/base.py:877-886`)

The `close` event fires **before** the close is attempted, and unconditionally. And the close it
precedes cannot report failure:

```python
try:
    ... self._dialect.do_close(connection)
except BaseException as e:
    self.logger.error(f"Exception closing connection %r", connection, exc_info=True)
    if not isinstance(e, Exception):
        raise
```
(`pool/base.py:371-384` — a plain `Exception` is logged and swallowed.)

`_finalize_fairy` behaves the same way for a failed *reset*: `except BaseException as e:
pool.logger.error("Exception during reset or similar", exc_info=True); connection_record.invalidate(e=e)`
(`pool/base.py:1006-1011`), and `invalidate()` routes straight back into `__close()` above.

**Therefore: on every path where SQLAlchemy gives up on a connection whose OS-level SQLite handle
survives, the registry's entry is removed first, and the failure is written only to the
`sqlalchemy.pool` logger — which pytest discards for a passing test.** A connection of the product
engine still holding an uncommitted write transaction is *guaranteed* to print
`no connection checked out`.

That is not a small correction. It means the five identical negatives are **consistent with** a
product-engine connection being the holder rather than evidence against it, and the entry's
`n=4`/`n=5` falsification claim needs narrowing to what it actually supports: *no connection was
checked out **and still tracked** at the probe points.* This is precisely the failure mode
`CLAUDE.md`'s round discipline names — the argument is wrong while every measurement it is built on
is right.

### A silent leak path that fits the printout exactly, found by reading the driver

Given the above, the question becomes: is there a path where the handle survives *without even
logging*? There is, and it is specific to this dialect.

`SQLiteDialect_aiosqlite` sets `is_async = True` and `has_terminate = True`
(`sqlalchemy/dialects/sqlite/aiosqlite.py:435-436`, downgraded to `False` only if the installed
aiosqlite lacks `stop` — 0.22.1 has it). `_finalize_fairy` computes
`requires_terminate_for_close = is_async and has_terminate` → **True**, so the discard path calls
`_close_connection(terminate=True)` → `do_terminate` → `_terminate_force_close` →
`aiosqlite.Connection.stop()`:

```python
def stop(self) -> Optional[asyncio.Future]:
    self._running = False
    def close_and_stop():
        if self._connection is not None:
            self._connection.close()          # <- the ONLY real sqlite3 close
            self._connection = None
        return _STOP_RUNNING_SENTINEL
    try:    future = asyncio.get_event_loop().create_future()
    except Exception:    future = None
    self._tx.put_nowait((future, close_and_stop))
    return future
```
(`aiosqlite/core.py:116-132`)

`stop()` **queues** the real close onto the connection's worker thread and returns a future nobody
awaits. If that thread is not running the queue, the `sqlite3.Connection` is never closed, its
transaction is never rolled back, its locks persist — **and nothing raises, so not even the
`sqlalchemy.pool` ERROR above is emitted.** A terminate on this dialect is structurally incapable of
failing loudly.

Also confirmed against the installed 0.22.1 rather than taken from the ledger:
`_connection_worker_thread` (`aiosqlite/core.py:48-75`) wraps both `function()` and the
`future.get_loop().call_soon_threadsafe(...)` report in one `try`, and the `except` branch's own
`call_soon_threadsafe` sits outside any handler — so a closed loop kills the thread on the second
raise. F295's mechanism, verified first-hand.

### Four weakref facts, measured — and they correct the entry's own N-1 note

The N-1 section said only *"the DBAPI connection is not weakref-able but `_ConnectionRecord` is"*.
Checked against the installed SQLAlchemy 2.0.50 / aiosqlite 0.22.1:

| Layer | Weakref-able |
|---|---|
| `_ConnectionRecord` | yes |
| `AsyncAdapt_aiosqlite_connection` (the DBAPI adapter) | **no** |
| `sqlite3.Connection` | **no** |
| `aiosqlite.Connection` | **yes** |

The last row is what makes the instrument possible at all, and it was not previously recorded. The
record alone would not have done: SQLAlchemy sets `record.dbapi_connection = None` when it closes one,
so the object holding the file becomes unreachable from the record at exactly the moment it becomes
interesting. The aiosqlite `Connection` is the one layer that both carries the leak signature and can
be weakly referenced.

Also measured rather than reasoned, and it makes the leak signature *exact*: `stop()` sets
`_running = False` immediately and then queues the only real `sqlite3` close. A stop whose worker
thread **is** draining leaves thread dead, `_running` False and `_connection` None within
milliseconds. So `_running == False` **with `_connection` still not `None`** is unambiguously the
close that was queued and never ran.

### The guard, and why `SystemExit`

`require_key()` raises `SystemExit`, not `RuntimeError`, and that is load-bearing rather than
stylistic. `api()`'s own `except Exception` catches everything and returns `(0, "...")`; the probe
demonstrated it swallowing a deliberate `RuntimeError` into exactly that shape. `SystemExit` is a
`BaseException`, so neither `api()` nor the bare `except Exception` blocks throughout this directory
can eat it, and it prints its message with no traceback. Written into the function's docstring so
the choice is not later "simplified".

| Leg | AW_KEY | HTTP attempted | Result |
|---|---|---|---|
| A — HEAD's code, tripwire on `urlopen` | unset | **True**, `Authorization='Bearer '` | returned `(0, ...)` |
| B — new code, same tripwire | unset | **False** | `SystemExit`, exit 1 |
| C — new code | `dummy-not-a-real-key` | True, header carries the key | proceeds — the guard gates on emptiness, not always |
| D — new code | `""` explicitly | False | `SystemExit` |
| E — HEAD's code, **live Hub :8010** | unset | — | **401, exit code 0** |
| F — new code, **live Hub :8010** | unset | — | local message, **exit 1** |
| G — new code, **live Hub :8010** | the real key | — | **200**, 1 project — unchanged |
| H — new code, **live Hub :8010** | wrong-but-nonempty | — | **401** `Invalid or revoked operator credential` — unchanged |
| I — caller wrapping in `except Exception` | unset | — | not swallowed, exit 1 |

The tripwire is what makes A/B evidence at all: an assertion that only checks *that* it failed
cannot tell a local refusal from a 401, and both "fail".
