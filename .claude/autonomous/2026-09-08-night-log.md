### The suite reached F295's precondition on its own, on a green run

Worth recording because it was not looked for. Among the 247 warnings is a
`PytestUnhandledThreadExceptionWarning` carrying this, four times:

```
aiosqlite/core.py:66  in _connection_worker_thread
  future.get_loop().call_soon_threadsafe(set_result, future, result)
RuntimeError: Event loop is closed
During handling of the above exception, another exception occurred:
aiosqlite/core.py:75  in _connection_worker_thread
  future.get_loop().call_soon_threadsafe(set_exception, future, e)
RuntimeError: Event loop is closed
```

That is the F295 mechanism **verbatim** — and specifically it is the mechanism task 3.1 instructs the
implementer to reproduce deliberately: the worker fails to report a result on a closed loop, fails
again reporting *that* the same way, and its `while True` ends (`core.py:47-75`). The dead-worker
state F295 is about is therefore **not hypothetical in this suite; it occurred tonight on a green
run.** The suite stayed green only because nothing checked that connection out again — which is
exactly the finding's claim, observed rather than argued.

This does not change the finding's severity or any task, and it is **not** a claim that F295 causes
F292. It is corroboration that the precondition is reachable in practice, and it means task 3.1's
kill mechanism is known-good before anyone writes it.

### Driven, not just compiled

`testbed/scratch/f295/probe_impl_check.py` (uncommitted, per 4.3) imports the **real**
`hub.db.engine` against a temp database and kills a worker by 3.1's real mechanism — second loop,

worker's two `RuntimeError: Event loop is closed` tracebacks appear exactly as `core.py:66` then


out again, and `engine.dispose()` still returned in 0.00s, which is what task 2.3 depends on. C is
the healthy path: same pooled connection, no reconnect, no warning.
