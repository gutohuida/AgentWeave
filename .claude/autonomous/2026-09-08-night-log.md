F292. It is corroboration that the precondition is reachable in practice, and it means task 3.1's

## Iteration 3 — shutdown settles its runs, then lets go of the pool

**Branch and state agree.** `autonomous/2026-09-08-daily`, `HEAD` `00d72a8` (iteration 2's guard
commit), tree clean at start, `parent_sha` `755bdad` six commits back on the same line. Nothing to

Item `c1-shutdown`: tasks **2.1, 2.2, 2.3** of
`2026-09-07-a-dead-connection-is-never-handed-back-out`, all in `hub/hub/main.py`. 2.4 was already
ticked and is a question, not a step.

`_settle_background_runs()` (+45 lines above `lifespan`) and three lines added to the teardown:

```
    await terminate_all_active_runs()
    await shutdown_scheduler()
    await _settle_background_runs()
    await engine.dispose()
```

The settle sits **after** both existing steps, per 2.4's answer — terminating the run *processes*
does not settle the in-process tasks driving them, and `shutdown_scheduler()` is what stops the set
being refilled behind the settle. It cancels the current members, `gather(...,
return_exceptions=True)`, `difference_update`s what that pass settled (**not** `clear()`), and loops
while the set refills, to `_MAX_BACKGROUND_SETTLE_PASSES = 5`. On the bound it logs at WARNING with
the count and continues (2.2) — `conftest.py:580-601` raises there, which is right for a test and
wrong for an instance that has been asked to stop. It does `clear()` the abandoned leftovers, and
says why in a comment: `_background_runs` is module-level, so anything left in it would be awaited
by a later lifespan in the same process against a loop that has closed.

### Driven, not just compiled

`testbed/scratch/f295/probe_shutdown.py` (uncommitted, per 4.3) runs the **real** `lifespan()` async
context manager against a temp database, three cases:

```
A: task done after teardown: True  cancelled: True
A: set empty: True
A: pool replaced by dispose: True
B: successors created: 6  set empty after: True
B: warnings: ["Shutdown: 1 background run task(s) did not settle in 5 passes; stopping anyway: ..."]
C: worker alive after kill: False
C: teardown (settle + dispose) returned in 0.00s
C: neutralised: _running=False _connection=None
```

- **A** is 2.1 and 2.3 together: a run task registered in `_background_runs` and still pending at
  teardown is cancelled and settled, the set is empty, and `engine.pool` is a different object
  afterwards — the dispose actually happened, and it happened after the settle.
- **B** is 2.2, and it is the case the bound exists for: the task re-registers a successor from its
  `except CancelledError` every pass, so **6** tasks are created (one plus one per pass), the loop
  exhausts, the WARNING is emitted with the leftover count, and the teardown **returns** rather than
  raising. One `await asyncio.sleep(0)` was needed before the teardown for the first task to start
  at all — cancelling a task that has never run skips its `except` clause entirely, which is worth
  knowing when `c1-tests-shutdown` writes 3.6.
- **C** is 2.3's dependency on 1.5, measured on this code rather than on a probe of it: a connection
  whose aiosqlite worker was killed by 3.1's real mechanism (second loop, future on it, close the
  loop, `put` on `_tx`) and returned to the pool idle does not hang the teardown — **0.00s**, with
  the connection neutralised. Iteration 2 measured the same dispose hanging to a 45-second external
  kill with the `close` listener removed, so the precondition 2.3 was gated on is satisfied by
  measurement at both ends.
