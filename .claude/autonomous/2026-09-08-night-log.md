## Iteration 3 — shutdown settles its runs, then lets go of the pool

**Branch and state agree.** `autonomous/2026-09-08-daily`, `HEAD` `00d72a8` (iteration 2's guard

ticked and is a question, not a step.

`_settle_background_runs()` (+45 lines above `lifespan`) and three lines added to the teardown:

```
    await terminate_all_active_runs()
    await shutdown_scheduler()
    await _settle_background_runs()
    await engine.dispose()
```

The settle sits **after** both existing steps, per 2.4's answer — terminating the run *processes*
does not settle the in-process tasks driving them, and `shutdown_scheduler()` is what stops the set
being refilled behind the settle. It cancels the current members, `gather(...,
return_exceptions=True)`, `difference_update`s what that pass settled (**not** `clear()`), and loops
while the set refills, to `_MAX_BACKGROUND_SETTLE_PASSES = 5`. On the bound it logs at WARNING with
the count and continues (2.2) — `conftest.py:580-601` raises there, which is right for a test and
wrong for an instance that has been asked to stop. It does `clear()` the abandoned leftovers, and
says why in a comment: `_background_runs` is module-level, so anything left in it would be awaited
by a later lifespan in the same process against a loop that has closed.

### The finding: `asyncio.wait_for` does not bound `engine.dispose()`

3.10's task asked for the dispose "under a bounded wait that must not time out" and to
"confirm it hangs with 1.5 removed". Both halves were run, and the second one is sharper
than expected:

- with 1.5 in place — `RETURNED in 0.00s, pool replaced: True`;
- with `_neutralise_dead_worker_on_close` reverted to `return` — the pytest run was killed
  externally at **240s** having printed nothing, and `faulthandler` at 40s showed the main
  thread inside a live event loop with nothing progressing.

`testbed/scratch/f295/probe_310_wait_for_bound.py` (uncommitted, per 4.3) isolates it away
from any fixture: `asyncio.wait_for(engine.dispose(), timeout=5.0)` **never raises** — no
return in 60 seconds. The dispose reaches aiosqlite through SQLAlchemy's greenlet bridge
and the cancellation does not land. The same `wait_for` *does* bind the checkout/execute
path: 3.11's mutation row above failed on `TimeoutError` in 15.5s.

So the guarantee is narrower than the task's wording, and the test's own docstring now
says so rather than claiming a bound it does not have. The `wait_for` stays — it costs
nothing and bounds every other way the test could go wrong — but a 1.5 regression costs a
stuck job, which is the same price already recorded in `test_dead_worker_connection.py`'s
module docstring and the same reason that file ships no listener-removed variant.
