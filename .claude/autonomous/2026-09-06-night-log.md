**Two deliberate divergences from the letter of the tasks, both recorded rather than silent.**

1. **1.1 asks for `isLoading` to be destructured; it is not.** In a `data`-first render
   `!data && !isError` *is* the not-yet-answered state — in flight, or the query disabled because no
   project is selected — so `isLoading` carries no information the third branch needs, and binding
   it unused fails `--max-warnings 0`. `isError`, `error` and `refetch` are all read as 1.1 intends.
   Stated in the component's doc comment.
2. **1.3 says the *fallback string* must say nothing stored has been changed.** Instead that
   sentence is a static line in the alert, always rendered, with the fallback carrying only
   "The Hub did not return a reason." This is strictly stronger: the reassurance then also holds for
   an error *response* that carries a body and so displaces the fallback, not only for the bodiless
   dropped-connection case the scenario names. The scenario "A failed read reports something useful
   with no server response to quote" is satisfied either way.
