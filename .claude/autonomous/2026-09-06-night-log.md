**Two tests initially failed for the wrong reason, and were rewritten.** 2.2 and 2.6 first waited on
`findByRole('alert')`, so against a page that renders no alert they failed as *copies of 2.1* rather
than on the write and the stale editor they exist to catch. Both now wait on
`client.getQueryState(...)?.status === 'error'` — a settle condition true of both versions — and only
then assert. The table above is the corrected run.

**2.5 needed a second mutation and initially survived it — the finding of this iteration.** Its
mutation is not the pre-change page (which passes it) but an `isError`-first ordering, applied as
`data && !isError`. It **passed anyway**: React Query notifies only on result fields a render
actually read, and a `data`-first branch never reads `isError` while data is present, so the failed
refetch re-rendered nothing and the wrong ordering was invisible. 2.5 now asserts the query really
reached `error` with its data retained, then **keeps typing** — which forces the re-render — and it
fails against that mutation with `Unable to find an accessible element with the role "textbox"`.
Worth carrying: *a React Query render-path test can pass because nothing re-rendered.* The masking is
in the observer, so it applies to any test of a branch on a field the happy path short-circuits past.

**2.5 and 2.7 pass before and after, stated rather than glossed.** 2.7 is the success path and its
being unchanged is the evidence the fix took nothing away; 2.5's mutation is the ordering, above.

so a newly selected project's key has no data and the editor branch cannot be reached holding the
previous project's text. There is no explicit guard, and the test says so.
