What is being proposed

The Hub already puts a run's credential (AW_RUN_TOKEN) and the Hub's address (HUB_URL) into the spawned process's environment (agent_trigger.py:1071, :1090-1114) — and then, on the non-MCP branch, tells that same run it has no tool surface at all (launchability.py:325-330). The proposal is that a run without MCP is told how to reach the capability plane over HTTP, and that a run is told the access path it actually has. The credential is named, never valued — interpolating it would put a live credential into a durable turn prompt.

The seed's question 1 — one change or two — is answered two, HTTP first. A Copilot runner is blocked at four layers and the fourth, the output parser, cannot be settled without Copilot's real output, which this window was forbidden to go and find. The HTTP half needs nothing from Copilot and is a live defect for any harness without MCP.

The proposal's own premise, in one line

_hub_request (mcp_server.py:151-183), the single helper every MCP tool goes through, authenticates with os.environ["AW_RUN_TOKEN"] against os.environ["HUB_URL"] + "/api/v1/agent-actions". The MCP adapter is literally a wrapper around the two environment variables the notice tells the agent it has nothing to do with.

The continuity kit's scope, decided rather than assumed

  • File contract plus a stdlib-only CLI. The exit code is the integration contract (0 conforms, 1 mechanical violation, 2 bad invocation) plus --json. A harness that cannot run a subprocess still gets the contract by reading the files — which is the cheapest possible harness surface and the one least likely to be blocked by a policy that blocks MCP. MCP and HTTP are named as later adapters and forbidden as second sources of truth, as a requirement, since “pluggable” in a design document has never stopped one appearing.
  • The UI is deferred with a stated trigger, not dropped. You asked for CLI and UI. The UI's value is chain review, it is a consumer of check --json, and building a consumer before its producer's output is stable is how the output stops being able to change. Trigger: --json findings stable across two repositories.
  • The checker decides only what is mechanical. All 14 items of the handoff checklist plus 8 further rules are classified mechanical / heuristic / judgement; the checker never emits judgement as a finding, and every run reports how many rules it did not evaluate, so a green exit code cannot be read as a verdict on quality.
  • AgentWeave becomes a consumer, not a third copy. The two existing copies become renders of one upstream source under profiles local and distributed, with byte-for-byte reproduction as the acceptance test — already demonstrated in R2.

A third spec loop, asked for after the first two finished, seeded by openspec/explorations/2026-09-07-an-overseer-for-any-harness.md: a system that connects to any AI harness, records what the agents are doing, and offers metrics and governance over them. Three rounds ran, each re-deriving against the code rather than re-reading the round before it. The output is a second new sibling repository — witness, local, no remote, four commits. §8 supersedes the rest of this paragraph. When §7 was written the repository held a proposal and no code, and its own recommendation was propose-then-shelve because every requirement was downstream of data-policy questions only you can answer. A fifth iteration then found that the reading was too broad, built a skeleton against a surface that needs none of those answers, and drove it — so the repository now also carries a running cut 0 and eight findings from driving it. Six questions are still yours to answer, in §7.4.

The question the loop existed to settle, and the answer that replaced the seed's

The seed asked: is this a new product, or AgentWeave's Hub with the orchestration removed? It offered a distinction to test — AgentWeave governs agents it spawns; an overseer governs agents it does not control — and R1 was told to test it, not inherit it. Tested: true, but a restatement rather than evidence. It names the difference; it does not show the difference is load-bearing. Three measurements do, and R2 re-derived all three independently and confirmed all three:

The framing was settled against the seed's reason and for a stronger one. CLAUDE.md states the Hub's security property as identity is never accepted from a request body or header. An overseer's core operation is to accept a record about an actor it never authenticated — that is, to relax exactly that property. Building it inside the Hub means adding a second, weaker identity tier to the system whose strength is having one. That is a security argument, and it survives where the seed's taxonomy argument does not.

§7.4 — Six more decisions, and they are policy rather than engineering

These continue the SQ series and sit here rather than in §6 only because they all belong to loop 3. Unlike the twelve above, none is a question about the code: what data may be recorded is a policy question, and the loop deliberately did not guess. SQ-13 blocks every phase of the change except phase 0 — nothing is buildable until it has an answer.

SQ-13 (OV-1) — May Witness read the local Claude Code transcript corpus at all?

~/.claude/projects/**/*.jsonl is 2,084 files and 1.09 GB of your real sessions: prompts, source code, tool arguments and plausibly credentials. Unlike every OTel surface — where content is off until several flags are set — nothing is withheld by default; it is already on disk in full. It is also the only retroactive surface. Two things you would not otherwise be told: the scope silently includes 169 delegated-agent transcripts under <session>/subagents/ that “my sessions” does not bring to mind, and the question is time-sensitive — the corpus deletes on a rolling window, the oldest survivor is 2026-08-09 and at least 51 earlier sessions are already gone, so “yes, later” is not the same answer as “yes”. There is no partial answer that keeps the retroactive property.

SQ-14 (OV-2) — Redaction: at read, at write, or not at all?

At read loses fidelity permanently and makes the record less useful for the incident it exists for. At write leaves a window. Not at all makes the Witness store the most sensitive file on the machine. AgentWeave's redact_secrets (runner_events.py:63) is a working starting point either way. Evidence that this cannot rest on the reader's discipline: R2 quoted eleven words of a real operator prompt into its own write-up to prove the prompts were genuine — breaking a rule written three files away, in a file it had read that hour. Removed, and left recorded.

SQ-15 (OV-3) — How long is the record kept?

A record that answers “what did the agents do last quarter” must be kept for a quarter, which is a different risk profile from a debugging aid kept for a week. This is no longer only a risk question: a batch reader cannot keep a record past the harness's own deletion window, so keeping more requires copying transcripts before deletion, which requires a resident process. See SQ-18 — this and that are one decision.

SQ-16 (OV-4) — Who may read the record: you only, or anyone else?

Single-operator local is the first cut's assumption and it is written into the specs as one. The moment a second reader exists this becomes an access-control product and the scope roughly triples.

SQ-17 (OV-5) — Does the name witness survive?

Chosen because it commits the product to the passive posture: a witness testifies to what it saw and is expected to say what it did not see. If a later round decides the product must enforce, the name has to change with it. Whether it collides with an existing project could not be checked offline.

SQ-18 (OV-6) — Do you want a live mode, and would you run something resident to get it?

Measured this round: the transcript is written live — a record was readable 0.114 s after its own timestamp. A tailer is therefore buildable, and design D8 deliberately does not build one, because a process reading your transcripts unattended is a materially larger disclosure than SQ-13 asks about, and a resident reader's crash is silence indistinguishable from inactivity. It is also the only way to keep records past the harness's deletion window. “Nothing resident” and “records older than 29 days” cannot both be had — this and SQ-15 are one decision wearing two hats. Blocks D8, and every task downstream of it if the answer is yes.

8What driving the skeleton found

§7 ended with a proposal and no code. This section is the fifth overseer iteration, which built the smallest thing that could be pointed at real data and run, and ran it: 44 tests, and one drive over 2,829 real commits. It produced eight findings, five of which are defects in the specs §7 describes rather than in the code. That ratio is the argument for driving, restated on a second project in one day.

Why there was anything to build, when §7 said shelve

tasks.md said “every phase is blocked on 0.3”, and 0.3 is your permission to read your own sessions. The tasks file had generalised that into permission to read anything — which shelves work that discloses nothing. A repository’s own commit history is data you have already published, and it is still a record of turns performed by agents Witness did not spawn, which is the product’s entire subject. So the gate belongs to the surface, not to the product. Everything below follows from acting on that; nothing below read a single transcript, and the build compiles no reader for that surface at all — the block is an absence, not a flag that could be flipped.

What the drive did not falsify

Said explicitly, because a drive that falsifies nothing was not looked at hard enough and this one is allowed to name what held. The four provenance states held — every one exercised, and no path found that produced a value a record claimed not to have. derived earned its place on first contact: cost_usd ran its derivation, found its inputs unmeasured, and returned unavailable naming the missing input on all 2,829 records, never partially derived. The closed surface list held — unknown, absent and known-but-no-reader all exit non-zero naming what the build knows, and the no-surface case was checked on both halves, the exit code and the file that must not be created. conditional was the right call: 1,699 records resolved one way and 1,130 the other, within one surface, in one repository — the same shape R2 measured across models, reached from a different direction.

What this does not change

Nothing in §7.4 is answered by this. The six decisions are still yours, the transcript surface still has no reader, and no line of this skeleton read a session file. What changed is that propose-then-shelve was too blunt: one surface could move without you, it moved, and it found five things three careful rounds did not. Whether git-commit should survive as a surface at all is itself open — W-6 is a real argument that it should not, and it was chosen because it was drivable without a decision from you, not because anyone decided the product wants it.
