## Findings

### [Major] Agent name uniqueness is check-then-insert with no database constraint

**Where:** `hub/hub/api/v1/agents.py:430-438` (the `existing`/`configured_names` check) and
`hub/hub/db/models.py:124`
**What:** The "project-unique name" contract is enforced by a SELECT followed by INSERT with no
`UniqueConstraint` on `agents(project_id, name)` — the table has only a non-unique
`Index("ix_agents_project_name", ...)`.
**Failing scenario:** Two operators (or a retried/duplicated request) POST the same agent name
concurrently. Both sessions pass the duplicate SELECT before either commits, both INSERT, both
return 201. The project now has two agents sharing the addressable identity; every name-addressed
lookup downstream (`launchability.get_agent_config` uses `.scalars().first()` by name, message
routing by name, `/agents/{name}/...` routes) silently picks one.
**Evidence:** `models.py:124` — `__table_args__ = (Index("ix_agents_project_name", "project_id",
"name"),)` (no `unique=True`); `agents.py:430-470` — `await session.execute(select(Agent.id)...)`
then `session.add(agent); await session.commit()` with no `IntegrityError` handling. The new test
(`test_operator_agent_creation.py:82-93`) exercises only sequential duplicates. Spec:
`operator-agent-creation` — "Creating an agent SHALL require a valid project-unique name".
**Suggested direction:** Add a `UniqueConstraint("project_id", "name")` (with migration) and map
the resulting `IntegrityError` to the existing 409, rather than relying on the pre-check.

### [Minor] Global actionable-condition chips were dropped with StatusBar, not relocated

**Where:** `hub/ui/src/App.tsx:280-312` (StatusBar removed; ProjectHeader carries only
settings/theme/setup), `hub/ui/src/components/layout/StatusBar.tsx:121-146`
**What:** The removed StatusBar was the only global surface for the compact
`BudgetExhaustionNotice` and the SSE "Reconnecting…" indicator. After this change the budget
notice renders only inside `AccountingPanel` and the reconnect indicator only inside
`AgentOutputPanel` — an operator on Overview, Tasks, Spec, or Jobs sees neither.
**Failing scenario:** (a) The project budget exhausts while the operator is on the Tasks board —
no visible notice anywhere on screen; the state is reachable only by navigating to the accounting
panel. (b) The SSE connection drops on any non-conversation page — the board goes silently stale
with no indicator (pre-change: a visible "Reconnecting…" chip).
**Evidence:** `grep BudgetExhaustionNotice` → rendered only in `AccountingPanel.tsx:105` (full
variant); `grep useSSEConnectionState` → consumed only in `AgentOutputPanel.tsx:158` and the now
unmounted `StatusBar.tsx`. The change's own approved plan, `tasks.md` 1.2, required relocating
global affordances "without hiding actionable conditions". Note the stale comment at
`hub/ui/src/api/agents.ts:130-134` that still justifies the removed poll fallback by pointing at
"the StatusBar 'Reconnecting…' indicator" which no longer exists in the shell. (The aggregate
context-warning chip was also removed, but per-agent `ContextUsageIndicator` survives on
Overview's health cards, so that condition is not hidden.)
**Suggested direction:** Mount the two indicators (or a single combined shell-level affordance) in
`ProjectHeader` or another always-visible shell slot.

### [Minor] Dialog focus trap is escapable via scrim click

**Where:** `hub/ui/src/hooks/useDialogFocus.ts:24-40`
**What:** The Tab trap only redirects when `document.activeElement` is exactly the first or last
focusable element inside the panel. Clicking the (non-focusable) scrim moves focus to
`document.body`; the next Tab then follows document order into the page behind the modal, and the
handler does not intervene because the active element is outside the panel.
**Failing scenario:** Open Add agent → click the gray scrim (the dialog stays open) → press Tab →
focus lands on a rail/header control underneath the modal; the keyboard user is now operating
obscured UI while `aria-modal="true"` claims a modal context.
**Evidence:** `useDialogFocus.ts` — the handler returns early unless `event.shiftKey &&
activeElement === first` or `!event.shiftKey && activeElement === last`; there is no containment
branch for focus outside `panelRef`. Both dialogs use this hook. Spec: `hub-workspace-shell` —
"Lifted surfaces" requirement and the handoff's own "opaque focus-trapped dialogs" claim.
**Suggested direction:** On Tab, if `document.activeElement` is not inside the panel, redirect to
the first focusable element (and consider ignoring/rejecting scrim pointer-downs or closing on
scrim click deliberately).
