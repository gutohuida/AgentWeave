## What this iteration did

Added two phases to a lifecycle that previously stopped at `approved`: `archived` (reachable only
from `approved`, no way out) and `current` (reachable only at creation, for `kind='capability'`
documents that sit outside the phase machine entirely). Added an operator-authored merge path so a
finished change's content folds into a capability document, with agent-authored edits arriving as
`SpecEditProposal` rows the operator accepts or rejects. Then made scheduled jobs able to be
"loops" — an `AIJob` wearing a purpose and an optional stop condition — with the loop's queue being
the existing task board via a new `Task.loop_id`.

The composition instruction was followed closely. `Loop` deliberately has no `status` enum because
`AIJob.enabled` already answers that; the loop's queue is `Task`; there is no parallel loop API,
the fields ride the existing jobs routes. This is the opposite of the reinvention failure mode that
was the main risk.

## Findings

### [Major] Migration 0074's downgrade aborts on any database holding a capability document

**Where:** `hub/hub/migrations/versions/0074_archive_and_capability_phase.py:135-148`

**What:** `downgrade()` runs its `UPDATE` **before** dropping the CHECK constraint that the `UPDATE`
violates, so the downgrade fails partway instead of completing.

**Failing scenario:** A database with one `kind='capability'`, `phase='current'` row — i.e. any
database actually using the feature this migration adds. `alembic downgrade 0073` executes
`UPDATE spec_documents SET phase='approved' WHERE phase IN ('archived','current')` while
`ck_spec_documents_kind_phase` — `(kind='capability' AND phase='current') OR (kind!='capability'
AND phase!='current')` — is still in force. Setting a capability row to `approved` violates it.

Note the asymmetry that makes this easy to miss: a database with only *archived change* documents
downgrades fine, because `change-spec` + `approved` satisfies the paired CHECK. **Only capability
documents trigger it** — the exact rows the feature exists to create.

**Evidence:** Reproducer against the real path (`create_all`, `stamp 0073`, `upgrade head`, seed,
`downgrade 0073`):

```
1. create_all + upgrade to head OK
   uq_spec_documents_project_path: PRESENT
   ck_spec_documents_phase: PRESENT
   ck_spec_documents_kind: PRESENT
   ck_spec_documents_kind_phase: PRESENT
2. seeded capability(current) + change(archived)
   paired CHECK correctly rejects capability+approved
sqlalchemy.exc.IntegrityError: (sqlite3.IntegrityError) CHECK constraint failed:
  ck_spec_documents_kind_phase
[SQL: UPDATE spec_documents SET phase = 'approved' WHERE phase IN ('archived', 'current')]
  File ".../0074_archive_and_capability_phase.py", line 135, in downgrade
```

**Fails safe** — the transaction aborts and the database stays at head, so there is no corruption
and no data loss. The cost is that the rollback escape hatch does not exist precisely when the
feature has been used. No test covers `0074`'s downgrade; `test_migrations.py` only tests a
downgrade for `0052`.

**Suggested direction:** Move the `UPDATE` inside/after the `batch_alter_table` block that drops the
constraints, and add a downgrade test that seeds a capability row first.

### [Minor] `_KINDS` is restated in migration 0074 with no test pinning it to `spec_payload.KINDS`

**Where:** `hub/hub/migrations/versions/0074_archive_and_capability_phase.py:52`

**What:** The migration restates the `kind` vocabulary — correctly, since migrations run standalone
and cannot import `hub.spec_payload` — but nothing asserts the two agree. `CLAUDE.md` requires
exactly this pattern to carry a drift test: *"anything it needs from the Hub is restated there, with
a test asserting the two agree."*

**Failing scenario:** Someone adds `"playbook"` to `spec_payload.KINDS` (a one-line change) and
submits a document with that kind. Python-layer validation passes; the `INSERT` is rejected by
`ck_spec_documents_kind`, which no longer lists it. The whole suite stays green.

**Evidence:** `spec_payload.py:43` and the migration's `_KINDS` are identical today (both
`("baseline","system-map","roadmap","change-spec","capability")`), so there is no live bug. `grep`
for `_KINDS` / `ck_spec_documents_kind` across `hub/tests/` returns no drift test. Migration 0074's
own docstring calls the restatement out, so the author was aware of the pattern but did not add its
guard.

**Suggested direction:** One test importing both and asserting set equality, mirroring the existing
`mcp_server.py` restatement test.

### [Minor] Two bumped head assertions carry a stale failure message

**Where:** `hub/tests/test_migrations.py:147` and `:515`

**What:** The assertion checks `"0076"` but its message says `expected alembic_version=0075`, so a
future failure reports the wrong expected revision to whoever is debugging it.

**Failing scenario:** Head moves to `0077` without these being bumped. The test fails with
`expected alembic_version=0075, got 0077` — sending the reader to the wrong migration.

**Evidence:** Introduced in this range; the run bumped the assertion twice (0074→0075→0076) and the
message tracked neither:

```
-    assert version == "0073", f"expected alembic_version=0073, got {version}"
+    assert version == "0076", f"expected alembic_version=0075, got {version}"
```

**Suggested direction:** Interpolate the expected value instead of hardcoding it twice.

## Open questions

1. **Is "queue empty" the right stop trigger for a loop that has not been populated yet?** The
   operator described "shorter dev loops that keep developing" — create-then-populate is the natural
   order, and doing it in that order with `stop_when_queue_empties=True` kills the loop before its
   first useful fire, permanently (`job.enabled = False`). Opt-in and tested, so not a defect, but
   worth ruling on: should the stop condition require the queue to have been non-empty at least once?
2. **Does the downgrade path need to work at all?** If rollback is not a supported operation for
   this product, the Major finding is documentation rather than code. If it is supported, it should
   be tested.

### [Minor] The UI build stamp is stale, so `/health` permanently false-positives `ui_stale`

**Where:** `hub/hub/static/ui/ui-build-stamp.json`

**What:** The stamp records `src_commit f6b2e19` / `src_fingerprint 5a9c7773…`, but the current
fingerprint of `hub/ui/src` is `e7562bb9…`. `/health` therefore reports `ui_stale` continuously.

**Failing scenario:** Any operator or CI check reading `/health` sees `ui_stale: true` and its
detail telling them to run `refresh_ui_bundle.py`, on a bundle that does not actually need it. This
is the "trains you to ignore the signal" failure in its most literal form — and `CLAUDE.md` states
the stamp exists precisely "so `/health` can stop reporting `ui_stale`."

**Evidence:**
```
recorded: 5a9c7773b782fceaa95fd30905a5123fbe1bf4b3eed977b9e0236b9af15e7edb
current : e7562bb98cfb3bca28d8f9df76ad2c23f16f4c93d31cb60b072835456adc60df
STALE
```
`git log f6b2e19..HEAD -- hub/hub/static/ui` shows `2a52fcd` **did** copy a fresh bundle; the stamp
alone was not re-recorded.

**The bundle content itself appears correct.** `2a52fcd` added `SpecProposalsPanel.tsx` (175 lines),
`SpecDocumentPanel.tsx` wiring and `api/spec.ts` functions, and a literal unique to the new panel
(`'at the top'`, `SpecProposalsPanel.tsx:91`) **is present** in `hub/hub/static/ui/assets/*.js`. A
control literal from a previously-built panel confirmed the grep method. So this is a false alarm in
a health signal, not a missing feature.

**Most likely cause, not confirmed:** the fingerprint covers all of `hub/ui/src` **including
`__tests__`** (the known over-broad-fingerprint item in `prep_notes.backlog`), and `2a52fcd` also
added `specProposalsPanel.test.tsx`. If `refresh_ui_bundle.py` ran before that test file was
written, the stamp would lag by exactly one test file while the bundle content is current. I did not
confirm this by rebuilding.

**Correction to the record:** I initially read the commit ordering as "244 lines of UI code were
never rebuilt" and told the operator the shipped bundle lacked the proposals panel. That was wrong —
the literal check above disproves it. Recorded here because the wrong version briefly informed a
merge decision.

**Suggested direction:** Run `python scripts/refresh_ui_bundle.py` and commit the stamp. Separately,
the over-broad fingerprint is worth narrowing so test-only edits stop marking the bundle stale.
