Summary

A locally-installed multi-agent development environment. One local instance owns a collection of projects, spawns the agent processes on your machine, and connects specification, tasks, runs and evidence into one surface. This document is the corpus's entry point: it states the invariants that hold across the whole product and that no single capability document owns. The 33 capability documents beneath it describe individual behaviours.

Problem

Multi-agent development tools fragment the work: the specification lives in one place, the tasks in another, the agent transcripts in a third, and nothing connects a requirement to the run that satisfied it or the evidence that proves it. AgentWeave's premise is that these are one workflow, and that the barrier to using them together should be as close to zero as a local install allows.

Scope

In scope

  • Multi-agent collaboration with inter-agent communication
  • Spec-driven development with the agents: requirements, tasks, runs and evidence connected to the conversation
  • Governance and quality gates over that work
  • A local install that owns the agent processes on one machine

Non-goals

  • Remote or multi-user deployment; a federated connect-to-other-users-agents story is deliberately deferred
  • A no-Hub product: the CLI-as-collaboration-substrate, the watchdog, and the local and git transports were removed, not preserved
  • Backward compatibility with those removed surfaces; there is no external install base to protect

Requirements

FR-1

SHALL There SHALL be exactly one runtime that executes agent work. The command-line interface MUST do only what cannot be done from inside the application - start it, diagnose why it will not start, stop it, reset it - and MUST NOT be a collaboration surface.

A second runtime is a second source of truth about what an agent is doing. The CLI carried one until 2026-08-02; removing it is why the watchdog, the local and git transports, and the role subsystem no longer exist and are not to be recreated.

FR-2 consumer

SHALL An agent's identity SHALL be established from the credential its run was started with, and MUST NOT be accepted from a request body, header or parameter.

Anything a caller can assert about itself, a caller can assert falsely. A per-run credential makes every effect attributable to the run that caused it.

FR-3

SHALL Every project filesystem path SHALL resolve through the project workspace, which refuses absolute paths, traversal, control characters and symlink escapes. The instance's own working directory MUST NOT be used as project identity.

One instance owns many projects, so the current directory names nothing. A path that skipped this check would let one project read another's files.

FR-4

SHALL A specification document SHALL be a file in the project's working directory, rendered by the instance from a structured payload. An author MUST NOT write specification markup directly, and markup written by any other means MUST NOT be treated as a document's content.

The instance mints requirement identifiers and records content digests while rendering. Markup that arrived another way has neither, so it cannot be traced to or from anything.

FR-5

SHALL Approval, rigor, archiving, and the arrangement of the document index SHALL be reserved to the operator. An agent MUST NOT be able to express any of them, and the refusal MUST hold at the service boundary rather than only at the surface that offers it.

A rule enforced in one place survives exactly as long as nobody adds a second caller. These are judgements about whether work is acceptable, which is the thing a person is for.

FR-6

SHALL A capability document's content SHALL be written only by the operator. A submission from any other actor SHALL be refused regardless of the document's phase.

A capability document states current, shipped behaviour. It sits outside the phase machine, so no phase would otherwise block a submission against it.

FR-7

SHALL A project's identity SHALL travel with its directory rather than with the database that first saw it. An instance encountering a project marker naming an identity it has never seen SHALL adopt that identity rather than refuse the folder.

An operator should be able to open any AgentWeave project from any AgentWeave instance they choose. Identity bound to a database makes a folder unopenable anywhere else.

FR-8

SHALL The agent tool server SHALL be a thin adapter over the same operations the HTTP surface exposes, and MUST depend on nothing beyond the standard library and its own server framework.

It is spawned as a standalone process, so anything it imports from the wider application would not be there. Direct HTTP stays first-class because some environments prohibit tool servers entirely.

Behaviour

How a specification document reaches current behaviour

  1. The operator starts an exploration, which creates an empty document in the exploring phase
  2. An author fills it in by submitting a structured payload; the instance renders it and mints identifiers
  3. The operator closes the exploration, then proposes the document - proposal is refused while any requirement lacks a covering acceptance criterion or task
  4. The operator approves it; approval is theirs alone and is refused for any other actor
  5. When the work ships, the operator archives the change, or merges its delta into a capability document that describes current behaviour
  6. A capability document is created directly in the current phase and never transitions; the operator writes it, either by merging an approved change into it or by writing its content outright

How a corpus travels between machines

  1. Each document is a file beneath spec/ in the project's working directory
  2. spec/index.json records each document's title, kind, phase, parent and order, and which document is home
  3. Both the files and the index travel with the folder, so any instance that opens the directory can read the whole corpus and its arrangement
  4. What does not travel is per-database: the requirement, evidence and coverage graph, which the receiving instance rebuilds
  5. An instance rebuilds the index from the documents it holds, preserving any arrangement already recorded rather than recomputing it

Design

Three components. The command-line interface (src/agentweave/) starts, diagnoses, stops and resets the application and does nothing else; it is published as agentweave-ai and its own code imports nothing outside the standard library. The application itself (hub/) is a FastAPI backend with a React dashboard, and owns execution: the agent processes, the run credentials, the specification documents, the task board and the event stream. Documentation (docs/) is built with MkDocs.

Three independent project-scoped concepts underpin the roster. A runner describes reusable execution capability - a tool, a model and flags. An agent is an addressable identity bound to at most one runner and at most one charter. A charter is an editable behaviour contract injected into an agent's turn context. Fresh projects seed default runners and nine starter charters.

The 33 capability documents beneath this one describe individual behaviours in detail. They group loosely into the agent surface (capability plane, charter, composer, configuration, context, conversation workspace, loops, run sandboxing, stream events, tool surface), the specification surface (document authority, chat session, requirement traceability, task lifecycle governance), and the workspace surface (local project workspace, workspace shell, project environment settings, app lifecycle, runtime diagnostics, usage accounting).

Evidence and coverage limits

Checked

  • src/agentweave/cli.py - exactly five cmd_ functions: status, doctor, stop, hub_start, reset. Verified by enumeration, 2026-08-20
  • hub/hub/agent_auth.py - run tokens are minted per run and matched by hash against the Run row; hub/hub/api/v1/agent_actions.py binds the actor to the run rather than to anything in the request body
  • hub/hub/project_workspace.py - resolve_relative refuses absolute paths, traversal and control characters; hub/hub/spec_documents.py routes every path through it
  • hub/hub/spec_service.py:128 - a capability write is refused for any actor that is not the operator; hub/tests/test_operator_authored_documents.py exercises both halves over HTTP
  • hub/hub/mcp_server.py - imports are json, os, re, time, urllib and typing from the standard library, plus fastmcp. Verified by enumeration, 2026-08-20
  • hub/hub/project_lifecycle.py - open_existing adopts a marker naming a project this database has never seen, creating the row under that same identity
  • hub/hub/data/charters/charters.json - nine starter charters, verified by count 2026-08-20

Limits

  • This document was authored rather than migrated: unlike the 33 capability documents beneath it, it has no openspec source, so its requirements are the author's synthesis of invariants stated across CLAUDE.md, the product-direction exploration and the code cited above. Each was checked against the code on 2026-08-20; none was carried verbatim from a specification that already existed.
  • The project's stated rule that live state reaches the interface by server-sent events and never by polling is NOT asserted here as a requirement, because it is not currently true: hub/ui/src/api/permissions.ts, questions.ts and unaskedQuestions.ts each set a refetchInterval. Recorded rather than asserted.
  • The component groupings in the design section are the author's, for orientation. The corpus records no parent-child structure, so nothing in the index reflects them.
