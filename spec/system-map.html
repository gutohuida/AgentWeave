AgentWeave — System Map

Durable system context: intent, constraints, bounded contexts and ownership, and the shared contracts every child change specification must respect.
Status: Living Scope: whole system Last reviewed: 2026-07-27

0.Front Matter#

0.1Role of this document#

This document holds the durable system knowledge for AgentWeave: what the system is for, the constraints that outlive any single change, which bounded context owns what, and the contracts that cross those boundaries. It is deliberately small. Detailed behavior lives elsewhere:

DocumentHoldsChanges when
This system mapIntent, durable constraints, context ownership, shared contractsA boundary, constraint, or contract changes
agentweave-spec.htmlDetailed living behavioral baseline (CLI, transport, MCP, Hub, UI)Specified behavior changes
roadmaps/agentweave-reconstruction.htmlIndependently deliverable vertical slices and their dependenciesA slice is added, split, or completed
spec/changes/<name>/spec.htmlOne approved change: requirements, acceptance criteria, design, tasksPer change, via /aw-spec-propose
Note Keeping durable context out of child specs is what stops every change document from re-litigating system-wide decisions, and stops the same rule from being restated in divergent forms across sibling specs. A child spec should link here rather than copy from here.

0.2Conformance classes#

Following the WHATWG HTML Living Standard's producer/consumer distinction, requirements in AgentWeave specifications separate two audiences:

  • Requirements on producers — what a user, agent, or client is allowed to supply (well-formed input, valid field values, permitted call sequences).
  • Requirements on consumers — how AgentWeave software must act in response (validation, persistence, side effects, responses). Requirements on producers have no bearing on how a consumer handles malformed input; that behavior is specified separately.

The key words must, must not, should, and may are to be interpreted as in RFC 2119.

0.3Typographic conventions#

Only Requirement blocks and inline must/should/may statements are normative.

RequirementSM-X-000 A normative, testable assertion with a stable ID, listed in the Requirements Index.
Note Non-normative rationale — the "why" behind a rule.
Example Illustrative only; one valid possibility, not the only one.
Warning A hazard or common mistake.
Open Issue A known unresolved question that a reader must not treat as settled.

1.System Intent#

AgentWeave coordinates AI agents working on a shared project through a CLI, local/git/HTTP transports, an optional Hub backend and UI, and role-based workflow guidance. The detailed behavioral baseline is agentweave-spec.html.

RequirementSM-I-001 Every change specification must state which part of this intent it advances, and must not introduce a capability that belongs to a context it does not own (see §3) without an accompanying shared-contract change (see §4).

2.Durable Constraints#

These hold across changes. A change that breaks one is not a normal change: it supersedes this document and must update it in the same change set.

RequirementSM-C-001 The Python CLI must support Python 3.8+ and must not require runtime dependencies for its default feature set.
RequirementSM-C-002 The Hub backend must be FastAPI with SQLAlchemy; the Hub UI must be React/TypeScript. A substitution is a system-map change, not a child-spec decision.
RequirementSM-C-003 Tasks, messages, sessions, and transport operations must retain the validation and concurrency guarantees specified in the living baseline. A change that relaxes one must record the relaxation as a normative change there, not only in its own spec.
RequirementSM-C-004 Tests, schemas/migrations, fixtures, configuration, and runbooks are independent verification evidence. A change must not claim complete behavioral coverage from a passing test suite alone; it must name the evidence it checked and the coverage gaps that remain.
Note SM-C-004 exists because a spec-driven workflow makes it cheap to generate confident-sounding coverage claims. Naming what was not verified is what keeps a regenerated implementation honest.

3.Domains & Ownership#

Each row is a bounded context: it owns its internal model and exposes a public integration surface. Contexts integrate through that surface only.

RequirementSM-D-001 A context must not import another context's internal model. Integration must go through the listed public surface.
Note The same term may be represented differently across contexts. The Hub's persisted task representation and the CLI's local task representation integrate through their contract; neither imports the other's internal model. This is deliberate — a single unified model across all contexts costs more than it returns.
Example A change that adds a task field visible in the dashboard touches CTX-COLLAB (the field and its validation), SM-K-002 (the Hub REST/SSE contract carrying it), and CTX-UI (its presentation) — three ownership areas, one shared contract, and therefore one contract task rather than three private field definitions.

4.Shared Contracts#

A shared contract is any interface owned by no single change. Changing one is a cross-context event.

IDContractProducersConsumers
SM-K-001BaseTransport method contract and transport payload validationCLI, watchdog, MCP toolslocal / git / HTTP transport implementations
SM-K-002Hub REST API, SSE event vocabulary, Hub-side MCP tools, authentication behaviorCLI HTTP transport, Hub UI, agents over MCPHub backend
SM-K-003spec.html metadata and task-attribute convention used by the AW-Spec workflow/aw-spec-propose/aw-spec-apply, /aw-spec-archive, Hub spec viewer
SM-K-004agentweave.yml and the generated agent-context / role contractsoperators, agentweave setup commandsCLI, runners, quality governance, skills
RequirementSM-K-010 A change that alters a contract in this table must, in its own child spec, name: (a) the contract ID, (b) its compatibility strategy, and (c) the contract tests that verify it.
RequirementSM-K-011 The contract change must be specified once, in one task traced to one requirement. Sibling specs must not restate it; they reference the contract ID.

Applied to a proposed cross-context change, in order:

  1. Identify every context in §3 the change touches.
  2. If more than one context is touched, identify the contract in this table that carries the interaction.
  3. If no existing contract carries it, stop: either the change belongs inside one context, or a new contract must be added here first.
  4. State the compatibility strategy for the contract: additive, versioned, or breaking with a migration.
  5. Name the contract test that fails today and passes after the change; if none exists, add writing it as a task.

5.Rules for Child Specs#

RequirementSM-R-001 A child spec must cover exactly one vertical capability with its own acceptance criteria. Splitting by frontend / API / database layer must not be used.
RequirementSM-R-002 When a request contains multiple independently demonstrable outcomes, a shallow roadmap must be created or updated before any child spec is authored. Each roadmap row carries a stable ID, intent, explicit in/deferred boundary, dependencies, status, and a link to its child spec.
RequirementSM-R-003 A child spec must link to its parent roadmap row, and the roadmap row must link back to the child spec.
RequirementSM-R-004 A child spec must declare its persistence model — flow-back (artifacts edited and reconciled manually), flow-forward (a new immutable change directory per change), or living spec (the spec is the source and downstream artifacts are regenerated) — and the reconciliation rule that applies after implementation.
Note The three names come from the spec-persistence literature (Böckeler, Understanding Spec-Driven Development, martinfowler.com) and from GitHub Spec Kit's docs/concepts/spec-persistence.md. AgentWeave uses flow-forward for spec/changes/<name>/ and living spec for this map and agentweave-spec.html.
Warning Do not create a roadmap for a small coherent change merely because it has several tasks. Decomposition has a cost — apply it when a slice is not independently testable or cannot be implemented in one approval cycle.

6.Non-Goals of This Document#

Stated explicitly so nothing is inferred from omission:

  • It does not specify behavior. Field-level rules, command surfaces, endpoints, and events belong to agentweave-spec.html.
  • It does not schedule work. Sequencing and slice boundaries belong to the roadmap.
  • It does not hold tasks, agent assignments, or approval state. Those belong to a change's spec.html.
  • It does not record implementation history. That belongs to the repository's changelog and commits.
