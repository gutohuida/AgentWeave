Project checks

capabilitycurrentsketch

11 MUST·11 requirements·19 criteria

Summary

The operator configures shell commands (tests, linters) that the Hub runs, in the background, on the exact commit a task's approval would merge, and records the result so approval can read it.

Problem

A task can pass its own evidence and still break the project once merged onto a main branch that has moved. Running the project's own checks on main-plus-the-task's-work, before approval, catches that without trusting anything an agent says.

Scope

In scope

  • Operator-only configuration of a project's checks
  • When a check run starts, what commit it runs on, where, and with what environment
  • How a run is recorded, read, re-run, interrupted and retried

Non-goals

  • Refusing or allowing approval on the result (task-lifecycle-governance owns the gate and the operator override)
  • Running anything an agent supplies: every command comes from the operator's settings

Requirements

FR-1# Requirement 1 of 11

SHALL A project SHALL carry an ordered list of at most 20 checks, each with a non-blank name unique within the project, a non-blank shell command and a timeout of 10 to 3600 seconds (default 900), set only through the operator's project settings; no run credential SHALL be able to change it.

WhyThe Hub executes these commands, so only the operator may write them. A project with no checks (null or empty list) records no runs and approval ignores checks entirely.

FR-2# Requirement 2 of 11

SHALL A check run SHALL execute every configured check, in order, in a Hub-owned scratch worktree detached at a commit whose tree is the project's main branch tip with every merge target of the task's approval merged in, and SHALL never run in the project's root checkout or an agent's worktree.

WhyChecking the task branch alone misses breakage caused by main having moved; checking in a shared checkout would disturb the operator or an agent. The merged commit is built with git plumbing, so no branch, index or checkout changes.

FR-5# Requirement 3 of 11

SHALL The Hub SHALL start a check run in the background, never inside the request that triggers it, when a task is moved to `completed` outside a turn, when a turn bound to a task that is `completed` ends, and when approval is requested and the latest result is missing, stale, interrupted or `error`.

WhyWork an agent completes mid-turn is only committed when its turn ends, so checking at completion would check the wrong commit. A check can take minutes; no transition waits for it.

FR-6# Requirement 4 of 11

SHALL A check run SHALL be recorded with the main tip it was built on, the merge targets, the merged commit, a state (`running`, `passed`, `failed`, `error` or `interrupted`) and, per check, its exit code, whether it timed out, its duration and the last 4000 characters of its combined output; a check that exits non-zero or exceeds its timeout SHALL fail the run, and a timed-out check SHALL have its whole process tree ended.

WhyThe record is what approval, the reviewer briefing and the operator read; a timed-out check left running would hold the scratch worktree and leak processes.

FR-7# Requirement 5 of 11

SHALL When a merge target does not merge cleanly onto the main tip, or the Hub otherwise fails to produce a result, the run SHALL be recorded `error` with the reason, and an `error` result SHALL be treated as no verdict and run again when approval is requested.

Why`error` is the Hub failing to check, not the work failing its checks, so it must not stand as a result the way `failed` does.

FR-8# Requirement 6 of 11

SHALL Merge targets already reachable from the main tip SHALL be excluded from a run; a project with no main branch, or a task with nothing left to merge, SHALL record no run.

WhyA target already on main would re-check main and blame its failures on this task.

FR-3# Requirement 7 of 11

SHALL A Hub that starts and finds runs still `running` SHALL record them `interrupted`, and a result whose main tip or merge targets no longer match the current ones SHALL be treated as stale rather than trusted.

WhyA restart kills in-flight checks; leaving them `running` would block approval forever, and a pass on an older main says nothing about the work approval would merge now.

FR-9# Requirement 8 of 11

SHALL No more than two check runs SHALL execute at once per Hub, at most one per task; a request for a task whose run is already executing SHALL start nothing new, and a request whose latest `passed` or `failed` result is current SHALL return that result instead of running again.

WhyChecks are often whole test suites; unbounded parallel runs would starve the machine and the agents on it.

FR-4# Requirement 9 of 11

SHALL A check SHALL run with the Hub process's environment minus the Hub's own configuration: every variable whose name starts with `AW_`, `HUB_` or `AGENTWEAVE_`, `DATABASE_URL`, and any variable whose value starts with `aw_live_` or `aw_run_`; any removed value or credential-shaped string (`aw_live_…`, `aw_run_…`) appearing in its output SHALL be recorded as `[redacted]`.

WhyA check runs the project's commands, which may be changed by the very agents being checked; the Hub's credentials and database must not reach them or be echoed into records agents read.

FR-10# Requirement 10 of 11

SHALL The operator SHALL be able to read a task's last 10 check runs, newest first, with whether checks are configured and whether a run is executing (`GET /tasks/{task_id}/checks`), and to start a run even over a current result (`POST /tasks/{task_id}/checks/run`); the task drawer SHALL show the latest run's state and offer that re-run.

WhyWhen checks fail for a reason outside the work (a flaky test, a fixed environment), the operator needs to see why and re-run without touching the task.

FR-11# Requirement 11 of 11

SHALL A reviewer's turn briefing SHALL state the task's recorded check result (passed, failed with the failing checks and output tail, could not run, or not finished) and that fixing a failure is the author's work, returned with `revision_needed`; reading it SHALL start no run.

WhyA reviewer who does not know the checks failed approves into a refusal, or fixes the author's work itself.

Design

D1 Merged commit by plumbing. The commit approval would produce is built with `git merge-tree --write-tree` and `commit-tree`, one target at a time onto the main tip, skipping targets already in the base. No branch, index or checkout moves, so building it is safe while agents and the operator work.

D2 Scratch worktree per task. The merged commit is checked out detached at `.agentweave/checks/<task_id>` under the project root (gitignored), with the repository's shared dependency directories symlinked in when the OS allows. It is removed after the run; a leftover locked registration is unlocked and force-removed before the next. Adding and removing it may take up to 900 s, since it writes the whole tree.

D3 One record per run (`task_check_runs`). Results are written after each check, so a reader sees progress. Deleting a task deletes its runs.

D4 Bounded, per-task queue. Two runs per Hub, one per task, in-process. A restart marks leftover `running` rows `interrupted` at startup.

D5 Never inside a request. Completion outside a turn, the end of a turn bound to a completed task, and an approval request with no current result each schedule a background run; the approval gate itself only reads (`project_checks.view`). Only callers that are approving may schedule.

D8 Hub configuration stays in the Hub. A check's environment drops the Hub's own variables by prefix and by credential-shaped value, and output is scrubbed of anything removed, because check output is quoted to agents.
