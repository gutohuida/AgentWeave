Task lifecycle governance

capabilitycurrentsketch

33 MUST·33 requirements·115 criteria

Summary

Which task status moves are legal and who may make them; the append-only record of every accepted move; who may change a task's other fields; the waiting (`blocked`) status; the gates on starting, completing and approving work; and what approval does to the repository (local integration of the approved commits, its record and retries).

Problem

Without a declared machine a task's status is whatever the last writer said: a run could move its own work to `approved` in one call, and a single mutable column could not show that author and approver were the same. This capability makes every recorded move legal, attributed and made by an entitled actor, and makes `approved` mean the work reached the main branch or says why it did not. It governs validity, not liveness: whether a move happens when reality changes is `run-task-binding`'s.

Scope

In scope

  • The transition map, entry statuses, actor kinds, causes and status bands
  • The transition history and its read routes
  • Author/reviewer separation, the review-entry holder rule and the completion binding gate
  • Which task fields only the operator may set; rename and delete
  • The `blocked` status: entry, release and what it records
  • Approval gates: requirement rigor, live turn, conflicts, unaccepted evidence, checks, git unavailable
  • Integration on approval, its record, retry and re-attempt triggers, and the preview
  • Task list scoping and the task view's requirement links

Non-goals

  • Binding runs to tasks and divergence handling (`run-task-binding`)
  • Dependency declaration and evaluation (`task-dependencies`)
  • Evidence recording and coverage (`requirement-traceability`)
  • Running project checks (`project-checks`)

Requirements

FR-33# Requirement 1 of 33

SHALL The Hub SHALL declare, in one place, every legal move between the nine task statuses (`pending`, `assigned`, `in_progress`, `blocked`, `completed`, `under_review`, `revision_needed`, `approved`, `rejected`) and SHALL refuse any status change that is not a declared move. A refusal SHALL name the task's current status and the statuses reachable from it for the requesting actor, and SHALL leave the task and its history unchanged. Restating the status a task already holds SHALL succeed as a no-op that records nothing.

WhyA status that is whatever the last writer said cannot be governed. Naming what is reachable lets a refused caller correct itself; making a restatement a no-op stops a retried call from manufacturing a transition (and a false answer to who completed the task).

FR-34# Requirement 2 of 33

SHALL The Hub SHALL let a task be created only in an entry status, `pending` or `assigned`, and SHALL refuse creation in any other status over every route. Creation SHALL NOT record a transition.

WhyA lifecycle that can be entered anywhere is not a lifecycle: without this a caller reaches `approved` by creating the task there. The history begins with the first move; the entry status is stated by the task itself.

FR-36# Requirement 3 of 33

SHALL The transition map SHALL declare, per edge, which actor kinds may take it, and SHALL give the operator edges no agent run has: rejecting from any non-terminal status other than `under_review`, reassigning a `blocked` task, and reopening `approved` (to `revision_needed`) or `rejected` (to `pending`). The operator SHALL NOT be able to make a move the map does not declare.

WhyOperator authority is extra legal edges rather than a bypass, so every recorded history is a legal sequence. Rejecting from `under_review` is a review outcome and open to agents; rejecting elsewhere is abandoning the work, which is the operator's.

FR-35# Requirement 4 of 33

SHALL The app SHALL let the operator take every transition the map grants them from a task's view, and SHALL offer only the moves legal for the operator from the task's current status, read from the Hub's own declaration (`GET /tasks/transitions/allowed`).

WhyExclusive operator authority with no surface to exercise it grants nothing; offering only legal moves means nothing is presented and then refused, and the client never holds a second copy of the map.

FR-37# Requirement 5 of 33

MUST The Hub SHALL record one immutable row per accepted transition naming the task, the from and to status, the actor kind, the run and agent where an agent run acted, the cause (`actor`, `runtime` or `job`, with the job id for `job`), the policy that governed it and any checks-override reason, ordered by a sequence number. No application path SHALL update a transition row; rows are removed only when the operator deletes the task itself.

Why`Task.status` is the materialised current value; the history is the durable account of how it got there, and author/reviewer separation reads it. The cause distinguishes a move an actor asked for from one the runtime or a scheduled job made on someone's behalf, so a check like "did this run advance its task?" is not satisfied by the system's own bookkeeping.

FR-38# Requirement 6 of 33

SHALL The Hub SHALL refuse an agent run's move to `approved`, `rejected` or `revision_needed` when that run's agent is the agent recorded as moving the task to `completed`, or is an agent that recorded evidence for the task (whatever that evidence's review state, and whoever completed the task). Evidence the operator recorded SHALL refuse no agent. The operator SHALL be permitted every review outcome regardless of who produced the work.

WhyDistinctness is on agent identity, not run: every turn is a new run, so a run check forbids nothing. Evidence is the one authorship record that reviewing does not create, so it catches an agent judging its own work where the completion names nobody (an operator completion) or names a different agent (F505). Evidence keyed on its review state would make the authority to review depend on the review's outcome. The operator is exempt so a single-operator project can approve anything; the history says an operator did it.

FR-39# Requirement 7 of 33

SHALL The Hub SHALL refuse, for every actor including the operator, a move to `under_review` while the task's assignee is the agent recorded as completing it or an agent that recorded evidence for it. A task with no assignee, or whose assignee is neither, SHALL be permitted. Where one request sets both the assignee and the status, the assignee SHALL be applied first. The refusal SHALL name a remedy the refused actor has: to the operator, landing the task or dispatching another agent's review turn (`POST /agent/trigger` with `review_task_id`); to an agent, that none of its task tools reassigns a task and the operator can move it on.

WhyThis is about the state the move produces, not authority: `under_review` held by its author claims a reviewer holds work its author holds, and such a task is claimable by nobody and strands its assignee (F70). An evidence author holding the review could not finish it, because its verdict is refused. Applying the assignee first lets one operator request name a reviewer and enter review together.

FR-41# Requirement 8 of 33

MUST Transition legality, actor separation, the completion and approval gates, and history recording SHALL be enforced in the single transition service every status write passes through, so they hold identically for the operator API, the agent HTTP plane, the MCP adapter, scheduled jobs and runtime moves. The MCP adapter MUST surface a refusal as a failed tool call carrying the reason, never as an empty or successful result.

WhyA rule enforced at one route holds only for the callers somebody remembered. One choke point means a surface gets every gate without knowing it exists.

FR-42# Requirement 9 of 33

SHALL When the Hub moves a task because of something it observed, it SHALL act as the responsible run, and a scheduled job's firing SHALL act as the operator; each such move SHALL be subject to every rule the same actor's own request is, and only its recorded cause (`runtime` or `job`) SHALL distinguish it. There SHALL be exactly two actor kinds, agent run and operator.

WhyActor kind is what the map and author/reviewer separation key on; a third "system" kind would need every edge to declare whether the system may take it and would admit moves nobody is accountable for.

FR-82# Requirement 10 of 33

SHALL A transition made by a loop or flow firing, including the dispatch of a review the firing queued, SHALL be recorded with the operator as actor and cause `job` naming that job; a move the operator makes by hand, including dispatching a review themselves, SHALL be recorded as cause `actor`.

WhyThe firing holds the operator's authority because the operator created the job, but the history must not say the operator asked for a move made while they were asleep. The job id outlives the firing's own records.

FR-94# Requirement 11 of 33

SHALL The Hub SHALL let the operator and agents read a task's full transition history, oldest first, each row naming its statuses, actor kind, agent, run, cause, the job's name and kind (`loop` or `flow`) where a job made it, the recorded policy and any checks-override reason; an unknown task SHALL answer 404 rather than an empty history.

WhyThe history was append-only and complete but unreadable without opening the database (F203). "No history" and "no such task" are different answers.

FR-72# Requirement 12 of 33

SHALL An agent run SHALL move a task to `completed` only while that run is bound to the task; a run bound to another task, or to none, SHALL be refused with HTTP 403 naming what it holds. The operator SHALL need no binding.

Why`completed` puts work in the reviewable pool, so a false completion is reviewed by an agent that finds the code correct (someone else wrote it), approved and merged with no human on the path (F27). Every legitimate completion has already passed the claim into `in_progress`, so the run is bound. Completion deliberately requires no evidence: evidence is judged after review.

FR-95# Requirement 13 of 33

SHALL When a task moves to `revision_needed`, the Hub SHALL make the agent recorded as completing it the task's assignee again; where no agent is recorded as completing it, the assignee SHALL be left unchanged.

WhyA reviewer is the assignee while it reviews; without this the reviewer reworked what it reviewed, became the completer, and the author was staffed to review the reviewer's fix (F495). An operator completion names no agent, so nothing is guessed.

FR-96# Requirement 14 of 33

SHALL An agent's update to a task SHALL be refused, before anything in the request is applied, when it names the task's assignee, priority, description, title, divergence policy, escalation agent, loop or a checks-override reason; an agent changes a task only through its status, notes and requirement links.

WhyWho holds a task and how it is described are the operator's statements. An agent able to unassign or self-assign a task bypasses the holder rules above (F366); one able to set its own divergence policy could disarm the check that catches it dropping work.

FR-84# Requirement 15 of 33

SHALL The operator SHALL be able to change a task's title after creation; an agent SHALL NOT. A blank title SHALL be refused, a request that omits the title SHALL leave it unchanged, and a rename SHALL record no transition and need no status.

WhyA title written once at creation goes stale as the work moves; without a rename the only remedy is replacing the task and losing its history.

FR-44# Requirement 16 of 33

SHALL The `blocked` status SHALL mean work began and cannot proceed until a person supplies something. It SHALL be reachable only from `in_progress`, SHALL have no edge to `completed`, and SHALL leave by `in_progress` (either actor) or, for the operator only, by `assigned` or `rejected`.

WhyA task nobody started is pending, not waiting. Forcing finished work back through `in_progress` keeps any history from saying a task was completed while still waiting on an answer that never came.

FR-45# Requirement 17 of 33

SHALL The Hub SHALL move a task to `blocked` when a run bound to it asks a blocking question, at the moment of asking, as a runtime move attributed to that run; and, at the end of such a run, for a task not yet blocked whose run left a qualifying question unanswered. It SHALL move the task back to `in_progress` when that question is answered. An agent SHALL be refused (HTTP 403) when it asks to move its own task into or out of `blocked`.

WhyThe wait matters during the ask, so the board must say so then. The run-end check covers a task that was not `in_progress` at the ask, or a park that failed (a failed park never costs the agent its question). An agent that could declare itself blocked could claim a wait it never asked for; one that could unblock itself could finish the work with no record that it proceeded without an answer.

FR-47# Requirement 18 of 33

SHALL A task SHALL be recorded as waiting only on a question that is marked blocking, unanswered, not declined, whose wait has not already ended, and that was asked by the run whose ask or end is being evaluated.

WhyA non-blocking question is a note; a question another run left open is not evidence this run stopped for it; a question whose wait ended is waited on by nobody, and parking on it would hide a real divergence.

FR-46# Requirement 19 of 33

SHALL A `blocked` task SHALL carry a statement of what it is waiting for: derived from the question where the Hub parked it, and required of the operator (HTTP 422 without it) where they set it. The statement SHALL be cleared whenever the task leaves `blocked`. The app's control that collects it SHALL take keyboard focus once the operator chooses the move.

WhyThe status answers "why is nothing moving"; only the statement answers "what do you need from me". A mandatory field reachable only by pointer makes the move unavailable from the keyboard with nothing saying why.

FR-48# Requirement 20 of 33

SHALL Declining the question that parked a task SHALL return the task to `in_progress` and clear its reason, as an operator transition; a declined question SHALL never park a task.

WhyThe operator has said the answer is not coming, so nothing is being waited on; re-parking on the declined question at run end would undo the release.

FR-75# Requirement 21 of 33

SHALL When a bounded wait for an answer ends without one and the asking run carries on, the Hub SHALL record that the wait ended unanswered and return the blocked task to `in_progress`. It SHALL accept the run's report only for its own questions whose Hub-recorded deadline (the Hub's own configured wait, not a duration sent with the ask) has passed and that are neither answered nor declined, refusing any other report. Where no report arrives, the run's end SHALL do the same if the deadline has passed. A wait ended by the operator answering or declining SHALL NOT be recorded as unanswered.

WhyNobody is waiting any longer, and a `blocked` task cannot reach `completed`. A deadline supplied by the reporting party would let it choose the threshold it is checked against; the run-end sweep handles a report that was sent and lost, and can never end a wait early.

FR-76# Requirement 22 of 33

SHALL Where a run's wait for an answer ended unanswered, the task it was bound to SHALL state that its work proceeded without the operator's answer, naming the question, in every later status, even after the question is answered. The statement SHALL be derived from the recorded wait, not stored a second time.

WhyAn agent that waited out its question and decided alone otherwise leaves a task that reads clean (F60). Clearing the statement when a late answer arrives would hide the unilateral call exactly when it may contradict what shipped.

FR-70# Requirement 23 of 33

SHALL Every status the transition map defines SHALL be classified into exactly one lifecycle band (agent-actionable, awaiting a person, awaiting hand-off, with a reviewer, terminal), checked against the map itself, and the Hub SHALL fail to start when a status is unclassified, classified into an unknown band, or classified without being in the map.

WhyStatus sets scattered as literals drifted apart and caused stalls (`completed` and `revision_needed` fell between sets). A gap found at import cannot be found at 3am by a loop firing forever.

FR-71# Requirement 24 of 33

SHALL Every set of statuses the Hub uses to answer whether a task is claimable, reviewable, with a reviewer, a queue's current item, live, or terminal SHALL be derived from the band classification, one set per question; two questions SHALL NOT share a set because their members overlap.

WhyDeriving makes a new status reach every set that includes its band; keeping one set per question stops the classification from re-merging questions that differ (`blocked` is not claimable but is a loop's current work).

FR-58# Requirement 25 of 33

SHALL The Hub SHALL refuse a move to `approved` while a requirement the task serves on a `gate`-rigor document is not verified, or is structurally invalid; and, at every rigor, while a requirement it serves is `rejected`. `contract` requirements SHALL be reported on the approval and SHALL NOT block; `sketch` ones SHALL block only when rejected. Verification SHALL be read from the same coverage computation the document surfaces use, and the typed refusal SHALL name each requirement with its state and remedy.

WhyA gate that computed its own answer could disagree with the document beside it. A `rejected` requirement means its only proof was judged not to prove it; approving over it records as done what was refused (the FR-11 incident). An unactionable gate gets turned off.

FR-59# Requirement 26 of 33

SHALL A transition into `approved` SHALL record the policy that governed it: the state, integration and rigor of every requirement the task serves, `sketch` included; a task serving no requirement SHALL record none.

WhyRigor is editable, so a gate that passed last month cannot be explained today without the policy it ran under.

FR-98# Requirement 27 of 33

SHALL The operator SHALL be able to carry a `completed` task to `approved` in one action (`POST /tasks/{id}/land`), which clears the holder and takes the two declared moves `completed -> under_review -> approved`, each recorded as an operator transition; it SHALL evaluate the approval gate first and leave the task unchanged when any step is refused, and SHALL refuse a task not in `completed`.

WhyLanding otherwise cost three calls, two of them refusals (F163). Composing declared edges keeps the map unwidened, so `completed -> approved` never becomes a way to skip review.

FR-57# Requirement 28 of 33

SHALL A task's representation SHALL report the requirement identifiers it is linked to, in the form they were supplied, sorted with numeric parts compared by value (deterministically where there is none), and SHALL NOT include references that resolved to no requirement, which are reported separately as unresolved.

WhyA write-only field makes a task look tied to nothing while links govern its merge. Plain-text order puts FR-11 between FR-1 and FR-2.

FR-60# Requirement 29 of 33

SHALL The task list SHALL accept a loop scope that returns every task naming that loop, whatever its status, and no other task; a loop with no tasks SHALL return an empty list.

WhyA loop's queue is the tasks that name it, including finished ones, and the caller must see all of it.

FR-61# Requirement 30 of 33

SHALL The task list SHALL accept a document scope that returns every task that document declared, whatever its status or the document's phase; a document with no tasks SHALL return an empty list.

WhyA document's board must show all of its work, finished or not, archived or not.

FR-62# Requirement 31 of 33

SHALL The task list SHALL offer an opt-in mode that hides a task only when its declaring document is `archived` and its own status is terminal; it SHALL NOT apply when not asked for or when a loop or document scope is given, and SHALL change no task.

WhyFinished work from tidied-away documents clutters the board; open work and tasks with no document are never hidden.

FR-64# Requirement 32 of 33

SHALL The app SHALL show a task's full detail (description, acceptance criteria, deliverables, notes, requirement links) in a drawer sized independently of the board's columns.

WhyA board column cannot hold a long task without clipping it.

FR-89# Requirement 33 of 33

MUST The operator MUST be able to delete a task (`DELETE /tasks/{id}`), removing its dependencies, requirement links, transitions, integrations, check runs, evidence and queued entries, and clearing the task pointer on rows that only mention it (runs, conversations, messages, questions); the delete MUST be refused (HTTP 409) while a run bound to the task is active. No agent surface deletes a task.

WhyA task nobody should work is otherwise only ever rejected and stays counted. Deleting is the one path that removes transition and integration rows, because they exist only for the task.

Design

## D1. One declared map; operator authority is extra edges

`hub/hub/task_transitions.py` declares `TRANSITIONS` (from -> to -> actor kinds) and `ENTRY_STATUSES`; it does no I/O. The operator's extra power (rejecting before review, reassigning a blocked task, reopening `approved`/`rejected`) is extra edges, not a bypass, so every history is a legal sequence and no forced-move override exists. `completed -> approved` is deliberately absent; landing composes the two declared edges instead.

## D2. Two actor kinds, three causes

Actors are `run` (always with run id and agent) and `operator`. There is no system actor: the runtime acts *as* the run (cause `runtime`), a scheduled job acts *as* the operator (cause `job` + job id), and both pass every rule the same actor's own request would. Only the run-to-task binding records `runtime`, enforced by a source scan in the tests.

## D3. One choke point, fixed order

Every status write goes through `task_transition_service.apply_transition`. Order: no-op restatement -> map legality (409) -> author/reviewer separation (403) -> review-entry holder rule (403) -> run holds the task (403) -> dependency gate on starting edges (409) -> approval gate on `approved` (409, typed `gate_unsatisfied`) -> write status and history row -> resolve open divergences -> integrate (on `approved`) -> schedule checks (operator completion) -> release checkout and slice hook (terminal). 409 means the task's state forbids it; 403 means this asker may not.

## D4. Authorship is read from records reviewing does not create

Separation compares agents, never runs. The completer is the last `-> completed` transition by sequence. Evidence authorship (agent-recorded evidence rows, any review state) is the fallback and the F505 widening; the wider union (transitions, assignee, bound runs, evidence) is used only to *exclude candidates* when staffing a review, never to refuse a verdict, because by then the staffed reviewer is assignee and bound. The wedged-review predicate (`assignee_produced_the_work`) is shared by the flow's recovery and the dispatch's holder check so they cannot disagree.

## D5. `blocked` is observed, never asserted

Agents may not move into or out of `blocked`; the MCP status type omits it. The runtime parks at ask time and at run end, and releases on answer, decline or a verified expired wait. The Hub records the wait deadline from its own configured wait. `blocked -> in_progress` is exempt from the dependency gate because it resumes started work.

## D6. Approval means integration

Approving merges, locally and in the same operation, the commits accepted evidence names (reduced by ancestry per line of work), or the task's own branch tip where evidence does not govern; never an agent branch, never a remote. Integration can never roll back the approval: preconditions that make it impossible are recorded skips, and a failed merge is aborted and recorded. Each attempt is an append-only `task_integrations` row with outcome, reason, riders, mechanism `local` and `retryable` decided by `task_integration.is_retryable`.

## D7. Gate checks that ask "what would merge" stay silent when the question cannot be asked

Conflict, unaccepted-evidence and checks gates run only when `merge_situation` resolves (main branch set and existing, workspace resolvable, a repository). The live-turn and rejected-requirement refusals are not about the repository and apply everywhere. A git call that raises is a refusal (`GitUnavailableError`), not a 500 and not an approval. The preview asks the same `merge_situation` and test merge, but never refuses.

## D8. Lifecycle bands

Every status is in exactly one band (`STATUS_BANDS`), checked against the map at import. Each status set (claimable, reviewable, with-reviewer, current item, live, terminal) is a union of bands for its own question; sets are never merged because their members overlap.

## D9. Field ownership

An agent changes a task only through status, notes and requirement links; assignee, priority, description, title, divergence policy, escalation agent, loop and checks overrides are the operator's, refused before anything is applied. `revision_needed` returns the task to its recorded completer. `loop_id` is write-once at creation.
