Summary

How AgentWeave tells the operator whether it can run and why something did not: `agentweave doctor` and `agentweave status` for the instance, the Hub's per-agent launchability and collaboration-readiness report, typed refusals before a spawn, durable failure facts for runs and jobs, and the severity vocabulary those events carry.

Problem

Most runtime failures look alike from the outside ("the run failed", "the Hub is down"). Without checks that inspect the real instance and failures that carry their own facts, the operator diagnoses by guessing which other agents still work.

Scope

In scope

  • `agentweave doctor` and `agentweave status`, the result model they share, and how they describe a running instance
  • `GET /agents/launchability`: runnable and collaboration-ready verdicts per agent, including a provider runner's missing key
  • Pre-spawn refusals for agents that cannot run
  • Failure facts on `run_failed` and `job_run_failed`: exit statuses, the operation in flight, the error-stream tail
  • The severity values operator-facing events carry
  • The Logs view and the UI-bundle staleness signal

Non-goals

  • Context-window and token reporting (agent-context-usage, usage-accounting)
  • How runs are rendered in a conversation (agent-stream-events, turn-outcome-visibility)
  • What a run states about how it reached the Hub (agent-tool-surface)
  • The runner controls offered for an agent that will run but cannot collaborate (agent-configuration)
  • Which command form starts and manages the instance (app-lifecycle)

Requirements

FR-13# Requirement 1 of 17

SHALL `agentweave doctor` SHALL check Python support, the installed Hub runtime, runner CLIs on PATH, the Hub instance on the chosen port, port availability, database accessibility, Hub-state permissions and directory-symlink privilege, without starting the Hub, creating state, or calling any model provider.

WhyA readiness check that changes what it inspects, or needs the thing it is diagnosing to be up, cannot be run before first launch.

FR-14# Requirement 2 of 17

SHALL Each readiness check SHALL produce a result with a stable check ID, a target, a status (`pass`, `warn`, `fail`), a severity, a message and an optional hint, SHALL redact secret values from its data, and `doctor` SHALL exit non-zero only when a check fails.

WhyA stable structured result is what `--json`, logs and scripts read; secrets never belong in a diagnostic.

FR-15# Requirement 3 of 17

SHALL For a runner configured to send its runs to a model provider, the Hub SHALL report the agent not runnable when the environment variable the runner names for the key is unset, naming the variable and never its value.

WhyA missing key otherwise surfaces as an opaque provider failure mid-run.

FR-16# Requirement 4 of 17

SHALL Before spawning a run the Hub SHALL refuse, with a typed 409 naming the reason, an agent that does not exist, is archived, has no runner or a deleted runner, is not runnable, or already has a run in progress, and SHALL refuse with 501 a runner it has no adapter for; a refused delivery SHALL stay queued for retry.

WhyA launch known to be impossible should fail immediately and say why, and must not lose the input that asked for it.

FR-17# Requirement 5 of 17

SHALL A run that fails SHALL be recorded as a persisted `run_failed` event with severity `warn` carrying the agent, run ID, error, and where known the exit code and the runtime's error-stream tail, scrubbed of the run's registered secrets.

WhyA failure that exists only in a log line or a broadcast is gone by the time someone looks.

FR-19# Requirement 6 of 17

SHALL The Logs view SHALL offer an agent filter drawn from the project's roster and from agents named in returned log entries, shown as separate groups, and SHALL offer search and category filters (runner, proxy, setup, jobs, stderr).

WhyA deleted agent's history must stay filterable, and a fixed agent list hides custom agents.

FR-20# Requirement 7 of 17

SHALL A scheduled or manually fired job run that fails to start, fails to trigger its agent, or meets an internal error SHALL be recorded as a failed job run with an error summary and a `job_run_failed` event, and the job view SHALL show a failed or skipped run with its summary, distinct from disabled or idle jobs.

WhyA job that fails every five minutes in silence is indistinguishable from one that never fires.

FR-21# Requirement 8 of 17

SHALL The Hub SHALL report for each of a project's agents its runner, CLI, whether the CLI is present and authorized, whether it is runnable, and the reason when it is not, without starting a run.

WhyThe operator should know an agent cannot run before they send it work.

FR-22# Requirement 9 of 17

SHALL For a runnable agent bound to a runner, the Hub SHALL also report whether it can collaborate (its provider will let it call the Hub's tools, and the Hub knows the callback address it gives runs), naming each unmet condition in terms the operator can act on, without starting a run.

WhyAn agent that runs but cannot reach the Hub fails quietly; installed and authorized is not enough.

FR-23# Requirement 10 of 17

SHALL A run that fails because its runtime process ended SHALL report, as separate fields, the process's exit status, the operation in flight, and a bounded tail of what it wrote to its error stream, whether the failure was raised at start or reported by the turn.

Why'The process ended' is true of a crash, a missing binary, a rejected credential and an unresumable session alike; separate fields reach every reader, not only one sentence.

FR-30# Requirement 11 of 17

SHALL The Hub SHALL read the error stream of every runtime it starts, retaining only a bounded tail.

WhyA captured stream nobody reads fills and blocks the very process being diagnosed.

FR-31# Requirement 12 of 17

SHALL A turn's exit status SHALL be reported separately from the runtime process's exit status, and every displayed exit status SHALL be rendered readably (a forced termination reported as a large unsigned value is shown as the termination), while the recorded value stays as the platform reported it.

WhyOne death described by two or three different numbers cannot be diagnosed.

FR-24# Requirement 13 of 17

SHALL The Hub SHALL treat the bundled UI as current when its build stamp's source fingerprint matches the UI source as it stands, including uncommitted changes, SHALL otherwise report it stale through `/health`, `status` and `doctor` naming `python scripts/refresh_ui_bundle.py` as the remedy, and SHALL fall back to comparing commit dates when no stamp exists.

WhyA date comparison cannot be cleared by a rebuild that produces identical output, and a warning that survives its remedy gets ignored.

FR-32# Requirement 14 of 17

SHALL A newly recorded build stamp SHALL clear the staleness warning without restarting the Hub.

WhyThe staleness answer is cached briefly, not for the process lifetime.

FR-26# Requirement 15 of 17

SHALL `status` and `doctor` SHALL describe a running Hub by the runtime it reports about itself on `/health` (`native`, `docker`, or `AW_RUNTIME`), SHALL examine the port and profile database the operator named rather than the defaults, and SHALL report an unreachable instance rather than omit it.

WhyOnly the running process knows whether it is in a container; a clean report on the wrong instance is worse than none.

FR-27# Requirement 16 of 17

SHALL Where the Hub deliberately degrades instead of failing, `doctor` SHALL report the condition as a warning (not a failure) naming its consequence and remedy; in particular it SHALL test whether a directory symlink can be created, leave nothing behind, and warn that agent checkouts will lack linked dependency directories when it cannot.

WhyDegrading can be right; nobody being told is not. An agent finding missing dependencies by failing the suite is the cost.

FR-33# Requirement 17 of 17

SHALL Events persisted for the operator SHALL carry a severity from the set the operator's views style and filter by (`info`, `warn`, `error`, `debug`); the persistence layer SHALL normalise any other value to `warn` before writing, and a live broadcast of the same event SHALL carry the normalised value.

WhyA severity no view recognises renders unmarked and is hidden by the filter meant to reveal it.

Design

D1 Two halves, no shared code. The CLI's `agentweave/diagnostics.py` checks the machine and the instance; the Hub's `launchability.py` and runner adapters judge agents. The Hub does not import the CLI package, so the two are kept separate on purpose.

D2 The instance describes itself. `/health` returns `runtime` (`native`, `docker`, or `AW_RUNTIME`) and the UI staleness verdict; `status` and `doctor` read that rather than inferring from a PID file.

D3 Collaboration readiness comes from the same adapter member the trigger path uses to pick a transport, so what the operator is told and what actually runs cannot drift.

D4 Exit codes: recorded raw (`Run.exit_code`), rendered readably wherever a payload is composed for display (`readable_exit_code`, applied in `_broadcast_run_lifecycle`).

D5 UI staleness is an assertion (`hub/hub/static/ui/ui-build-stamp.json` with a source fingerprint), not a proof; with no stamp the old commit-date comparison applies, so no installation is declared current by default.
