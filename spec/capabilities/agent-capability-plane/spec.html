26 MUST·26 requirements·71 criteria

Summary

The least-privilege, run-authenticated HTTP contract (`/api/v1/agent-actions`) through which an agent causes effects and makes scoped reads: messages, the task ledger, operator questions and their answers, checkpoints and recall, governed agent requests and scheduled work, and specification and evidence writes. It fixes how a run is authenticated and attributed, which rules the contract itself enforces so that no adapter or hook can hold them, and what a run is told about the access path it actually has. The adapters that expose it are agent-tool-surface.

Problem

An agent that can name its own identity, set fields that are the operator's, or reach a rule only through one adapter is not governed. The plane makes every agent effect attributable to a live run and governed identically however the agent connected.

Scope

In scope

  • Run credential authentication, actor derivation, and scrubbing a run's registered secrets from agent-action writes.
  • The set of agent operations, task-ledger paging, and the refusals the contract states (messages to the operator, to oneself, to an archived agent or conversation; checkpoints and recall the agent is not granted).
  • Attribution of every agent-caused effect, and a task named on a delegation as runtime state.
  • Rules that must hold for every access path: operator direction for archiving jobs, project-setting refusals, blocked status, task field ownership, and no rule held only in a hook.
  • Operator questions: batches, declines, and delivering an answer to an asker whose run or wait has ended.
  • What a run is told about its access path, and the record of whether its harness started the tool server.

Non-goals

  • The MCP tool schemas, the `aw-tool` command, its notice and how it carries the run's authority: agent-tool-surface.
  • Which tool surface, approval channel and plane access a run is given: runner-registry.
  • Per-agent limits on how long a run waits for the operator: agent-configuration.
  • Operator-facing severity values: runtime-diagnostics.
  • Reading specification documents: spec-document-authority; creating them: agent-document-creation.
  • Requirement wording on tasks and recording or deciding evidence: requirement-traceability.
  • Permission postures and path judging of a run's own tools: agent-run-sandboxing.
  • Task transition legality: task-lifecycle-governance.

Requirements

FR-22# Requirement 1 of 26

MUST The system SHALL mint an unguessable credential for each Hub-owned run, store only a non-reversible digest of it, and accept it only while that exact run is running and, where the run records the Hub instance that issued it, only by that instance. Authentication SHALL derive the project, agent and run from the matched run row. The credential MUST NOT appear in output, events, turn text, command arguments or API responses.

WhyA credential that outlives its run, or that a second Hub sharing the database could honour, lets an ended or foreign run cause effects nobody can attribute to live work.

FR-23# Requirement 2 of 26

MUST The agent application API SHALL expose only: peer messaging; the shared task ledger (create, paged list, read, update, transition history, integration outcome and retry); operator questions (single, batch, reading one's own question, reporting a wait that ended); checkpoint notes, and reading checkpoints and recalled observations the agent is granted; governed agent requests; governed scheduled work (create, toggle, run, archive, delete); specification documents (create, rename, submit, read); requirement evidence (record, list, decide); and the runtime's own permission-request, permission-decision and adapter-online reports. It MUST NOT expose any agent's inbound queue, the roster, project settings, agent configuration, charters, credentials, or other operator capabilities.

WhyTurn-start state is injected by the Hub, so a read is offered only where the agent needs it for its own work and is scoped to its project; everything that governs the agent stays the operator's.

FR-24# Requirement 3 of 26

MUST Agent-action request bodies SHALL carry no project, agent, sender, assigner, requester or run identity field, SHALL reject unknown fields, and every service they call SHALL use only the authenticated actor. Caller headers or extra body fields MUST NOT change attribution.

WhyAn agent able to name its own identity could cause an effect attributed to another agent, which defeats every review and attribution rule built on top.

FR-25# Requirement 4 of 26

MUST Every message, task creation and transition, question, scheduled-work mutation, agent request, specification write and evidence record caused through the agent API SHALL durably identify the responsible agent and run in its own row, not only in an event log. Task status attribution SHALL be an append-only record of every accepted transition, each naming its own run. Operator effects MAY carry no run.

WhyApproval is a judgement about work a different run performed; a single mutable 'last updated by' field cannot say whether author and reviewer differ.

FR-26# Requirement 5 of 26

MUST Direct HTTP SHALL be the application contract. The MCP server and the call command SHALL be one adapter program over that contract, offering the same operations with the same validation, governance, attribution and failure meaning. An adapter MUST NOT hold a governance or waiting rule the contract does not impose on every caller, MUST NOT duplicate queue, budget, identity or lifecycle rules, and MUST NOT turn a failure into an empty or successful result. Any deadline the contract enforces on a caller SHALL be disclosed to that caller.

WhySome deployments forbid MCP servers but allow ordinary commands; if a rule lives in one adapter, which rules bind an agent depends on how it connected.

FR-28# Requirement 6 of 26

SHALL The system SHALL tell a run it has the MCP tools only when the operator declared `hub_client: mcp` or the agent's most recent tested run recorded the harness connected, and SHALL otherwise describe the call command, in both the turn notice and the canonical context, from one decision. A run that tested itself before its first prompt and found the server absent SHALL be told the call command whatever the operator declared. What a run is told SHALL NOT change what it is given or its containment.

WhyBeing given an MCP configuration is not the same as a harness offering it; telling a run tools it lacks, or denying tools it holds, both send it down a path that fails.

FR-30# Requirement 7 of 26

SHALL The question operation SHALL accept one to four questions in one call, each with a header, two to eight options and a multi-select flag, and a blocking call SHALL wait until every question is answered or declined or the shared deadline passes. Where the asking run is no longer waiting, the answers SHALL reach the agent as one queued delivery per batch, only once every question is answered or declined, in asked order, each marked answered or declined, including any answer recorded during the wait but never received; a batch with no answers delivers nothing. Each answer SHALL be persisted and SHALL release any task it parked when it is given.

WhyAsking together is one interruption and one wait; delivering answers one at a time would have the agent act on part of a decision while the operator is still making the rest.

FR-31# Requirement 8 of 26

SHALL The operator SHALL be shown one question of a batch at a time with a step counter (`step/total`), advanced to the next once the current one is answered, and, where nobody is waiting on the batch, told that the answers reach the agent together once all are finished.

WhyShowing a batch at once turns a conversation into a form; without the 'together' note a part-answered batch looks like answers were discarded.

FR-34# Requirement 9 of 26

SHALL An agent's message naming an archived conversation of the recipient SHALL be refused 409 with a detail stating that the conversation is archived, that the agent should send to a new conversation by omitting `conversation_id`, and the submitted content verbatim. No message or queue entry SHALL be created, and the message SHALL NOT be redirected to another conversation.

WhyReturning the content makes the retry mechanical for an agent that has moved past its own context; redirecting would decide for it where its message goes.

FR-35# Requirement 10 of 26

SHALL Every rule the system enforces on agent behaviour SHALL be enforced at a boundary the Hub owns (the agent API, the run boundary, or the data model), independently of any runner hook; the Hub SHALL install no runner hook that decides a call, and SHALL remove hooks it did not write from homes it manages.

WhyHooks are per-machine, uneven across runners and absent from some; a rule living only in one would be missing wherever the hook is.

FR-36# Requirement 11 of 26

SHALL When an agent sends a message naming a task, the system SHALL validate the task against the sending run's project at the time of the call and SHALL bind the run that does the delegated work to that task; the binding's attribution SHALL derive from the authenticated run.

WhyA task carried only as a field on a message cannot govern the run that does the work, and a caller must not be able to assert on whose behalf a binding is made.

FR-37# Requirement 12 of 26

SHALL No agent-facing operation SHALL move a task into or out of `blocked`. That status SHALL be reached only when the system observes a blocking question unanswered, or by the operator.

WhyA state the subject can assert does not constrain it, and `blocked` is the status an agent under a completion gate most wants, because it excuses unfinished work.

FR-38# Requirement 13 of 26

SHALL The system SHALL let the operator close an outstanding question without answering it and SHALL record that they did. No agent-facing operation SHALL decline a question, and an answered question SHALL NOT be declinable.

WhyAn agent able to close its own question could clear the record of having asked without anyone deciding anything.

FR-39# Requirement 14 of 26

SHALL Where an agent is waiting on a question, the system SHALL end that wait when the question is declined and SHALL report the decline distinctly from an answer and from an expiry, without requiring any particular response to it.

WhyAn expiry means nobody was there; a decline means someone was and handed the decision back, which the agent can act on immediately.

FR-45# Requirement 15 of 26

SHALL Where the Hub refuses an agent capability because of project state the agent cannot change (today: `allow_agent_jobs` off), it SHALL open a question of record on the operator's Questions destination that names the setting, its value, what enabling it allows and where it is changed; the record SHALL carry no run or conversation, SHALL NOT make any run, conversation or loop read as waiting, and its answer SHALL be queued to the refused agent and wake it even after the run ended. After the latest record for that state is resolved the Hub SHALL open at most one further record, stating it is the last, and none after that, counting records rather than reading answers. If the record cannot be opened the refusal SHALL still be returned without claiming the operator was asked. The call SHALL NOT wait and the rule SHALL live in the contract, not an adapter.

WhyA refusal that exists only in the agent's transcript reaches nobody; a record bound to the refused run would be swept with it.

FR-46# Requirement 16 of 26

SHALL A refusal caused by project state SHALL carry the code `project_setting_blocks_capability`, name the setting and its current value, include the record's id in the sentence itself where one was opened and say plainly where none was, state what the caller may do instead and that the operator's answer arrives as input rather than as this call's result, and SHALL NOT describe an approval or allowance the system has not opened.

WhyOnly the sentence reaches the refused agent's turn, and a sentence promising an approval nobody was asked for sends the operator looking for something that does not exist.

FR-47# Requirement 17 of 26

SHALL A message an agent addresses to a reserved operator name SHALL be refused 404 with a reason stating the operator is not a message recipient, that the agent's reply is what the operator reads, that a result is recorded on a task's notes, and that a question needing an answer goes through `ask_user`. The system SHALL NOT read an agent's text to decide it was addressed to the operator.

WhyNo agent can hold the reserved names, so such a message is never a mistyped peer; 'no agent by that name' leaves the agent guessing.

FR-48# Requirement 18 of 26

SHALL An agent's task update SHALL accept only status, notes and requirement links (`requirement_ids`, `spec_document`), and SHALL refuse, before anything is persisted and whichever access path is used, any of assignee, priority, description, title, loop, divergence policy, escalation agent or check override, with a reason saying an agent moves its task with status and notes and links requirements, and that the other fields are the operator's. An agent SHALL be able to link requirements without restating status.

WhyWho holds a task, its priority and its description are the operator's statements about the work; an agent able to set the holder could take another's work or name itself on finished work.

FR-50# Requirement 19 of 26

SHALL For every run given the MCP server the system SHALL record whether its harness started it as `connected`, `failed` or `absent`, with the harness's own recognised report deciding over the adapter's online report, and that over a pre-prompt wait that ended without it, whatever order they arrive in; a run with no report stays untested. The call command SHALL never produce the online report, and recording SHALL never fail the run.

WhyThe adapter reports online when its process starts, before the harness connects, so it proves the program started, not that the tools are offered; and this record is the grounds for what the next run is told.

FR-52# Requirement 20 of 26

SHALL Before any agent-action route parses a write, the Hub SHALL replace, in the request body, every secret registered for the calling run (such as a provider key placed in its environment), so that no agent-action write stores it.

WhyAn agent that reads a key in its environment and passes it to any tool would otherwise store it in the database and send it to the app; one middleware covers every route, including ones added later.

FR-53# Requirement 21 of 26

SHALL Archiving scheduled work through the agent API SHALL require the operator's direction for that job every time, regardless of the run's permission posture or the `allow_agent_jobs` setting: the route SHALL refuse 409 with code `operator_direction_required` and a permission request id until the operator allows that request, and SHALL refuse outright a job that has a loop.

WhyThe standing allowance grants the capability to manage scheduled work, not direction to retire this job now; a loop is retired only by the operator.

FR-54# Requirement 22 of 26

SHALL A message an agent addresses to itself without naming one of its other conversations SHALL be refused before any message, queue entry or turn exists, with a reason naming where the operator reads its reply; a message to one of its own other conversations by id SHALL be accepted.

WhyAn agent asked to 'message me' reaches for the nearest name, its own, and would otherwise spend a model turn acknowledging itself.

FR-55# Requirement 23 of 26

SHALL A message to an archived agent SHALL be refused 409 with a detail that names the agent as archived, says how to proceed, and restates the submitted content; nothing SHALL be queued for it.

WhyAn archived agent never runs, so a queued entry would wait forever while the sender believed it delivered.

FR-56# Requirement 24 of 26

SHALL Reading a checkpoint or recalling an observation the agent is not granted SHALL answer 404, indistinguishable from an id that does not exist, and a filter argument SHALL only narrow what the agent may read.

WhyA refusal distinguishable from absence discloses that the record exists.

FR-57# Requirement 25 of 26

SHALL Listing the task ledger SHALL return a page (100 by default, at most 1000, oldest first) with the total and whether more remain.

WhyA real board in one result spills past a tool result's size, and an agent not told more remain believes it has seen the newest work.

FR-58# Requirement 26 of 26

SHALL Where a blocking question is answered after the asking run has ended, or after that run's wait for it has ended, the system SHALL deliver the answer as queued input; where the asking run is still waiting it SHALL NOT also queue it, and where it cannot establish that the wait ended it SHALL assume the asker is still waiting.

WhyAn answer that reaches no one leaves the operator believing work is unblocked. The decision is taken after the answer or the wait's end is recorded and against recorded state, so an answer racing an expiry report is delivered at least once; a duplicate costs a turn, a lost answer costs the operator's decision. A question declined before its wait's end is recorded is not marked as gone ahead without an answer. The operator's view says nobody is waiting from the moment the wait ends.

Design

D1 One namespace. Every agent operation is under `/api/v1/agent-actions` (hub/hub/api/v1/agent_actions.py), the only routes that accept an `aw_run_` credential (hub/hub/agent_auth.py). Identity is the matched Run row; request models forbid extra fields.

D2 HTTP is the contract. Every operation and its refusals are defined by its agent-actions route; the adapters (agent-tool-surface) add no rule of their own, so a rule holds identically on every access path.

D3 Waiting is a poll over contract routes. `ask_user` and `archive_job` poll `/questions/{id}` and `/permission-requests/{id}`; the deadline is stamped by the Hub and returned (`wait_expires_at`), and `/questions/wait-ended` is a report the Hub checks against its own deadline. Holding a request open was rejected because it pins a pooled connection for minutes.

D4 Rules that need a person live in the route: archive direction (hub/hub/operator_direction.py) and project-setting refusals (hub/hub/refused_capability.py). A setting refusal opens a question of record with no run or conversation, at most two per setting.

D5 What a run is told is decided apart from what it is given. `described_access_path` (hub/hub/launchability.py) reads the operator's declaration or the latest tested run's `harness_mcp_status`, never the access axes the run is given (runner-registry), so honesty fixes cannot move containment.

D6 Secrets are scrubbed once, in middleware over the agent-actions prefix (hub/hub/agent_action_scrub.py), not per route.
