Summary

A checkpoint is the Hub's durable record of where a conversation got to: an envelope the Hub computes from its own records plus a written body only a model can supply, generated out of band by a worker on the operator's chosen runner, verified by a blind probe, and readable by other agents only under explicit grants. Checkpoints are taken on the operator's request, at a context threshold, or when the runner compacts.

Problem

An agent asked to write its own checkpoint file produced it in unreachable places or not at all, and was reported ready because readiness meant the run had ended. Conversations then continued on a runner's own compaction that nobody authored or could inspect.

Scope

In scope

  • The checkpoint record, its computed envelope (files, tasks, open questions, decisions, overrides, covered turns, lineage) and its generated body
  • Worker invocations used for generation and verification, including the Copilot worker's tool exclusion
  • Agent notes as input to generation, and their caps
  • Verification by blind probe and checkpoint status
  • Read and recall grants, citations, listing and recall
  • Checkpoint mode and threshold policy, warnings, dismissal, the final warning, on-demand checkpoints, and runner compaction as a trigger

Non-goals

  • Cutting over to a successor conversation and delivering the checkpoint into it: agent-conversation-handoff
  • A flow's checkpoint lineage shared across the agents it fires, and which checkpoint briefs a firing or reviewer: agent-flows
  • How a settings save applies a partial body: project-environment-settings
  • Measuring context usage itself: agent-context-usage

Requirements

FR-13# Requirement 1 of 22

SHALL The Hub SHALL persist each checkpoint as a durable record attached to the conversation it describes, and SHALL NOT depend on an agent writing a file, invoking a skill, or having any template or directory installed in the project.

WhyAn agent asked to write a checkpoint file produced it in unreachable places or not at all, and was still reported ready. A record the Hub writes itself cannot be refused by a sandbox or lost in a nested workspace.

FR-14# Requirement 2 of 22

SHALL Checkpoint generation SHALL run as an out-of-band worker invocation on the runner and model the operator chose for the project, using a prompt the Hub owns and versions; a worker invocation SHALL NOT be an agent turn, SHALL record its outcome, and SHALL NOT raise into its caller.

WhyGeneration must not need the agent's cooperation or occupy its turn, and a cheap model can summarise work done on an expensive one. A worker is not a Run, so it never makes the agent look busy to the scheduler. Failures are recorded by outcome because a timeout, a missing CLI and a prose answer need different fixes.

FR-15# Requirement 3 of 22

SHALL A checkpoint's identity, lineage, covered turns, changed files, tasks, open questions, permission decisions and runtime overrides SHALL be computed by the Hub, and the generating model SHALL be asked only for judgement: objective, current state, decisions with rejected alternatives, dead ends with symptoms, ordered next actions, and risks.

WhyWhat the Hub can check it must not delegate: a model asked for a timestamp invented one, and one asked for pending work reported none from an always-clean worktree. Changed files are read from the project repository the Hub resolves itself, because task checkouts are removed when tasks finish while their commits stay readable from the repository, and a repository supplied by a caller was omitted by every caller.

FR-16# Requirement 4 of 22

SHALL Generation SHALL read the conversation's latest written checkpoint and only the turns since it, and SHALL NOT re-read the whole conversation from its start.

WhyRegenerating from scratch loses information gradually and pays full price each time. An unwritten checkpoint has no body to carry forward, so it is skipped as an anchor and the next checkpoint covers its span too.

FR-17# Requirement 5 of 22

SHALL The Hub SHALL ask the agent for brief notes through a tool call at a configured notes point below the checkpoint threshold, SHALL treat those notes as one input to generation, and SHALL produce the checkpoint whether or not notes arrive.

WhyThe record cannot hold what the agent was about to do, suspects, or would warn a successor about. Asking through a tool makes the request, the answer and its absence observable. Asking earlier than the threshold keeps the notes from being written from an exhausted context.

FR-18# Requirement 6 of 22

SHALL The Hub SHALL verify a written checkpoint by having a reader given only the rendered checkpoint name its changed files, tasks and unanswered questions, SHALL compare those answers with its own records, and SHALL mark a checkpoint whose answers disagree as failed; ready SHALL mean a written checkpoint exists and did not fail verification.

WhyReadiness used to mean a run had ended, so a run that produced nothing was reported ready. The dimensions summaries lose most are exactly the ones the Hub can settle without a judge. A probe that cannot run is the Hub's failure, not the checkpoint's, so it leaves the checkpoint ready.

FR-19# Requirement 7 of 22

SHALL A checkpoint SHALL cite the recorded outputs of the turns it covers by stable id with a short preview, and the Hub SHALL return a cited output verbatim to a permitted reader.

WhyA summary is lossy. Citing outputs that are already retained verbatim gives an exact escape hatch without re-running tools or similarity search. Citation is also what scopes recall to the conversation a checkpoint describes.

FR-20# Requirement 8 of 22

SHALL The Hub SHALL hold permission to read other agents' checkpoints and permission to recall their cited observations as two independent grants on the agent record, both off by default, resolved from the identity bound to the running turn; an agent SHALL always be able to read and recall its own checkpoints.

WhyA checkpoint is a bounded distillation; a recorded observation is raw tool output that may contain another workspace's files or secrets. Grants are structured configuration, never charter prose, so editing a paragraph cannot widen access. The read grant reaches every checkpoint in the project because no checkpoint can restrict itself.

FR-21# Requirement 9 of 22

SHALL The Hub SHALL record on each checkpoint its predecessor and a lineage identifier shared along its conversation's chain, and SHALL NOT store cross-agent participation separately from existing run attribution.

WhyLineage is a linear chain within one conversation; participation is cross-agent and already answerable from the runs recorded on task mutations. Storing participation would be a second graph to keep correct, and sharing one identifier for both would make it mean two things.

FR-22# Requirement 10 of 22

SHALL The Hub SHALL let the operator set a checkpoint mode (off, offered or automatic) and a threshold given as one mode (percent or tokens) with one value, resolved agent then project then built-in default, where an agent's threshold replaces the project's mode and value together.

WhyContext windows differ by an order of magnitude, so an absolute count is often the meaningful unit, and it still works for a model whose window is unknown. Combining an inherited mode with an overriding value would produce a threshold nobody configured, such as 150%.

FR-23# Requirement 11 of 22

SHALL The Hub SHALL make every checkpoint of a conversation readable through the API with its status, probe verdict and generation error, and SHALL tell the operator in that conversation the outcome of a checkpoint they took or were offered, naming a failed or unwritten one rather than omitting it.

WhyA checkpoint nobody can inspect reproduces the defect this capability removes: a signal reported as successful that nothing examines.

FR-24# Requirement 12 of 22

SHALL When a conversation crosses its threshold under offered mode, the Hub SHALL mark it due and broadcast a warning without generating anything; under automatic mode it SHALL generate a checkpoint and hand the conversation over without asking.

WhyGeneration is a billed model call, and an operator who would rather keep working should not pay for a summary they discard. Automatic means acting alone. The warning hands over the decision while the context it would be written from still exists, so taking it generates immediately rather than later.

FR-26# Requirement 13 of 22

SHALL Where a checkpoint lists a conversation's open questions, a question whose bounded wait ended without an answer SHALL still be listed, and SHALL be marked as one whose wait ended rather than as one still awaiting a reply, both in the record and in the rendered checkpoint a successor receives.

WhyThe successor needs to know a decision was taken without the operator, and that no answer is coming; dropping the question loses that, and listing it unmarked makes the successor wait for or defer to an answer that will not arrive.

FR-27# Requirement 14 of 22

SHALL A worker or conversation-title invocation on a copilot runner SHALL exclude every built-in, MCP and custom tool and SHALL NOT pass an empty tool allow-list; it SHALL spawn the Copilot CLI's native executable under a Copilot home the Hub owns, with no GitHub token variable the Hub merely inherited.

WhyA worker's prompt is transcript text the Hub did not write, so an injection in it must find nothing to act with. Copilot's non-interactive mode pre-approves every available tool, and it reads an empty allow-list as no filter at all.

FR-28# Requirement 15 of 22

SHALL The Hub SHALL derive the built-in threshold, notes point and final warning from the compaction point C of the runner the agent is bound to, as C-15, C-25 and C-3 percent (C defaults to 95), and SHALL lower any configured percent threshold above C-3 to C-3 for that agent, stating the lowering in the agent's and project's settings.

WhyEach threshold exists to act before the runner compacts on its own, so it must move with the runner: Claude and Codex compact near 95% (80/70/92), Copilot near 80% (65/55/77). Lowering rather than refusing is required because one project threshold serves agents on runners that compact at different points.

FR-29# Requirement 16 of 22

SHALL Where a runner reports that it compacted a conversation's root context successfully, the Hub SHALL act on that conversation as though it had crossed its threshold, under every other gate it already has, without requesting notes.

WhyThe threshold exists so the Hub acts before the runner compacts; once it has, there is no reason to wait. Notes written after compaction come from the runner's summary, which the checkpoint exists to replace. A dismissed conversation's final warning exists to precede the loss, so after the loss the stream's compaction card is the notice.

FR-30# Requirement 17 of 22

SHALL The operator SHALL be able to take a checkpoint of a conversation on demand; the Hub SHALL refuse with 409 when the project has no checkpoint runner configured or a checkpoint of that conversation is already being written, and taking one SHALL clear any due, final or dismissed warning on the conversation.

WhyFalling back to another agent's runner would be a bill nobody agreed to, and two concurrent generations for one conversation waste a call. Once a checkpoint exists the warning has been answered, so the next crossing must be offered afresh.

FR-31# Requirement 18 of 22

SHALL The operator SHALL be able to dismiss a due checkpoint warning; a dismissed conversation SHALL NOT be warned again until its proportion of context in use reaches the final-warning point, when it SHALL be warned once more with a warning that cannot be dismissed.

WhyDismissal means 'not yet', not 'never': without the final warning, the runner's own compaction would replace the conversation with a summary nobody authored. The final warning needs a known proportion, because inventing a denominator would report a proportion the conversation does not have.

FR-32# Requirement 19 of 22

SHALL A conversation that has already been handed over and was reopened SHALL NOT be asked for notes, warned that a checkpoint is due, or have a checkpoint generated by the threshold, under either mode; it SHALL still receive the final warning if its warning was dismissed.

WhyA conversation is handed over at most once, so any notes request, warning or generation toward a second handover spends a turn or a model call on something that cannot happen. The final warning is free.

FR-33# Requirement 20 of 22

SHALL The Hub SHALL accept agent notes only from a run attached to a conversation and only within fixed caps (intent at most 1500 characters; suspicions and warnings each at most 8 entries of at most 400 characters), naming the entry and its overshoot when refusing, and a checkpoint SHALL take only the newest unconsumed notes and retire the older ones with it.

WhyNotes are one input to a record the Hub is authoritative for; an uncapped essay would be writing the checkpoint by the back door. Notes describe a moment, so once a checkpoint covers that moment they must not resurface in a later one, even when generation failed.

FR-34# Requirement 21 of 22

SHALL Agents SHALL be able to list the written checkpoints they may read, newest first, and open one by id; a checkpoint or observation outside a reader's grants SHALL be answered not-found, indistinguishably from one that does not exist.

WhyA grant nobody can spend is no grant, so readable checkpoints must be discoverable. A refusal that differs from absence would itself disclose that the record exists.

FR-35# Requirement 22 of 22

SHALL A worker invocation SHALL run in a temporary directory outside the project, with no project tool server, and offered no tools its runner can withhold: Claude with an empty tool set and strict MCP config, Codex in a read-only sandbox.

WhyThe worker reads transcript text the Hub did not write; anything it can act with is a tool a prompt injection could use.

Design

D1 Envelope computed, body generated. Everything the Hub can verify is read from the database and git; the model writes only judgement (objective, state, decisions, dead ends, next actions, risks). A body-less checkpoint is stored as unwritten, never ready (database constraint).

D2 Changed files from the project repository. The Hub resolves the project's repository itself and reads each covered run's snapshot commit there, because linked task checkouts share its object store and may already be removed.

D3 Anchoring. Generation reads the latest written checkpoint plus the turns since its covered boundary; a span with no new turns keeps the previous boundary.

D4 Verification by blind probe. A second worker call reads the rendered checkpoint and names files, tasks and unanswered questions; a deterministic grader compares them with the envelope. Disagreement marks the checkpoint failed; an unrunnable probe leaves it ready.

D5 Workers are not turns. One-shot CLI spawns in a temporary directory, no tools, no Run row, stdin closed, outcome and usage recorded in worker_invocations, at most two concurrently, never raising.

D6 Policy. Mode off/offered/automatic; threshold is one mode plus one value; agent overrides the project's threshold whole. Built-in points derive from the bound runner's compaction point C (threshold C-15, notes C-25, final warning C-3); percent thresholds above C-3 are lowered, token thresholds also fire on proportion only for runners with C below 95.

D7 Warn before spending. Offered mode marks the conversation due (checkpoint_warning column: null, due, dismissed, final) and generates only when the operator asks; automatic generates and hands over. Generation is dispatched off the output-recording path, one consideration per conversation at a time, with a compaction that arrives mid-consideration queued behind it.

D8 Access. Two grants on the agent row (can_read_checkpoints, can_recall), off by default; an agent always reads and recalls its own. Out-of-reach ids answer 404 like unknown ones.
