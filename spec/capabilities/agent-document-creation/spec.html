Agent document creation

capabilitycurrentsketch

7 MUST·7 requirements·16 criteria

Summary

An agent may start its own specification document — a change specification or a roadmap — through `create_spec_document`, without asking the operator first. The Hub chooses where the document lands, the document starts in `exploring` like any operator-created one, and creating it gives the agent no say over its lifecycle.

Problem

An agent that reaches something worth writing up — a finding, a proposal, a design — should record it and keep working. If only the operator could create documents, every such moment became a stop. Letting an agent create documents must not, however, let the least trusted caller choose where a write lands, create a document it can never fill, or gate its own work.

Scope

In scope

  • The agent creation route `POST /agent-actions/spec/documents/create` and its MCP tool `create_spec_document`
  • Which kinds an agent may create, and where the created document lands
  • The refusal an agent sees when it submits against a path with no document

Non-goals

  • Renaming a document and the path a subject yields (spec-document-authority)
  • What a submission validates and stores, and the operator-only phase transitions (spec-document-authority)
  • Roadmap and slice semantics (spec-roadmaps)
  • When a spec-chat turn should write into the operator's open document instead of creating one (spec-chat-session)

Requirements

FR-1# Requirement 1 of 7

SHALL The Hub SHALL let an agent create a specification document through `create_spec_document` (`POST /agent-actions/spec/documents/create`); the document SHALL start in the `exploring` phase, SHALL be attributed to the calling agent and run taken from the run credential, and SHALL be immediately writable by that agent through `submit_spec_document`.

WhyAn agent that needs a document should record its finding and keep working rather than stop for the operator. A document an agent created is an ordinary document: same phase, same lifecycle, listed for the operator like any other. Identity comes from the credential because a request body is caller-controlled.

FR-2# Requirement 2 of 7

SHALL The creation operation SHALL NOT accept a path, filename or slug; the Hub SHALL mint a meaningless placeholder path that is free against both the project's recorded documents and the files in the specification directory, and SHALL ignore (not refuse) any path or identity field a caller sends anyway.

WhyPath validation is the single control keeping a document from being written anywhere beneath `spec/`. A minted path makes a wrong destination unexpressible rather than merely refused, and minting against the disk as well as the records guarantees creation never overwrites an existing file. Stray fields are ignored rather than refused so they cost the caller nothing and gain it nothing.

FR-3# Requirement 3 of 7

SHALL The creation operation SHALL create a `change-spec` document by default or a `roadmap` when the agent asks for one, and SHALL refuse every other kind with a 422 (`kind_not_creatable`) whose message names the two kinds an agent may create.

WhyA capability document is created directly in `current` and agents may never write one, so allowing an agent to create it would produce a document that can never be filled in — success that yields an unusable artefact. Change specifications and roadmaps are the kinds whose lifecycle is authored by an agent and gated by the operator. A refusal that names what is allowed tells the agent what to do next.

FR-4# Requirement 4 of 7

SHALL An agent that created a document SHALL have no capability over it beyond what any agent has over any document; in particular it SHALL NOT be able to propose, approve, transition or archive it.

WhyAuthorship is not authority. An agent that could approve what it wrote would be the only party in its own gate. The agent surface offers no transition route, and the operator's transition routes refuse a run credential.

FR-5# Requirement 5 of 7

SHALL When an agent submits a payload for a path with no document, the Hub SHALL refuse it with a 404 whose message tells the agent to call `create_spec_document` (then `rename_spec_document`), and SHALL NOT say that only the operator may create documents.

WhyThe refusal is where a confused agent looks next. Naming the remedy the agent actually has keeps it working; naming a rule that no longer exists would have the product contradict its own tool descriptions.

FR-6# Requirement 6 of 7

SHALL Document creation by an agent SHALL NOT depend on the project's agent-jobs allowance (`allow_agent_jobs`).

WhyThat allowance gates scheduled jobs an agent may create. Reusing it here would silently stop agents from recording findings in every project that has not opted into agent jobs.

FR-7# Requirement 7 of 7

SHALL When the Hub cannot mint a free placeholder name, or cannot resolve the project's workspace, the creation operation SHALL refuse with a 409 and create nothing.

WhyMinting is bounded so a full namespace yields a refusal rather than a hang, and a document whose file cannot be written must not be recorded.

Design

D1 — One minting rule. The agent route and the operator's `POST /project/documents` share `spec_service.mint_document_path`, so there is exactly one definition of a free path (free in the records and on disk).

D2 — The path arrives second. Creation returns a meaningless placeholder (a colour and a mythic animal); the agent calls `rename_spec_document(path, subject)` once it knows the subject, and the Hub derives the real path. Renaming is specified in spec-document-authority.

D3 — Lax body by design. `SpecDocumentCreate` deliberately does not inherit the strict `RequestModel` (it is the one entry in `LAX_BY_DESIGN`, hub/tests/test_request_strictness.py): stray `path`, `actor`, `agent` or `run_id` fields are ignored, which keeps placement and identity unexpressible without making a forward-compatible client fail.

D4 — Creation writes through the normal save path. The route records the document, then saves a minimal payload (`schema_version`, `kind`, `title`) through `spec_service.save_document`, so the file exists and is rendered the same way as any later submission.
