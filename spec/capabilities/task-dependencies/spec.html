Task dependencies

capabilitycurrentsketch

13 MUST·13 requirements·52 criteria

Summary

Tasks can depend on other tasks. A dependency is declared by a specification document (by task key, including imported tasks of other approved documents) or by the operator, and is written through one writer that refuses cycles. A task may not start until every prerequisite is approved; started work is flagged, never halted, when a prerequisite regresses; and a task's isolated checkout carries its prerequisites' work.

Problem

A decomposition without order makes every task look ready at once, leaving the operator to hold the real order in their head and agents to discover it by collision.

Scope

In scope

  • declaring dependencies in a document (local keys and imports) and through the operator's task routes
  • the start gate in the task transition service and its refusal
  • dependency fields on task reads
  • bringing prerequisite work into a task's isolated checkout

Non-goals

  • the board that draws the graph (task-dependency-board)
  • which tasks a loop or flow claims (agent-loops, agent-flows)
  • review staffing beyond the reviewer hint (agent-flows)

Requirements

FR-1# Requirement 1 of 13

SHALL A specification document's task entries SHALL be able to name, in `depends_on`, other task entries of the same document by their task key; when the document is approved, each such reference SHALL become a dependency edge between the materialised tasks.

WhyA decomposition without order claims every piece of work can start at once, which is rarely true. Task keys are already stable, document-unique handles, so dependencies reuse them instead of a new identifier.

FR-2# Requirement 2 of 13

SHALL A task SHALL NOT move from pending or assigned to in_progress while any task it depends on is not approved; the refusal SHALL be a 409 with code `dependency_unmet` that lists every unmet prerequisite and, separately, every rejected one. Assigning, rejecting, and resuming a blocked task (blocked to in_progress) SHALL NOT be gated.

WhyA dependency is a precondition on starting work, not a property the task carries. Assigning ahead lets a whole wave be routed before it can start. A blocked task has already started (blocked is reachable only from in_progress), so refusing its resume could not prevent the work, only strand it; a prerequisite that changed after the start is surfaced instead (see the regression requirement). The gate lives inside the transition service so every caller is covered.

FR-3# Requirement 3 of 13

SHALL A dependency SHALL count as met only when the task depended upon has status approved.

WhyCompletion is the author's claim; approval is a second party's agreement. Advancing on completion would let each wave build on unreviewed work that may be sent back, and since approval is also where requirement coverage is judged, a chain cannot advance past unverified work.

FR-4# Requirement 4 of 13

SHALL Where a task depended upon is not approved while a dependent is in_progress or blocked, the dependent SHALL keep its status and SHALL read `dependency_state: running_on_regressed`.

WhyThe gate is a precondition evaluated when work starts, not an invariant maintained while it runs. Halting a running task over a change to a different task would take work away mid-turn; flagging it tells the operator without undoing anything.

FR-5# Requirement 5 of 13

SHALL Where a task depends on a rejected task, the Hub SHALL refuse to start it, SHALL report it as `gated_on_rejected` naming the rejected prerequisite, and SHALL NOT release, reject, or otherwise change the dependent on the operator's behalf.

WhyA rejected task will never reach approved on its own, so the remedy is a decision (reopen the work, or remove the dependency), not waiting. Propagating the rejection would cascade unseen through a decomposition; treating rejected as met would start work whose prerequisite was abandoned.

FR-6# Requirement 6 of 13

SHALL A document SHALL be able to declare an imported task entry (`from: {document, key}`) naming a task of another document, so that its local tasks can depend on it by a local key; approving the document SHALL resolve the import to the existing task without creating one, and an import that cannot be resolved SHALL be recorded as an unhonoured dependency rather than dropped or raised.

WhyDeclaring the foreign task as an entry keeps `depends_on` a list of local keys, makes the cross-document dependency visible in the document, and lets a per-document view lay itself out alone. An approval must never fail over the shape of a dependency, so an unresolved import is kept as evidence of what went wrong.

FR-7# Requirement 7 of 13

SHALL An imported entry SHALL name a document that is approved; an import naming a document in any other phase SHALL be reported as `import_not_approved`, blocking a proposal but not a submission.

WhyAn approved document's path is permanent and its tasks already exist, so the reference cannot dangle. Reporting rather than refusing at submission lets an author write down a dependency on work still being explored.

FR-10# Requirement 8 of 13

SHALL The operator SHALL be able to add (`POST /tasks/{id}/dependencies`) and remove (`DELETE /tasks/{id}/dependencies/{depends_on}`) a dependency between any two tasks of the project, including tasks that belong to no document; both this path and document approval SHALL write edges through one shared writer that refuses self-dependencies, missing tasks and cycles.

WhyWithout it the gate, the board and the dependency fields are reachable only if an agent authors ordering into an approved document. One writer means the graph cannot be built two different ways, and both paths gain the same cycle check.

FR-11# Requirement 9 of 13

SHALL When a task's isolated checkout is created, it SHALL be cut from the integration branch and then merge, for each direct prerequisite, the commit the system would integrate for it: a prerequisite's accepted-evidence commit at any status, or, for a prerequisite whose work needs no evidence, its branch tip only once approved. A conflict or a missing commit SHALL refuse the turn, name the prerequisite, and leave no checkout or branch behind.

WhyApproval's integration is best-effort, so approved work may never reach the main branch; the successor must build on it regardless. Accepted evidence is already a reviewer's acceptance, and a task branch is cut at dispatch before the gate fires, so restricting seeding to approved prerequisites would drop reviewed work the successor needs. A branch tip has no such acceptance until approval.

FR-12# Requirement 10 of 13

SHALL When a turn is bound to a task whose checkout already exists, the Hub SHALL first merge in the commit of each approved prerequisite the branch does not contain, without discarding anything; uncommitted changes, a conflict, or a merge that does not finish SHALL abort the merge, leave the branch and files as they were, and refuse the turn with a message naming the prerequisite, its commit, the checkout and the merge command.

WhyA checkout seeded only at creation keeps whatever prerequisites happened to be approved then, while every surface reports the dependency as satisfied. The existing branch holds the task's own work, so the catch-up must never destroy it.

FR-13# Requirement 11 of 13

SHALL Every task read (single task, list and board) SHALL carry `prerequisites` and `dependents` (id, title, status, owning document) and a `dependency_state` of `gated`, `gated_on_rejected`, `running_on_regressed` or null.

WhySurfaces render why a task will not start from the read model; without it a gated task looks like an ordinary pending one (F19).

FR-14# Requirement 12 of 13

SHALL Re-approving a document SHALL add any edge its task entries now declare, including on tasks already materialised, and SHALL NOT remove an edge an earlier approval created.

WhyThe document is where ordering is declared, so a revision that adds a dependency must be able to reach an existing task; removal is left to the operator route so that a re-approval never silently releases a gate.

FR-15# Requirement 13 of 13

SHALL Deleting a task SHALL delete every dependency edge naming it, in both directions, and its unhonoured references.

WhyAn edge to a task that no longer exists is a hole in the graph, not a fact worth keeping; removing it releases dependents rather than gating them on nothing.

Design

D1 Gate placement. The gate runs inside task_transition_service.apply_transition, before the history row, on pending/assigned -> in_progress only, so every caller (operator, agent HTTP, tools, loops, run binding) is covered. blocked -> in_progress is exempt because a blocked task has already started; scheduler.candidate_is_startable makes the same exemption so the loop and the gate agree. D2 Met at approved. Nothing earlier counts; rejected is reported separately because its remedy is a decision, not waiting. D3 Join table. Edges are rows in task_dependencies (unique per pair, indexed both ways), not a JSON list, so the gate and the board can query either direction. Unhonoured document declarations are kept in task_dependency_references with a reason. D4 One writer. task_dependency_writer.add_dependency is the only creator of edges; it reports (added/duplicate/self/missing/cycle) rather than deciding. The operator route maps refusals to 400/404/409; document approval records them as unhonoured references so an approval never fails over a dependency. D5 Checkout seeding. Creation merges what task_integration.merge_targets would integrate for each direct prerequisite (accepted evidence at any status; branch tip only when approved), all-or-nothing. An existing branch catches up approved prerequisites only, never destructively. Direct prerequisites suffice because each link carries its own prerequisites' work.
