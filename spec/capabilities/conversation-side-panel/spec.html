Conversation side panel

capabilitycurrentsketch

HomeConversations

15 MUST·15 requirements·39 criteria

Summary

One panel shell beside a conversation, showing one tab at a time: the specs, files and loops index tabs and the keyed detail tabs they open (a specification document, a workspace file, a loop). The operator controls the tab strip; tab configuration is remembered per project, the width is one global preference, and one resize/overlay rule applies whatever is shown.

Problem

Specification documents, workspace files and loops each need to be read beside the conversation without leaving it. Separate side surfaces with their own rules for opening, closing, width and narrow windows made the right-hand side unpredictable.

Scope

In scope

  • The panel shell, its tab strip, plus menu and empty-state launcher
  • Per-project tab persistence and its restore rules
  • The conversation/panel boundary, and the overlay below the combined minimum width
  • The files index tab, the file detail tab, and the workspace file content endpoint
  • Inserting a file mention into the composer from a file tab

Non-goals

  • What a specification document tab renders (spec-document-authority, spec-chat-session)
  • What the loops index and loop tabs show (agent-loops)
  • The workspace path listing endpoint itself (agent-composer)

Requirements

FR-1# Requirement 1 of 15

SHALL The conversation surface SHALL host at most one panel shell beside it, whose strip shows only the tabs currently open and whose body renders the content of exactly one of them. Every open tab SHALL be closable, closing the last one SHALL close the shell, and an open shell with no tab SHALL show a launcher card for every index tab it can open, each with a one-line description and, where the caller supplies one, a count of live items.

WhyOne surface with one set of rules; an empty shell that reads as a launcher, not a broken grey box.

FR-2# Requirement 2 of 15

SHALL The shell SHALL offer a plus menu listing only the index tabs (Specs, Files, Loops) that are not already open, and SHALL hide it once all are open. Opening a tab that is already open, from any entry point, SHALL make that tab visible rather than open a second one.

WhyOffering an already-open tab would read as "open another" when it cannot.

FR-3# Requirement 3 of 15

MUST Selecting an item from an index tab SHALL open a detail tab for that item and make it visible. Selecting an item whose detail tab is already open SHALL make that tab visible and re-reveal the item within it, and MUST NOT open a second tab for the same item.

WhyOpening the same thing again means "show it to me again", not "give me a copy".

FR-4# Requirement 4 of 15

SHALL A detail tab SHALL be keyed by an identifier that survives renaming wherever the item has one: a specification document by its Hub document id (falling back to its path only until the document inventory has loaded, then re-keyed in place without changing which tab is visible), a loop by its loop id, and a file by its workspace-relative path.

WhyDocuments can be renamed by agents; a path-keyed tab would dangle for a document that still exists.

FR-5# Requirement 5 of 15

SHALL Opening a file detail tab SHALL close the Files index tab in the same step. Opening a loop or a specification document from its index MUST NOT close that index.

WhyThe file tree is a launcher, and in a narrow column a tab spent on it once used is wasted; the loops and specs indexes are worth keeping in view.

FR-6# Requirement 6 of 15

MUST Which tabs are open, their order, which is visible and whether the shell is open SHALL be stored in this browser per project and restored when the operator returns to that project, and MUST NOT be shared between projects. The width of the conversation beside the shell SHALL be one value shared across every project and conversation.

WhyEach project has its own working set of documents and files; nothing suggests the operator wants a different width per project.

FR-7# Requirement 7 of 15

SHALL Persisted tab state SHALL carry a version and SHALL be migrated step by step on load when older, and discarded when newer or when no migration step exists. Unreadable or malformed state SHALL be ignored, and duplicate tab ids dropped. A file or document detail tab whose item no longer exists SHALL be dropped, but only once the listing of that kind has loaded. If restoring leaves no tab, the shell SHALL be restored closed; if the visible tab is gone while others survive, a survivor SHALL be made visible.

WhyPersisted tabs point at things that can stop existing; a misread configuration is worse than a lost one, and a listing that has not loaded must not be read as "nothing exists".

FR-8# Requirement 8 of 15

MUST The boundary between the conversation and the shell SHALL be draggable, bounded only by the conversation's minimum width and the visible tab kind's own minimum width. When the available width is below the conversation minimum plus the visible tab's minimum plus the divider, the shell SHALL open as an overlay drawer instead of a column; dismissing the overlay MUST NOT close the open tabs, and a control above the conversation SHALL reopen it.

WhyThe threshold is derived from the same per-kind minimum the column uses, so the layout and the switch to overlay cannot disagree; the chosen width is clamped, not overwritten, when the window narrows.

FR-9# Requirement 9 of 15

SHALL The Files index tab SHALL present the project's workspace path listing as a navigable tree marking the file currently open, SHALL switch to a ranked flat list of matches while a search is typed (Escape clears it), SHALL state an empty workspace or an empty search rather than show an empty box, and selecting a path SHALL open that file's detail tab.

WhyThe tree is for finding your way around; search is for when you know the name.

FR-10# Requirement 10 of 15

SHALL `GET /api/v1/projects/{project_id}/workspace/file?path=` SHALL serve content only for a path that is byte-for-byte a member of the workspace path listing for that project and whose resolved location lies inside the project's workspace root; any other path, including traversal, ignored files and symlinks pointing outside the workspace, SHALL be answered 404.

WhyMembership of the listing is the allowlist; the containment check exists only because git lists a symlink by its own path, not its target.

FR-11# Requirement 11 of 15

MUST A file up to the Hub's maximum body size SHALL be served in full; a larger file SHALL be refused with 413 and a message stating its size and the bound, checked before any content is read, and MUST NOT be served truncated.

WhyA silently truncated file is worse than a clear refusal.

FR-12# Requirement 12 of 15

SHALL The Hub SHALL classify a file as binary when a NUL byte appears in its first 8,000 bytes and SHALL then return no content; the file tab SHALL state that the file is binary and its size instead of rendering it. Text SHALL be decoded as UTF-8 with replacement and rendered with syntax highlighting, or as Markdown for Markdown files.

WhyGarbled bytes are never useful; an extensionless text file is still text.

FR-13# Requirement 13 of 15

SHALL A file detail tab SHALL offer "Insert into composer", which appends to the conversation's composer text exactly the mention the composer's own `@` trigger produces for that path, separated by a space from text already typed. The control SHALL NOT be offered for a path containing an `@` that is neither its first character nor directly after `/`.

WhyA mention inserted from either surface is indistinguishable, and an unsafe path would type a second live mention.

FR-14# Requirement 14 of 15

SHALL The tab strip SHALL follow the tablist pattern with automatic activation: only the visible tab is in the sequential focus order, Left/Right arrows move focus and activation between tabs with wrap-around, Home/End jump to the first and last tab, Enter or Space activates a focused tab, and each tab's close control and the plus menu are reachable and operable by keyboard. A newly visible tab SHALL be scrolled into view in the strip.

FR-15# Requirement 15 of 15

MUST Closing a specification document's tab, or opening a document from the Specs index, MUST NOT change which document the conversation has attached; attaching a document SHALL open or reveal its tab, and only the composer's stop-exploring control SHALL detach it (also closing the shell).

WhyTidying the reading pane is not an edit to what the agent is working on.

Design

D1. Tab kinds are a closed literal union in the UI (`specs`, `files`, `loops`, `spec:<id>`, `file:<path>`, `loop:<id>`); the kind is derived from the id, never stored beside it or built from external input.

D2. Index tabs launch keyed detail tabs; reopening an open tab bumps a reveal counter instead of duplicating it.

D3. The store persists `{version, projects}` in localStorage under one key, per project, with a migration chain; an unknown version is discarded rather than guessed at. Width is not in it: the conversation width preference is global.

D4. Reconciliation drops only `file:` and `spec:` tabs, and only for a kind whose listing has loaded. Index and loop tabs never dangle.

D5. The overlay threshold and the column's minimum both read `minWidthForTabKind`, so they cannot disagree.

D6. File content is allowlisted by membership of the path listing, plus `ProjectWorkspace.resolve_relative` to refuse symlink escapes; no second traversal check.

D7. Attaching a document and reading a document are separate: the attach drives the tab open, never the reverse.

Limits

  • `panelTabsStore.reconcile` is unit-tested but has no production caller (grep of hub/ui/src outside __tests__), so dangling file and document tabs are not dropped on load today; a missing file's tab shows the 404 sentence instead. The requirement is kept; see report.
