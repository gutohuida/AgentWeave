Summary

How a specification file that exists on disk without a Hub record becomes a tracked document, one at a time or for a whole corpus, read-only and with its identity taken from the file itself.

Problem

A specification document is a committed file plus a machine-local `spec_documents` row. A clone, a migration or a restored machine yields files with no rows, and every lifecycle, requirement, coverage and task operation is keyed on the row, so such a corpus is readable but inert.

Scope

In scope

  • Adopting one document (`POST /documents/adopt`) and a whole corpus (`POST /spec/adopt`), as an operator action
  • Reading title, kind and phase from the file, and the refusals when it cannot
  • Reporting disagreement between a file and an existing row
  • The baseline digest, the `adopted` event and the broadcast a successful adoption records
  • The Adopt and Adopt-all surface in the document browser

Non-goals

  • Updating an existing row from its file (an operator decision, not adoption)
  • Discovering documents and writing `spec/index.json` (spec-corpus-map)
  • Creating a new document through the Hub (spec-document-authority, agent-document-creation)

Requirements

FR-1# Requirement 1 of 11

SHALL The Hub SHALL create a `spec_documents` row for a specification file under `spec/` that has no row (`POST /documents/adopt`), taking the row's title and kind from the file's `aw-spec-payload` block and indexing the file's requirements against the new row, so that the adopted document is thereafter indistinguishable from one created through the Hub.

WhyThe file is committed and travels between machines; the row is machine-local. Every lifecycle, requirement, coverage and task operation is keyed on the row, so a file without one is readable but inert.

FR-2# Requirement 2 of 11

SHALL Adoption SHALL be read-only on disk: no adoption path, single or corpus-wide, successful or refused, may write, truncate, create, rename or delete a specification file.

WhyAdoption exists to believe the file; a recovery operation that rewrites what it recovers would destroy the evidence it relies on. The adoption module imports no writer, so the property is structural.

FR-3# Requirement 3 of 11

SHALL Adoption SHALL take the row's phase from the file's `aw-spec-status` metadata. Where that metadata is absent, names no known phase, or names a phase the document's kind cannot hold (only a `capability` may be `current`, and a `capability` may only be `current`), adoption SHALL use the phase a newly created document of that kind receives (`current` for `capability`, `exploring` otherwise) and SHALL report the phase as defaulted, together with any value the file carried.

WhyThe payload has no status key, so the rendered metadata is the only record of a lifecycle this machine never saw. Refusing over a bad status would strand a corpus over a value the operator cannot easily see; defaulting silently would pass a guess off as a reading.

FR-4# Requirement 4 of 11

SHALL Adoption SHALL refuse, without creating a row, a file that does not declare its own identity: one with no `aw-spec-payload` block (`payload_absent`), one whose block is not a JSON object (`payload_unreadable`), or one whose payload declares no title or a kind that is not a known document kind (`payload_identity_missing`). Adoption MUST NOT derive a title from the path.

WhyA guessed name would enter a committed file that outlives the machine that guessed it. The two missing-payload cases are refused distinctly because their remedies differ: write the document through the Hub, or repair a block that is already there.

FR-5# Requirement 5 of 11

MUST Where the path already has a row, adoption MUST refuse with `document_exists` (409), MUST NOT change the row, and SHALL report every field among title, kind and phase on which the file and the row disagree, with both values; the file's phase is compared as the file declares it, not as adoption would have defaulted it. Agreement SHALL be reported as an empty difference list.

WhyWhich side wins is an operator decision; adoption supplies the diagnostic without taking it. Comparing the defaulted phase would report a hand-edited capability file as agreeing with its row.

FR-6# Requirement 6 of 11

SHALL The Hub SHALL adopt every adoptable document discovered beneath `spec/` in one operation (`POST /spec/adopt`) that never fails as a whole: each discovered path SHALL be reported as adopted or skipped with its reason, discovery's diagnostics (including truncation) SHALL be returned, and a repeated run SHALL adopt nothing and create no duplicates.

WhyA clone, a migration or a restored machine produces a corpus whose files predate its rows; one call per document is not a recovery procedure, and one hand-written file must not block the rest. A truncated sweep presented as complete is the worst outcome.

FR-7# Requirement 7 of 11

SHALL Adoption SHALL validate the path as a spec path (beginning `spec/`, ending `.html`, no dot, hidden or empty segment) and resolve it through the project workspace before reading the file, refusing anything else as `unsafe_document_path` (400).

WhyAdoption reads files the caller names; it must not become a way to read outside the project's specification tree.

FR-8# Requirement 8 of 11

SHALL An adopted document SHALL be filed into `spec/index.json` with its real title and kind by the next reindex, and SHALL appear in the specification listing with its document id and phase. Adoption itself SHALL NOT write the index.

WhyBefore adoption a file is reported as `unindexable_document`; adoption is what makes it indexable, while writing the index stays the reindex operation's job so adoption remains read-only.

FR-9# Requirement 9 of 11

SHALL The operator's document browser SHALL offer Adopt beside each listed file that has no document record, and an "Adopt all" action naming how many are untracked. Each refusal SHALL be shown in the Hub's words with any field differences; a sweep's result SHALL count adopted documents, count (not list) already-tracked documents whose record agrees, list every other skip with its reason, show discovery diagnostics, and prompt the operator to rebuild the index to file what was adopted.

WhyThe browser already shows those files; showing them without a way to track them leaves documents the Hub cannot move through any phase. Listing every agreeing tracked document buries the skips that matter.

FR-10# Requirement 10 of 11

MUST Adoption SHALL be an operator action whose request carries only the path; a run-scoped credential MUST be refused, and a body naming any other field (title, kind, phase) MUST be refused.

WhyEverything about the document is read from the file. A caller able to state its identity could state it differently from the file, and a run should not bring a document into existence by writing a file next to itself.

FR-11# Requirement 11 of 11

SHALL A successful adoption SHALL record the content digest of the bytes it read as the document's baseline, SHALL record an `adopted` event in the document's history carrying the identity it read, and SHALL broadcast `spec_updated` so open views refresh.

WhyWithout a baseline the first outside edit after adoption would be undetectable; the digest is taken from the bytes already read so it cannot straddle an edit landing between two reads.

Design

D1 Separate route. Adoption is `POST /documents/adopt`, not a flag on `POST /documents`: creation renders a starter file over its path, so a missing flag would destroy the document it was meant to adopt.

D2 Identity from the file. Title and kind come from the `aw-spec-payload` block (payload wins over the meta tag for kind; the meta tag fills a kind the payload omits); phase comes from the `aw-spec-status` meta tag because the payload carries none. The request carries only a path.

D3 Default, report, never refuse over phase. An absent, unknown or kind-incompatible status falls back to the kind's creation default and is reported as `defaulted`, with the file's value in `unrecognised_phase`.

D4 Refuse rather than update. An already-tracked path is refused with a field-by-field difference list; choosing whose version wins is left to the operator. Phase is compared as declared, not as defaulted.

D5 A sweep never fails as a whole. Each discovered path is adopted or skipped independently, discovery diagnostics are passed through, and re-running is idempotent because a tracked path is refused.

D6 Baseline digest. The digest of the bytes adoption read becomes the row's `content_digest`, so later outside edits are detectable.

Refusal status mapping (`hub/hub/api/v1/spec.py`): `unsafe_document_path` 400; `document_exists` 409; `file_missing`, `file_unreadable`, `payload_absent`, `payload_unreadable`, `payload_identity_missing` 422.
