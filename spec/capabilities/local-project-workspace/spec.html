Local project workspace

capabilitycurrentsketch

31 MUST·31 requirements·72 criteria

Summary

One local Hub owns many projects. Each project has a durable ID and one canonical working directory, bound by a marker file in that directory; every project filesystem operation goes through one server-side resolver; the operator opens, creates, relocates and deletes projects explicitly; and one operator event stream carries every project's events, stamped with the project they belong to.

Problem

A Hub that serves several projects must never confuse one project's files, events or cached state with another's, must never take its own process directory as a project's identity, and must keep a project's history intact when its folder goes missing, moves, or is copied.

Scope

In scope

  • Project identity: the project ID, the canonical directory binding, and the `.agentweave/project.json` marker
  • Opening, creating, relocating, adopting and deleting projects
  • Choosing a project directory: typed path, Hub-side directory browsing, the host's folder dialog
  • Directory availability states and what they pause
  • The project settings resource as a whole, and the main-branch setting
  • Ignore rules for the Hub's own working files
  • The single operator event stream: project stamping, commit-ordered announcements, overflow notice
  • Project-scoped frontend state, project views, and project-consistent agent colour

Non-goals

  • How agent and task checkouts are provisioned (workspace-isolation)
  • What an agent run may touch on disk (agent-run-sandboxing)
  • How individual settings sections are presented and saved (project-environment-settings)

Requirements

FR-20# Requirement 1 of 31

SHALL Each project SHALL have a stable project ID and one canonical absolute working directory, the ID SHALL survive rename and relocation, and no two projects MAY be bound to the same canonical directory.

WhyEvery task, conversation and run is keyed by the project ID; the directory is a binding that can change, the ID is not.

FR-41# Requirement 2 of 31

SHALL A registered directory SHALL contain `.agentweave/project.json` holding exactly a marker version and the project ID, and nothing else: no credential, setting or absolute path.

WhyThe marker is what lets a moved or copied folder be recognised; it lives in the operator's tree, so it must be safe to leave there.

FR-42# Requirement 3 of 31

SHALL Opening a directory whose marker names a project ID this database has no record of SHALL register it under the marker's own ID, seeded like a new project, and SHALL record a `project_adopted` event.

WhyA folder registered in another database, or a project deleted from this one, should come back as itself rather than be refused; the event lets the operator see afterwards that it was adopted, not created.

FR-21# Requirement 4 of 31

SHALL The Hub SHALL canonicalize project directories server-side and route every project filesystem operation through one resolver, which MUST refuse filesystem roots, the Hub data directory, directories inside `.agentweave/worktrees` or `.agentweave/tasks`, relative paths, traversal, control characters, a leading `~`, and symlink escapes, and MUST NOT use the Hub process working directory as project identity.

WhyOne resolver is one place to get containment right; a Hub serving many projects has no meaningful current directory.

FR-22# Requirement 5 of 31

MUST Opening SHALL register an existing directory without creating it; creating SHALL make exactly one new directory inside an existing parent, MUST refuse a target that already exists, MUST NOT create intermediate directories, and SHALL name the project after that directory.

WhyOpening and creating are different intents; neither may silently do the other, and creation must not build a path the operator did not see.

FR-43# Requirement 6 of 31

SHALL The create dialog SHALL take an existing parent directory and a project name, SHALL refuse a name that is empty, contains a path separator or is a traversal segment with a message naming the problem rather than rewriting it, and SHALL show the absolute path to be created, derived from the same value it submits.

WhyThe operator should not have to compose a filesystem path, and a preview that can disagree with the payload is worse than none.

FR-44# Requirement 7 of 31

SHALL Registration SHALL create the project row, its default runners and starter charters, and its marker as one unit, rolling back the row and restoring the marker if the marker cannot be written, and SHALL NOT initialise git, start an agent, create a specification or modify project source.

WhyA half-registered project that looks ready but has no marker cannot be resolved later.

FR-45# Requirement 8 of 31

SHALL Relocating a project SHALL be its own action, accepted only when the target carries the project's marker, the old directory is no longer available, no other project claims the target, and no run is in progress, and SHALL then repair the git registrations of the checkouts the project contains.

WhyA marker at two live paths is a copy, not a move; a claimed path would break the one-directory rule; a move breaks the absolute paths git keeps for every linked checkout.

FR-23# Requirement 9 of 31

SHALL The local app SHALL authenticate with one automatically discovered instance operator credential that grants the project collection without selecting a project, and project resources SHALL carry the project ID in their route.

WhyProject identity comes from the route the operator chose, never from which key happened to be used.

FR-46# Requirement 10 of 31

MUST A run credential MUST remain scoped to its recorded run, agent and project, and MUST NOT accept a project identity chosen by the caller.

WhyAn agent naming another project must not reach it.

FR-24# Requirement 11 of 31

SHALL Each project SHALL expose its settings (name, hop budget, per-turn delivery cap, agent budget, token budget, agent-job allowance, and the settings other capabilities add) as one project-scoped resource whose updates are validated as a whole against the stored values and take effect through the existing scheduling and budget services.

WhyOne resource with one validator means a save cannot leave the project in a state no single field check would allow.

FR-25# Requirement 12 of 31

SHALL A project whose directory is missing, unreadable, not a directory, unbound, not mounted, or in identity conflict SHALL stay listed with that state and its history readable, SHALL refuse new operator input and new process starts, and SHALL keep its queued entries and jobs, pausing them until the directory is available again.

WhyA missing folder is usually a moved folder; the operator needs the project visible to repair it, and nothing should be lost meanwhile.

FR-47# Requirement 13 of 31

SHALL A refusal caused by a project's directory SHALL answer with a `code`, a `message` and the `directory_state`, as 409 for an unavailable or conflicting directory and 422 for an invalid path.

WhyThe app branches on the code (for example to offer 'register the copy as new'), never on the prose.

FR-26# Requirement 14 of 31

SHALL The local app SHALL receive one operator event stream for the instance, every project-scoped event on it SHALL carry a `project_id` stamped by the server from trusted context, and it SHALL carry events for projects that are not selected.

WhyThe rail stays live for every project, and a payload can never redirect an event to another project.

FR-27# Requirement 15 of 31

MUST Every project-scoped query, mutation, invalidation, URL destination and persisted draft SHALL carry the project ID, so that a response or event for one project MUST NOT populate another project's view, even when the operator switches projects mid-request.

WhyCross-project bleed is invisible until it causes a wrong action.

FR-28# Requirement 16 of 31

MUST The rail SHALL list registered projects and their open agents; a project SHALL offer Overview, Tasks, Spec, Jobs and Activity tabs and an Environment destination (quality, instructions, runners, charters, worktrees, diagnostics, budgets, settings), and adding a project view MUST NOT add a rail destination.

WhyThe rail is for choosing a project or an agent; everything about a project lives inside it.

FR-29# Requirement 17 of 31

SHALL An agent's colour SHALL be the same on every surface within its project, SHALL always be shown with the agent's name, and SHALL be looked up by project and agent together.

WhyTwo projects may each have an agent called `dev`; colour alone must never be the identifier.

FR-30# Requirement 18 of 31

SHALL An existing unbound legacy project SHALL be preserved and bound by the first explicit open of a directory with no marker when it is the only unbound project, the legacy bootstrap key SHALL become the instance operator credential with its value unchanged, and the Hub MUST NOT bind legacy state to any directory implicitly.

WhyUpgrading must not lose a single-project installation's history or change the key its tools hold.

FR-31# Requirement 19 of 31

MUST When `AW_WORKSPACE_ROOT` is configured, the Hub SHALL accept only directories beneath it, MUST refuse anything else with a `project_workspace_not_mounted` diagnostic naming the root, and MUST NOT mount the Docker socket or guess host-to-container path mappings.

WhyIn a container the only safe paths are the ones the operator mounted; guessing a mapping would register the wrong folder.

FR-32# Requirement 20 of 31

SHALL The Hub UI SHALL let the operator browse directories visible to the Hub process, and the chosen directory SHALL be usable without editing: the project directory when opening, the parent directory when creating.

WhyBrowsers withhold absolute paths, so the Hub lists them; a browsed folder exists, so in create mode it can only be the parent.

FR-33# Requirement 21 of 31

SHALL Directory listing SHALL require operator authentication, SHALL list directories only and never follow a symbolic link, and where a workspace root is configured SHALL start from it and refuse any path outside it with a stated reason.

WhyA listing endpoint is a filesystem probe; it must not become a way out of the mounted tree.

FR-34# Requirement 22 of 31

SHALL On a Windows Hub with an interactive desktop, the operator SHALL be able to choose a project directory through the host's own folder dialog; the Hub SHALL report availability before the dialog is offered, SHALL keep serving other requests while it is open, and typing and browsing SHALL remain available either way.

WhyThe native dialog is the fastest way to a real path, but only where it can actually open.

FR-35# Requirement 23 of 31

SHALL The host dialog SHALL report `chosen`, `cancelled`, `timeout`, `unavailable` or `failed`; cancelling SHALL leave the current input unchanged and not be shown as an error, and a request while a dialog is already open MUST be refused with 409 rather than open a second dialog.

WhyCancelling is a normal choice; a timeout and a failure each need their own words.

FR-36# Requirement 24 of 31

SHALL A project SHALL carry an explicit main-branch setting that approval merges into; while it is unset nothing SHALL merge and no task transition SHALL be blocked, and a branch named in settings that does not exist SHALL be refused.

WhyWriting commits into a branch the operator did not choose is worse than not merging.

FR-48# Requirement 25 of 31

SHALL Opening a git project whose main branch is unset SHALL set it to the branch the repository names as its main branch, SHALL NOT overwrite a branch already chosen, and, once a branch is set by open or by settings, SHALL retry the integrations that were skipped for want of one.

WhyLeaving the setting empty after the Hub had already detected the answer kept worktree isolation and integration degraded with nothing on screen saying why (F4); skipped approvals cannot be re-run by approving again.

FR-37# Requirement 26 of 31

SHALL The Hub SHALL keep its own working files (checkouts, logs, evidence, context, calls, reads, the project marker) and the build artefacts its own commits would sweep in out of version control in every checkout it provisions, by maintaining a marked block in the repository's `.git/info/exclude` at registration and whenever it resolves an agent or task workspace.

WhyThe Hub commits an agent's checkout with `git add -A`; anything not excluded becomes the operator's history. `info/exclude` reaches every linked worktree without the Hub committing to the operator's repository.

FR-49# Requirement 27 of 31

SHALL Seeding SHALL leave every rule outside its own block untouched, SHALL be idempotent and bring an older block up to date, SHALL NOT untrack anything already committed, SHALL do nothing for a directory that is not a repository, and its failure SHALL NOT fail registration or a turn.

WhyThe operator's ignore rules are theirs; ignore rules are a convenience, not a precondition.

FR-38# Requirement 28 of 31

MUST The operator SHALL be able to delete a project and every Hub record scoped to it, removing database rows only and never touching the project's directory or any file in it, including its marker.

WhyDeleting from the Hub is about the Hub's collection, not the operator's files.

FR-50# Requirement 29 of 31

MUST Deletion MUST be refused with `project_has_active_run` while any of the project's runs is running, SHALL NOT be blocked by any other record, SHALL require the operator to type the project's current name, and deleting the last project SHALL leave the app in a non-error state that still offers adding one.

WhyDeletion is irreversible; a running process must not lose its project underneath it.

FR-39# Requirement 30 of 31

MUST The Hub SHALL broadcast an event reporting a database write only after the transaction holding that write commits, MUST NOT broadcast it when the transaction rolls back, and a failure to publish a deferred announcement MUST NOT fail the commit or change the route's answer.

WhyA client that refetches on an event must find the change the event described.

FR-40# Requirement 31 of 31

SHALL When the Hub drops events for a subscriber whose queue is full, that stream SHALL send one `stream_gap` frame with the number dropped and no `project_id` as soon as it is sending again, and the app SHALL refresh all server state as on a reconnect and show in Activity that events were not delivered.

WhyDropping for a slow reader keeps other broadcasters moving, but a silent drop leaves the app showing stale state as current.

Design

D1 Identity lives in the database; the directory is a binding. `Project.id` is durable; `working_directory` and its host-semantic `path_key` (unique) can change. The marker in `.agentweave/project.json` carries only the version and ID, so a moved folder is recognised and a copied one is detected.

D2 One resolver. `resolve_project_workspace` (hub/hub/project_workspace.py) canonicalizes, checks containment and the marker, and records `directory_state` (available, missing, unreadable, not_directory, unbound, not_mounted, identity_conflict). It deliberately does not stamp `last_seen_at`, so resolving a workspace writes nothing and holds no SQLite write lock (F349).

D3 Open, create and relocate are separate verbs (`POST /projects/open`, `/create`, `/{id}/relocate`). Open never creates; create never opens an existing folder; relocate is the only way to move a binding deliberately, and open performs the same move when an unavailable project's marker turns up elsewhere. Relocation repairs git worktree registrations instead of refusing over existing checkouts.

D4 Main branch: a detected branch is adopted on open only into an empty setting, because the Hub had already computed it and leaving it empty degraded integration silently (F4). An operator's choice is never overwritten; a named branch must exist.

D5 Ignore rules go in `.git/info/exclude`, not `.gitignore`: an uncommitted `.gitignore` does not reach linked worktrees, and committing one would be the Hub writing to the operator's history. The list covers what the Hub's own `git add -A` snapshot would sweep in.

D6 Deletion sweeps every table with a `project_id` column found in `Base.metadata`, so new tables are covered by construction, and never calls a filesystem API.

D7 Events: a write's event is staged with the transaction and published from the session's `after_commit` hook; a full subscriber queue counts drops and the stream reports them once as `stream_gap`.
