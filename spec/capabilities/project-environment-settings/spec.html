Summary

The project's configuration surface under Environment and the settings write behind it: how each section introduces itself, how settings are laid out as labelled rows, how saving reports its outcome, the main-branch control, that a change may name only the fields it changes, that a runner named in settings must belong to the project, and that a saved change is recorded in the project's history.

Problem

Per-project configuration moved out of the navigation rail into Environment sections. Those sections must read as complete, show what each setting does, never silently revert settings the surface did not know about, and say whether a save worked.

Scope

In scope

  • Presentation of Environment configuration sections (project and per-agent settings share it)
  • Typed numeric fields and save feedback
  • The main-branch control in Settings
  • `PUT /projects/{id}/settings` partial-update semantics, runner references, and its history record

Non-goals

  • What each individual setting means: owned by its capability (budgets, checkpointing, checks, conversation titles)
  • The settings resource as a whole, the main-branch setting's rules and detection, project identity, relocation and deletion: local-project-workspace
  • Re-attempting integrations when a main branch is named: approval-integration

Requirements

FR-1# Requirement 1 of 9

SHALL Every configuration section SHALL open with its scope, its title and a short statement of what it governs.

WhyA section with few settings should still read as complete, and the operator should know whether it is project or agent configuration.

FR-2# Requirement 2 of 9

SHALL A configuration section SHALL present its settings as rows, each pairing a label and an explanation of the setting's effect with its control, separated by hairlines rather than each enclosed in a card.

WhyRows scan quickly and keep the explanation next to the control it explains.

FR-3# Requirement 3 of 9

MUST A configuration section SHALL fill the content region it is given, bounding text and controls to a readable measure without leaving a large unused region beside a narrow column.

WhyA narrow column in a wide pane reads as unfinished.

FR-4# Requirement 4 of 9

MUST Numeric settings SHALL be typed, with no increment or decrement steppers in any browser engine, and SHALL keep their numeric constraints, an invalid value being refused with an explanation.

WhySteppers invite accidental changes on hover and scroll; removing them must not remove validation.

FR-5# Requirement 5 of 9

SHALL Saving a configuration section SHALL report success in the section, and a refused save SHALL state the reason in the section and keep the values the operator entered.

WhyA save whose outcome is only in a log is a save the operator has to guess about.

FR-6# Requirement 6 of 9

SHALL The Settings section SHALL offer a main-branch control showing the project's chosen branch, offering the repository's detected branch as a one-click suggestion when none is chosen, and disabled with an explanation when the project is not a git repository.

WhyThe note on an unmerged task sends the operator to settings to choose a branch; the control it names has to be there.

FR-7# Requirement 7 of 9

SHALL `PUT /projects/{id}/settings` SHALL accept a body naming only the fields being changed, treating an omitted field as unchanged and an explicit null as a clear, and SHALL apply cross-field validation to the merged result.

WhyA surface that must resend every setting can silently revert one it does not know about, which is how a save once cleared a project's checkpoint configuration.

FR-8# Requirement 8 of 9

SHALL A settings save that changes at least one value SHALL persist a `project_settings_updated` event listing each changed field's previous and new value, and a save that changes nothing SHALL record nothing.

WhyBudget changes made in Accounting were already in the project's history; the same change made in Settings must be too (F238).

FR-9# Requirement 9 of 9

SHALL A settings save naming a conversation-title runner or checkpoint runner that does not exist in this project SHALL be refused with 400 naming the runner ID.

WhyThese references are not foreign keys, so the route is the only place a cross-project or deleted runner can be caught.

Design

D1 One shared `SettingsSection` / `SettingsRow` pair (`hub/ui/src/components/environment/SettingsSection.tsx`) serves project and per-agent settings; its `scope` eyebrow says which.

D2 The update body is derived from `ProjectSettings` with every field optional (`ProjectSettingsUpdate` in `hub/hub/api/v1/projects.py`), so a field cannot be accepted and then silently not written; the handler merges onto stored values with `exclude_unset` and validates the merged object.

D3 Steppers are removed in CSS (`hub/ui/src/index.css`), not by changing input types, so browser validation still applies.
