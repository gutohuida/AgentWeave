Run task binding

capabilitycurrentsketch

HomeWork and traceability

26 MUST·26 requirements·93 criteria

Summary

Which task a run is working on, who decides that, what binding does to the task, and what happens when a run ends holding work nobody moved. The Hub binds a run when it starts, from the cause that started it, and checks it when it ends, for every runner and without relying on a runner hook; a bound run that ends having caused no transition of its own is recorded as a divergence and answered by the task's divergence policy. task-lifecycle-governance decides whether a transition is legal; this capability makes sure one happens at all.

Problem

Without an edge from run to task, a task's status stays current only if an agent remembers to say so, and an agent that does the work and never touches the ledger passes every validity check. Evidence, reviews and flows all need to know which task a run was about.

Scope

In scope

  • The run's task binding and where it comes from: delegation, operator start, flow firing, review dispatch, conversation inheritance, an unbound run's claim
  • The automatic move to in_progress and assignee on binding, and who a claim may take
  • Resolving a turn's task before its workspace is chosen
  • Binding and waiting tasks: no divergence while waiting, no release by a run starting, questions that record their task
  • Read-only agents holding no task work
  • The run-end divergence check, its durable record, severity, resolution, and the per-task policy (surface / retry / escalate) with its one-hop bound
  • Conversation bindings and their release; what a decided task stops accepting

Non-goals

  • Transition legality, actor rules and the blocked status itself (task-lifecycle-governance)
  • How a review that records no verdict is restaffed, and withdrawing waiting reviews when a task is decided (agent-flows)
  • Delivering an operator's answer to an asker whose run has ended (agent-capability-plane)
  • Which workspace a bound turn gets (workspace-isolation)

Requirements

FR-16# Requirement 1 of 26

SHALL The system SHALL record, on each run, the single task that run was started for, or nothing. A run SHALL NOT be bound to more than one task.

WhyA run with no binding is legitimate (conversation, questions, scheduled work); a run with two would make the end-of-run check ambiguous.

FR-17# Requirement 2 of 26

SHALL The system SHALL set a run's binding itself, from the cause that started the run. No agent-facing operation, over HTTP or MCP, SHALL create, change, or remove a run's binding, except that an unbound run's own move of a task to in_progress binds it to that task.

WhyAn agent able to bind or unbind itself could arrange never to be checked; the one exception (a claim) can only add a binding, never remove or swap one.

FR-18# Requirement 3 of 26

SHALL The system SHALL bind a run started to review a task to the task under review, by the same binding mechanism used for work, without moving the task and without merging the review checkout selector into the work binding.

WhyA review has exactly one subject, so it is not an exempt unbound turn. The queue entry keeps work (task_id) and review (review_task_id) as separate fields because which commit a reviewer checks out and which task a run is about are different questions. Staffing the reviewer and moving the task into review is the dispatch's act, not the binding's.

FR-19# Requirement 4 of 26

SHALL The system SHALL carry a task named on an agent-to-agent message through the receiving agent's inbound queue and bind the run that delivers it to that task. A named task that does not exist in the sender's project SHALL be refused when the message is sent; a task that has been deleted or decided by the time the entry is delivered SHALL leave the entry deliverable without a binding.

WhyThe sender learns about a bad id in the tool result it is reading; a task that changed after the message was queued is not a reason to lose the message.

FR-20# Requirement 5 of 26

SHALL The system SHALL let the operator start work on a task directly from the task, producing a run of the chosen agent bound to it, and SHALL show on the conversation which task its turns are bound to.

FR-21# Requirement 6 of 26

SHALL The system SHALL, when binding a run to a task from whose current status an agent run may reach `in_progress`, move the task to `in_progress` and attribute the move to the binding run.

WhyThe move goes through the same transition service as every other status change, recorded with origin runtime and the binding run as actor, so no legality rule or later gate is bypassed and the move is not counted as the run's own progress.

FR-22# Requirement 7 of 26

SHALL The system SHALL, when a bound run ends, determine whether that run caused any actor-origin transition of its bound task, and SHALL record a bound run that caused none as divergent, whatever its exit status, unless its delivered input was returned to the queue or its task is waiting on a person.

WhyThe check sits at the run boundary the Hub owns for every runner. A crash is still a run that ended holding unmoved work, and the record names the exit status. Input returned to the queue is about to be redelivered to a new bound run, so nothing was dropped.

FR-23# Requirement 8 of 26

MUST The system SHALL persist one record per divergence, naming the run, agent, task, the task's status at run end, the run's exit status, the policy applied, the outcome, the previous assignee where the work was reassigned, and the run started in response where one was. After creation only its resolution time and response run SHALL be written, and the record SHALL be removed only when the operator deletes its task.

WhyThe operator must be able to see divergences that occurred while they were not watching and ask how often an agent diverged; deleting a task deletes what exists only for it.

FR-24# Requirement 9 of 26

SHALL The system SHALL let each task carry a divergence policy of surface, retry, or escalate, and an escalation agent; a task with no policy is surface. For a work run, surface records and starts nothing, retry queues one further turn of the same agent bound to the task, and escalate reassigns the task to its escalation agent and queues a turn of that agent bound to it. The policy SHALL NOT govern a run started to review the task, and retry SHALL NOT answer a divergence of a live flow's own work turn.

WhySurface is the default so the capability never starts runs nobody asked for. A live flow fires the task again on its next tick, so a retry would race it; such a divergence is surfaced and recorded with policy 'flow'. A review that gave no verdict is a different failure, recorded with policy 'review' and answered by agent-flows. An escalation agent that no longer exists surfaces instead.

FR-25# Requirement 10 of 26

SHALL Where a flow firing claims a task and starts a run to work it, the system SHALL bind that run to the claimed task. The binding SHALL be carried on the queue entry the firing stages, so that the run that delivers the entry is bound by the same mechanism as every other cause that names a task.

WhyBinding through the queue entry means a flow's run is bound and checked by the same mechanism as every other cause. A firing that staffs a review names the task as review_task_id, not task_id; a firing that claims nothing starts an unbound run.

FR-26# Requirement 11 of 26

SHALL The system SHALL announce a divergence at information severity only when the run was a live flow's own work turn, ended completed, and its task is still assigned to the run's agent after the policy was applied; every other divergence SHALL be announced as a warning.

WhyA flow's multi-turn work that is simply not finished is not a problem for the operator; a released task, a failed run, or a reassignment needs their attention.

FR-27# Requirement 12 of 26

SHALL The system SHALL emit an event when an open divergence is resolved, naming the task and how many open divergences were closed.

WhyAn announced condition with a silent answer cannot be told apart from a standing one. The event is emitted only after the transition that resolved it commits.

FR-28# Requirement 13 of 26

SHALL The system SHALL record, on a run started in response to a divergence, the run whose divergence caused it. A run carrying that reference SHALL NOT itself trigger a retry, and SHALL NOT trigger an escalation unless it was itself started by a retry.

WhyA chain starts at most one retry and one escalation before surfacing, so no sequence of divergences starts an unbounded number of runs. The bound is per chain: a response run that moves its task ends the chain, and a later independent divergence gets the full policy again.

FR-29# Requirement 14 of 26

SHALL The system SHALL let the operator read and change a task's divergence policy and escalation agent from the task itself, SHALL refuse an agent's attempt to change either with 403, and SHALL show on the task whether it has an open divergence.

WhyAn agent able to set its own task's policy could disarm the check that exists to catch it.

FR-30# Requirement 15 of 26

SHALL The system SHALL record a task binding on the conversation, and SHALL bind a run started in that conversation to it when nothing more specific applies.

WhyWork spans more turns than a run, and the turn where the agent stops is the one that matters. An input naming its own task rebinds the thread. Each run still records its own task, so integrity records never depend on joining through a conversation.

FR-31# Requirement 16 of 26

SHALL The system SHALL let the operator release a conversation's binding, and SHALL release it automatically when the bound task is approved or rejected; it SHALL NOT release a binding by inferring what the conversation is now about.

WhyA wrong inference silently stops checking runs.

FR-32# Requirement 17 of 26

SHALL The system SHALL NOT record a divergence for a run whose bound task is waiting on a person.

WhyA waiting task has an account of why it stopped; a retry would restart an agent still waiting for the same answer.

FR-33# Requirement 18 of 26

SHALL Binding a run to a task that is waiting on a person SHALL leave that task waiting. The system SHALL NOT move it back to the in-progress status as a consequence of a run starting.

WhyThe edge out of the waiting status exists, so without this rule the act of starting a run would release the block — and that run's end would then find the task no longer waiting and record a divergence against work that was never dropped. A block ends when the answer arrives or the operator ends it, never because something started.

FR-35# Requirement 19 of 26

SHALL A blocking question asked about a task that is already waiting SHALL record that task, so that answering that question releases the block. Recording which task a question is about SHALL NOT depend on that question being the one that moved the task into waiting.

WhyA task already waiting has no transition to make, so the question's link to the task is recorded separately; otherwise answering the newer question would release nothing.

FR-36# Requirement 20 of 26

SHALL A run that moves a task it does not hold into `in_progress` SHALL become bound to that task. A run that already holds a different task SHALL be refused, preserving the existing invariant that a run carries at most one task binding.

WhyThis makes 'go and find waiting work' a recorded claim, and is what lets task-lifecycle-governance require that only the holder completes a task.

FR-37# Requirement 21 of 26

SHALL The system SHALL resolve which task a turn is about before it chooses the workspace that turn will run in, so the workspace can be the one belonging to that task.

WhyResolution is a read; the binding, the move and the rebinding are staged later, before delivery commits, so no partial write exists. A request that will be refused leaves no checkout behind, and an unavailable project directory is still reported first, with its directory state.

FR-39# Requirement 22 of 26

SHALL An agent run not already bound to a task SHALL be refused a move of that task to in_progress where the task is assigned to a different agent, naming the assignee and the operator's remedy and leaving the task, its assignee and the run's binding unchanged; where the task is unassigned, the claim SHALL record the run's agent as its assignee in the same transaction; a claim of the run's own agent's task, a bound run, and the operator SHALL behave as before.

Whyassignee is an authorization boundary: a takeover of another agent's task is the operator's to make, and an unassigned task claimed by a run must name who is working it.

FR-40# Requirement 23 of 26

SHALL An agent declared read_only SHALL hold no task's work: a turn of it bound to a task's work SHALL be refused before any workspace is resolved, naming the agent, the task and the remedy; a task create or update naming it as assignee outside a review status, and its run's claim of a task, SHALL be refused; and a flow SHALL NOT select it for ordinary work. Its review turns SHALL be unaffected.

WhyA read-only agent gets no task checkout, so a task-bound turn of it would write into the operator's project directory unsnapshotted. Reviewing is its intended use.

FR-41# Requirement 24 of 26

SHALL When the system binds a run to a task that names no assignee, it SHALL record the run's agent as the task's assignee; it SHALL NOT overwrite an assignee already set.

WhyOtherwise a task being worked reads in_progress with nobody holding it and the board reports the agent idle; an assignee the operator or a flow set is a statement a run starting must not override.

FR-42# Requirement 25 of 26

SHALL A task that is approved or rejected SHALL take no new work: the operator's request to start a run on it SHALL be refused with 409 naming the remedy, queued work entries naming it SHALL be unbound when it is decided, and a delegation that reaches it at delivery SHALL be delivered unbound.

WhyTurns attributed to decided work would put stalled markers on work the operator has already approved. The operator, who is reading the response, is refused; a delegation that was true when queued is not lost.

FR-43# Requirement 26 of 26

SHALL The system SHALL deliver a divergence response into a conversation: a retry continues the diverged run's own open conversation, and a response for a different agent opens a new conversation with origin 'divergence'.

WhyA queue entry with no conversation can never be scheduled, and a conversation belongs to one agent. Continuing the same agent's thread keeps the retry in the history that explains it and its resumable provider session.

Design

D1 Binding is a column on Run (task_id), set by the runtime in agent_trigger from the queue entries a turn delivers (earliest entry naming a task wins), else the explicit task, else the conversation's binding. Resolution reads only and happens before the workspace is chosen; the staging (bind, auto-move, rebind) happens just before delivery commits.

D2 Work and review are separate fields on the queue entry (task_id, review_task_id). Binding reads either; a review run's régime is derived from its delivered entries, not a Run column.

D3 Progress is measured as an actor-origin TaskTransition by the run on its bound task. The runtime's own auto-move is origin 'runtime' and does not count.

D4 The check runs at run end (evaluate_run_end, hub/hub/run_divergence.py) in its own session so it can never strand a finished run. Divergences are rows in run_divergences; only resolved_at and response_run_id are written later. Any actor transition on the task resolves all its open divergences.

D5 The retry bound is structural: a response run carries divergence_source_run_id and never retries; it may escalate only if it was a retry. No counter to misconfigure.

D6 Responses are queued, never spawned directly, so hop budget, delivery caps and ordering apply unchanged.
