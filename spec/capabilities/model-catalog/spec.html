Summary

The Hub's declaration of what each provider it can spawn offers: its models (id, label, aliases, context window) and its runtime controls (effort, permissions), each with its own permitted values and how it reaches the provider. The catalog is served to the operator interface, which renders choices from it, and every model or control the Hub accepts is validated against it before any provider process starts.

Problem

Providers accept model names and control values they cannot honour and silently fall back to a default, so a turn can run under settings the operator never chose. Hard-coding provider knowledge in the interface and in command construction also makes every new model or control a multi-place edit.

Scope

In scope

  • The catalog's content for `claude`, `codex` and `copilot` (hub/hub/model_catalog.py), including each model's context window or its absence
  • GET /api/v1/model-catalog and the source it reports for a cache-backed provider
  • Validation of a model, alias or runtime override against the catalog, and rendering of a validated control into the provider's invocation
  • The built-in window fallback for a model the cache does not list

Non-goals

  • Which runner a model is bound to, and a runner that sends its model to an operator-supplied provider: runner-registry
  • How a run's context usage is computed and presented from a window: agent-context-usage
  • What each permission posture lets a run do: agent-run-sandboxing

Requirements

FR-6# Requirement 1 of 11

SHALL The Hub SHALL declare a catalog entry for exactly the providers it can spawn (`claude`, `codex`, `copilot`), each listing its models with the identifier passed to the provider, a label, any aliases the provider accepts, and the model's context window, declared as unknown rather than substituted when the Hub does not know it.

WhyA provider listed but not spawnable would offer a choice that can never run, and a substituted window would show a usage percentage that is not true.

FR-7# Requirement 2 of 11

SHALL Each provider entry SHALL declare its runtime controls with an id, a label, a kind, its permitted values, a default, and how it is applied to the invocation (a command-line flag, a configuration override, or nothing on the command line), and a permitted value MAY carry its own application in place of its control's.

WhyCommand construction renders any declared control without knowing what it means, so adding a control is a catalog edit rather than a change to command building, validation and the interface.

FR-8# Requirement 3 of 11

SHALL A control's permitted values SHALL be declared on that provider's control, and a value permitted for one provider SHALL be refused for a provider that does not declare it.

WhyProviders support different effort levels; Codex's effort values are the intersection of what every listed Codex model supports, so the Hub never accepts a value a specific model would reject or silently discard.

FR-9# Requirement 4 of 11

SHALL The Hub SHALL serve the catalog at GET /api/v1/model-catalog to any authenticated operator, identically for every project, and the operator interface SHALL present model and control choices from it rather than from provider knowledge of its own.

WhyThe catalog is not project data; serving it once keeps the interface free of hard-coded model ids, control ids and values, so a catalog edit reaches every picker without an interface change.

FR-10# Requirement 5 of 11

SHALL The Hub SHALL validate a turn's requested overrides against its runner's provider entry before the turn is queued, and SHALL refuse with HTTP 400 and a stated reason an override naming an undeclared control, an enum value the provider does not permit, or an undeclared model, so that no provider process starts.

WhyProviders warn and continue at their default on an invalid value, so the Hub's own check is the only one that keeps a turn from running under settings nobody chose.

FR-11# Requirement 6 of 11

SHALL The Hub SHALL accept a model alias the catalog declares wherever it accepts that provider's model identifiers (runner create and edit, agent creation, turn overrides, one-shot workers), and SHALL store and pass on the alias as written; a value that is neither a declared identifier nor a declared alias SHALL be refused with a reason naming every identifier and alias that would be accepted.

WhyAn alias is the provider's way of following the latest model of a family; resolving it on the day it was chosen would freeze the choice the alias exists to keep current.

FR-12# Requirement 7 of 11

SHALL For Codex, whose installed CLI keeps a model cache (`$CODEX_HOME/models_cache.json`, else `~/.codex/models_cache.json`), the Hub SHALL offer the cache's listed models in the cache's priority order with the first as default, and SHALL fall back to its built-in list only when the cache is absent, unreadable, malformed or lists no model, without failing any request.

WhyThe provider's server sends each client version its own list, so the list the installed client wrote is the one it will accept; a built-in list can only be a fallback.

FR-14# Requirement 8 of 11

SHALL For a cache-backed provider, the served catalog SHALL state whether its models came from the CLI cache (with the cache's fetch time and client version) or from the built-in list (with the reason the cache was not used), and a change to the cache SHALL be reflected on the next read without restarting the Hub.

WhyAn operator choosing a model needs to know whether the list reflects the installed CLI or a fallback.

FR-15# Requirement 9 of 11

SHALL Where a run reports usage on a model the provider's cache does not list but the built-in list declares, the Hub SHALL still take that model's context window from the built-in list, and this fallback SHALL NOT make the model acceptable where a model is newly set.

WhyA run on a model the cache has since dropped keeps an honest window, while new choices stay limited to what the installed CLI accepts.

FR-13# Requirement 10 of 11

SHALL The catalog SHALL describe `copilot` with `auto` (labelled "Auto") as its default model followed by the models `copilot help config` documents, held as a built-in list, each with its context window unknown, with an Effort control and with the same four permission postures and labels as the other providers, defaulting to Workspace only; a model outside that list SHALL be refused before a Copilot process starts.

WhyCopilot accepts any model name and silently replaces one the account's plan does not allow, so the Hub's validation is the only check a model name gets; Copilot reports the window it actually ran per turn, and it has no sandbox of its own, so an unset posture is judged as Workspace only.

FR-16# Requirement 11 of 11

SHALL A model the catalog offers without a declared window SHALL produce readings reported as unknown unless its provider reports a window, and SHALL NOT take another model's window.

WhyAn absent window must degrade to unknown rather than to a borrowed value.

Behaviour

Reading the Codex model list

  1. Resolve the cache path: `$CODEX_HOME/models_cache.json`, else `~/.codex/models_cache.json`.
  2. If the file is missing, return the built-in list with reason "no Codex model cache at <path>".
  3. If (path, mtime, size) matches the last successful reading, reuse it.
  4. Parse the bytes as JSON; on any error return the built-in list with reason "unreadable".
  5. Keep entries with `visibility == "list"` and a non-empty `slug`; if none, return the built-in list with reason "lists no models".
  6. Sort by `priority` (missing sorts last, ties keep file order); the first becomes the default.
  7. Take each entry's `display_name` and `context_window`; keep the built-in controls unchanged.

Design

**Catalog as data.** `hub/hub/model_catalog.py` holds one `ProviderDescriptor` per runner CLI. Controls carry an `ApplySpec` (`flag`, `config`, or `none`); `render_control_args` and `render_control_config` render any control without knowing its meaning, so a new control needs no change outside the catalog.

**Validation is the Hub's.** `validate_overrides` checks `model` against declared ids and aliases and every other key against declared controls before a turn is queued; `undeclared_model_reason` is the single refusal sentence for every site that refuses a model (runners, agents, worker, trigger).

**Aliases are choices, not shorthand.** `ProviderDescriptor.model()` resolves an alias only to decide acceptance; what is stored and sent is the alias as written.

**Codex reads its CLI's cache; Claude and Copilot are literals.** Claude's ids and windows were live-verified from Claude's own reported `contextWindow`; Copilot keeps no model file and listing models costs a spawn, so its list is the captured `copilot help config` output. `scripts/check_model_catalog.py` reports drift of the built-in lists.

**One model, one window.** No per-model window variant is offered: the current Claude models have one window each, and `[1m]` on Haiku fails. A model with no declared window reads as unknown rather than borrowing another model's.

Evidence and coverage limits

Checked

  • hub/tests/test_model_catalog.py — provider coverage, per-provider values, rendering, Copilot entry.
  • hub/tests/test_model_catalog_api.py — served catalog, auth, not project-scoped.
  • hub/tests/test_a_model_alias_is_a_model_choice.py — alias accepted and stored as written on every path.
  • hub/tests/test_codex_models_from_the_cli_cache.py — cache reading, fallback, source reporting, window fallback.
  • hub/tests/test_a_refusal_says_what_would_work.py — refusal names what would be accepted.

Limits

  • Validation checks values only for `enum` controls; no `boolean` or `number` control is declared today, so a value for one would be accepted unchecked.
