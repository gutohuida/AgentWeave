Agent configuration

capabilitycurrentsketch

24 MUST·24 requirements·38 criteria

Summary

An agent's configuration is a destination of its own, addressed by URL, divided into sections named for what an operator is trying to do: identity, execution, charter, interaction, context, access and workspace. It holds settings, not live observations. Settings are written through `PATCH /agents/{name}`, which refuses unknown fields. An agent is archived, never deleted, because every run is attributed to one; archival releases the agent's charter but keeps its runner.

Problem

Settings reached through a conversation depend on which conversation is selected, settings mixed with live status change under the reader, and a deletable agent would orphan or destroy the record of work it did.

Scope

In scope

  • The agent settings page (`hub/ui/src/components/agents/AgentSettingsPage.tsx`) and its seven sections.
  • `PATCH /agents/{name}`, `POST /agents/{name}/archive`, `POST /agents/{name}/unarchive`.
  • Agent-level settings: description, runner and charter binding, default permission posture, waiting times, grants, Copilot GitHub server.

Non-goals

  • Creating an agent (operator-agent-creation).
  • Runner and charter records themselves (runner-registry, agent-charter).
  • What a posture permits at run time (agent-run-sandboxing).
  • Checkpoint policy semantics (conversation-checkpoint); the Context section only hosts them.

Requirements

FR-11# Requirement 1 of 24

SHALL The Hub SHALL present an agent's configuration as its own destination, addressed by URL (`?project=<id>&agent=<name>&settings=<section>`), reachable without opening a conversation and restored on reload.

WhyAn agent may have many transient conversations but has one durable configuration; it should not depend on which conversation happens to be selected.

FR-12# Requirement 2 of 24

SHALL An agent's configuration SHALL show its section list in place of the surrounding navigation, with a back control that always returns to the agent's most recent conversation and keeps any document that was open beside it.

WhyA settings surface is stepped into and out of; a fixed, named return target can be read before it is used, unlike a remembered origin. Dropping the attached document would silently change what the next turn is written against.

FR-13# Requirement 3 of 24

SHALL An agent's configuration SHALL NOT present live observations (status, latest status message, last-seen time), which stay with the agent's conversation, and no setting SHALL be editable from more than one surface; provider sessions MAY appear only as diagnostic detail in the Workspace section.

WhyObservations change without anyone configuring anything. Provider sessions are listed under Workspace because their value is the directory each ran in, and they are never used to address a conversation.

FR-14# Requirement 4 of 24

SHALL An agent's configuration SHALL be divided into the sections Identity, Execution, Charter, Interaction, Context, Access and Workspace, and no section SHALL be named for a concept the product no longer has.

WhySections named for intent let later settings be added without restructuring; checkpointing lives in Context and read grants in Access.

FR-15# Requirement 5 of 24

SHALL An agent SHALL carry an optional description of at most 256 characters, edited in Identity and returned with the agent's summary, stored trimmed with a blank value stored as none, and never injected into any turn's context.

WhyThe charter is where behaviour is stated; a second behaviour-shaping field would leave two places to look when an agent acts wrongly. "Cleared" and "never written" are one state.

FR-16# Requirement 6 of 24

SHALL The Hub SHALL let an operator archive and unarchive an agent, SHALL offer no means of deleting one, and SHALL refuse with 409 and the reason to archive an agent with a run in progress or with undelivered queued input.

WhyEvery run is attributed to its agent; deletion would cascade through or orphan that history. Stopping a live run from a settings page destroys work, and archiving over queued input strands it because nothing delivers to an archived agent.

FR-24# Requirement 7 of 24

SHALL An archived agent SHALL NOT be offered where a working agent is chosen (new conversation, message recipient, task assignee, launchability report by default) and SHALL NOT be triggered, but SHALL remain reachable when asked for explicitly, including its configuration where it is unarchived; its conversations stay readable and its runs and messages keep their attribution.

WhyAn agent that could be archived but never found again would be deleted in all but name.

FR-25# Requirement 8 of 24

SHALL Archiving SHALL release the agent's charter binding and keep its runner binding, the archive response SHALL name the charter released, and the unarchive response SHALL state that no charter is bound, that archiving releases one and unarchiving does not restore it, and that an agent with no charter still runs.

WhyA charter bound to an agent nothing runs governs nothing and only blocks the charter's deletion behind a name the roster hides. The runner stays so the archived agent's configuration still shows what it ran on.

FR-26# Requirement 9 of 24

SHALL Binding a charter to an archived agent SHALL be refused with 409 naming unarchiving as the repair, while clearing an archived agent's charter binding SHALL be permitted.

WhyRe-binding would undo the release archival made; clearing is not re-binding.

FR-27# Requirement 10 of 24

SHALL Each real archive or unarchive SHALL be recorded as an `agent_archived` / `agent_unarchived` event (the archive event naming the released charter or none) and broadcast to open clients, and archiving an archived agent or unarchiving an open one SHALL answer 200 saying nothing changed, without a new event.

WhyA response body reaches one client; the event is the durable record and tells a second client its roster changed. A repeated event would read in the log like a real transition.

FR-22# Requirement 11 of 24

SHALL When archiving is refused because input is queued for the agent, the refusal SHALL state how the input is cleared (bind a runner so it can be delivered when none is bound, otherwise let it be delivered, or discard it) and carry the count and ids of the blocking entries.

WhyAn unlaunchable agent accumulates undeliverable input that then blocks archiving it; the refusal must name the remedy, non-destructive first.

FR-17# Requirement 12 of 24

SHALL The Workspace section SHALL state the directory an agent's turns run in and whether it is the agent's own checkout or the shared project checkout, SHALL list each task checkout of the agent's tasks with its branch and task, marking a task worked in the agent's own checkout because it began before per-task checkouts, SHALL state why isolation is unavailable when it is, and SHALL NOT provision anything by being read.

WhyAn operator shown one directory for an agent working three tasks is shown a place most of its work is not; a blank section is indistinguishable from one that failed to load.

FR-18# Requirement 13 of 24

SHALL An agent SHALL carry an optional default permission posture, chosen in Execution from the postures the catalog's providers declare with the same labels, applied to any run whose conversation has not chosen one (including peer- and schedule-started runs), and overridden by a conversation's own choice.

WhyRuns no operator starts still need a posture the operator chose.

FR-29# Requirement 14 of 24

SHALL Setting the default posture SHALL set the agent's legacy `config.yolo` flag to whether the posture is Full access, clearing it SHALL clear the flag, and every surface that shows a posture at rest SHALL show the one the next run would use, derived the same way, without recording it as a conversation's choice.

Why`yolo` is the older spelling of the same setting and is still read by command construction; letting the two disagree runs an agent under one posture while showing another.

FR-19# Requirement 15 of 24

SHALL The Hub SHALL NOT present or return an agent setting that has no stored state behind it, SHALL NOT show a setting as a read-only badge when it has an editable home in the configuration, and SHALL NOT ask the operator to choose a persona or organizational role.

WhyA control with no state claims something is configurable when it is not; state with no control reports a value the operator cannot act on.

FR-20# Requirement 16 of 24

SHALL The operator SHALL be able to grant and withdraw an agent's authority to accept or reject requirement evidence (`can_accept_evidence`), shown in Access apart from the read grants, stating that a granted agent still cannot accept its own work; with no agent granted, the operator SHALL still be able to decide evidence.

WhyAuthority over what merges is the operator's to give, and is not a kind of reading; an enforced capability settable nowhere is a refusal of everyone.

FR-30# Requirement 17 of 24

SHALL The operator SHALL be able to grant and withdraw an agent's read grants `can_read_checkpoints` and `can_recall` in Access, both closed by default.

WhyReading a summary of a peer's work and reading the raw output behind it are different permissions.

FR-31# Requirement 18 of 24

SHALL The Interaction section SHALL let the operator set how long a run waits for a permission decision and for an answer to a question, each a whole number of seconds from 10 to 600 or cleared to the built-in default (the page states 120 s and 240 s), refused with 400 otherwise.

WhyHow long an agent holds its turn open for the operator is a per-agent choice; validating at the route keeps a nonsense value out of the column a run reads.

FR-32# Requirement 19 of 24

SHALL `PATCH /agents/{name}` SHALL refuse the whole body with 400 naming the valid fields when it carries an unknown field, and SHALL apply `config` as a JSON merge patch in which null removes the key it names and `"config": null` clears the configuration.

WhyA misspelt safety setting answered 200 and changed nothing; a half-applied body leaves the operator believing all of it was saved.

FR-33# Requirement 20 of 24

SHALL Binding a runner to an agent that had none, or a different one, SHALL schedule delivery of the agent's queued input.

WhyBinding a runner is the repair the unbound refusal names; input queued meanwhile must be delivered once the repair is made.

FR-34# Requirement 21 of 24

SHALL A configuration change that would switch whether an agent works in its own checkout SHALL be refused with 409 while the agent has a running turn or a non-terminal task assigned, storing no part of the request.

WhyFlipping isolation under held work runs the next task turn in a different checkout from the earlier ones, and nothing commits the difference.

FR-23# Requirement 22 of 24

SHALL For an agent bound to a `copilot` runner, the Execution section SHALL offer a GitHub server setting, stored per agent and enabled only when the stored value is `true`, described as giving the agent read-only GitHub tools Copilot runs without asking in every posture and as not governing `gh` in a shell; with it off, the agent's runs SHALL start with Copilot's built-in MCP servers disabled.

WhyThat server acts on GitHub as the signed-in operator, outside the agent's workspace, so it is off until the operator turns it on.

FR-36# Requirement 23 of 24

SHALL Each agent SHALL carry its own optional limits for how long a run waits on a permission decision and on a question, passed to its runs as `AW_DECISION_TIMEOUT` and `AW_QUESTION_TIMEOUT`; an agent with no limit set, or a value outside 10-600 seconds, SHALL use the system default (120 s for decisions, 240 s for questions).

WhyA reasonable wait depends on the agent and on whether the operator is watching; one compiled-in number serves neither case.

FR-37# Requirement 24 of 24

SHALL An agent's runner control SHALL show the Hub's own collaboration reason when the Hub reports the agent runnable but not collaboration-ready, SHALL show nothing for a ready agent or one the verdict does not apply to, and SHALL refresh the verdict without a reload after the runner or permissions change.

WhyThe condition should be named where it can be fixed, and must not linger after it is fixed.

Design

**Destination, not dialog.** Settings are a URL-addressed destination whose section rail replaces the workspace rail; back always goes to the agent's most recent conversation.

**Archive, never delete.** `agent_lifecycle.archive` sets `lifecycle=archived`, stamps `archived_at` and clears `charter_id`; `runner_id` is kept so the archived agent's configuration still shows what it ran on, and runner deletion clears archived holders instead (runner-registry). Migration 0105 cleared charters from agents archived before this rule.

**One PATCH route.** `PATCH /agents/{name}` takes an untyped body, so it carries the whole vocabulary check (unknown fields refused) and per-field validation (description, posture, waiting times, grants, Copilot review agents); `config` is an RFC 7396 merge patch.

**Posture and yolo are one setting.** `default_permission_mode` is authoritative and `config.yolo` is rewritten from it, because command construction still reads `yolo`.
