Project instructions

capabilitycurrentsketch

6 MUST·6 requirements·16 criteria

Summary

Each project has one block of instructions, stored in the Hub database, served to every agent ahead of its charter, and edited on the project's Instructions screen, which never writes content it did not read and asks before blanking what is stored.

Problem

Instructions are a single row with no history. An editor that saves over content it never loaded, or blanks it with the same click as a one-word edit, destroys the only copy.

Scope

In scope

  • `GET` and `PUT /api/v1/project/instructions`
  • Placing instructions ahead of charter content in agent context
  • The Environment > Instructions screen

Non-goals

  • Charter authoring (agent-charter)
  • How agent context is assembled overall (agent-context-onboarding)

Requirements

FR-4# Requirement 1 of 6

SHALL The Hub SHALL store one instructions text per project in `project_instructions`, return an empty string when none is stored, and replace it in place on `PUT`, accepting the empty string as a deliberate clear.

WhyThe database is the only source; there is no local-file mirror and no revision history.

FR-5# Requirement 2 of 6

SHALL When a project's instructions are non-empty, the Hub SHALL place them before the charter content in `GET /agents/context` (separated by a rule) and as a `## Project Instructions` section before the `## Charter` section of an agent's full context; when they are empty, the charter SHALL be returned unchanged.

WhyProject-wide rules frame every role, so they come first.

FR-6# Requirement 3 of 6

SHALL Once the selected project's instructions have been read, the Instructions screen SHALL present them in a markdown textarea with a Save control and a notice that changes take effect when agents start a new session.

WhyThe operator edits project-wide guidance in the app, where every other project setting lives.

FR-7# Requirement 4 of 6

SHALL The Instructions screen SHALL present an editable textarea only after the selected project's instructions have been read successfully; a failed read SHALL be stated in the section with a retry that needs no reload, a pending read SHALL show loading, and a later failed background read SHALL NOT remove content already shown.

WhyEmpty instructions and unreadable instructions are different situations; showing the second as the first invites the operator to overwrite content they cannot see.

FR-9# Requirement 5 of 6

SHALL The Instructions screen SHALL NOT issue a write for a project whose stored instructions have not been read successfully.

WhyThe route accepts an empty string on purpose, so only the client can tell an intended clear from state it never loaded.

FR-8# Requirement 6 of 6

SHALL The Instructions screen SHALL ask the operator to confirm, naming the project and how much would be lost, before saving empty or whitespace-only content over stored instructions that contain more than whitespace, compared against the content last read successfully; declining SHALL write nothing and keep the editor as it was, and every other save SHALL proceed without confirmation.

WhyA blanking save is unrecoverable; a confirmation on every save would be dismissed by habit.

Design

D1 One row per project, replaced in place; no history. That is why the client guards are strict.

D2 The guards live in the client (`hub/ui/src/components/instructions/InstructionsPage.tsx`): the screen renders from `data` first, so a refetch error never removes a loaded editor, and the blanking check compares against the last successful read, with whitespace counted as empty on both sides.

D3 The PUT body is a strict request model: an unknown field (for example `contents`) is refused by name instead of being read as an empty string and blanking the instructions.
