Agent flows

capabilitycurrentsketch

35 MUST·35 requirements·179 criteria

Summary

A flow is a loop that declares a specification document. Where a loop fires one agent on a schedule, each firing of a flow decides both the tasks and the agents, so work crosses agents (implementer to reviewer) without any agent choosing its next step. This capability owns firing-time staffing and width, reviewer resolution and re-resolution, review dispatch and the briefings around it, the surfacing of reviews nobody can staff or is doing, the flow's checkpoint lineage, and how a flow is started from an approved change document.

Scope

In scope

  • Staffing a flow's firing: which tasks, which agents, and how wide
  • Who may review finished work, how a reviewer is resolved, and what happens when a review gives no verdict
  • What work and review briefings tell the agent, including the gates that can refuse a verdict
  • Surfacing reviews a flow cannot staff or nobody is doing
  • Starting a flow from an approved change document

Non-goals

  • Loop scheduling, stop conditions, in-flight definition and landing (agent-loops)
  • Transition guards and approval gates themselves (task-lifecycle-governance)
  • Divergence policies for non-review runs (run-task-binding)

Requirements

FR-1# Requirement 1 of 35

SHALL The Hub SHALL treat a loop that declares a specification document as a flow and apply this capability's requirements to it. A loop that declares no document SHALL NOT staff reviews, SHALL NOT draw agents from the project's pool, and is governed by `agent-loops` alone.

WhyNo separate record exists for a flow: the declared document is the whole distinction, so a loop and a flow share one scheduler, one queue and one board.

FR-2# Requirement 2 of 35

SHALL Each firing of a flow SHALL determine deterministically, from the queue order and the agent roster in name order, which tasks are worked and which agent works each. An agent with no runner bound, or that is archived, SHALL be treated as unavailable rather than selected.

WhyNo agent chooses its own next step, and a rerun on the same state pairs the same tasks with the same agents. Selecting an agent the Hub cannot start would turn a staffing question into a launch failure one step later.

FR-3# Requirement 3 of 35

SHALL A task in `completed` SHALL be claimable for review only by an agent that could record a verdict on it: where an agent is recorded as completing it, by any other agent that recorded no evidence for it; where the operator recorded the completion, by any agent that no record associates with the task (its transitions, its assignee, runs bound to it, or agent-recorded evidence for it); and where no completion is recorded at all, by nobody.

WhyClaimability uses the same attribution the author/reviewer guard uses, so a flow never offers work to an agent that would then be refused for judging it. Where the completer is unknown the determination is over-inclusive on purpose: excluding an agent that did nothing costs a review the operator sees go unstaffed, while including the author costs an unseen self-approval. Evidence excludes its author whatever its review state; evidence the operator recorded excludes nobody.

FR-4# Requirement 4 of 35

SHALL Where a review turn ends with its task still `completed` or `under_review`, the Hub SHALL record a divergence naming the run, the reviewer, the task, the task's status and the run's exit status, and SHALL NOT move the task.

WhyA review that produced no judgement is a positive fact to hold, not something to infer from the absence of a live run; the system does not supply a verdict on the reviewer's behalf.

FR-5# Requirement 5 of 35

SHALL Where the Hub queues a run in response to a review that gave no verdict, that run SHALL be given the same checkout of the work under review that the original review turn was given.

WhyA reviewer fired into its own workspace cannot see the author's unmerged work.

FR-6# Requirement 6 of 35

SHALL The Hub SHALL resolve a reviewer for a task by: (1) the declared reviewer, via the same resolution every review path uses, when it names an open agent that may judge the task; (1b) where a declaration exists and does not resolve, or names an agent that may not judge the task, no substitute, surfacing the declaration and why; (2) with no declaration, the first agent in name order that has a runner, is not running a turn, is not held by a usage-allowance refusal, holds no work as `an-active-task-makes-its-assignee-unavailable-only-while-som` defines, and may judge the task; (3) otherwise, surface that the review could not be staffed, naming the task, leaving the flow's job enabled and scheduled.

WhyA declaration that named someone is a different fact from no declaration: quietly staffing another agent would tell the operator the named one checked the work. An agent may not judge work it completed or recorded evidence for, so the ladder excludes such agents up front rather than staffing a review that is refused on arrival. A reviewer that is merely taken by another selection of the same firing is deferred to the next firing, not surfaced.

FR-30# Requirement 7 of 35

SHALL Where a review turn ends without a verdict, the Hub SHALL answer it through the same ladder: if the reviewer was the task's declared reviewer, surface it and substitute nobody; if it was chosen by availability, resolve again excluding the work's authors (by the same determination the first resolution used), every agent with an unresolved verdict-less review of the task, and the agent that just failed, and queue the review to the agent found or surface the ladder's reason.

WhyOne rule staffs and re-staffs a review, so the two cannot reach different answers. Excluding every reviewer already silent on the attempt terminates against a finite roster, and the surfaced reason names each excluded agent's own reason (completed it, reviewed without a verdict, recorded evidence, worked on it), so it never claims an agent completed work no agent completed.

FR-7# Requirement 8 of 35

SHALL Where a flow fires an agent for a task in `completed`, the turn SHALL be a review turn: the agent works in a detached checkout of the commit under review (the most recent evidence naming a commit where evidence governs the merge, otherwise the tip of the task's branch), and its context names the task and that commit. Where the review cannot be prepared the flow SHALL surface the stated reason and SHALL NOT fire an ordinary turn instead, and a turn that would batch a review entry with a work entry SHALL be refused.

WhyAn ordinary turn places the agent in its own checkout, where unintegrated work does not exist. The guarantee holds over the delivered turn, not only the firing that staged it, because one turn can carry several firings' input.

FR-8# Requirement 9 of 35

SHALL A firing of a flow MAY start several tasks, and SHALL start only tasks whose dependencies are met and for which an agent resolved, with at most one task per agent per firing. The number started SHALL be bounded only by the graph and the agents available, never by a configured limit.

WhyParallelism is decided at spec time by decomposing into independent work, not by a dial. A task left unstaffed because the free agents were already selected keeps its status and assignee and is reconsidered next firing; that deferral is recorded but not surfaced, since nothing needs doing.

FR-9# Requirement 10 of 35

SHALL The Hub SHALL keep one checkpoint lineage per flow, shared by every agent the flow fires, and each checkpoint SHALL record the agent whose conversation it summarises.

WhyA firing that is not a review is briefed with the flow's most recent checkpoint regardless of which agent wrote it.

FR-10# Requirement 11 of 35

SHALL Every firing's briefing SHALL lead with whether the agent works inside a flow or a loop and SHALL tell it to finish the given task and stop; only a flow's briefing SHALL state that finished work is offered for review by another agent.

WhyAn agent in a flow did not choose to be there; routing is the flow's job. Telling a loop's agent that someone reviews its work would be false. The statement precedes the prior checkpoint so truncation of a long checkpoint cannot remove it.

FR-11# Requirement 12 of 35

SHALL Where a flow staffs a review, the firing SHALL only queue the review turn; the move to `under_review` and the reviewer as holder SHALL be recorded by that turn's dispatch. A task with a review turn waiting for any agent, or already held by a reviewer, SHALL NOT be offered for review again. Where the waiting turn's last delivery was refused, the firing SHALL surface the task with the agent and the refusal's sentence and staff no other review; once the turn is given up on or withdrawn, the task returns to the pool on the next firing.

WhyStaging the review at the dispatch, under its rollback, means a refused dispatch leaves the task exactly as it was instead of held by a reviewer that never ran. A task held by a reviewer stays visible as the flow's current work, naming that reviewer, for as long as it is held.

FR-12# Requirement 13 of 35

SHALL A review turn's context and the flow's review briefing SHALL both name `approved` and `revision_needed` as the two verdicts, legal from `under_review`, recorded with `update_task`. Where a requirement the task serves has only rejected evidence, both SHALL say `approved` will be refused for it and that `revision_needed` returns the task to its author.

WhyMeasured: with no stated way to end a correct review, no flow-dispatched reviewer had ever recorded a verdict. The rejected-requirement remedy is the author's, so a reviewer not told this approves into a refusal it cannot clear.

FR-13# Requirement 14 of 35

SHALL At the end of a run, inside a loop or flow firing's conversation, that moved a task to `completed`, the Hub SHALL generate a checkpoint carrying the notes the agent recorded for its reviewer, attributed to the loop, without any context-usage threshold or operator action. It SHALL generate nothing where the agent recorded no notes, where checkpointing is off for that agent and project, or where the project has chosen no checkpoint runner, and SHALL NOT substitute another runner.

WhyA firing's conversation reaches neither a usage threshold nor an operator action, so a briefing that depended on either would never be delivered. Generation runs in the background and never fails the finished turn.

FR-14# Requirement 15 of 35

SHALL A review turn's briefing SHALL carry the checkpoint of the conversation whose run completed the task under review, within the same flow, and SHALL fall back to the flow's most recent checkpoint only where that author left none.

WhyWith several agents firing concurrently the most recent checkpoint is usually another task's; the reviewer needs the author's account of this work.

FR-15# Requirement 16 of 35

SHALL A flow SHALL record a staffing outcome naming the task for every task it considers for review and does not staff, as one the operator must resolve rather than as work in flight or deferred. Where nothing was claimable and nothing is in flight, the firing's stall reason SHALL be the first such outcome rather than a count of open tasks by status.

WhyA count of tasks by status describes the queue, not the task the operator can act on. A completed task with no recorded completion is named as such, with reviewing it directly as the way forward, since no firing can give it provenance.

FR-16# Requirement 17 of 35

SHALL A flow SHALL resolve a reviewer through the ordinary ladder for a task whose most recent completion the operator recorded, excluding every agent that has worked the task as `a-completed-task-is-claimable-by-an-agent-that-did-not-compl` determines, and the reason it surfaces when nobody is left SHALL say the excluded agents worked on the task, never that any of them completed it.

WhyThe operator marking work finished is a judgement that it is done, not that it is right; withholding review from it removes the flow's second half exactly where the operator involved themselves, and `completed` offers them no exit back to an agent.

FR-17# Requirement 18 of 35

SHALL Every firing that claims a task for work SHALL name in its briefing the `update_task` calls that finish it, legal from the task's current status, and what a turn that ends with the task unmoved costs. Where the task serves requirements of record the briefing SHALL name them and `record_evidence`; where it serves none it SHALL say nothing about evidence. A flow's briefing SHALL say that notes for the reviewer are delivered only when the task reaches `completed`. For a task returned for revision it SHALL say who sent it back and quote their notes, and, measured when composed, whether the task's branch still merges into the main branch, naming conflicting paths and the remedy; a failed measurement SHALL NOT withhold the briefing.

WhyMeasured: agents call the tool the briefing names, not one listed only in the tool inventory. An instruction to record evidence against a requirement that does not exist is refused when followed. A rework brief that carried only the description sent an author back over a merge conflict to complete the same commit again.

FR-18# Requirement 19 of 35

SHALL A firing staffed as a review SHALL state that the turn is a review, SHALL NOT instruct the agent to do the task's work, SHALL present the task's description and acceptance criteria as the standard the work is checked against, and SHALL identify the loop's message that follows as its standing message delivered on every firing, without telling the agent to disregard it.

WhyA reviewer handed the implementation briefing may re-implement the work and approve its own edit. The loop's message is never rewritten, because it is its author's durable record; it may itself address reviews. At-signs in it are neutralised on delivery as `agent-run-sandboxing` requires of every firing's text.

FR-19# Requirement 20 of 35

SHALL Where a task is `under_review` with an agent named on it and that agent has no turn running or deliverable on it, the flow SHALL surface the review naming the task and the agent and the operator's own remedies, however the task got there and whether or not a run was ever bound to it. Where that agent's input on the task was refused, the sentence SHALL carry the refusal's words. The flow SHALL NOT substitute another agent through this surfacing.

WhyAn operator can move a task into review by hand, leaving no run boundary to diagnose it. Input queued for a third agent is not the named agent reviewing it. Where the named agent produced the work and some turn is on the task, recovery waits for that turn and the task is not described as a review that agent is neglecting.

FR-20# Requirement 21 of 35

SHALL A flow SHALL treat an agent whose queue is held by a refusal of its provider's usage allowance as unable to take a turn: it is not the firing's default agent, not recruited for new work or for review, and a task assigned to it is briefed at most once while held, then reported in flight while input naming the task is queued for it, or surfaced with the refusal's words where that input was refused.

WhyThe scheduler starts no autonomous turn for a held agent, so repeated briefings would only stack identical input for when the hold ends. A declared reviewer is still resolved; its review waits for the hold.

FR-21# Requirement 22 of 35

SHALL A flow SHALL count an agent as holding work only for a task in a live status that belongs to a loop neither ended nor archived (paused counts as live), or on which that agent has a turn running or queued within the project's hop budget, or for which a review turn is queued for it. The firing's busy refusal, the pool of agents a flow may give new work to, and reviewer availability SHALL all use this one definition.

WhyAn assignee is a record of who holds a task, not evidence anything will move it; counting a task nothing will move withdrew its assignee from every flow forever. This changes only staffing, not a task's status, assignee or loop, nor the roster's count of active tasks.

FR-22# Requirement 23 of 35

SHALL Where no reviewer is free, the surfaced reason SHALL name each non-archived agent on the roster with the first applicable reason: excluded from this review (with that agent's own reason), no runner bound, waiting for its provider's usage limit to reset, booked for named tasks (identifier and status, up to three, the rest counted), or running a turn. It SHALL end with the operator's own remedy for the task's status (`completed`: land it to review it yourself, without promising approval; `under_review`: decide it yourself), and SHALL suggest rejecting unwanted tasks only when some agent was booked. It SHALL fit 500 characters, counting rather than omitting agents that do not fit, and name at least one agent where any exists.

WhyA sentence that names nobody leaves the operator unable to see that holdings outside the flow are what starves it. The facts come from the same read that decided availability, and the reason never names pausing, ending or archiving a loop as freeing an agent, since none of them reliably does.

FR-23# Requirement 24 of 35

SHALL Where a review turn ends without a verdict and approving the task is refused for a reason only the operator can remove (evidence awaiting a decision the selected agent may not take, a drift candidate, an unsatisfiable requirement, or the Hub being unable to ask the repository whether the work merges), the Hub SHALL surface the review with that refusal's own remedy and SHALL NOT resolve a second reviewer; later firings SHALL surface the same reason and SHALL NOT suggest asking the same reviewer again.

WhyA second reviewer meets the identical refusal, and a reason about staffing sends the operator to the roster where nothing they change moves the task. Where the agent the ladder selects may itself decide the evidence, or the only refusal is the author's to repair, the review is re-staffed as usual.

FR-24# Requirement 25 of 35

SHALL Where the app shows an approved change document, it SHALL show the unarchived flow that declares it, ended or not, and let the operator open it; when none exists it SHALL offer Start a flow, asking for name, agent, message, schedule (default every 5 minutes) and stop condition (default when the queue empties), saying the first firing is at the next schedule tick, and SHALL refuse to send with no stop condition.

WhyThe offer is never shown for a document that is not an approved change document. After a flow is started the document names it without being reopened.

FR-25# Requirement 26 of 35

SHALL When the operator approves a change document whose delivery is a flow, the Hub SHALL create a flow declaring that document, named after it, using the delivery's agent (or the agent the operator chose at approval), stop condition and schedule, owning the approval's tasks, first firing at the next tick, and SHALL report the outcome in the approval. It SHALL NOT create one where an unarchived flow already declares the document (reporting that flow and whether it is running, disabled or ended), where the agent is archived or not on the project, where no stop condition is set or the stop time has passed, or where the flow would own no open task; the document is approved and its board created regardless.

WhyThe operator is the actor, so creation does not depend on the project letting agents create scheduled work. A flow whose queue was never filled fires every tick and never stops. An agent chosen at approval applies to the flow only and never edits the document.

FR-26# Requirement 27 of 35

SHALL Where an agent bound to a `copilot` runner is given a review turn and its configuration lists Copilot review agents (`code-review`, `security-review`, `rubber-duck`), the review context SHALL name them with the exact `task` dispatch Copilot accepts, the changes from the merge base with the main branch to the commit under review (or the commit's own changes where no base is found), how to retry when the model is unavailable, and that the verdict remains the reviewer's to record with `update_task`.

WhyA Copilot review agent is a tool the reviewer may use, not a reviewer. The setting is off by default (each consult is billed), offered only for `copilot` agents, refused on write for an unknown name, and filtered to the offered list on read. A missing merge base narrows the bullet but never prevents the review.

FR-27# Requirement 28 of 35

SHALL Where a Copilot review turn's context named review agents, the run's stream SHALL record at the end of the turn, as a status event visible with diagnostics hidden, which Copilot subagents ran (with outcome and model), and which named agents did not run, including that none ran.

WhyA reviewer can claim a consultation that never happened; the Hub states what ran beside the reviewer's prose without judging it. Building the report never fails the turn.

FR-28# Requirement 29 of 35

SHALL Where the project has checks that apply to the work approval would merge, both review channels SHALL state the task's check result: passed; failed, naming the failing checks with the last output, that `approved` will be refused and that `revision_needed` with that output returns the task; could not run; or not finished (running, stale or not yet run), with `approved` refused until they pass. Where no check applies they SHALL say nothing about checks.

WhyThe reviewer reads what is recorded and starts nothing; a briefing never fails over reading checks.

FR-29# Requirement 30 of 35

SHALL A change document's delivery MAY name a default reviewer, which SHALL count as the declaration for every task whose own entry names none: resolved by the declared-reviewer rule, surfaced and never substituted when it is not an open agent, and overridden by a task's own reviewer. For a flow delivery not yet approved, the app SHALL state who reviews (the default by name, or any free agent) and flag a default that is not an open agent.

WhyA planner promised a reviewer in prose with no field naming it, and the flow gave the review to whichever free agent sorted first.

FR-31# Requirement 31 of 35

SHALL A flow SHALL NOT staff a read-only agent with a task's work, whether as the firing's default agent or from the pool, and SHALL still allow it to be resolved as a reviewer.

WhyThe dispatch refuses a read-only agent's work turn, so staffing one stages a step that cannot start; reviewing is what a read-only agent is for.

FR-32# Requirement 32 of 35

SHALL Where a flow's next work task is assigned to an archived agent, the firing SHALL surface it naming the task and the agent, with unarchiving or reassigning as the remedy, and SHALL change neither the task nor the agent.

WhyAn archived agent's turn is refused, so selecting the task for it only produces a refused turn and a loop that says nothing.

FR-33# Requirement 33 of 35

SHALL A review a flow could not staff SHALL be persisted and broadcast as a `review_unstaffed` event naming the job, loop, task and reason, and SHALL be emitted again for the same task only when its reason changes. Emitting it SHALL NOT disable, unschedule or stop the flow.

WhyEvery remedy (adding or freeing an agent, fixing a name) is something the next firing should pick up by itself; repeating an unchanged sentence every tick buries the events that carry news.

FR-34# Requirement 34 of 35

SHALL Where evidence that governs the task's merge is awaiting a decision, both review channels SHALL name each awaiting evidence id, its requirement and commit, and say `approved` can be refused until it is accepted; they SHALL tell a reviewer granted evidence decisions to accept it with `decide_evidence` first (never its own), and any other reviewer to ask the operator with `ask_user` and not report the task approved until `update_task` succeeds.

WhyMeasured: approvals refused by the evidence gate were reported to peers as approved because neither channel mentioned the gate. Where evidence does not govern the merge, nothing is said.

FR-35# Requirement 35 of 35

SHALL Where the task under review depends on other tasks, both review channels SHALL name each prerequisite and whether it has merged (with its merge commit) or not, and say that merged work is on the main branch and not in this task's diff.

WhyA reviewer judging the diff alone sent correct work back for missing tests that belonged to its already-merged prerequisite.

Design

D1 — A flow is a loop with `spec_document_id` set. No separate table or job kind; the scheduler branches on that column (`scheduler.decide_firing`, `_agents_a_loop_may_staff`).

D2 — One walk decides a firing. `decide_firing` walks the queue once, in `_loop_queue_order`, and returns selections, in-flight rows, unstaffed and deferred outcomes. The firing and the board both read it, so they cannot disagree about what a flow is doing.

D3 — Refuse to offer, permit to act. Claimability withholds work whose author cannot be ruled out; the transition guards permit when attribution is unknown. Each is the safe direction for its job, and both call the same attribution functions (`task_transition_service.completion_attribution`, `agents_that_may_have_authored`, `agents_that_recorded_evidence_for`).

D4 — The reviewer ladder is one function (`scheduler.resolve_reviewer`) used for first staffing and for re-staffing after a silent review (`run_divergence._answer_failed_review`). Declared names are never substituted; `exclude` carries a per-agent reason so the surfaced sentence is true for every excluded agent; `unavailable` (taken by this firing) yields `deferred`, which is never surfaced.

D5 — Availability is one read (`_roster_availability`) from which both the pool and the unstaffed sentence are derived, so the sentence cannot name an agent the resolution counted free.

D6 — A flow's review is staged at the dispatch, not the firing. The firing queues a review entry; the dispatch moves `completed -> under_review` and sets the holder under its own rollback. A waiting review entry is what keeps the task out of the pool meanwhile.

D7 — Width has no setting: a firing starts every ready task an agent resolves for, one task per agent per firing.

D8 — Briefings state the contract. Agents follow what the briefing names over the tool inventory, so the briefing names the finishing call, the verdicts, and the gates that can refuse them; the two review channels (loop briefing, turn context) share their gate sentences through `review_turn.verdict_evidence_sentence` so they cannot disagree.
