Summary

The adapters through which an agent reaches the capability plane: the Hub's own MCP tool server and the `aw-tool` call command, which are one pinned program. This capability covers how that program is given to a run and told the Hub's address, how a run without MCP is told to use `aw-tool` and how the command carries the run's authority, how tools are typed and described, how failures reach the agent, the record of how each run reached the Hub, and the shape of individual tools (messages, scheduled work, agent requests, document renaming). The contract the tools call is agent-capability-plane.

Problem

An agent knows only what its tools' names, schemas and descriptions tell it. A tool that is mis-described, untyped, unreachable from the agent's harness, or served from a different program than the Hub loaded fails in ways the agent cannot diagnose.

Scope

In scope

  • The MCP server and `aw-tool`: how they are pinned, spawned, put on PATH and told the Hub's address, and Copilot's tool naming and timeout.
  • The `aw-tool` notice for a run whose harness cannot use MCP, and how the command takes the run's credential and arguments.
  • Tool schemas and descriptions, including each tool's description rendered into the context, and which tools are described.
  • How tool failures are reported.
  • Recording which surface a run was told and whether its harness started the tool server.
  • Tool-level rules for messages held by the hop budget, scheduled work, agent requests and document renaming.

Non-goals

  • The HTTP contract, authentication and attribution: agent-capability-plane.
  • The state a turn is given and the tool names its context states: agent-context-onboarding.
  • Which tool surface a runner gets by default: runner-registry.
  • `create_flow` versus `create_loop`: agent-flows.
  • Permission postures and approving a run's own tool calls: agent-run-sandboxing.

Requirements

FR-14# Requirement 1 of 23

SHALL A tool that brings a new agent into existence SHALL be bounded by the project's agent budget, counted over the project's own agents. A tool that creates, enables, triggers or archives scheduled work SHALL be refused while the operator has not turned on the project's `allow_agent_jobs` setting, and archiving SHALL additionally need the operator's direction for that job.

WhyEach new agent or recurring job commits spend the operator did not authorise per occurrence.

FR-15# Requirement 2 of 23

MUST The tool server and call command MUST take identity only from the run credential the Hub placed in their environment, MUST refuse every effect when it is absent rather than fall back to a placeholder identity, and a credential SHALL be honoured only by the Hub instance that issued it.

WhyAn agent must not be able to cause an effect attributed to another agent, and an environment variable naming an agent proves nothing without a live credential.

FR-16# Requirement 3 of 23

SHALL The Hub SHALL give each run whose tool surface is MCP exactly one tool server, its own, configured on the run's command line with no operator wiring, and the build SHALL verify the surface by spawning the server as the Hub does, from a directory other than the package root, and comparing the tools it advertises over stdio with the imported module's; any difference SHALL fail.

WhyImporting the module runs the whole file while spawning it stops at the entry-point guard, so a tool defined below the guard is visible to every test and to no agent.

FR-17# Requirement 4 of 23

SHALL The Hub SHALL give each run, as `HUB_URL`, the operator's explicit `HUB_URL` if set, else the loopback address on the port the Hub has observed itself serving, and SHALL refuse to start the run (409, retried later) when it has neither, never a configured default or assumed port.

WhyA guessed address can be a different Hub, typically the operator's real one, where the run's credential is unknown.

FR-18# Requirement 5 of 23

SHALL A failed tool call SHALL be reported to the agent distinguishing a Hub rejection (with status, the method and path called, and the Hub's sentence) from an unreachable Hub (with the address tried), and SHALL be recorded on the agent's timeline where the Hub observes it.

WhyA call delivered to the wrong Hub is diagnosable only if the report names where it went.

FR-20# Requirement 6 of 23

MUST Where a tool parameter accepts only certain values, its published schema SHALL declare them as an enum restated from the Hub's own validator, with a test holding the two equal; a rejection SHALL reach the agent as a sentence naming the field and what is accepted, never the validator's raw error structure.

WhyAn agent must not discover a constraint by being rejected, and a raw validation dump is not something a model can act on.

FR-21# Requirement 7 of 23

SHALL A tool that serves the runtime (`approve_tool_call`) SHALL NOT be described to the agent or callable through the call command, though it is served on the same MCP server; every other served tool SHALL be described in the standing surface unless recorded as a deliberate omission with its reason (today only `submit_checkpoint_notes`, described in the checkpoint prompt).

WhyThe described surface tells an agent what it can deliberately use; a silently incomplete one is believed.

FR-22# Requirement 8 of 23

SHALL The tool surface SHALL include `rename_spec_document(path, subject)`, which derives the new path from the subject, takes no destination path, returns the new and previous paths, and appears in the described surface.

WhyThe agent learns a document's subject first; taking a path would let the least trusted caller choose where a write lands.

FR-23# Requirement 9 of 23

MUST The `send_message` description SHALL describe the delivery rule the Hub enforces: omitting `conversation_id` continues the thread bound between sender and recipient or starts one if none is bound; a new thread is started only by `start_new_thread` or by checkpoint cutover; and a send to an archived conversation fails returning the content. It MUST NOT describe a rule the Hub no longer applies.

WhyThe tool schema is the agent's only documentation of the surface, and a stale rule is acted on.

FR-24# Requirement 10 of 23

SHALL Every object or array parameter of a tool SHALL declare that type in the schema clients receive.

WhyA client can only shape a call it can see; the operator chose the advertised schema over a hand-written refusal that needed untyped parameters to fire (2026-08-25).

FR-27# Requirement 11 of 23

SHALL The Hub SHALL give every run a copy of the tool server it read at start, held under `~/.agentweave/hub/tool-server/<digest>/` in a directory only the Hub's user can write, rewriting the copy if it is missing or altered, and SHALL refuse the run naming the failure if it cannot, never falling back to the source file. A copy no Hub has touched for 7 days MAY be pruned, never the current one.

WhyRoutes are fixed at Hub start; a server read later can call routes the Hub lacks, and a half-written edit reaches running agents as a server that fails to start.

FR-28# Requirement 12 of 23

SHALL When a sent message is queued past the project's hop budget, the send SHALL still succeed with the message id, and SHALL add `held_by_hop_budget` and a note naming the depth and budget, that the recipient receives it only if the operator continues the chain or raises the budget, that resending queues it at the same depth, and that it must not be reported delivered. A send within budget SHALL be answered as usual.

WhyThe sender reads only the answer to its send; answered like an ordinary send, a held message silently stops a chain of work.

FR-29# Requirement 13 of 23

SHALL `request_agent` SHALL name as template an open agent of the same project with a bound runner, and create the new agent with that agent's runner, charter and runner configuration, but without its grants, default posture, `hub_client` declaration, description, per-agent overrides or wait override; a template that does not exist SHALL be refused naming the open agents, and one archived or with no runner SHALL be refused saying so.

WhyThe operator approves a kind of agent by creating one; an agent must not create a second holder of a grant the operator gave to one.

FR-30# Requirement 14 of 23

SHALL The Hub SHALL configure its MCP server for a Copilot run with a tool-call timeout (660 s) longer than the longest wait any tool can make, and SHALL name the tools to a Copilot run as `agentweave-<tool>`.

WhyCopilot ends an MCP call after 30 s unless told otherwise, which would cut off every answer the operator took longer to write.

FR-31# Requirement 15 of 23

SHALL The Hub SHALL put an `aw-tool` command first on the `PATH` of every run, as both `aw-tool.cmd` and a POSIX `aw-tool`, each running the pinned tool server with `-I -S --call` and nothing in between; call mode SHALL NOT import the MCP library.

WhyThe command must be the pinned program for the same reason the server is; it is not named `aw` because that is the application's own CLI; `-I -S` stops environment variables or site packages changing what an auto-approved command runs.

FR-32# Requirement 16 of 23

SHALL When a run is told the call command, its canonical context SHALL render every operation in the `aw-tool` form from the same operation descriptions the MCP rendering uses, SHALL state once that an operation named elsewhere by its short name is called through `aw-tool`, and SHALL state how long `ask_user` waits and that `archive_job` waits for direction.

WhyOperations are named by short name throughout a turn; one stated rule maps them all, and a run must give a waiting command a longer timeout than its shell's default.

FR-33# Requirement 17 of 23

MUST `aw-tool --help <tool>` MUST print that tool's complete description with its parameters, and a name that is not a callable tool is refused as a usage error naming it; `aw-tool --list` prints each tool's parameters and only the first line of its description. The call-command notice SHALL say which of the two shows the whole description.

Why`--list` cut descriptions to one line, hiding the fields an agent needed.

FR-34# Requirement 18 of 23

SHALL Every `aw-tool` invocation SHALL print exactly one JSON object as its last line, `{"ok": true, "result": ...}` or `{"ok": false, "error": {"kind", "detail"}}` with kind `rejected`, `unreachable`, `unbound`, `usage` or `internal` and a matching exit code, SHALL refuse an unknown argument naming the accepted ones, and SHALL never print a traceback; an internal failure SHALL say the outcome is unknown and how to check before retrying.

WhyThe envelope is the whole contract a shell caller has; a traceback or mixed output cannot be parsed reliably across shells.

FR-35# Requirement 19 of 23

SHALL The tool server SHALL refuse to start, and the call command SHALL refuse every call, when `HUB_URL` is unset, and neither SHALL fall back to a default address.

WhyThe one address a guess lands on is the operator's own Hub.

FR-36# Requirement 20 of 23

SHALL A turn that is not told the MCP tools SHALL be told, in a notice prepended to the turn prompt, that the capability plane is reached through the `aw-tool` command, how an operation is called with it (arguments in a `.json` file under `.agentweave/calls/`), and how to list and describe the operations, and SHALL NOT be told to place the run credential in any command it writes.

WhyCapability that exists but is never described is not capability; and a command that carries the credential puts it into text the harness records.

FR-37# Requirement 21 of 23

SHALL The call command SHALL read the run's credential and the Hub's address only from its own process environment, SHALL NOT accept either as an argument or from a file, and SHALL take an operation's arguments only from a `.json` file inside the workspace's `.agentweave/calls/` directory.

WhyA command that carries its credential puts it into text the harness records; a command naming only an operation and a file holds no secret.

FR-38# Requirement 22 of 23

SHALL The Hub SHALL record for each run which surface it was told to reach the Hub through and whether its harness started the Hub's tool server, and when a run given the server did not start it, SHALL say so once in that run's activity, naming the surface that run was told and quoting the harness's own account where it gives one.

WhyA machine that blocks tool-protocol servers otherwise shows only as runs that behave differently; the statement must describe what that run was told, not what the next one will be.

FR-39# Requirement 23 of 23

SHALL The context SHALL describe every tool the agent can call, with each parameter and the accepted values of a constrained one, derived from the same source as the tool definitions and written in the idiom of the run's access path.

WhyA tool never mentioned cannot be used deliberately, and a description kept separately from the definitions drifts.

Design

D1 One program, two modes. `hub/hub/mcp_server.py` is the MCP server and, with `--call`, the `aw-tool` command. Call mode is decided before the fastmcp import and every tool registered with `_tool()` is callable through it (`_CALLABLE_TOOLS`). The file imports only stdlib and fastmcp; constrained values are restated as `Literal`s and tests (test_mcp_tool_schemas.py) hold them equal to the Hub's validators.

D2 The Hub pins the program at start (hub/hub/tool_server.py): a digest-named copy under the user's home, 0700, with `aw-tool`/`aw-tool.cmd` launchers keyed by interpreter, prepended to every run's PATH. An edit reaches agents on the Hub's next restart, never mid-run.

D3 One description of the operations (`_operations` in hub/hub/api/v1/agents.py) is rendered as MCP names, as `aw-tool` calls, or (tests only) as HTTP. `UNDESCRIBED_TOOLS` records each deliberate omission; test_tool_surface_matches_server.py fails on any other difference.

D4 Waiting tools poll contract routes with Hub-stamped deadlines; per-agent waits arrive as environment variables, bounded 10-600 s, else defaults (120 s decisions, 240 s questions). Copilot's MCP timeout (660 s) exceeds the longest wait.

D5 The adapter never guesses: no `HUB_URL` means no server and no call; no credential means no effect.

  • hub/tests/test_hop_budget_bound.py, test_request_agent_models_an_existing_agent.py, test_agent_trigger.py (bound address)

Limits

  • `send_message`'s description (hub/hub/mcp_server.py:288-295) does not yet say that checkpoint cutover starts a new thread; the requirement is kept and this is reported as a finding.
  • The loop/flow refusals are enforced in the adapter only (hub/hub/mcp_server.py:822-940); the HTTP route accepts a loop with no stop condition (see agent-capability-plane).
  • Many criteria still carry an empty GIVEN from the openspec import.
