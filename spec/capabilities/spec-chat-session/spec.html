Spec chat session

capabilitycurrentsketch

11 MUST·11 requirements·27 criteria

Summary

Working on a specification document from inside an agent conversation: the conversation surface is the one composer every conversation uses, a specification document opens in a tab beside it, the document the operator has attached travels with each message as turn context (never as message text), and the operator starts an exploration by creating an empty document from the composer. Continuity, new conversations and the composer itself belong to `agent-conversation-workspace`; the panel shell's tabs and resizing belong to `conversation-side-panel`; phases, payloads and authoring rules belong to `spec-document-authority`.

Problem

An operator authoring or reading a specification needs the agent working with them to know which document they mean and what phase it is in, and needs to answer the agent's questions and permission requests while doing so. A separate specification chat surface could not show those cards and duplicated the composer, so this capability defines the specification work as a property of the ordinary conversation surface.

Scope

In scope

  • The conversation surface used while a specification document is attached or open
  • The `spec_document` carried by a trigger and how it reaches the turn context
  • Attaching, detaching and reading specification documents beside a conversation
  • Starting an exploration from the composer or the new-conversation surface

Non-goals

  • The project-level Spec page (`spec` project tab) and the corpus navigation it hosts
  • Phase transitions, payload validation and authoring obligations (spec-document-authority)
  • The panel shell's tab strip, persistence and resize rules (conversation-side-panel)

Requirements

FR-1# Requirement 1 of 11

MUST A conversation with a specification document attached or open SHALL use the same composer, banner stack and conversation transcript as any other agent conversation, and MUST NOT provide its own message input, run trigger, output rendering or agent selector.

WhyThe authoring flow depends on the agent being able to ask the operator questions and request permissions; only the shared surface renders those cards. The agent is whichever conversation the operator is in, so a second agent picker would contradict navigation.

FR-2# Requirement 2 of 11

MUST Specification work SHALL happen in the conversation the destination names; a message sent with no conversation named SHALL create an ordinary conversation with origin `operator`, and the Hub MUST NOT create a conversation with the `spec` origin.

WhyA thread's relationship to a document is the attachment the operator makes, not a category the thread was born into. The `spec` origin value is accepted by the schema but has no defined scope, so nothing produces it.

FR-3# Requirement 3 of 11

MUST When a turn is triggered with a specification document attached, the Hub SHALL name that document in the canonical turn context, with its phase and that phase's obligation, and MUST NOT add it to the stored operator message; when no document is attached, or the path names no document in this project, the context SHALL name none.

WhyThe message is the durable record of what the operator said; turn context is rebuilt each turn and read identically by every runner. A path that resolves to nothing is a stale client value, and naming it would be a guess. The phase statement is code-owned so that it holds with no charter bound.

FR-4# Requirement 4 of 11

MUST The attached specification document SHALL open in a tab of the panel shell beside the conversation, SHALL be part of the conversation's URL destination so a reload restores it, and closing its tab MUST NOT detach it; only the composer's own detach control detaches it, and detaching MUST NOT delete the document.

WhyTidying the reading pane is not an edit to what the agent is working against: the attachment decides the next turn's context and restricts the agent's file writes. An exploration leaves an artifact, so a detach that discarded it would be a trap.

FR-5# Requirement 5 of 11

SHALL Every control the conversation surface presents SHALL stay within its container at every width the surface can be shown at, wrapping rather than being removed or clipped, and no two interactive elements SHALL overlap.

WhyThe surface is shown beside a document in a pane narrower than a full-width conversation; the permission control in particular must remain readable before sending. The check is geometric, not presence in the DOM.

FR-6# Requirement 6 of 11

MUST The operator SHALL be able to start an exploration from the composer with one action that creates an empty `exploring` document under a Hub-minted placeholder path and attaches it to the conversation; the Hub MUST NOT infer an exploration from conversation content.

WhyAn exploration is declared, not detected. Creating the document up front gives later propose and approve actions a subject, and the Hub mints the path because nobody yet knows the subject; the agent renames it once the interview settles it.

FR-7# Requirement 7 of 11

SHALL When a new conversation is started with an exploration armed, the document SHALL be created before the first turn is triggered and sent with it, and if the trigger is refused or fails the client SHALL delete that document.

WhyThe first message decides how the agent frames the exploration, so it must already carry the document; a refused send must not leave an empty placeholder behind on each retry.

FR-8# Requirement 8 of 11

SHALL When the attached document is an `exploring` document with no requirements yet, the turn context SHALL tell the agent that this document is the one it is interviewing for and that it must submit to that path rather than create another document.

WhyThe general framing — an open document is context, not an instruction — is wrong for a freshly started exploration, and following it produced a second, orphaned document every time.

FR-9# Requirement 9 of 11

SHALL The trigger SHALL validate `spec_document` against the specification path contract, refusing an unsafe path, SHALL treat an empty string as no document, and SHALL store the document on the queued entry so a message delivered later still carries it.

WhyOne definition of a legal specification path serves both writes and reads, and a queued message must not lose the context the operator sent it with.

FR-10# Requirement 10 of 11

SHALL The attached document SHALL stay attached when the operator moves to another agent or conversation in the same project, SHALL stay detached when they move with none attached, SHALL survive a round trip through agent settings, and SHALL NOT be carried in from a project-level page.

WhyA document is what the operator is working on, not a property of the thread; but arriving from project-level work should open nothing, because the memory is of what is on screen.

FR-11# Requirement 11 of 11

SHALL Opening a document from the panel's specification index for reading SHALL NOT change which document is attached to the conversation, and more than one document MAY be open for reading at once.

WhyReading a document and directing the agent at it are different acts; only attaching changes what the next turn is written against.

Design

D1 One surface. Specification work is a property of the ordinary conversation, not a screen: a separate chat could not render question, permission or checkpoint cards, and the authoring flow needs all three.

D2 Document as turn context. The attached document travels as `spec_document` on the trigger, is stored on the queued entry, and is rendered into the turn context (plus a turn-start notice, owned by spec-document-authority). It is never written into the operator's message, which is the durable record of what they said.

D3 Attachment lives in the URL. The attached document is part of the conversation destination, so reload and links restore it, and it follows the operator across agents in a project. Reading tabs are separate from the attachment; closing a tab never detaches.

D4 Exploration is declared. One press creates an empty `exploring` document under a Hub-minted placeholder name and attaches it; the agent renames it once the subject is known. A refused first send withdraws the document it created.
