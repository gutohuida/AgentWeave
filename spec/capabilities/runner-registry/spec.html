Summary

Runners are project-scoped Hub records naming which CLI (`claude`, `codex` or `copilot`) and which model an agent launches with. An agent is bound to at most one runner, and that runner is the single source for what a run launches, which transport and tool surface it gets, and what launchability reports; an agent with none says so. Each supported CLI is served by one runner adapter, and a Copilot runner may send its model to an operator-chosen provider with a key held in the Hub's own environment.

Problem

When execution capability lived inside agent identity, the probe and the spawn could disagree about the same agent, a missing binding fell back to a binary named after the agent, and every CLI difference was a name comparison scattered through the Hub.

Scope

In scope

  • The `runners` table, its routes (`/api/v1/runners`, `/runners/launchability`, `/runners/launchability-by-provider`) and the Runners settings page
  • Binding an agent to a runner, and what that binding decides at trigger and probe time, including an agent with no runner
  • The runner adapters (`hub/hub/runner_adapters/`) as the single place CLI differences live
  • Transport selection, and the tool surface, approval channel and plane access resolved for each run
  • Copilot runner specifics: executable resolution, minimum version, failure recording, launchability, and the operator model provider

Non-goals

  • Which models and controls each provider offers (model-catalog)
  • What a permission posture permits a run to do, and scrubbing a provider key from a run's output (agent-run-sandboxing)
  • Whether a launchable runner can also collaborate through the Hub's tools, and pre-spawn refusals (runtime-diagnostics)
  • What a run is told about how it reaches the Hub (agent-tool-surface)
  • Holding an agent's queue when its provider allowance or Copilot quota is spent (provider-allowance-holds)
  • OpenCode, Kimi and other legacy runner strings: no runner record can name them

Requirements

FR-7# Requirement 1 of 29

SHALL The Hub SHALL persist each runner as a project-scoped database row naming a supported CLI (`claude`, `codex` or `copilot`), a non-blank name, optional flags, an optional model and an optional model provider, and SHALL enforce the supported CLI set identically in the request schema and in the database constraint.

WhyA CLI the schema admits but the database refuses surfaces as a false 409 "already exists"; deriving both from one tuple keeps them from drifting.

FR-8# Requirement 2 of 29

SHALL The Hub SHALL create one default runner per supported CLI, named "<Cli> (default)" with no model, when a project is registered and, at startup, for any project that has no runner, and SHALL create none for a project that already has one.

WhyA new project can bind an agent immediately, and an operator who deleted defaults in favour of their own runners does not get them back.

FR-9# Requirement 3 of 29

SHALL Each agent SHALL reference at most one runner, a triggered run SHALL launch the CLI, flags and model of the bound runner, and triggering an agent with no runner bound SHALL be refused with 409 and the sentence "No runner is bound to this agent. Bind one in the Hub UI before it can run." rather than fall back to any default.

WhyA silent default would launch something the operator never chose; the refusal says what to fix.

FR-10# Requirement 4 of 29

SHALL The Hub UI SHALL provide a Runners page to list, create, edit and delete runners (name, CLI, model, model provider), and SHALL let the operator bind an agent to a runner from the agent's configuration.

WhyRunners are operator-managed records; the app is the way to manage them.

FR-11# Requirement 5 of 29

SHALL A runner's model SHALL be one the catalog declares for its CLI (an identifier or an alias, stored as written) or unset (the provider's default), offered as a selection rather than free text, and the Hub SHALL refuse with 400 a request that newly sets a model the catalog does not declare.

WhyA free-typed model is refused at spawn or silently replaced by the provider; a selection makes the valid choices the only ones.

FR-24# Requirement 6 of 29

SHALL A runner edit SHALL distinguish an explicit null model (clear it to the provider's default) from an absent model field (leave it unchanged), and SHALL accept a request carrying the model the runner already records even when the catalog no longer declares it.

WhyA picker sends the stored model back on every save; refusing it would make a legacy runner uneditable in every other respect.

FR-25# Requirement 7 of 29

SHALL A runner whose recorded model the catalog does not declare SHALL be reported with `model_unrecognised: true`, marked as unrecognised in the runner list, and offered that model still selected when edited, so that saving it unchanged keeps it.

WhyOpening a runner for editing must not silently re-point it at a different model, and runners needing attention should be visible without opening each one.

FR-12# Requirement 8 of 29

SHALL Wherever the operator chooses a model for a provider, the interface SHALL offer each declared alias as its own choice labelled "<alias> — latest (now <label of the model it stands for>)".

WhyChoosing an alias and choosing the identifier it stands for behave the same today and differently after the provider moves the alias; the label makes that difference readable.

FR-13# Requirement 9 of 29

SHALL When the Hub refuses a runner create, edit or delete, runner management SHALL show the refusal's own sentence, and a refused create or edit SHALL leave the dialog open with the operator's input intact.

WhyA refusal that reaches no surface is indistinguishable from a button that does nothing.

FR-14# Requirement 10 of 29

MAY A runner's flags MAY carry a transport sentinel declared by its CLI's adapter, which SHALL select how the Hub starts the run and SHALL NOT be passed to the CLI; a runner with no sentinel SHALL get its CLI's default transport, the one whose tool surface the agent can call.

WhyCodex runs over its app-server by default; its exec transport is degraded and must be opted into explicitly. Sentinels are the union of every adapter's declared set.

FR-15# Requirement 11 of 29

SHALL An agent's launchability SHALL be derived from its bound runner whenever one is bound, so that the probe and the spawn cannot disagree, and `GET /agents/launchability` SHALL report the same agents the roster lists for the same `lifecycle` selector (default `open`).

WhyReporting an archived agent as runnable, or an unbound one as needing a binary named after itself, is the probe contradicting the trigger one call later.

FR-26# Requirement 12 of 29

SHALL The Hub SHALL report launchability per runner (`GET /runners/launchability`) and per supported CLI before any runner exists (`GET /runners/launchability-by-provider`).

WhyRunner management and agent creation must show whether a choice can run before the operator commits to it.

FR-16# Requirement 13 of 29

SHALL Deleting a runner that no open agent holds SHALL succeed and clear the runner from every archived agent that held it, and deleting a runner an open agent holds SHALL be refused with 409 naming those agents.

WhyAn archived agent runs nothing, so its binding should not keep a runner undeletable; the agent and its history stay.

FR-17# Requirement 14 of 29

SHALL Wherever the operator chooses a runner from a list, each choice SHALL read "<name> — <model> (<cli>)", where the model is the catalog label, "Provider default" when unset, "<alias> (latest)" for an alias, or "<id> (unrecognised)" when undeclared; the model part SHALL be omitted when the name already ends with it, and a setting that overrides the model for that use (the checkpoint model) SHALL be named instead of the runner's own.

WhyRunners of one provider may share a name and differ only in model, and the model is what the choice decides.

FR-22# Requirement 15 of 29

SHALL The Hub SHALL decide everything that differs between runner CLIs (launch and transport, event parsing, usage and context reading, tool-server and context injection, posture, launchability, one-shot invocation, catalog provider) through one adapter per supported CLI, and the adapters, the CLIs a runner may name, the database's accepted set and the catalog's providers SHALL be the same set.

WhyAdding a CLI should be adding one adapter; code outside the adapters that branches on a supported CLI's name is where CLIs drift apart. A legacy runner string with no adapter is never spawned through another CLI's adapter.

FR-18# Requirement 16 of 29

SHALL The Hub SHALL spawn Copilot by its native executable, resolved from the runner's pinned executable, then a native `copilot` on PATH, then the platform binary inside the npm package a `copilot` shim on PATH belongs to, and SHALL name the path it looked for when it finds none.

WhyAn npm shim runs a second process in front of the CLI, and stopping the shim can leave the CLI running.

FR-19# Requirement 17 of 29

SHALL The Hub SHALL fail a Copilot turn, before any session is created, when the version the CLI reports in its handshake is missing or below 1.0.81, and SHALL spawn Copilot with `--no-auto-update` so the version checked is the version that runs.

WhyOlder versions lack the session events the Hub depends on; an auto-update could swap in a different version after the check.

FR-20# Requirement 18 of 29

SHALL Once a Copilot turn's prompt is sent, the Hub SHALL record an error answer, process exit, timeout, or a session error for the turn's own agent as the run's failure, keeping what the turn wrote, even when Copilot then reports a normal end (unless the turn was stopped), and SHALL record a subagent's error in the run's timeline without failing the turn.

WhyCopilot can report an error and still say the turn ended normally; a subagent's failure is not the turn's.

FR-27# Requirement 19 of 29

SHALL When a Copilot turn fails to start because the CLI is not signed in or is too old, the Hub SHALL record that verdict for the runner before the input is retried, so the queued input is held rather than retried into the same failure.

WhyAn authentication or version failure cannot succeed on retry; retrying it spent the input's delivery attempts for nothing.

FR-21# Requirement 20 of 29

SHALL The Hub SHALL decide whether a Copilot runner is authorized by a model-free handshake with the Copilot CLI, not from GitHub token variables in its own environment, SHALL report not-signed-in and too-old as not authorized with a reason saying what to do, SHALL re-check such a verdict on its next read, and SHALL NOT refuse agent creation while no verdict has been computed yet.

WhyCopilot keeps its sign-in in the OS credential store; a token variable overrides it rather than proving it exists. Signing in or updating must be seen without waiting for a cached verdict to age.

FR-28# Requirement 21 of 29

SHALL Before its probe and before every Copilot run, the Hub SHALL copy the operator's account record (never a token) from the operator's Copilot home (`$COPILOT_HOME`, else `~/.copilot`) into each Copilot home it owns, and the not-signed-in reason SHALL name the file it read.

Why`copilot login` records the signed-in account only in the operator's own home, and the CLI reads the credential store through that record.

FR-23# Requirement 22 of 29

MAY A `copilot` runner MAY name the model provider `anthropic` with a base URL and the name of a Hub environment variable holding the API key; the Hub SHALL store only the variable's name, SHALL refuse a provider on a `claude` or `codex` runner or of any other type, and SHALL start every process it runs on that runner (agent runs, checkpoints, handovers, titles) against that provider with that key.

WhyThe key stays where the operator already keeps credentials, the Hub's environment; the runner holds only a name.

FR-29# Requirement 23 of 29

SHALL A submitted provider SHALL be refused with 400, storing nothing and never repeating a submitted value, when its key-variable field is not a variable name or names one of the Hub's own credentials, when its address is unencrypted to a host other than the local machine, when an unknown field is present, or when the runner's flags choose a model.

WhyThe likeliest mistake is a pasted key; echoing it would put it in a response body, a log and the browser's history. A Hub credential named as the key would be shipped off the machine.

FR-30# Requirement 24 of 29

SHALL A provider runner's model SHALL be set and SHALL be one of the Claude API model identifiers the catalog declares for `claude` (no alias); a single run SHALL NOT override it; a conversation or checkpoint model recorded before the provider was added SHALL NOT be used; and adding or removing a provider SHALL be refused when the model left behind is not valid for the resulting runner.

WhyThe provider receives the model as is and cannot choose one, and a CLI alias is not an API model.

FR-31# Requirement 25 of 29

SHALL A Copilot run SHALL take provider settings from its runner alone: every Copilot provider variable inherited from the Hub's environment or set in the agent's own environment SHALL be removed, a provider runner SHALL then get only the provider, address, key and model it names, and a runner whose stored provider is damaged SHALL NOT be spawned.

WhyNeither the operator's shell nor an agent's settings may silently move a run onto another account or provider.

FR-32# Requirement 26 of 29

SHALL A provider runner SHALL be reported launchable only when its key variable is set in the Hub's environment, the report naming the variable and not asking for a GitHub sign-in, on every surface that reports launchability; runner management SHALL state that an API key is required and that a subscription sign-in cannot be used.

WhyA provider runner does not use the GitHub subscription, so the sign-in question is the wrong one; a Claude Max plan is not a key.

FR-34# Requirement 27 of 29

SHALL For every run the Hub SHALL resolve three separate values: its tool surface (whether the Hub's MCP server is given), its approval channel (taken from the runner's transport, and withdrawn by removing the tool surface only where that channel is carried by the tool server), and its plane access (MCP exactly when the tool surface is given). A posture naming the Hub as answerer SHALL be the default only where the run has an approval channel, and resolving these values SHALL NOT widen any run's containment.

WhyFor some runners the three move together and for others not; one value standing for all three removed approvals from runs whose approvals never depended on MCP.

FR-35# Requirement 28 of 29

SHALL Where a runner offers more than one way to start a run and only some let the Hub answer approvals per request, the Hub SHALL select an approvable transport by default; a less capable transport SHALL be reachable only by an explicit opt-out flag, and an agent's reported readiness SHALL reflect the transport its next run will use.

WhyAn operator must not need to know a flag or sentinel for a newly created agent's tools to be callable.

FR-36# Requirement 29 of 29

SHALL Where an agent has no bound runner and its synchronised session configuration names none, its launchability and its queued input's waiting reason SHALL state that no runner is bound, and SHALL NOT name a missing executable derived from the agent's own name; an agent whose session configuration names a runner SHALL keep that configuration's verdict, and a bound runner SHALL outrank it.

WhyNaming a binary after the agent sends the operator looking for something that was never supposed to exist.

Behaviour

Resolving the Copilot executable

  1. If the runner pins an executable, use it.
  2. Else, if `copilot` on PATH is a native executable (not a `.cmd`/`.ps1`/`.js` script), use it.
  3. Else, if it is an npm shim, use the platform binary inside the `@github/copilot` package the shim belongs to.
  4. Else report not present, naming the path looked for.

Design

**Three separate records.** Runner (which CLI and model), Agent (identity) and Charter (behaviour) are distinct project-scoped rows; an agent holds at most one `runner_id`.

**The bound runner is the one truth.** `launchability.get_agent_config` overwrites any session-configured runner with the bound `Runner` row, so the probe describes what `agent_trigger` launches; an agent with nothing bound gets `RUNNER_UNBOUND`, never a binary named after it.

**One adapter per CLI.** `runner_adapters.ADAPTERS` = `RUNNER_CLIS` = catalog providers; the database check constraint is generated from `RUNNER_CLIS`. Legacy strings in `launchability.LEGACY_RUNNER_CLI` (kimi, opencode, codex_mcp, claude_proxy) are dead residue reachable only from hand-made legacy payloads. Codex remains a fully supported adapter even though it is no longer driven.

**Model provider on the runner only.** A Copilot runner's `provider_config` is `{type, base_url, api_key_var}`; the key lives in the Hub's environment and only its variable name is stored. Provider settings from anywhere else are stripped.

**Given and told are separate.** What a run is given (tool surface, approval channel, plane access) is resolved by `resolve_access_axes` from the runner's transport; what it is told about its access is decided elsewhere, so neither can move the other. Where a CLI offers several transports, the approvable one is the default and a weaker one is an explicit opt-out.

Evidence and coverage limits

Checked

  • hub/tests/test_runners_api.py, test_runner_charter_models.py — records, CLI set, delete rules.
  • hub/tests/test_launchability.py — bound runner, unbound reason, lifecycle filter.
  • hub/tests/test_runner_adapters_conformance.py, test_no_runner_literals.py — one adapter per CLI.
  • hub/tests/test_copilot_probe.py, test_copilot_acp_run_turn.py, test_copilot_home.py — Copilot executable, version, failures, sign-in.
  • hub/tests/test_runner_provider_config.py, test_copilot_byok_env.py — model provider.
  • hub/ui/src/__tests__/runnersUi.test.tsx, runnerOptionLabel.test.ts, runnerProviderConfig.test.tsx.

Limits

  • Copilot-name branches remain outside the adapters (F476 open), and `test_no_runner_literals.py` scans only `claude`/`codex`.
  • A provider runner has never completed a turn with a valid key (F494 open).
  • The app neither shows nor edits a runner's flags (F469 open).
  • Runner list order is `created_at` only; ties are unordered (F177 open).
