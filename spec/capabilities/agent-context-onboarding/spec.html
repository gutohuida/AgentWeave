Agent context onboarding

capabilitycurrentsketch

12 MUST·12 requirements·20 criteria

Summary

Before every run the Hub renders the model-facing context for an agent from its own records. That context covers the project, where the run executes, the task's specification, the team, quality gates, which capabilities the agent holds and which it does not, the project instructions, the tool surface, and the agent's charter. The Hub delivers it the way the agent's runner needs. The same renderer answers `GET /agents/agent-context` outside any run, and an agent the Hub has no record of gets onboarding context instead.

Problem

An agent that is not told where it is, who its peers are, what its tools accept or what it may not do guesses, and its guesses are refused mid-turn, after the turn has already been spent.

Scope

In scope

  • `_render_hub_agent_context` (`hub/hub/api/v1/agents.py`) and its delivery per run.
  • `GET /agents/agent-context` and `GET /agents/context`.
  • The workspace, task specification, team and capability sections of the context.

Non-goals

  • The exact tool list and per-tool wording (agent-tool-surface), and the access-path notice (agent-capability-plane).
  • Review-turn briefings (agent-flows) and the document the operator has open (spec-chat-session).
  • Charter content itself (agent-charter) and project instructions (project-instructions).

Requirements

FR-12# Requirement 1 of 12

SHALL The Hub SHALL render an agent's context from its current Hub records before every run and deliver it through the runner's mechanism: written to `<run workdir>/.agentweave/context/<agent>.md` and passed to the CLI for Claude and Codex, and for Copilot split into a stable part (written into the agent's Copilot custom agent) and per-turn and tool-surface parts sent with each prompt.

WhyA change to an agent, runner, charter, instructions or quality settings must reach the next run without any regeneration step.

FR-13# Requirement 2 of 12

SHALL The context SHALL name the project and, when the project has at least one other open agent, a Team section listing every open agent by name with its bound runner's CLI, its model and the names (never values) of its environment variables, marking the reading agent's own entry; identity and roster SHALL come from Hub records only, not from `agentweave.yml` or synced session state.

WhyAn agent cannot message a peer it was never told about. Archived agents are left out because sending to one is refused, and a lone agent gets no Team section because naming the absence invites it to wait for someone.

FR-14# Requirement 3 of 12

SHALL The context SHALL be layered as: project profile and per-turn facts (workspace, specification, team, quality gates, capabilities), then project instructions, then the communication mode and tool surface, then the charter, and each section the Hub has nothing for (quality gates, instructions, team) SHALL be omitted rather than rendered empty or with invented defaults.

WhyStable guidance and per-turn facts change at different rates; an empty or placeholder section reads as a fact.

FR-15# Requirement 4 of 12

SHALL `GET /agents/agent-context?agent=<name>` SHALL return the same rendered context with machine-readable fields (`agent`, `known`, `registered`, `charter_id`, `charter_name`, `missing`, `context`, `stable`, `per_turn`, `tool_surface`), where an agent is known exactly when the Hub has a record of it; an unknown agent SHALL get onboarding context telling it to ask the operator to register it, and a known agent SHALL never be told to withhold work, wait for assignment, or report to a principal or `agentweave.yml` declaration.

WhyAn agent the operator created and addressed is one the operator intends to act; a stand-down block once made every Hub-native agent ignore its instructions.

FR-16# Requirement 5 of 12

SHALL `GET /agents/context?charter=<id>` SHALL return that project charter's content, preceded by the project instructions when there are any, with a hint to use the agent-context route for full context, and 404 for a charter of another project or none.

WhyA direct charter lookup is kept for callers that know a charter but not an agent.

FR-18# Requirement 6 of 12

SHALL For a run, the context SHALL state the absolute directory it executes in and whether that is an isolated checkout, naming the branch the process is actually on (the task's branch for a task checkout, the agent's own otherwise) and that peers work in checkouts it cannot see, or the shared project directory, saying so and claiming no isolation.

WhyAn agent uses the branch name to ask what it has already done; told the wrong branch it resolves its history wrongly, and an agent that guesses its directory is refused.

FR-24# Requirement 7 of 12

SHALL In a project whose directory is not a Git repository, the context SHALL say there is no isolated checkout or branch, that git should not be expected to work, and that any other agent works in the same directory where edits can overwrite each other.

WhyLeft unsaid, an agent discovers the missing repository by running git and reads the failure as a broken machine.

FR-19# Requirement 8 of 12

SHALL The context SHALL describe every tool the agent can call, with each parameter and the accepted values of a constrained one, derived from the same source as the tool definitions and written in the idiom of the run's access path.

WhyA tool never mentioned cannot be used deliberately, and a description kept separately from the definitions drifts.

FR-20# Requirement 9 of 12

SHALL The context SHALL NOT direct an agent to read a file whose contents it already carries, including the materialized context file itself.

WhySuch a read is redundant at best and, outside the agent's permitted paths, is refused, turning delivered information into an apparent failure.

FR-21# Requirement 10 of 12

SHALL When a turn is bound to a task that implements a specification document, the context SHALL name that document as what the work implements and say how to read it, SHALL NOT frame the turn as authoring a specification, and SHALL name it once when the operator is also viewing it.

WhyWithout the document path an agent guesses, fails, and falls back to a summary, which is how an implementation stops matching what was approved.

FR-22# Requirement 11 of 12

SHALL The context SHALL state each operator-conferred capability the agent holds: evidence decision (`can_accept_evidence`), reading peers' checkpoints (`can_read_checkpoints`) and recalling cited observations (`can_recall`), naming the tools that use it.

WhyA capability an agent does not know it holds is one it does not use; one it guesses at is a refusal in the middle of a spent turn.

FR-23# Requirement 12 of 12

SHALL For each of those capabilities the agent does not hold, the context SHALL say so and what to do instead: that evidence decisions are the operator's and a verdict belongs in a message or on the task, that only its own checkpoints are listed, and that a not-found from `recall` on a cited id is this boundary rather than a missing record.

WhyA reviewer once spent a whole turn before discovering it could not record its verdict, then wrote it into its isolated worktree where nobody reads it; a not-found is deliberately indistinguishable from absence, so the boundary must be stated up front.

Design

**One renderer, Hub records only.** `_render_hub_agent_context` serves every run and both context routes. Whether an agent is known is `agent_row is not None`; synced session state is read only for quality gates, which have no Hub-native home yet.

**Facts supplied by the trigger.** Working directory, isolation and branch are passed in by `trigger_agent_directly`, which computed them for the process, so the text cannot disagree with where the run actually is. Outside a run (the routes) no workspace is described.

**Parts for Copilot.** Lines are tagged `stable`, `per_turn` or `tool_surface` as they are appended, because a Copilot agent receives the stable part once, in its custom agent file, and the rest with each prompt.

**Both directions of a grant.** Each grant is stated whether held or withheld, because the withheld case is the one that costs a turn.

Evidence and coverage limits

Checked

  • hub/tests/test_agents.py, test_charter_context.py — context routes, known/unknown agents, charter section.
  • hub/tests/test_agent_facing_text.py — tool-surface wording and access-path idioms.
  • hub/tests/test_task_spec_document_context.py — task specification section.
  • hub/tests/test_agent_evidence_grant.py — granted and withheld evidence capability.
  • hub/tests/test_tool_surface_matches_server.py — described tools match the served ones.

Limits

  • `metadata.context_path` reports `.agentweave/context/<agent>.md` relative to the run's working directory, which the route cannot know.
