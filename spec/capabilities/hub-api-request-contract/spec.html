Hub API request contract

capabilitycurrentsketch

5 MUST·5 requirements·12 criteria

Summary

What the Hub's HTTP write surface promises about the request a caller sent: a body field the receiving contract does not declare is refused by name, uniformly; the few contracts that decline the rule say why in the code; legacy vocabularies are translated without swallowing unknown fields; and a test over the routing table catches any route that slips.

Problem

A field silently discarded tells the caller they were understood when they were not. When the field was a supervision posture, the run is already executing unsupervised by the time the response is read (F116).

Scope

In scope

  • Every HTTP request body model (`RequestModel`, `extra="forbid"`)
  • Before-validators that translate legacy field names
  • The declared exemptions and the test that enforces the rule

Non-goals

  • Validation of field values (owned by each route's capability)
  • MCP tool argument handling (agent-tool-surface)

Requirements

FR-1# Requirement 1 of 5

SHALL A write request whose body carries a field its contract does not declare SHALL be refused, and the refusal SHALL name the field, on every route alike.

WhyThe Hub cannot tell a typo from a field that changes behaviour; only the caller can, and only if told. One policy across routes means no route looks safe by accident.

FR-2# Requirement 2 of 5

SHALL A request contract MAY accept undeclared fields only where its own requirement demands it, and SHALL then be listed with its reason among the declared exemptions; a body accepted as an untyped mapping SHALL likewise be listed with its reason and SHALL refuse unknown keys by name itself.

WhyAn exemption without a reason is indistinguishable from the rule never having been applied.

FR-3# Requirement 3 of 5

SHALL A contract that translates a superseded vocabulary before validation SHALL remove every name that vocabulary defines, including names nothing reads any more, and SHALL carry every other field forward to be refused, so that a request carrying two legacy names for one value is accepted and a field outside both vocabularies is refused by name.

WhyA translation that rebuilds the body from the names it knows drops the rest silently, reintroducing the failure inside the mechanism meant to prevent it; one that removes only the name it read refuses a rolling upgrade's second alias.

FR-4# Requirement 4 of 5

SHALL The test suite SHALL derive every write route from the application's routing table and fail when a body model, or any model nested in it, tolerates extra fields, or a route declares no body model, unless it is a listed exemption with a reason.

WhyThe rule fails by omission, so a one-time check decays at the next route; deriving the list from routing makes a new route covered by construction.

FR-5# Requirement 5 of 5

SHALL Every timestamp the Hub returns SHALL state its zone (UTC), and the app SHALL show it as that instant whatever the operator's machine's zone.

WhySQLite stores no zone; a bare timestamp is read as local time by browsers and was shown an hour off on a UTC+1 machine.

Design

D1 Every request model inherits `RequestModel` (`hub/hub/schemas/common.py`, `extra="forbid"`), so strictness is the default rather than a per-model decision.

D2 Exemptions live in `hub/tests/test_request_strictness.py` as `LAX_BY_DESIGN` (today: the spec document payload, forward compatible by its own requirement) and `NO_CONTRACT_BY_DESIGN` (today: `patch_agent`, which refuses unknown keys by hand with 400), each with a reason that the suite also asserts is present.

D3 Legacy translation subtracts the whole vocabulary (`LEGACY_CONTEXT_VOCABULARY` in `hub/hub/schemas/agents.py`, assignee aliases in `hub/hub/schemas/tasks.py`) and starts from the residue, so `forbid` judges everything else.

Limits
