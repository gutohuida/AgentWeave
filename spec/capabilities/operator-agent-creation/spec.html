Operator agent creation

capabilitycurrentsketch

15 MUST·15 requirements·27 criteria

Summary

An operator creates an agent from the project workspace by naming it and choosing a launchable provider and a model (or an existing runner), with an optional charter. The Hub finds or creates the matching runner in the same transaction, checks launchability again on submit, and announces the new agent. Creation provisions no checkout. Which checkout an agent's turns later get is decided per task, with a shared directory for projects that are not Git repositories. A Copilot agent's native files are written into a Copilot home the Hub owns.

Problem

Agents that can only be created by editing configuration, or that look ready in the app but cannot run, put the first moment an operator uses the product behind a barrier or a lie.

Scope

In scope

  • The Add agent dialog (`hub/ui/src/components/agents/AgentCreateDialog.tsx`) and `POST /agents`.
  • Which checkout a writing turn is given: per task, per agent, grandfathered per-agent, or the shared directory.
  • A Copilot agent's Hub-owned Copilot home.

Non-goals

  • How a checkout is provisioned, released and reported (workspace-isolation).
  • Editing an agent after creation (agent-configuration).
  • Agents requested by other agents (`POST /agents/request`).

Requirements

FR-8# Requirement 1 of 15

SHALL Each project workspace SHALL offer an Add agent action that creates an agent from a project-unique name, a launchable provider and a model that provider's catalog declares, with an optional charter, and SHALL NOT require a runner to exist beforehand nor ask for a persona or organizational role.

WhyChoosing a provider and a model is enough to describe a working agent; anything more at creation is friction at first use.

FR-18# Requirement 2 of 15

SHALL `POST /agents` SHALL refuse with 400 a name that does not match `^[a-zA-Z0-9_-]{1,32}$` or is a reserved name (`user`, `operator`), and with 409 a name already held by an agent or a session-configured agent in the project, and SHALL accept either `runner_id` or both `provider` and `model`, never both and never neither.

WhyAn agent's name becomes a path component, a branch suffix and an attribution; reserved names already mean someone who is not an agent, and every route that runs an agent refuses them.

FR-9# Requirement 3 of 15

SHALL The creation dialog SHALL show every provider with its current launchability from `GET /runners/launchability-by-provider`, keep an unlaunchable provider visible but not selectable with its reason, and the Hub SHALL re-check the chosen runner's launchability on submit and refuse with 409 and the current reason when it cannot run.

WhyLaunchability can change between loading the dialog and submitting it; an agent that looks ready but cannot run is the failure this prevents.

FR-11# Requirement 4 of 15

SHALL When created from a provider and model, the Hub SHALL reuse a project runner with the same CLI and model, or else create one named "<provider label> — <model label>" ("<alias> (latest)" for an alias) in the same commit as the agent, so that a failure leaves neither record behind.

WhyDuplicate runners for one choice clutter runner management, and a runner left behind by a failed creation is a record nobody asked for. An alias-created runner is named for the alias, since its target moves.

FR-19# Requirement 5 of 15

SHALL A created agent SHALL receive a stable project color, be bound to its runner and optional charter, and be recorded as an `agent_created` event broadcast to open clients, so it appears in the rail without a reload.

WhyThe operator should be able to talk to the agent immediately, and other open clients should see it too.

FR-12# Requirement 6 of 15

SHALL Where the operator chooses a provider, each SHALL be shown by its name with its own inline mark where one exists, never another provider's mark, and marks SHALL use no second icon system, webfont or network request and SHALL NOT affect which providers are offered or selectable.

WhyA mark helps recognition but must never be the only distinction; launchability alone decides what can be chosen.

FR-13# Requirement 7 of 15

SHALL Agent creation SHALL offer a setting only when the agent's first turn would be materially different without it, and SHALL leave every setting with a workable default that can be changed before it takes effect to the agent's configuration.

WhyA stated placement rule stops creation growing by accretion. A charter is offered because it shapes the first turn, and stays optional.

FR-10# Requirement 8 of 15

SHALL Creating an agent SHALL NOT provision or change any Git checkout; in a Git project, a writing turn bound to a task SHALL run in that task's own checkout on a branch carrying only that task's work, a writing turn bound to no task SHALL run in the agent's own checkout, and a turn whose checkout cannot be provisioned SHALL be refused with the reason rather than run in the primary checkout.

WhyA per-agent branch carries every task its agent ever worked on, so merging it integrates unapproved work; a branch per task is what lets one approval land one task's work. Silently losing isolation is worse than refusing.

FR-14# Requirement 9 of 15

SHALL In a project whose directory is not a Git repository, the Hub SHALL run writing agents in the project directory without refusing, serialising or locking them and without creating a repository, SHALL tell each agent in its context that it shares the directory with any other agent and has no isolated checkout, and SHALL NOT report the absent repository as a queue waiting reason.

WhyWithout a repository there is no way to produce a conflict, so the honest mitigation is to say so to every agent; refusing would make a plain folder unusable.

FR-20# Requirement 10 of 15

SHALL A turn's `work_dir` override SHALL be refused with 400 for a writing agent in a Git project, and resolved as a project-relative path under the containment guard in a project that is not a Git repository.

WhyThere is isolation to override only where a repository exists.

FR-15# Requirement 11 of 15

SHALL A task that had been worked before per-task isolation shipped (stamped `workspace_scheme = agent` once, by migration 0095, and never written again) SHALL keep being worked in its agent's own checkout, and no existing branch SHALL be renamed, deleted, split, rewritten or adopted as a task branch.

WhyNothing records which commit on a per-agent branch belongs to which task, so any split is a guess that rewrites history; recomputing the set per turn would let a task change scheme mid-life without anyone deciding it.

FR-16# Requirement 12 of 15

SHALL While a writing turn holds a task's own checkout, a writing turn for that task by a different agent SHALL be refused with 409 naming the holder, as a transient refusal that keeps the input queued for delivery once the holding turn ends; review turns, shared-checkout agents and grandfathered tasks SHALL NOT be refused by this rule.

WhyTwo processes editing one working tree lose each other's changes silently; the exempt cases have no task checkout to collide over.

FR-17# Requirement 13 of 15

SHALL When a Copilot agent is created or its runner or charter binding changes, and before every Copilot turn, the Hub SHALL write a custom agent named after the agent (its identity, the project's instructions and its charter, with a statement that this takes precedence over the repository's instruction files) and the `agentweave` MCP configuration into a Copilot home it owns under `~/.agentweave/hub/copilot-home/projects/<project>/<agent>/`, never into the repository and never with a credential.

WhyCopilot reads custom agents and MCP configuration from its home; writing them into the repository would change the operator's project. Per-turn material reaches each turn with its prompt instead.

FR-21# Requirement 14 of 15

SHALL The Copilot home's path SHALL be built only from identifiers checked to be single, safe path components, and a turn whose home cannot be written SHALL be refused with a reason, while a write failure at creation SHALL NOT undo the agent's creation.

WhyA project's identifier can come from a marker file inside the project's own folder.

FR-22# Requirement 15 of 15

SHALL Before every Copilot turn the Hub SHALL remove from the agent's home any hook, plugin, MCP configuration or custom agent it did not write and any setting that trusts a folder or grants a permission, leaving Copilot's own harmless files in place, and SHALL NOT send a prompt while a custom agent it did not write is selected.

WhyNothing left in the home may answer a permission request in the Hub's place.

Behaviour

Which checkout a writing turn gets

  1. If the turn is a review, use a detached checkout of the commit under review.
  2. If the agent is read-only, or the project is not a Git repository, use the project directory.
  3. If the turn is bound to a task whose `workspace_scheme` is `task`, use (and provision on first use) that task's checkout, refusing if another agent's turn holds it.
  4. Otherwise (no task, or a grandfathered `agent`-scheme task), use the agent's own checkout.
  5. If the chosen checkout cannot be provisioned, refuse the turn with the reason.

Design

**Find-or-create in one commit.** `POST /agents` adds a new runner to the same session as the agent and commits once, so neither record survives a failure; an existing runner with the same CLI and model is reused.

**Launchability twice.** The dialog reads per-provider launchability before a runner exists; the route probes the actual runner on submit.

**Isolation is per task.** `task_workspace` decides which checkout a turn is entitled to from the database and never writes `Task.workspace_scheme`; migration 0095 stamped the grandfathered set once, so it can only shrink.

**Copilot home owned whole.** The Hub writes the custom agent and MCP config and sweeps everything else that could approve a permission, so the Hub stays the only approver.
