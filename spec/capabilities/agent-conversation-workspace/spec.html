Agent conversation workspace

capabilitycurrentsketch

84 MUST·84 requirements·290 criteria

Summary

The agent conversation is the operator's primary workspace. AgentWeave owns a durable conversation id that outlives every provider session beneath it; navigation reaches a conversation directly from a tree of project, agent and conversation (or a recency view); the conversation surface carries its turn-level controls on the header and a bounded, draft-keeping composer; and the inbound queue delivers operator, peer and job input into conversations, routing peer traffic by binding, bounding chains by the hop budget, retrying and giving up on failed deliveries, holding an agent whose provider allowance is spent, and telling each request the truth about its own input. Titles, origin, rename and archival belong to `conversation-lifecycle`.

Scope

In scope

  • Durable conversation identity and how a conversation is shown and navigated to
  • The conversation surface: header controls, composer behaviour, timeline presentation, scroll following, banners
  • Peer-message routing into recipient conversations
  • Inbound-queue delivery: hop budget, turn composition, retries and give-up, refusal reporting, allowance holds
  • Review-turn checkouts

Non-goals

  • Conversation titles, origin, rename and archival (conversation-lifecycle)
  • Checkpoint generation and cutover (conversation-checkpoint, agent-conversation-handoff)
  • Stream event normalisation (agent-stream-events)

Requirements

FR-48# Requirement 1 of 84

SHALL The system SHALL allocate a stable `conversation_id` before starting a provider process. A conversation SHALL belong to exactly one project and one immutable target agent, SHALL remain the same across runs, retries, stops, failures and provider-session binding, and SHALL treat the provider session as nullable continuation data rather than as its identity.

WhyRuns, queue entries and recorded output all carry the conversation id, so the operator-facing thread survives everything that happens to the provider process beneath it.

SHALL Selecting an agent from navigation or from the project overview's agent roster SHALL open that agent's conversation directly, with no intermediate agent list, filter tab bar or selection placeholder.

WhyReading the conversation is the reason for selecting the agent; any intermediate step is a click that carries no information.

WhyExpanding to look and opening to go are different intents, and one control cannot express both.

FR-106# Requirement 55 of 84

WhyThe turn is built from the oldest eligible input, which may belong to a conversation the caller cannot see.

FR-108# Requirement 57 of 84

WhyA start reported to the wrong conversation is indistinguishable from success; input selection itself stays in arrival order.

FR-109# Requirement 58 of 84

FR-110# Requirement 59 of 84

WhyThe operator was told synchronously that the request failed; a queue still counting the input would say the opposite.

FR-111# Requirement 60 of 84

SHALL Where a submission is refused, the interface SHALL present the refusal's own sentence to the operator.

WhyA correct status that reaches no readable message has not told the operator anything.

FR-112# Requirement 61 of 84

SHALL The system SHALL NOT count a delivery attempt against queued input where the turn was refused for a reason that prevents the agent from running at all, or where the agent's own workspace cannot be prepared and no other queued input would have run in a different workspace; every other refusal of a turn SHALL count an attempt.

WhyCounting the operator's own retries against an agent that cannot run destroys input nothing tried to deliver; where other input could run, the head of the queue really is in the way. When uncertain, the system holds rather than counts.

FR-113# Requirement 62 of 84

SHALL The system SHALL re-evaluate every agent holding queued input in a project whenever a run in that project reaches a terminal status, on every execution path, regardless of whether the bookkeeping after the terminal status succeeds, and a later bookkeeping failure MUST NOT relabel a run that had already ended.

WhyNothing re-evaluates the queue on a timer, and restart reconciliation only examines runs still recorded as running, so a release gated on bookkeeping strands input indefinitely.

FR-114# Requirement 63 of 84

SHALL The system SHALL bring every run whose execution ends inside the process that started it to a terminal status on every execution path without a restart, recording and logging why when it ended abnormally, while still propagating deliberate cancellation.

WhyAn agent with a run stuck in `running` is refused every later turn; a run whose Hub was killed is left to startup reconciliation.

FR-115# Requirement 64 of 84

SHALL Where an attempt to start an agent's turn ends by giving up on queued input, the system SHALL, in the same pass, attempt the input queued behind it, SHALL continue only after a give-up, SHALL count an attempt against any one input at most once per pass, and SHALL answer the request from the attempt that ended the pass (the give-up's refusal where the queue was then empty).

WhyGiving up releases the queue only if something then tries it; counting a rider each time would spend its allowance in one pass.

FR-116# Requirement 65 of 84

SHALL The system SHALL hold an agent's queue, starting no turn for agent or job input, while the provider's most recent word about that agent (the newest turn outcome carrying an allowance reading or served tokens) is a refusal of its usage allowance, until the later of the stated reset time and one minute after the refusal; the hold SHALL be derived from recorded outcomes, not stored.

WhyEvery turn before the reset would be refused the same way; the one-minute floor stops a reset already in the past from becoming a cycle of refused turns, and deriving it lets a served turn end it.

FR-117# Requirement 66 of 84

WhyA remembered refusal may have stopped being true; presenting it as current contradicts the live state beside it.

FR-118# Requirement 67 of 84

FR-119# Requirement 68 of 84

FR-120# Requirement 69 of 84

WhyThe start of a long response is what the operator reads first; pinning only the bottom scrolled it away as it streamed.

FR-121# Requirement 70 of 84

FR-123# Requirement 72 of 84

FR-124# Requirement 73 of 84

FR-126# Requirement 75 of 84

FR-127# Requirement 76 of 84

WhyEach live check describes the agent now; the stored refusal and the attempt count are records of the past and only explain the wait when nothing current does.

FR-128# Requirement 77 of 84

SHALL After an input's second failed delivery, the system SHALL clear its conversation's provider session so the next delivery starts a fresh provider session.

FR-129# Requirement 78 of 84

FR-132# Requirement 81 of 84

SHALL While an agent's queue is held, operator input that arrived after the refusal SHALL let one turn start; if the provider refuses it too, the renewed hold SHALL stop input that arrived before it from starting another.

WhyOnly the operator can change the allowance (overage, credit, another runner), and a hold derived from the provider's last word cannot see that they did.

FR-133# Requirement 82 of 84

SHALL When a hold's end passes, the system SHALL attempt the agent's queue again without operator action, including a hold whose end passed while the Hub was stopped, and SHALL record an operator-visible event each time a refusal starts or renews a hold.

WhyNothing re-evaluates a queue on a timer, so the hold arms its own wake and startup re-arms every held queue.

FR-134# Requirement 83 of 84

SHALL A job firing whose input waits on a held queue, including the firing whose own turn was refused and one held across a Hub restart, SHALL be reported as in progress, not failed, and SHALL take the outcome of the turn that finally delivers it.

WhyIts input is waiting for a stated time, not refused.

FR-135# Requirement 84 of 84

SHALL While a Copilot quota refusal holds an agent's queue, the hold notice SHALL state the date and time it ends and the way out — bind the agent to another runner and then send it a message, since rebinding alone does not end the hold and its loops and jobs stay blocked — and the notices given to blocked loops and jobs SHALL state the date, not only the time.

WhyA Copilot plan quota resets monthly, so a time of day alone is ambiguous, and rebinding without a served turn changes nothing the hold can see.

Design

D1 Conversation id is AgentWeave's; the provider session is nullable continuation data. A run that reports a different provider session fails with a binding conflict and does not return its input, because the turn already ran.

D2 Navigation owns selection and starting. Conversation switching, new conversation and agent settings live in navigation (row menus, URL-backed destinations); the header keeps only turn-level controls and the always-visible Checkpoint control. There is no overflow menu.

D3 Following is scroll-position driven (40px threshold), lands once per conversation arrival, and offers "Jump to newest" only while suspended.

D4 One turn = one conversation, one kind, admitted by the oldest eligible entry within the hop budget (`inbound_queue.select_turn`, shared by the scheduler and the status route); its depth is the admitting entry's.

D5 Peer routing resolves: named conversation, forward binding on the sender's line of work (sender identity when there is no sending conversation), reverse binding, then a new bound conversation. Never recency.

D6 Delivery failure: count per entry; at 2 clear the provider session, at 3 withdraw with a reason (`RESUME_RETRY_LIMIT`, `DELIVERY_ATTEMPT_LIMIT`). Allowance refusals with a reset ahead are counted separately and never trip the limits; provider-named unretryable failures give up at once. Refusals that stop the agent running at all, or block only its own workspace with nothing else runnable, are not counted.

D7 Refusal vs environment: a `TriggerAgentError` marked `request_level` and not transient is the request's failure (status + sentence, input withdrawn); everything else is a wait the input survives. Each answer is attributed to the request's own entries.

D8 Release is unconditional on run end: every terminal path calls `redrain_queued_agents`, independent of whether the bookkeeping after it succeeds. There is no timer.

D9 Allowance holds are derived from the newest informative turn outcome (inserted order), floor one minute, with a scheduled wake at the end and re-arming at startup.
