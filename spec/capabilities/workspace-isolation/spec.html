Workspace isolation

capabilitycurrentsketch

24 MUST·24 requirements·66 criteria

Summary

What a Hub workspace is and what it guarantees: the agent, task and review checkouts the Hub provisions inside a project's git repository, where each lives, how it is provisioned and given back, how it is reported, and how conflicts between workspaces are detected. Which workspace a given turn uses belongs to `run-task-binding` and `operator-agent-creation`; when a release is triggered belongs to `task-lifecycle-governance`. Implemented in `hub/hub/worktrees.py`, `hub/hub/task_workspace.py` and `hub/hub/api/v1/worktrees.py`.

Scope

In scope

  • Checkout namespaces, paths, branches and id validation
  • Provisioning, prerequisite catch-up, release and snapshots
  • Workspace and conflict read routes (`/worktrees`)
  • Refusals to provision and their remedies
  • The guard on changing whether an agent works in its own checkout

Non-goals

  • Which workspace a turn uses (run-task-binding, operator-agent-creation)
  • When a task checkout is released or integrated (task-lifecycle-governance)
  • Recording writes that leave a run's workspace (agent-run-sandboxing)

Requirements

FR-1# Requirement 1 of 24

SHALL The Hub SHALL provision a writing agent's own checkout at `.agentweave/worktrees/<agent>` on branch `agentweave/<agent>`, and a task's checkout at `.agentweave/tasks/<task-id>` on branch `agentweave/task/<task-id>`, and SHALL accept as a task id only `task-` followed by 1 to 64 lowercase hexadecimal digits, and as an agent name only a name that is valid and not reserved.

WhyThe `task/` segment makes the two namespaces disjoint by construction: an agent name cannot contain `/`, so no agent branch can take a task branch's shape, even for an agent named like a task id. Lowercase is required rather than normalised because two ids differing only in case are two git refs but one directory on Windows and macOS. Both are validated before use as a path component or ref suffix.

FR-2# Requirement 2 of 24

SHALL Deriving a workspace path or branch name, listing checkouts, and reading an agent's workspace SHALL provision nothing; for a workspace that does not exist yet they SHALL report where it will be.

WhyOpening a panel must not write to the repository; otherwise how many checkouts a project carries would depend on who looked at what.

FR-3# Requirement 3 of 24

SHALL Provisioning a task checkout that already exists, correctly registered for its branch, SHALL return it without rebuilding it and SHALL then merge in, as merge commits, the commits of the task's approved prerequisites that its branch lacks; a merge that conflicts, a merge that does not finish in time, or a checkout with uncommitted changes when something must be merged SHALL refuse the turn and leave the branch tip and files unchanged.

WhyRepeated turns on one task must not rebuild it, and a dependent started before its prerequisite was approved must not go on without that work. The existing branch carries the task's own work, so nothing may be rewritten: the merge is aborted on failure and the refusal names the prerequisite task, the commit, the checkout and the command that merges it, so a person can reconcile it. A task released and worked again is re-provisioned from its retained branch, so it resumes with its prior work.

FR-12# Requirement 4 of 24

SHALL Creating a task checkout SHALL cut its branch from the integration base the caller supplies, SHALL merge the prerequisites' work into it, and SHALL leave no checkout and no branch behind when any prerequisite cannot be merged.

WhyA half-provisioned workspace is worse than none: the next turn would find a registered checkout and adopt it. The base is never substituted with `HEAD`, which would cut the branch from wherever the operator's checkout happens to sit; a task checkout requested without a base is an error.

FR-4# Requirement 5 of 24

SHALL Releasing a checkout SHALL commit any uncommitted change onto its branch, remove the directory, keep the branch, and report whether a checkout was released, the branch, the snapshot commit if one was made, and the branch's commits not on the project checkout's HEAD.

WhyThe checkout is what bounds a repository's size; the branch is the record of what was done and what a reopened task resumes from. Releasing an agent's checkout also removes that agent's review checkout, which carries no work; releasing a task's checkout releases no review checkout, since none is keyed by a task.

FR-5# Requirement 6 of 24

SHALL Every commit the Hub creates itself - a turn or release snapshot, a prerequisite merge, or the merge that integrates approved work - SHALL carry the Hub's own author identity (`AgentWeave <agentweave@localhost>`) and SHALL NOT rely on the repository's configured identity.

WhyA project with no configured git identity is ordinary, and git refuses to commit there; relying on configuration lets the Hub snapshot work and then fail to merge it. Snapshots also skip the project's commit hooks, so a project hook cannot strand an agent's work uncommitted.

FR-6# Requirement 7 of 24

SHALL A newly provisioned agent, task or review checkout SHALL have the project checkout's `node_modules`, `.venv` and `venv` directories, where present, linked into it rather than reinstalled; where the platform refuses the link, provisioning SHALL still succeed without it.

WhyProvisioning is on the path of an agent's first writing turn, so a dependency install there is paid at the worst moment. The set stays explicit and grows only for directories that are expensive to regenerate and safe to share across concurrent checkouts. A Windows host without symlink privilege degrades to no shared dependencies rather than to no checkout.

FR-7# Requirement 8 of 24

SHALL Every API response describing a checkout SHALL identify it by a kind (`agent` or `task`) and a name; `GET /worktrees` SHALL be built from git's own worktree registration and list only checkouts registered at the path their namespace predicts, excluding retained branches with no checkout and review checkouts.

WhyA task id is not an oddly named agent, and one name field cannot say which it holds. Reading git's registration means a checkout registered somewhere unexpected is absent rather than reported where it is not. An agent's workspace response (`GET /worktrees/{agent}`) also lists the checkouts of that agent's live tasks, marking a task whose work predates per-task isolation as working in the agent's checkout, so an operator who finds no directory for it does not conclude the work was lost.

FR-13# Requirement 9 of 24

SHALL `GET /worktrees` and `GET /worktrees/conflicts` SHALL state whether the project is a git repository, and when it is not SHALL give the reason and what would change it; `GET /worktrees/{agent}` SHALL refuse a name that is not a valid agent name (400) or not an agent of the project (404).

WhyA bare empty list reads the same for a non-repository as for a healthy repository with no checkouts, and the panel then promises checkouts that will never come (F249). Describing a workspace for an agent that was never created invents one (F247).

FR-8# Requirement 10 of 24

SHALL A conflict report SHALL name each side as a workspace (kind, name and branch) and SHALL be computed without touching any checkout's working tree or index.

WhyTwo tasks held by the same agent can diverge from each other, which a pair of agent names cannot express. Detection uses `git merge-tree`, so asking never disturbs work in progress.

FR-14# Requirement 11 of 24

SHALL Conflict detection SHALL also check every workspace against the project's accepted main branch, reported as a workspace of kind `main`, and SHALL include released task branches of non-rejected tasks whose work has not reached that branch; with no accepted or resolvable main branch it SHALL check nothing against one.

Why"This work will not merge" is the conflict an operator most needs, and before F245 it surfaced only when integration failed at approval. A finished task's branch outlives its checkout and still has to land (F246). A guessed base would make conflicts that are not facts.

FR-9# Requirement 12 of 24

SHALL A refusal to provision a workspace SHALL say whether it concerns the agent's own workspace or a named task's checkout, and SHALL state the remedy for the specific obstruction found.

WhyWhich workspace failed decides what is blocked: the agent's own carries every turn not about a task, a task's carries one task. The operator's input is held until they repair it, so the remedy must be stated, and per obstruction: a link is removed (and only the link), a foreign directory is moved aside, and a checkout left mid-merge must not be removed but finished or aborted.

FR-15# Requirement 13 of 24

SHALL Provisioning SHALL refuse, before creating any directory, a checkout whose source ref names no commit, telling the operator to make a first commit when the repository has none, and naming the ref that does not resolve when it has commits elsewhere.

WhyGit's own error for this is plumbing nobody can act on (F347). The Hub deliberately creates no commit and no orphan branch of its own in the operator's repository; the two cases need different repairs.

FR-16# Requirement 14 of 24

SHALL An agent's own checkout SHALL be cut from the project checkout's HEAD when its branch does not exist; when the branch exists from an earlier release it SHALL be reused, fast-forwarded to HEAD only if it carries no commit HEAD lacks.

WhyA released agent resumes its own history rather than starting over; a branch whose work already landed can safely catch up, while one carrying unique commits is the agent's retained work and is not moved.

FR-17# Requirement 15 of 24

SHALL A review turn SHALL run in a checkout keyed by the reviewing agent at `.agentweave/reviews/<agent>`, detached at the commit under review with no branch, re-pointed at each later review, and SHALL be refused when that commit is not in the repository.

WhyKeying by the reviewer bounds the directories by the roster rather than by the number of reviews. Detached means a reviewer is not an author: `git status` states the role, and an accidental commit is orphaned. A reviewer pointed at the wrong tree would report on code nobody wrote, so a missing commit is refused.

FR-10# Requirement 16 of 24

SHALL The directory recorded for a run SHALL mean the directory the run was started in, and SHALL NOT be presented as a statement that the run's writes stayed inside it.

WhyA workspace is the process's working directory and the root of its branch, not a wall: whether a write stays inside depends on the path the model spells and on the run's permission posture. A consumer that needs to know whether writes left it reads the record of outside writes that `agent-run-sandboxing` defines.

FR-11# Requirement 17 of 24

SHALL The Hub SHALL refuse a change to whether an agent works in its own checkout while that agent has a running turn or an assigned task not in a terminal status, judged on the configuration the Hub reads to choose the workspace (the agent's stored configuration with the synced session entry laid over it), on every route that changes that configuration, and a refused request SHALL change nothing.

WhyChanging it moves where the next turn runs; work already in the old place is left where the agent no longer looks, and a task-bound turn in the shared checkout is not committed onto the task's branch (F242). A request whose effect the session entry overrides, or that leaves the setting as it was, is not a change and is not refused. The refusal (`isolation_change_under_held_work`) names each running turn and open task and what clears it.

FR-18# Requirement 18 of 24

SHALL Where evidence governs a task's merge, the Hub SHALL take the review commit from the most recent evidence naming a commit, and SHALL state in the reviewer's turn context when earlier evidence named different commits.

WhyPresenting the newest commit as the only one would hide that the work moved.

FR-19# Requirement 19 of 24

SHALL Where evidence does not govern a task's merge, the Hub SHALL hand a review turn the tip of the task's branch and SHALL NOT require evidence; where such a task has no branch, a review request SHALL be refused saying the task has no branch to review, and every caller SHALL resolve the target through `task_integration.review_target`.

WhyThe reviewer must see the commit approval would merge; one shared resolution keeps the trigger, preparation, scheduler and flow staffing from disagreeing.

FR-20# Requirement 20 of 24

SHALL When a task reaches `approved` or `rejected`, after integration, the Hub SHALL release the task's own checkout: commit any uncommitted change onto the task's branch, keep the branch, report commits it carries beyond main, and never fail the transition. Reopening the task SHALL re-provision its checkout from the branch. Removing an agent from the roster SHALL release the agent's checkout and not the task's.

WhyA checkout per task bounds disk only if it is released; the branch is the record and the resume point. Releasing after integration keeps release from changing what merges. A roster edit says nothing about the task.

FR-21# Requirement 21 of 24

SHALL In a project whose directory is not a Git repository, the Hub SHALL run writing agents in the project directory without refusing, serialising or locking them and without creating a repository, SHALL tell each agent in its context that it shares the directory with any other agent and has no isolated checkout, and SHALL NOT report the absent repository as a queue waiting reason.

WhyWithout a repository there is no way to produce a conflict, so the honest mitigation is to say so to every agent; refusing would make a plain folder unusable.

FR-22# Requirement 22 of 24

SHALL A task that had been worked before per-task isolation shipped (stamped `workspace_scheme = agent` once, by migration 0095, and never written again) SHALL keep being worked in its agent's own checkout, and no existing branch SHALL be renamed, deleted, split, rewritten or adopted as a task branch.

WhyNothing records which commit on a per-agent branch belongs to which task, so any split is a guess that rewrites history; recomputing the set per turn would let a task change scheme mid-life without anyone deciding it.

FR-23# Requirement 23 of 24

SHALL While a writing turn holds a task's own checkout, a writing turn for that task by a different agent SHALL be refused with 409 naming the holder, as a transient refusal that keeps the input queued for delivery once the holding turn ends; review turns, shared-checkout agents and grandfathered tasks SHALL NOT be refused by this rule.

WhyTwo processes editing one working tree lose each other's changes silently; the exempt cases have no task checkout to collide over.

FR-24# Requirement 24 of 24

SHALL A turn's `work_dir` override SHALL be refused with 400 for a writing agent in a Git project, and resolved as a project-relative path under the containment guard in a project that is not a Git repository.

WhyThere is isolation to override only where a repository exists.

Design

D1 Namespaces by construction. Agent checkouts live under `.agentweave/worktrees/`, task checkouts under `.agentweave/tasks/` on `agentweave/task/<id>`, review checkouts under `.agentweave/reviews/` detached. The `task/` branch segment cannot be produced by an agent name, so the namespaces cannot collide.

D2 Git's registration is the truth. Whether a checkout exists is decided from `git worktree list --porcelain`, never from a directory existing: git run inside an untracked directory answers about the enclosing repository. Path functions are pure; only the `ensure_*` functions provision.

D3 Never destroy work. Release removes the directory and keeps the branch, snapshotting first. Catch-up on an existing branch merges with `--no-ff` and aborts on any failure. Only a branch seconds old (creation path) is ever deleted, by the unwind.

D4 The Hub commits as itself (`COMMIT_IDENTITY`) with `--no-verify` on snapshots, so neither a missing git identity nor a project hook can strand work.

D5 No repository, no isolation. A project that is not a git repository (or a machine without git) runs writers in place; a repository whose provisioning fails refuses the turn rather than falling back to the operator's checkout.

D6 Refusals name scope and remedy. The trigger prefixes the scope (agent's own workspace or task checkout) using the same predicate the resolver obeys (`takes_task_workspace`); the module writes one remedy per obstruction.
