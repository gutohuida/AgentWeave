Summary

How an agent comes to exist and run inside a project: the roster identity, the runner it is bound to, the charter that shapes its behavior, the model it calls, the tool surface it is offered, how it onboards into a turn's context and uses that context once running, and the sandbox its run executes inside.

Map (generated on reindex — hand edits here are overwritten)

  • Agent capability plane capabilitycurrent

    The least-privilege, run-authenticated HTTP contract (`/api/v1/agent-actions`) through which an agent causes effects and makes scoped reads: messages, the task ledger, operator questions and their answers, checkpoints and recall, governed agent requests and scheduled work, and specification and evidence writes. It fixes how a run is authenticated and attributed, which rules the contract itself enforces so that no adapter or hook can hold them, and what a run is told about the access path it actually has. The adapters that expose it are agent-tool-surface.

  • Agent charter capabilitycurrent

    Charters are project-scoped, operator-authored markdown records describing what an agent is answerable for. Each project is seeded once with a bundled starter set. An agent binds to at most one charter, whose content is injected verbatim into the agent's turn context. A charter is managed on the Charters page and cannot be deleted while an open agent holds it.

  • Agent configuration capabilitycurrent

    An agent's configuration is a destination of its own, addressed by URL, divided into sections named for what an operator is trying to do: identity, execution, charter, interaction, context, access and workspace. It holds settings, not live observations, including the per-agent limits on how long a run waits for the operator. Settings are written through `PATCH /agents/{name}`, which refuses unknown fields. An agent is archived, never deleted, because every run is attributed to one; archival releases the agent's charter but keeps its runner. The runner control says when an agent will run but cannot collaborate.

  • Agent context onboarding capabilitycurrent

    Before every run the Hub renders the model-facing context for an agent from its own records: the project, where the run executes, the task's specification, the team, quality gates, which capabilities the agent holds and which it does not, the project instructions, the tools it may call under the names its harness uses, and its charter. Everything a turn needs to begin is placed in it rather than fetched by a tool, and a turn on an open phased document is told what ending it requires. The same renderer answers `GET /agents/agent-context` outside any run, and an agent the Hub has no record of gets onboarding context instead.

  • Agent context usage capabilitycurrent

    How full an agent's context window is, measured from what each runner reports, expressed as one canonical sample per reading, and shown on every surface the same way, including the open conversation's header. A reading replaces the previous one and is never summed. It names the model it measured. It is expressed against a window the provider reported or the catalog declares for that model, and is reported as unknown otherwise. Readings are stored as `context_warning` events, attributed to a conversation, broadcast to open clients, and kept apart from the run's output stream.

  • Agent run sandboxing capabilitycurrent

    The permission posture the Hub imposes on every agent run, independent of the machine's own harness configuration: the four postures (Edit files, Workspace only, Ask me, Full access), how the Hub decides each tool call under them for Claude, Copilot and Codex (including calls to Copilot's GitHub server), the operator's permission cards and their lifecycle, how refusals and outside-workspace writes are recorded, and what text and environment a run receives so that no harness feature bypasses the posture and no provider runner's key leaks into what is recorded.

  • Agent tool surface capabilitycurrent

    The adapters through which an agent reaches the capability plane: the Hub's own MCP tool server and the `aw-tool` call command, which are one pinned program. This capability covers how that program is given to a run and told the Hub's address, how a run without MCP is told to use `aw-tool` and how the command carries the run's authority, how tools are typed and described, how failures reach the agent, the record of how each run reached the Hub, and the shape of individual tools (messages, scheduled work, agent requests, document renaming). The contract the tools call is agent-capability-plane.

  • Model catalog capabilitycurrent

    The Hub's declaration of what each provider it can spawn offers: its models (id, label, aliases, context window) and its runtime controls (effort, permissions), each with its own permitted values and how it reaches the provider. The catalog is served to the operator interface, which renders choices from it, and every model or control the Hub accepts is validated against it before any provider process starts.

  • Operator agent creation capabilitycurrent

    An operator creates an agent from the project workspace by naming it and choosing a launchable provider and a model (or an existing runner), with an optional charter. The Hub finds or creates the matching runner in the same transaction, checks launchability again on submit, and announces the new agent. Creation provisions no checkout, and a Copilot agent's native files are written into a Copilot home the Hub owns and keeps clean.

  • Runner registry capabilitycurrent

    Runners are project-scoped Hub records naming which CLI (`claude`, `codex` or `copilot`) and which model an agent launches with. An agent is bound to at most one runner, and that runner is the single source for what a run launches, which transport and tool surface it gets, and what launchability reports; an agent with none says so. Each supported CLI is served by one runner adapter, and a Copilot runner may send its model to an operator-chosen provider with a key held in the Hub's own environment.

  • Workspace isolation capabilitycurrent

    What a Hub workspace is and what it guarantees: the agent, task and review checkouts the Hub provisions inside a project's git repository, which one a turn works in, where each lives, how it is provisioned and given back, how it is reported, and how conflicts between workspaces are detected. A project that is not a git repository runs its agents in place. Implemented in `hub/hub/worktrees.py`, `hub/hub/task_workspace.py` and `hub/hub/api/v1/worktrees.py`.

  • Provider allowance holds capabilitycurrent

    What the Hub does when a provider refuses an agent's turn because its usage allowance or plan quota is spent. The agent's queue is held until the stated reset, the refused input goes back uncounted, one operator turn may still pass, the queue is retried at the reset, job firings wait instead of failing, and the operator is told when the hold ends and how to get out of it.
