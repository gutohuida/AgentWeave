Summary

The app itself, running on one machine for one operator: its lifecycle from start to stop, the project workspace it opens, the environment settings and instructions scoped to a project, its own configuration file, the diagnostics that report on its runtime health, the usage it accounts for, and the quiet hours that hold it back from running unattended when told to.

Map (generated on reindex — hand edits here are overwritten)

  • App lifecycle capabilitycurrent

    The one supported way to start and manage a local AgentWeave instance: bare `agentweave` launches or reuses the instance, registers the invocation directory as a project and opens the app; `status`, `stop` and `reset` manage it, honouring global options wherever the documented command form places them; named profiles give separate instances; the Hub refuses to guess which database to open; and shutdown releases what it holds in a safe order.

  • Local project workspace capabilitycurrent

    One local Hub owns many projects. Each project has a durable ID and one canonical working directory, bound by a marker file in that directory; every project filesystem operation goes through one server-side resolver; the operator opens, creates, relocates and deletes projects explicitly; and one operator event stream carries every project's events, stamped with the project they belong to.

  • Project environment settings capabilitycurrent

    The project's configuration surface under Environment and the settings write behind it: how each section introduces itself, how settings are laid out as labelled rows, how saving reports its outcome, the main-branch control, that a change may name only the fields it changes, that a runner named in settings must belong to the project, and that a saved change is recorded in the project's history.

  • Runtime diagnostics capabilitycurrent

    How AgentWeave tells the operator whether it can run and why something did not: `agentweave doctor` and `agentweave status` for the instance, the Hub's per-agent launchability and collaboration-readiness report, typed refusals before a spawn, durable failure facts for runs and jobs, and the severity vocabulary those events carry.

  • Usage accounting capabilitycurrent

    Every Hub-owned run gets one durable token-accounting outcome, measured or explicitly unavailable; usage is aggregated per agent, conversation and project; allowance and cost are presented without implying a bill; Copilot's AI credits are recorded beside tokens; and a project token budget pauses autonomous work while the operator keeps control.

  • Project instructions capabilitycurrent

    Each project has one block of instructions, stored in the Hub database, served to every agent ahead of its charter, and edited on the project's Instructions screen, which never writes content it did not read and asks before blanking what is stored.

  • Hub API request contract capabilitycurrent

    What the Hub's HTTP surface promises about the data that crosses it. A body field the receiving contract does not declare is refused by name, uniformly; the few contracts that decline the rule say why; legacy vocabularies are translated without swallowing unknown fields; a test over the routing table catches any route that slips; and every timestamp the Hub returns states its zone and is shown as that instant.
