Summary

How work is tracked once it leaves the conversation: a task's lifecycle and who governs its transitions, how a run binds to the task it is doing, how a recurring loop notices and reacts to what's in front of it, and the trace timeline that ties a run's actions back to the task and requirement they served.

Map (generated on reindex — hand edits here are overwritten)

  • Agent loops capabilitycurrent

    A loop is a scheduled job given a purpose and a stop condition. Each firing claims work from the loop's queue of tasks and briefs the loop's agent with the tier it works in, how its claimed task is finished and a bounded handover from the previous firing; the loop ends when its stop condition is met or the operator stops it, and is archived rather than deleted. Its job routes, history and views in the app belong here too.

  • Run task binding capabilitycurrent

    Which task a run is working on, who decides that, what binding does to the task, and what happens when a run ends holding work nobody moved. The Hub binds a run when it starts, from the cause that started it, and checks it when it ends, for every runner and without relying on a runner hook; a bound run that ends having caused no transition of its own is recorded as a divergence and answered by the task's divergence policy. task-lifecycle-governance decides whether a transition is legal; this capability makes sure one happens at all.

  • Task lifecycle governance capabilitycurrent

    Which task status moves are legal and who may make them; the append-only record of every accepted move; who may change a task's other fields; the waiting (`blocked`) status; author/reviewer separation and the completion binding gate; the requirement-rigor approval gate and one-action landing; and how tasks are listed, shown and deleted.

  • Agent flows capabilitycurrent

    A flow is a loop that declares a specification document. Where a loop fires one agent on a schedule, each firing of a flow decides both the tasks and the agents, so work crosses agents (implementer to reviewer) without any agent choosing its next step. This capability owns how a change document declares its delivery and becomes a flow, the flow's adoption of the document's tasks, firing-time staffing, width, in-flight judgement and agent capacity, reviewer declaration and resolution, review dispatch and withdrawal and the briefings around review, the surfacing of steps and reviews nobody can staff or is doing, the flow's checkpoint lineage, and the `create_flow` tool.

  • Loop firing accountability capabilitycurrent

    A job's firing records say truthfully what each firing did. A firing whose agent cannot start is recorded as failed at once, a stranded record never makes a loop read as firing, a refused firing leaves no conversation behind, a firing that does not fire records only what is new, and each record names the conversation it used. The firing count counts firings rather than agents started, and the job's surfaces show each record's own status and distinguish fired from refused.

  • Project checks capabilitycurrent

    The operator configures shell commands (tests, linters) that the Hub runs, in the background, on the exact commit a task's approval would merge, and records the result. Approval is refused until the checks passed on the current main tip and merge targets, unless the operator approves over a failure with a recorded reason.

  • Task dependencies capabilitycurrent

    Tasks can depend on other tasks. A dependency is declared by a specification document (by task key, including imported tasks of other approved documents) or by the operator, and is written through one writer that refuses cycles. A task may not start until every prerequisite is approved; started work is flagged, never halted, when a prerequisite regresses; and a task's isolated checkout carries its prerequisites' work.

  • Task dependency board capabilitycurrent

    A second view of the Tasks area that lays one document's tasks out by dependency depth, draws the edges between them, shows each card's status and why it cannot start, collapses finished layers, and names prerequisites that live in other documents.

  • Approval integration capabilitycurrent

    What approving a task does to the code. Approval merges the approved work into the project's main branch in the same operation, choosing which commit to merge; it is refused when that merge would conflict, when the work is still being produced, when evidence that would merge is unaccepted, or when git cannot be asked. Every integration attempt is recorded, a skipped one can be retried, and a preview says what approval would merge.
