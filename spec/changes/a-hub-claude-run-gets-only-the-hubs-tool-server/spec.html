A Hub Claude run gets the Hub's tool server and no other

change-specproposedsketch

2 MUST·2 requirements·3 criteria·2 tasks

Summary

Every Claude agent run the Hub spawns carries --strict-mcp-config, so it loads only the MCP servers the Hub's own --mcp-config names (the Hub's server, plus any a runner's flags add). The operator's claude.ai account connectors (Gmail, Drive, Calendar, Docs) and their user- and project-scope servers stop reaching agent runs (F531).

Problem

_build_claude_command (runner_commands.py:172) passes --mcp-config without --strict-mcp-config, so Claude Code merges in every server the operator's own configuration and account carry. Driven on :8010 on 2026-10-08 (scripts/drive/d1008_f531_no_connectors_drive.py, 1/3): a fresh Haiku agent's turn listed eight mcp__claude_ai_Claude_Docs__* tools; a Hub-shaped claude -p with alwaysLoad also showed Drive, Calendar and Gmail (needs-auth). Those tools were granted by no Hub surface, are described nowhere in the run's context, and under bypassPermissions or yolo are callable with no prompt. The Hub's one-shots (titles, workers) already pass the flag for this reason (claude.py:168-170; conversation_titles.py:81-83).

Scope

In scope

  • The argv of every Claude agent turn (_build_claude_command), with or without the Hub's MCP server injected
  • The agent-run-sandboxing capability: a requirement stating which MCP servers a Claude run loads

Non-goals

  • Codex and Copilot runs: Copilot already runs in a Hub-made COPILOT_HOME; Codex reads ~/.codex/config.toml servers and is undrivable here (backlog, not this change)
  • A UI for choosing extra MCP servers per runner: runner flags already carry --mcp-config, which strict mode honours
  • The Hub's one-shot spawns: already strict

Requirements

FR-1# Requirement 1 of 2

MUST Every Claude agent run the Hub spawns MUST load only the MCP servers named on its own command line, by passing --strict-mcp-config, whether or not the Hub's own server is injected.

WhyA run's tool surface is the Hub's to grant and describe; servers inherited from the operator's account or user configuration are neither granted nor recorded, and a no-server run must not inherit them either.

FR-2# Requirement 2 of 2

MUST An MCP server a runner's flags name with --mcp-config MUST still load in that runner's runs.

WhyThe escape hatch for an operator whose agents need another server (a project's .mcp.json server, say): strict mode honours every --mcp-config on the command line.

Design

Tier 2: a cross-cutting change to every Claude agent run's argv, and a containment question. No migration and no UI. HAZARD: it reaches :8000's agents at :8000's next restart, and from then on a project's own .mcp.json servers and the operator's user-scope MCP servers no longer load in any Hub agent run. Nothing in spec/capabilities promises them (grep: the only match is agent-run-sandboxing's allowlist of the Hub's own server), and the Hub describes none of them to the agent, but an operator could have come to rely on one; the remedy is a runner flag --mcp-config naming it, which strict mode honours (criterion runner-flag). ROLLBACK: revert the one commit; no stored state changes. WHERE: _build_claude_command, not _claude_mcp_args, because the latter returns [] when no server is injected and that run must not inherit either. CLAUDE.md and project settings still load: the flag affects MCP servers only (measured for the titler, conversation_titles.py:81-83).
