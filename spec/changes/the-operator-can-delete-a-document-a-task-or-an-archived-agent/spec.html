The operator can delete a document or a task, and a runner only archived agents hold

change-specapprovedsketch

4 MUST·4 requirements·5 criteria·3 tasks

Summary

Operator deletes for a specification document (not a capability, not archived, not folded) with its requirements, evidence and tasks, and for a task with its links and evidence; history that only mentions a deleted thing keeps its row and loses the pointer. An agent stays archived, never deleted (agent_lifecycle.py's decision, kept by the operator 2026-10-08): instead a runner held only by archived agents can be deleted, unbinding them. The app offers the document and task deletes behind a confirm.

Problem

F532: the operator API deletes projects, runners, jobs and charters and nothing else. Clearing drive residue out of this repo's trial project (26 documents with no file, 28 tasks, 20 archived agents, 168 runs) took a hand-written cascade over 30 tables with the Hub stopped. An archived agent also blocks deleting its runner (runners.py:238), so archiving is no way out. The operator chose (2026-10-08) to keep 'an agent is archived, never deleted' and free the runner instead.

Scope

In scope

  • DELETE /project/documents/{path} and DELETE /tasks/{id} on the operator API
  • Removing a deleted document's file and rebuilding spec/index.json without it
  • Deleting a runner held only by archived agents, unbinding them
  • Delete controls in the app: the spec phase bar and the task detail

Non-goals

  • Deleting an agent: an agent is archived, never deleted; its name attributes its runs and conversations (operator, 2026-10-08)
  • Deleting a capability, an archived change or a folded change: they are the corpus and its history
  • Agents deleting anything: these are operator routes only
  • Undo: a delete is final, and the confirm says so

Requirements

FR-1# Requirement 1 of 4

MUST The operator MUST be able to delete a specification document that is not a capability, not archived and named by no merge, removing its file, its index entry, its requirements with their revisions, evidence and links, its events, its tasks as a task delete does, and its stopped flows; it MUST be refused, writing nothing, for a capability, an archived or folded document, a document with a run active on one of its tasks, or one whose flow is still running.

WhyDrive residue and abandoned drafts otherwise stay on the board and in the coverage forever.

FR-2# Requirement 2 of 4

MUST The operator MUST be able to delete a task, removing its dependencies, links, transitions, integrations, checks, evidence and queued entries; rows that only mention it (runs, conversations, messages, questions) MUST keep their row with the pointer cleared; it MUST be refused while a run bound to it is active.

WhyA task nobody should work is otherwise only ever rejected, and stays counted.

FR-5# Requirement 3 of 4

MUST Deleting a runner that no open agent holds MUST succeed, clearing the runner of every archived agent that held it; a runner an open agent holds MUST still be refused, naming the agent.

WhyAn archived agent runs nothing, so its binding only blocked the runner's deletion forever (runners.py:238); the agent and its history stay.

FR-4# Requirement 4 of 4

MUST The app MUST offer Delete for a deletable document on its phase bar and for a task in its detail, each behind a confirm naming what goes with it, and show the Hub's refusal when there is one.

WhyThe cleanup should never again need a database script.

Design

Tier 2: it deletes data. No migration and no schema change. HAZARD: from :8000's next restart the operator's real instance gains these deletes, and the UI bundle reaches its app at its next reload; a delete there is final. Mitigations: every delete is operator-only, refuses what the corpus (capabilities, archived and folded changes) or a live run depends on, and sits behind a confirm naming what goes with it; agents are never deleted; a runner only archived agents hold is unbound from them and deleted. History that only mentions a deleted thing keeps its row with the pointer cleared rather than being deleted. Rollback: revert the commits; deleted rows are not recoverable except from a database backup, which the drive takes on :8010's profile before it runs. The cascades live in one module with a test that fails when a new table references tasks, agents or runs without being covered.
