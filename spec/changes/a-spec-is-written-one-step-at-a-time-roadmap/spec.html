A spec is written one step at a time, and a tester keeps it true

roadmapapprovedsketch

Home

Summary

Writing a specification becomes a journey of short steps, each briefed with only its own instructions and each saving its result into the document, sized at intake and customisable per project; approval warns instead of refusing; and a tester in the flow drives the built product and amends the spec visibly, without lowering the bar it is judged by.

Problem

The spec agent receives one flat exploring duty of about 7-8k characters on every turn (hub/hub/api/v1/agents.py:1720-2284), whatever the conversation is doing; the only marker inside exploration is the operator's 'exploration is complete' boolean. Instruction adherence drops as instructions grow and early wrong turns are not recovered, so steps get dropped in long explorations. Nothing sizes the work, so a small fix gets the same ceremony as a hazard, the field's main reported failure. Approval only refuses or passes and cannot say what is missing. After approval a flow's reviewer reads code and evidence but never drives the product, and what it finds never reaches the spec, which drifts from what was built. Research: testbed/research/reports/Spec driven development with agents.md (2026-10-08); the operator approved its recommendations together with the decisions in each slice below.

Scope

In scope

  • A document-held current step, the Hub briefing only that step, the agent proposing to advance and the operator choosing continue here, a fresh conversation, or stop
  • Sizing at intake (small or large, announced and overridable); a small fix leaves the journey; small work merges Requirements with Acceptance; an optional Approach step for large or hazardous work
  • Acceptance agreed with the operator: per criterion, how to check it and whether an agent or only the operator can; task 1 of every change is the acceptance drive, recorded failing
  • A project setting listing the steps in order, where the operator adds a step (pasted Markdown) at any position and appends an instruction to any step
  • Approval warnings computed by the Hub, with approve anyway, the overridden warnings recorded
  • A tester in a flow's delivery that drives the running product, reviews code and evidence, and amends the spec; amendments marked not reviewed by the operator, per item and per document
  • Criteria protection: the builder never edits criteria; a tester amendment that relaxes or removes a criterion cannot count as passing it until reviewed; an explicit cannot-satisfy exit
  • A reconcile step before fold, and recording which step caught each defect

Non-goals

  • Hard gates between steps, or an operator approval per step: approvals are a scarce resource (operator, 2026-10-08)
  • Persona casts (analyst, PM, architect) or spec-as-source regeneration; the field retreated from both
  • Mandatory criteria for every SHOULD or MAY requirement

Slices

  1. step-journey — The spec is written one step at a time
    A change document records its current step and size. The spec agent is briefed with only that step's instructions, writes the step's result into the document, then asks the operator to continue here, continue in a fresh conversation, or stop; any conversation resumes at the recorded step. Default journey: intake (problem, size and reason, non-goals, one question at a time) -> requirements -> acceptance (never skipped; how to check each criterion and who can) -> approach (optional, for large work) -> tasks (task 1 is the acceptance drive, recorded failing) -> delivery. Size fix keeps intake, tasks, delivery; small merges requirements with acceptance.
    Done when: In a real Haiku exploration on a scratch Hub, each turn's briefing holds only the current step's instructions, a fresh conversation resumes at the recorded step with nothing lost, and a small change reaches Approve without the steps it skipped.
  2. project-steps — A project orders its steps, adds its own and appends instructions
    Project settings hold the ordered steps. The operator adds a step by pasting Markdown at any position and appends an instruction to any step; each instruction reaches only its own step and has a size cap. An instruction says where its output goes (a document section, a file); when it does not, the agent decides.
    Done when: A custom step inserted after Requirements runs in that position, and an instruction appended to Intake appears in Intake's briefing and in no other.
    Builds after: step-journey
  3. approval-warnings — Approve lists what is missing and lets the operator approve anyway
    Clicking Approve lists what the Hub finds missing (a MUST with no criterion, a criterion with no how-to-check, an operator-only check with no owner, no acceptance drive, a requirement with no task, unresolved questions, skipped steps, unreviewed amendments); the operator approves or approves anyway, and the overridden warnings stay on the document. The list is kept short.
    Done when: Approving a document with a requirement lacking criteria shows that warning, approve anyway approves it, and the document then reads approved with that gap recorded.
    Builds after: step-journey
  4. tester-amends — A tester drives the built product and keeps the spec true
    A flow's delivery names a tester (on by default) that drives the running product and reviews code and evidence. What it finds becomes amendments to the spec, each recording its author and run, marked not reviewed by the operator and saying how to check it; the operator marks reviewed per item or per document. Additions take effect at once and become tasks the implementer picks up. A change that relaxes or removes a criterion cannot count as passing it until reviewed, the builder never edits criteria, and cannot-satisfy is a first-class outcome. Findings stay within the stated criteria; side findings go to the backlog.
    Done when: In a real Haiku flow with a planted bug, the tester finds it by driving, adds a task to the spec marked not reviewed, the implementer fixes it, and a relaxing amendment is refused as passing evidence until the operator reviews it.
    Builds after: approval-warnings
  5. reconcile-and-measure — A change is reconciled with its code before it is folded, and each defect names the step that caught it
    Before fold, the gaps between code and spec are classed missing, partial, contradicts or unrequested; each defect records which step caught it, so the journey can be tuned from data.
    Done when: Folding a change shows its reconcile result, and the project can report per change which step caught each defect.
    Builds after: tester-amends
