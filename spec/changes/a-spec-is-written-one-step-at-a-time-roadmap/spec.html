A spec is written one step at a time, and a tester keeps it true

roadmapproposedsketch

Summary

Writing a specification becomes a journey of short steps, each given only its own instructions and each saving its result into the document, sized at intake and customisable per project; approval warns instead of refusing; and a tester in the flow drives the built product and amends the spec, visibly and without lowering the bar it is judged by.

Problem

Today the spec agent receives one flat exploring duty of about 7-8k characters on every turn (hub/hub/api/v1/agents.py:1720-2284), whatever the conversation is doing, and the only marker inside exploration is the operator's 'exploration is complete' boolean. Instruction adherence drops as instructions grow (IFScale, arXiv 2507.11538), long contexts degrade (Chroma, Context Rot) and early wrong turns in multi-turn work are not recovered (arXiv 2505.06120), so steps get dropped in long explorations. Nothing sizes the work, so a small fix gets the same ceremony as a hazard, the field's main reported failure (Bockeler, martinfowler.com; Scott Logic: 10x slower). Approval only refuses or passes; it cannot say what is missing. After approval a flow's reviewer reads code and evidence but never drives the product, and what it finds never reaches the spec, which then drifts from what was built. Research and decisions: testbed/research/reports/Spec driven development with agents.md (2026-10-08, operator approved its recommendations).

Scope

In scope

  • A document-held current step, the Hub briefing only that step, the agent proposing to advance and the operator choosing continue here, a fresh conversation, or stop
  • Sizing at intake (small or large, announced and overridable); a small fix leaves the journey; small work merges Requirements with Acceptance; an optional Approach step for large or hazardous work
  • Acceptance agreed with the operator: per criterion, how to check it and whether an agent or only the operator can; task 1 of every change is the acceptance drive, recorded failing
  • A project setting listing the steps in order, where the operator adds a step (pasted Markdown) at any position and appends an instruction to any step
  • Approval warnings computed by the Hub, with approve anyway, the overridden warnings recorded
  • A tester in a flow's delivery that drives the running product, reviews code and evidence, and amends the spec; amendments marked not reviewed by the operator, per item and per document
  • Criteria protection: the builder never edits criteria; a tester amendment that relaxes or removes a criterion cannot count as passing it until reviewed; an explicit cannot-satisfy exit
  • A reconcile step before fold, and recording which step caught each defect

Non-goals

  • Hard gates between steps, or an operator approval per step (approvals are scarce: operator, 2026-10-08)
  • Persona casts (analyst, PM, architect) or spec-as-source regeneration (the field retreated from both: Agent OS v3, Tessl)
  • Mandatory criteria for every SHOULD or MAY requirement
  • Per-project journeys before the default has been used; projects customise the default, they do not start from nothing

Slices

  1. step-journey — The spec is written one step at a time
    A document carries its current step and size; the spec agent is briefed with only that step's instructions, proposes advancing, and the operator continues here, starts fresh, or stops; small work takes the short path.
    Done when: In a real Haiku exploration on a scratch Hub, each turn's briefing holds only the current step's instructions, a fresh conversation resumes at the recorded step with nothing lost, and a small change reaches Approve without the steps it skipped.
  2. project-steps — A project orders its steps, adds its own and appends instructions
    Project settings list the journey's steps; the operator adds a pasted-Markdown step at any position and appends an instruction to any step, each reaching only its own step.
    Done when: A custom step inserted after Requirements runs in that position, and an instruction appended to Intake appears in Intake's briefing and in no other.
    Builds after: step-journey
  3. approval-warnings — Approve lists what is missing and lets the operator approve anyway
    Clicking Approve shows the Hub's warnings for the document; the operator approves or approves anyway, and the overridden warnings stay on record.
    Done when: Approving a document with a requirement lacking criteria shows that warning, approve anyway approves it, and the document then reads approved with that gap recorded.
    Builds after: step-journey
  4. tester-amends — A tester drives the built product and keeps the spec true
    A flow's tester drives the running product and reviews code and evidence; what it finds becomes amendments to the spec, marked not reviewed, which become tasks the implementer picks up; criteria cannot be lowered to pass.
    Done when: In a real Haiku flow with a planted bug, the tester finds it by driving, adds a task to the spec marked not reviewed, the implementer fixes it, and a relaxing amendment is refused as passing evidence until the operator reviews it.
    Builds after: approval-warnings
  5. reconcile-and-measure — A change is reconciled with its code before it is folded, and each defect names the step that caught it
    Before fold, the gaps between code and spec are classed missing, partial, contradicts or unrequested; each defect records which step caught it, so the journey can be tuned from data.
    Done when: Folding a change shows its reconcile result, and the project can report per change which step caught each defect.
    Builds after: tester-amends

Design

D1 Steps live in the document, not the conversation. The document records its current step; each step must write its decisions into the document before it may propose advancing, so a fresh conversation, another day or another agent loses nothing. Rejected: steps as conversation state (dies with the context). D2 The agent proposes advancing; the operator answers continue here / fresh conversation / stop (operator, 2026-10-08). Replaces the operator-set 'exploration is complete' boolean. Steps are skippable and revisitable; a skipped step becomes an approval warning, never a refusal. D3 Default journey: Intake (problem, size and its reason, non-goals, files touched, open questions; one question at a time, multiple choice where possible) -> Requirements (MUST/SHOULD/MAY, stable keys) -> Acceptance (never skipped; how to check, agent or operator, the acceptance drive) -> Approach (optional, on for large or hazardous work: 2-3 options, the choice, hazard and rollback) -> Tasks (task 1 is the acceptance drive, recorded failing) -> Delivery (implementer, tester on by default, schedule, stop) -> Approve. Small work merges Requirements and Acceptance; a small fix leaves at Intake as one task with one failing check. D4 Project customisation (operator, 2026-10-08): one strong default, then a project setting holding the ordered steps, where the operator adds a step by pasting Markdown at any position and appends an instruction to any step. Each instruction reaches only its own step and has a size cap. An instruction states where its output goes (a section of the document, a file); when it does not, the agent decides (operator, 2026-10-08). D5 Approval warns, it does not refuse (operator: approvals are a scarce resource). Warnings: a MUST with no criterion, a criterion with no how-to-check, an operator-only check with no owner, no acceptance drive, a requirement with no task or a task with no requirement, unresolved questions, unreviewed amendments. Approve anyway records which were overridden. Keep the list short; a long list is clicked through. D6 The tester amends freely and visibly (operator, 2026-10-08). Each amendment records its author and run and is marked not reviewed by the operator, per item, with how to check it; the operator marks reviewed per item or per document, each mark recorded. Additions take effect at once. A change that relaxes or removes a criterion cannot count as passing that criterion until reviewed, the builder never edits criteria, and cannot-satisfy is a first-class outcome (ImpossibleBench: models cheat about half the time where spec and tests conflict, mostly by editing tests; an abort option cut one model from 54% to 9%). Tester findings stay within the stated criteria; side findings go to the backlog.

Limits

  • No controlled study supports per-step instruction delivery, interview-first elicitation or warnings over gates; they rest on general degradation studies and practitioner convergence (research report, evidence note)
  • What a running flow does while its document is reopened and amended has not been driven
