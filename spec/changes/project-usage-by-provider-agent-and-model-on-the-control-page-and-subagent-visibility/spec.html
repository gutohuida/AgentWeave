Project usage on the control page, and a Budgets page of its own

change-specapprovedsketch

17 MUST·17 requirements·21 criteria·10 tasks

Summary

The control page loses the context meter and the duplicated budgets panel, and gains a small usage summary — money as the headline figure, the equivalent tokens beneath it, defaulting to today and switchable to the last 7 or 30 days — that links to Budgets, promoted to a project tab of its own, where usage breaks down by provider with models nested inside, by agent, and separately by AgentWeave's own worker calls. Providers that report no cost are priced from a rate table shipped with the release and refreshed over the network when it can be reached. Subagent tracking is deliberately not in this document.

Problem

The project Overview tab is the control page. Each agent card carries a context-usage meter (`ContextUsageIndicator`, fed by `AgentSummary.context_usage`, derived from the newest usable `context_usage` event row for that agent). It reports what fraction of a context window the agent's most recent run consumed. That answered a real question when an agent had one long-lived session; with many conversations per agent it reports one arbitrary recent thread and answers nothing. The operator's decision: it only makes sense inside a conversation, and leaves the control page.

The same page also renders `AccountingPanel` — the identical component Environment > Budgets renders — so the control page's usage story today is a duplicated settings panel beside a meter that has lost its meaning.

What is wanted instead: a headline showing money spent, with the equivalent token count underneath, over a window defaulting to today; and Budgets as a page of its own carrying the breakdown by provider, by agent and by model. A question the operator wants answerable and today is not: how much went on actual work, and how much AgentWeave spent driving itself — worker calls will only grow.

GROUNDING — what the code already holds - `TurnUsage` is one immutable row per Hub-owned run, carrying `agent`, `runner`, `model`, input/output/total tokens, cache read and write, reasoning tokens, `api_equivalent_usd_micros`, a provider `allowance` blob, and `observed_at`. Per-provider, per-model and windowed rollups are group-bys and date filters over columns that already exist, and apply retroactively to history already recorded. - `accounting_snapshot` today aggregates a project total and a per-agent breakdown only, plus a `preferred_display` that prefers a rate-limit allowance over an API-equivalent dollar figure over raw tokens. - `WorkerInvocation` records out-of-band Hub model calls (checkpoint generation, probes) with their own cli, model, tokens and cost, and is absent from the accounting snapshot entirely.

GROUNDING — live probes of Claude Code 2.1.221 (`--output-format stream-json`, this machine, 2026-08-20) - A Claude run that spawns a subagent emits `system`/`task_started` carrying `task_id`, `tool_use_id`, `description`, `subagent_type`, `task_type` and `prompt`; every subagent turn then streams as an ordinary `assistant` line carrying `parent_tool_use_id` and its own `message.usage` and `message.model`. - The final `result` event's `usage` covers the MAIN CHAIN ONLY. Measured: deduplicated main-chain usage was input 18, cache-read 57,940, cache-write 544 — an exact match to `result.usage`. The same run's `modelUsage` reported cache-read 84,169 and cache-write 14,355, the difference being the subagent's work, and `total_cost_usd` (0.03333765) equalled `modelUsage.costUSD` exactly. - `runner_parsing` builds accounting from `result.usage` first and only falls back to `modelUsage` when `usage` is absent, while passing `total_cost_usd` through in either case. So for any Claude run that spawned a subagent, the Hub today stores a dollar figure that INCLUDES the subagent and a token count that EXCLUDES it — precisely the pair of numbers this change stacks on top of each other. No Hub-spawned run in this project's database has in fact spawned a subagent to date (0 of 28 sessions), so no recorded row is known to carry the inconsistency yet. - Real `rate_limit_info` is `{status, resetsAt, rateLimitType: "five_hour", overageStatus, overageDisabledReason, isUsingOverage}`. It names which limit window is in force and when it resets; it carries NO remaining-allowance figure, and no weekly window appeared in the sample. The repository's own test fixture uses a different, invented shape (`{"five_hour": {"remaining_percent": 64}}`); the parser stores the blob verbatim so nothing is broken, but no live payload observed here carries a percentage.

GROUNDING — how the money is computed for a provider that reports none - Codex reports no cost. Its `turn.completed` accounting is built with no `cost_usd` argument at all, and the model catalog carries no price table. Six recent Codex rollout transcripts on this machine (`~/.codex/sessions/**/*.jsonl`) contain no cost field of any kind. Its usage payload is `{input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens, total_tokens}` with `total_tokens = input + output`, so its `input_tokens` already includes cache reads (matching the `cache_is_separate_input=False` path the Hub already takes for Codex, against `True` for Claude). Model ids appear as e.g. `gpt-5.6-sol`. - T3 Code, the operator's reference, prices what the provider does not (read from its shipped sourcemaps, `src/usage/`, design reference only): rates come from LiteLLM's public `model_prices_and_context_window.json` — the same table `ccusage` prices against. Each entry supplies USD-per-token rates for input, output, cache read and cache creation; a missing cache rate falls back to the input rate rather than to free, and an entry lacking either input or output is dropped, because a half-priced model under-reports silently. Model names are canonicalised by stripping a `provider/` prefix and lowercasing; bare family names ("opus", "sonnet", "haiku") are treated as unpriceable rather than guessed at a generation. Rates are read at the base tier only, because the record does not say which tier served a request. Every priced bucket carries a cost source of `providerReported`, `modelPriced` or `unpriced`. Reasoning tokens are never charged on top of output, being already counted inside it. Buckets are `(day, provider, model)` cells cut on the reporting time zone's calendar day, so a turn lands on the day the operator experienced it rather than the UTC day. - One architectural difference deliberately not adopted: T3 derives usage by scanning the provider CLIs' own on-disk transcripts, so its numbers cover turns never driven through T3 at all. AgentWeave's `TurnUsage` covers exactly the turns the Hub spawned, and is the only source that knows which agent, task and project a turn belonged to — which is also the only way the work-versus-overhead split is answerable.

Scope

In scope

  • The project control page's usage summary: a combined monetary headline, an equivalent token figure, and a window control defaulting to today
  • Budgets promoted to a project tab of its own, carrying the breakdown by provider with models nested inside, and by agent
  • A monetary figure for providers that report no cost, computed from a rate table shipped with the release and refreshable over the network
  • Reporting AgentWeave's own worker calls as a category separate from agent work
  • Showing when the provider's current rate-limit window resets
  • Removing the context-usage meter from the control page's agent cards
  • Ending the duplicate rendering of the same budgets panel in two places
  • Making the money figure and the token figure describe the same work, for turns recorded from here on

Non-goals

  • Recomputing or backfilling usage rows already recorded — the consistency fix applies forward only, and a window spanning the cutover may mix rows written under both behaviours
  • Tracking Claude's spawned subagents, attributing their spend, or giving them a page — its own exploration
  • Scanning provider CLI transcripts for usage that AgentWeave did not itself drive
  • Showing how much rate-limit allowance remains, or any percentage of a plan limit
  • Per-conversation cost reporting
  • Changing how the project token budget pauses autonomous turns
  • Adding a new provider or a new spawn path

Requirements

FR-1

MUST The project control page shows one project usage summary for the selected window, presenting a monetary total as its primary figure and the equivalent token count as a secondary figure beneath it; the monetary total covers both agent work and AgentWeave's own model calls.

Money is the figure a person acts on; tokens are how it is explained. The headline is combined because a single figure that silently omits a category understates what the provider account saw — the separation lives on the Budgets page.

FR-2

MUST The control page shows only the summary, and does not render the per-provider, per-agent or per-model breakdown or the budget-limit controls.

The same panel is rendered today both on the control page and in Environment > Budgets; the control page is a place to notice something, not a place to administer it.

FR-3

MUST The control page summary offers a navigation to the Budgets page.

FR-11

MUST Budgets is reachable as a top-level project tab alongside Overview, Tasks, Spec, Jobs and Activity, and is not also rendered as an Environment section.

Spend is something the operator checks, not something they configure once.

FR-4

MUST Where the monetary figure is an API-equivalent estimate rather than an amount actually billed, the summary marks it and states that subscription plans are billed on a different basis.

On a subscription plan the dollar figure is not what the operator pays; presented bare it is a number that reads as a bill and is not one.

FR-12 consumer

MUST A monetary figure is produced for every provider: where the provider reports a cost for a turn that figure is used, and where it does not the cost is computed from a per-model rate table of USD-per-token rates for input, output, cache read and cache creation. A rate table is present in every release; the Hub may fetch a newer one, and falls back to the shipped table when a fetch cannot be completed or parsed.

Claude's CLI reports `total_cost_usd`; Codex reports no cost anywhere. Shipping a table means an offline machine still prices its work; fetching means a model released after the build can still be priced. Neither alone is sufficient.

FR-13

MUST Each monetary figure declares whether it was reported by the provider, computed from the rate table, or unavailable because the model has no rate.

A reported cost and a computed one carry different confidence, and a reader who cannot tell them apart will treat a rate-table estimate as an invoice.

FR-14 producer

MUST Work whose model has no rate is counted in the token totals, contributes nothing to the monetary total, and the surface states how much work was excluded from the money figure.

Silently dropping unpriced work makes a partial total read as a complete one. Counting it at a guessed rate is worse: a fabricated number indistinguishable from a measured one.

FR-5

MUST The usage window is today by default, and the operator can switch it to the last 7 days or the last 30 days; every figure on the surface reflects the selected window.

An all-time total stops being actionable once a project is a few weeks old; every usage row already carries `observed_at`, so any of these windows is derivable.

FR-15

MUST A window boundary falls on the operator's local calendar day, not on the UTC day.

"Today" is the default and the figure the operator sees most often. Cut on UTC, an evening's work west of Greenwich lands on tomorrow and today reads as empty while the operator is still working.

FR-6

MUST For a turn recorded after this ships, the monetary figure and the token figure presented together describe the same set of work: any turn counted in one is counted in the other.

Verified defect today — for a Claude run that spawned a subagent the stored cost comes from `total_cost_usd` (which includes the subagent) while the stored token count comes from `result.usage` (which does not). Stacking those two numbers publishes a contradiction. Scoped to turns recorded from here on because usage rows are immutable and are not recomputed.

FR-7

MUST The Budgets page breaks usage in the selected window down by provider, showing each provider that ran at least one turn.

FR-8

MUST The Budgets page breaks usage in the selected window down by agent.

FR-9

MUST The Budgets page breaks usage down by model, with each model shown within the provider that served it rather than as a separate flat list.

A model belongs to exactly one provider, so the nesting costs nothing and keeps the provider as the unit the operator reasons about. The same agent on a different model is a different bill, which is what this dimension explains.

FR-16 producer

MUST AgentWeave's own out-of-band model calls are reported as a category of their own, separate from and not summed into the per-agent breakdown, so the spend on work and the spend AgentWeave incurs driving itself are separately readable.

The operator's stated question: how much went on actual work, and how much AgentWeave spent on itself. Worker calls belong to no agent, and folding them into an agent's figure would both misattribute them and hide a number that is expected to grow.

FR-17 consumer

MUST Where a provider reports a rate-limit window, the surface shows which window is in force and when it resets, and states no figure for how much of the allowance remains.

Verified: the provider reports the window type, its reset time and whether the request was allowed, and no remaining-allowance figure. A percentage would need a denominator that is not in the stream, and an invented number sitting beside measured ones is worse than an absent one.

FR-10

MUST The control page does not show a context-usage meter for any agent; the meter remains available within a conversation.

Context fill is a property of one conversation. With many conversations per agent, an agent-level meter reports whichever thread ran most recently, which is not a question anyone is asking.

Design

Decisions taken while exploring, with the reasoning, so a later reader can tell a choice from an accident.

RATE TABLE DISTRIBUTION (operator, 2026-08-20). A rate table is shipped inside every release, refreshed to the newest published rates at release time, and the Hub may also fetch a newer copy at runtime. If the fetch cannot be made or its result cannot be parsed, the shipped table is used. Pricing therefore never becomes unavailable because a machine is offline, and a model that appeared after the release was cut can still be priced by a machine that can reach the network. This differs from the reference implementation, which fetches first and reports everything as unpriced when it has neither a fresh copy nor a snapshot — acceptable there, not here, because AgentWeave is meant to work local-first.

TURN USAGE STAYS THE SPINE. Usage is derived from the Hub's own `TurnUsage` and `WorkerInvocation` records, not by scanning provider CLI transcripts. Scanning would catch turns AgentWeave never drove, but has no idea which agent, task or project a turn belonged to — and the work-versus-overhead split the operator asked for is only answerable from AgentWeave's own records.

THE CONSISTENCY FIX IS FORWARD-ONLY (operator, 2026-08-20). Making the money figure and the token figure cover the same work applies to turns recorded after it ships; rows already written are left as they are. `TurnUsage` rows are immutable by design and there is no recompute path, and no recorded row in this project is known to carry the inconsistency — the affected case requires a Hub-spawned run that spawned a subagent, of which there have been none. A window spanning the cutover may therefore mix rows written under both behaviours.

RATE-LIMIT DISPLAY IS DELIBERATELY MINIMAL (operator, 2026-08-20). The provider tells us which limit window is in force and when it resets, and does not tell us how much of the allowance remains. So the surface says when the window resets and nothing more. A percentage would need a denominator that is not in the stream and would be an invented number sitting beside measured ones.

COMBINED HEADLINE, SEPARABLE BREAKDOWN (operator, 2026-08-20). The control page's single figure covers everything the provider account saw — agent work and AgentWeave's own worker calls together — because a headline that silently omits a category understates the bill. The separation the operator wants lives on the Budgets page, where worker spend is its own category and is not summed into any agent's figure.

MODELS NEST UNDER PROVIDERS (operator, 2026-08-20). A model belongs to exactly one provider, so the nesting costs nothing and keeps the provider as the unit the operator reasons about.

  • Ship a rate table, refresh it, fall back — Carry a per-model rate table (input, output, cache read, cache creation, USD per token) inside the release, allow the Hub to fetch a newer copy, and fall back to the shipped one when the fetch cannot be completed or parsed. Canonicalise model ids for lookup and treat ambiguous family names as unpriceable rather than guessing. — satisfies FR-12
  • Price a turn and say where the price came from — Use a provider-reported cost when the provider gives one, otherwise compute from the rate table, otherwise mark the work unpriced. Carry the source alongside every figure, and count unpriced work in tokens while excluding it from money. — satisfies FR-13, FR-14
  • Make money and tokens count the same work — Resolve the recorded inconsistency where a Claude turn's stored cost includes subagent spend while its stored token count does not, so the two figures presented together cover the same turns.
