A run claims only work that is its agent's or nobody's

change-specarchivedsketch

3 MUST·3 requirements·6 criteria·3 tasks

Summary

A run may claim a task (-> in_progress) only where the task is unassigned or assigned to the run's own agent; claiming an unassigned task makes the run's agent its assignee. Today any idle run takes any task, and the board keeps naming the agent it was assigned to (F450).

Problem

Found by the 2026-09-25 sweep (row 7): task-bdb51ddeea1c was assigned to alpha and never started; a real Haiku turn on idle beta called update_task in_progress then completed, both 200. The transitions record beta, tasks.assignee still says alpha, so the board and timeline name the wrong holder and alpha may later be briefed on work already done. `_guard_run_holds_the_task` (task_transition_service.py) binds a run holding nothing to any task it claims and never compares the run's agent with the assignee.

Scope

In scope

  • An agent run's claim (-> in_progress) through the task routes
  • The assignee written when a run claims an unassigned task

Non-goals

  • The operator: an operator move is a person's statement and stays unguarded
  • The runtime binding (bind_run_to_task) and a flow's own staging, which write the assignee before the run exists
  • Review verdicts, already governed by the author/reviewer guards
  • Reassigning from an agent: no agent tool reassigns, and this adds none

Requirements

FR-1# Requirement 1 of 3

MUST The system MUST refuse an agent run's move of a task to in_progress where the task is assigned to a different agent and the run is not already bound to it, naming the assignee and the operator's remedy, and leaving the task, its assignee and the run's binding unchanged.

WhyThe assignee is who the board, the briefings and the flow's resumption believe holds the work; a claim that leaves it naming someone else makes all three wrong.

FR-2# Requirement 2 of 3

MUST Where an agent run claims an unassigned task, the system MUST record the run's agent as the task's assignee in the same transaction as the claim.

WhyClaiming waiting work stays a real behaviour (the charter's list_tasks), and the board then names who took it.

FR-3# Requirement 3 of 3

MUST A claim by a run whose agent is the task's assignee, or by a run already bound to the task, MUST behave as before.

WhyFlows, loops, delegations and the operator's bound runs all arrive this way.

Design

Tier 2 (an authorization boundary). Hazard: a live flow whose task carries a stale assignee could now see its agent's claim refused instead of silently taking the work. Every path that legitimately starts work writes the assignee first (enter_selected_task, bind_run_to_task) or arrives bound, so the refusal fires only on an agent picking up someone else's card; the remedy is the operator reassigning, which the refusal names. Rollback: revert the guard; no data is migrated. Refused rather than taken-over-and-recorded: a silent takeover is what F450 is, and the operator, not an agent, decides who holds work.

Evidence and coverage limits

  • The operator returns first in the guard (actor.is_operator)
