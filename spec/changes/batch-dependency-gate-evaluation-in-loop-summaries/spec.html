Batch dependency gate evaluation in loop summaries

Summary

`_batch_loop_summaries` (hub/hub/api/v1/jobs.py) computes every job's `loop` field for a listing in a fixed, bounded number of queries per its own docstring and design D7 — except for `current_task`, which calls `dependency_gate.evaluate` once per non-in_progress candidate task it examines while searching for the first startable one, and each call issues its own fresh SQL query. Listing jobs therefore costs one extra query per gated candidate task, across every loop in the batch — an N+1 (worse: an M×N, where M is per-loop queue depth) hiding inside the one function whose stated job is to avoid exactly that.

Problem

GET /api/v1/jobs, GET /api/v1/jobs/{id}, and the enable/disable responses (hub/hub/api/v1/jobs.py:507,532,763,858) all call `_batch_loop_summaries` to compute the `loop` block for one or more jobs in a single response. The function's docstring states the design contract plainly: "Compute every job's `loop` block in six fixed queries, never one query per job (design D7)." Five of the six batched lookups (loops, job names/agents, queue counts, open questions, active firings) honor that: each is one query across all `job_ids`/`loop_ids` regardless of how many jobs are in the batch.

The sixth piece, `current_task`, does not. To find each loop's current task, the function walks that loop's claimable-status candidates in queue order (hub/hub/api/v1/jobs.py:192-203) and, for every non-`in_progress` candidate until it finds one the gate does not refuse, calls `await dependency_gate.evaluate(session, task)`. `dependency_gate.evaluate` (hub/hub/dependency_gate.py:74-101) issues its own `session.execute` — a fresh query joining `TaskDependency` to `Task` — on every call, with no batching or caching across calls.

The result: listing a project's loops issues one extra dependency-gate query for every gated candidate task examined, summed across every loop in the response. A project with several loops whose queue heads are blocked on unmet dependencies pays for all of them on every job-list poll, not once per loop as the "six fixed queries" contract promises.

This is not the only place `dependency_gate.evaluate` is called candidate-by-candidate — `scheduler._first_startable_candidate` (hub/hub/scheduler.py:283-323) does the identical walk-and-evaluate for a single loop. That call site is not part of this finding: it runs once per loop per firing, not once per loop across every loop in an HTTP listing response, so it does not compound the way `_batch_loop_summaries` does. It is recorded as a non-goal below rather than addressed here.

Scope

In scope

  • _batch_loop_summaries in hub/hub/api/v1/jobs.py (current_task computation, lines 192-203)
  • its use of dependency_gate.evaluate in hub/hub/dependency_gate.py

Non-goals

  • scheduler._first_startable_candidate in hub/hub/scheduler.py — single-loop per-firing use, not batched across loops in one response, so it does not compound the way _batch_loop_summaries does and is left as-is by this change
  • changing the shape or meaning of DependencyRefusal
  • changing the TaskDependency schema
  • changing what current_task or gated mean to a consumer of LoopSummary — only the query cost of producing them changes

Requirements

FR-4

MUST Loop summary computation used by every endpoint that calls _batch_loop_summaries (job listing, single-job fetch, enable, disable) executes a fixed, bounded number of database queries that does not grow with the number of jobs or loops included in the batch.

This is the function's own stated design contract (D7: "six fixed queries, never one query per job") for every other field it computes; current_task is the one exception.

FR-5

MUST The bound above holds even when determining a loop's current_task requires examining more than one queued candidate task — evaluating dependency gating for additional candidates must not add one query per candidate examined, whether within a single loop's queue or across multiple loops in the same batch.

A queue with several consecutive gated tasks before the first startable one is the case that currently multiplies query count past the "six fixed queries" bound.

FR-6

MUST For any given set of loops and their task queues, the current_task reported for each loop remains exactly the first candidate, in existing queue order, that dependency gating does not refuse.

This change is scoped to query cost only; it must not alter which task the board and the firing agree is current (the invariant human-only check 13.1 exists to protect, per the existing comment at jobs.py:165-169).

Design

The fix must preserve `_batch_loop_summaries`'s existing external contract — same `LoopSummary` shape, same `current_task` selected, same set of tasks a caller would independently learn are gated (e.g. `tasks.py`'s derivation, referenced at hub/hub/api/v1/tasks.py:235) — and change only how many queries producing it costs. The requirements below describe that contract as an observable, testable bound rather than prescribing the query shape that satisfies it.
