Tracking and showing the subagents Claude spawns

change-specexploringsketch

Summary

A Claude agent can spawn subagents, and AgentWeave records them only as an opaque tool call. This document is a seeded exploration: the problem, what live probing established about what is knowable, and the questions that decide the shape. No requirements yet — the operator has not been interviewed on this one.

Problem

A Claude agent working in AgentWeave can spawn subagents. The Hub records a spawn only as a generic tool call in the run timeline; it attributes no identity, no type, no model, no tokens, no duration and no outcome to the subagent itself. From the operator's chair a subagent is a tool call named `Task` (or `Agent`) followed by a blob of result text, with no way to see what was delegated, what it cost, or whether it succeeded.

Two distinct problems live here and either is worth solving alone: - ATTRIBUTION — subagent tokens should land in the project's totals so the money and token figures are honest. - VISIBILITY — a place to see what was spawned, what it was asked to do, how long it took and what it returned.

The operator has asked for this to be developed separately from the control-page usage change, and has named a page in the side panel as a possible home.

WHAT LIVE PROBING ESTABLISHED (Claude Code 2.1.221, `--output-format stream-json`, this machine, 2026-08-20)

Everything needed to track a subagent is already in the stream the Hub parses today; none of it is currently read.

- A spawn emits `system` / `subtype: task_started`, carrying `task_id`, `tool_use_id`, `description`, `subagent_type` (e.g. `Explore`), `task_type` (e.g. `local_agent`) and the full `prompt`. Identity and intent arrive up front, before any work happens. - Every subagent turn then arrives as an ordinary `assistant` line with `parent_tool_use_id` set to the spawning tool call's id, carrying its own `message.model` and its own `message.usage`. Per-subagent, per-model token attribution is therefore directly measurable, live, without waiting for the subagent to finish. - On completion the parent's tool result carries `agentId`, `agentType`, `resolvedModel`, `status`, `totalDurationMs`, `totalToolUseCount`, `toolStats` (read/search/bash/edit counts, lines added and removed) and `usage`. An asynchronous launch instead returns `{agentId, description, prompt, resolvedModel, status, isAsync, outputFile, canReadOutputFile}`, so the completed and the launched-in-background cases are different shapes and a reader must handle both. - Claude Code also writes each subagent's own transcript to `~/.claude/projects/<slug>/<session>/subagents/agent-<agentId>.jsonl`, whose entries carry `isSidechain: true`, the parent `sessionId`, the `agentId`, and per-message `usage`, `model` and `effort`.

TRAP — `totalTokens` on the tool result is NOT the subagent's cost. It is the final request's footprint. Measured against a real subagent transcript: the tool result reported `totalTokens` 40,314, while summing that subagent's 18 actual requests gives 530,405 (36 input, 3,083 output, 394,591 cache read, 132,695 cache write). Pricing a subagent from `totalTokens` understates it by more than an order of magnitude. The per-turn `usage` on each `parent_tool_use_id` line is the figure that can be summed.

RELATIONSHIP TO THE USAGE CHANGE — the final `result` event's `usage` covers the main chain only, while `modelUsage` and `total_cost_usd` cover the whole session including subagents (measured: main-chain cache-read 57,940 exactly matching `result.usage`, against `modelUsage` cache-read 84,169; `total_cost_usd` equal to `modelUsage.costUSD` to the last digit). The Hub reads `result.usage` first, so it currently stores a cost that includes subagents beside a token count that does not. That inconsistency is being fixed in the control-page usage change rather than here, because that change is what puts the two numbers side by side. Per-subagent attribution — which subagent spent what — is this document's problem.
