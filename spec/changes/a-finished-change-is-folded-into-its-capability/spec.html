A finished change is folded into its capability, then archived

change-specapprovedsketch

5 MUST·5 requirements·7 criteria·3 tasks

Summary

The operator closes a finished change from the app: the Hub drafts the capability's new content by copying the change's requirements and criteria in, the operator may edit the draft, and one confirm merges it (audited) and archives the change. Archiving a change is refused until its tasks are done and it was folded somewhere, or the operator says it changes no capability. A capability's content changes only through a merge.

Problem

Closing a change has needed a hand-written script per change. The merge route (spec.py:2260) exists but takes the capability's whole new payload and has no app screen (the-corpus-keeps-what-shipped design D7), so every reconcile so far went through PUT .../content instead (scripts/drive/reconcile_f4xx.py, reconcile_f509.py, reconcile_f531.py): spec_document_merges holds 0 rows on :8010. Archive checks only that the actor is the operator (spec_lifecycle.py:319), so nothing stopped a shipped change being archived unfolded, and nothing noticed F509's three slices sat in no capability for two days (DEAD-ENDS 2026-10-08).

Scope

In scope

  • A fold draft and a fold route for an approved change-spec, built on spec_service.merge_document
  • The archive transition's guard for change-spec documents
  • Capability content writes outside a merge (PUT .../content) refused; a merge naming no change allowed as an audited edit
  • fold_state on the document view, and the phase bar's fold dialog in the app
  • spec-document-authority: ac136 now reads that the operator's capability write succeeds through a merge

Non-goals

  • Removing a capability requirement through a fold (a change that retires one is folded by an edited merge): backlog
  • Agents folding changes: merge stays operator-only
  • Back-filling merge rows for the ten changes archived before this change
  • Closing a change's tasks and evidence for operator-built work (close_change.py's first half)

Requirements

FR-1# Requirement 1 of 5

MUST For an approved change-spec and a named capability document, the Hub MUST return a fold draft: the capability's current payload with each of the change's requirements appended verbatim under the key <change-slug>-<key> (the change's folder name, trimmed so the key is at most 64 characters), each acceptance criterion of those requirements appended with its requirement re-pointed at the new key, and every draft key that already exists in the capability reported as a collision rather than overwritten.

WhyThe operator reviews text instead of writing it; most reconciles so far copied the change's statements unchanged.

FR-2# Requirement 2 of 5

MUST The operator MUST be able to fold an approved change-spec into a capability document in one request, choosing which of the change's requirements to fold (default all), each optionally with an edited key, statement or modal, or naming an existing capability requirement it replaces; the fold MUST write through the merge (one spec_document_merges row naming the change and one merged event) and, unless told not to, move the change to archived in the same transaction. It MUST be refused before anything is written when the change is not approved, a task of it is still open, a named requirement is not the change's, a key collides without naming what it replaces, a replaced key is not the capability's, or the target is not a capability document.

WhyReplaces the per-change reconcile scripts with one audited operator action; a change touching two capabilities is folded twice, archiving on the second.

FR-3# Requirement 3 of 5

MUST Archiving an approved change-spec MUST be refused, naming what is missing, unless every task the document declared is approved or rejected and either a merge names the change or the operator states no_capability_change with a non-empty reason. Other kinds and the existing exploring/proposed archive rule are unchanged.

Whyarchived has no way back; a shipped change whose requirements live nowhere else must not become history (F509).

FR-4# Requirement 4 of 5

MUST A capability document's content MUST change only through a merge: a direct content write to a capability document is refused with a code naming the merge route, and a merge naming no change is accepted as an operator edit and recorded as one. Creating a capability document is unchanged.

WhyEvery capability change then has an audit row saying which change it came from, or that it was an edit; the original design said capability documents are written only by merge.

FR-5# Requirement 5 of 5

MUST The document view of an approved change-spec MUST carry fold_state (tasks_open, ready, or folded with the capability paths it was folded into), and the app's phase bar MUST show a ready change as shipped but not yet in a capability, with a Fold into capability action (capability picker, the draft's requirements with editable key and statement, an archive option on by default, confirm) and an Archive without a capability change action that asks for a reason.

WhyThe close-out becomes something the operator does in the app, and an unfolded shipped change is visible where the operator already looks.

Design

Tier 1, no migration (spec_document_merges exists since 0074). The fold is spec_service.merge_document with a payload the Hub builds, so validation, identity minting, rendering and the audit row are the merge's own. Key rule: <change-slug>-<key>, the slug trimmed from the right so the whole key is at most 64 characters (KEY_RE, spec_payload.py:42); the dialog lets the operator rename. The archive guard lives in spec_lifecycle.transition beside the operator check, so every archive path meets it; no_capability_change rides PhaseRequest. HAZARDS: the UI bundle reaches :8000's app at its next reload, and from :8000's next restart a direct capability content write is refused there too (the operator's app never makes one; only scripts did). Rollback: revert the commits; no data changes shape.
