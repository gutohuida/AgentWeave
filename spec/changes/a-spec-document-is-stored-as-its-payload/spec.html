A spec document is stored as its payload

change-specexploringsketch

10 MUST·10 requirements·10 criteria·4 tasks

Summary

Each specification document is stored as spec.json, holding the submitted payload plus the Hub's copy of its phase, rigor, step and size. The Hub renders the HTML from it when the app opens the document, so the page beside the composer is unchanged. A one-time, reversible conversion moves an existing corpus across. Decided 2026-10-08 (spec-queue/DECISIONS.md, structure-format).

Problem

Every document under spec/ stores its content three times: the JSON payload the Hub reads (2.0 MB across this repo's 77 files), an HTML rendering of that same payload (2.2 MB), and its own copy of the CSS (0.67 MB). Every save rewrites the whole file, so a one-word edit shows as two changes buried in markup, and 'what changed since I last reviewed' (needed by approval-warnings and tester-amends) has no clean source to diff. A document's step and size live only in the database (migration 0122), so a clone cannot tell where a change stands. The operator reads documents only in the app (SpecFrame renders the HTML), so storing HTML buys nothing visible.

Scope

In scope

  • spec.json as the stored form of every spec document: the payload verbatim plus a hub block (phase, rigor, step, size)
  • GET /spec renders the HTML from spec.json with the same render a save uses today
  • One storage seam in spec_documents through which every Hub reader gets a document's payload
  • Path rules, discovery, naming and spec/index.json move from spec.html to spec.json
  • A per-project conversion route, html to json and back, that rewrites file, database paths and payload references
  • Converting this repository's corpus on the trial Hub, and updating scripts and rules that name spec.html paths

Non-goals

  • Moving archived changes to spec/changes/archive/ (next change)
  • Generated system maps (later change)
  • Project-defined steps file (roadmap slice project-steps)
  • Reading legacy spec.html documents in place: they are reported and converted, not served (operator, 2026-10-08: the two on :8000 are test documents)
  • A Convert button in the app: the route is enough for the one corpus that needs it

Requirements

FR-1# Requirement 1 of 10

MUST The Hub MUST store each spec document as a spec.json file holding the submitted payload verbatim (unknown fields kept) and a hub block with the document's phase, rigor, step and size, and MUST NOT write an HTML file for it.

WhyOne stored copy of the meaning; the database stays the authority for phase, rigor, step and size, and the file's copy lets a clone see where each change stands.

FR-2# Requirement 2 of 10

MUST GET /spec MUST return HTML rendered from the stored spec.json by the same render a save produces today (identifiers, anchors, corpus navigation, slice line, phase and rigor chips), so the page the app shows beside the composer is unchanged.

WhyThe operator reads specs only in the app; the format change must not be visible there.

FR-3# Requirement 3 of 10

MUST spec.json MUST be written deterministically (stable key order, indented, one value per line, LF, trailing newline), so that rewording one requirement changes only that requirement's lines.

WhyReview diffs and tester amendments build on a diff that shows meaning only.

FR-4# Requirement 4 of 10

MUST Every Hub reader of a document's payload (reading, indexing, review turns, adoption, agent actions, task transitions, roadmap slices, divergence) MUST obtain it through one storage function in spec_documents; no caller parses a stored file itself.

WhyTwenty call sites parse file content today; one seam is what makes a future format change one edit.

FR-5# Requirement 5 of 10

MUST A document path MUST end in /spec.json: validate_spec_path, discovery, path naming and spec/index.json MUST use it, and creating a document at an .html path MUST be refused with a message naming the .json path.

FR-6# Requirement 6 of 10

MUST Discovery MUST report each legacy .html spec document as a legacy_html_document diagnostic naming the conversion route, and MUST NOT list it as a document.

WhyA document missing from a list looks identical to one never written; the diagnostic says why and what to do.

FR-7# Requirement 7 of 10

MUST A per-project conversion route MUST turn every legacy .html document into spec.json and rewrite spec_documents.path, undelivered inbound_queue_entries.spec_document, payload references (roadmap.document, a task's from.document) and spec/index.json, keeping document ids, requirement identifiers, evidence, events and tasks unchanged; running it again MUST change nothing.

WhyIds already carry identity everywhere else in the database; only these places hold a path.

FR-8# Requirement 8 of 10

MUST The conversion route MUST also convert spec.json back to .html with the same rewrites, so a rollback is the reverse call plus reverting the Hub code.

WhyNo schema migration is involved; the rollback is the converse operation.

FR-9# Requirement 9 of 10

MUST The conversion MUST refuse, changing nothing, while any run in the project is active, naming the runs.

WhyA running turn holds a document path in its context; renaming under it breaks the turn's next call.

FR-10# Requirement 10 of 10

MUST A journey move (step or size) MUST rewrite the document's spec.json hub block in the same request.

Design

Tier 2: a cross-cutting contract (every reader of a document file, the path rules, the index) and a conversion of the live corpus. No Alembic migration: the database already refers to documents by id except spec_documents.path and inbound_queue_entries.spec_document, which the conversion rewrites. Hazard: a conversion under a running turn; refused while any run is active. :8000 runs this checkout; after its next restart its two .html test documents show as legacy diagnostics (operator: test data). Rollback: the reverse conversion, then revert the code.

D1. Path keeps the file name (spec/changes/x/spec.json), not the directory. Rejected: directory-as-identity, which would change every path consumer at once for no gain here. D2. Render on read, not cached. render_document already runs per save; the per-open cost is one render of one document. Rejected: committing a generated spec.html (keeps the noisy diff the change exists to remove). D3. The hub block is a copy, the database the authority, exactly as the HTML head's aw-spec-status is today. Rejected: payload fields for step/size (agents could submit them). D4. Legacy .html is reported, not read in place. Rejected: a dual reader, kept forever for two test documents. D5. Conversion is a route, not a migration: migrations do not touch project files, and only the Hub resolves a project's directory (ProjectWorkspace). D6. src/agentweave/spec_manifest.py, the CLI twin, has no importer; it is deleted with its agreement test rather than kept in step.
