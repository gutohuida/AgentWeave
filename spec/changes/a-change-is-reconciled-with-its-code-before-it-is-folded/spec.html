6 MUST·6 requirements·10 criteria·4 tasks

Summary

Before a finished change is folded, an agent reconciles it with the code and records each gap as missing, partial, contradicts or unrequested; the fold shows that result. Every defect the Hub already knows about (a tester's added task or cannot-satisfy, a review that sent a task back, a reconcile gap, or one the operator records) names the step that caught it, and the project reports them per change, so the journey can be tuned from data. Roadmap slice reconcile-and-measure.

Problem

Fold copies a change's requirements into a capability with no comparison against the code (spec_service.fold, hub/hub/spec_service.py:997-1051; fold_state is computed per read, api/v1/spec.py:497-513), so a capability can state behaviour that was never built, and code nobody asked for is never named. The Hub holds no defect record and nothing says which step caught a problem: a review's send-back reason is free text in Task.notes (db/models.py:705), and the only ledger of where defects were caught is a hand-kept spec-queue/METRICS.md. The research behind the roadmap finds no tool that measures this, and Spec Kit's converge classifies code-vs-spec gaps as missing, partial, contradicts or unrequested (testbed/research/reports/Spec driven development with agents.md).

Scope

In scope

  • An agent tool to record a reconcile result for an approved change: its gaps, each classed missing, partial, contradicts or unrequested, with a place and a summary
  • An operator route and button that ask an agent to reconcile a change, with the Hub's reconcile brief
  • The fold dialog shows the latest reconcile result, or says the change was not reconciled
  • A per-change defect list derived from what the Hub already records, each naming the step that caught it, plus defects the operator records by hand
  • A project report of defects per change by step, on the spec page

Non-goals

  • Refusing a fold that was not reconciled: approvals and folds are the operator's, warn do not gate (operator, 2026-10-08)
  • The Hub comparing code with the spec itself: an agent reads both and records what it found
  • Fixing the gaps a reconcile finds: they are recorded; the operator decides
  • Moving METRICS.md into the Hub: the report reads the Hub's own records

Requirements

FR-1# Requirement 1 of 6

MUST An agent run MUST be able to record a reconcile result for an approved change document: a summary and a list of gaps, each with a class of missing, partial, contradicts or unrequested, a place and a summary, naming one of the document's requirements unless it is unrequested; the result MUST be recorded with its author and run, and a result with no gaps MUST be accepted.

WhySpec Kit's converge classes (research); an empty result says the change was reconciled and nothing was found.

FR-2# Requirement 2 of 6

MUST The operator MUST be able to ask a named agent to reconcile an approved change; the Hub MUST start that agent's turn with a brief that says to read the document and the code, class each gap, record the result with record_reconcile and change nothing.

FR-3# Requirement 3 of 6

MUST The document's fold state MUST carry its latest reconcile result (author, when, the count of each class and the gaps), or say it was not reconciled, and the fold dialog MUST show it; a fold MUST NOT be refused for an absent or non-empty result.

WhyWarn, do not gate (operator, 2026-10-08).

FR-4# Requirement 4 of 6

MUST A change's defects MUST be listed from what the Hub records, each with the step that caught it: a tester's add_task amendment (test), a cannot_satisfy report (build when the reporting run was working a task, else test), a transition of one of its tasks to revision_needed (review), a missing, partial or contradicts gap in its latest reconcile result (reconcile), and a defect the operator records with a step of their choosing.

WhyEach defect records which step caught it, so the journey can be tuned from data (roadmap slice).

FR-5# Requirement 5 of 6

MUST The project MUST report its defects per change document, each change with its defects and a count per step, through a route and a section on the spec page.

FR-6# Requirement 6 of 6

MUST The operator MUST be able to record a defect against a change with a summary and the step that caught it: a step of the project's journey, or build, review, test, reconcile or after-fold.

WhyA defect found after fold, or by the operator, is otherwise invisible to the report.

Design

Tier 1: two agent/operator routes, one tool, a derived report and two UI sections. No migration: a reconcile result and an operator defect are spec-document events (kind free, detail JSON, hub/hub/db/models.py:2128-2167); everything else in the report is read from records the Hub already keeps. No Hub-restart hazard.

D1. The reconcile result is an agent's record, made by a turn the operator asks for; the Hub does not compare code with the spec itself. Rejected: a Hub-side comparison (drift detection fingerprints files, it cannot read meaning) and a turn the flow starts on its own when every task is decided (a scheduler change for a step the operator triggers once per change). (morning-1009-7) D2. Defects are derived from existing records rather than stored as rows: an add_task amendment, a cannot_satisfy, a send-back to revision_needed, and a missing/partial/contradicts reconcile gap each already are one; only the operator's own defect is a new event. Rejected: a defect table written at each source (a migration plus four writers that could disagree with their source). (morning-1009-8) D3. An unrequested gap is reported in the reconcile result but is not a defect: code nobody asked for is a question for the operator (fold it, or remove it), not a failure of a step. (morning-1009-9) D4. Steps a defect can be caught at: the project's journey steps, then build, review, test, reconcile and after-fold. A review send-back counts once per transition to revision_needed. D5. Fold is never refused for reconcile; the dialog says Not reconciled and offers to ask.
