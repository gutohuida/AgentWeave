Slice tester-amends (A tester drives the built product and keeps the spec true) of the roadmap A spec is written one step at a time, and a tester keeps it true (spec/changes/a-spec-is-written-one-step-at-a-time-roadmap/spec.html)

9 MUST·9 requirements·11 criteria·5 tasks

Summary

A flow's review turn becomes a test turn by default: the tester drives the running product as well as reading code and evidence, and what it finds becomes amendments to the approved spec. Each amendment records its author and run, says how to check it, and stays not reviewed until the operator marks it reviewed, per item or for the whole document. Additions take effect at once and a new task joins the flow for the implementer; a change or removal of a criterion cannot count as passing until reviewed; the builder never amends; cannot-satisfy is a recorded outcome. Roadmap slice tester-amends.

Problem

After approval nothing can change a document: save_document refuses every submission to an approved document (hub/hub/spec_service.py:195-199), so what a reviewer learns never reaches the spec and the spec drifts from what was built. A flow's review turn reads code and evidence (scheduler._compose_loop_briefing, hub/hub/scheduler.py:3127-3132; the review turn-context, hub/hub/api/v1/agents.py:1997-2025) but is never asked to drive the running product. Tasks enter a flow only at approval (spec_tasks.materialise, called only from api/v1/spec.py:2380). The research the roadmap rests on finds that agents game the checks they can edit: Claude models cheated mainly by modifying tests, and prompts barely help (testbed/research/reports/Spec driven development with agents.md, ImpossibleBench and METR), so a tester allowed to amend criteria must not be able to pass the criteria it relaxed. There is no cannot-satisfy outcome anywhere (task blocked with a free-text reason is the nearest, task_transitions.py:112-133).

Scope

In scope

  • delivery.tester: absent or null means testing is on and staffed like the reviewer; an agent name staffs the flow's review turns with that agent first; false turns testing off
  • The test turn's briefing: drive the running product against the task's criteria, review code and evidence, amend within the stated criteria, side findings outside the flow
  • An agent tool to amend an approved document with structured operations (add a task, add a criterion, change a criterion, remove a criterion), each with a reason and how to check it, allowed only to a run delivered to test a task of that document
  • Amendments recorded as Hub-owned events with author and run, not reviewed until the operator marks them reviewed per item or per document
  • Additions take effect at once; an added task is materialised into the document's live flow
  • A change or removal of a criterion is a relaxing amendment: its requirement cannot be verified while it is not reviewed
  • An agent tool to report that a criterion cannot be satisfied, recorded as an amendment, blocking the builder's task
  • Unreviewed amendments as an approval gap
  • The document page lists the amendments with author, run, how to check, reviewed or not, and marks them reviewed

Non-goals

  • Adding a new requirement by amendment: findings stay within the stated criteria; a new requirement is a reopen and a new approval
  • Judging whether a criterion change is stricter or looser by reading it: every change or removal counts as relaxing
  • A separate test turn beside the review turn
  • Reconciling code with the spec before fold (slice reconcile-and-measure)
  • Changing an operator's edits: the operator still reopens to edit an approved document

Requirements

FR-1# Requirement 1 of 9

MUST A flow document's review turns MUST be test turns unless its delivery sets tester to false; when delivery.tester names an agent, the flow MUST staff a task's review with that agent before delivery.reviewer, and a task's own reviewer MUST still come first.

WhyOn by default (roadmap slice); absent means on, so no stored payload changes.

FR-2# Requirement 2 of 9

MUST A test turn's briefing MUST tell the agent to drive the running product against the task's criteria as well as review code and evidence, to amend the document only within its stated criteria, and to put side findings in a task outside the flow; a review turn with testing off MUST NOT carry it.

WhyA reviewer prompted to find gaps reports some (research, over-reporting).

FR-3# Requirement 3 of 9

MUST An amendment MUST be accepted only from a run delivered to test a task of the amended document while its testing is on; any other caller, the task's builder included, MUST be refused with 403 amend_not_tester and nothing changes.

WhyThe builder never edits criteria: it is the agent being judged (ImpossibleBench).

FR-4# Requirement 4 of 9

MUST An amendment MUST be one of add_task, add_criterion, change_criterion or remove_criterion; it MUST name only requirements and criteria the document already holds, carry a reason and a how_to_check, and be applied to the approved document at once; an added task MUST be materialised into the document's live flow.

WhyAdditions take effect at once and become tasks the implementer picks up (roadmap slice).

FR-5# Requirement 5 of 9

MUST Each amendment MUST be recorded with its operation, target, reason, how_to_check, author and run, as not reviewed, and MUST stay not reviewed until the operator marks it reviewed, either by its id or for the whole document.

WhyAgent-amendment provenance; mark reviewed per item or per document (roadmap slice).

FR-6# Requirement 6 of 9

MUST A requirement with a not-reviewed change_criterion, remove_criterion or cannot_satisfy amendment MUST NOT be verified, whatever evidence it holds, and MUST report the state amendment_unreviewed; once the operator marks the amendment reviewed its evidence MUST count again.

WhyMarking alone is not enough: a relaxing amendment cannot satisfy until a human has looked (research).

FR-7# Requirement 7 of 9

MUST A run working or testing a task of the document MUST be able to report that a named criterion cannot be satisfied, with a reason; the report MUST be recorded as a not-reviewed cannot_satisfy amendment and a builder's task in progress MUST move to blocked with that reason.

WhyAn explicit flag-for-human exit cut cheating from 54% to 9% (ImpossibleBench).

FR-8# Requirement 8 of 9

MUST Approving a document that holds not-reviewed amendments MUST list them as the gap amendments_unreviewed.

WhyThe approval-warnings slice left this gap to this slice.

FR-9# Requirement 9 of 9

MUST In the app, an approved document MUST list its amendments with operation, target, author, run, reason, how to check and whether reviewed, and MUST offer Mark reviewed per amendment and for all.

Design

Tier 2: a new agent write path to approved documents and a change to what counts as verified (cross-cutting, trust-bearing). No migration: amendments are spec-document events (kind free, detail JSON, append-only, hub/hub/db/models.py:2128-2167). No Hub-restart hazard beyond the code itself. Rollback: revert; the events stay inert.

D1. Amendments are structured operations through their own agent tool, applied to the approved document at once and recorded as Hub-owned amendment events; review is an amendment_reviewed event naming the ids. Rejected: a new table (a migration for what the event log already is), marks in the payload (agents write the payload and could erase the operator's record), and SpecEditProposal (pending until accepted, the opposite of taking effect at once). (morning-1009-1) D2. Only a run delivered to test a task of this document may amend, read from the run's queue entries (run_task_binding.review_task_for_run). Rejected: matching the caller's name to delivery.tester (a name is not the turn) and letting any agent amend. (morning-1009-2) D3. Relaxing is structural: every change_criterion, remove_criterion and cannot_satisfy blocks verification until reviewed; additions never do. Rejected: judging stricter-or-looser by reading, which is a guess the motivated agent writes. (morning-1009-3) D4. Testing is on by default without a stored field: absent or null tester means the review turn is a test turn, staffed by the existing reviewer ladder; a name goes before delivery.reviewer; false turns it off. Rejected: a separate test turn after the review (doubles turns per task) and a required field (rewrites every stored payload, spec_payload.py:592-598). (morning-1009-4) D5. Amendments stay within stated criteria: they name existing requirements and criteria only; a new requirement is a reopen. Side findings go to a task outside the flow. (morning-1009-5) D6. cannot_satisfy is its own tool and an amendment kind: recorded, not reviewed, blocks the requirement's verification and blocks the builder's task in progress. Rejected: ask_user, which asks rather than records a judgement the evidence rule can read. (morning-1009-6) D7. Amendments bypass contract/gate edit proposals: they have their own review. The operator's own edits still go through reopen.
