Summary

A turn opened on a specification document starts its Codex app-server thread read-only in every posture, declines every file change and sandbox escape that is not the Hub's own call, and keeps the Hub's own call (the arguments file and aw-tool) and its MCP tools. Today the restriction never reaches app-server, Codex's default transport (F462).

Problem

F4's rule, that a turn triggered with a specification document open loses file-write tools regardless of phase, rigor or posture, is applied as restrict_spec_writes=bool(spec_document) on the runner request. codex exec honours it with --sandbox read-only (runner_commands.py). app-server reads no argv, and CodexAppServerTransport.run_turn passes neither the flag nor anything derived from it, so the thread starts under the posture's own sandbox (workspace-write, or danger-full-access under Full access) and a Codex agent on a spec turn can write files. Found from code in each-runner-cli-is-one-adapter R2 (D11), confirmed by its Opus review, never driven.

Scope

In scope

  • The thread policy a Codex app-server turn starts under when a specification document is open
  • The Hub's answers to that thread's sandbox approval requests (command execution, file change)

Non-goals

  • codex exec, which already starts --sandbox read-only
  • Claude and Copilot spec turns, governed by their own adapters
  • MCP elicitation, whose answer (the Hub's own server only) is unchanged
  • Proving what a real Codex binary does with the policy: Codex is not drivable on this machine (plan cancelled 2026-08-29)

Requirements

FR-1# Requirement 1 of 4

MUST A Codex app-server turn opened on a specification document MUST start its thread with sandbox read-only in every permission posture, with approval policy untrusted under Ask me and on-request otherwise.

WhyThe sandbox is Codex's real write barrier. never is excluded because under it Codex refuses the Hub's own arguments-file write silently instead of asking, and a turn told the call command could not submit the document it was opened on.

FR-2# Requirement 2 of 4

MUST On such a turn the system MUST decline every file-change approval, and every command-execution approval outside Ask me, that is not the Hub's own call, in every posture and without an operator card for a file change.

WhyAn approval is the only way out of a read-only sandbox, so answering it by the posture would hand back what the sandbox took away. Under Ask me a command still goes to the operator, who answers it as today.

FR-3# Requirement 3 of 4

MUST On such a turn the system MUST accept a file change whose every path is a .json file inside the calls root, and a command that is exactly one aw-tool invocation, as mcp_server._hub_own_call defines them, in every posture.

WhyThe one write a spec turn keeps (a-run-reaches-the-hub-without-mcp D16); it is bounded by the run's own credential.

FR-4# Requirement 4 of 4

MUST A turn with no specification document open, and the answer to an MCP elicitation on any turn, MUST behave as before.

WhyThe restriction is the document's, not a narrowing of any posture.

Design

Tier 2 (a permission boundary). Operator approved the design in chat on 2026-10-07 (Approve (Recommended)). Hazard: none to data or the running Hub; no migration, nothing restarts. The behavioural risk is a real Codex binary treating the policy differently from the scripted session (a wrapped command text, or a read-only sandbox blocking aw-tool's network before it asks), which fails closed: the spec turn cannot reach the Hub through the call command, and the MCP form is unaffected. Rollback: revert the commit. Same rules as Copilot's spec turn (copilot_acp._decide_permission: the Hub's own call first, every other edit refused), stricter on commands because Codex has a real sandbox and an approval is a request to leave it. The shell dialect given to _hub_own_call follows the platform Codex runs on (PowerShell on Windows, Bash elsewhere).

Evidence and coverage limits

Checked

  • runner_adapters/codex.py CodexAppServerTransport.run_turn passes no restrict_spec_writes to codex_appserver.run_turn, although RpcTurnRequest carries it
  • codex_appserver._thread_policy reads only yolo and posture
  • codex_appserver.decide_approval answers sandbox approvals by posture alone
  • In the test environment a Codex spec turn is told the shim (aw-tool) access path, so a bare read-only sandbox would cut it off from the Hub

Limits

  • Codex is not drivable on this machine; the real binary's handling of the policy is not observed
