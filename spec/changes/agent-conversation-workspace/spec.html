Specification: Agent Conversation Workspace

Status: DRAFT — awaiting user approval

0 / 0 tasks complete

1. Summary

Make the agent conversation the primary surface of the Hub: reachable in one click from a project-and-agents rail, occupying the whole content area with a single header, and usable while the agent is running. This is row H1 of the Hub-Native Experience roadmap.

The backend for all of this already exists. This change is almost entirely a client-side correction: the shipped interface hides a working merged timeline behind a master-detail list and a tab bar, and it disables the composer for the exact duration in which the durable inbound queue was built to accept input.

2. Problem / Motivation

2.1 The operator cannot talk to a running agent

This is the sharpest problem, and it is a contradiction rather than a missing feature. The approved agent-inbound-queue delta spec requires that entries arriving while an agent is running are queued and delivered at the start of the next turn, and the approved agent-conversation-timeline delta spec requires that operator input submitted during a run appears immediately in an undelivered state and that the operator "may continue submitting further input."

The backend honours this. POST /api/v1/agent/trigger returns status: "queued" with a queue_entry_id, persists a queue_entry_queued event, and broadcasts it over SSE. The chat endpoint appends still-queued entries to the timeline in the undelivered state.

The interface then throws it away. In AgentOutputPanel.tsx, interactionLocked is defined as isRunning || isSending || handoffState === 'preparing' || isBindingNewSession, and that flag disables the textarea and the send button. So during precisely the window the queue exists to serve, the operator is locked out and the placeholder reads "agent is responding…". A durable queue whose only human producer cannot reach it is dead weight.

2.2 The conversation is buried

Reaching a conversation costs four steps: open Agents, pick a filter tab, select an agent from a 240 px master list, then find the Output tab inside the detail panel. The conversation is a tab inside a panel inside a page. It renders two agent headers, one from the page and one from the panel, and the timeline gets whatever vertical space is left.

Meanwhile Messages is a separate top-level destination, even though peer traffic in both directions is already merged into the conversation timeline. The operator is offered two places to read the same records.

2.3 The composer is a single-row input with no memory

The composer is a rows={1} textarea with a 96 px ceiling — roughly four lines — holding its value in component state. Navigating away discards whatever was typed, which the agent-composer delta spec explicitly forbids. Around it sit controls that do not earn their permanent place: a raw session <select> listing truncated UUIDs, a handoff button, and a "Pause scroll" toggle that duplicates what the scroll position already says.

Note: the visual direction for this change was agreed against openspec/changes/2026-07-30-hub-native-experience/mock-full.html. The mock is static and proves layout only; it is a reference, not a contract.

3. Scope & Non-Goals

In scope

  • A navigation rail listing the current project and its agents, replacing the flat page list.
  • Direct navigation from rail or overview roster to a full-height agent conversation, and back to the project in one action.
  • Removal of the Agents master-detail page and the Messages destination from navigation, leaving their records and APIs untouched.
  • Input accepted, submitted, and queued while a turn is running.
  • An autosizing composer with per-conversation drafts that survive navigation and reload.
  • Consolidation of conversation controls into a small visible set plus a keyboard-operable overflow menu.
  • A banner stack above the composer for run failure, stream loss, and blocked-queue conditions.
  • The existing context-usage indicator placed in the composer.
  • A rail data adapter shaped for many projects but populated with the one authenticated project.

Non-Goals

  • Real multi-project switching or project creation. Authentication binds one API key to one project; see roadmap RP-1. No control in this change may imply a second project exists.
  • Composer trigger menus for @path, /command, and $skill. These need a workspace path-listing endpoint that does not exist, and they are roadmap row H2.
  • Changing what a turn receives. Queue semantics, hop budget, per-turn cap, and delivery ordering are unchanged.
  • Changing which agent handles a conversation from inside the composer. The composer shows which agent is active (FR-10); it does not offer a searchable in-place switcher. Once every agent is one click away in the rail, a switcher's remaining value is reassigning an in-flight conversation, which is a change to turn routing rather than to layout. It belongs with the other composer selectors in row H2.
  • Runner records, model reassignment, charters, or templates — roadmap row H5.
  • Specification authoring, requirement traceability, and approval gates — roadmap rows H6 and H7.
  • Token accounting and budgets — roadmap row H4.
  • Deleting message storage, message APIs, or the agents API. Only the navigation destinations go.
  • A permission-mode control. No permission behaviour exists to control yet.
  • A project-level agent directory. Once agents are reachable from the rail and the overview roster, a bulk list has no remaining job; it may return if a real bulk-management workflow appears.

4. Conformance

Producer requirements (allowed inputs)

  • The operator MAY submit text of any length, containing newlines, at any time, regardless of whether the agent is idle, running, or unlaunchable.
  • The operator MAY navigate away from a conversation, to another agent or to the project overview, while unsent text remains in the composer.
  • The operator MAY reload the page at any point, including with unsent text present.
  • The operator MAY select an agent from the navigation rail or from the project overview's agent roster.
  • The operator MAY operate every conversation control using the keyboard alone.

Consumer requirements (required behavior)

  • The interface MUST route input to the existing trigger endpoint unchanged and MUST reflect whichever outcome that endpoint reports — started or queued — rather than predicting it.
  • The interface MUST NOT suppress an input affordance on the basis of agent state that the backend accepts.
  • The interface MUST NOT present an affordance whose backing capability does not exist.
  • The interface MUST preserve every behaviour listed in FR-16 exactly as it behaves today.

7. Behavior / Algorithms

7.1 Submitting composer input

This replaces the current path, whose first step is effectively "if the agent is running, do nothing."

  1. If the composer text is empty or whitespace only, stop.
  2. If a submission for this conversation is already in flight, stop.
  3. Mark a submission in flight and clear the composer text optimistically.
  4. Call the trigger endpoint with the agent, the text, and the current session selection. Do not branch on the agent's running state — the endpoint decides.
  5. If the endpoint reports the turn started, clear the stored draft and let the existing output stream render the turn.
  6. If the endpoint reports the input was queued, clear the stored draft and rely on the queue_entry_queued event and the chat endpoint's undelivered entries to render it; do not synthesize a local entry, because the timeline is built from stored records and must not gain an entry the server did not record.
  7. If the call fails, restore the text into the composer, restore the stored draft, and raise a run-failure banner.
  8. Clear the in-flight mark.

7.2 Draft persistence

  1. Drafts are keyed by agent name, under one namespaced storage key.
  2. On mounting a conversation, read the draft for that agent and seed the composer with it; an absent draft seeds an empty composer.
  3. On every change to the composer text, write the draft for that agent, debounced.
  4. On successful submission, delete that agent's draft.
  5. If storage is unavailable, the composer still functions; only persistence is lost. This mirrors how the rail width is persisted and must never break the surface.

7.3 Autoscroll

  1. Maintain a single derived flag: the operator is at the bottom if the scroll position is within a small threshold of the maximum.
  2. When new content arrives and the flag is set, scroll to the newest entry.
  3. When new content arrives and the flag is clear, do not move the viewport.
  4. Recompute the flag on every scroll event. No manual override control exists, because the operator's scroll position already expresses the intent the control duplicated.

7.4 Control placement

  1. Render submit, the active-agent indicator, and context usage in the composer control row.
  2. If the agent is running, additionally render stop.
  3. Render every remaining conversation action inside the overflow menu, in a fixed order: new conversation, session selection, handoff, fold all, agent details.
  4. If an action is unavailable — for example handoff on a manual runner — present it disabled with its reason, rather than omitting it, so the menu's contents do not shift between agents.

8. Design (How)

The conversation surface stops being a tab inside AgentsPage → AgentDetailPanel and becomes a destination in its own right. App.tsx's flat Page union gains an agent-scoped destination, so the active view is either a project-level view or one agent's conversation. AgentOutputPanel is split: the timeline host stays, and the composer becomes its own component owning drafts, controls, and the banner stack.

No backend change is required. Every endpoint and event this change consumes already exists and is already exercised by tests. 

  Rail (adapter: Project[] — one entry today)
    └─ Project ▾ ──────────────► ProjectOverview
         ├─ agent A ───────────► AgentConversation(agent)
         ├─ agent B                   │
         └─ agent C                   ├── one header  ── back-to-project
                                      ├── AgentTimeline  (unchanged)
                                      ├── BannerStack    (new)
                                      └── Composer       (new)
                                            ├── textarea + draft store
                                            ├── submit / stop
                                            ├── active agent · context usage
                                            └── overflow ▸ new · session · handoff
                                                            · fold all · details

  POST /api/v1/agent/trigger  ──►  { status: "started" | "queued", queue_entry_id? }
  SSE  queue_entry_queued / queue_entry_delivered / agent_output   (all existing)

Key decisions

  • The composer never inspects isRunning to decide whether to accept input. The endpoint already returns which of the two outcomes occurred, and the queue is durable. Any client-side prediction of agent state is a second source of truth that can only be wrong.
  • Queued input is rendered from server records, not optimistically. The agent-conversation-timeline spec requires entries to be placed by recorded association. A locally synthesized entry would violate that and would double-render when the real record arrives.
  • Drafts live in browser storage keyed by agent, not on the server. A draft is unsent operator text with no coordination value; persisting it server-side would create a record other agents could observe. Storage failure degrades to no-persistence rather than breaking the composer.
  • The rail consumes a project collection from day one. Shaping the adapter now costs nothing and means row H3 changes what fills the collection rather than rewriting the rail. Shaping it as a single project would guarantee a rewrite.
  • Messages disappear as a destination, not as a model. Peer traffic is already merged into the timeline, so the destination is redundant; the records remain source data for routing, attribution, and history.
  • Unavailable overflow actions are shown disabled with a reason. A menu whose contents change between agents forces the operator to re-learn it each time.

Security considerations

  • No new endpoint, no new permission, and no change to authentication. The change consumes the same project-scoped bearer credential and the same signed SSE ticket as today.
  • Drafts are unsent operator text held in browser storage on the operator's own machine. They are not transmitted and not shared between agents. Draft keys are namespaced and keyed by agent name, which is already constrained by ^[a-zA-Z0-9_-]{1,32}$, so a key cannot be forged into another namespace.
  • Removing navigation destinations does not remove authorization checks; the underlying endpoints keep their existing dependencies.
  • No new runtime dependency is introduced.

Coverage limits

  • No test currently asserts that the composer accepts input while an agent is running. That gap is why the contradiction between the shipped interface and agent-inbound-queue survived phases 6–8. It is closed by T6.
  • No test currently asserts draft persistence; agent-composer's "draft survives navigation" scenario has never been exercised.
  • The visual direction comes from a static mock. It proves layout at one viewport and proves nothing about live data, streaming, or state transitions.
  • Backend behaviour is taken as given from reading the endpoints and their existing tests; this change adds no backend test because it adds no backend behaviour. If applying it reveals that the trigger endpoint's queued path is untested, that test belongs to this change.
  • Accessibility beyond keyboard operability of the overflow menu (FR-10) is not specified here and is not claimed.

10. Spec Lifecycle

Model: flow-forward. spec/changes/agent-conversation-workspace/ is frozen at archive time and becomes history. Corrections before archive are made here; corrections after archive belong to a new change.

Reconciliation rules:

  1. On approval, this document is the authority for the behaviour it defines. Where it conflicts with phases 9–16 of the openspec umbrella, this document wins.
  2. Phases 10 (partially), 11, and 12 of openspec/changes/2026-07-30-hub-native-experience/tasks.md are annotated as superseded by roadmap row H1, naming this spec. Superseded tasks are not marked complete — only real implementation closes work, and it closes it here.
  3. The delta specs agent-inbound-queue, agent-conversation-timeline, and agent-composer remain authoritative for the behaviour they describe. This spec brings the interface into conformance with them; it does not restate or amend them.
  4. On archive, roadmap row H1 moves to done and this document's entry in spec/index.json is updated to its archived path.
