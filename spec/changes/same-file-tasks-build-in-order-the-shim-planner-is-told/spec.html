Summary

Slice 1 shipped `files` and the overlap warning, but a planner that reaches the Hub through `aw-tool` never reads the text that teaches them. This follow-up puts the rule, worded as a per-task step, where that planner reads, and lets it ask `aw-tool` for a tool's whole description.

Problem

Slice 1's acceptance drive failed (scripts/drive/FINDINGS.md F509). On a fresh Hub with the merged code, a real Haiku planner was asked twice for three features that all edit one file. Both times it left the tasks unordered and declared no `files`; the response carried `"warnings": []`, so the plumbing works and nothing could trigger it. Reading the code shows three places a shim planner can learn about the tool, and slice 1 reached only the one it does not read. (1) `aw-tool --list` prints only the first line of each tool's description (`_call_listing`, hub/hub/mcp_server.py), so the full `submit_spec_document` docstring, which holds the `depends_on` rule and the only documentation of `files`, is unreachable; `aw-tool --help` ignores any further argument and prints one fixed usage text. (2) The tool section of the turn prompt, rendered for the shim by `_shim_lines` from `_operations()` (hub/hub/api/v1/agents.py), lists `tasks` as an argument name and says nothing of `depends_on` or `files`. (3) The exploring duty (`SPEC_PHASE_DUTIES["exploring"]`) does reach the planner and carries slice 1's "Order the tasks" sentence, which the planner did not follow: it states a principle ("may name... chained") not a step the planner performs for each task.

Scope

In scope

  • Exploring duty text restated as a per-task step covering `files` and chaining shared-file tasks with `depends_on`
  • The `submit_spec_document` entry of the rendered tool section names `depends_on` and `files`
  • `aw-tool --help <tool>` prints a tool's complete description
  • The run's tool-access notice tells a shim run that `--help <tool>` exists
  • Tests at the seam where the text is produced; the end-to-end drive is named but run by the operator after merge

Non-goals

  • Changing the overlap check, the `files` validation, dependency_gate, the scheduler or merge behaviour
  • Refusing a proposal because of an overlap (warn only, as in slice 1)
  • Changing the shape or content of `aw-tool --list`
  • Inferring files from descriptions (roadmap slice flag-missed-overlap)
  • A database migration, or any need to restart the Hub that is orchestrating the build
  • Running the end-to-end drive inside this slice
  • Guaranteeing that a given model follows the text: the tests show the text reaches the planner, the drive shows whether it acts on it

Design

Decisions, each with its reason.

D1. Two places the planner always reads get the rule: the exploring duty, and the `submit_spec_document` entry in the tool section (`_operations()` text, shared by the MCP, shim and HTTP renderings, so one edit covers every access path). Reason: a planner follows what is in its prompt; it does not go looking. Slice 1's own evidence is that the duty sentence was read and ignored, so the wording changes too: from a principle to a per-task step ("for each task you write, list in `files` the repo-relative paths it will edit; where two tasks share a path, chain them with `depends_on`"), placed where the planner decides its tasks.

D2. `aw-tool --help <tool>` prints that tool's complete description; `--list` keeps its shape. Alternative considered: put every full description into `--list`. Rejected: it multiplies the size of the one listing every run may call, and it changes a payload that is read for names and arguments. The recommendation can be overturned at approval. The run's tool-access notice (hub/hub/launchability.py) is told the form exists and that `--list` shows only a first line, because nothing else tells a planner to ask.

D3. No restart while the slice builds. Edits to mcp_server.py and agents.py reach agents only on a Hub's next start (the tool server is pinned per Hub); the build touches code and tests only, and the end-to-end drive runs on a fresh Hub after merge.

Acceptance drive (the operator's, after merge, not run inside this slice): a fresh Hub, a real Haiku planner on the shim path, asked to draft a slice of three features that all edit one file. Pass condition: those tasks are chained with `depends_on`, or the submission's response carries an `unordered_file_overlap` warning naming them. It fails today (F509: two of two runs left them parallel and declared no `files`).

The two tasks are disjoint by file (agents.py; mcp_server.py and launchability.py), so neither needs ordering. Their files are named in each description because the Hub serving this authoring turn predates slice 1 and refuses a `files` field; they carry no `files` list for that reason only. Each names aw-reviewer as reviewer, and each is to run `black --check --target-version py311` and `ruff check` on the files it touched before completing.

Evidence and coverage limits

Checked

  • hub/hub/mcp_server.py `_call_listing` and `call_main`: `--list` keeps only the first docstring line; `--help` returns a fixed usage text and ignores a following tool name
  • hub/hub/api/v1/agents.py `_shim_lines`, `_operations()` (submit_spec_document text) and `SPEC_PHASE_DUTIES['exploring']`: the shim's tool section carries no mention of `depends_on` or `files`; the duty states ordering as a principle
  • hub/hub/launchability.py tool-access notice: names `--list` as listing every tool and its arguments, and no `--help <tool>`
  • scripts/drive/FINDINGS.md F509 (on master): two of two real Haiku runs left same-file tasks parallel with no `files`; the duty sentence was present in the transcript and not followed

Limits

  • Tests prove the text reaches the planner's prompt and that `--help <tool>` works; they do not show a model follows the step. Only the acceptance drive shows that, and it is the operator's after merge.
  • Whether the planner would ever run `aw-tool --help <tool>` unprompted is untested; D1 does not rely on it, and FR-4 only tells it the form exists.
  • Agents read the new text only after a Hub restart (pinned tool server, duty text loaded at start); this was not exercised here.
  • My worktree predates slice 1 (it lacks the `files` field and F509); I read the merged code and F509 from master with git show, not from a running Hub.
