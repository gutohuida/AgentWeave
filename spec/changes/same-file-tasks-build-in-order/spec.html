Summary

A planner drafting a slice is told to chain tasks that edit the same files with depends_on, can declare each task's expected files, and gets a non-blocking warning when two unordered tasks overlap.

Problem

Parallel tasks of one slice that edit the same files conflict after the first merges (F504, F506: review rounds per task 1/4/2, the extras being merge conflicts). The ordering mechanism exists (depends_on, gated by dependency_gate and the flow claim) but the planner is not told about it: the submit_spec_document description of `tasks` lists key, description, requirements and title only (hub/hub/mcp_server.py), the only explanation of depends_on is a schema field description the untyped tool never shows (hub/hub/spec_payload.py), and the exploring duty text (hub/hub/api/v1/agents.py SPEC_PHASE_DUTIES) says nothing of ordering. Nothing records which files a task expects to touch, so nothing can notice an unordered overlap.

Scope

In scope

  • Documenting depends_on and the shared-file rule in the submit_spec_document tool description and the exploring duty text
  • An optional per-task list of expected files
  • A non-blocking overlap warning in the submission response
  • Tests at the validation seam; the end-to-end drive is specified but run by the operator after merge

Non-goals

  • Refusing a proposal because of an overlap (warn only)
  • Inferring files from task descriptions or from real changes (roadmap slice flag-missed-overlap)
  • Counting conflict-caused review rounds (roadmap slice measure-conflict-rounds)
  • Changing dependency_gate, the scheduler, or merge behaviour
  • A database migration, or any need to restart the Hub that is orchestrating the build
  • Running the end-to-end drive inside this slice

Requirements

FR-1# Requirement 1 of 4

MUST The submit_spec_document tool description and the exploring-phase duty text each state that a task may name sibling tasks in `depends_on`, and that tasks expected to edit the same file are chained with it rather than left parallel.

WhyThe planner cannot use an ordering mechanism it was never shown; today neither place mentions depends_on.

FR-2# Requirement 2 of 4

MAY A task declared in a document may carry a `files` list of repo-relative paths it expects to edit. A document with `files` on its tasks is accepted and stored unchanged, and a path that is empty or absolute is refused naming the task. A directory path covers every path beneath it.

WhyWithout a declared set nothing can notice an unordered overlap. Directory coverage is chosen so that two tasks editing different files in one package are still reported.

FR-3# Requirement 3 of 4

MUST When two tasks declared in one document have overlapping `files` and neither can reach the other through `depends_on`, directly or transitively, the submit_spec_document response carries a warning naming both task keys and an overlapping path, and `ready_to_propose` is not made false by it. No warning is given for a pair that is ordered by `depends_on`, for a task that declares no `files`, or for an imported task entry.

WhyWarn rather than refuse: declared files are an estimate, and a wrong one must not block a legitimate plan. A warning that fires on correct plans teaches the planner to ignore it.

FR-5# Requirement 4 of 4

MUST The change adds no database migration.

WhyThis repository runs the Hub that orchestrates the build; a migration runs at its next restart on live data.

Behaviour

Overlap check

  1. Take the locally declared tasks that declare at least one file.
  2. Compute, for each task, the set of tasks reachable through depends_on, transitively.
  3. For each pair neither of which reaches the other, find a path in one list equal to, or beneath, a path in the other.
  4. For each such pair report one warning with both keys and one overlapping path.

Design

Guidance and a warning, not enforcement. The planner is told in the two places it reads (the tool description and the exploring duty) that tasks expected to edit the same file are chained. A task may declare the files it expects to edit; at submission the Hub reports any pair of tasks whose files overlap with no dependency path between them. The report is a warning because declared files are the planner's estimate, and a wrong estimate must not block a legitimate plan (operator decision, 2026-10-06). The files list lives in the stored document payload, so no migration is needed. Python changes, including the tool server copy in mcp_server.py, take effect at each Hub's next restart; nothing here needs a restart while the slice is being built. The new tool text and the overlap warning reach agents only after a Hub restarts on the merged code, and the Hub orchestrating this build must not restart, so the end-to-end drive is not a task of this slice: the operator runs it after both tasks merge, on a fresh Hub. Drive: a planner drafts a slice whose tasks share a file; the submission must either chain them or return the overlap warning, and the review rounds per task are recorded against F504. Open follow-ups, recorded in the roadmap and not built here: counting conflict-caused rounds, and flagging overlaps from real changed files.

Evidence and coverage limits

Checked

  • hub/hub/mcp_server.py: the tasks description omits depends_on (grep finds no occurrence in the file)
  • hub/hub/spec_payload.py:128: depends_on explained only in a field description; the tool takes untyped dicts
  • hub/hub/api/v1/agents.py:1712: exploring duty text has no ordering guidance
  • hub/hub/dependency_gate.py and hub/hub/scheduler.py:733: a task cannot start until its prerequisites are approved, in the flow claim as well
  • hub/hub/task_workspace.py:160: a task's workspace is cut from the integration base at start, so a dependent starts after its prerequisite merged
  • hub/hub/spec_tasks.py:202: tasks are read from the payload dict, so a payload field needs no column

Limits

  • Proposed coverage only: every acceptance criterion is derived from this document, none from behaviour watched running
  • The end-to-end drive cannot pass inside this slice: the new tool text and warning reach agents only after a Hub restarts on the merged code, and the orchestrating Hub must not restart during the build; the operator runs the drive on a fresh Hub after both tasks merge
  • Declared files are the planner's estimate; an overlap it did not predict is not caught here (roadmap slice flag-missed-overlap)
  • Whether the tool server copy of mcp_server.py reaches agents only after a restart is taken from .claude/rules/mcp-server.md, not tested
  • Chaining tasks trades wall-clock time for fewer review rounds; that trade is not measured here (roadmap slice measure-conflict-rounds)
