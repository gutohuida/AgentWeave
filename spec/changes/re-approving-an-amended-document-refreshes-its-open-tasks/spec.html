Re-approving an amended document refreshes its open tasks

change-specarchivedsketch

4 MUST·4 requirements·4 criteria·3 tasks

Summary

When an amended document is approved again, a task it already created and still declares is brought up to date if it is still open: its title, description, criteria and its links to this document's requirements become what the document now says. Status, assignee and links to other documents are never touched; closed tasks stay as delivered. The approval report says what changed, which closed tasks still link a retired requirement, and which tasks the document no longer declares.

Problem

F535: reopening F532's approved document, retiring FR-3 and adding FR-5, then approving again created no task and changed none. The backend task kept its first title and its link to the retired FR-3, and FR-5 was served by no task until the operator linked it by hand. Coverage showed a new requirement unserved while a task claimed a retired one. task-lifecycle-governance says a task that already exists for a declared task SHALL NOT be modified by a later approval; that freezes the description of the work along with its progress.

Scope

In scope

  • Refreshing an open declared task's title, description, acceptance criteria and same-document requirement links at re-approval
  • Reporting refreshed tasks, closed tasks linking a retired requirement, and tasks the document no longer declares
  • Showing those three in the approval report in the app

Non-goals

  • Changing a task's status, assignee, priority or dependencies' removal: progress and who does the work stay the board's
  • Touching an approved or rejected task: it records what was delivered against what was asked then
  • Deleting or closing a task the document no longer declares: reported, the operator decides
  • Touching links to requirements of other documents, or free-text requirement notes

Requirements

FR-1# Requirement 1 of 4

MUST When a document is approved and a task it created earlier is still declared under the same key and is neither approved nor rejected, approval MUST set that task's title, description and acceptance criteria to what the declared entry now gives, and its links to this document's requirements to exactly the requirements the entry names. Its status, assignee, priority and its links to other documents' requirements MUST NOT change.

WhyThe document declares what the work is; a revision that changes what is asked must reach the open work, or coverage reports a new requirement unserved while a task claims a retired one. Progress and assignment remain the board's, so re-approving still cannot reset or reassign work.

FR-2# Requirement 2 of 4

MUST A task that is approved or rejected MUST NOT be changed by a later approval of its document.

WhyA closed task records what was delivered or turned down against what was asked at the time.

FR-3# Requirement 3 of 4

MUST The approval report MUST list each refreshed task with the fields that changed and the requirement links added and removed, each closed task that links a requirement this document has retired, and each task this document created whose key it no longer declares; none of these MUST be changed beyond the refresh rule.

WhyAnything a re-approval changed or chose not to change must be visible where the operator decided it.

FR-4# Requirement 4 of 4

MUST The approval report in the app MUST show refreshed tasks, closed tasks linking a retired requirement, and tasks no longer declared.

WhyThe report is where the operator sees what approval did to the board.

Design

Tier 1, no migration. Operator decision 2026-10-08: refresh open tasks (rejected: additive links only; report only). Open means status is neither approved nor rejected. Links are set by diff, so an unchanged task is not reported and a link the entry still names keeps its row and actor. Removed links are deleted rows; the approval report event is their record. Folds into task-lifecycle-governance, replacing the requirement that says an existing declared task SHALL NOT be modified. HAZARD: the UI bundle reaches :8000's app at its next reload. Rollback: revert.
