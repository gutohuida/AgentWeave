Roadmap: Hub-Native Experience

Status: LIVING — decomposition of the remaining hub-native epic

1. Purpose

This roadmap decomposes what remains of the 2026-07-30-hub-native-experience change into independently approvable, independently testable capabilities. That change began as a single umbrella covering runtime ownership, the inbound queue, the conversation timeline, agent identity, visual language, the composer, and the entire specification program. Phases 1–8 are complete. The remaining 69 checklist items span eight phases and at least five unrelated outcomes, which is more than one approval gate can honestly cover.

Each row below states its intent, an explicit in/deferred boundary, its dependencies, its status, and the path to its child specification. A child spec MUST stay inside its row's boundary. Shared API, event, or schema changes belong to an explicit contract task referenced by both rows, never duplicated across siblings.

Note: this roadmap is non-normative about how anything is built. It is normative only about what belongs in which slice and in what order.

2. Completed foundation

The following are implemented and verified, and every row below may assume them. They are recorded here so no child spec re-specifies them.

  • Native Hub runtime; the Hub spawns agent processes directly and owns their lifecycle.
  • Direct, synchronous trigger with an observable outcome; execution_confidence and the synthetic-message trigger protocol are gone.
  • Durable inbound queue with typed origin, hop depth, delivery state, per-turn delivery cap, and stop semantics.
  • Merged, typed conversation timeline assembled from recorded turns, output, queue entries, and messages — never from timestamp proximity.
  • Stable per-agent identity colours; peer-message tinting; withdraw and deliver-now.
  • SSE as the live-state channel, including queue_entry_queued and queue_entry_delivered.
  • Context-usage recording end to end: record_context_usage on the backend, context_usage on the agent summary, and a rendered ContextUsageIndicator with a compact variant.
  • Workspace isolation, agent tool surface, and the feel foundation (self-hosted variable fonts, motion layer, single icon system, resizable persisted panes).

Warning: the older reconstruction roadmap still reports rows R1–R6 as planned with no child spec authored. That is stale with respect to the code and MUST NOT be used as a current task ledger. It describes a from-scratch regeneration exercise, which is a different epic from this one.

5. Research prerequisites

Two rows cannot be specified from the existing material. Each needs a discovery pass whose output is a decision, not an implementation.

RP-1 — Operator identity versus project-scoped authentication

Authentication today binds one bearer API key to exactly one project: _project_from_api_key resolves a key row to a single project_id, and the SSE ticket is signed as {project_id}:{expires}. Every request and every event stream is therefore scoped to one project for the lifetime of the credential, and the local setup endpoint hands back the first non-revoked project key.

A project switcher is consequently not a sidebar feature. It requires deciding what an operator is when they are not a project, how a session selects a project, whether one credential may span projects or the client holds several, and how the SSE stream is torn down and re-established on a switch without dropping events. Until that is decided, any multi-project affordance in the interface would be a claim the backend cannot honour.

Output: a technical exploration under spec/discovery/multi-project-access/technical.md, then the H3 child spec.

RP-2 — Specification file authority

Two specification systems currently coexist: Markdown deltas under openspec/ and authoritative portable HTML under spec/ with a manifest at spec/index.json. The specification program in H6 introduces stable requirement identifiers, evidence records, proposals, and live verification state — all of which need one unambiguous home.

The recommended architecture, carried forward from the planning session, is that portable files remain authoritative while the database acts as an indexed read model for requirement identity, links, evidence, proposals, and live state. That recommendation is not yet a decision. Building the Accept/Reject/Discuss authoring surface before settling it would force a second migration once identifiers and evidence need to survive an external edit.

Output: a decision on file authority, stable identifier format, revision and proposal concurrency, and external-edit reconciliation, then a sub-roadmap for H6.

6. Epic non-goals

  • Not forking T3 Code, and not reimplementing its event-sourced orchestration engine.
  • Not adopting Effect-TS, a monorepo layout, or typed RPC over WebSocket. FastAPI, SSE, React Query, and Zustand stay.
  • Not building Electron, iOS, Android, or a hosted relay.
  • Not rebuilding the coordination primitives — tasks, messages, jobs, and quality gates stay as they are except where they touch the trigger path.
  • Not changing the CLI's local or git transports. This epic concerns Hub-managed agents.
  • Not multi-user accounts, permissions, or sharing. H3 is one operator with several projects.

7. Relationship to the openspec umbrella

openspec/changes/2026-07-30-hub-native-experience/ remains the record of phases 1–8 and the source of the ten delta specs. Its phases 9–16 are superseded by the rows above. To avoid two live ledgers, the following rule applies:

  1. A phase whose work is fully claimed by a roadmap row is annotated in tasks.md as superseded, naming the row.
  2. A superseded task is never marked complete on the strength of the child spec existing — only real implementation closes a task, and it closes it in the child spec.
  3. The ten delta specs under specs/ stay authoritative for behaviour already implemented in phases 1–8; a child spec references them rather than restating them.
  4. When every row reaches done, the umbrella change is archived and its delta specs are synced.

Warning: two delta specs describe behaviour the shipped interface does not yet honour. agent-inbound-queue requires operator input submitted during a running turn to enter the queue and appear immediately as undelivered, and agent-composer requires a draft to survive navigation. Neither holds today. H1 closes both; until it lands, those specs overstate the system.
